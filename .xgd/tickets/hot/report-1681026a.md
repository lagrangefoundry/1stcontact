### Why this overlap is acceptable

The survey read two serving surfaces. There are in fact **three**, and each has a
distinct audience, trust boundary and set of obligations:

| Surface | Implementation | Owner | Audience |
|---|---|---|---|
| Public delivery Worker | `apps/public-site/src/` (own `routes.ts`, `content-type.ts`, `site-store.ts`) | CAP-82 / STORY-95 | Public visitor |
| Standalone local preview server | `tools/generate/src/cli/serve.ts` | CAP-82 / STORY-96 (local half) | Author previewing |
| Builder workspace origin | `tools/generate/src/cli/builder.ts` | CAP-85 / STORY-99 | Operator working on a site |

The obligations that *look* duplicated are, on inspection, opposite or disjoint —
which is the strongest available evidence that the boundary is real rather than
tolerated:

- **Caching is contradictory by design, not duplicated.** Public delivery is
  cacheable — `public, max-age=31536000, immutable` for snapshot-addressed bytes
  and `public, max-age=60` for published ones (`apps/public-site/src/index.ts`;
  AC-909, AC-911). The workspace origin is `no-store, must-revalidate` on every
  response including the document (`serve.ts` `NO_STORE`; AC-977), because it
  rewrites its own bytes underneath the browser. Merging these capabilities would
  force one policy onto two surfaces that require opposite ones.
- **Confinement guards different threats.** CAP-82's is a multi-tenant *address
  grammar* plus a servable store tree fixed in the server, defending against a
  stranger crafting a URL toward another tenant or the non-servable tree (AC-907,
  AC-927). CAP-85's is filesystem-tree confinement across three local trees,
  answered by clamping (AC-978). Neither substitutes for the other.
- **Content typing is claimed only by CAP-82** (AC-908, AC-920). CAP-85 has no
  content-typing criterion at all.

No AC pair across the two capabilities asserts the same behaviour, so there is
nothing to merge and no story is misfiled.

### Known code sharing that crosses the boundary (already documented, not a defect)

`builder.ts` imports `NO_STORE`, `resolveStaticFile` and `sendFile` from
`serve.ts`. That is deliberate: the resolver's own comment states the reason —
the builder origin serves several static trees and "one implementation, so a
traversal guard can never be present on one tree and missing on another."

Two behaviours therefore leak across the capability line as *inherited but
unclaimed*:

1. **Freshness.** The non-cacheable directive was added to the shared send path,
   so the standalone preview server acquired it too. STORY-99's technical context
   already records this under "Divergence flagged, not absorbed", and explicitly
   declines to claim it as a criterion — the correct handling.
2. **The clean-URL mapping.** `resolveStaticFile` carries the extensionless →
   `.html` fallback, so the workspace origin inherits it. STORY-96's ACs scope
   themselves precisely to the two surfaces they mean — AC-915 "In local preview",
   AC-916/AC-923 "On the deployed site" — and claim nothing about the workspace
   origin; STORY-99 claims nothing about the mapping either.

In both cases shared *implementation* crosses the line while the *claims* stay on
their own side. That is capability boundaries working as intended: a module may be
reused, but each capability remains answerable only for the behaviour it asserts.
Neither leak is ambiguous ownership, so neither warrants a reassignment.
