### Exclusivity

No two ACs describe the same criterion. The four pairs close enough to warrant
checking, and why each survives:

- **AC-1478 / AC-1480** — both end at "a freshly migrated database works", but by
  different mechanisms with different failure modes: AC-1478 fails if the
  `config` ALTER is dropped, AC-1480 fails if register-if-absent is dropped.
- **AC-1479 / AC-1480** — AC-1479's distinctive claim is the *two independently
  obtained handles*; AC-1480's is the empty-registry bootstrap.
- **AC-1483 / AC-1484** — read barrier (fetch + listing) vs write barrier
  (refusal + target unchanged).
- **AC-1489 / AC-1490** — separation vs repetition. STORY-127's Technical Context
  names this split deliberately: a general both-halves criterion already exists
  elsewhere in the matrix, and neither it nor the site store's own criterion says
  a second store exists or why it must not be the public one.

## Notes for the Editor

**Nothing blocks this level.** Zero violations, zero needs_review. Both warnings
are AC-text widenings on criteria that are already correct as far as they go, and
neither implies a code change — I checked both against the implementation before
writing them up.

**Warning 2 is the one worth doing first.** It is the only finding where the
current AC text would let a real regression through: AC-1483's verification steps
can all pass while the scoped handle re-exposes a re-scoping operation, which is
the exact barrier STORY-126's body names. Warning 1 is genuine completeness
tidying with no such hole behind it — the `origin` enum refuses out-of-set values
today by the same mechanism as its two siblings.

**Both warnings are `ac-edit`, not `ac-add`.** Each extends a criterion that
already owns the claim. Adding a fourth enum-refusal AC or a second
account-barrier AC would split one claim across two criteria and create the
exclusivity problem this check exists to prevent.

**This matrix is unusually well-anchored, and that is worth recording.** Every
criterion that goes beyond REQ-162's own acceptance list is labelled as a
reconciliation decision in its story body, dated, and given the reason the
landed code settles it that way — and each of the eight such decisions I spot-
checked resolves to a named line in `apps/control-app/src/tickets.ts`,
`tools/generate/src/cli/assets.ts`, `tests/support/ticketing-installed.ts` or
`apps/control-app/wrangler.toml`. The two places the matrix overstates the landed
evidence (finding 3) are disclosed by the matrix itself rather than found by this
check. A future check should treat the Reconciliation Decisions sections as
load-bearing and not as prose.

**Pre-empting one false positive at the `uat` level.** The AC-1477 evidence lives
in `tests/reconciliation-product-ticket-store-schema.test.ts`, which does not
match the `test_UAT_AC<number>_*` convention, and the AC-1476/1489/1490 evidence
lives in `test_UAT_FC_REQ-162_ticket_store_bindings.test.ts`, which is REQ-keyed
rather than AC-keyed. A `uat`-level coverage check that greps only for
`test_UAT_AC1477_*` will find nothing and report a gap that is not there. The
suites exist; the naming is REQ/reconciliation-keyed from the free-coded landing.

**Two gates are environment-conditional, not absent.** The AC-1477 and AC-1485
skip paths are reached when `@lagrangefoundry/ticketing` is absent or predates
the `BlobStore` port. A run in that state reports those two checks as named
skips, which is the behaviour AC-1477 and AC-1485 specify rather than a failure
to assert them. Do not read such a skip as a violation.
