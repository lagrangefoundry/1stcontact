## Why

On production, 2026-10-28, a Site consultant turn on the 1st Contact site (design, page plan, builder pass and checks) was killed by Cloudflare at 21:34:12Z with **`exceededCpu`**: 303,344 ms of CPU against `cpu_ms = 300000`, the Workers maximum, over 13.8 minutes of wall time (BUG-312's finding). The limit can't be raised, so long turns have to fit.

A `Delegate` runs the builder as a second session inside the same `SessionManager` and the same request (`@lagrangefoundry/ai`, `delegation_toolbox.js`). So the consultant's work and every builder pass, with its renders, layout checks and design validation, count against one request. Waiting on the model is wall time, not CPU, so the 303 s is our own code.

BUG-312's automatic carry-on stays as the general safety net for deploys, evictions and the like. This ticket is the structural fix.

## What

### Phase 1 — measure where the CPU goes

- Replay the lost turn (`turn_c0dee7acc77c135e6c7e03f61df4ea86`, biz `biz_51a6746495c8057e886ff98d4208e6b9`), or a faithful copy, against a snapshot Worker under a CPU profiler (`wrangler dev --inspect` / workerd profiling, or the existing replay-a-live-request harness).
- Attribute CPU to:
  - the consultant's own model loop: transcript assembly, priming and serialisation;
  - each tool call, in particular the builder's renders, `layout-check`, `describe_page`, design validation and page assembly;
  - the delegation bookkeeping.
- Record the breakdown here: the top contributors, with their share, and whether any single step is near the limit by itself.

### Phase 2 — choose the split from the measurement, and record why

- **A. Move heavy tools out:** run the dominant steps in their own invocation (a Durable Object, or a Worker service binding to self), so each call has its own CPU budget. 1stcontact only.
- **B. Run each builder session in its own invocation:** `Delegate` hands the worker session to a per-site Durable Object and awaits it. That needs a framework seam ("where a worker runs") in `lagrange-framework`: file that ticket there and do the 1stcontact wiring here.
- **C. Resumable turns:** each model round in its own invocation, driven by the junction Durable Object. This is a framework-level turn-loop change; choose it only if A and B can't bound the worst case.

Prefer the smallest option that bounds the worst case with margin, and fix obvious waste found in Phase 1 (for example, re-rendering unchanged pages, or re-serialising the whole transcript each round) whatever the option.

### Phase 3 — build it, and guard it

- Implement the chosen option, with no parallel old path (replace, don't extend).
- **A budget check:** a representative heavy turn (first draft with two pages, including builder passes and checks) must stay under a stated CPU share per request, for example 50% of the limit, measured the same way as Phase 1. Record the measured after numbers here.

## Phase 1 finding (2026-10-29): the CPU is the framework's stop polling, not the tools

**Method.** The lost turn's 52 model requests came from production `request_spend` (19 consultant, 33 + 8 builder). They give the tool mix:
- ~45 `set_l1`, ~27 `screenshot`, ~10 `compare`, 6 `describe_page`;
- 612 s of model wall time and ~240 s of tool wall time.

The CPU was then measured in Node with `process.cpuUsage`. The same JS runs in the Worker, and workerd's clock doesn't advance during CPU work, so it can't be measured there. Inputs:
- the production 1st Contact site (`sites`, `site_pages`);
- a real full-page screenshot of it;
- the Worker's own `fidelityDeps` over the fake puppeteer;
- the installed `@lagrangefoundry/ai` watchers over real dev junction logs.

**Tools are cheap** (CPU per call, current 1st Contact home page):

| Step | CPU per call |
|---|---|
| preview render | 61 ms cold, 17–24 ms warm or after a write |
| `set_l1` | 7 ms |
| `screenshot` (decode, tile, encode, base64) | ~200 ms |
| `compare` | ~120 ms |
| CDP parse of the shot | 1 ms |

Even scaled for a longer draft page, the turn's tool calls come to tens of seconds, not 300.

**The 303 s is two polls that re-parse the whole session log** (`SessionLog.readFrom(0)`, ≈3.5 ms CPU per MB):
- `ControlWatcher.check()`, every 50 ms, for every live turn;
- the delegation watch's `callerStopped()`, every 100 ms, for the whole `Delegate`, on the caller's log.

The site conversation's junction is never truncated: local dev logs are 6–27 MB. On a real 6.5 MB log, with nothing else running:

| Poll | CPU share of wall time |
|---|---|
| `ControlWatcher` | 42–46% |
| delegation watch | 22–23% |
| both, tailing from a cursor | ~1% |

A ~4 MB log over the lost turn's 13.8 min (≈10 min of it in `Delegate`) comes to ≈290 s, the production figure. A turn's CPU therefore grows with log size × wall time, whatever it does. No single tool step is anywhere near the limit.

## Phase 2 decision: no split; remove the waste upstream

- **A** (heavy tools out) and **B** (builder sessions out) leave the cost where it is. The consultant's `ControlWatcher` polls the consultant's log for the consultant's whole request, so a 13.8-min turn on a 6.5 MB log costs ~350 s even if it never delegates.
- **C** (resumable turns) would bound each invocation, but it is the largest change and keeps the waste.
- The ticket's own rule ("fix obvious waste found in Phase 1, whatever the option") is the whole fix: both watchers tail from a cursor. That lives in the framework, so it is filed there as **lagrange-framework BUG-101** (`bug-c77500d1`, "components/ai: stop watchers re-parse the whole session log…"). It carries the measurements, the fix design and its test plan.
- 1stcontact picks the fix up through the shared store. No wiring changes here.

**Expected after-numbers for a turn like the lost one**, once BUG-101 lands:
- screenshots ≈ 27 × 0.2–0.6 s;
- compares ≈ 10 × 0.1–0.4 s;
- writes, renders and describes a few seconds;
- the per-round full reads that remain in the manager a few seconds more.

That comes to roughly **20–40 s, ≈10% of the 300 s limit**, well inside the 50% budget. BUG-312's automatic carry-on stays as the safety net.

## Each host continuation in its own request (2026-10-29)

**What changes.** Today the host's continuations of one client message run inside the same Worker request as the round they continue. That covers REQ-409's budget continuation, the layout, structure, review, promise and held-round carry-ons, and BUG-249's and BUG-277's stall and error recoveries. So a 50-minute first draft is one invocation, with one 300 s CPU budget. From now on, every continuation starts a fresh request, with its own CPU budget:

- **At each point where the host would start a continuation, the Worker ends the request** once that round has finished. Its terminal frame says the work continues (`meta.continues: true`), and the turn ledger row for that request closes `complete`, with the detail "continued in a new request".
- **The panel then sends the host cue `continue`** (`POST /api/ai/prompt {cue: "continue"}`), the same way BUG-312's `lost` cue is sent. That request picks up exactly where the host left off: the same cue, the same remaining continuations, the same message clock and spend ceiling, and the same owed work. Nothing about the message is reset. The client sees the next round's words in a new bubble. No message is sent in their name.
- **The route takes `continue` only while this isolate holds the message's next round** for that session. Otherwise it answers 409 and starts no turn, and the panel paints BUG-294's notice and Carry on button, so the client is never left with neither. A held round is dropped when the session's next client message (or any other cue) arrives: a new message is a new message.
- **A request whose client has gone** (BUG-277's detached stream) carries on inside the same request, as before. Nobody is there to send the cue.
- **The local `1c` host is unchanged.** Only the Worker host asks for rounds to be handed off, because only it has a per-request CPU limit.

**Limit.** A single round can itself run for up to `turn_timeout_seconds` (3600). This bounds one request at one round, not at a fixed time. Inside one round, the CPU bound is BUG-101's watcher fix plus lagrange-framework BUG-102.

**What landed (2026-10-29).**
- **The host** (`tools/generate/src/cli/ai/host-core.ts`) yields `ROUND_HANDOFF` before each continuation `continuedTurn` starts: the stall recovery, the error recovery and the budget/hold continuation. It does so only when `HostDeps.handOffRounds` is set, and only the Worker host (`apps/control-app/src/ai.ts`) sets it.
- **The route** (`apps/control-app/src/router.ts`) steps the turn stream by hand. At a hand-off it parks the suspended generator in `heldRounds` (by session, at most 10 minutes) and ends the request with `done {status: 'complete', continues: true}`. The ledger closes `complete` with the detail `continued in a new request` (`HANDED_OFF_DETAIL`).
  - The `continue` cue resumes the held generator in the new request. With nothing held, it answers 409 and opens no ledger row.
  - Any other prompt or cue first ends the held generator (`return()`, so its `finally` runs).
  - A detached client (BUG-277) gets no hand-off: the round runs on in the same request.
- **The panel** (`apps/control-app/src/builder/chat.js`) sends the `continue` cue when a stream's `done` says `continues`, once the panel is free. It doesn't send the cue once the client has written. A refused cue paints BUG-294's notice and Carry on button.
- **Ledger consequence.** A message that recovered from a stall or an error now has one turn-log row per request. The recovery's cause ("recovered after …") is on the row of the request that recovered, and the earlier row says it was handed off.
