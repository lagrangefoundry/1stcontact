Found while diagnosing iteration 3 of `repro-faelan-com`
(`storage/tmp/repro-console/repro-faelan-com/iteration-3`) against
`storage/references/faelan.com/index`.

**`defect_class`: `instrument-blind`** — `gate.json`'s `layout.findings` assert an
overhang in prose and carry no number to put against it, so the artifact a round
reads reports a measurement it does not contain. The fix that added that number
landed one layer short of the artifact.

## What it is

BUG-153 item 3's second ask was *"a finding whose whole record was
`{kind, detail, paths}` could not be checked from the artifact at all"*, and its
fix (`18389b822e`) added `boxes` to every `escape` and `overlap` finding in
`tools/generate/src/l1/probes.ts` — the run's box and the surface's box, in
`paths` order, so the overhang the `detail` claims is arithmetic a reader can
close. That landed and works.

`gate.json` still does not carry it. The only path from a probe finding into
`gate.json` is `layoutCollisions`
(**tools/generate/src/cli/gate-core.ts:188-200**), which rebuilds each finding
field by field into a `LayoutCollision`:

```ts
      findings.map((f) => ({
        kind: f.kind,
        detail: `at ${width}px${height !== undefined ? `×${height}px` : ''}: ${f.detail}`,
        width,
        ...(height !== undefined ? { height } : {}),
        paths: [...f.paths],
      })),
```

and the `LayoutCollision` interface it builds (**gate-core.ts:158-173**) has no
`boxes` member to put them in. So `boxes` is dropped at the report boundary, on
its way to the one file a diagnosing round actually opens.

## The evidence — the two sides of the boundary, on HEAD

The probe's own finding, and the same finding after `layoutCollisions`, from the
BUG-153 fixture (the faelan.com footer shape with `nowrapFromPx` removed so it
genuinely escapes):

```
PROBE finding keys : kind,detail,paths,boxes,width
PROBE boxes        : [{"x":24,"y":32,"width":327,"height":60},{"x":0,"y":0,"width":375,"height":84}]
REPORTED keys      : kind,detail,width,height,paths
REPORTED boxes     : undefined
REPORTED detail    : at 375px×768px: '© 2025 Faelan Westhead. All rights reserved.' is no longer covered by its backing surface section-band-1 — 8px below its bottom edge
```

The probe's two boxes close the sentence exactly — run bottom `32 + 60 = 92`,
surface bottom `0 + 84 = 84`, overhang `8`. The reported record cannot.

## What it cost this round

This round was handed a `structural-failure` verdict whose two findings were, in
full:

```json
{ "kind": "escape",
  "detail": "at 375px×768px: '© 2025 Faelan Westhead. All rights reserved.' is no longer covered by its backing surface section-band-1 — 8px below its bottom edge",
  "width": 375, "height": 768, "paths": ["0.2.0", "0.2"] }
```

(`storage/tmp/repro-console/repro-faelan-com/iteration-3/diff/gate.json`,
`layout.findings[0]`, verbatim — five keys, no geometry.) With the two boxes in
the record, the 8px would have been one subtraction and the run's 60px height
would have shown immediately that the *run* had been grown to three lines rather
than that the *band* was too short — which is the opposite of what the verdict's
`nextStep` prescribes (*"Make each escaping surface size itself from the content
it backs"*). Without them the only routes left were to re-run the evaluator or to
find BUG-153's own UAT and read its prose, which is what this round did.

## The proposed change

Add `boxes?: EvalBox[]` to `LayoutCollision` (gate-core.ts:158-173, beside
`paths`, documented the same way) and copy it in `layoutCollisions` when the
finding carries one:

```ts
        paths: [...f.paths],
        ...(f.boxes ? { boxes: f.boxes.map((b) => ({ ...b })) } : {}),
```

One box per path, in `paths` order, which is the contract the probe already
guarantees and BUG-153's UAT already asserts
(`tests/test_UAT_FC_BUG-153_a_nowrap_run_does_not_wrap.test.ts:178`,
`expect(found!.boxes).toHaveLength(found!.paths.length)`).

**The UAT that should have caught this asserts on the probe's return value, not on
the artifact.** Whatever test covers this fix should read `gate.json`'s
`layout.findings[0].boxes` — or `layoutCollisions`' output, as the repro below
does — because that is the surface the claim is about.

## What changed

`LayoutCollision` gains `boxes?: EvalBox[]`, beside `paths` and documented the
same way, and `layoutCollisions` copies it through whenever the probe finding
carries one. The type is imported from the probes module rather than redeclared
locally: the boxes a collision carries are the probe's own, unchanged, so a
structurally-identical second rect type here would let the two drift and read to
a caller as if they were different facts.

Three consequences of that, each a decision rather than a restatement:

- **Both kinds, not just the one that exposed it.** `escape` is what iteration 3
  was handed, but BUG-153 put `boxes` on `overlap` findings for the same reason
  and both reach the artifact through the same one function — so the fix is a
  property of the boundary, and the evidence has to say so on both arms.
- **Copies, not aliases.** `boxes` is copied rect by rect, as `paths` is already
  copied element by element. A collision list outlives the report it was
  flattened from, so an aliased rect is a rect a later caller can move under a
  reader who has already been told it is the measurement.
- **Absent stays absent.** `boxes` is optional on the probe finding because a
  finding may be raised where only a path is in hand, and the key is therefore
  omitted rather than emptied at the boundary too: `boxes: []` reads as
  "measured, and there were none", which is a different and false claim from "not
  recorded".

`gate.json` now carries six keys per collision where it carried five. BUG-112's
UAT pinned that key set exactly (`test_UAT_FC_BUG-112_verdict_names_the_colliding_leaves_and_widths`)
and its pin is updated to six — the assertion's intent is that the record's shape
is stated rather than left to drift, and this ticket changes that shape
deliberately.

## Test plan

`tests/test_UAT_FC_BUG-158_gate_json_carries_collision_geometry.test.ts`. Every
assertion is made on a `reconcileGates` report put through
`JSON.parse(JSON.stringify(…))` — which is `gate.json` exactly, because `1c gate`
writes the file as `JSON.stringify(report, null, 2)` and adds nothing. That is
the point of the ticket: BUG-153's own UAT asserts on what the probe returns and
passed throughout, because the probe was never the layer that dropped them.

1. An escape reaching `gate.json` carries one box per path, and the overhang its
   `detail` asserts in prose closes as a subtraction over the two rects in the
   same record.
2. An overlap reaching `gate.json` carries both rects, and they really intersect
   on both axes.
3. The reported boxes equal the probe's own and are copies of them — mutating one
   does not move the other.
4. A finding raised with no geometry reports no `boxes` key at all.
5. The rail: a clean reproduction still reports `{ pass: true, findings: [] }` —
   the layout gate has not become unconditionally red, or loud, by acquiring a
   field.

Verified RED: with the production change reverted, 1–3 fail and 4–5 pass, which
is the correct split. Regression scope: the ten gate/layout/fidelity UAT suites
(105 tests) plus the surface and CLI-hygiene structural suites, all green;
`tsc --noEmit -p tools/generate/tsconfig.json` clean.
