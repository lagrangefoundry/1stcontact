## The blocker: the framework half hasn't landed, and I can't land it from here

The ticket says the `lagrange-framework` chunk-indexer change **must land first**. Checking the state:

- `@lagrangefoundry/knowledge/src/chunk_index.js` in the shared store still chunks `membership.get(uid)[0].body` and mentions comments nowhere.
- No `lagrange-framework` ticket exists for it (I searched their store for chunk+comment requests).
- I **cannot install** a framework change from this session: `/Users/martin/lagrangefoundry/node_modules/@lagrangefoundry/` is outside the sandbox write allowlist (`touch` → *Operation not permitted*), so even if I wrote it in `lagrange-framework`, this app would keep resolving the old copy and nothing would be testable against it.

Two facts that sharpen the trade-off:

- **The loss is real, not theoretical.** `session-knowledge.ts:225` fans the AI's search out to `kmSearchChunks` per KB, so deep retrieval is live today. Moving the text to a comment against today's indexer genuinely makes page 12 of a brand book unreachable.
- **The same gap already exists for chat.** The chat transcript lives in a `chat_transcript` comment, so only the AI-maintained summary in the `chat` body is chunked. DOC-10 §4.3 assumes transcripts are chunk-indexed; mechanically they aren't. That's an argument for doing the framework change properly rather than working around it.

**Q1 — how do you want to sequence this?**

- **(a) Hold.** I populate this ticket's body with the resolved design, file the framework ticket in `lagrange-framework`, and stop. No code here until the indexer ships.
- **(b) Ship the split now**, accept a retrieval-gap window until the framework catches up.
- **(c) Ship now with a local bridge that loses nothing.** `buildChunkIndex(store, kbs, source, …)` takes its **own** `kbs` argument, separate from the document index's — `knowledge.ts:359` just happens to pass the same one. So I can hand the chunk builder a widened corpus (project KB + `type=comment AND fields.kind=material_text`) while the document index and the awareness map keep the digest-only corpus. That's the exact division of labour the ticket argues for, with no framework change. **Wart:** `searchChunks` groups hits by `parent_uid`, which would be the *comment's* uid — so a hit reads "Comment on material-xxx" rather than naming the material, unless I map it back. And it's a local mechanism the framework change would later supersede.

My recommendation is **(c)**, then delete the bridge when the framework lands — it keeps deep retrieval unbroken and doesn't block on a repo I can't install from. If you'd rather not carry a mechanism destined for deletion, **(a)** is the clean call.

## Three design calls

**Q2 — where does the digest model call go?** The image path calls the Anthropic SDK directly through the injected `DescribeImage` seam, with a note saying that second LLM path is deliberate-and-temporary *because the AI host's surface is text-only*. For a document that argument doesn't apply — but the host is a session/conversation runtime with no one-shot text prompt either. I'd add a sibling `DescribeText` seam wired in `router.ts:341` beside `defaultDescriber`, same shape, same injectability for UATs. Object if you'd rather I widen the host instead.

**Q3 — no key configured.** Today a text/PDF document with extractable text never degrades; under the new scheme the digest needs a model. With no `ANTHROPIC_API_KEY` I'd write `description_status: 'no_describer'`, a body that is an honest excerpt-plus-provenance rather than the full dump, and **still write the full-text comment** (extraction succeeded; only the digest didn't). Confirm that's the shape you want — the ticket says degraded paths are unchanged, but this path is new.

**Q4 — the comment.** I'd use `fields.kind: 'material_text'` (matching the `chat_transcript` marking precedent), one comment per material written at ingest, carrying the extracted text **unclipped** — `MAX_BODY_CHARS`/`clipBody` then applies only to the digest path and effectively stops mattering. Say if you want the 200k clip kept on the comment too.
