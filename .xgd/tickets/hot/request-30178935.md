Parent: [[EPIC-16]]. Asked for by the operator on 2026-09-23 and scoped in
[[EPIC-16]] §K, whose §K2 records the decision this ticket implements. §J — a
*cloud* staging environment — is a different thing and is not this ticket.

## What is wrong today

The problem is not "there is only production". It is that **locally there is no
boundary at all**. `pnpm dev` runs `./bin/1c builder`, which composes
(`dev-env.ts:184`) `wrangler dev --port 8788` plus the env-file layering, with three
consequences:

- **No `--env`**, so it reads the **top-level** `wrangler.toml` block — which carries
  `ACCESS_DEV_OPEN = "1"`. `d1-migrations.ts:82` states reading the top-level block as
  a deliberate choice, for exactly this reason.
- **`wrangler dev` watches.** Every save rebuilds and reloads, so the running Worker
  and the file being edited are the same bytes, continuously. A half-finished function
  or a just-written migration is immediately what serves.
- **State persists to `apps/control-app/.wrangler/state`**, which `reset.ts:17` calls
  "the whole of what survives a restart … There is no second place."

## The decision this implements

Asked whether a dev environment should share `.wrangler/state` or get its own, the
operator answered that the question is malformed. The new environment **REPLACES**
today's arrangement. There is **ONE** local dev environment; the way to use it is to
**run a deploy**; it holds **THE ONLY COPY** of the dev data. There is therefore
nothing to share with and no seeding fork. `.wrangler/state` does not become a second
store — it becomes this environment's store.

## Behaviour

**`bin/deploy` gains a target table.** The script's own header says *"ONE CODE PATH.
`--dry-run` is a TARGET, not a different script."* It already has the concept of a
target; what it lacks is a table mapping an environment to **how to ship to it**,
rather than a hardcoded `npx wrangler deploy`. Adding that table is this change. The
hooks, their ordering, the exported `DEPLOY_ENV`, and the capability report are
**identical** between a cloud deploy and a local one — the "looks like a cloud deploy"
requirement is met by using that path, not by imitating it.

**`[env.dev]` exists in `apps/control-app/wrangler.toml`**, with its own Worker name,
so `bin/deploy --env dev` resolves. It fails today with *"No environment found in
configuration with name 'dev'"*, which is what [[REQ-315]] measured and built its
framing on.

**The snapshot is the existing bundle.** `bin/build` stage 4 already runs `wrangler
deploy --env production --dry-run --outdir dist` and leaves a complete bundled Worker
at `apps/control-app/dist/worker.js`. It exists on disk today purely as a typecheck
gate and **nothing consumes it**. The local target's ship step is to place that bundle
where the runner reads it.

**The freeze comes from what is watched, not from a flag.** `wrangler dev` has no
`--no-watch`. Pointing it at a snapshot directory that nothing writes to except the
next deploy makes the environment frozen **by construction**. The runner is the
installed wrangler's `dev` with `--no-bundle`, `--persist-to`, `--env dev` and
`--port` (all verified present in `wrangler dev --help`). Editing a source file must
have **no effect** on what the dev environment serves until the next `bin/deploy --env
dev`; that is the acceptance condition for this ticket, not a nicety.

**`d1-migrations.ts` follows the environment.** It reads the top-level block today
precisely because that is what `wrangler dev` reads. Once the dev target is `--env
dev`, that reasoning inverts, and the file must resolve its bindings from the
environment being deployed to. The comment stating the old reason is corrected with
it, so the next reader is not told something that stopped being true.

**The store is guarded on entry.** Before anything opens `.wrangler/state`, the
entry point runs [[REQ-316]]'s check and **refuses to start when more than one
`workerd` resolves in the tree**. §M1 records the incident that makes this a
precondition rather than hygiene: `workerd` owns the on-disk schema of the store and
migrates it forward silently and one-way, and this environment holds the only copy of
the dev data. REQ-316 builds the check; this ticket calls it, and calls it before the
store is touched rather than after.

**The migrate hook stops hardcoding a database name.** §J3 — the database name written
literally into `bin/deploy.d/migrate/10-d1-site-store` — is fixed here, because the
moment a second environment exists it is live.

**The new environment runs beside the old one.** Per §L1, the dev ports are **not** the
old ports, and `.wrangler/state` does not move or change shape, because the old path
reads the same store. Both can be up at once, which is the condition that lets the
replacement be trusted before anything is deleted.

## Acceptance

- `bin/deploy --env dev` completes, runs the same hooks in the same order as a cloud
  deploy, and prints the same capability report.
- After a deploy, editing a source file changes nothing about what the dev environment
  serves; a second `bin/deploy --env dev` picks the edit up.
- The dev target resolves its D1 binding from `[env.dev]`, not from the top-level
  block, and `ACCESS_DEV_OPEN` is whatever `[env.dev]` says rather than inherited by
  accident.
- With two `workerd` versions resolvable, the entry point refuses **before** the store
  is opened.
- The old `pnpm dev` path still works, on its existing ports, against the same store.
- [[DOC-41]] gains the dev target where it describes `bin/deploy`'s environments.

## Boundaries

- **No retirement.** `pnpm dev`, `pnpm dev:control` and `1c builder` as an operator
  entry point all survive this ticket untouched, per §L1: the deletion is a separate
  step so the replacement can be proved first, and folding it in here would mean this
  ticket could not close until the old path was gone. Nothing is removed from
  `package.json` or `dev-env.ts`.
- **No process supervision.** `bin/dev up/down/reap` and `1c ps` are the sibling
  ticket. This one ships a deploy target; starting and stopping the services around it
  is that ticket's subject.
- **Nothing from §J.** No provisioning, no Access application, no `ACCESS_AUD`, no
  Turnstile, no DNS, no secrets, no `SESSION_COOKIE_DOMAIN`. The account-side 80% of
  the cloud version does not exist here (§K7).
- **No seeding fork and no second store.** There is one copy of the dev data (§K2).
