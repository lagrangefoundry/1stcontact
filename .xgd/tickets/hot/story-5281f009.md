## Story

**As a** small-business owner whose site the assistant is building,
**I want** everything I have given the system — my conversations, the files I
uploaded, the sites captured on my behalf, and the brief of what we decided — to
be a body of knowledge the assistant can search, held privately to my account,
**so that** it can answer from what it knows about *my* business, and never from
somebody else's.

## Description

The shipped knowledge base (CAP-100) makes the assistant knowledgeable about
websites and about this product. It is identical for every client and says
nothing about any of them. This capability is the other half: **the client's own
knowledge**, built out of the account's own records rather than out of a release
artefact.

What the client-facing outcome rests on, and what this story makes true:

- **The corpus is the four kinds of thing a site is made from** — the
  conversations held with this client, the material they uploaded, the reference
  sites captured on their behalf, and the brief recording what was decided. It is
  read live out of the account's own store; there is no export and no second copy,
  because unlike a release corpus it is written continuously by the people using
  the product.
- **It is declared, once, beside the shipped one**, and what the declaration says
  is what is actually selected. A declaration nobody reads is worse than none: it
  invites an edit that changes nothing.
- **The account is a hard barrier and the site is only a predicate.** One client's
  knowledge is invisible to another's search — over the records and over the
  vectors derived from them alike, since isolating one while sharing the other
  would leak a body snippet. Within one account the knowledge is shared across
  that client's sites, deliberately: two sites belonging to one business should
  share what has been learned about that business.
- **The index does not ship and is not public.** It is a derivative of the client's
  private material, so it lives in private storage under the account's own key,
  outside everything the public internet is served from and outside the namespace
  attached files are addressed in.
- **Indexing is affordable enough to run on every write.** A new document costs one
  embedding and unchanged ones cost nothing, which is what makes "the document is
  searchable the moment it arrives" a property the product can afford rather than
  a scheduled job that has not run yet.
- **An account with no index yet is an ordinary state**, because it is the state
  every account starts in.

**In scope**: the declaration of the client's knowledge base and its corpus; each
host serving only the knowledge bases whose corpus it can actually reach; the
account barrier over records and vectors; where the index lives; the incremental
refresh and immediate retrievability; the absent-index starting state; and the
embedding model being available wherever the product runs.

**Out of scope**: when the index and the map are refreshed and what the assistant
is told about the shape of the corpus — the two triggers and the landscape floor,
which are the companion story; session priming, the per-turn delta and the
change-feed operation (REQ-160); the ingestion that creates material from bytes
(REQ-163); and the Library surface that lists it (REQ-161). What lands here is the
driven capability all of those call.

## Technical Context

- The corpus is resolved through the ordinary record API of the account's own
  store (CAP-106), which owns the material's types, its rights and provenance
  vocabulary and the place its attached bytes are kept. This capability adds no
  storage of its own beyond the derived index.
- **The same knowledge component serves both knowledge bases**, through one
  narrow port for where an index lives — a directory of files for the shipped one
  (CAP-100), private object storage for this one. That the two are the same seam
  is what keeps the build and search behaviour identical between them; what
  differs is residency, and residency is the thing that must differ.
- **Each host serves the knowledge bases it can resolve, rather than a filter
  guessing.** The release build has the shipped corpus; the deployed runtime has
  the account's store. Handing a host a knowledge base whose corpus it cannot
  reach does not fail — it produces a knowledge base reported as searchable and
  empty, which is the worst of the three outcomes.
- **One embedding model on both sides is a correctness property, not a
  convenience.** Search compares a query vector against index vectors; vectors
  from two different models are not comparable and the failure mode is not an
  error but plausible-looking nonsense. The same model indexes the shipped corpus
  at build time and this one at run time.
- **The machine-written awareness map needs its record type declared** in the
  account store's type vocabulary, since that store refuses an undeclared type —
  without it the first map rebuild would fail validation. The type, its kind and
  the field naming which knowledge base it describes are taken from the knowledge
  component's own constants rather than restated, because they are the same triple
  the component's lookup queries on and its corpus recursion guard excludes. The
  declaration lands with this story; what publishes into it is the companion
  story's. This extends CAP-106's declared type set, which pins no closed set, so
  nothing there is contradicted.
- Related capabilities: CAP-100 (System Knowledge Base) is the shipped half and
  shares the declaration file and the component; CAP-106 (Client Material Store)
  owns the records this reads; CAP-90 (AI Site Assistant) is the eventual consumer
  and is not wired here.

## Reconciliation Decisions

- **An absent index reads as "no index" rather than as a failure** (decided at
  reconciliation, 2026-09-10): REQ-159 is silent on what reading an index that
  has never been written does. Formalized as an AC, because the alternative makes
  the first document a new account ever adds an error — every account passes
  through this state exactly once, at the moment the product is least able to
  afford a failure, and a behaviour that only ever runs on a brand-new account is
  the classic one to leave untested. This is reconciliation filling a gap in the
  spec, not an operator request.

- **An unavailable embedding model refuses by name rather than degrading**
  (decided at reconciliation, 2026-09-10): REQ-159's record of what landed names
  the model binding and the requirement to declare it in every environment, but
  says nothing about the behaviour when it is missing. The landed behaviour is a
  refusal naming the missing configuration and where it must be declared.
  Formalized as an AC, because the alternative is not a degradation but a silent
  one: a knowledge base with no embedder reports as searchable and returns
  nothing, which is indistinguishable to the client from having told us nothing.
  The same reasoning REQ-164 applies to a silently short corpus applies here.

- **The account barrier is asserted over vectors as well as records** (decided at
  reconciliation, 2026-09-10): REQ-159 states the barrier in terms of the handle —
  no argument can name another account. Formalized as an observable
  cross-account search plus separated index residency, because the handle
  argument is a claim about an interface and the client's guarantee is a claim
  about outcomes; a correct handle over a shared index would satisfy the first
  and break the second.

No contradiction between intent and code was found for this plan item. The one
supersession REQ-159 records — DOC-39 §7 settling the enumeration budget against
the ticket's own proposed figure — falls in the companion story's scope, not this
one's.
