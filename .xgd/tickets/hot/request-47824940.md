## Issue 1: a band carried on its captured backdrop never owns its runs

**Kind:** class 1, engine shortfall. **Residual class:**
`fold-carries-a-band-on-a-backdrop-that-never-owns-its-runs`.
**defect_class: `fold-wrong`.** The capture has the backdrop, its runs and their
containment, and L1 can express ownership (a `container` with children, as
`section-bg-0` shows). The fold just never builds it for a backdrop.

**Test I ran:**
1. Can L1 express it? Yes. `section-bg-0` in the same document is a `container`
   holding its runs.
2. Is the value right in L1? No. In `page.json`, every one of the 5 bands below the
   hero (`backdrop-0`…`backdrop-4`) is a childless `box`. All 29 runs that stand on
   them are root-level siblings that point at them with `backedBy` only.
   (Count: `jq -r '.. | objects | select(.backedBy) | .backedBy' page.json | sort | uniq -c`
   gives backdrop-0 6, backdrop-1 2, backdrop-2 4, backdrop-3 9, backdrop-4 8.)

**Mechanism, by file:**
- `fold.ts` `buildSolidBands` (REQ-380, ~l.3003–3008): when a captured backdrop of the
  same fill already covers a band's rows, the fold emits no `section-band-N` and pushes
  `{backdrop: carrier, rows}` onto `carried`.
- `fold.ts` ~l.4942–4945 writes `r.run.backedBy = backdrop.id` for those rows.
- `fold.ts` ~l.4966 `nestBackingSurfaces([...bandNodes, ...sectionBgNodes, ...cardNodes], …, backdropNodes, grounds)`
  passes the backdrops only as `ownable`. Its docblock (~l.3774) says:
  *"`ownable` IS OWNED AND NEVER OWNS"*.

So each band REQ-380 carries loses BUG-142's ownership. The runs stay pinned siblings of
a pinned plate, and nothing can make the plate follow them. The recovery can't fix it
either. `promoteToFlow` flows the runs and leaves a childless fill absolute
(`keepsAbsolute`). I ran `contentRobustnessProbe` on both candidates
(`mountBehaviours` applied, scale 2.5, measured heights):

```
base      {"overlap":524,"escape:backdrop-1":12,"escape:backdrop-2":18,"escape:section-bg-0":10}
recovered {"overlap":164,"escape:backdrop-1":12,"escape:backdrop-2":24,"escape:backdrop-3":96,"escape:backdrop-4":60}
```

Recovery clears `section-bg-0`, because it owns its runs and they now flow. It makes
every backdrop worse (40 → 192 escapes), because the copy now moves and the plates
don't.

**Proposed change:** a backdrop that backs content should own it like a band does.
The minimal version: when `buildSolidBands` carries a band on a backdrop, that
backdrop becomes a surface for the ownership pass (an owner), not only `ownable`. It
keeps its id and fill, so its oracle pairing does not change. REQ-338's reason for
"never owns" is paint order between a section's fill and its overlay element. It
still holds when the owner is the backdrop itself, because its children paint after
it. The containment-at-every-width rule in `containsEverywhere` still decides which
runs it takes.

## Issue 2: `promoteToFlow` deletes every already-in-flow child, here the sticky header rail

**Kind:** class 1, engine shortfall (the recovery stage). **Residual class:**
`recovery-drops-children-already-in-flow`. **defect_class: `fold-wrong`.** The base
document is correct (`sampleFidelity` maxDelta 0.009, 0 residuals). The recovery pass
that writes the alternative document removes nodes from it, and neither the capture
nor the renderer is involved.

This is why nothing on the page is served in flow, including the hero, which already
owns its runs.

**Test I ran:** I loaded `probes.ts` through Vite (same as `bin/1c`), ran
`promoteToFlow(l1.json, {scale: 2.5, measured})`, and checked the result with

`gate.json` from the console doesn't carry the recovery block. The same numbers come

`{"promoted":["0.5","0.7","0.8"],"served":false,"servedFindings":564,"recoveredFindings":356,"fidelityMaxDeltaPx":84.00375,"fidelityResiduals":30}`.

**Mechanism:** REQ-377's sticky header is folded as `pin-0-rail`. It's a root child
with `geometry.place: 'flow'`, height equal to the document (2946 at 1280), and it
holds `pin-0`, which holds `backdrop-0` and the 6 nav links (`fold.ts` ~l.3713–3731,
"The rail goes first: it is in flow"). In `probes.ts` `promoteToFlow`, `plan()`
(~l.3746) skips every non-pinned child (`if (!isPinned(c)) return`), so it is put in
neither `flowing` nor `absolute`. The rebuild (~l.3991) is
`rebuiltChildren = [...absolute.map(i => children[i]), ...emitted]`, so that child is
dropped. The comment at ~l.3701 says *"A non-pinned child is already in flow and stays
where it is"*, but the code doesn't do that.

The root has a full-document-height flow box at its head. Keeping it naively in front
of the flow would push everything 2946px down (I tested it: maxDelta 4950). Keeping it
naively at the end puts the header at the bottom (maxDelta 4313). The +66/+84 on the
five absolute root nodes doesn't come from removing the rail alone: base minus rail
has 0 residuals. So it comes from the recovery's rebuild of the root around a
missing rail. I measured it and did not trace it further.

**Proposed change:** in `promoteToFlow`, keep a child that is already in flow at its
original index, and seed the flow cursor past it only by the space it actually takes
in flow. A REQ-377 rail occupies the page's full height *as a containing block for
the sticky pin*. It shouldn't consume flow space for the siblings that follow it.
Two ways to do that: render the rail out of flow (absolute, `inset: 0`, sticky child
inside), or have the evaluator treat a `pin-*-rail` as zero-advance. Either needs a
UAT where a document has a pin rail and a recovered region. Expected result: recovery
fidelity goes from 84.00/30/24 to ≤0.1/0/0, and `chooseRecovery` then serves the flow
document.

**Fix order with issue 1:** land issue 1 first. Landing issue 2 alone flips
`served: true`, and because escapes aren't priced in `scoreCandidate` (BUG-143), it
ships the recovered document with **192** backdrop escapes instead of 40. The
structural count would go up.

## Issue 3: a control with a visible label loses its placeholder, and L1 can't hold both

This is 9 of 12 ranked regions and 258.27 of 401.17 ranked score (64.4%), with 0 value
deltas.

**Kind:** two parts.
- (a) class 1, **`capture-loses-it`**: the placeholder string is in `raw.html` and in no
  bundle file.
- (b) class 2, **`l1-cannot-express`**: even with the string, the form field can't
  author a placeholder that differs from its label.

**Evidence.** Regions #2–#8, #10 and #11 (`regions.json`) all sit inside a textbox. In
each one, `nodes.ref` is the textbox under its accessible name (e.g. "Your Email
Address*") and `nodes.actual` is "(textbox)". The box is the same on both sides to
0.02px (ref `(676.09, 2203) 546×53`, ours `(676.08, 2203) 546×53`). Examples: #2
`bbox {816,2224,32,16}` score 53.44 meanDiff 26.72; #5 `{784,2128,16,16}` 25.16; #8
`{960,2688,16,16}` 24.83.

I counted pixels with sum(RGB) < 690 inside each field's padding box on both
screenshots:

| field (box at 1280) | reference ink | ours |
|---|---|---|
| Your Name `(676,2111) 546×53` | 470 px, bbox (694,2133)–(808,2146), darkest (133,136,139) | none |
| Email `(676,2203) 546×53` | 716 px, (694,2224)–(865,2238) | none |
| Message `(676,2295) 546×96` | 691 px, (693,2316)–(859,2330) | none |
| footer Your Name `(852,2665) 375×53` | 472 px, (870,2687)–(983,2700) | none |

`raw.html` has `<input id="Your Name" placeholder="Enter your name" …>`, `placeholder="Enter your email address"`,
`<textarea id="Message" placeholder="Type your message here" …>` and `placeholder="Enter your email address for updates"`.
There are 0 occurrences of `Enter your` in `capture.json`, `multistate.json`,
`forms.json` and `l1.json`. The served `site/index.html` emits
`<input class="form-0-form-l1-1" id="cf-your-name" name="your-name" type="text" />`
with no placeholder.

**Mechanism:**
- (a) `extract.ts` `accessibleNameOf` (~l.2247) returns one `{name, source}`, with the
  label taking priority over the placeholder. A control with a `<label for>` reports
  `nameSource: "label"`, and the placeholder string is never recorded anywhere. There
  is no placeholder-text field in `ValueElement`. `placeholderColorOf` (~l.1553) does
  see `el.placeholder` and records `placeholderColor: "#0d141a"`, so the capture knows
  a placeholder exists.
- (b) `l1/forms.ts` `FoldedFormField` (l.50–67) and the module's `ContactFormField`
  (`packages/framework/src/modules/contact-form/controls.ts:22–28`) have one `label`
  string and `labelMode: 'visible' | 'placeholder'`. In `contactFormControls` (l.53),
  `placeholder = field.labelMode === 'placeholder' ? field.label : undefined`. A field
  can show its label above the box or inside it, but it can't show "Your Name*" above
  and "Enter your name" inside, which is what this reference does on all 5 controls.

**Secondary, same issue:** the recorded `placeholderColor` is `#0d141a`, but the ink
is at most (133,136,139). That's consistent with #0d141a at α≈0.505 over white on all
three channels: (255−133)/(255−13)=0.504, (255−136)/(255−20)=0.506,
(255−139)/(255−26)=0.507. The stylesheet isn't mirrored into the bundle, so I could
not see whether that's `opacity` on `::placeholder` or a translucent colour. The
REQ-265 docblock says the field is the *rendered* colour, and here it isn't.

**Proposed change:**
1. Capture: record the placeholder string as its own field, independent of
   `nameSource`, and compose its alpha into `placeholderColor`. Needs a re-capture.
2. L1/module: give the field an optional `placeholder` string separate from `label`.
   `labelMode` keeps deciding where the label goes, and `placeholder` is what's painted
   inside. The fold fills it from (1).
3. Instrument (it will add deltas, which is intended): the control pass should compare
   placeholder text, so this stops scoring 0 deltas.

```
grep -c 'Enter your' raw.html capture.json multistate.json forms.json l1.json
```

## Issue 4: `withChipInset` rounds a centred pill's inset to whole pixels

Regions #9 and #12, 49.11 of 401.17 (12.2%).

**Kind:** class 1. **Residual class:** `fold-rounds-a-chip-centring-inset-to-whole-pixels`.
**defect_class: `fold-wrong`.** L1 padding takes fractions
(`packages/site-schema/src/l1/schema.ts:874`, `finite.nonnegative()`), the capture
has the exact numbers, and the fold rounds them.

**Evidence** (`expected-manifest.json` / `actual-manifest.json`, index 11 and 12):
"2. Order A Session" has box `(440.83, 654) 194×56` on both sides, border 1px.
`renderedTextBox.y` is **672.5** in the reference and **673** in ours. "3. Book
Appointment" is the same: 672.5 vs 673. In `page.json`, the run carries
`"padding":{"topPx":18,"bottomPx":17}`. Arithmetic: inner = 56 − 2 = 54, lines = 19,
so the inset is 35 → 17.5 / 17.5, and the glyph top is 654 + 1 + 17.5 = 672.5.
Ours is 654 + 1 + 18 = 673.

**Mechanism:** `fold.ts` `withChipInset` l.326–327: `total = Math.round(inner - lineH)`,
`top = Math.min(total, Math.round(lineTop - contentTop))`.

**Change:** keep the inset at the precision the fold writes geometry (a hundredth),
instead of `Math.round`.

**How to see it:**
`jq -c '.data.page.l1.root.children[5].children[] | select(.text|tostring|test("Order A Session|Book Appointment")) | .padding' storage/tmp/repro-console/repro-www-bluelotusintegralhealing-com/iteration-3/page.json`.
**Wrong:** `{"topPx":18,"bottomPx":17}`. **Right:** `{"topPx":17.5,"bottomPx":17.5}`.

## Issue 5: a flattened paint order takes the innermost stacking level, not the one that orders the element

1 HIGH value delta, no pixels I can attribute to it.

**Kind:** class 1. **Residual class:** `fold-takes-the-innermost-z-level-not-the-ordering-one`.
**defect_class: `fold-wrong`.** The capture's `paintStack` carries the deciding levels
(8 vs 7). The fold reads only the scalar `zIndex`, which is 0, and the result is the
wrong order.

**Evidence:** `values-diff.json`: `{"text":"(img)","property":"zIndex","expected":"above \"© 2025. All rights reserved.\"","actual":"below …","tier":"HIGH","severity":3050.5}`.
In `expected-manifest.json`, the footer logo (`box (504.94,2617) 270×254.5`) has
`"zIndex":0` and `paintStack [{…4.1,z:14},{…4.1.8,z:8},{…8.0.0,z:0},{…8.0.0.0,z:0}]`.
The © run (`box (57.98,2824.52) 503×18.19`) has `"zIndex":7` and paintStack
`[{…4.1,z:14},{…4.1.7,z:7},…]`. Their boxes overlap at x 505–561, y 2824–2843. The
level that orders them is the one under their shared context, 8 > 7. In `page.json`,
`image-1` has no `paintOrder` and the © run has `paintOrder: 7`, so ours paints © on
top.

**Mechanism:** `extract.ts` `zIndexOf` (~l.1731) returns the first applicable level
walking *up* from the element, which is 0 here. `fold.ts` `foldPaintOrder` (~l.1437)
folds that scalar.

**Change:** fold `paintOrder` from `paintStack`, taking the level just below the
outermost stacking context the page's flattened siblings share. Or have `zIndexOf`
return that level. If the change goes in the capture, it needs a re-capture.

**How to see it:**
`jq -c '.data.page.l1.root.children[9] | {id, paintOrder}' storage/tmp/repro-console/repro-www-bluelotusintegralhealing-com/iteration-3/page.json`.
**Wrong:** `{"id":"image-1","paintOrder":null}`. **Right:** a `paintOrder` greater
than 7.

## Implementation (free-coded, REQ-383 session)

Commits on `free-REQ-383`: `c5c06e00602a` (issues 1–5), `2b8dc5074345` (grid-cell height,
found on the second bundle). UATs: `tests/test_UAT_FC_REQ-383_carried_bands_rail_placeholder_inset_level.test.ts`

### What changed, by issue

1. **A backdrop that carries a band owns its runs.** `nestBackingSurfaces` takes an `owners` set:
   the captured backdrops `buildSolidBands` carried a band on. They are candidate parents beside the
   reconstructed surfaces (containment at every width still decides), keep their id and fill, and are
   built as `container`s holding their runs. This also works when *every* band on a page is carried,
   so there is no reconstructed surface at all. Backdrops that carry no band still own nothing (REQ-338).
   Consequences that are part of this behaviour:
   - **Recovery flows an owning backdrop whole, like a section.** `promoteToFlow`'s "page and every
     section flow whole" rule applies to `isBackingSurfaceId`, not only to fold-synthesized ids.
   - **An owning backdrop still pairs with its oracle sample.** `sampleFidelityProbe` puts a captured
     backdrop that owns content in the `box` pairing queue from its resolved rect. It is a structural
     node, not a leaf, so before this it went unmatched: 5 per width on bluelotus.
   - **A container's reading-order key comes from its TEXT members** when it has any. Document-order
     pairing is text-only; an image's index is wherever its table row fell. Before this, the footer
     backdrop, owning the early-indexed logo, sorted ahead of the testimonials and contact section,
     and every repeated label was graded against the wrong twin (812px at 320).
2. **`promoteToFlow` keeps a child already in flow** (REQ-377's pin rail), in its original order among
   the kept children and ahead of the recovered flow. It seeds the flow cursor past it, so the first
   flowed band's lead is negative by the rail's height. That reproduces the capture at every sampled
   width, and segments where the rail's own track snaps are held as discontinuous.
   - **Grid cells are placed from their own stack height** (second commit). A recovered cell container
     is as tall as its LAST member's bottom. Columns are matched at the widest width, and at a narrower
     one a wrapping member can run over the one below it, so the cell ends above its union box.
     Placing the next band from the union put everything after it too far down (12px per testimonial
     row on hearingzone510.com).
3. **Placeholder words.** Capture schema **21** (BUG-199 took 20 concurrently): every field records `placeholderText` (the
   `placeholder` attribute, whitespace-collapsed, null when none), independent of `nameSource`.
   `placeholderColor` multiplies in the `::placeholder` pseudo-element's own `opacity` before
   compositing (`#0d141a` at opacity .5 over white → `#868a8d`, matching the measured (133,136,139)).
   `FoldedFormField` gets an optional `placeholder`, set when the control is visibly labelled
   (`labelMode: 'visible'`) and has placeholder words. The contact-form module's field schema gets an
   optional `placeholder`: it is painted inside the box, and `labelMode` still decides only where the
   label goes. A placeholder-labelled field with no explicit placeholder behaves as before. values-diff
   compares `placeholderText` (kind `text`, type A) when both sides were captured at schema ≥21, and
   lists it on the control card. **Needs a re-capture** of the reference to take effect on bluelotus.
4. **Padding keeps hundredth precision.** `withChipInset`, `foldPadding` and the per-width padding
   tracks use the fold's `round2` instead of `Math.round`: the 56px pill is now 17.5 / 17.5.
   *This explicitly supersedes REQ-371's "split 18/17 so it still sums" assertion*
   (`test_UAT_FC_REQ-371_the_inset_around_the_lines_is_carried_as_padding_summing_to_the_box` now pins
   17.5 / 17.5).
5. **Paint order from `paintStack`.** For each element (keyed by the last link of its chain), over every
   element its box overlaps in any projection: the index where the two chains first name different
   boxes, counted only where the two levels there differ. The deepest such index wins, and
   `paintOrder` is that level. An element with no such partner keeps its `zIndex`, so a page that
   stacks nothing folds as before. On bluelotus: logo `paintOrder` 8, © run 7.
