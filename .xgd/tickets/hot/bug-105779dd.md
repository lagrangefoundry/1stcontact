## Symptom

On dev, 2026-11-04/05, every consultant message on one shop site ends with "The work stopped before it finished … Press Carry on". The last three jobs all did so, the latest running in the new per-job container (REQ-646) with no memory problem: peak 752 MB, exit ok, 0 memory kills. turn_log reads `lost — job …: step 3 failed 2 times` each time, and the dev-worker log shows:

```
job_step_failed … kind:"round" … StepFailure: content.startsWith is not a function
  at isCue (roles.ts) ← isHostCue ← openMessage ← roundOfJob (the drain)
```

Carry on runs a new message, which does its work and then dies the same way, so the client sees "stopped" every time, even when the work itself got done.

## Root cause

**A poisoned queued message.**
- The site's junction holds one `enqueue` record (2026-11-04T21:46:25Z, message `18654b44…`) whose `content` is a **content-block array**, not a string. The record is a Delegate result (`[The result of your Delegate call with handle worker-builder-2-…`).
- The framework allows this: `pendingMessages` (lagrange-framework `components/ai/js/src/control.js`) documents that since its REQ-111 "a queued message may be content blocks".
- **1stcontact's host doesn't handle it.** When a job's message ends, `roundOfJob` drains the next waiting message (`tools/generate/src/cli/ai/host-core.ts`, `openMessage(…, next.content as string, …)`). `openMessage` calls `isHostCue(text)` → `isCue`, which calls `content.startsWith`. That throws on an array, the step fails twice, and the job is ended lost.
- **The poison never clears.** A queued message is retired only by a `turn_start.from_message` that consumes it, and the crash happens before that turn starts. Every future job on the site hits it at its drain.

**Prod exposure:** any site where a message with content blocks is queued gets the same poison. That covers a client sending a photo while the consultant is busy, and a Delegate result queued as a message.

**Where the Delegate result came from (answered from the dev junction).** Job `turn_bf1c4b7a…` had already been ended `lost` at 21:37:59 by another process (`stop_request reason:lost` + its `job_end`), while its step 3 was still running. At 21:46:24 that step, still alive, went on to deliver builder result `worker-builder-2-zm6sfz`. The live job (`turn_95687d93…`) was delivering the same handle in turn `5219d0…` at the same moment. The zombie's `promptStream` lost the claim, so the framework queued its delivery content (blocks, because `withPictures` builds blocks for a delivery) and the zombie recorded `delivered` and wrote a second `job_end`. **So yes, the enqueue was a bug: a step of a job that has already ended must not deliver or run a round.**

## Fix

- The drain and `openMessage` accept a queued message's content as sent: a string or content blocks. Cue and rejection checks read the text of the blocks; the turn runs with the blocks intact, so a queued image runs as an image.
- No `as string` casts on queued content anywhere in the host.
- A queued message that cannot be run is **retired with a recorded reason**, and the job ends normally. It is never retried until the job is lost, so one bad record can't block a site. (The host records the retirement on the junction; the host's view of waiting messages leaves retired ones out.)
- **A step of a job that has already ended does nothing:** it runs no round and delivers nothing, and it doesn't write a second `job_end`. That closes the path that queued the Delegate result.

## Test plan

UATs `test_UAT_FC_BUG-353_*`, using the in-process runner (the same steps the container runs):
- A job whose message ends while a content-block message is queued drains it: the queued message runs as a turn with its blocks, and the job completes.
- A job on a session whose junction already holds such a record completes, and the record is retired: a second job no longer sees it pending.
- A queued message that cannot be opened is retired with a reason, and the job ends `complete`, not `lost`.
- A step run for a job that has already ended runs no round, delivers nothing, and adds no second `job_end`.


## What landed (commits 8dbef25, 3475243 — v0.2.776)

All in `tools/generate/src/cli/ai/host-core.ts`:
- `queuedContent` accepts a queued message as words or a non-empty array of typed content blocks; `queuedText` gives the blocks' text for `openMessage`'s cue and rejection checks. The drain (`roundOfJob`) and `followQueued` both go through it; the `as string` casts are gone.
- The first round of a drained message re-reads its blocks off the junction by message id (`queuedBlocks`) and sends them as they are, with any stage guide after them as a block of its own. The job's persisted state never carries image bytes.
- Unrunnable content is retired with a `message_retired` job record (`message_id`, `reason`). `waitingAmong` leaves retired messages out of every waiting-message read. The drain then carries on, and the job ends with its own message's end.
- Ended-job guard: `runJobStep` returns the job's recorded end when it already has one. `roundOfJob` checks again right before the round, because a step's setup can take minutes. `endJob` writes no second `job_end`.

UATs: `tests/test_UAT_FC_BUG-353_queued_content_blocks_drain.workers.test.ts` (4 cases, one per test-plan line; all fail on the old code). Regression suites run green: REQ-624, REQ-627, BUG-256, BUG-294, BUG-326, BUG-343. Four REQ-416/REQ-436 talker cases fail identically with and without this change; they were already failing.
