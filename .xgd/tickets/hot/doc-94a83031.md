# Spatial visibility and pointing — giving the AI measurements, and the user a way to point

## 1. Purpose

Two capabilities, from one failure.

On 2026-09-09, between 02:15 and 02:31, a chat session drawing the 1st Contact
wordmark made **13 `write_image` calls and 13 `screenshot` calls** and still did not
land the logo. The user's summary: *"when the AI fumbles about it does not fill the
user with confidence."*

The session diagnosed itself repeatedly and correctly — *"I'm positioning SVG text
blind"*, *"I can't measure actual glyph bounds, so I'm guessing at every
iteration"* — and eventually resorted to drawing a **ruler grid into the drawing
itself** (`wordmark-measure`: red verticals at x=20/25/30/35/40, blue horizontals at
y=8/10/12/14), rendering it, screenshotting it, and reading the glyph edge off the
picture by eye.

That failure has two independent causes, and this document specifies a response to
each:

1. **The AI cannot measure.** It authors absolute coordinates into a space whose
   geometry it can only see as a picture. §3.
2. **The user cannot point.** *"Move the st a little closer to the 1"* — *a little*
   is a continuous quantity with no efficient encoding in language, so every
   iteration is a lossy round trip that does not converge. §4.

The organising principle, which the two halves share:

> **The user's hand is a better encoder of position than the user's vocabulary, and
> the machine is a better encoder of alignment than either.** The user says
> *roughly there, that feels right*; the AI says *exactly cap-aligned to 0.1 units*.
> Neither is good at the other's job.

Everything below follows from that division of labour. The user supplies intent; the
AI supplies precision; the AI keeps final say over the number that is actually
written.

---

## 2. What actually happened, as evidence

The wordmark that resulted:

```xml
<text x="0"  y="62" font-family="system-ui, -apple-system, sans-serif" font-size="62" font-weight="800" fill="#1a3a6b">1</text>
<text x="27" y="29" font-family="system-ui, …"                          font-size="20" font-weight="700" fill="#e76f51">st</text>
<text x="48" y="62" font-family="system-ui, …"                          font-size="62" font-weight="800" fill="#1a3a6b">Contact</text>
<line x1="80" y1="78" x2="240" y2="78" stroke="#e76f51" stroke-width="3.5" stroke-linecap="round"/>
```

Three **separately, absolutely positioned** `<text>` elements. Every gap in that
wordmark is a number that was guessed, and the only way to check a guess was to
render and look.

Two defects are visible in those four lines, and they are the two shapes this
document addresses:

- **The positions are guesses.** `x="27"` and `x="48"` were tuned over seventeen
  minutes against a screenshot. The underline's `x1="80" x2="240"` was never tuned
  at all — the session noted it *"ends at the right edge of the viewbox rather than
  at the end of Contact"* and shipped it anyway, because measuring where "Contact"
  ends was the same unavailable operation.
- **The positions are not portable.** `system-ui` is not a font. It resolves to SF
  Pro on macOS, Segoe UI on Windows, Roboto on Android — different advance widths in
  each. The coordinates that were tuned are correct on the machine they were tuned
  on and wrong nearly everywhere else. **This is a live defect in the draft,
  independent of tooling**, and §3.2 is the rule that prevents its recurrence.

## 3. Part one — giving the AI eyes

Ordered by cost. The first two are free and would have prevented most of the
session; the rest are real work in roughly descending value.

### 3.1 Text runs compose — and nothing had to be built (settled)

The session stated, and believed, that inline formatting was impossible: *"I can't
render true superscript in a text element (no inline formatting within a string)."*

That is **true of L1 page text** (§3.7) and **false of SVG**. `<tspan>`, `dx`, `dy`,
`font-size`, `font-weight` and `fill` are all already in the allowlist in
`packages/site-schema/src/svg.ts`. This validates today — run against `validateSvg`,
it returns `{ ok: true, errors: [] }`:

```xml
<text x="0" y="62" font-family="Satoshi" font-size="62" font-weight="800" fill="#1a3a6b"
  >1<tspan font-size="20" font-weight="700" fill="#e76f51" dy="-33">st</tspan><tspan dy="33">Contact</tspan></text>
```

One `<text>`, three runs. **The browser advances the pen.** Horizontal position is
automatic and exactly correct in whatever font resolves; there is no `x` to guess, no
gap to measure, and no screenshot loop. `dy` alone carries the superscript raise,
which is a single perceptual judgement rather than a search.

The capability existed the whole time. Nothing in the `write_image` documentation
mentions it: the description covers *"shapes, paths, gradients, text and grouping"*
and the security rules, and never says that text runs compose. **That omission cost
the session.**

**Action:** a paragraph in `write_image`'s description stating that a run of styled
text is one `<text>` with `<tspan>` children, that the pen advances automatically,
and that separate absolutely-positioned `<text>` elements are the wrong tool for
text that sits on one line.

### 3.2 A mark names a real font (settled)

A drawing that resolves to a different font per visitor is not a logo. `system-ui`,
`-apple-system` and bare `sans-serif` must not appear in a generated mark; a mark
names a font registered for the site in `fonts/registry.yaml`.

**Action:** a rule in `write_image`'s description. Optionally enforced later — the
SVG validator is the natural place, but a documented rule is the cheap first move.

### 3.3 `measure_drawing` — the geometry read-out

Render an SVG asset headless and return its geometry as **numbers, in the SVG's own
user coordinate space** — the space the AI authors in, so no transform inversion is
required of the reader.

Per node: `getBBox()`, and the node's `id` where it has one. Per text node
additionally: `getComputedTextLength()`, and **`getExtentOfChar(i)` per glyph**. That
last one is precisely the question the ruler grid was built to answer — *where does
the `1` end* — returned as a number in one call instead of a render, a screenshot and
a squint.

It must also report **font metrics** (§3.4) and **which font actually resolved**.
The resolved-font report is how `system-ui` gets caught in practice rather than only
in principle.

The machinery exists. `tools/generate/src/cli/capture/extract.ts` already drives
Playwright and reads `getBoundingClientRect()` and `Range` rects; this is the same
capability pointed at an asset and returning numbers instead of a picture.

### 3.4 Abstract references — measurement that means something (the important one)

*Specified in full in §5.*

A read-out of forty bounding boxes is a large number of tokens to reason over and
still leaves the AI doing arithmetic that goes stale. The durable form is to let both
sides refer to **features**, not coordinates.

**Named anchors.** A drawing's meaningful positions have names — `cap-top`,
`baseline`, `x-height`, `descender`, `left-edge`, `right-edge`, `centre`, and the
`gap` between two nodes. Measurement should be expressible and answerable in those
terms.

**Relational queries.** Rather than only dumping geometry, the tool should answer a
stated relationship:

```
align(#ord, #one, 'cap-top')  →  delta = 2.4u
```

One number, directly actionable, and it converts *"does it look right?"* into a
pass/fail the AI can act on without a picture.

**Why this matters more than raw boxes.** Bounding boxes let the AI *verify*
alignment; font metrics let it *solve* alignment. Cap-height alignment has a closed
form — given the font's cap-height ratio:

```
top("1")  = baseline₁  − capHeight × 62
top("st") = baselineₛₜ − capHeight × 20
⟹ baselineₛₜ = baseline₁ − capHeight × (62 − 20)
```

One equation. Exact. No iteration and no screenshot. That is a categorically
different activity from `y=40 → y=44 → look again`, and it is the strongest argument
for exposing font metrics rather than only geometry.

**The honest limit.** A solved number is still a number, and it is wrong again the
moment the font, the size or the string changes. So the settled shape is: the AI
**recomputes from metrics** whenever an input changes, and measurement is the
**check**, not the discovery. Abstract references are what make that recomputation
expressible rather than a fresh guess each time.

### 3.5 `outline_text` — exact and portable

`(font, size, weight, string) → { d, advanceWidth, capHeight, bbox }`, computed from
the registered font file via `fontkit` / `opentype.js`. No browser.

The AI drops `d` into a `<path>`, which the allowlist already accepts — so this is
**not a schema change**. It is how real logos ship: exact at author time, and
**identical for every visitor** regardless of what is installed. It dissolves §2's
two defects together.

**Licence caveat.** Converting a face to outlines can be a separate grant from
webfont use. `fonts/registry.yaml`'s `licence.redistribute_in_product` is the field
that has to say yes, and `1c fonts check` is the gate that would need to know about
outlined text.

### 3.6 `measure_page` — geometry for the page, not just the drawing

Box per stamped L1 segment at a given width. Far broader value than logos — *"the
headline sits 4px from the edge"*, *"these two blocks overlap at 900"* — and it is
what makes the grid overlay (§4.9) unnecessary **for the AI**, though not for the
user.

`l1/probes.ts` already computes this analytically and browser-free. It is not
sufficient on its own: it **estimates** text height and cannot know glyph widths,
which is exactly the blind spot that caused §2. Use the analytic evaluator as a cheap
pre-check and a browser-backed render for truth.

### 3.7 Multi-variate text in L1 — the latent hazard

`packages/site-schema/src/l1/schema.ts:1098`:

```ts
export const l1TextSchema = z.object({
  kind: z.literal('text'),
  text: z.string(),                     // ← flat string
  axes: l1TextAxesSchema.optional(),    // ← applies to the whole run
  …
}).strict()
```

One string, one set of axes, `.strict()`. No runs, no spans, no inline vocabulary.

**This is not a missing typographic nicety.** The only way to get one coloured word
in a headline today is three text nodes positioned absolutely — which is the §2 trap,
except worse on the page, because absolutely-positioned text fragments are fragile at
every breakpoint and break the moment copy reflows. The schema actively pushes the AI
toward brittle geometry for something as ordinary as an ordinal or an emphasised
word.

**Proposed shape (contained).** `text` accepts either a string — unchanged, every
existing document stays valid — **or** a one-level array of `{ text, axes? }` runs,
where run axes are a narrow subset: fill / palette ref, size scale, weight, baseline
shift. No nesting, no links inside runs. The schema stays closed.

**The real cost is blast radius, not schema.** The renderer emits spans; the fold has
to *recover* runs from captured HTML; `probes.ts` text estimation changes; and
[[DOC-28]] §3's exposure rule (*"a plain string or a pick from a closed list"*) needs
an answer for multi-run copy. Simplest honest answer for the editor: **one field per
run**.

**Note these do not compete with §3.5.** For a *logo* you want outlines, for
portability. For *page copy* you want runs. Different surfaces, different answers.

## 4. Part two — Marked Points

### 4.1 The problem this solves

*"Move the st a little closer to the 1."* **A little** is a continuous quantity with
no efficient encoding in language. Every iteration is a lossy round trip — intent →
words → guess → render → perception → words — and nothing in the loop carries a
number, so nothing converges. Thirteen iterations was not the AI being dim; it was a
channel with no bandwidth for the thing being communicated.

Marked Points gives that quantity a channel: **the user points, and the pointing
becomes text in the message.**

### 4.2 The constraint that shapes everything: the AI never sees the marks

`screenshot` takes `kind: 'edit'` — *"the page as your user is editing it right
now"* — but it renders **server-side**. The marks live in the user's browser overlay
and are not in that render.

This is good news twice: the marks cannot pollute `compare`, and they cannot leak
into the fidelity gates. But it means **the pill's expansion is the entire channel.**
There is no fallback where the AI squints at a red X. Whatever the pill expands to is
all the AI gets, so §4.6 is the load-bearing part of this design.

### 4.3 The interaction

1. **Edit mode only.** View mode must behave exactly as published ([[DOC-28]] §7.1),
   and the bridge already refuses to bind without the `data-fc-edit` marker.
2. **A "Mark Points" toggle** within edit mode.
3. **Left click places a point** — a small high-contrast X, with a label (*Point A*,
   *Point B*, …). The label **fades when the pointer moves away from it**, or when
   the next point lands, and returns on hover. It does not fade on a timer: a timed
   fade fires while the user is still reading it. The fade exists so a label never
   occludes where the next point goes.
4. **The label carries two controls** — `x` deletes the point, `+` inserts another
   pill referring to it (§4.5).
5. **Dragging the X moves the point**, updating any live pill. First placement is
   usually approximate, so nudging beats delete-and-replace.
6. **Placing a point inserts a pill into the message composer** (*Point A*). On send,
   the pill expands to the full spatial description of §4.6.
7. **Letters are reused after deletion**, keeping the namespace small.

**Toggle, not modifier-click.** Alt-click would avoid a mode, but it is a power-user
idiom, it is undiscoverable, and it does not exist on touch. The cost of the toggle
is that it **reassigns edit mode's primary gesture** — today a click resolves a
segment and opens its modal (`edit-client.ts:105` calls `preventDefault()` then
`onSegment`). If Mark Points is on and clicking the headline does not open its
editor, that must be unmistakable: crosshair cursor, persistent visible state, and
hover outlines kept but **dimmed** — knowing which element you are marking inside is
useful context and previews what the pill will say.

### 4.4 The pill behaves like a pill

- **Atomic.** One backspace removes the whole chip, never part of it. This prevents
  the mangled half-pill state entirely.
- **Cut, copy and paste work as expected.** A pill survives being cut and pasted
  within the composer, and carries its identity with it.
- **Deletion is undoable.** Ctrl-Z in the composer is what the user reaches for
  first, before thinking to look back at the page.
- **Coordinates on hover**, so a reused letter can always be disambiguated.

### 4.5 The `+` control, and why it earns its place

The motivating failure is real and common: the user places a point, starts typing,
makes a mistake, and **accidentally deletes the pill**. The X is still on the page,
but there is now no way to refer to it.

`+` on the label re-inserts a pill for that point. It is preferred over
"click near the X again" because a proximity tolerance fights directly with placing a
*new* point nearby — which is exactly what a tight spacing question requires
("the gap between here and here") — and because it separates *refer again* from
*place another* into two unambiguous gestures.

§4.4 makes the accident rarer, but `+` earns its place independently: it also serves
*"move this to A, and align that to A too"* — one point, two references, one message.

**Safety net.** Since the pill reads *Point A*, typing `Point A` should re-resolve to
it, given lenient matching. Costs nothing.

### 4.6 What a point resolves to (the load-bearing decision)

A pill must **not** expand to raw viewport pixels. `(142, 88)` asks the AI to invert a
transform chain it cannot see — an SVG user space, inside an `<img>` of some size,
inside an L1 node, at some viewport width. That is the same guessing game in a new
costume.

A point resolves **through the hit chain**, and carries every useful frame at once,
because the AI does not know in advance which one it needs:

```
Point A — inside image node 0.1 (asset wordmark-option-a.svg)
  svg user space: (31.2, 24.8)    [viewBox 0 0 320 86]
  node-relative:  (58, 46) of 148×40
  viewport:       (142, 88) at width 375
  near:           cap-top of "1" (2.1u above), left edge of "Contact" (17u right)
```

Roughly forty tokens, unambiguous, and the first line is *directly* the number to
write into `y=`.

**`near:` is not decoration.** The user is pointing at *"the top of the t"* — a
feature, approximately. If the pill reports a cap-height line 2 units away, the AI can
recognise the intent and place the element **exactly** on that line rather than at the
user's approximate pixel. This is §1's division of labour made concrete, and it is
strictly better than snapping the X for the user, which would be a guess made at the
wrong end and would fight them when they genuinely meant *just below*.

**Which variables belong, and which do not:**

| Variable | Verdict |
|---|---|
| **Viewport width** | **Essential.** L1 geometry is keyframed across six widths with `interpolate`/`snap` segments, so a point at 375 means something different at 1200. Without it the pill is unreadable. |
| **Document coordinates, not client** | **Required.** Report relative to the document and scroll position stops mattering rather than becoming a third number to carry. |
| **Which render it was taken against** | **Include.** Cheap, and it makes a stale reference detectable. |
| **Device pixel ratio** | **No.** User space is already CSS px; DPR adds a number nobody divides by. |

**SVG user space does not require inlining the SVG.** The renderer emits
`<img src="…svg">` (`packages/framework/src/l1/render.ts:2155`), and one cannot
hit-test inside an `<img>` — but one does not have to. Given the img's rect, the
asset's viewBox and `preserveAspectRatio`, user space is a pure scale-and-offset
inversion, and the server knows the viewBox. **This takes the one expensive piece —
an inline-SVG edit channel — off the critical path.**

**Most of the resolution already exists.** The edit bridge
(`packages/framework/src/l1/edit-client.ts:105`) already resolves a click to
`{ moduleId, slot, path }` plus the element — including the module/slot address-space
scoping, which is the genuinely hard part. It currently hands that to a modal instead
of to the chat. The offset within the resolved element is
`clientX − element.getBoundingClientRect().left`.

**Implementation contract.** The preview iframe is currently **unscaled** —
`previewScale` in `page-style.js` concerns font preview in the modal, not the iframe,
and there is no transform on it. Point capture depends on that. If a "fit to pane"
zoom is ever added, click coordinates must be un-scaled or every point silently lands
in the wrong place.

### 4.7 Lifetime — points last one turn (settled)

**Points clear on send.**

Persistence only pays when a marked point stays valid across a turn, and in the real
loop it almost never does: the user marks a point *because* they want that thing to
move, and then it moves. Persistence would buy the minority case — a point on an
element that is *not* being changed — at the cost of carrying re-projection
machinery: anchor to node plus offset, re-project after render, invalidate when the
node disappears. Clearing on send makes that entire category of design problem
disappear.

Sent pills keep their literal coordinates in the transcript. That is history and
needs no machinery at all — and it means a reused letter can never confuse the AI,
whatever it might do to the user.

**Dragging still earns its place within a turn** (§4.3.5). It just does not need to
survive the send.

**On send, the Xs grey out and stay visible until the new render arrives**, so the
user can still see what they referred to while the answer is coming. They are already
inert, so this reintroduces no staleness.

### 4.8 One point is usually enough; two points are for extents

A **delta** does not need two points. *"Move the st from A to B"* — A is redundant,
because once the AI can measure (§3.3) it already knows where the `st` is. **One
point plus measurement is all a move requires**, and this is why a separate
drag-to-communicate feature is not specified: a drag is a delta, and deltas are the
redundant case.

Multiple points earn their keep for **extents and equalities**, where no endpoint is
measurable from an existing object:

- *"The underline should run from here to here"* — an extent. Two points, neither
  redundant. This is §2's `x1="80" x2="240"`, hardcoded and wrong at both ends.
- *"Make this gap match that gap"* — four points, no object being moved at all.

### 4.9 The width-ambiguity rule

The frames in §4.6 expose a fault line, and it is the same one that runs through this
whole document:

- A point **inside a drawing** is width-independent. An SVG has one coordinate space
  and no breakpoints, so *"put the cap-top here"* has exactly one meaning and one fix.
- A point **on an L1 node** is width-dependent. Marked at desktop, *"move it here"*
  might mean *at this width* or *at every width* — different edits to different
  keyframes.

**Rule:** when a point resolves to an L1 node rather than into a drawing, the AI asks
which width the instruction is for, unless the user has said. The viewport width in
the pill is what tells it to ask.

This is the same reason direct manipulation is tractable inside a drawing and
awkward on a page, and it is why [[DOC-28]] §7.3's scope wall is not breached by any
of this (§4.10).

### 4.10 Why this does not breach DOC-28 §7.3

[[DOC-28]] §7.3 is explicit: *"no adding, removing, reordering, resizing or
repositioning segments. Structure is the AI's job."*

Marked Points does not touch it. **The user is not editing anything** — there is no
write path, no diff, no validation and no re-render. A gesture produces a **message**,
not a mutation. The user is *specifying intent*, which is the same category of act as
*"make the headline shorter"*, and the AI retains final say over every number that is
actually written.

That is also what keeps this on the right side of the product principle in
[[DOC-46]] / [[DOC-33]] — the client answers questions about their business and never
designs. **Pointing at where you want something is communicating, not designing.**

### 4.11 Out of scope

- **Drag-as-communication** — subsumed by §4.8.
- **A grid overlay.** As a *positioning* channel it is dominated by pointing:
  *"three squares closer"* requires a quantisation performed in the user's head and
  is only meaningful if the AI knows the square size. It remains worth building
  **later, for a different job** — reading off and discussing spacing that already
  exists (*"this gap is three squares, that one is five — make them match"*). That is
  about the user's eye, not the AI's; once §3.6 exists the AI does not need it.
- **Freehand annotation.** Genuinely valuable for what language and pointing are both
  bad at — *this shape*, *curve it like this*, arrows and circles on a screenshot —
  but it is annotation and critique rather than precise positioning, and it costs an
  image round trip, which is the expensive channel.
- **Keyboard-only point placement.** Not supported. Acceptable for this feature
  provided pointing never becomes the *only* way to express a position.

## 5. The relational vocabulary

*This section settles §7 Q2.*

Raw geometry is not enough. A read-out of forty bounding boxes is a large number of
tokens to reason over, and it leaves the AI doing arithmetic that goes stale. What
makes measurement durable is being able to name **features and relationships**, not
coordinates.

### 5.1 Three different lines, and the difference is what the eye catches

"The top of the 1" is ambiguous in a way that decides whether alignment looks right:

- **Font lines** — derived from the font's metrics × font-size, independent of the
  string: `baseline`, `cap-top`, `x-top`, `ascender`, `descender`. Exact, stable,
  computable without rendering.
- **Ink extents** — the painted bounds of *this* string in *this* font: `ink-top`,
  `ink-left`, `ink-right`, `ink-bottom`. Needs real outlines.
- **Advance** — where the pen lands. `advance-end` differs from `ink-right` by the
  right side bearing.

These are not interchangeable. In "st" the `t`'s ascender rises **above** cap height;
a digit typically sits **at** cap height. So aligning ink-tops and aligning cap-tops
give visibly different results. The instruction that drove §2 — *"the top of the t
should align with the top of the 1"* — was an **ink** statement, not a typographic
one, and there was no vocabulary in which to say so.

Likewise §2's `x="27"` was reaching for *"where the 1 ends"*, which is `ink-right` for
tight optical spacing and `advance-end` for ordinary typesetting. The measured values
differ by 8.4 units (§5.3). The session had no way to name either, and guessed a
number within one unit of `ink-right` — the right intent, arrived at blind.

**The vocabulary must therefore name the family explicitly.** That is the single most
important property of it.

### 5.2 The anchor grammar

`<node>.<anchor>` — node by `id`, anchor from a closed set:

| Family | Anchors | Applies to |
|---|---|---|
| Box | `left` `right` `top` `bottom` `centre-x` `centre-y` | any node |
| Ink | `ink-left` `ink-right` `ink-top` `ink-bottom` | text |
| Font | `baseline` `cap-top` `x-top` `ascender` `descender` | text |
| Advance | `advance-start` `advance-end` | text |

Closed set; no expressions, no nesting. **Axis is inferred** from the anchor
(`top`/`baseline`/`cap-top` → y; `left`/`right` → x), which removes a parameter and
makes a mismatched pair — `relate(a.top, b.left)` — a refusal rather than a silently
meaningless number.

### 5.3 `measure` — the primitives, not the anchors

`measure` returns **the primitives every anchor derives from**, not the anchors
themselves. Returning fifteen anchors per node would be larger *and* subtly lossy: it
hands over fifteen scalars and no way to compute the sixteenth relationship nobody
enumerated.

```json
{
  "viewBox": [0, 0, 320, 86],
  "space": "root user units, y-down; nested transforms resolved",
  "fonts": [
    { "ref": "f0", "requested": "Satoshi", "resolved": "Satoshi",
      "unitsPerEm": 1000,
      "capHeight": 0.70, "xHeight": 0.50, "ascender": 0.75, "descender": -0.25 }
  ],
  "nodes": [
    { "ref": "#one", "kind": "text", "text": "1", "font": "f0", "fontSize": 62,
      "box":  [0,    15.5, 34.4, 62.0],
      "ink":  [1.2,  18.6, 24.8, 43.4],
      "baseline": 62, "advanceWidth": 34.4 },
    { "ref": "#ord", "kind": "text", "text": "st", "font": "f0", "fontSize": 20,
      "box":  [34.4, 14.0, 18.2, 20.0],
      "ink":  [35.1, 14.2, 16.8, 14.8],
      "baseline": 29, "advanceWidth": 18.2 },
    { "ref": "0.3", "kind": "line", "box": [80, 76.25, 160, 3.5] }
  ]
}
```

Four numbers give all six box anchors. `baseline` plus the font's ratios give all five
font lines — and **the ratios are reported once per font, not per node**, which is
where most of the compression comes from. `advanceWidth` gives `advance-end`.

**The §2 bug is legible in that response.** `#one`'s `ink-right` is 26.0 and its
`advance-end` is 34.4 — 8.4 units apart. And `ink-top` of `#ord` (14.2) vs `#one`
(18.6) is a delta of 4.4, where `cap-top` vs `cap-top` is 3.6: two legitimate readings
of "align the tops", nearly a unit apart.

**Coverage.** Paintable leaves and any id'd node; `<defs>`, gradients and clipPaths
are skipped as having no meaningful geometry. Nodes without ids still appear under a
path ref (`0.3` above) — otherwise an un-id'd drawing measures to nothing, which is a
bad first experience, and seeing the path is what prompts adding an id. A `<text>`
with `<tspan>` children reports each id'd node's own box and the parent's union.
Degenerate nodes (no glyphs, zero size) are reported **with a flag rather than
omitted**, so "empty" is never ambiguous with "not measured".

**`fonts[].resolved`** is how §3.2 is caught in practice: a `requested` ≠ `resolved`
mismatch is visible without a screenshot.

### 5.4 `relate` and `solve`

**`relate(a, b)`** → `{ delta: 2.4, axis: 'y' }`. Verification, in one number.

**`solve({ move, so, equals, offset? })`** → the attribute value that achieves the
relation:

```
solve({ move: '#ord', so: '#ord.cap-top', equals: '#one.cap-top' })
  → { node: '#ord', attr: 'y', value: 29.4 }
```

**`solve` is the operation that removes the iteration**, and the reason to build this
rather than only returning boxes. With `measure`/`relate` alone the loop is still
*measure → compute → write → re-measure*; with `solve` it is *state the intent → get
the number → write it once*.

It is nearly free given the other two: for translation the delta from `relate` **is**
the correction. That gives a clean scope boundary — **`solve` handles translation
only.** It never solves scale or rotation, and does not need to, because alignment is
entirely translational.

**Relations: `equals` and `offset(n)`.** Equal-distribution ("make this gap match that
gap" — the four-point case of §4.8) is **deliberately deferred**: it needs multi-node
solving and a different return shape, and should not hold up the 95% that `equals` and
`offset` cover.

**The space asymmetry, stated because it is otherwise a bug factory.** `measure`
reports in **root** user space with nested transforms resolved — a node inside
`<g transform="translate(40,0)">` should measure where it *actually is*. But an
attribute is written in **local** space. So `solve` returns the node and attribute it
belongs on, never a bare number.

**The organising principle.** If the AI is doing arithmetic on a `measure` result, it
should have called `solve` instead:

> `measure` gives you the map, so you know what to name. `relate` and `solve` do the
> arithmetic, so you never have to.

That is why returning primitives is safe — the derivation happens in the operation
built for it.

### 5.5 Verification belongs in the write

`solve` is arithmetic and will be right. **The risk is the gap between `solve` and the
artifact**: `solve` applies nothing, and the AI then rewrites the *entire* SVG
document by hand through `write_image`. That transcription hop fails in ordinary ways
— the number lands on the wrong node or attribute; the same rewrite also changes the
font-size so the solved value is stale before it is written; an ancestor gains a
`transform` so the local value now means something else; the written document names a
different font than `solve` computed against.

So the check is not of `solve` — it is of **the write**. Which is where it should
live:

```
write_image(… , assert: [ ["#ord.cap-top",  "=", "#one.cap-top"],
                          ["#ord.ink-left", "=", "#one.ink-right", 2] ])

→ written. assertions: cap-top delta 0.0 ✓ · ink gap delta 0.0 ✓
```

Three benefits over solve → write → verify as separate steps: **one round trip
instead of two**; **it cannot be skipped** (models forget to verify — a write that
echoes its relations checks them whether or not anyone remembered); and **the intent
becomes durable**, which is §5.6's recorded comment made checkable rather than merely
noted.

**Advisory, not gating.** Assertions report deltas; they do not refuse the write. A
refusal would be a new failure mode with no upside — the AI may have deliberately
changed something, and a blocked write on a stale assertion is worse than a visible
non-zero delta.

**The cost, stated plainly.** `write_image` today is a pure string scan
(`validateSvg`) with no browser. Assertions require a headless render on write.
Mitigation: **render only when an `assert` block is present** — an opt-in cost, with
no impact on ordinary writes.

**Where `measure` is the right verifier** is the *other* question: "what else moved?"
A `measure` before and after, diffed, catches collateral damage that a targeted
`relate` would miss — the underline that shifted, the node that reflowed because an
ancestor's box changed. Regression checking, not intent checking.

### 5.6 One vocabulary, two surfaces — and two free conventions

The same grammar serves `measure_page` (§3.6): different coordinate space, identical
anchors for the box family. Page nodes additionally want `content-*` / `border-*` /
`margin-*` box-model edges, added then rather than now. **One vocabulary across both
surfaces is worth more than a perfect fit to either**, and it means the anchor set
belongs in a shared module rather than inside either tool.

Two prerequisites are already free — both verified against `validateSvg`, which
returns `{ ok: true, errors: [] }` for each:

- **Addressing needs `id`s**, and `id` is already allowlisted on `<text>` *and*
  `<tspan>`. This is a documentation rule alongside §3.1: *when you draw something you
  intend to position precisely, give it an id.*
- **Recorded intent can be an SVG comment**, and comments pass the validator:
  `<!-- #ord.cap-top = #one.cap-top -->`. This addresses §3.4's staleness limit. It is
  a note, not an enforced constraint — SVG has no constraint system and none is
  proposed — but when the font-size changes the intent is still legible, and `solve`
  can be re-run instead of re-guessed. `solve` could optionally read these back and
  re-derive every recorded relation in one call.
