## Summary

After REQ-352 retired the `§1.contentAnchor` refusal, gigabytealchemy iteration 12 (recaptured 2026-10-01 19:54Z) reads **unmeasured 7**. The seven come from two causes, and neither is specific to this site:

| part | count | source |
|---|---|---|
| populations: `values.bandPaintActual` | 6 | [[BUG-161]] started counting these |
| axes: `arrangement`, reference side | 1 | [[BUG-160]] started reporting this |

Both were already being skipped before; BUG-160/161 made them *visible*. This ticket makes them *measured*. Expected result: unmeasured 7 → 0 on gigabytealchemy, and the same two causes removed on every site with full-bleed bands (nearly all of them).

## Cause 1 — a band's own paint has nowhere to land (6)

The reproduction emits each section band as a full-bleed box (gigabytealchemy: 6 boxes at x=0, width 1280, at y = 0, 800, 1288, 1882, 3139, 4260). `isBandPaint` + `bandPaintRepresented` (`values-diff.ts:3788`) correctly route these out of `unpairedActual`, because the reference represents the band on its **section record** (`SectionValues`, `values-diff.ts:318`) — fill, imagery, overlay, padding, text-align.

But `SectionValues` has no field for the box's own **opacity, filter, blend mode, corner radius or shadow**. So those axes are compared on neither side, and `gate-core.ts:983` says so. Concrete case: the hero band paints at `opacity: 0.49` under `filter: brightness(0.67)` and no check reads either fact.

## Cause 2 — `arrangement` unread for 22 of 59 pairs (1)

`arrangement` (CRITICAL tier) relates an element to the one before it in **that side's own** top-to-bottom sort. The two sides don't sort the same list — the reproduction emits band containers the reference has no counterpart for — so `relate` returns null on one side for 22 of 59 paired elements, and the both-sides guard skips them (`values-diff.ts:3944`, reason from `arrangementUnreadReason`). This is a CRITICAL-tier axis going uncompared on over a third of the page — the more important of the two causes, despite counting as 1.

## Behaviour wanted

1. **Band paint is compared.** For a section band, the box's own `opacity`, `filter`, `blendMode`, `borderRadiusPx` and `boxShadow` are read on both sides and compared, so a band whose paint matches produces no delta and no unmeasured entry, and a band whose paint differs produces a delta naming the axis. The implementer chooses the mechanism — carry the axes on the section record (capture + extractor), or compare the band-paint box against the reference band element directly — and records why. If capture-side, the axes are optional-on-read and a bundle taken before them stays **unmeasured**, never compared against a default (REQ-277 / BUG-106 discipline).
2. **`bandPaintActual` drains.** A band-paint box whose paint axes were all compared no longer enters `values.bandPaintActual`; only boxes with an axis still uncomparable stay there. The count keeps its meaning — "partly compared" — and stops being permanent.
3. **`arrangement` is compared over one population.** Both sides compute an element's predecessor over the same list — the paired elements, in each side's order — so a synthesized reproduction container with no reference counterpart cannot become, or hide, an element's predecessor. A pair is skipped only when an element genuinely has no predecessor on that side.
4. **No new silence.** Neither change may convert an unmeasured entry into a pass by defaulting a missing value; an axis still unreadable on a side stays in `unmeasuredAxes` / `bandPaintActual`.
