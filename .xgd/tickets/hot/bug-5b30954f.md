## Symptom (operator, after BUG-367 was deployed)

The operator opened a shop's checkout page in the builder draft:
- Continue to payment now greys out, but it is still full width, its label is not centred, and there is no Cancel beside it. BUG-367's items 8–9 are not visible.
- The ship-to prompt still reads the site's own wording. This is expected: BUG-367 changed only the framework default. The site's `countryPrompt` override has to be removed as a site edit, which is not code.
- Continue to payment answers "Payment opens on your published site. Only you see this." The operator wants to test checkout and cannot do so without publishing.

## Likely cause (to confirm by reading the site's checkout page first)

- BUG-367 put the action row (label-sized, right-aligned, Cancel at its left, stacked on phones) into the checkout component's **default template** (`packages/framework/src/l2/checkout.ts`). A site whose checkout page carries its **own** template, authored by the consultant, keeps its own `continue` node: full width, no Cancel.
- Label centring is skipped wherever an authored `textAlign` is present, by design. It is also skipped wherever the control isn't drawn as a `<button>` or a filled or bordered link.

## Fix

1. **The checkout's actions look right on every checkout page, not only the default.** Wherever a template places the `continue` control, the renderer draws the BUG-367 action row: label-sized and right-aligned from 768px, a matching Cancel on its left in the secondary style, and both stacked full width on phones with Continue on top. A template that already places `cancel` keeps its own placement.
2. **Button labels are centred unless the node explicitly asks otherwise.** "Explicitly" means a `textAlign` on that control's own node. A value inherited from its container doesn't count.
3. **The draft's checkout works exactly like the published site's.** This supersedes BUG-367 item 2 ("the draft never takes money"). The operator found no reason for that rule, and none holds up: the draft is visible only to the signed-in owner, so no visitor can buy from it. Price, stock and shipping are read from the same live records either way. A purchase from the draft is a real order through the same `start`, webhook and order flow.
   - In the builder preview, Continue opens a Stripe Checkout session just as it does when published. Stripe's success and cancel return URLs point at the preview's own checkout-complete and checkout-cancelled pages.
   - There is no test-order marking and no special case. Whether money moves is up to the Stripe connection's mode: test mode takes test cards and charges nothing; live mode charges for real, exactly as on the published site, and the owner refunds in Stripe.
   - The owner-only "Payment opens on your published site" notice and its preview-only branch in `startCheckout` are deleted.
4. **The consultant can clear a site's ship-to override** (no code needed if `update_component` already reaches `countryPrompt`). The fix session confirms this, and the playbook notes that the framework default is now "Please select a region for delivery".

## Test plan

- UAT (Chromium, rendered page): on a checkout page with an authored template that places `continue` full width with `textAlign: left` on its container, the rendered Continue is label-sized and right-aligned at 1024px. Cancel sits to its left at the same height. Both are full width at 375px. The label is centred.
- UAT (workers, real D1, stubbed Stripe): a preview `start` creates a Checkout session and a pending order exactly as a published `start` does, with return URLs on the preview's complete and cancelled pages. The BUG-367 notice is never returned.
- Regression scope: BUG-367, BUG-363 and REQ-643 suites.
