## Notes for the Editor

**The violation is one test edit and touches no production code.** The
behaviour AC-967 describes exists and works — `toolbar.js:124` builds the
options from the `sites` it is handed, `main.js:22` fetches that list from
`/api/sites`, and `builder.ts` answers it from the store. What is missing is
evidence joining those three, and `…-mounted.test.ts` was created last cycle for
exactly this shape of problem (a live origin plus a mounted chrome in one file).
Putting the store→origin assertion in that file's *unconditional* half is worth
more than a stronger jsdom assertion would be: it is the only repair here that
yields evidence on a machine with no component store.

**Finding 3 is the dominant fact about this capability's evidence and should
not be read as a pass.** Twelve of twenty-two criteria have no executed
assertion on this branch, and three of them report green while asserting
nothing. That is intent-sanctioned and correctly signposted, but a regression
run on this worktree cannot distinguish a working workspace chrome from an
absent one. If the regression gate is meant to *prove* this capability rather
than merely not contradict it, provisioning the shared artifact store in the
regression environment is the single highest-value change available — it would
convert twelve conditional criteria into executed ones at zero test cost.

**BUG-32 is landing and touches all three suites.** It is `free_coded` (not
reconciled) and absent from this branch, which still writes `@gendevlabs`
literally at `…-origin.test.ts:335` and `webui.ts:33`. When it reconciles, those
assertions move to `WEBUI_SCOPE`. Nothing in the story body or any AC names a
scope, so no matrix element is stale — but an editor working these files should
expect the conflict.
