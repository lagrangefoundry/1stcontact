## Story

**As a** small-business owner talking to the site assistant,
**I want** the assistant's knowledge of what the product itself does — what
components a site can use, what the layout vocabulary means, what may be changed
and how — to come from the product's own machine-readable definitions,
**so that** what I am told is what the product actually does today, and cannot be
a sentence somebody wrote once and forgot to update.

## Description

The shipped knowledge base is a corpus of documents the assistant retrieves
from. Once architecture documents are excluded from it (DOC-39 §3.1), that
corpus holds consultation material and **nothing that says what the product
does** — the assistant discusses design well and cannot say what a component is.

This capability closes that hole without anybody writing the missing documents.
A second corpus producer **generates** reference documents from the product's
own machine-readable sources of truth, into the same corpus directory, indexed
and mapped like any other member. The assistant does not know which of its
knowledge was written and which was generated; it asks a question and gets an
answer.

Three sources, three reference documents, one source each:

| Source of truth | Reference document |
|---|---|
| the framework's component (behavior) catalogue | what components exist, the settings each takes, the parts of a page each holds |
| the L1 element schemas and their validation envelope | the layout vocabulary, its value sets, and the limits every page is held to |
| the declared control surface | what the assistant may change, how, and what is deliberately impossible |

The discipline that makes them trustworthy is part of the capability, not an
implementation detail: each reference reads **exactly one source and no
document**, so every sentence is either rendered from the shape of that source or
lifted verbatim from prose the source itself carries. A sentence copied out of an
authored document would recreate the two-sources drift this exists to prevent; an
invented one would be a fact with no source at all.

**In scope**: generating the three reference documents into the shipped corpus on
every corpus export and every index build; each document asserting its own
knowledge-base membership; the two producers coexisting in one directory without
destroying each other's output; not rewriting an unchanged document; naming the
source in the document itself; and the assistant answering a product question
from the generated reference.

**Out of scope**: authoring system-KB documents by hand (DOC-39 §3.5, deliberately
deferred); changing any of the three sources — this reads them; and how the
generated references cluster in the awareness map (see Reconciliation Decisions).

## Technical Context

- The corpus now has **two producers** writing into one directory: the doc-ticket
  export (CAP-100, STORY-117) and this generator. They are separable by
  namespace — generated documents occupy a reserved `REF-` filename namespace,
  each producer sweeps only its own, so neither can delete the other's output
  whatever order they run in. Without the split, a build could lose a reference
  to ordering, and a knowledge-base test fixture that supplies its own stubbed
  ticket store would silently receive three documents it never asked for — which,
  for a suite tuning a corpus to make a clustering assertion, is destructive.
- **Membership is read from the knowledge-base declaration, never hardcoded.** An
  exported ticket satisfies the corpus predicate by carrying its own fields; a
  generated document has no ticket and must assert membership itself. Hardcoding
  today's predicate would drop the references out of the knowledge base the day it
  changed — the one failure a generated document is supposed to be incapable of,
  and a day that has already come once (the predicate was a boolean opt-in field
  until REQ-164 made it a document kind and left the shipped corpus unrestricted).
  This is the dependency on plan item 1 (STORY-117 / REQ-164).
- **The frontmatter dialect is the export's own**, because the same corpus
  directory reader parses both producers' output; a second dialect in one
  directory would be a silent reader failure rather than a formatting preference.
- **An unchanged generated document is not rewritten.** The corpus reader derives a
  document's timestamp from its file stamp and the index keys its incremental
  manifest on that stamp, so rewriting an identical file every build would
  re-embed the entire reference every build, at cost, while telling the ranker
  every document had just changed.
- **This is not the tool manual.** The shared AI library already projects the same
  control-surface declaration into a manual the model is primed with; that manual
  is rendered *through a grant* — the operations one role was given, in the second
  person, as instructions. A reference describes the whole declared surface to a
  reader asking what the product can do. One source, two renderings; the rule is
  one source per fact, not one rendering.
- Prose harvested from a source's own doc comments is **scoped to the declaration
  it was written in**. A flat field-to-prose map is the trap this exists to avoid:
  a term documented once on one shape and left undocumented on a dozen others
  would have that definition filed against all of them and read as authoritative —
  a confidently wrong sentence in a generated reference, which is the one thing it
  must never contain.
- Related capabilities: CAP-100 (System Knowledge Base — the corpus, its index and
  its generated map) hosts the corpus, index, chunking and awareness map this
  writes into; CAP-72 (Behavior Module Contract & Catalog), CAP-70 (Framework
  Substrate: L1 Layout, Values & Behavior Modules) and CAP-92 (Site Control
  Surface: Declared, Granted, Validated & Audited) own the three sources, which
  this reads and never changes.

## Reconciliation Decisions

- **Granularity: one reference document per source** (decided at reconciliation,
  2026-09-10): REQ-165 names three sources and three projections but leaves the
  granularity open — one catalogue per source versus one document per component.
  The landed choice is one document per source, and the reason is retrieval: a
  chunk is only useful if it is coherent alone, and with a small catalogue a
  per-component split produces documents too small to cluster and a map territory
  per component. Formalized as the set assertion in AC "a reference document for
  every source". This is reconciliation settling a question the intent left open,
  on the evidence of how retrieval works, not an operator request.

- **`1c kb status` reports the two producers separately** (decided at
  reconciliation, 2026-09-10): REQ-165's acceptance list is silent on what the
  build reports. The landed status line names the exported count and the generated
  count rather than one total, because with two producers writing into one
  directory a single number no longer says how much of the corpus came from the
  ticket store — and a corpus whose generated references are missing has exactly
  the same shape as one that is merely small, which is the silent-short-corpus
  failure REQ-164 exists to close. Formalized as its own AC; the reporting rule
  is the same one item 1 applies to the ticket half.

- **"No projected fact is also stated in an authored document" stays
  review-asserted** (decided at reconciliation, 2026-09-10): REQ-165 states this
  acceptance item and states in the same breath that it is *asserted by review*.
  It has no observable boundary — no test can distinguish a sentence rendered from
  a source from an identical sentence copied out of a document — so it is
  deliberately NOT formalized as an AC. The testable half of the same discipline is
  covered instead: every component/element/operation described is one the source
  declares, and nothing outside the source is described (the "describes nothing the
  catalogue does not carry" and exhaustiveness ACs).

- **How generated references cluster in the awareness map is left open** (decided
  at reconciliation, 2026-09-10): REQ-165 records this as an open question — the
  references are a different kind of knowledge from consultation material and may
  cluster oddly beside it. The intent is explicit that they are indexed and mapped
  like any other member, which the ACs assert; no AC pins territory composition, so
  a later map-clustering change is not a regression against this story.

No contradiction between intent and code was found for this plan item.

## Dependencies

- Plan item 1 — System Knowledge Base corpus selection (STORY-117 / REQ-164).
  Membership is derived from the knowledge-base declaration, and REQ-164 is what
  changed that declaration to an unrestricted corpus and moved membership to a
  document kind. The derivation must hold across that change, which is precisely
  why it is derived rather than restated.
