## BUG-31: 1c deploy: --sandbox writes to a real site's R2 keyspace

## Problem

`1c deploy --sandbox` reads from the throwaway `storage/sandbox/` tree but writes
to the **same R2 keyspace as a real site**. The local store carefully separates
the two roots; the R2 layout flattens them.

`--sandbox` is honoured everywhere locally — `commands.ts:36` resolves
`root: Root = opts.sandbox ? 'sandbox' : 'sites'`, and `deploy.ts:118-123` passes
it to `cmdRender`, `readHistory`, `draftDir` and `revisionDir`. It then stops
mattering. Every R2 key is built with no root component:

| Location | Key |
|---|---|
| `tools/generate/src/deploy/manifest.ts:39` | `` `sites/${slug}/manifest.json` `` |
| `tools/generate/src/deploy/deploy.ts:131` | `` `sites/${slug}/preview/${sha}` `` |
| `tools/generate/src/deploy/deploy.ts:132` | `` `sites/${slug}/rev/${padRevision(live)}` `` |
| `tools/generate/src/deploy/deploy.ts:285` | `` client.list(`sites/${slug}/`) `` (prune) |
| `apps/public-site/src/site-store.ts:89` | `` `sites/${slug}/preview/${preview.sha}/out` `` |
| `apps/public-site/src/site-store.ts:93` | `` `sites/${slug}/rev/${padRevision(manifest.live)}/out` `` |

Found by code reading, not by execution — the destructive paths were not run
against the live bucket.

## Consequences, in order of severity

1. **A sandbox deploy can silently replace a real site's published output.**
   `1c deploy --sandbox <slug> --channel published` computes `live` from the
   *sandbox* history and uploads to `sites/<slug>/rev/NNNN/`, then sets
   `manifest.live`. Sandbox revision 1 overwrites the real site's revision 1
   bytes, and `/site/<slug>/` starts serving throwaway content.
2. **Throwaway experiments become world-readable.** With no collision at all, any
   `1c deploy --sandbox <slug>` publishes to
   `https://1stcontact.io/site/<slug>/draft/<sha>/`. `storage/sandbox/` is
   gitignored and documented as scratch space; nothing about it suggests its
   contents become publicly servable.
3. **Manifest cross-contamination.** `readManifest(client, slug)` (`deploy.ts:141`)
   reads the real site's manifest, appends the sandbox snapshot as a legitimate
   preview, and writes it back. No entry is lost, but the real site's manifest now
   references sandbox content.
4. **`--prune` enumerates the wrong site.** `deploy.ts:285` lists the shared
   `sites/<slug>/` prefix, so a sandbox prune walks the real site's keys.

Latent today: no sandbox site currently shares a slug with a real one, and no
`--sandbox` deploy has been run. The failure mode is silent when it does happen.

## Root cause

The R2 key layout omits the root that every other layer preserves. [[DOC-12]] §3.1
makes the two roots a stated invariant, and `distDir(ctx, slug, channel)` already
namespaces rendered output as `storage/dist/<root>/<slug>/<channel>/`.

The R2 mapping specified in [[REQ-110]] had no root component either, so the
implementation is faithful to a spec that was wrong. [[DOC-12]] §7 inherited the
same omission and needs the same correction.

## Fix

**Invariant to restore: sandbox content is never publicly servable, and sandbox
keys never collide with real ones.**

- Namespace every R2 key by root: `sites/<slug>/…` and `sandbox/<slug>/…`.
  Thread `root` through `manifestKey`, the snapshot prefix, and the prune listing.
- `SiteStore` in the Worker resolves **only** `sites/`. There is no route that can
  reach a `sandbox/` key.
- Correct the [[DOC-12]] §7 mapping table to show the root in the key layout.

**Resolved: option (b) — namespace, do not refuse.** The `Fix` bullets above and
every acceptance criterion below describe a namespaced sandbox root, so that is
what landed. It also keeps `--sandbox` uniform across every command rather than
adding a one-command refusal, which is the simpler shape once the root is
threaded (~20 lines). Refusing outright (option (a)) remains a small follow-on if
the sandbox root proves to be dead weight.

Neither option lets sandbox exercise the *serving* path — that still needs a
throwaway slug under `storage/sites/` (`harbor-cafe` already has a published
revision and is fictional). The CLI help now says so.

## What changed

- `manifestKey(root, slug)`, `readManifest(client, root, slug)` and
  `writeManifest(client, root, slug, …)` take the root; `cmdDeploy` passes
  `ctx.root`. The snapshot prefix and the `--prune` listing are built from it too.
- `DeployResult` gains `root`, and `url` becomes `string | null`: a sandbox
  deploy uploads and indexes normally but reports **no URL**, because nothing can
  serve it. `formatDeployReport` prints the prefix and
  `(sandbox — not publicly reachable)` in its place.
- The Worker's servable root is now the named constant `SERVABLE_ROOT = 'sites'`.
  No root is ever derived from a request, so a sandbox key is unreachable **by
  construction** rather than by a check that could be missed.
- CLI help for `1c deploy` documents the sandbox root and points at the throwaway-
  slug workaround for exercising serving.
- [[DOC-12]] §7's mapping table now shows `<root>` in the key layout, with a note
  that only `sites/` is servable.

## Acceptance

All five UATs live in `tests/bug31-sandbox-r2-namespace.test.ts` and drive the
real `cmdDeploy` and the Worker's real `fetch` entry point, with R2 faked only at
the upload boundary and the binding:

- `test_UAT_FC_BUG-31_sandbox_keys_are_namespaced` — a sandbox deploy writes no
  key under `sites/`; the bytes land under `sandbox/`; `url` is null and the
  report says the snapshot is not publicly reachable.
- `test_UAT_FC_BUG-31_sandbox_cannot_overwrite_real_published` — a real and a
  sandbox site share a slug and both publish revision 1; `--sandbox --channel
  published` leaves the real site's `manifest.live`, its `rev/0001/` bytes, and
  what `/site/<slug>/` serves entirely unchanged.
- `test_UAT_FC_BUG-31_sandbox_manifest_is_separate` — a sandbox deploy leaves the
  real manifest byte-identical, and each root indexes only its own preview.
- `test_UAT_FC_BUG-31_worker_never_serves_sandbox` — a slug deployed only to
  sandbox 404s on every route the grammar admits, including a path that names the
  sandbox key itself.
- `test_UAT_FC_BUG-31_prune_scoped_to_root` — with an orphan in each root, a
  sandbox prune deletes only the sandbox orphan and leaves the real one in place.

Regression scope run green: the five new UATs plus `req110-r2-deploy`,
`req111-public-site-serving`, `req113-worker-extensionless-urls`,
`deploy-workflow`, `public-site`, `control-app` (28 tests). `tsc --noEmit` clean
for `tools/generate` and `apps/public-site`.

## Dependencies

Fixes the layout shipped by [[REQ-110]] and consumed by [[REQ-111]]. Requires the
matching [[DOC-12]] §7 correction.

## REQ-114: L1 palette colour model (literal base, palette overlay) + retrofit existing sites

## What this builds

The **palette colour model** for L1 ([[DOC-23]] §5), plus the retrofit of every
existing site onto it.

Today `l1Color` is hex-only by construction, so **every colour in every site is an
individually chosen literal** and there is no way to change one conceptual colour
and have its uses follow. This ticket makes the palette the unit of colour change,
without weakening reproduction.

## The model (DOC-23 §5)

Colour takes the same shape geometry already has — **absolute base, overlay**:

- **A literal hex is always valid.** Transcription from a capture stays lossless
  and inference-free; nothing is gated on a palette existing.
- **A palette reference is the refinement**, resolving to an entry whose value is
  a hex — so rendered output is identical either way.

## Scope

### 1. Schema (`packages/site-schema`)

- **Palette shape**, site-level: an ordered map of named entries
  `{ name → { value: hex, steps?: { <step> : hex } } }`. **Arbitrary size**; names
  are free-form (validated as kebab-case), with [[DOC-23]] §5.4's standard
  vocabulary as a *starting set*, not a schema constraint.
- **Widen `l1Color`** from hex-only to `hex | PaletteRef`. It is one type alias used
  in **12 places** (gradient stops, shadows, borders, textures, link states, surface
  fills…), so all 12 inherit the change.
- **Reference syntax**: a role name, optionally with a step. Must not collide with
  the hex grammar. Exact form is an implementation choice; keep it a *typed object*
  rather than a magic string if that reads better against the strict-object rule.
- **Validation**: a reference naming a missing entry is a **validation failure**,
  never a render-time fallback ([[DOC-23]] §6). Palette entries are opaque —
  translucency stays a separate axis, so no alpha in an entry.

### 2. Renderer (`packages/framework/src/l1/render.ts`)

- Resolve references to their entry's hex at render time.
- The renderer stays the only emitter; no new raw-CSS path, no `var()` hole opened
  in L1's output unless it is provably equivalent and still round-trips.

### 3. Retrofit of existing sites

Convert `storage/sites/{xgd,gigabytealchemy,1stcontact,harbor-cafe}` (and the
sandbox sites if cheap) from literals to palette references:

- **Alpha collapse first — exact, zero inference.** `xgd` carries `#2e86a3`,
  `#2e86a3a6` (α .65), `#2e86a355` (α .33): one colour at three opacities → one
  entry plus the existing opacity axis. This is mechanical and lossless.
- **Then ramp grouping — mild, reviewable inference.** Measured hue families:
  `xgd` neutrals hue 215–220 at lightness 17/34/46/65/84; brand teal hue 192–196 at
  33/41/54/95; warm surfaces hue 49–53 at 87/94/99. `gigabytealchemy` shows ~6 such
  families across 29 colours. Group each family into one role with steps.
- **Anything unclustered stays its own entry.** A slightly large palette is a fine
  outcome; a *wrong* one is not.
- Name entries from [[DOC-23]] §5.4's vocabulary where the role is obvious.

### 4. Retire the legacy palette — completely

The closed 15-slot `paletteTokensSchema` is what this ticket replaces. Both cannot
survive: two colour systems is the legacy-mode state the project forbids. **Delete
it and everything that exists only to serve it.** Scope is the *colour* group only
— typography, spacing, radius, shadow and breakpoint tokens are a different axis
family with no replacement here and stay untouched.

Surveyed targets (verify each is fully cut, do not leave stubs):

**`packages/site-schema`**
- `paletteTokensSchema` and the `PaletteTokens` type.
- The required `palette:` key on `themeTokensSchema` (`schema.ts` ~L914) — every
  site currently must carry one.
- `layerColorRoleSchema` (`schema.ts` L286) — a second closed colour-role enum
  (13 names) used at L313 (layer border colour) and L354 (layer text colour). Layers
  belonged to the deleted semantic layout modules; confirm dead, then delete with
  its two use sites.

**`packages/framework/src/tokens`**
- `paletteVars()` (`css.ts` L102-106) and the `t.palette` spread (`css.ts` L30) —
  the emitter of every `--color-<role>` custom property.
- The **dark-mode palette override** (`css.ts` L50-60, `options.dark` →
  `@media (prefers-color-scheme: dark)`). **No caller passes `dark:`** — confirmed
  unused, so it goes with the palette rather than being ported.
- The `palette` block in `defaults.ts` and `PartialPalette` in `contract.ts`.

**`packages/framework/src/modules`** — the residual aesthetic resolvers, now that
REQ-96 is finished. Colour-role references only; leave the non-colour dials alone:
- `dials.ts` — the colour-role dial resolving to `var(--color-<role>)` (L66).
- `text-style.ts` — the palette-role alias (`accent` → `var(--color-accent)`, L103).
- `markdown.ts` — the eight `blockquote.fc-callout--*` colour rules (L48-62).

**`tools/generate`**
- `render.ts` L139 emits `body { … background: var(--color-bg); color: var(--color-text) }`
  — the only live `--color-*` consumption on the L1 path (two uses in a rendered
  page). Its replacement already exists: the L1 document's own `background` field
  ([[DOC-23]] §2). Page-level text colour needs an equivalent home; do not
  reintroduce a token to solve it.

**`storage/sites/*/draft/site.json`** — drop `theme.palette` from all four
(`1stcontact` 9 keys, `gigabytealchemy` 15, `harbor-cafe` 9, `xgd` 15) as part of
the retrofit in §3.

### 5. Tooling

- Whatever the retrofit needs to be repeatable rather than hand-done — at minimum
  a colour census over a site's pages (the analysis in [[DOC-23]] §5.3 was ad hoc;
  it should be a command).
- The capture→L1 fold continues to emit **literals**. Palette assignment is a
  separate, re-runnable pass over a folded site, not a change to the fold.

## Non-goals

- **No colour picker / palette editor UI.** Deferred; this ticket is the data model
  and the retrofit. The editor is [[DOC-28]]'s phase 2 and depends on
  `xgd-framework` REQ-55.
- **No change to the capture→L1 fold's output.** It stays literal-only.
- **The non-colour token groups stay.** Typography, spacing, radius, shadow and
  breakpoint tokens are out of scope — §4 retires the colour group only.

## Acceptance criteria

1. A site definition may declare a palette of arbitrary size with free-form
   kebab-case entry names; a colour axis accepts either a hex literal or a
   reference to an existing entry.
2. A reference to a non-existent entry (or step) fails validation — no render-time
   fallback, no silent default.
3. **Conversion is pixel-identical**: for every retrofitted site, the render before
   and after the retrofit is byte-identical (or, where byte-identity is impossible,
   passes the values-diff gate with zero delta). Any difference is a conversion bug,
   not an accepted cost ([[DOC-23]] §7).
4. Documents using only literals validate and render exactly as they do today —
   the palette is optional, and no existing site is broken by the schema widening.
5. `xgd`'s three `#2e86a3` alpha variants resolve to **one** palette entry plus the
   opacity axis.
6. All four `storage/sites/*` sites are retrofitted, and the resulting palette for
   each is small enough to be a palette rather than a colour list (report the count;
   `xgd` should land well under its current 15 distinct RGB).
7. A repeatable colour-census command exists and reproduces the [[DOC-23]] §5.3
   table.
8. **`paletteTokensSchema`, `layerColorRoleSchema` and `PaletteTokens` no longer
   exist**, `themeTokensSchema` has no `palette` key, and no site.json carries one.
   A grep for `--color-` across `packages/` and `tools/` returns nothing outside
   the new palette model.
9. No rendered page emits a `--color-*` custom property, and no stylesheet
   references one. The page's background and text colour come from the L1 document,
   not a token.
10. The dark-mode palette override path is gone (confirmed to have no callers), not
   ported forward. If dark mode is wanted later it is designed against the new
   model, not resurrected from the old one.
11. The non-colour token groups (typography, spacing, radius, shadow, breakpoints)
   are untouched and still validate/emit exactly as before.
12. Full suite green, and a clean `pnpm -r build` typechecks — the schema cut is
   wide enough that stale `dist/` output would mask type drift.

## Origin

[[DOC-23]] §5, written from the CHAT-9 discussion of the web editor's colour
surface. The measured evidence in §5.3 withdrew an earlier assumption that
palette-driven colour threatened reproduction fidelity.

## REQ-116: The edit render: non-functional channel, derived segments, L1 addresses, outlines

## What this builds

The **edit render** — a third render channel producing the page the editor works on:
deliberately non-functional, showing everything at once, segmented, and stamped with
addresses that map a clicked element back to the definition that produced it.

Renderer-side only; no UI, and testable entirely on rendered output. Phase 1 ticket
**T2** of [[DOC-28]] §12. Design: [[DOC-28]] §5, §6.

## Why a render and not an overlay

The alternative — a client-side overlay hit-testing the normal page — was rejected.
The renderer is already walking the L1 tree, so it knows which node it is emitting
and can stamp the address as it goes; a client would have to rebuild that mapping
and keep it valid. Making edit mode a render also makes "the page does not work"
honest (we simply do not emit the link targets, the form action, or the behaviour
scripts) rather than a working page smothered in JavaScript.

## Scope

### 1. The channel

A third channel alongside published and draft preview ([[DOC-8]] §4.1): the **same
L1 document and the same renderer**, rendered differently. It is never published,
never content-addressed, and never enters `history.json` ([[DOC-12]] §11).

### 2. The page deliberately does not work

- **Links have no target** — clicking a link edits its copy, it does not navigate.
- **Forms have no action**; behaviour scripts are not emitted — nothing submits or
  fetches.
- **No motion** — the motion script is not emitted.

### 3. Content renders in its settled state — load-bearing

Emitting content in its *initial* state is the trap: pages that fade text in on
scroll would render that copy **invisible** and its segment unclickable, which is
worse than leaving the animation on. The edit render emits the **final, settled**
state.

Generalised: **the edit render shows all content simultaneously**, because nothing
is interactive to reveal it. Worked example — a carousel's slides are all in the DOM
(a scroll track, not `display:none`), so their copy is reachable, but with behaviour
off they sit scrolled out of view; the edit render lets the track **stack** so every
slide is visible at once.

### 4. Derived segmentation

Segments are **derived from the tree, not declared** in the definition — no schema
change, no author burden, nothing for the AI to forget ([[DOC-28]] §6.2):

| L1 node | Segment kind |
|---|---|
| `text` | copy segment |
| `image` | image segment |
| `box`/`container` carrying paint (background, fill, border…) | container segment |
| behavior-module instance | module segment |

Regions with nothing editable are **not outlined**, so the outlines themselves tell
the user what is available. Measured expectation on `storage/sites/xgd/draft`: ~62
copy, ~10 container, 1 module slot; nesting 2–5 deep.

### 5. Addresses

- **Behavior-module instances** already carry `data-fc-module` / `data-fc-type`
  (landed, CHAT-9 M1). Unchanged.
- **L1 nodes** get a **render-scoped structural path** — the renderer's own walk of
  child indices — stamped in the edit render **only**. Content inside a module slot
  is addressed the same way, rooted at the instance rather than the document.

The address is **render-scoped, not persistent**: it need only stay valid for the
lifetime of the document the client is displaying, because every edit re-renders and
regenerates it. So a structural path is safe here despite the usual objection that
reordering breaks it — reordering produces a new render.

**L1's existing `id` must not be reused for this.** REQ-106 gave it a different job
(real DOM `id`, so `href="#how"` resolves and `for`↔`id` wires up); it is optional
and sparse — 34 of 128 elements on `xgd/home` — and user-visible in URLs.

### 6. Outlines

Drawn **by the renderer**, which knows each segment's box, rather than hit-tested and
computed by the client. Faint by default; the hover treatment (brighter outline, small
movement) is the client's to add in T3.

## Non-goals

- **No UI, no modals, no click handling** — T3.
- **No change to the published or draft-preview channels.** Handles and outlines
  exist only in the edit render; published bytes are untouched.
- **No preserved animation.** Rejected for phase 1: untriggered reveals hide
  segments, motion competes with the outline signal, and a segment mid-transition has
  no stable box to outline.
- **No structural editing affordances** — no drag handles, no insert points.
  Structure stays with the AI ([[DOC-28]] §7.3).

## Acceptance criteria

1. The edit channel renders the same document as the draft preview, with links
   carrying no navigable target, no form action, and no behaviour or motion scripts
   emitted.
2. A page whose copy is revealed by a scroll-triggered animation renders that copy
   **visible** in the edit render.
3. A carousel's slides are all simultaneously visible in the edit render.
4. Every `text` and `image` node, every painted `box`/`container`, and every module
   instance carries a segment address; a node with nothing editable carries none and
   is not outlined.
5. An address resolves to exactly one node in the definition, and resolving every
   stamped address on a page yields the nodes it was derived from.
6. Reordering sibling nodes and re-rendering yields addresses that still resolve
   correctly — the client resolves only against the render it is displaying.
7. Copy inside a behavior module's slot is addressable, rooted at the instance.
8. The published and draft-preview renders of the same page are **byte-identical
   before and after this ticket** — no handle, outline or attribute leaks.
9. L1's `id` is unchanged in meaning and emission; nothing in this ticket writes or
   depends on it.

## Implementation (free-coded)

Landed as a render **mode** threaded through the existing single emitter — no
second renderer, no overlay, no schema change.

**Framework** (`packages/framework/src/l1/render.ts`)
- `L1RenderOptions.edit` / `renderL1Fragment(..., { edit })`. `emitNode` now carries
  the child-index `path` it walked.
- `segmentKind()` derives the segment from the tree: `text`→copy, `image`→image,
  painted `box`/`container`→container, mounted `slot`→module. "Carries paint" is
  answered by asking `surfaceDecls` rather than by a hand-kept axis list, so future
  paint axes are covered automatically. Returns `null` — no address, no outline —
  for unpainted containers, unmounted slots and `control` leaves.
- Stamps `data-l1-path` + `data-l1-segment` together, segments only.
- Edit render drops: the link's `href`/`target`/`rel` (the `<a>` ELEMENT stays, so
  the render differs by the missing target and nothing else), the reveal rules AND
  the `l1-rv` class, and the pointer-accent rules (inert without their script).
- `L1_EDIT_CSS` — one faint `outline` per segment. `outline`, not `border`: painted
  outside layout, so becoming a segment cannot move a box.

**Behavior modules** own their own settled state, since only they know which
attributes carry behaviour. `contact-form` drops `action`/`method`; `carousel`
wraps its track via a rule keyed on the document-level `data-fc-edit` marker.

**Pipeline / CLI** — `RenderChannel` gains `'edit'` → `dist/<slug>/edit/`;
`1c render <slug> --edit` (always from `draft/`; a revision is immutable, so there
is nothing on it to edit). Edit pages reference no `capabilities.js`, and none is
written beside them.

### Addressing

Dot-joined child indices rooted at the render's **root node list** — `[doc.root]`
for a document, the subtree array for a fragment. One resolution rule serves both:
index the list, then `children` at each later step. Slot content is therefore
addressed relative to its instance, disambiguated by the enclosing
`data-fc-module` / `data-l1-slot`. Render-scoped only; `id` (REQ-106) untouched.

### Verification

`tests/req116-edit-render.test.ts` — 8 UATs covering all 9 ACs, driven through
`1c render --edit` and asserting on the bytes written to disk. AC5/AC7 share one
test; AC8/AC9 share one. Full suite: 992 passed. Four pre-existing failures in the
fold/gate reconciliation tests were confirmed present at HEAD without these
changes (they arrived with REQ-114's commit) and are unrelated.
