## Symptom

On production, 2026-11-08, after a redeploy that included BUG-380's index fixes, typing "hello" to the consultant in a business's builder fails:

    The assistant could not be reached: POST /api/ai/session → 500
    embeddings.bin holds 33792 float(s), which is not a whole number of rows for 86 metadata entr(ies) — the index is corrupt

33792 floats is exactly 88 rows of 384, against 86 metadata entries: the vectors and the metadata were written by two different writers that interleaved. That's the corruption BUG-380 names.

## Root cause

- BUG-380 (`8053cf54b8`) made the business's Library index heal itself, but only on the **refresh** path. `ProjectKnowledge.healing()` (`apps/control-app/src/knowledge.ts`) rebuilds a corrupt index when a `refreshIndex()` build fails.
- The **readers** on the session path, `search()` and `clusteredLandscape()`'s `loadIndex()`, still call the component's `loadIndex` / `kmSearch` directly. They throw the corruption error, and `POST /api/ai/session` returns 500. Until something writes a Library material and triggers a refresh, the business's consultant can't be reached at all.
- The corruption may also still arise. BUG-380's "one index writer" serialises writers within one instance. Separate requests can still each run their own writer against the same R2 objects; a handoff copy (REQ-654) lands Library tickets in batches of 25, one request per batch. Confirm whether this business's index was written that way, and whether two concurrent requests can still interleave `embeddings.bin` and `metadata` writes.

## Fix

- **A corrupt index never fails a session.** Any read of a business's Library index (the session's priming and landscape, `search`, the access-point check) that finds the index corrupt rebuilds it from the stored materials through the same single writer and rebuild `healing()` uses. That rebuild logs `kb_index_rebuilt` once. If the rebuild itself can't run in time, the session starts without Library search for that turn and logs that it did, rather than returning 500.
- **Writers can't interleave across requests.** Every write of a business's index (the per-material refresh, the handoff/import landing, a rebuild) goes through one coordination point per business (e.g. the business's Durable Object or a lease row). A second writer waits or skips rather than writing alongside it. Vectors and metadata are written so that a reader never sees one updated without the other, e.g. both in one object or with a generation number both carry.
- The fix covers the chunk index as well as the document index.

## Why free-coded

A production consultant is unreachable for any business whose index is corrupt.

## Where it happened (operator, 2026-11-08)

The business was an ordinary copy (no `--handoff`) on production. Its **shop inventory import broke partway through**, and the next session start returned the 500. So the overlapping writers to rule in or out first are:

- the shop import's photo phase (since BUG-380 it runs in the job container and writes each photo into the Library, which updates the index), and
- whatever else wrote the index at the same time: request-path refreshes in the control app, and a second or retried import run after the first one stopped. A run killed partway, or retried while the first is still writing, must also count as a writer that can't overlap another.

The cross-writer coordination in the Fix covers the container as well as request isolates: the job container reaches the index through the control-app's internal entrypoint, so it goes through the same per-business coordination point and never writes the R2 objects alongside another writer. An import that stops partway leaves an index whose vector count equals its metadata count, and that's one of the UATs.


**Confirmed workaround (2026-11-08 19:12 UTC):** a Library photo upload (`POST /b/<id>/api/material`) ran BUG-380's refresh and healed the index. Workers Logs show one `kb_index_rebuilt` for it, with the same 33792-float / 86-entry reason. That confirms the refresh path heals and the session path doesn't, which is the gap this ticket closes.


## Cause found (BUG-384 session, 2026-11-08)

- **The production pair was a writer stopped between two R2 writes, not two writers interleaving.** The index was four R2 objects written one after another (`saveIndex`: `embeddings.bin` first, then `metadata.json`, `manifest.json`, `model_info.json`). 88 rows of vectors against 86 metadata entries is a new `embeddings.bin` beside the previous `metadata.json`: the shop import's photo phase in the job container was killed after its first put of a refresh. BUG-380's lease can't prevent that. A dead writer's half-written index persists.
- **Cross-request writers were already coordinated.** BUG-380's lease is the SITE_COORDINATOR Durable Object (`kb-index:<business>`), bound in production, and the job container reaches it over the platform wire. Every refresh, from a request or the container, takes it. What was missing was atomicity of the write itself, and healing on the read path.
- **Readers mid-write saw the same mismatch.** Any read during a refresh's four puts could pair new vectors with old metadata and throw, which would 500 a session on its own.

## What changed

- **An index is one R2 object.** `kb/<business>/project/index/index.bin` and `.../chunks/index.bin`, holding the vectors, metadata, manifest and model info together (`r2IndexSource`, `INDEX_OBJECT`). One put is atomic, so a reader sees the whole old index or the whole new one, and a writer stopped partway leaves the previous index whole. The component's per-file `IndexSource` port is unchanged; a build runs against an in-memory copy and the result is stored in one `commit`.
- **Reads share one object.** Reads within 100 ms share one fetch. After that a read asks R2 again, conditional on the etag it holds, so an unchanged index costs no transfer and a write from any isolate is seen at once.
- **A corrupt or missing index never fails a read.** `ProjectKnowledge.index` / `.chunks` are reader views. Before answering, a read checks the stored index loads. If it doesn't (corrupt, or not yet stored in the one-object layout), the read triggers `refreshIndex()`, the one writer under the lease. That path rebuilds a corrupt index and logs `kb_index_rebuilt` once. The reader waits up to `READ_REPAIR_MS` (10 s). Past that the index reads as empty for that turn, the session starts without Library search, `kb_index_unavailable` is logged once, and the rebuild carries on behind (`defer`). This covers every reader: the session's `KnowledgeRuntime.open`, `KnowledgeSearch` / `KnowledgeChunkSearch`, `search()`, and the clustered landscape's index read and access-point check. Reader views refuse writes.
- **Existing indexes migrate by rebuild.** A business whose index is still in the four-object layout (including the corrupt production one) has no `index.bin`. Its first read builds one from the stored materials. The old objects are left in place, unread.
- **Transcript cursors** (`transcripts.json`) are their own R2 object at the same key as before (`r2CursorFile`), never inside the index object, so a cursor write can't race a build.

## Supersedes

REQ-159 / AC-1661 pinned the index as separate `embeddings.bin`, `metadata.json`, `manifest.json`, `model_info.json` objects. Those assertions now name the one `index.bin` object. Their intent is unchanged: the index lives in private R2 (`BLOBS`) under the business's own prefix, never in `SITES`. `test_UAT_FC_REQ-159_project_kb` and `test_UAT_AC1661_*` are updated accordingly. The BUG-380 index UATs read and corrupt the index through `r2IndexSource`.
