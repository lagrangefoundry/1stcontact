## Symptom

`update_brief`'s `audiences` parameter is declared `"type": "array"` in `tools/generate/src/cli/ai/plan-surface.json`, but its description tells the consultant to send a list of objects: `{"who": ..., "priority": 1}`. In a toolbox declaration a plain `array` is an array of **strings** (the framework's `checkItems` defaults `itemBase` to `string`). So a call that follows the description fails with *"update_brief parameter 'audiences' entry 0 must be a string, got dict"*.

That refusal comes back as the tool's text, not as a thrown error. The whole `update_brief` call is rejected, so any other brief fields and the `quote` sent in the same call are lost too. The consultant may not notice.

Found while building REQ-408: `pin_notes` hit the same defect and was fixed with a declared param type.

## Root cause

Arrays of objects need a `param_types` entry with `"item_base": "object"`, and the param must reference that type. REQ-408 added `"story_notes": { "base": "array", "item_base": "object" }` and used it for `pin_notes.notes`; `audiences` was never given one.

## Fix

Declare an audience-list param type (`"base": "array", "item_base": "object"`) in `plan-surface.json` and use it for `update_brief.audiences`. `update_brief` already stores the value as given (`BRIEF_VALUE_KEYS`), so no core change is expected. Check `constraints` stays a string list, as its description says.

## Test plan

UAT `test_UAT_FC_<ID>_*`: through the real Toolbox (`box.run`, as REQ-408's suite does), `update_brief` with `audiences: [{"who": "local families", "priority": 1}]` succeeds and the stored brief holds that list. A UAT checking the call's result must check that the write actually landed, not only that the result text has no `PLAN_INVALID`, because the refusal arrives as text.
