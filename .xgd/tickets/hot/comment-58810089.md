## What happened

1. **20:38:20, the trigger.** In the 20:36 turn, `screenshot {detail:"low"}` of a library image returned the full 1024×1024 PNG as base64. Its junction record was **2,460,779 bytes**. The Durable Object (DO) refused it because it is over its ~2 MB value limit. `dev.log` shows: `junction durable:site-site_c78b…: write did not land — SQLITE_TOOBIG` at `junction-do.ts:194`.
2. **The DO stream got a hole.** The write-behind queue in `junctions.ts` (`queue`) deliberately keeps going after a failed write, so every later record landed. The DO now holds seq 1–5237 **minus seq 3648**. The code's comment assumes a failed write leaves a missing *tail*, which the next `prepare` re-sends. A hole in the middle can't be repaired that way.
3. **20:50:09, the poisoned watermark.** The end-of-turn save read the isolate's in-memory mirror, which still had seq 3648. The archive saved correctly: it contains that screenshot call (`toolu_01Fv9LF8…`), which the DO doesn't. But the archive watermark it wrote was a byte position in the mirror's numbering: 19,592,232 + 2,460,779 = **22,053,011**. That value was then written to the DO. On the next `prepare`, the mirror was replaced with the DO's shorter stream but kept that watermark, which now pointed 2.46 MB too far.
4. **21:04 and 21:16, the silent turns.** The stream was still shorter than 22,053,011, so `readSpans` returned nothing. The save "succeeded" with nothing to write. Nothing threw, so nothing could be logged.
5. **22:07 onward, the error.** That turn's 1.43 MB screenshot record pushed the stream past 22,053,011. Reading from there starts 151 KB inside that record, so `JSON.parse` gets `guWid6rN1D…`. The string isn't stored anywhere because it's a slice from the middle of a record. The 00:12 UTC turn on the redeployed snapshot fails in 130 ms only because a fresh isolate runs the save at turn start.

The proof: `guWid6rN1D` starts at byte 22,053,011 of the rebuilt stream, exactly the stored watermark. Every line of the stream parses as valid JSON.

## Recovery

Nothing is lost. Every record since 20:50 is in the DO. Setting the DO's watermark (`meta`) back to 19,592,232, the true end of the 20:50 turn, makes the next save fold everything from 21:04 onward into the archive. The DO's own copy of seq 3648 is gone, but the archive already has that record, trimmed to 5,800 bytes like other large tool results. The simplest way is to stop dev, back up the DO's `.sqlite`, and update that one row. That needs your go-ahead, since it's live dev state.

## Fixes to agree on

1. **Root fix (`junction-do.ts`):** the DO must accept any record by splitting a large append across several rows. Rows would need a "record boundary" marker so the check that reads only start at record boundaries stays honest. With the hole gone, the mirror and DO can't disagree on byte positions again. The alternative, stopping the queue after a failed write, isn't enough: re-sending the tail would hit TOOBIG every time and leave the session in RAM only.
2. **Make an impossible watermark loud.** A watermark past the end of the stream, or not at a record boundary, is corruption, but today the save just returns nothing. Two options:
   - Check it in our adapter on `prepare`: log it and pull it back to the last boundary the archive is known to hold.
   - Check after each save that the turn that just closed actually reached the archive. This is what would have caught 21:04, because there was no error to catch.

   Then show BUG-121's "reply may not have been saved" notice. The ticket's "save failure is never silent" item only covers errors that throw, so it wouldn't have caught this on its own.
3. **The trigger (open question):** should `detail:"low"` on a library image really return a full-resolution 2.4 MB PNG? It also costs tokens. I couldn't find where that path lives, and it may be upstream. Should it go in this ticket or be noted separately?

The UAT I'd propose sends a tool result over 2 MB through the real host with only the model scripted. It would assert that the turn is archived, that the next turn is archived too, and that the DO stream matches the mirror.
