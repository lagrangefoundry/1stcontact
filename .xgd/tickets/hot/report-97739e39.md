In every run the port test finished far below its 60 s limit. The 16–26 failures in the full and quality runs were other tests (blocked network, coverage-v8 module errors), not this batch.

- **The import-graph file isn't the polluter.** Its three unlocked mirrored builds take 46–600 ms each, and its first build takes milliseconds. That much work can't hold up the rest of the suite for minutes. Leaving the file out didn't make anything faster; that run was actually 11 s slower. Putting the lock back would change nothing I can measure, and it would undo iteration 7 with no evidence for doing so. I left the file as it is.
- **The three capture tests are skipped here.** The two REQ-211 capture tests and AC-2449 only run when Chromium is available, which it isn't in this sandbox. They already have bounded 120 s timeouts, so a diagnostic pass would only add another wait. Their stall can only be seen on the gate.
- **The gate report has no evidence.** All four failures in REPORT-11556 are placeholders ("JUnit XML missing or unparseable", no traceback, no `artifact_dir`). The session log has no "Test timed out" line. So even the claim that these four timed out comes from the planner's reading of the 263.7 s total, not from a recorded message.
- **My best guess at the cause, unconfirmed:** something on the gate host at run time, such as a hung Chromium launch or heavy CPU load. That would fit two sequential 120 s capture timeouts and three slow cold `1c` spawns. Nothing in the repo since the last green run (REPORT-11548) explains it.
