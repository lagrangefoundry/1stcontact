I couldn't fix this batch. The real fix is a schema change, which the code freeze rules out. I made no edits.

**What I found**

1. **The first failure has cleared.** The quality report shows the suite stopped at load time (0 tests ran) with `Cannot find module './generated/ticketing'`. The `apps/control-app/src/generated/` folder is build output, not committed, and was regenerated at 11:30, after that 11:27 run. With it in place the suite runs.

2. **The real failure is a schema mismatch.** In `tests/test_reconciliation_passwordless_sign_in.workers.test.ts`, 8 of 13 tests fail: AC2347–AC2354, every test that redeems a link or creates a session. The root error is `D1_ERROR: table sessions has no column named issued_at`, and redeeming returns 503 instead of 303.
   - The code imports `auth-passwordless` from the shared store outside the repo, at `/Users/martin/lagrangefoundry/node_modules/@lagrangefoundry/auth-passwordless`, installed Nov 6 17:43.
   - That installed copy is a newer version (REQ-151, session rotation). Its `sessions` table has four extra columns (`issued_at`, `origin_id`, `superseded_by`, `retired_at`) and two extra indexes. Its own comment calls `SESSION_MIGRATIONS` the step that adds those columns to a table created before them.
   - The repo's `db/migrations/0001_baseline.sql` (around lines 811–824) still has the old five-column table.

3. **The pre-existing evidence for REQ-202 fails the same way.** The free-coded tests were run without changes:
   - `test_UAT_FC_REQ-202_every_statement_in_SCHEMA_STATEMENTS_is_in_the_migration` fails with "migration is missing: CREATE TABLE IF NOT EXISTS sessions …".
   - The conformance suite run against this deployment's D1 fails.
   - Three tests in `test_UAT_FC_REQ-202_sign_in` fail (503 and 401).

   So the new tests are correct. The schema contract between the deployment and the component is broken.

**Why I couldn't fix it in the tests**

Setting up the newer table inside the test would hide a real deployment defect: the wiring test exists to catch exactly this mismatch. Nothing in the acceptance criteria or the story is wrong either. The fix has to be one of these:
- **Change the migration** to match the current component. That is production code, so it is blocked.
- **Reinstall the older component** in the shared store so it matches the baseline. That is a task for you, outside this repo.
