## Symptom

On Bob's salon 2 (2026-10-19), the client pressed Publish when the consultant suggested it, on a site with no web address. Instead of REQ-250's dialog, which explains what's missing and has a button to the Settings web-address section, they got the yellow failure banner showing the server's raw sentence, site id included:

> This site was not published. Site 'site_c78b12e50dde030a34e9becfabb6815d' has no public address, so publishing it would put it somewhere nobody can reach. Choose a 1stc.site hostname, or connect a domain you own — either one is enough.

## Root cause

The builder always publishes with the streaming form (`Accept: text/event-stream`, REQ-222). In that form, `/api/publish` sends `200` straight away, and the address check runs inside `run()`, after the stream has started. So `NoPublicAddressError` is never turned into the route's `409 {code: NO_PUBLIC_ADDRESS}` (`router.ts` around line 7398). Instead it's caught by `streamPublish`'s catch (`router.ts` around line 8238), which writes a final `{kind:'done', ok:false, error}` message **without a code**. `api.js`'s `streamPublish` turns that into a plain `Error` with no `code`, so `app.js`'s check `err?.code === NO_PUBLIC_ADDRESS` (around line 980) never matches, and `block.fail()` shows the banner. The comments in `api.js` assume the refusal happens "before committing to a stream", but it doesn't.

## Fix

1. **Check the address before the stream starts.** The publish route checks the site's addresses, through the same `addressesOf` gate, before it commits the response. A site with no address gets the ordinary `409 {code: NO_PUBLIC_ADDRESS}` in both forms, so REQ-250's dialog opens.

2. **The stream's final message carries the code too**, as a fallback. If a refusal with a code is thrown after the stream starts, the final message includes it, and `api.js` passes `code` on to the error the same way it does for a non-OK response. Nothing on the client branches on the wording of an error.

3. **Friendlier failure banner, with nothing internal in it.** Error text the client can see never contains a site id, an error code, or internal terms (hostname, slug, ladder, …).

- The publish banner shows a plain line, such as _"Something went wrong publishing your site. Try again in a minute, and tell us if it keeps happening."_, with the server's text behind a **Details** toggle for us.

- Refusals the client can act on keep their own wording and action. Today that's the no-address dialog.

- Check the builder's other failure banners against the same rule, and list what changed in the commit.

4. **The consultant can link to the web-address section.** Add a `web_address` target to `show_client` (REQ-413). `link` gives a line that opens Settings at the web-address section, using the same `revealWebAddress()` the dialog's button uses. `switch` does the same. The consultant's going-live instructions, which since `1c6a268d7e` tell it to check for an address before suggesting Publish, then name this link.

5. **The consultant is told the fact.** The per-turn plan notice says _"No web address yet: the site can't be published until one is chosen."_ while the site has no address and the plan has reached Finishing touches or Ready to publish. It disappears once an address exists. This is what makes step 4's instruction reliable rather than something the consultant has to remember (Finding 13).

## What landed (implementation notes)

- **Fix 1, as built.** Rather than a second address read at the route, `streamPublish` (router.ts) holds the response until the publish first reports progress (the ladder's plan frame) or settles. The address check runs inside `publishSite` through the same `addressesOf` reader, before the ladder, so a site with no address is thrown to the route's existing error mapping: `409 {code: NO_PUBLIC_ADDRESS}` in both forms. This keeps `publishSite`'s refusal order (an invalid draft is still reported before a missing address). The same applies to every refusal before the ladder (invalid draft, nothing built, a missing site, the ladder's own over-budget refusals), so all of them are now ordinary statuses in the streaming form. This supersedes REQ-222's assumption that the stream commits `200` before the publish runs. REQ-222's "failure in the terminal frame" UAT now uses a real failure after the stream starts (a ladder that reports progress and then throws).

- **Fix 2.** The terminal `{kind:'done', ok:false}` frame carries `code` whenever the error has one (`refusalCode`: NO_PUBLIC_ADDRESS, NOTHING_BUILT, INVALID_DEFINITION, CommandError codes). `api.js` sets `err.code` from it.

- **Fix 3.** New `failure-notice.js` `fillFailure(el, line, detail)`: a plain line, plus a closed `<details>` toggle labelled **Details** that holds the server's text. Publish banner line (`PUBLISH_FAILED_MESSAGE`): _"This site was not published. Something went wrong — try again in a minute, and tell us if it keeps happening."_ Other banners checked: the plan panel's "That answer was not saved" echoed server text and now gets the same treatment. The session-ended, no-business and no-API-key (REQ-173) banners show only our own wording, so they are unchanged.

- **Fix 4.** `show_client` target `web_address`, as a `link` or a `switch`. The link is `#show=web_address`, labelled "where you choose your web address". In the builder it calls `revealWebAddress()`. Surface enum/description and both priming copies name it.

- **Fix 5.** `planReminder(plan, {noAddress})` adds `NO_ADDRESS_LINE` while the site has no address and `finishing_touches` or `ready_to_publish` is in progress or done (`nearPublishing`). The addresses are read only at those stages, through the host's existing `addresses` reader. A failed read drops the line, never the plan entry.
