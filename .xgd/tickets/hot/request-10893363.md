## Why (operator, 2026-11-05)

Today "the plan" is mostly the consultant's notes to itself: the brief, the decision ledger, and nine fixed stages the consultant rarely marks. The client sees those stages only as a progress bar. Its labels mean little to them, and it implies a route they won't necessarily take. In a recent run only one stage was ever marked.

The operator's view: **the big picture of how the client and the consultant will work together should be agreed and shared, and it should be specific to this client.** What the site is for differs from client to client, and that should be discovered up front and shown in the plan. Some want only a shop front, others their story told, others bookings or commissions, or a mix; these are examples, not a fixed set. The same goes for the route: some want a choice of looks, others are happy with the first one.

## What

**1. A Plan panel at the very top of Input,** above the story board and questions, with a permanent "the plan" link in "How you can help".
- It lists, in order, the activities this client and the consultant will go through. Each entry has:
  - **the consultant's own wording for this client,** saying what it involves for them;
  - **a status:** done, now, next, later or skipped;
  - **a link to where that work happens,** where one exists (the story board, the comparison board, looks, Questions, the draft, Publish).
- Skipped activities appear under "Not included", each with its reason (for example "you want a shop front, so no story pages").
- The panel changes live as the plan does.

**2. The plan record holds these activities, replacing the nine stages.** One plan, not two.
- **Each entry is one kind from a fixed menu:** what the site is for, first draft, story, look, pages and content, shop, finishing touches (hero movement, entrance effects, tab icon, share card), final checks, publish. Each entry also has the consultant's specific wording, its status, and whether it's included, with a reason when it isn't.
- The consultant may give a kind more than one entry, for example a separate entry for one important page.
- **The fixed menu lets the host link each entry to its panel and set the statuses it can see for itself:**
  - first draft is done when every page of the first build has returned;
  - publish is done on publish;
  - final checks are done when the pre-publish review has run.
- The consultant sets everything else.
- **The consultant writes and updates it with one tool.** It replaces `set_stage` and the stage list in `plan-seed.json`.
- `agree_plan` stays: it records the client's yes, which is welcome but never required.

**3. The progress bar is removed.** The Plan panel replaces it. Delete the bar and its code; don't hide it.

**4. No gate.**
- The consultant writes the plan once it knows what the site is for, usually when the first build starts. Nothing waits for the plan or for the client's yes to it.
- If a first build has started and there's still no plan, the build's result tells the consultant so, as information.

**5. The client changes it through the consultant,** for now ("skip the story", "add a shop page"). The panel is read-only for the client.

The consultant's guidance for all this is already in the playbook (DOC-75, edited directly on 2026-11-05):
- find out early what the site is for, in the client's terms (a shop front, their story, bookings, commissions and so on are examples, not a fixed set);
- the plan is shared and specific, with each line saying what it involves and whether it's in;
- it doesn't need a yes before building, but must exist before going far;
- nothing is final until the client says so;
- "what's coming" is said when the first build starts.

Update DOC-75's references to `set_stage` and the stages when the tool changes.

## Implementation (as landed, 2026-11-05)

**The plan record.** `PlanFields.activities` replaces `stages`: an ordered list of `{ kind, text, status, reason? }`. `kind` is one of the fixed menu in `plan-seed.json` (`activities`: purpose, first_draft, story, look, pages, shop, finishing, final_checks, publish), each with the client-facing name and the `show` target its link opens (questions, draft, story, comps, publish). `status` is done, now, next, later or skipped. A skipped activity is "not included" and needs a reason; there is no separate `included` field, since skipped already means that. `checkPlan` refuses an unknown kind (naming the kinds), an empty text, an unknown status, or a skip without a reason. A new plan has no activities. Old plans' `stages` are left in place and ignored: there's no conversion.

**One tool.** `set_plan` (in KeepMilestones, both roles; withheld from the talker) writes the whole list at once, so the consultant rewrites it whenever it changes. It replaces `set_stage`, which is gone along with the stage list, `STAGES` and the "pieces" helpers. `agree_plan` stays and records the client's yes, which is welcome and never required.

**What the host marks.** The host works out these statuses when the plan is read (`hostDone`, `activityStatus`), and a skipped entry stays skipped:
- `first_draft` is done once `milestones.first_pass_at` is set (the first build's message has finished building, BUG-322).
- `publish` is done once `published_at` is set.
- `final_checks` is done once the review before publishing has run (`publishCritiqued`).

Before those facts hold, `set_plan` refuses `done` for them: NOT_YET for first_draft and publish; for final_checks, NOT_LOOKED while a changed page is unlooked and NOT_CRITIQUED where the host runs the critic. A refused done on final_checks, or final_checks set to `now`, makes the review before publishing due (REQ-427 behaviour, kept).

**No gate.** `firstBuildMissing` now waits for the design only, never for `plan_agreed`. A first `Delegate` with no plan written and no handoff carries `plan_note` (`NO_PLAN_NOTE`) in its result, and is not refused. Once the plan is written, nothing is said.

**What the consultant reads.**
- The per-turn plan entry's line is "The plan (agreed / not yet agreed with the client) — done: …; now: …; next: …; later: …; not included: …", or "No plan yet: write it with set_plan once you know what the site is for. Nothing waits for it."
- The initiative line names the next activity, or "find out what the site is for, then write the plan (set_plan)".
- Priming (both copies) and the plan surface's overview now describe the shared plan, set_plan, finding out what the site is for, and "nothing is final until they say so". DOC-75 needs no set_stage edits (it never named it). Its handoff line about pieces is updated at merge.

**Handoff mode (REQ-638), adapted.** A prepared site waits for its owner's view until the consultant has written their plan or the client agreed one. `enterHandoff` now only records the handoff. Built sites with no plan are no longer auto-converted to handoff on read, so `planOnRead` is removed. The site copy no longer reports "prepared pieces".

**Other readers moved to activities.**
- Feedback's stage and the tester timeline read the activity that is now under way.
- `nearPublishing` reads final_checks or publish as now or done.
- Input's Stories and Comparison sites sections are Complete when every story or look activity is done or skipped.
- A first-draft copy (REQ-450) sets done build activities back to next.
- The plan ticket schema declares `activities`.

**The builder.**
- The Plan panel (`plan-route.js`) is the first thing in Input, above "Your input", the questions and the story board.
- Its heading is "The plan", with "Agreed with you" once the client has agreed it.
- Each included activity is a row: its status in words, the kind's name, the consultant's text, and an Open link (a `show` target: Questions, the draft, the story board, the comparison sites, or Publish, which focuses the Publish button).
- Skipped activities sit under "Not included", each with its reason. The panel ends with "To change it, just say so in the chat. Nothing is final until you say it is."
- Before the plan is written it reads "Your plan appears here once we know what your site is for." It is read-only and redraws from every plan view.
- "How you can help" always ends with a "The plan" line that opens the panel. The "Your input" summary leaves that line out, because the panel sits right above it.

**The progress bar is deleted:** its markup, tip, code, CSS and strings. The status row that sat inside it remains as `.progress-status` (`planPanel.statusSlot`), the first thing in the progress area. The questions panel's aria-label becomes "Questions for you" so it doesn't clash with "The plan". The REQ-653 "published hides the stages" behaviour goes with the bar.
