Two defects in what the dev environment tells the operator about itself. Both are
small, both are in the same layer — the sentences an operator reads before
deciding what to do — and both send that decision the wrong way. Filed together
because a child session fixing one is already reading the other's code path.

## 1. `1c ps` reports snapshot-served apps as belonging to nobody

`1c ps` shows `dev` (8789) and `public-site` (8787) with an empty `started`
column while `filing` and `access-sim` correctly show `bin/dev` — even though all
four have valid pidfiles written by the same `bin/dev up`.

The cause is a call site that did not travel with its fix. BUG-147 established
that a service is not always the process `up` spawned: `wrangler dev` forks
`workerd`, and it is the GRANDCHILD that holds the port, so a pidfile records both
`pid` and `listenerPid` and `devPidfilePids` returns both. `devTable` passes
`readDevPidfiles(root).flatMap(devPidfilePids)` (`tools/generate/src/cli/dev.ts:295`).
The `ps` verb passes `readDevPidfiles(root).map((r) => r.pid)`
(`tools/generate/src/cli/index.ts:1543`) — the spawned pid only. For exactly the
two services whose listener is a grandchild, the pid `lsof` resolves matches
nothing in the managed set.

This is BUG-147's own symptom, surviving in the one command an operator runs to
ask the question. It is worse than cosmetic because of what it is read before: a
managed service shown as unowned is the signal that sends someone to
`bin/dev reap`, which escalates to SIGKILL and takes every unmanaged listener in
the project with it. The summary line stops short of calling them strays — they
are recognised services — so nothing today turns the misreport into a reap, but
the column an operator actually reads says the opposite of the truth.

Expected: `1c ps` names the starter of every service `bin/dev` started, whether
the listener is the spawned process or a descendant of it. The two call sites
should not be able to disagree about what "managed" means — one of them being
right and the other wrong is the defect, not the specific pid that was dropped.

## 2. A stale Access cookie reports as a broken key configuration

After any `bin/dev up` or `bin/dev restart access-sim`, browsing the environment
fails with:

    Cloudflare Access rejected this request: no Access signing key matches kid 'local-dev-88241'

which reads as a misconfigured Access team, a missing JWKS or a wrong `.dev.vars`
— none of which it is. The operator's actual state is "your cookie was signed by
a process that no longer exists", and the repair is one click at
`http://127.0.0.1:8799/login`. Nothing in the message says so.

The mismatch is structural, not accidental. `bin/access-sim` generates a fresh RSA
keypair per process and derives `KID = local-dev-${process.pid}`
(`bin/access-sim:195`), deliberately, so that `access.ts` treats a restart as a key
rotation and force-refreshes its JWKS cache on an unseen `kid`
(`apps/control-app/src/access.ts:249`). That works — for the NEXT cookie. The
cookie already in the browser was minted with `Max-Age = 60*60*24*30`
(`bin/access-sim:116`), so the credential outlives its signing key by up to thirty
days by design. Every restart of the simulator therefore guarantees this failure
for anyone who had signed in, and the failure names a `kid` rather than an action.

Observed today: JWKS at 8799 publishes `local-dev-87914`, the live process; the
cookie presented carried `local-dev-88241`, a sim from an earlier cycle.

Expected: a token whose `kid` is well-formed for this simulator but absent from a
freshly-refreshed JWKS is reported as an expired local sign-in, naming the sign-in
URL. A `kid` that is not of that shape keeps the current message, because then it
genuinely is a configuration question. The distinction is what makes the sentence
worth reading: the simulator's own restart is the overwhelmingly likely cause
locally, and the deployed path must not learn to be reassuring about a real key
mismatch.

## What changed

### 1. One definition of "managed", not two that happen to agree

The `ps` verb no longer composes a managed-pid set at all. It reaches the table
through `devTable({ repoRoot: repoRoot() })` — the same call every `bin/dev` verb
makes — so `readDevPidfiles(...).flatMap(devPidfilePids)` is written exactly once,
in `dev.ts`. The specific pid that was dropped was never the defect; a second call
site free to assemble its own answer was, and it stayed wrong for as long as it
existed while `devTable` was right. `devProcessTable`'s `managedPids` parameter is
unchanged and still caller-supplied, because `ps.ts` has no business knowing where
`bin/dev` writes its pidfiles — what changed is that only one caller supplies it.

`1c ps` now prints `bin/dev` in the `started` column for a service whose listener
is a `workerd` grandchild, which is the two snapshot servers.

### 2. A stale local sign-in is reported as a stale sign-in

`verifyAccessJwt`'s "no signing key matches this kid" refusal now splits in two.
When the presented `kid` takes `bin/access-sim`'s shape (`local-dev-<pid>`) AND the
just-refreshed JWKS from the team domain publishes a kid of that shape too, the
reason becomes:

    Cloudflare Access rejected this request: this local sign-in has expired —
    `bin/access-sim` re-keys every time it starts, so the cookie you are holding was
    signed by a simulator that is gone. Sign in again at http://127.0.0.1:8799/login.

Every other case keeps the original message verbatim, including a
simulator-shaped `kid` presented to a team domain whose JWKS is Cloudflare's. That
second condition is what makes the deployed path structurally unable to reach the
reassuring sentence rather than merely unlikely to: Cloudflare's kids are hex
digests and can never take this shape. The refusal is still a 401 — this is a
better diagnosis, not a new admission.

Two small exports carry it: `isAccessSimKid(kid)` and
`accessSimSignInUrl(teamDomain)`. The sign-in URL is built by the same team-domain
substitution `certsUrl` and `accessLogoutUrl` already rest on, and `/login` is only
ever named in the one case where the team domain provably IS the simulator that
serves it.

## Test plan

`tests/test_UAT_FC_BUG-152_ps_names_the_starter.test.ts` (2 legs)

- `ps_calls_a_grandchild_listener_managed` — runs against the REAL checkout and the
  REAL `1c ps` subprocess, because the defect was in the verb: BUG-147's suite
  asserted against `devTable` and passed throughout, which is exactly how the
  misreport survived, and `repoRoot()` is source-anchored so a temporary root
  cannot reach the verb. `devUp` starts a real wrapper whose grandchild holds a
  real port (8780–8798, a range no sibling suite draws from), the production writer
  writes the pidfile, `lsof` resolves the listener, and `1c ps --json` is parsed.
  The premise is measured, not assumed: the listener pid is asserted to differ from
  the spawned pid before the row is checked. Verified RED against the pre-fix verb
  (`managed` was `false`).
- `ps_composes_no_managed_set_of_its_own` — the verb's body (comments stripped)
  contains `devTable({ repoRoot: repoRoot() })` and no `devProcessTable`,
  `managedPids` or `readDevPidfiles`. This pins the invariant the ticket asks for —
  two call sites that *cannot* disagree — rather than the value they agree on today.

`tests/test_UAT_FC_BUG-152_stale_local_sign_in.test.ts` (3 legs)

- `restarted_simulator_names_the_sign_in_url` — performs the restart rather than
  describing it: a real simulator is spawned, signed into over loopback, SIGKILLed,
  and a second real simulator takes the same port. The token under test is a real
  cookie signed by a keypair that genuinely no longer exists. Asserts the new
  sentence and the sign-in URL, asserts the old sentence is gone, and asserts a
  fresh cookie from the live simulator still verifies — so this is a better
  diagnosis and not a new refusal. Verified RED against the pre-fix branch.
- `a_kid_that_is_not_the_simulators_keeps_the_key_message` — a hex-digest `kid`
  presented while the simulator is live still gets `no Access signing key matches
  kid '…'`. The shape is the whole discriminator, pinned from that side too.
- `a_cloudflare_jwks_never_reports_an_expired_local_sign_in` — a simulator-shaped
  `kid` against a Cloudflare JWKS keeps the original message and never names
  `/login`. `fetch` is stubbed in this leg and nowhere else in either file; the
  certs endpoint of a team that does not exist is the one thing that cannot be run
  locally.

Regression scope (11 files, 111 tests, all passing): the two new suites plus
BUG-147, REQ-319, REQ-147, REQ-192, REQ-204, BUG-59 (access-sim service token),
BUG-150, BUG-146 and REQ-322. `tsc --noEmit` clean on both
`tools/generate/tsconfig.json` and `apps/control-app/tsconfig.json`.
