## Scope

Container clean-up and memory accounting for EPIC-32's per-job containers, in **production and dev**. Found reviewing dev runs on 2026-11-05 after the 16:08Z dev deploy (REQ-646). The containers work: 13 turns ran on 3 sites with none lost and none OOM-killed. But nothing guarantees a job's container is gone when the job ends, and dev doesn't reproduce production's memory limit.

## Problems

### Production (and dev)

1. **Only a successful `end` step stops a job's container.** `AgentContainer.end()` (`apps/control-app/src/agent-container.ts`) destroys the container and deletes the job's token, and `runStep` calls it only when an `end` step returns OK. In `turn-job.ts`, a job that ends any other way leaves its container running and its token valid:
   - the `end` step fails all 3 of its attempts, or answers an error;
   - the `abandon` step fails past its retries, so the Workflow errors out before reaching `end`;
   - the Workflow is terminated or cancelled from outside, or a deploy kills it.
   
   In production a leftover container keeps billing until Cloudflare evicts it, and its token can still call the platform's internal entrypoint as that job. That breaks architecture item 31 ("No container is kept awake per site between jobs") and item 32 (containers hold no state and are disposable).
2. **Old job images pile up in the registry.** Every production deploy pushes a new ~1.5 GB image to the account's Cloudflare registry, and nothing deletes the old ones. It only costs storage, but it grows with every deploy. (On 2026-11-05 the registry was still empty: the job container hadn't been deployed to production yet.)

### Dev and test

3. **Dev does not enforce the production memory limit.** Production jobs run as `standard-1` (4 GB). Local dev containers start with no memory limit (`docker inspect` → `HostConfig.Memory=0`) and can use all of Docker's 9.7 GB. A job that would be OOM-killed in production finishes on dev, so dev can't catch memory regressions, which is the reason EPIC-32 exists.
4. **The recorded peak memory leaves out Chromium.** `container/server.ts` `usage()` reports `process.resourceUsage().maxRSS`, which covers the Node server process only. Chromium runs as child processes and counts against the instance's limit, so it should be included. Seen: the live container used 1.7 GB in `docker stats` while its `turn_log.peak_memory_mb` was 854 MB. `exit_reason`/`memory_kills` and any headroom judgement built on this number understate the real risk. (This applies in production too: it's the same server code.)
5. **The container UAT suites leak containers.** 17 `cloudflare/proxy-everything` sidecars named `workerd-1stcontact-control-app-AgentContainer-*-proxy` (the non-dev worker name, i.e. `unstable_dev` test runs) were still running 20+ hours later with no agent container beside them. They were removed by hand on 2026-11-05. Each suite run adds more.
6. **Old local job images pile up.** Every dev-worker start on a new snapshot builds a new `cloudflare-dev/agentcontainer:<hash>` image (~1.5 GB) and nothing removes the old ones: six of them built up in ~24 h.

## Fix

1. **A stop backstop on the container's Durable Object, timed from idleness, not the step timeout.** A round step may legitimately run up to 2 hours (`ROUND_STEP.timeout`), so an alarm set to "longest step + margin" would leave an abandoned container billing for 2 hours. The DO records when a step starts and when it finishes. Between steps the Workflow calls again within seconds (retry delay 1 s), so:
   - **no step in flight** and none started for `IDLE_STOP` (a few minutes) after the last one finished → stop the container and delete the job's token;
   - **a step in flight** longer than the step timeout → stop it (the Workflow has given up on it by then anyway).
   
   `end()` stays the normal path; the alarm is the guarantee. A step arriving after the backstop fired starts a fresh container, as a retry already does (containers hold no state, item 32).
2. **`end` stops the container even when the step fails.** The `end` request destroys the container and deletes the token whatever answer it gets, so a failed `end` attempt never leaves it running.
3. **Prune old registry images on deploy.** After a successful production deploy, `bin/deploy` deletes that app's older images from the Cloudflare registry, keeping the image now deployed plus the one before it for rollback.
4. **Dev catches what production's memory limit would kill.** Local containers are created by workerd itself, which sets no memory limit and ignores `instance_type` (checked in wrangler 4.111 / miniflare: there is no option to pass one). So rather than trying to cap the local container, the job is given its instance type's limit (derived from `instance_type`, not hard-coded) and compares its whole-container peak (item 5) with it. On dev and in the UAT rig, a step whose peak exceeds the limit fails as `exit_reason=oom`, counted in `memory_kills`, the same outcome production's kill produces. In production the platform enforces the limit itself and the comparison is only recorded.
5. **Measure peak memory for the whole container:** the cgroup's peak (`memory.peak`, or the highest `memory.current` sampled during the step) rather than the Node process's `maxRSS`. Where no cgroup figure covers just the container (Cloudflare runs containers in a VM, where the cgroup may not), sample the summed RSS of the server's whole process tree (`/proc`, about once a second) instead. Never fall back to the Node process's own `maxRSS`, which is the bug. Record which method produced the figure.
6. **The container UAT suites stop and remove every container they started,** sidecar proxies included, on success, failure and timeout, with a teardown check that no `AgentContainer` container from the run is left behind.
7. **Prune old local images on dev start:** after a dev deploy/start succeeds, remove that app's older `cloudflare-dev/agentcontainer:*` images so only the one now being served remains, and never remove an image a running container uses.

Out of scope: `-production:worker` images from `bin/build`'s dry run (stopped by BUG-352), and one-off images from REQ-646 experiments (removed by hand).

## Design decisions (agreed with the operator, 2026-11-05)

1. **One ticket for all container clean-up, production and dev.** The operator chose to fold the production gaps into this ticket instead of filing a separate production bug. Severity is high because of the production cost and the live-token exposure.
2. **The backstop is an alarm on the container's Durable Object, timed from idleness.**
   - *Why on the DO:* the DO addresses the job's container and holds its token, so it's the one place that can stop both whatever happened to the Workflow. A Workflow-side `finally` can't help when the Workflow itself is killed.
   - *Why idleness, not the step timeout:* a round step may run up to 2 hours (`ROUND_STEP.timeout`). An alarm set to "longest step + margin" would leave an abandoned container billing for 2 hours. Between steps the Workflow calls again within about a second (retry delay 1 s), so a short idle wait is safe.
   - *`IDLE_STOP` = 5 minutes:* long enough to cover the Workflow's retry gaps with a wide margin, short enough that a leaked container costs pennies. It's one named constant, so it can be tuned.
   - *A step still in flight* is left alone until the step timeout, after which the Workflow has given up on it anyway.
   - *Rejected:* a `sleepAfter`-style idle stop from the `Container` helper class. The DO drives the raw `ctx.container` API, and the alarm gives the same result without swapping the class out.
3. **`end` always stops the container,** even when its answer is an error. A retry of `end` then starts a fresh container to finish the job's bookkeeping. That's cheap, and it's correct because containers hold no state (architecture item 32).
4. **Registry pruning keeps the deployed image plus the one before it.** That allows a one-version rollback. *Accepted trade-off:* rolling a Worker back further than one version loses its image and needs a redeploy. Pruning runs only after a successful production deploy. Dev runs locally and has no registry.
5. **Dev doesn't try to cap the local container's memory.** Workerd creates local containers itself, with no memory limit, and wrangler 4.111 / miniflare have no option for one (checked). A `docker update --memory` after start was rejected as racy and hacky. Instead the job is told its instance type's limit (derived from `instance_type`, never hard-coded) and compares its whole-container peak with it. On dev and in the UAT rig, going over fails the step as `exit_reason=oom`, which is what production's kill produces. In production the platform enforces the limit, and the comparison is only recorded.
6. **Peak memory is whole-container, never the Node process's `maxRSS`.** The preferred source is the cgroup's peak. Cloudflare runs containers in a VM, where the cgroup may not cover just the container. In that case the fallback is the summed RSS of the server's whole process tree from `/proc`, sampled about once a second. Falling back to `maxRSS` would bring back the very bug this fixes. The record says which method produced the figure.
7. **Local clean-up is part of the tooling, not a manual chore.** The container UAT suites tear down everything they started, sidecar proxies included, whether they pass, fail or time out. Dev start removes that app's older local images and never touches an image a running container uses. Already out of scope: `-production:worker` images (stopped by BUG-352) and one-off REQ-646 experiment images (removed by hand on 2026-11-05).

## Implementation defaults (BUG-359 session, 2026-11-05; change any before coding starts)

- **Where the memory figures are recorded:** two new `turn_log` columns in migration `0052` (numbered `0050` when first written; renumbered after BUG-360's `0050` and BUG-366's `0051` landed first). `peak_memory_source` (`cgroup` or `process_tree`) says which method produced the turn's peak. `memory_limit_mb` is the instance type's limit the peak was compared with. That comparison is how production "only records" it.
- **How the job knows to enforce:** the limit comes from the `[[containers]]` `instance_type` through a table of Cloudflare instance types (`lite` 256 MiB, `basic` 1 GiB, `standard-1` 4 GiB, `standard-2` 6 GiB, `standard-3` 8 GiB, `standard-4` 12 GiB). A var, `JOB_MEMORY_ENFORCE=1`, is set in `[env.dev.vars]` and by the UAT rig, and absent in production. With it set, a step whose peak goes over the limit answers `exit_reason=oom`.
- **Registry pruning failures:** a delete that fails warns and leaves the deploy successful. The images go through the Cloudflare containers images API with the deploy's existing token.
- **Which containers belong to a suite run:** a container named `workerd-<worker>-AgentContainer-*`, proxy sidecars included, created after the rig started. The rig removes those, and its stop fails if any remain.
- **Local image pruning:** the images to keep are the tags that appeared during this dev start (wrangler gives each start a new random tag). The older tags are removed with a plain `docker rmi`, which Docker refuses for an image a container uses. *Accepted risk:* a dev deploy during a container test run can remove that run's image between two of its jobs.

## What landed (2026-11-05)

- **Backstop** (`apps/control-app/src/agent-container.ts`): the container's DO records when each step starts and answers, and arms an alarm: `IDLE_STOP_MS` (5 min) after a step answers with no new one started, or the step timeout while a step is in flight. When it fires it destroys the container and deletes the job's token. A step that arrives later starts a fresh container.
- **`end` always stops:** the `end` request destroys the container and deletes the token whatever it answers, including when the container dies mid-request.
- **Whole-container memory** (`apps/control-app/container/memory.ts`, wired into `container/server.ts`): sampled about once a second during the step. The cgroup source reads the working set, `memory.current` minus `inactive_file` (cgroup v2), or `memory.usage_in_bytes` minus `total_inactive_file` (v1). That's the figure `docker stats` shows: reclaimable page cache isn't counted, because the kernel drops it before OOM-killing. Where no cgroup covers just the container, the source is the summed RSS of the server's process tree (descendants of the server only) from `/proc`. The answer carries `peakMemoryMb`, `peakMemorySource` and `memoryLimitMb`, which are written to `turn_log`. A failed read never rejects unhandled.
- **The limit:** `JOB_INSTANCE_TYPE` in every environment's `[vars]` restates the `[[containers]]` `instance_type` (a UAT keeps them equal). The Worker looks it up in `INSTANCE_MEMORY_MB` and passes `JOB_MEMORY_LIMIT_MB` (and `JOB_MEMORY_ENFORCE` when set) to the container. With `JOB_MEMORY_ENFORCE=1` (in `[env.dev.vars]` and the UAT rig), a step over the limit fails as `exit_reason=oom` and is counted in `memory_kills`. Production only records it.
- **Registry prune:** new verb `1c images prune --app <app> --worker <name>` (`tools/generate/src/cli/container-images.ts`). It works out which tag is deployed from the account's container application, orders the other tags by their Worker versions' upload times, keeps the deployed tag plus the newest other one, deletes the rest through the registry API, and frees unreferenced layers. An app with no containers is skipped. `bin/deploy` runs it after a cloud deploy that shipped, never on `--dry-run` or a dev deploy. A failure prints `⚠ <app>: the image prune did not run; the deploy is unaffected`, and the deploy still succeeds. `DEPLOY_PRUNE_IMAGES_CMD` replaces the command for tests.
- **Local image prune:** `devUp`, which `bin/dev up` and `1c dev refresh` both go through, records the app's `cloudflare-dev/<class>:*` tags before a start. After a start that succeeded it keeps the tags that appeared and `docker rmi`s (never `-f`) the older ones, skipping any image a running container uses. If no new tag appeared it removes nothing. The start report says what it removed.
- **Rig teardown** (`tests/support/job-container-rig.ts`): removes every `workerd-1stcontact-control-app-AgentContainer-*` container created since the rig started, sidecars included, also when `unstable_dev` fails to start, and fails its stop if any remain.

Extra UAT cases added beyond the test plan: a long-running step is left alone by the backstop; an `end` whose container dies still deletes the token; the deployed tag is kept even when it isn't the newest; a failed registry delete warns and never throws; the prune runs only after a cloud deploy and never in a rehearsal; a start that built no new image removes nothing; the server reports the container's peak, not its own; the process-tree figure sums only the server's descendants; the cgroup figure excludes reclaimable cache; production only records the limit; the instance type is stated once per environment; the rig teardown takes only its own run's containers.

Running the container UATs in the sandbox needs `DOCKER_CONFIG` pointed at a writable copy of `~/.docker` (buildx). Without it the rig times out opening a session.
