The evidence for this capability is strong: every one of the ten ACs has a
substantive UAT in `tests/reconciliation-site-locale-identity.test.ts`, all ten
run green (verified this round: 10 passed / 10), and the rendering claims are

## Notes for the Editor

**One gap, one fix, one file.** Findings 1 and 2 are two levers on the same
defect: add the registry-completeness AC to STORY-122, then add its assertions
to the existing `test_UAT_AC1436_…` (or a sibling test) in
`tests/reconciliation-site-locale-identity.test.ts`. No production code changes
— `packages/site-schema/src/locale.ts` already carries the complete registry, so
this is purely making the existing correct behavior falsifiable.

**A near-finding, considered and deliberately rejected — do not "fix" it.** The
story body says the derivation table covers **66 countries**, and REQ-151 names
eight RTL countries (`AE`, `EG`, `IL`, `IR`, `MA`, `QA`, `SA`, `PK`) of which
only `AE` and `IL` are exercised. This looks like the same shape as finding 1
but is not, and the asymmetry is the point:

- The country table is an **open, growing** surface — REQ-151 and the story both
  state that adding a country is a one-row data edit, not a code change. A test
  pinning "66 rows" or a fixed country list would fail every time someone adds a
  country, which is exactly the friction the data-edit property exists to avoid.
  AC-1435 already made the right call: anchor `IE`/`GB`/`US` explicitly, and hold
  *every* row — however many there are — to full validation plus round-trip.
- The ISO 639-1 registry is a **closed, frozen** surface of exactly 184 codes.
  Pinning its completeness costs nothing in future maintenance and buys the one
  thing nothing currently buys.

So: add the language-registry assertion, and leave the country table's breadth
unpinned.
