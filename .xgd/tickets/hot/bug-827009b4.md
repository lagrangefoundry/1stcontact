Found on loop-1 iteration 2 of `repro-gigabytealchemy-ai`.

Every round of every site is currently told, in its own prompt, that the
regression rail says the engine got worse — because no baseline has ever been
recorded. "The rail has nothing to compare against" is a state of the checkout;
"something regressed" is a claim about the engine. The round prompt makes the
second claim, twice, before the round has done anything.

## What the round is handed

`storage/tmp/repro-console/repro-gigabytealchemy-ai/iteration-2/rail.json`, in
full:

```json
{
  "available": true,
  "pass": false,
  "partial": false,
  "summary": "the regression rail — REGRESSED\nREGRESSED · references: no baseline at storage/rail/baseline.json. The rail cannot say \"no worse\" against nothing — record one with `repro-rail record`."
}
```

and there is indeed no baseline:

```
$ ls storage/rail
ls: storage/rail: No such file or directory
```

## Where it comes from

`tools/repro-console/src/rail.ts:626–649` — with no baseline, `runRail` returns a
report with `pass: false` and one `references` phase carrying the explanation as
a **failure**:

```ts
const baseline = readBaseline(opts.cwd)
if (!baseline) {
  return { pass: false, …, phases: [{ name: 'references', pass: false, …,
    summary: 'nothing recorded',
    failures: [`no baseline at ${BASELINE_FILE}. The rail cannot say "no worse" against nothing — …`],
  }] }
}
```

`tools/repro-console/src/rail-round.ts:59–67` then renders every phase failure
with a `REGRESSED ·` prefix and maps `!report.pass` to the verdict `REGRESSED`:

```ts
for (const failure of phase.failures) lines.push(`REGRESSED · ${phase.name}: ${failure}`)
…
const verdict = report.pass ? (report.partial ? 'no worse, partially covered' : 'no worse') : 'REGRESSED'
```

## Why it is a defect and not a wording preference

The file that does this states the distinction it then fails to make, eleven
lines below the code — `rail-round.ts:70–77`:

> A rail that throws is reported as unavailable rather than as a regression. The
> difference matters: "the rail could not run here" is a state of this checkout,
> and "the rail says something is worse" is a state of the engine — and only the
> second is a finding about the thing being diagnosed.

A missing baseline is squarely the first kind, and the interface in the same file
already has the vocabulary for it — `:38`: *"Undefined when no rail ran —
'unknown' is not 'pass'"*. It just never reaches that state, because `runRail`
returns rather than throws.

The cost is that the rail line in the round prompt is either believed (a round
spends part of itself hunting a regression that was never measured) or learned to
be ignored (the rail stops meaning anything, including on the day it is right).

## Proposed change

Keep `runRail`'s `pass: false` — a `repro-rail` invocation with no baseline
should still exit non-zero at a terminal — but make the state distinguishable:
add a discriminator (`noBaseline: true` on the report, or `kind: 'unavailable'`
on the phase) and have `summarise` / `runRailRound` render it as

```
not available — no baseline at storage/rail/baseline.json; record one with `repro-rail record`
```

with `available: false` and `pass` left undefined, exactly as the throw path
already does. The word REGRESSED should appear only when a recorded number got
worse.

## What was implemented

The discriminator is `noBaseline?: boolean` on `RailReport` — the first of the
two options above, chosen because the distinction is a property of the whole run
rather than of one phase: nothing was measured at all, so there is no phase whose
kind is the interesting fact. `runRail` sets it on the no-baseline return and
changes nothing else there; `pass` is still `false` and the `references` phase
still carries the explanation as a failure, so `repro-rail` still exits 1 and a
`--json` consumer still reads the reason where it always did.

Three renderers then read it:

- **`summarise`** returns `the regression rail — not available — no baseline at
  storage/rail/baseline.json; record one with \`repro-rail record\`` and returns
  it *before* the phase loop, which is the whole fix: the loop prefixes every
  phase failure with `REGRESSED ·`, and the no-baseline explanation is a phase
  failure. The string is exported as `NO_BASELINE` beside it.
- **`runRailRound`** returns `{ available: false, summary }` with `pass` left
  undefined — the same shape the throw path and the `REPRO_CONSOLE_RAIL=off` path
  already return, because it is the same kind of answer. `rail.json` and the
  round prompt are written from that result, so both are fixed by the one change.
- **`formatRailReport`** prints `regression rail: NOT AVAILABLE` and the two
  lines saying what is missing and how to record it, instead of `FAIL` followed
  by the missing baseline listed under the heading *"what is worse than the
  recorded bar"*. This was not named in the proposal above, and is included
  because it is the same claim in the terminal view — a heading asserting a
  comparison was made, over a line saying no comparison was possible. The exit
  code is untouched, per the proposal: still 1.

### REQ-256's assertion is superseded

`test_UAT_FC_REQ_256_the_rail_runs_read_only_and_its_result_is_shown` pinned
`expect(bare.summary.split('\n')[0]).toContain('REGRESSED')` — the behaviour this
ticket declares wrong. Its surrounding intent ("what the round must never show is
a green line nothing produced") is unchanged and still asserted; only the
vocabulary moves, to `available === false`, `pass === undefined`, the baseline
named, `repro-rail record` named, and `REGRESSED` absent.

## Test plan

`tests/test_UAT_FC_BUG-109_rail_missing_baseline_is_not_a_regression.test.ts` —
the rail, its baseline written and read back off disk, its comparison against the
bar, the round renderer and the round prompt builder are all real; only the
browser-driven probes are substituted, through the injected `CommandRunner` the
production runner plugs into.

- `a_missing_baseline_is_reported_as_unavailable` — `available: false`, the

  path and `repro-rail record` both named, `REGRESSED` absent, and the command log
  empty — nothing was measured, so nothing can have got worse.
- `the_round_prompt_never_claims_an_unmeasured_regression` — the artifact the
  defect cost something in. The real `buildPrompt` over the real brief: the whole
  prompt contains no `REGRESSED`, and its rail section carries the not-available
  line.
- `a_recorded_metric_that_got_worse_is_still_a_regression` — the control, and the
  reason the fix is a discriminator and not a deletion. A bar recorded at
  `meanDiff` 12.3 and re-probed at 40, through the same renderer, still says
  `REGRESSED` and still names the reference. It passes both before and after the
  fix, which is the point.
- `the_terminal_report_says_not_available_and_still_exits_non_zero` —
  `noBaseline === true`, `pass === false` (so `repro-rail` still exits 1),
  `NOT AVAILABLE` printed, and neither `regression rail: FAIL` nor the
  "what is worse than the recorded bar" heading.
- `summarise_reports_the_state_from_the_report_alone` — the exact string, from
  `summarise` directly, because it is exported and the console is not guaranteed
  to stay its only caller.
