Found on loop-1 iteration 2 of `repro-gigabytealchemy-ai`.

Every round of every site is currently told, in its own prompt, that the
regression rail says the engine got worse — because no baseline has ever been
recorded. "The rail has nothing to compare against" is a state of the checkout;
"something regressed" is a claim about the engine. The round prompt makes the
second claim, twice, before the round has done anything.

## What the round is handed

`storage/tmp/repro-console/repro-gigabytealchemy-ai/iteration-2/rail.json`, in
full:

```json
{
  "available": true,
  "pass": false,
  "partial": false,
  "summary": "the regression rail — REGRESSED\nREGRESSED · references: no baseline at storage/rail/baseline.json. The rail cannot say \"no worse\" against nothing — record one with `repro-rail record`."
}
```

and there is indeed no baseline:

```
$ ls storage/rail
ls: storage/rail: No such file or directory
```

## Where it comes from

`tools/repro-console/src/rail.ts:626–649` — with no baseline, `runRail` returns a
report with `pass: false` and one `references` phase carrying the explanation as
a **failure**:

```ts
const baseline = readBaseline(opts.cwd)
if (!baseline) {
  return { pass: false, …, phases: [{ name: 'references', pass: false, …,
    summary: 'nothing recorded',
    failures: [`no baseline at ${BASELINE_FILE}. The rail cannot say "no worse" against nothing — …`],
  }] }
}
```

`tools/repro-console/src/rail-round.ts:59–67` then renders every phase failure
with a `REGRESSED ·` prefix and maps `!report.pass` to the verdict `REGRESSED`:

```ts
for (const failure of phase.failures) lines.push(`REGRESSED · ${phase.name}: ${failure}`)
…
const verdict = report.pass ? (report.partial ? 'no worse, partially covered' : 'no worse') : 'REGRESSED'
```

## Why it is a defect and not a wording preference

The file that does this states the distinction it then fails to make, eleven
lines below the code — `rail-round.ts:70–77`:

> A rail that throws is reported as unavailable rather than as a regression. The
> difference matters: "the rail could not run here" is a state of this checkout,
> and "the rail says something is worse" is a state of the engine — and only the
> second is a finding about the thing being diagnosed.

A missing baseline is squarely the first kind, and the interface in the same file
already has the vocabulary for it — `:38`: *"Undefined when no rail ran —
'unknown' is not 'pass'"*. It just never reaches that state, because `runRail`
returns rather than throws.

The cost is that the rail line in the round prompt is either believed (a round
spends part of itself hunting a regression that was never measured) or learned to
be ignored (the rail stops meaning anything, including on the day it is right).

## Proposed change

Keep `runRail`'s `pass: false` — a `repro-rail` invocation with no baseline
should still exit non-zero at a terminal — but make the state distinguishable:
add a discriminator (`noBaseline: true` on the report, or `kind: 'unavailable'`
on the phase) and have `summarise` / `runRailRound` render it as

```
not available — no baseline at storage/rail/baseline.json; record one with `repro-rail record`
```

with `available: false` and `pass` left undefined, exactly as the throw path
already does. The word REGRESSED should appear only when a recorded number got
worse.

**Wrong (now):** `ls` reports the directory does not exist, and the same file
reports `"available": true, "pass": false` with a summary whose first two lines
both read `REGRESSED`.

**Right (fixed):** `"available": false`, no `pass` field, and a summary reading
`the regression rail — not available — no baseline at storage/rail/baseline.json;
record one with \`repro-rail record\`` — with the word REGRESSED absent until a
recorded metric actually moves the wrong way.
