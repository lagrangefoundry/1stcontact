## Clusters

### Cluster 1: The editing triangle — who owns the transport and the client code an edit travels through
**Capabilities**: CAP-85 (Builder Workspace), CAP-86 (Structured Copy Editing), CAP-87 (In-Page Copy Editing)
**Stories**:
- story-e674c60a (STORY-99): The builder workspace: one browser surface... served from a single origin
- story-37a3921b (STORY-100): Change the words and choose the images on my page through one validated, all-or-nothing edit
- story-3bf94bd4 (STORY-101): Click the words on my page and change them, and watch the page update in front of me

**Overlap**: One operator gesture crosses all three capabilities, and the middle
layer is claimed twice. CAP-85's scope explicitly includes *"the shared client
code the editing gesture runs in the displayed page"* and *"carrying the write
path's read/apply operations as a thin transport that adds no semantics of its
own"* — i.e. the workspace capability hosts both the gesture's runtime code and
the write path's endpoints. CAP-87 owns the gesture that runs that code; CAP-86
owns the semantics those endpoints carry. STORY-101 states the split in its own
body (*"the workspace that shows the page is a separate capability, and the
validated write path that applies the change is another; this one is the loop
that joins them"*), which shows the boundary was drawn deliberately — but it
leaves no rule for a future story about the transport itself. A story such as
"a refused save surfaces the write path's refusal code in the editor form"
could be filed under any of the three, because the refusal is produced by
CAP-86, relayed by CAP-85 and displayed by CAP-87.

### Cluster 2: Two surfaces serve a rendered page — the builder origin and public delivery
**Capabilities**: CAP-82 (Site Delivery), CAP-85 (Builder Workspace)
**Stories**:
- story-66115f6b (STORY-96): Clean page URLs: the link an author writes resolves the same in local preview and on the deployed site
- story-d34eccd8 (STORY-95): Serve a deployed snapshot: shareable previews and live published sites reach a visitor
- story-e674c60a (STORY-99): The builder workspace... served from a single origin

**Overlap**: The platform now has two independent HTTP serving surfaces with
overlapping obligations. CAP-82 owns *"which URL names which bytes, what a
visitor is and is not allowed to reach, caching, and how a miss is answered"*;
CAP-85 owns an origin that serves *"any rendered channel of any site in the
store"*, confined, with its own staleness rules. Both therefore answer path
resolution, tree confinement and miss-handling. STORY-96 is the sharpest case:
its own body says *"the agreement is the capability, not the mapping"* and that
it *"was closed only when both halves changed"* — the two halves being the
local preview server and the deployed site. It is filed wholly under CAP-82
while half its subject matter is the operator-side serving surface.

### Cluster 3: Cross-cutting `1c` CLI correctness filed inside one domain capability
**Capabilities**: CAP-63 (1c Capture & Diff Fidelity), CAP-71 (L1 Reproduction Pipeline), CAP-89 (Site Materials), CAP-82 (Site Delivery)
**Stories**:
- story-e15a19ef (STORY-79): 1c CLI: flags parse correctly, propagate into sub-commands, and --json emits a clean scriptable document
- story-5e7eb0c5 (STORY-97): Colour census and repeatable palette retrofit (`1c colors ... --json`)
- story-c46abfa6 (STORY-102): Ask my site what assets it has (listing surface, `--json`)

**Overlap**: This is the "infrastructure used by multiple capabilities" signal.
STORY-79 lives in CAP-63, whose scope claims *"CLI argument parsing and output
hygiene"* — but the story's own guarantees are explicitly CLI-wide, naming
`help`, `list`, `repro`, `l1-gate`, `capture` and `values-diff`, and requiring
that *"a store-selecting flag reaches the render/serve it triggers"*. `l1-gate`
and `repro` are CAP-71's commands; `1c colors` is CAP-89's; the deploy/serve
commands are CAP-82's. So a defect in flag propagation or `--json` hygiene on a
non-diff command has no unambiguous home: the behaviour belongs to CAP-63's
declared scope but the command belongs to another capability. The predecessor
capability CAP-66 (1c CLI Argument Parsing & Output Hygiene) was merged into
CAP-63 specifically, which is what created the asymmetry.

### Cluster 4: A gradient is both a diffed fidelity axis and an authorable framework value
**Capabilities**: CAP-63 (1c Capture & Diff Fidelity), CAP-70 (Framework Substrate)
**Stories**:
- story-82eb6908 (STORY-76): Gradients as a first-class value: stop positions and panel surface gradients — captured, authored, and diffed
- story-c490f1cf (STORY-80): Absolute values re-homed in L1: every colour, length, and radius carried as a validated literal

**Overlap**: STORY-76 is filed under CAP-63, but its title and body carry three
verbs — *captured, authored, and diffed*. Capture and diff are CAP-63; the
**authorable** half ("authorable as a content value that resolves to a surface
fill") is a typed value axis reaching the browser through the L1 renderer, which
is CAP-70's absolute-value system and its safe-emitter obligation. CAP-63's own
out-of-scope clause disclaims *"the L1 typed tree, its envelope validator and
safe renderer"* — yet this story adds a value form to exactly that. The
boundary rule that would resolve it (does a new value axis follow the *driver*
that demanded it, or the *layer* that renders it?) is not stated anywhere.

### Cluster 5: The palette colour model versus the migration onto it
**Capabilities**: CAP-70 (Framework Substrate), CAP-89 (Site Materials & Starting Point)
**Stories**:
- story-c490f1cf (STORY-80): ...with a palette overlay for colour
- story-5e7eb0c5 (STORY-97): Colour census and repeatable palette retrofit

**Overlap**: CAP-70 owns the "absolute base + named overlay" value model, which
is where a palette *reference* becomes an admissible form for a colour axis.
CAP-89 owns measuring a site's colours and rewriting its literals as references.
The retired CAP-83 acknowledged the seam in its own words (*"the palette colour
model (framework substrate capability) makes a palette reference an
admissible form..."*), and STORY-97 gates its write on *"the converted
definition still validates"* — i.e. on CAP-70's validator. Any story that both
extends the palette reference form and migrates sites onto the extension (a new
opacity axis, a new derivation rule) straddles the two.

### Cluster 6: Two implementations of the same geometry semantics — renderer and gate evaluator
**Capabilities**: CAP-70 (Framework Substrate), CAP-71 (L1 Reproduction Pipeline)
**Stories**:
- story-24098299 (STORY-86): End-to-end 3-probe reproduction acceptance gate
- story-d0a8cfad (STORY-83): L1 layout substrate rendered safe by construction
- story-3569e1a4 (STORY-81): Responsive layout: a container's layout mode varies per breakpoint and a row can wrap

**Overlap**: CAP-70 owns the renderer's per-viewport `interpolate | snap`
geometry math and its flow stacking. CAP-71's gate runs *"a browser-free layout
evaluator that mirrors the renderer's `interpolate|snap` geometry math and CSS
flow stacking"* — STORY-86 goes further and enumerates axes where the evaluator
was corrected to match the renderer (half-open breakpoint intervals). The
semantics are therefore defined once and implemented twice, in two capabilities.
A story of the form "breakpoint resolution changes at interval boundaries" must
land in both, and there is no stated rule for which capability holds the
canonical definition and which merely conforms to it.

### Cluster 7: The behavior-module contract accretes obligations demanded by its consumers
**Capabilities**: CAP-70 (Framework Substrate — module contract), CAP-87 (In-Page Copy Editing), CAP-86 (Structured Copy Editing)
**Stories**:
- story-179b8c06 (STORY-85): Behavior modules: vetted core + typed config + L1 presentation slots
- story-af36c2cb (STORY-98): The edit render... showing all content at once
- story-46e3b3c7 (STORY-82): Reproduction treatments: card veil/border, placeholder & inline contact form, footer overrides
- story-37a3921b (STORY-100): ...one validated, all-or-nothing edit

**Overlap**: The behavior-module contract is owned by CAP-70, but three other
capabilities add required members to it from outside. STORY-98 (CAP-87)
requires that *"each behavior module declares its own behaviour-off state"* — a
new obligation on every module, specified in the edit-render story rather than
the contract story. CAP-86 requires that *"a document and a behavior module's
slot resolve the same way"* — an addressing obligation on the slot seam.
STORY-82 (CAP-70) exercises the contract from the reproduction direction via
contact-form `config` + named slots. So "add a required member to the module
contract" is a story shape with at least three plausible homes, and it has
already been filed in two different capabilities.

### Cluster 8: The closed set of asset choices — listed in one capability, exposed by another, rendered by a third
**Capabilities**: CAP-89 (Site Materials), CAP-86 (Structured Copy Editing), CAP-87 (In-Page Copy Editing)
**Stories**:
- story-c46abfa6 (STORY-102): Ask my site what assets it has
- story-37a3921b (STORY-100): ...change what a region holds — its words, or which image goes there
- story-3bf94bd4 (STORY-101): Click the words on my page and change them

**Overlap**: STORY-102 defines one listing for *"the operator at the command
line, the builder origin, and any editing surface that must present a closed set
of assets to choose from"* — naming its consumers inside its own scope.
STORY-100 says image selection's whole substance is *"what a region answers when
asked which fields it exposes — and the closed list of choices that answer
carries"*. Both stories therefore claim the closed choice list: CAP-89 as the
authority on what exists, CAP-86 as the authority on what a field may hold, with
CAP-87 rendering it in the form. A story like "an undeclared file must not be
offerable as an image choice" is ambiguous between CAP-89 and CAP-86.

### Cluster 9: The standard width ladder is claimed by three capabilities
**Capabilities**: CAP-89 (Site Materials), CAP-70 (Framework Substrate), CAP-71 (L1 Reproduction Pipeline)
**Stories**:
- story-86c7c21b (STORY-93): A newly created site is a page that already renders
- story-d0a8cfad (STORY-83): L1 layout substrate rendered safe by construction
- story-8acc338d (STORY-84): Fold a multi-viewport capture into one L1 reproduction document

**Overlap**: STORY-93 seeds *"the standard width ladder"* and makes it
load-bearing that *"the ladder is the capture ladder... the same widths a
reproduction keyframes at"*. STORY-83 owns per-viewport geometry keyframes and
the validator that bounds them (*"geometry keyframes ⊆ the document's declared
widths"*). STORY-84 folds the captured sample ladder onto those widths. One
shared constant, three owners: a story that changes the ladder has no single
home, and CAP-89's scope statement asserts the cross-capability equality as its
own property.

### Cluster 10: The licence gate that stops a ship, versus the ship itself
**Capabilities**: CAP-89 (Site Materials — provenance), CAP-82 (Site Delivery)
**Stories**:
- story-8685be2d (STORY-92): Font provenance: ...an unresolved licence cannot ship as product
- story-5349d01f (STORY-94): Ship a site off the laptop: a content-addressed snapshot deploy

**Overlap**: STORY-92's terminal clause is a refusal at ship time — *"an
unresolved licence cannot ship as product"*, with every gate treating the
unresolved state as no, and the trigger condition being *"a site that ships
across customer domains uses a face shipped as part of the product"*. CAP-82's
scope explicitly owns *"what a deploy reports, what it refuses"*. So the
provenance capability specifies a refusal whose enforcement point is the
delivery capability's command. A story adding a new pre-ship compliance gate
sits on the boundary in the same way.

## Note on retired capabilities

Thirteen capability tickets hold no stories: CAP-64, CAP-65, CAP-66, CAP-67,
CAP-68, CAP-69, CAP-72, CAP-73, CAP-80, CAP-81, CAP-83, CAP-84, CAP-88. All are
`superseded` or `deprecated` and carry `merged_into` / `superseded_by_uid`
pointing at the surviving aggregate. They therefore do **not** constitute
competing claims on their former stories and are deliberately not flagged as
overlap. Several of them do, however, record the seam their merge created — the
clusters above cite CAP-83, CAP-80 and CAP-66 for exactly that reason.
