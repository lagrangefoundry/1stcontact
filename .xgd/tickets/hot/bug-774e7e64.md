## Symptom

In local dev the builder is browsed through `bin/access-sim` (127.0.0.1:8799), which proxies everything to the dev server. It **buffers every response to the end before sending any of it**:

```js
// bin/access-sim, ~L504
const out = Buffer.from(await upstream.arrayBuffer())
...
outHeaders['content-length'] = String(out.length)
res.writeHead(upstream.status, outHeaders)
res.end(out)
```

That is harmless for ordinary requests and wrong for streams. The chat's `POST /api/ai/prompt` and reattach responses are `text/event-stream`: the consultant's text as it is written, the working line, step lines, milestone posts and the announcement before a build are all events inside that stream. Through access-sim none of them can reach the browser until the turn is over.

Consequence: every dev observation of "she goes quiet for 15 minutes" and "nothing tells me she's working" has been measured through a proxy that hides exactly that. Production uses the real Cloudflare Access, which streams.

## Fix

- Pass the upstream body through as it arrives instead of reading it whole: write headers on arrival, then pipe `upstream.body` to `res` (e.g. `Readable.fromWeb(upstream.body).pipe(res)`), without a `content-length`, keeping the existing header rules (drop hop-by-hop and encoding headers, keep `set-cookie`). Streaming every response is simplest; at minimum stream `text/event-stream`.
- A client that disconnects aborts the upstream fetch, so a closed tab doesn't hold a builder connection open.
- Keep the existing `redirect: 'manual'` and 502-on-unreachable behaviour.

## Test plan

UAT (`test_UAT_FC_<ID>_*`): start access-sim against a stub upstream that writes one SSE frame, waits, then writes a second; a client reading through access-sim receives the first frame before the upstream writes the second. Also: a plain JSON response still arrives intact with its status and `set-cookie`.

Found during the EPIC-19 investigation of a chat error (2026-10-18).
