## Symptom

In local dev the builder is browsed through `bin/access-sim` (127.0.0.1:8799), which proxies everything to the dev server. It **buffers every response to the end before sending any of it**:

```js
// bin/access-sim, ~L504
const out = Buffer.from(await upstream.arrayBuffer())
...
outHeaders['content-length'] = String(out.length)
res.writeHead(upstream.status, outHeaders)
res.end(out)
```

That is harmless for ordinary requests and wrong for streams. The chat's `POST /api/ai/prompt` and reattach responses are `text/event-stream`: the consultant's text as it is written, the working line, step lines, milestone posts and the announcement before a build are all events inside that stream. Through access-sim none of them can reach the browser until the turn is over.

Consequence: every dev observation of "she goes quiet for 15 minutes" and "nothing tells me she's working" has been measured through a proxy that hides exactly that. Production uses the real Cloudflare Access, which streams.

## Fix

- Pass the upstream body through as it arrives instead of reading it whole: write headers on arrival, then pipe `upstream.body` to `res` (e.g. `Readable.fromWeb(upstream.body).pipe(res)`), without a `content-length`, keeping the existing header rules (drop hop-by-hop and encoding headers, keep `set-cookie`). Streaming every response is simplest; at minimum stream `text/event-stream`.
- A client that disconnects aborts the upstream fetch, so a closed tab doesn't hold a builder connection open.
- Keep the existing `redirect: 'manual'` and 502-on-unreachable behaviour.

## What landed

- `bin/access-sim` `forward()` now streams **every** response (not just SSE): status and headers are written as soon as the upstream answers, then the body is piped through with `stream.pipeline(Readable.fromWeb(upstream.body), res)`. No `content-length` is set, so Node frames it as chunked. Header rules unchanged: `content-encoding`, `content-length`, `transfer-encoding`, `connection` dropped; every `set-cookie` kept. A body-less response (204/304/HEAD) just ends.
- The upstream `fetch` carries an `AbortController` signal; the response's `close` event before it has finished (the caller went away) aborts it, whether the upstream is still sending headers or mid-body.
- `redirect: 'manual'` and the 502 plain-text answer for an unreachable builder are unchanged. Request bodies are still read whole before forwarding (out of scope).

## Test plan

`tests/test_UAT_FC_BUG-228_access_sim_streams.test.ts` drives a real `bin/access-sim` process in front of a stub builder:

- `the_first_sse_frame_arrives_before_the_upstream_writes_the_second` — the stub writes one SSE frame and holds the second until the test has read the first through access-sim (3 s deadline; no `content-length` on the response).
- `a_plain_json_response_arrives_intact_with_status_and_cookies` — a 201 JSON response arrives with its body, status and both `set-cookie` values.
- `a_client_that_disconnects_closes_the_upstream_connection` — aborting the client mid-stream closes the stub's upstream connection.

Verified the first and third fail against the old buffering code and all pass with the fix; adjacent access-sim suites (BUG-59, REQ-192, REQ-204, BUG-152) still pass.
