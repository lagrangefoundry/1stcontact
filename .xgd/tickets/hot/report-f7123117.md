### Why this overlap is acceptable

The two stories share a **storage substrate** (the declared registry inside the
site definition, and the site's draft asset directory) but not a behaviour. The
split is producer/consumer, and both stories already state it in their own
out-of-scope text:

- **story-c46abfa6 out of scope**: *"Uploading, importing, converting or resizing
  an asset. The store lists what exists; nothing here writes or transforms a
  file."* — CAP-89 disclaims the write.
- **story-b3de4571 out of scope**: *"Uploading any file, including licensed binary
  fonts, which remain the font-registry-and-provenance capability's work."* —
  CAP-94 claims only the one image a model authored, on the security rationale
  that it is the one image no person vouched for.

The boundary is therefore **who authored the bytes and under what grant** (CAP-94)
versus **what does the site contain, honestly reported** (CAP-89).

### Grounded in source

The two paths share the storage locations and not a line of logic:

- `editAssetWrite` (`tools/generate/src/cli/edit.ts:1431`) — CAP-94. Generates the
  filename from a plain word (no path to traverse), narrows the format to one text
  format, runs `validateSvg` (`packages/site-schema/src/svg.ts:239`) as a closed
  grammar, enforces conflict-unless-force, builds the registry entry, calls
  `validateOrThrow` before a byte hits disk, then writes both the file and the
  registry.
- `listSiteAssets` (`tools/generate/src/cli/edit.ts:1287`) — CAP-89. A pure
  union-and-merge over the same two sources, adding provenance (`onDisk`,
  `registered`), handle normalisation (`assetHandle`), usage kind (`assetKind`)
  and deterministic order.

`editAssetWrite` never calls `listSiteAssets`, and `listSiteAssets` has no
knowledge of generated images — a written drawing lands as an ordinary
`{onDisk: true, registered: true}` entry, which is exactly the point.

### No AC-level duplication

The nearest pair was checked and is distinct:

- `acceptance_criterion-651ded8e` (CAP-94) asserts a *generated* drawing is not
  special-cased — it appears in the listing as an ordinary image.
- `acceptance_criterion-feaa4db0` (CAP-89) asserts the listing derives a usage kind
  for *every* asset so a caller can narrow.

Different subject, different failure mode. Likewise `acceptance_criterion-4cd04340`
(CAP-89) covers the present-but-undeclared case, whereas a generated drawing is
written *and* registered — a different state.

### Recorded for a future reconciliation (not a defect)

`acceptance_criterion-651ded8e` creates a **directional read dependency** from
CAP-94 onto CAP-89's listing: its criterion states *"The site's image listing — the
same listing every image picker reads — reports it as an image,"* and its
verification asserts against that listing. This is legitimate strong-observation
use — the listing is the instrument proving the write landed as an ordinary asset,
not a claim of ownership over listing behaviour. It is recorded here so that a
later reconciliation changing the listing's shape knows a CAP-94 UAT observes it.
