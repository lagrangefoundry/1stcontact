## Symptom

The XGD whitepapers form has been correctly configured since Monday — `template:
"whitepapers-email"`, two assets with keys, names and URLs, and consent wording — and has
never sent a message. Every submission captures the contact and mails nobody.

The contact is also attributed to the wrong form. Seven submissions made on the
**whitepapers** page over four days are every one of them recorded as:

    page: "home.json", submitLabel: "Join the waitlist", form: "signup"

— the home page's waitlist form, which the operator never pressed. The record is wrong in
the CRM as well as silent in the mail.

## Root cause

**A component name is unique per PAGE. A submission is resolved per SITE.**

`editModuleAdd` (`tools/generate/src/cli/edit.ts:1867`) refuses a collision within one page
and only within one page:

    Page '<pageId>' already has a component called '<moduleId>'

`formDefinitionOf` (`apps/control-app/src/lead.ts:443`) then scans every page in the site and
takes the first instance whose id matches:

    for (const stored of pages) {
      for (const instance of instancesOf(stored.page)) {
        if (instance.id !== instanceId) continue

The XGD site holds two components called `signup`, both legal:

| page | version | template | assets | label |
|---|---|---|---|---|
| `home.json` | v5 | — | 0 | Join the waitlist |
| `whitepapers.json` | v7 | `whitepapers-email` | 2 | Send me both papers |

`home.json` precedes `whitepapers.json` in storage order, so a submission from the
whitepapers form resolves to *home's* definition. That definition names no template, and
`lead.ts:1134`'s `if (templateKey === '') return outcome` ends the call before any mail is
considered.

Every symptom is that one line: the wrong label and page in the event, the absent assets, the
silence.

**It also defeats [[REQ-247]] from outside.** The email-page pipeline works; the submission
never reaches it, because the configuration it would read is never the configuration loaded.

**And it misled the assistant.** The builder AI configured the form correctly, tested, saw
nothing happen, and told the operator the platform could not send mail — a reasonable
conclusion, given nothing could show it that its own configuration was being ignored.

## Fix

**The handle identifies the page as well as the instance.** The renderer emits
`<pageId>:<instanceId>` as the form's hidden handle, and `formDefinitionOf` resolves against
both halves instead of scanning for the first id that matches anywhere.

**No back-compatibility path.** The only bare-id handles in existence are a dozen rows in a
development store. A compatibility branch for them would be permanent weight carried for a
week-old artifact, and — worse — it would be a branch that GUESSES which form a bare id
meant, which is precisely the defect. A submission carrying a bare id is refused.

**The trust properties are unchanged.** Both halves are untrusted input naming something that
must already exist in the site the ROUTE resolved — exactly what the instance id is today. A
caller who edits the handle can still only name another form in the same site, and can assert
no template, no asset and no tenant of their own.

**Site-wide uniqueness was considered and rejected.** Two pages may each reasonably hold a
component called `signup`; enforcing uniqueness would break existing sites and buy nothing
once the handle names what it addresses.

### What the fix entails, beyond the two halves

Four consequences follow from the handle naming a page, and each is part of this change
rather than an addition to it.

**The grammar is one function, in the module's own vocabulary.** `formHandle(pageId,
instanceId)` and `parseFormHandle(value)` sit in
`packages/framework/src/modules/contact-form/fields.ts`, beside `FORM_INSTANCE_FIELD`, for
the reason that file already gives for the honeypot's name: three parties have to agree on
it and none of them can see the others. The separator is `:`, and the FIRST one is the
boundary — a page id cannot contain a colon (`isValidPageName` admits RFC 3986's unreserved
set less `~`), and a component id carries no such rule, so everything after the first colon
is the instance. `parseFormHandle` returns nothing for a bare id, which is what refuses one.

**The renderer hands every module its page.** `BehaviorProps` gains `pageId`, supplied by
`renderModuleInstances` from `page.id`. It is the renderer because the renderer is the only
thing that knows the answer, and it is on the props rather than in `contact-form`'s config
because a module's own configuration cannot state where it sits.

**Resolution reads the page and then the instance on it.** `formDefinitionOf` matches
`stored.page.id` against the handle's first half — the same name `findPageFile` addresses a
page by, and the name the store key `<id>.json` is built from — and then looks for the
instance on that page alone. There is no scan and no fallback: a handle that does not parse,
names a page this site does not hold, or names an instance that page does not carry resolves
to `null`, exactly as an unknown instance always has.

**A download grant is filed under the handle, and its column is renamed to say so.**
`asset_grants.instance_id` becomes `form_handle` (`db/migrations/0009_asset_grant_form_handle.sql`,
a plain `RENAME COLUMN` — the baseline always creates the old name, so it is correct once
against a fresh database and against a deployed one alike, and SQLite carries the rename into
`idx_asset_grants_live`). This is not cosmetic: the live-grant unique index is
`(contact_id, site_id, instance_id)`, so under the old key a grant minted for the whitepapers
`signup` and one minted for the home page's `signup` were the SAME ROW, and whichever was
minted first would open the other form's artifacts. Existing rows are not backfilled — which
page each bare id meant is the unanswerable question this ticket is about — and a contact who
submits again is minted a live grant under the real handle.

## Test plan

`tests/test_UAT_FC_BUG-93_form_handle.workers.test.ts` — a workerd suite, because the
assertions are on the real capture path against real D1 and R2 rather than on a hand-built
approximation:

- **The symptom, asserted directly.** Two pages each holding a component called `signup`,
  configured differently. A submission from the second resolves the SECOND's definition — its
  template, its assets, its submit label — and the message goes out.
- The `form.submitted` event names the page actually submitted from, and carries that page's
  submit label and asset keys.
- The XGD shape end to end: a form with a template and two assets delivers both; a waitlist
  form on another page of the same site with neither still sends nothing, and the two do not
  interfere in either direction.
- The download grant that submission mints is filed under the handle and not under the bare
  instance id, which is what keeps two same-named forms' grants distinct rows.
- A submission carrying a bare instance id is refused and captures nothing.
- A handle naming a page that does not exist in this site is refused; so is the right page
  with an instance it does not carry.
- A handle naming a page in a DIFFERENT site is refused, and the refusal comes from the
  route's site rather than from the payload.
- Order independence: three same-named forms on pages sorting either side of each other all
  resolve correctly, so the test cannot pass by accident of sorting or by a reversed scan.
- A single-page site with one form is unaffected.
- The at-most-once ledger is untouched by this change: it keys a delivery on the asset and
  the address, not on the form handle, so a contact who already received an asset does not
  receive it twice across the fix.
- The other end of the seam: the rendered form actually carries `<pageId>:<instanceId>` in
  its hidden handle, built by the same function the receiver parses with.

`tests/support/lead-site.ts` grows an `alsoPages` option so a fixture can seed two pages each
holding a form — the shape this ticket exists for, and one that neither two forms on one page
nor two sites can stand in for.
