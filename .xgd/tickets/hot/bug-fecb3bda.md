Parent: [[EPIC-19]]. Reported by the builder assistant in conversation on
2026-09-18; it had no way to file it itself ([[REQ-273]]).

## What happened

> Two attempts at the recursive image, both failed the same way: the picture
> generated fine but couldn't be stored — `store_unavailable`, reported as a
> deployment fault. **It burns the generation cost and hands back nothing.** Two
> identical failures is enough; I've stopped rather than spending more of your
> money into a void.

The assistant's judgement was right on both counts: it is a real fault, and
stopping after two was the correct call.

## Where the bytes go, and where they do not

`@lagrangefoundry/ai-imagegen/src/toolbox.js:519-541`, `_store`:

```js
let ticket
try {
  ticket = await this.store.create({ type: this.ticketType, title, body })
} catch (error) {
  throw new ImagegenToolboxError('store_unavailable', String(error?.message ?? error))
}
…
try {
  attached = await this.store.attach({ uid, bytes: image.bytes, … })
} catch (error) {
  throw new ImagegenToolboxError('store_unavailable', String(error?.message ?? error))
}
```

The generated bytes exist only as `image.bytes`, in memory, for the duration of
this function. There is no write-ahead. So:

- **`create` fails** → nothing was written anywhere. The bytes are discarded when
  the call unwinds. **Unrecoverable.**
- **`attach` fails** → a ticket exists with no image. Upstream's own comment says
  `attach` writes the blob before the record, so *if it got that far* there may be
  an orphan blob for a sweep to collect — but the caller is told nothing about
  which case it was, and there is no operation that could hand the orphan back.

Both raise the same code, with the same declared message:

> The image was generated but could not be stored, so there is no ticket to hand
> on. This is a deployment fault.

`host_detail` is `false`, so the underlying store error — the thing that would
say which of the two happened, and why — never reaches the caller.

## Why this is worse than an ordinary failure

Every other refusal in this system costs a retry. This one costs **money that has
already been spent**, on an artifact that was successfully made and then thrown
away. The generator was paid, the bytes existed, and the only record of either is
a sentence in a chat pane. And because the error carries no detail, a second
attempt is indistinguishable from the first — which is exactly what happened.

## Answering the operator's question: are the bytes recoverable?

**Almost certainly not, for these two.** Recovery would need either an orphan blob
(only possible if `attach` was reached and got as far as the blob write) or a
generator-side history, and this project has no operation that reads either.
Worth one look in R2 for an orphan under the tenant's prefix before concluding —
that look is part of this ticket — but the honest expectation is that the money
is gone.

## What this ticket wants

1. **Write the bytes before the record.** The bytes are the expensive, unrepeatable
   half; the ticket is cheap and reconstructible. Persisting to a staging key
   first means a store failure leaves something recoverable instead of nothing,
   and the existing orphan-sweep concept already covers the housekeeping.
2. **Distinguish the two failures.** "Could not create the record" and "could not
   attach the bytes" are different facts with different recoveries, and the caller
   is entitled to know which.
3. **Carry the cause.** `host_detail: false` on a fault this expensive is the wrong
   trade. The assistant should be able to say *why* it failed, and an operator
   reading the audit should not have to guess.
4. **Do not charge twice for the same picture.** If the bytes survive (1), a retry
   should be able to store the artifact already made rather than generating a new
   one.
5. **Find out why the store was unavailable here**, which nothing in the current
   record tells us.

## Upstream or here

(1)–(4) are the shape of `_store` in `@lagrangefoundry/ai-imagegen` — a
lagrange-framework ticket. (5) is ours: whatever made D1 or R2 refuse a write for
this tenant at that moment is this deployment's to explain, and may well be the
same underlying fault as [[BUG-117]], which broke in the same session.

**Check that first.** Two different surfaces reporting a store-level deployment
fault within one session is more likely to be one cause than two.
