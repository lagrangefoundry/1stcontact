## Story

**As an** operator of the deployed builder, **I want** the deployment itself to
photograph a page at a named viewport size, **so that** the assistant working on
my site can see what it built without a browser running on a machine of mine.

## Description

Capture — navigate a live page, return full-page PNG bytes — becomes available
*inside the deployed runtime*, not only on a developer's laptop. Which browser
answers is chosen by injection: each environment supplies its own way of
acquiring one, and nothing above that choice detects where it is running. The
laptop path is unchanged; this is a second way in, not a replacement.

**In scope**

- A screenshot of a reachable URL returned as PNG bytes, at one of three named
  viewport presets (mobile 375×667, tablet 768×1024, desktop 1280×800). An
  unrecognised preset name is refused by name rather than silently defaulted.
- A deployment with no browser capability configured is an **ordinary state, not
  a boot failure**. Editing, rendering and publishing are unaffected; only an
  attempted screenshot fails, and it fails saying what is missing rather than
  dereferencing nothing.
- Browser sessions are metered and capped, so a run **leases** one browser and
  hands each capture its own isolated context — own cookie jar, cache and
  storage, destroyed with the capture. The lease is time-bounded and released on
  **every** exit: success, failure, and time-limit. A stranded session is not a
  leak that reads as a leak; it counts against a concurrency cap until a remote
  reaper takes it, so a handful of wedged runs degrade into an outage that reads
  as a hang.
- **One navigation per capture.** A capture's record of what the page requested
  is what the security conformance dimension checks egress against, so a capture
  reused across two pages would merge the first page's network log into the
  second and land as a *clean verdict on a page that was not clean* — a false
  answer rather than a crash.
- **Honest limits.** The cloud path does not offer interaction-state actuation,
  so a multi-state capture restricts itself to the resting state and *says so*,
  rather than emitting an unactuated frame labelled `hover` that would read as a
  false clean.
- **One set of capture preconditions for every capture path** — motion landed
  and pre-animation hidden blocks revealed, the full-height scroll that trips
  lazy-load and entrance observers, the image-decode wait, the early font await
  and the pre-extraction per-run font barrier. A cloud capture and a laptop
  capture are the same capture, and every existing CLI verb behaves identically.
- The shipped deployment does not carry the local (Node) browser-automation
  stack.

**Out of scope**

- **Serving this capability over HTTP.** Exposing a metered session on a route
  is a rate-limiting and authorisation decision, not a wiring step, and is
  deliberately deferred to the ticket that gives the assistant the surface. What
  this story owns is the capability and its proof.
- **Screenshotting our own access-gated preview output correctly.** A picture of
  the operator's draft being the draft rather than a sign-in challenge is the
  sibling story from this same reconciliation (plan item 2 — self-origin
  fulfilment). This story can produce a technically perfect screenshot of the
  wrong document; that story is what makes it the right one.
- Moving reference bytes to object storage. That is capture-in-the-cloud; this
  is *eyes*-in-the-cloud, and the intent records both halves and which is open.

## Technical Context

The seam this story documents was declared on the day the capture pipeline was
written and has always had exactly one implementation. Nothing above it changed:
the capture pipeline, the conformance harness and the fidelity gate already
accept an injected browser factory. What is new is a second implementation and
the session economics it forces.

- **Capability placement.** Filed under CAP-102 (1c Capture & Diff Fidelity),
  whose own scope statement already anticipates "adding a browser-driving verb".
  The seam and both implementations live in that capability's capture directory.
- **Sibling story.** Plan item 2 of this reconciliation (self-origin fulfilment)
  depends on this story and supplies the guarantee that a capture of our own
  gated preview is the authored page rather than an access challenge. This story
  deliberately claims only the *browser-driving* half.
- **Deployment configuration is already covered elsewhere.** The new browser
  binding must be declared for every named deployment environment (a named
  environment inherits neither variables nor bindings). That guarantee is
  already owned by the deploy-configuration story, whose criterion identifies
  bindings *structurally* rather than from an enumerated list — precisely so a
  binding kind introduced later is covered without the check being edited. No AC
  here restates it; this story claims only the browser-specific consequence: a
  deployment either takes the picture or names what it lacks.

## Reconciliation Decisions

- **Named viewport presets, and refusal of an unknown one** (decided at
  reconciliation, 2026-08-31): the intent's criterion says only that a
  screenshot "returns a PNG when the code runs inside workerd" — it is silent on
  what sizes are offered and on what an unrecognised size name does. The landed
  code exposes exactly three presets and refuses an unknown name, listing the
  valid set. Formalised as **AC-1459** (PNG returned at the named preset) and
  **AC-1460** (an unrecognised preset is refused by name), because a preset that
  silently fell back to a default would produce a picture at the wrong width
  with nothing anywhere reporting it — the same silent-wrong-picture failure
  shape the rest of this story exists to close.

- **A missing browser capability is a named, catchable error rather than a boot
  failure** (decided at reconciliation, 2026-08-31): the intent assumes the
  binding exists and never says what happens without it. The landed code makes
  the binding optional on the deployment's environment type and raises a
  distinctly named error at screenshot time. Formalised as **AC-1461**, because
  the alternative reading — refusing to boot — would take the whole builder down
  over a capability no route yet exposes.

- **Chromium-only is recorded but not made an acceptance criterion** (decided at
  reconciliation, 2026-08-31): the intent's implementation record states the
  cloud path is Chromium-only, so the other engines in the fidelity ladder
  report unavailable rather than failing. That reporting is the *pre-existing*
  local engine-availability behaviour, unchanged by this work, and the cloud
  path has no engine selector at all. Formalising it here would manufacture an
  AC with no behaviour of this story behind it, so the fact is recorded in this
  Technical Context and no AC claims it. The honest-limits guarantee that *is*
  this story's — an unofferable interaction state is skipped and reported rather
  than faked — is formalised as **AC-1465**.

- **One-navigation-per-capture and rest-only actuation are treated as intent,
  not as gaps** (decided at reconciliation, 2026-08-31): both are stated in the
  intent ticket's own implementation record with their reasons, which is part of
  the operator's ticket. They are documented as ACs (**AC-1464**, **AC-1465**)
  on that authority rather than as reconciliation's own additions.

No contradiction between intent and code was found for this plan item. Every
criterion the intent states for the browser-driving half is honoured by the
landed code.
