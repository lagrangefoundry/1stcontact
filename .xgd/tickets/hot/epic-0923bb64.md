## Why this epic exists

A single hour of design work in the builder chat cost **$20** (2026-09-08,
site-1stcontact). Claude was costing more than minimum wage to draw one hero
segment, and the session felt slow as well as expensive. This epic holds what
we learned, what was fixed, and what is still owed.

The whole diagnosis, the arithmetic behind every number below, and the design
argument for delegation are in the chat transcript on **CHAT-47**
(`chat-5011da11`) — 2026-09-09 to 2026-09-10. Read that for the reasoning; this
body is the standing summary.

## What was actually wrong

Not the model. The request shape.

Every request is one prefix — `[tools][system][messages]` — and Anthropic's
cache matches it from the start. Two consequences govern everything:

- a change invalidates everything **after** it, never before it;
- therefore anything that changes often must sit as **late** in the prefix as
  possible.

A tool-using turn is not one request. After every tool result the backend calls
the API again carrying the whole conversation. The measured 2026-09-08 session
was **15 exchanges but 117 round trips** — one turn alone ran 41 tool calls.

`cache_control` was applied to the **system assembly only**. The message
history — including every screenshot — was re-sent uncached on all 117 round
trips. Cost was quadratic in turn count. Measured breakdown of the ~70k of
accumulated context: screenshots 33%, knowledge search 16%, `get_l1` 14%,
`set_l1` 11% — but screenshots were only ~2% of tokens *billed*, because the
expense was never their size, it was being re-sent 117 times.

Two aggravating facts found alongside it:

- **No token telemetry.** `usage` on the `message_start` frame was read and
  discarded, so spend could only be modelled, never observed.
- **`max_tokens` hardcoded at 4096.** A large `set_l1` payload hit the ceiling,
  the stream ended with no `content_block_stop`, and the tool was dispatched
  with an **empty input object** — silently. Observed twelve consecutive times
  in one session (2026-09-09, Lagrange Foundry site), 34% of all tool calls in
  that session failing, and the model retrying blind each time.

## The fix, and one thing we got wrong first

Caching the message history was the change with the best ratio, and it landed.
But the first version only helped **within** a turn, not across turns — because
the per-turn reminder (which carries "the site moved under you") sat at the end
of `system`, and `system` precedes `messages`. Every turn the reminder changed,
it invalidated the entire history behind it. 1stcontact's reminders change on
nearly every turn by design.

That gap was ours: the original acceptance criterion said "within a turn" and
never mentioned the second *turn*. The follow-up moved the volatile and
reminder tiers **past** the history, appended to the final user message at
request-build time and never written back into stored history. The principle
was generalised, not reversed: stable first, volatile last — applied to the
whole request rather than to one segment of it, because the request is the unit
the cache matches on. Recorded as **DOC-22 Amendment X**.

| | cost for the measured session |
|---|---|
| Before | ~$17–20 |
| System-only caching (in-turn) | ~$7 |
| Message-history caching past the reminder | ~$3 |

Observed in production after the fixes landed: **$1.67 for a 38-minute
session** — and 12 of that session's 48 round trips were wasted on the
truncation bug, so the useful work cost less still.

## What landed upstream (lagrange-framework)

All implemented; all sitting at `ready_to_reconcile`.

| Ticket | What |
|---|---|
| REQ-143 | Rolling cache breakpoints on `messages[]`; configurable TTL; capture `usage` from `message_start` / `message_delta`; Python peer at parity |
| REQ-144 | Deliver the volatile + reminder tiers **past** the history rather than in front of it; DOC-22 Amendment X |
| REQ-145 | Token spend reported from the CLI backends too |
| REQ-146 | Default the API backend to `claude-sonnet-5`; `max_tokens` becomes an option with room in it |
| BUG-48 | API backends dropped a turn's final assistant message — a warm segment sent two consecutive user turns (this is why 1stcontact BUG-66 is `wont_fix`: the defect was upstream) |
| BUG-49 | A reply truncated at the output ceiling dispatches an unfinished tool call and nothing reports it; also made model and ceiling **configuration** rather than framework constants |
| REQ-148 | The delegation surface — hand scoped work to a second session on a cheaper model |

## What is live in 1stcontact today

- **`claude-opus-5`, `max_tokens` 64000**, set in
  `tools/generate/src/cli/ai/backends.json` (BUG-67). The model is now this
  repository's decision, not a framework release — that seam is the part of
  BUG-49 we asked for.
- Message-history caching and per-request token telemetry are in the installed
  shared store and active on every session.
- The truncation failure that produced twelve empty `set_l1` calls is fixed on
  both halves: the ceiling is roomy, and an unfinished tool block is refused
  rather than dispatched.

Note the consequence of the Opus move: **the front face is now the expensive
model.** Opus 5 is $5/$25 against Sonnet's $3/$15, and thinking is on by
default. That is the right trade for judgement — what the thing is, what it
means, which direction to take — and the wrong one for the mechanical majority
of the work, where the payload is large and the decisions are small. Which is
what the remaining work is about.

## What is still owed

1. **Re-measure, from telemetry rather than a model.** Every number above for
   the current configuration is an estimate; REQ-143/145 mean real
   `cache_read_input_tokens` and per-request spend are now recorded. Confirm
   cross-turn reads are non-zero and scale with history, and establish a fresh
   per-session baseline on Opus 5. The CHAT-47 figures predate the Opus move
   and are no longer comparable.

2. **Effort levels — the cheap lever, still not taken.** The backend sends no
   `output_config` at all. Effort does not touch the cache prefix, so it is a
   per-turn dial with no architectural cost: low for mechanical construction
   turns, high for strategy. Not implemented anywhere in the framework yet.
   Worth doing **before** delegation, and this epic should not be used to skip
   it.

3. **Adopt the delegation surface.** REQ-148 shipped and
   `delegation_surface.json` is installed in the shared store, but 1stcontact
   grants nothing from it — `instances.json` declares one role, `consultant`,
   and no worker. Adoption means: a builder role with a narrower grant, a
   backend configured for that role's workers, `DelegateWork` granted to the
   consultant and `ReportDelegatedWork` to the builder.

   The shape the framework enforces, and which we should not fight:
   - the brief is **prose** (intent cannot be enumerated), but authority comes
     from the **role's declared grant** — no phrasing of a goal widens it;
   - the worker's conversation never enters the caller's, so the construction
     transcript stops being billed at the consultant's rate;
   - **no nesting**, and worker spend **rolls up** into the caller's ledger, so
     this cannot make cost invisible again;
   - `accept` checks are the load-bearing part. If Opus has to screenshot and
     re-inspect everything the worker did, the tokens have been moved to the
     more expensive side rather than saved.

   The likely split, from the existing capability groups: builder keeps
   ReadSite, AuthorPages, ManageComponents, MeasureDrawings, DrawImages,
   SeeSite; consultant keeps ManagePages, WriteConfig and ManagePalette — brand
   colours, site structure and config are the decisions worth Opus.

4. **Choose the worker's model from measurement, not from estimate.** On the
   2026-09-08 workload the bulk of spend was construction (21 screenshots, 21
   `write_image`, 18 `set_l1`, 15 `get_l1`). Haiku 4.5 at $1/$5 would do that
   roughly 3× cheaper than Sonnet does today, with the strategic layer on Opus
   small enough that its rate barely matters. That is an argument for trying,
   not a sizing — item 1 supplies the sizing.

## Explicitly not the approach

**Per-turn model switching within one conversation** — Opus for strategy turns,
Sonnet for construction turns, same session. Prompt caches are keyed per model.
Alternating A/B/A/B roughly halves the hit rate and pays the writes twice,
undoing most of what REQ-143/144 bought. Delegation exists precisely because
each side then keeps its own clean cache lineage.
