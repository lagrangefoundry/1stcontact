## 1C page editor — behavior scope (free-coding)

The builder's **site** view (the `site` tab; label is a config value, default "Site"): a non-technical user edits a site's copy and images
directly on a live preview. Only copy, asset selection, and friendly parameters
(e.g. a colour picker) are ever exposed; framework tokens/dials/axes are never
shown; anything sophisticated is delegated to the AI. Direct manipulation is a
*second producer of the same validated structured edits* the AI emits — never raw
HTML/CSS.

**Design is now documented:** [[DOC-8]] (builder app architecture — rewritten
2026-07-30 to withdraw in-browser render, the click-to-edit ban, and the
React/shadcn chrome) and [[DOC-28]] (the page editor itself). Those are
authoritative; this ticket is the free-coding scope.

Architecture decisions:
- The builder is a **feature of the `control-app` Worker** (`app.1stcontact.io`) —
  one 1C application, not a separate app or server. `public-site` is the
  multi-tenant server for the sites themselves.
- Preview is **server-rendered HTML in a same-origin iframe** (DOC-7 §2.4;
  DOC-8 §3.1 browser-render is withdrawn). Published sites render at build time;
  the draft preview renders on request. Same origin, so the builder overlays
  hover/click onto the iframe document.
- Editing granularity is **per block** (click a block → modal of its copy fields),
  enabled by a `data-fc-module`/`data-fc-type` hook stamped per instance at render
  time.
- Builder chrome is **vanilla ES modules on the `@gendevlabs/webui-*` components**
  (not React/shadcn), consumed from `xgd-framework` by **publish or submodule** —
  never copied into this repo, so the shell has one source of truth. (An earlier
  plan here to vendor `webui-shell` into `packages/builder-ui/vendor/` is
  withdrawn.)

- **Edit mode is a third render channel**, not a client-side overlay: the same L1
  document rendered with links/forms/behaviour/motion off, content in its settled
  state, and segment handles stamped by the renderer as it walks the tree.
- **Segments are derived** from the L1 tree (text → copy segment, image → image
  segment, painted box → container segment, module instance → module segment),
  not declared in the definition.
- **No structural editing in v1** — add/remove/reorder/resize/reposition stay with
  the AI.

**Implementation plan: [[DOC-28]] §12** — five tickets for phase 1:
T1 builder shell (the `site` tab; label is a config value, default "Site") ·
T2 the edit render (parallel with T1) · T3 copy editing, the first end-to-end
edit · T4 image selection · T5 deploy (request-time SSR in `control-app`).
Chat pane and phase-2 properties are follow-on, deliberately unticketed.
That table is authoritative; do not maintain a second milestone list here.

M1 (module edit-hooks, `data-fc-module`/`data-fc-type` stamped in
`tools/generate/src/render/render.ts`) is **done** and landed with tests
(`tests/chat9-edit-hooks.test.ts`).

The M3 blocker is resolved: because edit mode is its own render, the renderer
stamps a **render-scoped structural path** on each L1 node as it emits it. No
schema change, no persistent ids, no author burden — a fresh render regenerates
the addresses, so reordering cannot invalidate them. DOC-28 §5.2.

Naming note: "Weber" was a dictation artefact for the web-builder and is dropped
throughout — the editor is a feature of the 1C app, not a separately named
product. The last two code comments were renamed to "web editor" in 631b1ff31.
