## Observations

- **Empty matrix -> all features.** No `story`/`capability` tickets exist, so no `upgrade` items are possible; the reuse-first bias has nothing to reuse. Every REQ behavior needs a new story.
- **REQ-52 is an umbrella re-import** that surfaced three distinct capability buckets — tooling (items 3), hero positioning (item 4), and prose width (item 5). Split accordingly rather than forced into one story, because they touch unrelated modules with independent correctness rules.
- **REQ-54 + REQ-57 collapsed into one story (item 8).** REQ-57 extends REQ-54's block-document model in place (same module, same round-trip contract); the flat->block pivot within REQ-54 supersedes the initial flat model, so no parallel implementation survives. Two intents, one evolving capability.
- **REQ-56 kept as one coarse story (item 7)** across five commits/phases. All phases implement the same subscale pipeline (tokens -> consumer -> escape hatch -> capture -> diff) and share vocabulary; per-phase splitting would inflate the count with non-independent slices.
- **Dependencies** reflect code-level build order: items 2, 3, and 7 operate on the object-card structure introduced by item 1; item 7 phase-5 attribution also rolls up item 2's exact-match per-element rows.
- **FC-test evidence block was empty** in the dispatch, but the commits add test_UAT_FC_REQ-51/52/53/54/55/56/57 UATs; every such REQ has a covering plan item, so the story cycle can formalise each FC UAT into an AC and no FC orphans should remain.
- **Scope check (Step 3b):** all touched code maps to the seven bundled intents; no changes fall outside them, so no unintentional-regression notes against other intents' matrices are needed. Site-data edits (gigabytealchemy/1stcontact/harbor-cafe/ADA/Alchemy) are free-coding-exempt authoring, not framework capability, and are excluded from the plan.
