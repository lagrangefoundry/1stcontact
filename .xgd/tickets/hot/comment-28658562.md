#### Claude
Design is in the ticket (REQ-136, now titled *"Image editor: non-destructive framing and colour adjustment"*). The substance:

## Your instinct is right, and it's already the mandated model

Don't touch the bytes. Every tool writes a typed L1 axis; the renderer applies it. DOC-28 §9.2 already says this, and the reasons compound: one asset serves many framings, edits stay ordinary structured diffs (same validator, same one-modal-one-diff, same undo), no server-side image decoding to add as attack surface, and — the one that matters most for us — the AI can read `saturate: 0.4` and reason about it. It cannot read pixels.

The honest cost is bytes: a 4000px hero cropped to a thumbnail still ships 4000px. That's performance, not correctness, and the fix is additive later (a derived-render cache keyed on `(asset, adjustment)`).

## "Appears the same in the editor" is free — if you don't break it

The editor's preview **is** the edit render channel: same renderer, same L1 document. So parity isn't a feature to build, it's a consequence of putting the adjustments in L1. Two things could break it:

1. **Drag feedback.** A round-trip per pointer-move isn't 60fps. Answer: extract the adjustment→CSS mapping as a pure function *shared with the renderer*, and have the modal apply it as inline style to the live element while dragging. One emitter, two callers — same discipline as the shared validator. Cancel reverts; Save re-renders from the origin.
2. **A copy of the image in the modal.** Reject it. The iframe is same-origin and the bridge already reaches into that document, so draw the crop handles **over the real element on the page** and let the modal be a control panel. Then there's no copy to drift.

## What you already have vs. what's missing

Rotate (`transform.rotateDeg`) and scale (`transform.scale` / `sizing`) exist. `objectFit` exists. **`objectPosition` and colour adjustment don't** — and the interesting part is that `capture/extract.ts` already reads both `objectPosition` and `filter`, and `fold.ts` drops them because L1 has nowhere to put them. So this isn't only an editor feature; it shrinks the "expressible axes" qualifier on round-trip fidelity.

Also worth knowing: the existing `overlay` scrim **can't tint an `<img>`** (background paints behind replaced content). It does tint a background surface. That asymmetry is why filters are phase 1 and true tint isn't.

## Recommended phasing

**Phase 1** — all cross-browser: `objectPosition` (pan-crop) + a typed `filter` group (grayscale / sepia / saturate / brightness / contrast / hueRotate / blur / invert — bounded scalars, fixed emission order, never a raw string), plus `objectFit` exposed and rotate reused. That delivers crop-by-panning, rotate, scale and colorize.

**Phase 2** — zoom. `object-view-box` is the semantically exact primitive but is [not Baseline — unsupported in Firefox](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/object-view-box), so it fails the 3-engine gate. My recommendation: L1 keeps a one-node `crop` rect and the **renderer** emits a wrapper `<span>` with the clip — one L1 node, two DOM elements, construction owned entirely by the sole emitter (precedent: `link` already wraps the img in `<a style="display:contents">`). The alternative — an `overflow` axis plus an authored wrapper box — re-opens the "two nodes for one element" hole REQ-98/105 closed.

## Four things I need from you

1. **Is pan-only crop enough for v1?** If zoom is required, phase 2's wrapper decision moves to the front.
2. **"Scale" — which one?** The element's size on the page, or the picture's zoom inside a fixed frame. Different axes.
3. **"Colorize" — which one?** Adjustments (saturate/brightness/warmth/B&W) or a true tint/duotone. The second needs the wrapper too.
4. **Scope — `<img>` only, or background surfaces too?** The picker already serves both; if the editor should as well, the axes get named at intent level and the renderer picks `object-*` vs `background-*` per kind.

One note: the tree has uncommitted REQ-132 picker work in it (`image-picker.js` and friends). I left it untouched — but this ticket builds directly on that modal, so it wants to land first.

## Your shape question — all four work now

| Shape | How | Already possible? |
|---|---|---|
| **Circular** | `mask.shape: 'circle'` / `'ellipse'` | **Yes** — existed, just never exposed |
| **Rounded corners** | `axes.borderRadiusPx` | **Yes** — existed, never exposed |
| **Parallelogram** | `mask.shape: 'parallelogram'` + `slantPct` (±45) | New |
| **Random splat** | `mask.shape: 'blob'` + `roughness` (0–1) + `seed` | New |

Both new shapes compile to `clip-path: polygon(…)` built entirely by the renderer from those numbers — the document names an intent, never geometry, so the shape vocabulary widens without the attack surface widening.

The blob is **deterministic in its seed**: 24 vertices, radius perturbed by a seeded hash and smoothed across neighbours (24 independent radii read as a spiky star, not a blob). That's not polish — a shape that differed between two renders would break round-trip identity and make the picture twitch on every save. Rounding and masking are independent, so a rounded blob works and neither control clobbers the other.

## What phase 1 got you

**Three L1 axis families:** `objectPosition` on the image leaf (pan-crop, both components or neither — CSS silently defaults an unspecified one to 50%); a typed `filter` group on the *shared* surface (CSS-canonical fractions, fixed emission order because filter functions compose in sequence); and the two new mask shapes.

**Thirteen controls on the image segment** — fill mode, pan across/down, shape, corner rounding, rotate, scale, and six colour adjustments — every one a bounded integer or the axis's own keyword list.

**No new plumbing was needed.** The ticket predicted a numeric field type and a slider; REQ-135's `'integer'` descriptor with `min`/`max` already covers every control, and the modal's existing `type !== 'string'` split routes them into the property sheet with zero client changes.

**Two capture gaps closed, not just a UI gap.** `object-position` and `filter` were read by the capture all along and dropped by the fold — and `filter` was already a Type-A axis the values-diff compares, so every target painting one reported a delta nothing could close. Both now fold.

Three things worth knowing before you look at it:

- **Five existing suites pinned "an image segment exposes exactly `src` + `alt`".** REQ-136 changes that deliberately, so I re-stated each as its actual subject (the pair comes first, in that order) rather than as an exhaustive list — the same treatment REQ-135 already applied on the copy side. The supersession is recorded in the ticket with the AC list.
- **Pan only, no zoom.** True source-rect crop is phase 2 and needs the wrapper decision (`object-view-box` is exact but unsupported in Firefox, so it fails the 3-engine gate).
- **Image leaf only.** A painted surface's background is still pinned to `cover / center / no-repeat` by BUG-13; same intent, different CSS family, its own change.

Happy to add the palette-driven tint, unpin background framing, or take the zoom wrapper decision next — but I'd suggest looking at it first, since that was the point of "see what it gets us".
