### Why this overlap is acceptable

**1. The current home is a declared, deliberate consolidation — not an accident.**
CAP-63's own charter opens with "the `1c` reproduction toolchain's capture -> compare
spine, **and the CLI surface that makes it scriptable**", and carries a dedicated scope
bullet: "CLI argument parsing and output hygiene - boolean flags parse as boolean and do
not swallow following positionals; in `--json` mode stdout carries only the single JSON
document, with render/bootstrap diagnostics routed to stderr."

CAP-66 (`1c CLI Argument Parsing & Output Hygiene`) existed as a standalone capability and
was merged into CAP-63 on 2026-08-05 by structural rebalance (`status: deprecated`,
`merged_into: capability-aa030c83`), because it was individually below the matrix minimum
UAT threshold while covering one facet of the same capture-and-compare pipeline. Re-homing
STORY-79 now would reverse that decision and strand the CLI axis on a capability that does
not claim it.

**2. The other two capabilities appear only as negative space, never as co-owners.**
The story's cross-cutting reach is real but asymmetric. Its *positive* subject is entirely
CAP-63's verbs; the CAP-82/CAP-89 verbs are named only to state they are exempt:

- Guarantee 1 (boolean flag parsing) - `values-diff`. CAP-63.
- Guarantee 2 (`--json` stdout hygiene) - `values-diff`. CAP-63. The bootstrap-quiet clause
  names `help`, `list`, `repro`, `l1-gate`, `capture`, `values-diff` - none owned by CAP-82
  or CAP-89.
- Guarantee 3 (store-flag propagation) - `aligned-crops`, a capture/compare verb.
- Guarantee 4 (Astro-free render path) - the render path's container construction.
- Guarantee 5 (dependency preflight) - AC-1017 pins the gated set as exactly `capture`,
  `shot`, `values-diff`, `adopt-gaps`, `crop`, `diff`, `gate`, `aligned-crops`. Every one is
  a capture/compare verb. `serve` (CAP-82), `builder` (CAP-85), the structured-edit commands
  (CAP-86), and `repro`/`refold`/`l1-gate` (CAP-71) are enumerated in the **never gated**
  list.

A capability named only in an exemption clause is not a candidate owner. Reassigning to
CAP-82 (`Site Delivery: Deploy & Public Serving`) or CAP-89 (`Site Materials & Starting
Point`) would place the story on a capability none of whose commands it gates.

**3. No AC-level duplication exists — the boundary is clean in both directions.**
Reviewed every AC across CAP-82's three stories (STORY-94/95/96, AC-892..927) and CAP-89's
four stories (STORY-92/93/97/102, AC-857..876, AC-939..947, AC-1018..1023). The adjacent-
looking ACs are distinct in subject:

- AC-900 (deploy report names each stage on a labelled line) - the *content* of the deploy
  report, not stream separation.
- AC-868 (font check offers a machine-readable form whose success flag agrees with exit
  status) and AC-940 (census available as a single machine-readable document) - the
  *existence and shape* of each command's own `--json` form.
- AC-1022 (the store answers from the command line) - CLI reachability, not parsing.

None of these assert anything about flag-token consumption, stdout/stderr routing, bootstrap
suppression, sub-command flag forwarding, or dependency preflight. Conversely STORY-79's
AC-656/657/658/659/720/738/739/1013-1017 assert nothing about the content of any diff, crop,
deploy, census, or asset listing. The division is **mechanics of the CLI surface (STORY-79)
vs. the substance each command reports (owning capability)** - a clean, statable boundary.

**4. The one genuine contact point is a fixture, not a claim.**
Guarantee 4 / AC-739 uses "the empty starter" as one of the cases that must render with no
Astro container. That touches CAP-89's authoring start point (STORY-93, AC-869..876), but
only as a test input: AC-739 asserts whether a container is constructed, while STORY-93
owns what the starter *is* and that it validates and renders. No assertion is duplicated.
