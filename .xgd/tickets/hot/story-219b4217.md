## Story
**As a** business operator, **I want** every message we send a contact to be kept as a record on that contact, updated when the provider reports it delivered or bounced, **so that** I can see what each person actually received, whether it arrived, and which addresses are bad, without waiting for someone to just not turn up.

## Description
REQ-198 (design ref CHAT-39) adds an `email` record type to each business's own store. There is one record per outgoing message, joined to the contact it went to and to the specific address it went to. A bounce is a fact about an address, not a person, and REQ-191 gives a contact several addresses.

In scope:
- **The record.** Fields: contact, address, template key, optionally the template ticket (version), subject/from/to as sent, status (`queued` | `sent` | `delivered` | `bounced` | `failed`), provider message id, `queued_at` / `sent_at`, and a failure reason. The body is the rendered text as sent, not a reference to the template.
- **Queue -> send -> update.** The record is written `queued` before the provider is called. A successful send moves it to `sent` with the provider id and a send time. A failed send moves it to `failed` with the reason, and the caller does not get an exception. The sending port is passed in, never imported (REQ-196's port).
- **The signed delivery webhook.** Unauthenticated by necessity, it is mounted ahead of the Access gate on an exact path + POST match. It does not trust anything in a request until the request has passed four checks:
  - the shared secret is configured; otherwise it fails closed;
  - the provider headers are present;
  - the timestamp is within 5 minutes;
  - the HMAC signature verifies over the raw bytes. Any listed signature may match.

  After that it parses the body. `email.delivered` -> `delivered`, and `email.bounced` -> `bounced` with the provider's bounce reason. Other event types are acknowledged and ignored. An event naming no message we sent writes nothing and answers 404.
- **What the operator sees.** The Contacts detail pane gets a **Messages** section: the contact's messages newest first (by queued time), showing subject, when, status, and the failure reason on failed or bounced rows. The Contacts list marks contacts who hold a bounced message. The people list read reports them as a separate `bounced` list scoped to the business.

Out of scope (per REQ-198): retry of any kind, open/click tracking, inbound mail, aggregate reporting, any call site that sends mail (REQ-199's invite modal), and writing `email.*` contact events (deferred to REQ-199).

No unscoped cross-tenant read is created. The provider id is matched in code and never interpolated into a query predicate.

- `EMAIL_WEBHOOK_SECRET` is a Worker secret, never a committed var. The scheme is Svix/Resend-style: `webhook-`/`svix-` id, timestamp and signature headers, with the signature over `id.timestamp.payload` and keyed by the base64 part of `whsec_...`.
- `contact_id`, `address_id` and `template_uid` are plain strings, not ticket references. Contacts and addresses are identity rows rather than tickets, and an archived template must not make the record of a real send unwritable.
- Architecture policy #18/#26 (DOC-5): provider-managed email and evidence of what was sent. The webhook is the single deliberate route ahead of the Access gate. It is a platform endpoint, outside the L1 security-policy scope (§5).

## Reconciliation Decisions
- **All webhook refusals look identical on the wire** (decided at reconciliation, 2026-11-04): REQ-198 says only that the webhook must reject an unverified request. The code answers every refusal (unconfigured, missing headers, stale timestamp, bad signature) with the same 401 "Refused." and logs the distinction instead, so an anonymous caller learns nothing about which check failed. Formalized in the signature and fail-closed ACs.
- **Unmatched event -> 404, nothing written** (decided at reconciliation, 2026-11-04): REQ-198's added acceptance says "without writing anything" but names no response. The code answers 404 so that two deployments sharing one endpoint show up as a misconfiguration rather than being silently absorbed. Formalized in the unmatched-event AC.
- **Non-delivery events (opens, clicks, `email.sent`) are acknowledged and ignored** (decided at reconciliation, 2026-11-04): intent excludes open/click tracking but is silent on how the endpoint answers such events. The code returns 200 and writes nothing, so a slow `email.sent` cannot overwrite a `bounced` that arrived first. Formalized as its own AC.
- **Bounce reason is stored as the failure reason and shown on the row** (decided at reconciliation, 2026-11-04): intent asks that a bounce "identifies the address" and that a failed send shows why. The code also stores the provider's bounce message on the record and the pane prints it. The address is identified by the record's address id. Formalized in the delivery/bounce AC.
- **Messages ordered by queued time; an unknown contact gets an empty list** (decided at reconciliation, 2026-11-04): intent says "most recent first, showing ... when". The code orders by queued time, because failed and queued rows have no send time, and answers an unknown or foreign contact id with an empty list rather than a 404, so the route is not an existence oracle. Formalized in the messages-pane ACs.
- **Empty subject is still recorded** (decided at reconciliation, 2026-11-04): intent is silent. The subject is kept verbatim and the record is still written (titled "(no subject)"), so the evidence of the attempt is not lost. Formalized in the queue-first AC.
- No intent/code contradictions were found.
- **CODE-ISSUE — a store failure after the provider accepted is recorded as `failed`** (recorded at reconciliation, BUNDLE-37 review report-0cfddba5). In `messages.ts` the provider send and the `sent` store update share one `try`. If the provider accepts but the update throws, the catch marks the record `failed` with no `provider_id`, so later delivery webhooks for that message answer 404 and pressing send again duplicates the mail. No criterion endorses this; it is left for a follow-up fix.
- **CODE-ISSUE — a late `delivered` event overwrites `bounced`** (recorded at reconciliation, BUNDLE-37 review report-0cfddba5). The delivery webhook applies `event.status` unconditionally to the matched record (`messages.ts`), so an out-of-order `delivered` after `bounced` moves the record backwards. This contradicts the module comment "Nothing moves backwards". No criterion endorses this; it is left for a follow-up fix.
