## Symptom

1. **"On a computer" instead of "Desktop".** The builder's width control names its settings **Phone**, **Tablet**, **Desktop** and **Fit pane** (`apps/control-app/src/builder/view-width.js`). The consultant says "on a computer", "at computer width", "the computer header", so the client has to translate between the conversation and the UI. Operator: *"The consultant should say 'Desktop' not 'On the computer' to align language with the UI."* The consultant is taught the phrase: the layout-check host notes (`tools/generate/src/cli/ai/host-core.ts` "…checking the page on a computer and a phone…", and the matching line in `priming.json`), the plan criteria in `plan-core.ts` ("At computer width…", "at computer and phone widths"), and `upgrade-check.ts`.
2. **Filed issues the operator can't find.** When the consultant reports a platform fault, it gives the operator the record's internal uid ("I filed it as platform_issue-f87da062"). The platform console lists the same issue under the business as **PLATFORM_ISSUE-13** (`platformIssuesOf` → `human_id`), and nothing tells the operator where to look. Operator: *"The consultant says it's filing tickets but I can't find them."* They're in production's platform store, not the repository's tickets.

## Expected behaviour

1. **Widths are named as the UI names them,** everywhere the consultant speaks or is taught: **Desktop**, **Tablet**, **Phone** (capitalised as on the control when referring to the setting). "Computer" isn't used for a width. Every host note, guidance line, plan criterion and check message that names a width uses the same names, taken from the same table as the width control (`view-width.js`'s labels), so the two can't drift.
2. **A filed platform issue is named by its human id,** the one the platform console shows (PLATFORM_ISSUE-n): `ReportBug` returns it, and the consultant uses it in what it tells the operator. To the client, it still says only that it reported a fault on our side, with no id.
3. **The operator is told where to find it** the first time in a conversation the consultant files one: "Platform console → this business → Issues".

## Root cause (found while fixing)

- **The human id was never there to give.** Both peers of `@lagrangefoundry/ticketing` project a ticket (`canonical()`) *without* `human_id`; it lives only on the storage record. The product's `Ticket` type claimed a `human_id`, so `platformIssueProject`'s `filed()` read `ticket.human_id`, always undefined. `ReportBug` answered `{ id: null, uid: "platform_issue-…" }`, and the consultant could only quote the uid. The console's list read the same missing field, so its rows had no id either (the id is dropped from the summary line when null). The stale-preview filing route (`POST` preview-stale, BUG-400) fell back to the uid for the same reason.
- **Widths:** the guidance texts were hand-written with "computer"; the upgrade check also captured at 1280/390 (not the control's 375 Phone) and named a difference by px only.

## What changed

**Filed issues (`apps/control-app/src/platform-issues.ts`, `tickets.ts`).**
- `TicketStore.accessor` now types the scoped `get(uid)` the component already provides, and the accessor's records as `StoredTicket` (`Ticket & { human_id }`). `Ticket` no longer claims `human_id`, which the canonical shape never carries.
- `platformIssueProject`'s create / append / get read the human id from `store.accessor.get(uid)`, one scoped read per filing. So `ReportBug` (and `add_ticket_detail`) answer with `id: "PLATFORM_ISSUE-n"`, and the stale-preview route's `filed` is the human id too.
- `platformIssuesOf` (the console's "Issues filed" list) pages the accessor's listing (200 per page, untrashed only), so each row's `id` is PLATFORM_ISSUE-n.

**The consultant tells the operator (`priming.json` `rules-filing`, `roles.ts consultantRules`).** Rule 11, where ReportBug is granted, now adds: *"To the operator, in `bc`, name a report by the `id` ReportBug answered with (PLATFORM_ISSUE-13), never its uid; the first time in a conversation, add where it is: Console → this site → Issues filed."* "Console" and "Issues filed" are filled from the console's own labels (`CONSOLE_LABEL`, `PLATFORM_ISSUES_LABEL` in `builder/config.js`), so the path matches the UI. In the console you choose a site, so the path says "this site" where expected-behaviour 3 said "this business". Client-facing wording is unchanged: no id to the client. Without ReportBug, nothing about filing is said.

**Widths in the control's words, from `view-width.js`'s `VIEW_LABELS`:**
- host-core layout note: "checking the page at Desktop and Phone widths"; the pictured-pages line: "at Desktop width"; the brand note: "…px at Desktop".
- `layout-continuation-cue`: `{desktop}`/`{phone}` placeholders filled from the labels ("at Desktop and Phone widths").
- `plan-core` `EFFECT_CHECKS`: "At Desktop width…", "At Phone width…", "…at Desktop and Phone widths".
- `upgrade-check`: captures at the control's Desktop and Phone widths (`NOMINAL_WIDTHS`, 1280 and 375, was 1280 and 390), and names a difference's width as the control does: `[signed-out, Phone 375px]`.
- Declarations (static text): `l1-surface.json` grid starter "4 equal columns at Desktop, 3 at Tablet, 2 at Phone" and "at Phone the photos first"; `plan-surface.json` emblem size "96–120px visible height at Desktop and 64–72px at Phone".
- System KB **DOC-75** (the consultant's tools playbook), a doc edit made directly in the store: the same grid/emblem phrases, plus "the header holds at real size, at Desktop and Phone widths" and "look at every changed page at Desktop and Phone widths". Its "On a computer: click the **+**…" line is about the client's own device when sending a file, not a preview width, so it stays.

Not changed: `layout-check.json`'s own width names (`desktop (1280px)`, `tablet (900px)`) in findings. They're identifiers of the check's rulers, not the control's settings.
