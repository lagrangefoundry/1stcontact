## Symptom

During the long consultant turns on Ariel's site (2026-10-23), the builder's
status widget read **"~1 min · 3:04 elapsed"**: an estimate smaller than the time
already gone. In the 17-minute turn of BUG-256 it read "~5 min" with 11 minutes
gone.

## Cause

The progress frames this host relays (`tools/generate/src/cli/ai/progress-core.ts`)
put the **round's** start in `started_at` on every frame. In
`2e30bbe2fb1c4185812f373ff033bc54` and `35e1c20f…` that stayed the turn's start
for its whole length (00:41:40, and 01:16:03 for a 52-minute turn). Meanwhile
`eta_s` and the "about N minutes" line come from the **current step**: a
`Delegate` note, or a tool note such as "taking a screenshot" (`eta_s: 60`). The
widget therefore compares a step estimate with round-elapsed time. The framework's
own "still working, elapsed N min" lines restart per long tool call, a third clock,
so the chat and the widget disagree too.

## Fix (host side)

- Every model-sourced progress frame that carries an estimate also carries **the
  start of the step it estimates**: when that `Delegate`, tool call or noted step
  began. It is passed as the field agreed with lagrange-framework BUG-93 (for
  example `step_started_at`). `started_at` keeps meaning the round's start.
- A "still working, elapsed N min" line counts from the same step start, so all
  three readings agree.
- No widget or wording change here. That is lagrange-framework BUG-93, and this
  ticket's frames must work with the widget before and after that change.

## Test plan

`tests/test_UAT_FC_BUG-257_progress_frames_carry_the_step_start.*`, using the
scripted-model host harness:

- A turn with two delegated builds: the second build's progress frame carries a
  step start equal to the second `Delegate`'s start, and `started_at` is still the
  turn's start.
- A tool-note frame with `eta_s` carries that tool call's start.
- The relayed "still working" line's elapsed time counts from the step start.
- Re-run the REQ-222 progress UATs and the progress-core suite.
