## Summary

An `image` element set to `sizing.height.mode = "fluid"`, inside a `row` container whose `align` is `"stretch"`, does not stretch to the row's resolved height. It renders at the picture's natural proportions instead. The write is accepted and the fields persist on read-back, so nothing reports a problem — it simply has no visual effect.

## What I was trying to do

A two-column block: a portrait picture on the left at a fixed width, a heading and a paragraph of prose on the right. The client asked for the picture's height to match the height of the text beside it, so the two columns end on the same line.

This is an ordinary editorial layout — a media object where the image fills the depth of its companion column — and there appears to be no way to express it.

## Reproduction

1. A `container`, `layout: "row"`, `align: "stretch"`, with two children.
2. Child A: `kind: "image"`, `sizing: { width: { mode: "fixed", px: 182 }, height: { mode: "fluid" } }`, `axes: { objectFit: "cover" }`.
3. Child B: `kind: "container"`, `layout: "stack"`, `sizing: { width: { mode: "fluid", maxPx: 466, minPx: 240 } }`, containing two `text` children whose combined rendered height (~310px at a 1280px viewport) exceeds the image's natural height at 182px wide (~228px).

**Expected:** the image renders ~310px tall, cropping via `objectFit: cover`, and both columns end level.

**Actual:** the image renders at its natural height (~228px). The row's foot is ragged by ~80px.

## Notes

- `set_l1` accepted the node without complaint; `get_l1` returns `height: { mode: "fluid" }` and `align: "stretch"` intact afterwards. So this is a renderer gap rather than a rejected or silently-dropped field — which makes it expensive to diagnose from the authoring side, because every signal says the edit landed.
- The container's `align: "stretch"` is likewise accepted and persisted.
- Verified visually with a desktop screenshot of the draft at 1280px.

## Why it matters

The workaround is a fixed pixel height guessed against one viewport width. That is correct at exactly one width, approximately correct either side of it, and stale the moment the adjacent copy is edited — the same class of hand-tuned brittleness that pinned geometry keyframes produce, and that REQ-288's percent-of-own-box translate was introduced to eliminate.

## Suggested resolution

Either:

- **Honour it.** An `image` with a fluid height inside a stretch-aligned row should adopt the row's cross-axis height, with `objectFit` governing the crop — matching how a `container` child behaves in the same position.
- **Or refuse it.** If a fluid height on an image is not supportable, reject the write and say so. A silently inert field is the worst of the three outcomes: it costs a diagnosis cycle and it looks to the client as though the requested change was never made.

If neither is feasible, a declarative "match the height of my sibling" would solve the underlying need, but the fluid-height-in-a-stretch-row spelling already exists and is the natural place for it.

## Resolution — honour it

The first option. A `fluid` height is made to mean *fill*, in the CSS spelling that
actually fills, so the field stops being inert.

### Root cause

`sizingCss` compiles `mode: "fluid"` to `100%` on whichever axis it is given —
`width: 100%` for widths, `height: 100%` for heights. That is correct for a width
and inert for a height, and the asymmetry is not arbitrary: a block's containing
width is definite, so a percentage of it resolves; a flex row's height is
indefinite until its own content has been laid out, so `height: 100%` on a child
resolves to `auto` and the node falls back to its natural size. For an `<img>` the
natural size is the picture's proportions, which is exactly the reported symptom.

It is worse than a no-op. Because the *computed* value is `100%` rather than
`auto`, the flex `stretch` step does not apply either — the declaration actively
suppresses the stretch the row would otherwise have given the node for free.

### Behaviour

- **Height is the cross axis → fluid means stretch.** When a node's parent lays
  its children out as a `row` (flex cross axis) or a `grid` (the block axis of the
  track), `sizing.height.mode = "fluid"` compiles to `height: auto` plus
  `align-self: stretch`. The node adopts the row's resolved height. An `image`
  with `axes.objectFit = "cover"` therefore crops to that height instead of
  ignoring it, which is the ticket's expected result.
- **Height is the main axis → unchanged.** Under a `stack` parent — and under a
  `box`, which is not a flex container at all — `height: 100%` is retained. There
  the percentage has a definite parent height to resolve against whenever one is
  declared, and where none is there is no free space to fill either.
- **The child's own intent beats the container's alignment.** `align-self` is
  emitted on the child, so a node that asks for a fluid height stretches even in a
  row whose `align` is `center`, `start` or `end`. Per-node sizing is the more
  specific statement; the container's `align` remains the default for every child
  that does not make one.
- **Width is untouched on every axis and in every parent.** The defect is
  height-only, for the reason given above.
- **`minPx` / `maxPx` still compile to `min-height` / `max-height`** beside the
  fluid spelling, on both branches.
- **A responsive parent restates it per breakpoint.** REQ-104's
  `responsiveLayout` can flip a container between `row` and `stack` across the
  width ladder, which changes *which axis* `height` is. Where a track crosses that
  boundary the fluid-height spelling is re-emitted at each breakpoint that flips
  it, and emitted **whole** — including the `align-self: auto` reset on the stack
  side — on the same rule as `layoutDecls`: every rule in the cascade is
  self-sufficient, so no half of a spelling can leak past a media boundary into a
  mode it is wrong for.
- **Nothing else moves.** A document whose fluid heights all sit under `stack` or
  `box` parents renders byte-identically to before.

### Not chosen

*Refusing the write* (the ticket's second option) would have closed the diagnosis
hole but left the editorial layout — an image filling the depth of its companion
column — unexpressible, and the spelling already exists and is the natural one for
it. A declarative "match my sibling's height" is not needed: that is what a
stretch-aligned row already means.

### Test plan

`tests/test_UAT_FC_BUG-133_fluid_height_stretch.test.ts` — the emitted stylesheet
for the ticket's own reproduction (fixed-width image + fluid text column in a
stretch row), a row aligned `center`, a `grid` parent, a `stack` parent, a
`responsiveLayout` track that flips row<->stack, the min/max companions, and a
no-fluid-height document proving the byte-identical floor.
