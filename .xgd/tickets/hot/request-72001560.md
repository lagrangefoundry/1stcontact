# Review the session prompts and turn reminders — and make the chat summary one of them

## What this ticket is now

The session's priming grew by accretion, and the governing principle was never
stated: **nothing duplicative or irrelevant reaches the context.** This ticket
states it, restructures the session's texts around it, and closes the two gaps
that fall out.

Two pieces that were originally scoped here have landed elsewhere and are no
longer in scope:

- **[[REQ-174]]** retired `caretaker` and declared `consultant`, rewrote the
  system prompt for it, and left `LEGACY_ROLE_NAMES` so old sessions still read.
- **lagrange-framework REQ-113** added a `summary` level to the projected manual
  (`render(grants, order, { level })`) and a declared `DescribeTools` operation
  for fetching the full entry of a named tool.

REQ-113 is `free_coded` upstream but **not yet delivered to this repo's shared
store, and not wired**: all three call sites still pass `box.manual()` with no
level.

## The three-part structure

Four texts reach the model today. They should be three, split by **what changes
them** rather than by where they happen to live:

**(1) Product level — role-independent.** What the product is. What tools are
available and what they are for. How to reach the knowledge system. This is true
for every role, so it is written once and no role restates it.

**(2) Role level — per role.** What this session's role is, and the specific
documents it must read and follow.

**(3) Reminder — per role, per turn.** A handful of lines, and only what decays.

The win is (1) being role-independent. Today the system prompt is per-role and
carries product facts — how the site is built, tools-only, a malformed change
refused whole, private until published — every one of which is equally true for
the caretaker when the ongoing tier arrives ([[DOC-33]] §10/§11). Under the
current shape, standing that role up means copying them into a second prompt,
which is exactly the drift [[REQ-126]] exists to prevent.

It also removes a duplication upstream. The KMS usage doctrine — retrieval is
cheap so do not assume, query in natural language, the bolded map terms are
validated access points — is currently written twice: once as `DEFAULT_MECHANISM`
in `@lagrangefoundry/knowledge`, once as the `overview` of the knowledge surface.
Whenever a host passes a `mechanism`, which is the documented usage, the first is
dead text that still reads as live doctrine. As product-level material it is
stated once, and the duplication has nowhere to live.

### Amendment 1 — generated state needs a named home

The three parts are the right **authored** categories, but three things in the
session are generated rather than authored, and none of them fits:

- `# What exists` — the landscape maps, which are what the corpus holds right now.
- The corpus delta ([[REQ-160]]).
- The draft-change signal ([[REQ-131]]).

The last two already ride in the reminder for exactly this reason, and `roles.ts`
flags it in its own comment: *"REQ-131 ADDED ONE THING THAT IS NOT A HABIT."*

**Decision: the landscape maps sit in (1) as what the KMS currently holds; the
per-turn deltas stay in (3) as a named exception**, because a per-turn channel is
the only place a per-turn signal can go. Naming it as an exception is the point —
otherwise (3) accretes every volatile thing that fits nowhere else, which is how
the current reminder acquired its third and fourth jobs.

### Amendment 2 — (1) is shared prose plus a per-grant projection

"What tools are available" cannot be one shared list. The manual is projected per
grant, and the required property is that **a session is never told about a
capability it was not granted**, so it cannot propose one, apologise for one, or
probe for one. A shared inventory breaks that.

So (1) is role-independent *prose* plus a tool summary still projected against
this session's actual grant. It is product-level because it describes the surface,
not the role — not because it is one string for everybody.

### The consequence to accept

This makes the system prompt product-level and moves role identity into the
priming. That is an inversion of what is there now: the role's own text — who it
is, how it speaks, what it must not do — would sit in a document the model reads
*after* the product text rather than in the highest-weight position. That is the
right trade, but it is a real change in emphasis and not a re-filing.

## 1. Adopt the summary manual

Measured on this repo's L1 surface with the consultant's grant:

| | manual | whole priming document |
|---|---|---|
| `full` (today) | 43,047 chars | 43,732 |
| `summary` (REQ-113) | 10,830 chars | 11,515 |

**74% of the priming document is reference material the model does not need to
choose with.** Everything that is not the manual — the purpose, all three
headings, the searchable-KB list, the closing trigger — is 685 characters.

The full reference is not lost: `DescribeTools` fetches the entry for any tool
before it is called. This is the trade REQ-113 was built for.

Work: deliver the upstream change to the shared store, then pass
`{ level: 'summary' }` at the three call sites — `host.ts`,
`session-knowledge.ts`, `system-knowledge.ts` — and grant the manual surface so
`DescribeTools` is reachable. A summary with no route to the detail moves the
failure rather than fixing it.

**Gap:** 2 of the 9 groups in `l1-surface.json` carry no `description`. Under the
full manual that is invisible, because the operations underneath carry their own
prose. Under a summary those groups render as a bare title. They need writing.

## 2. The role's purpose — short, with references

[[REQ-174]] reworded `CONSULTANT_PURPOSE` for the new role, but its **framing is
unchanged**: it still describes only the system corpus — *"you will need to know
how this system builds and describes sites"* — which was the whole truth when
there was one KB. [[REQ-158]] added the system KB; [[REQ-159]] added the client's
own corpus.

It becomes a short statement of what the consultant is here to do plus the
documents this role must read. That is the shape the section was built for: the
trigger immediately after it says *"pick the territories above that bear on your
purpose"*, and a purpose naming no territory gives that instruction nothing to
bite on.

## 3. The reminder — pointers, not text

[[DOC-33]] §7's rules of interaction — options rather than iterations, show rather
than ask, ask for facts not diagnoses, push back once then execute, never defer —
are **too big for the reminder**. They belong in the corpus, and the reminder
carries a pointer: *"don't forget the rules of interaction in [[DOC-33]]."*

The habit that most decays for this role is options-not-iterations: a model slides
into refining a single proposal without noticing, which is the templatey pull the
product exists to escape ([[DOC-33]] §7.1).

**The pointer resolves today**: [[DOC-33]] is in the shipped system KB, chunked
and indexed, so a reminder naming it reaches a document the consultant can fetch.

## 4. What survives from the old system prompt, and what does not

[[REQ-174]] rewrote the opening and the register. One line it carried forward is
still wrong:

*"They are not technical."* [[DOC-35]] §9.4's asymmetry rule replaces it: fluency
is loud, confusion is silent, so default to the careful register and let
demonstrated fluency escalate it — never de-escalate on silence. A flat assumption
is wrong for a substantial part of the known population ([[DOC-35]] §5.3) and
patronising in a way fluent people do not forgive ([[DOC-35]] §9.3).

Product-level and true for every role, so bound for (1): tools-only with no other
path, a malformed change refused whole, the typed element tree plus vetted
components, never naming framework concepts to the client, read before you write,
changes private until published.

**The playbook does not go in any of the three.** [[DOC-33]] §12 says so itself,
and it is [[REQ-126]]'s rule: what changes when the method changes belongs in the
corpus and is referenced, not restated.

## 5. The summary gap is the ledger gap

[[DOC-10]] §8 reserved the `chat` ticket body for an AI-maintained summary.
**Nothing writes it.** [[DOC-33]] §3.1 supersedes that framing: the body is the
**ledger** — what was decided, **why**, what was rejected, and whether it is open
or locked.

That is what makes a conversation *knowledge*:

- The knowledge component indexes `title` and `body` (`ticketText`). The
  transcript is a comment and is not indexed, so a chat ticket with an empty body
  contributes an essentially content-free vector to the project KB.
- Its title is whatever the archive minted — the session id. Below the enumerate
  floor, which is every new client, the awareness map lists that verbatim.
- [[DOC-38]] §6 and [[DOC-39]] §7 both rest on every project-KB entry having an
  AI-written title over an AI-written body.

Two things follow from choosing the ledger over a summary:

1. **It fixes retrieval structurally rather than by instruction.** A summary must
   be *told* to lead with the words someone would search by ([[DOC-38]] §6); a
   ledger names the client's business, positioning and palette because that is
   what it records.
2. **It answers the trigger question: at decision points, not on a clock.** A
   grown-by-N-characters threshold is right for indexing a transcript
   ([[DOC-39]] §4.2) and wrong for a ledger — an entry is written when a decision
   locks, which is an event the role already knows about. `append_body` has
   compare-and-set and retry ([[DOC-33]] §3.3), so a gate commit writes the delta,
   not the document.

The title follows: the consultant renames the chat ticket once it knows the
business, rather than the archive guessing at creation time.

## The corpus already carries the playbook

**[[DOC-33]] and [[DOC-35]] are in the shipped system KB.** Five doc tickets carry
`doc_kind: system_kb` — [[DOC-17]], [[DOC-31]], [[DOC-33]], [[DOC-35]] and
[[DOC-39]] — and `kb/system/` holds four of them beside the three generated
`REF-*` projections, chunked and indexed.

So the "reference it rather than restate it" decisions above are **buildable
now**. The purpose can name documents the consultant can actually retrieve, and
the reminder's pointer to the rules of interaction resolves against a real
corpus rather than a hoped-for one.

What is not settled is whether those documents read as system-KB documents in
[[DOC-39]] §3.5's sense — addressed to the AI as its reader, actionable inside a
conversation, carrying no rationale for our engineering choices. [[DOC-33]] §12
says the playbook belongs here; [[DOC-35]] still ends in open questions about
itself. Being retrievable is not the same as being written for the retriever, and
a reading list should not point the consultant at a document answering a
different question than the one it is asking. That is a read-through, not a
blocker.

## Acceptance

- The session's texts are organised as product level, role level and reminder,
  and each piece of material sits in exactly one of them — with the choice
  justified by what changes it.
- Product-level material is role-independent: standing up a second role requires
  restating none of it.
- The tool summary in (1) is projected against the session's grant, and a session
  is told about no capability it was not granted.
- Priming carries the summary manual, not the full reference, and `DescribeTools`
  is reachable so the detail is one call away.
- The role's purpose is short and names the documents this role must read.
- The reminder is a handful of lines, references the rules of interaction rather
  than restating them, and its per-turn signals are marked as the deliberate
  exception they are.
- A chat ticket carries a ledger in its body and a title that is not its session
  id, both written for retrieval.
- The ledger is maintained on a stated trigger, and the cost of that trigger is
  stated with it.

## Decisions

**Scope.** All of it lands on one branch under this ticket: the summary adoption,
the three-part restructure, and the ledger.

**Where product-level material lives.** A **role-independent constant in this
repo**, composed into each role's system prompt — not a new section in KM's
priming. A KM section would mean changing `assemblePriming` upstream in
`@lagrangefoundry/knowledge`, in both languages, byte-for-byte conformant, and
delivered through another install cycle; that is a large dependency to buy an
ordering we can already have locally. The product constant keeps the
highest-attention position, and the product-level *projection* — the tool summary
— stays where it already is, in the priming's mechanism section.

So the system prompt becomes **product prose + role prose**, concatenated, and the
priming's purpose section answers the different question KM actually asks: what
this role needs to *know*, and which documents to read. Role conduct and register
stay in the system prompt; the reading list is the purpose. Nothing is stated
twice.

**How the ledger is written.** A **narrow host operation**, not the general
ticketing surface. `TicketAppendBody` and `TicketUpdate` exist on
`@lagrangefoundry/ai-ticketing`, but that surface is not registered in this
session and should not be: a consultant granted a general ticket API can write any
ticket in the project, and the grant would have to be scoped by predicate to claw
that back. A purpose-built operation that writes *this session's own chat ticket*
is scoped by construction. It follows the existing `extraOps` pattern — the same
seam `add_asset` and `publish` already use for operations only the host's runtime
can implement.
