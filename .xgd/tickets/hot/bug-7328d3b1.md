## Symptom

On First-Draft-Test Dina's Diner 2 the route map (IMAGE-7,
`Dina-s-Diner-Route-Map.png`) is cropped so that **the top of "Davis" is cut off**,
along with the bottom of its "Easy stop off I-80" banner, at every width. The
operator: "the map is cropped a little sloppily."

## Cause

- The map node has `aspect: "inline"`, which the design defines as **3:2**,
  rendered `object-fit: cover; aspect-ratio: 3 / 2`. The asset is **1448×1086
  (4:3)**, so cover removes about 60 source pixels from the top and the bottom. The
  "Davis" wordmark starts about 4% from the top, so its top is lost.
- **No focal point was recorded** for this image or for any of the tenant's 11
  materials. REQ-448 said the describer records a focal point when a photo is
  added. Copied materials (REQ-450) never had one, and either the describer path
  doesn't record one or it wasn't run.
- **A map is not a photo.** Text-bearing images (maps, menus, flyers, diagrams,
  signs, logos) lose meaning when cropped at all. A photo can be cropped around a
  subject; a map can't.
- The craft checks only judge a crop when a focal point exists (REQ-449), so this
  crop went unjudged.

On the same page, at 375px the hours table splits each row onto two lines ("Every
day" / "6am–3pm"), and the find-us Call button sits right on the footer. No check
reported either.

## Fix

1. **The describer classifies images**: `photo` vs **`graphic`** (map, menu,
   flyer, diagram, sign, logo, anything whose text matters). For a photo it
   records a focal point. For a graphic it records "do not crop". It runs for new
   uploads and as a backfill for materials that have neither, including copied
   ones.
2. **The renderer never crops a graphic.** An image classified as a graphic is
   shown at its natural aspect (`contain`, or the box sized to the image). An
   `aspect` set on it is ignored, and the node is reported off-system. A photo
   with `aspect` crops around its focal point (`objectPosition` from the focal
   point, as REQ-447 intends).
3. **The checks cover it:**
   - a cropped graphic is reported;
   - a photo crop that cuts its focal point is reported (existing);
   - a photo with no focal point under a crop that removes more than a threshold
     share is reported;
   - a two-column table whose rows wrap so a label and its value split onto
     separate lines at a width is reported (REQ-457's "text fits its column");
   - a button closer than the block gap to the next section or the footer is
     reported.

## What changed (as built)

**A picture is a `photo` or a `graphic`.** The image describer is asked, in the
same vision call, to end with `Kind: photo` or `Kind: graphic`. A graphic is a
map, menu, flyer, poster, diagram, chart, sign, logo, screenshot, or anything
else whose text or edges carry its meaning. For a photo it then asks for
`Focal point: X% Y%`. Both closing lines are read off and removed from the
description (`pictureTraitsOf`), in either order. A graphic records no focal
point. The material ticket carries `image_kind` (`photo` | `graphic`) beside
`focal_point`, and the Library row and catalogue item expose it.

**Backfill for material that has neither, copied material included.**
`classifyImageMaterial(s)` looks once at an image material with no `image_kind`.
It writes only `image_kind`, plus `focal_point` for a photo that had none. The
title and body are never rewritten; they are the client's to correct. It runs:
- from `POST /api/library/backfill`, whose answer now includes `classified`;
- on `place_on_site`, for an item nothing has classified yet, so a picture is
  classified at the moment it matters.

**The L1 image node has a typed `graphic: true` declaration.** A graphic is
never cropped. The design pass gives it no default aspect and no `cover`. The
renderer, the one sink, emits no `aspect-ratio` for it and draws a `cover` or
`none` fit as `contain`, so it shows at its own shape whatever reached it. An
`aspect`, or a `cover`/`none` fit, typed on a graphic is reported off-system,
under a new census axis, `imagery`.

**The consultant is told how to place it.** `place_on_site` now returns
`graphic: true` for a graphic. For a photo it returns the `focal_point`, which
REQ-448 meant to return: the host's place result carried it, but the surface
handler dropped it, so the model never saw it. The surface's description and
`placement` shape say what to do with each: set `graphic: true` and no aspect,
or set the focal point as `objectPosition`.

**The checks cover it** (layout check, all counted as craft kinds):
- `crop` → `cropped_graphic`: a picture whose material is a graphic, drawn
  cropped by any amount. The host passes the site's graphic file names
  (`LayoutContext.graphics`) beside the focal points.
- `crop` → `cropped_unframed`: with a library behind the page, a picture with no
  focal point whose crop hides more than `unframedShare` (0.2). A 4:3 photo at
  3:2 (≈11%) is not reported; at 16:9 (25%) it is.
- `crop` → `cropped_subject`: unchanged.
- `table` → `split_label`: a two-column table whose rows stack at a width, so
  each label and its value sit on separate lines (Dina's hours at 375).
- new `button_room` → `button_at_edge`: a button nearer the next section or the
  footer than the design's block gap (`minPx` 16 without a design).

## Design decisions

- **The classification reaches the renderer as a node declaration**, the same
  pattern as `logo`, validated by construction. It is not a render input looked
  up from the Library, because every render path would then need the Library.
  The node gets it from the place result. The `cropped_graphic` check catches any
  placed graphic that lacks it, including pictures placed before this change,
  such as Dina's map.
- **Classified on placing, not during the first-draft copy.** Copying stays a
  byte-and-field copy (REQ-450). The look happens once, when the picture is
  placed, or in bulk through the backfill route.
- The operator's image-editor src swap (router copy-set path) is unchanged: it
  edits copy-form fields, not L1 node fields.

## Test plan (as run)

`tests/test_UAT_FC_BUG-282_graphics_are_never_cropped.test.ts` (real renderer and
real Chromium):
- A 4:3 map marked `graphic`, with `aspect: inline` and `cover` typed on it, and
  one with nothing typed: both show at 4:3 and not `cover`, and the red band
  across the top of the file is visible at 1280 and 375. A 4:3 photo under the
  same aspect takes 3:2 and `cover` at `30% 70%`, and its band is cropped away.
- `checkLayoutAt` reports `cropped_graphic` for an unmarked map whose material is
  a graphic, and `cropped_unframed` for a 4:3 photo at 16:9 with no focal point.
  Marked, or framed, neither is reported.
- A stacked two-column hours table reports `split_label` at phone, not desktop.
  A button with nothing between it and the footer part reports `button_at_edge`.
  An unstacked table, with a block gap below the button, reports neither.
- An `aspect` or `cover` on a graphic is off-system under `imagery`. An aspect on
  a photo is not.
- The new checks are registry entries with thresholds, and their kinds are craft.

`tests/test_UAT_FC_BUG-282_graphics_are_never_cropped.workers.test.ts` (real D1/R2
routes; the describer is the only double):
- An upload of a map is `graphic` with no focal point, and a photo is `photo` at
  30% 70%. Neither closing line stays in the body.
- `/api/library/backfill` classifies material described before the describer
  was asked, and leaves its title and body alone. A second run classifies nothing.
- `place_on_site` on unclassified material classifies it. A map returns
  `graphic: true` and no focal point; a photo returns its `focal_point`.

Regression run: the REQ-447, REQ-448, REQ-449 and REQ-457 UATs (node and workers;
