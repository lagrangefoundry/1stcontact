## Story

**As an** operator who writes and maintains this product's design documentation, **I want** to build the builder assistant's domain knowledge out of those documents — as a repeatable release artefact, with each document declaring for itself whether it is in — **so that** the assistant answers from what we actually wrote rather than from a second copy that drifted, and nothing reaches a client-facing agent until somebody has said it should.

## Description

The assistant already knows what it can *do*: the control surface generates its manual. It does not know what the system *is* — how storage works, what the L1 substrate is for, what a behavior module may and may not contain, why a colour is a palette reference. That knowledge exists, written down, reviewed and versioned in the ticket store as `doc` documents. This story is the pipeline that turns it into something an assistant can search.

Three artefacts, built in one order, by one command:

| Step | What it produces | Why it is not optional |
|---|---|---|
| **export** | the corpus — the documents themselves, as files | the retrieval identity is the filename, so this is what a citation resolves to |
| **index** | a vector index over whole documents, and one over passages | a whole design document is far too coarse a unit to hand back as an answer |
| **map** | a generated awareness map: territories, described, with validated ways in | what a cold agent is primed with instead of the documents |

A build that produced only the document index would leave the knowledge base technically present and practically useless, so the whole pipeline is one command and the order is fixed.

A fourth artefact is derived from those three rather than built alongside them: the same knowledge base **packed as an importable module**, so a runtime that has no filesystem can search it. It is emitted by the build that assembles the deployable application, out of whatever the knowledge-base build last left behind.

Every one of the ways this pipeline can go wrong has the same shape: **the corpus quietly ends up smaller than intended.** No error, no warning — an index that builds, works, and is missing documents, with the symptom surfacing much later and several artefacts downstream as *"the assistant doesn't seem to know about that"*. Membership, the corpus declaration, the listing and the status report are each written against that failure mode rather than against tidiness. Packing has the same shape and one addition: a knowledge base that was never built at all can ship silently, so its absence is said out loud at the moment somebody could still fix it.

**In scope**

- **Building it.** One command runs the whole pipeline and reports what it produced. A second form does the corpus alone — no model, no credentials — and still leaves a coherent tree, because it writes the declaration too. A third reports what is currently built. An unrecognised form is refused with usage and a failing exit.
- **Packing it for a runtime with no filesystem.** The built knowledge base is also carried as values a host with no disk can hold: both indexes and the corpus text, each document keeping **its own** last-changed stamp rather than a shared default — a corpus dated differently from the index it was built against does not error, it simply disagrees with the ranker about how recent everything is, and the ranker's input is exactly what that stamp is. The packing is written on **every** application build, whether or not a knowledge base exists, because the generated directory is not in version control and the consuming import is static: a module written only when there was something to write would fail to *resolve* on any checkout that had never built a knowledge base, turning a missing capability into a build that does not compile. The absent case is therefore an explicit *nothing* to branch on, which is what makes it degrade to no knowledge tools instead of to a boot failure.
- **And an absent knowledge base is loud.** Degrading gracefully and saying nothing are different things. A build that packed nothing says so in the operator's face, alongside the command that repairs it; a build that packed something reports how much, in the ordinary register, so the shouting keeps meaning something. An assistant shipped with no knowledge tools looks exactly like one that has them until it answers a question badly, weeks later, in front of a client.
- **Membership is a kind, per document, on the document.** A document is in the knowledge base when it carries the document kind that means *this document is the assistant's, not ours*. A kind rather than a boolean, because a boolean invites the sentence *"this architecture document is **also** a system document"* — and that sentence is the category error the documentation scheme exists to prevent. An architecture document is written for someone deciding how to build the product; a system-knowledge document is written for an AI advising a client. They are different documents with different readers, not one document wearing two labels, and a single-valued kind makes that exclusivity a property of the shape rather than of discipline. Everything else is out: a different kind, an absent kind, a near-miss spelling — and **the retired boolean that used to carry this is not honoured at all**, because admitting a document on the strength of a marker nobody maintains any more is exactly how something reaches a client-facing assistant that nobody meant to put there. **Inclusion and not exclusion, deliberately**: an exclusion list answers "what did we throw out", which nobody asks; inclusion answers "what does the assistant know", which is the question that matters, and one a reviewer can settle by reading a single document's frontmatter. It also **fails safe**: a document written tomorrow carries some other kind, or none, until somebody says otherwise. The opposite default would put every new document in front of a client-facing agent the moment it was saved.
- **Named exclusions, and the repair named with them.** Every document the export leaves out is reported **by name**, and the line says which field and which value would have admitted it. A bare count tells an operator that something is missing without telling them what, which is the version of the message that generates a support question — and a document silently absent from the corpus is indistinguishable from one that was never written, with the symptom appearing far from the cause. Naming the marker as well as the document turns the report from a loss into an instruction.
- **The listing is exhaustive, and truncation is refused.** The corpus is a batch read of every document, so the store is asked for *every* document rather than for a page of them — and the envelope that comes back is checked as well as asked for. A consumer that reads the first page and stops takes page one and calls it the corpus, with no error and no warning. If a truncated answer arrives anyway — an older toolchain on the path, an affordance that stops meaning what it means — that is a loud failure naming the affordance that should have prevented it, because a quietly shorter corpus is the precise thing this step exists to prevent.
- **A short corpus is visible, not inferred.** Asking what is built reports the corpus against the number of documents the store says should be in it. A count of files on its own cannot show truncation: 37 documents looks exactly as healthy as 38 unless something says what the number was supposed to be. Both sides are asked and printed together, a disagreement is named along with the command that repairs it, and a store that cannot be read is reported as *unknown* rather than as zero — zero is a real and alarming answer, and manufacturing it from an unrelated failure sends an operator to rebuild a corpus that was never broken.
- **Identity that survives a retitle.** A document is addressed by its human id, never by its title. The address is what a search hit cites and what the incremental build keys on, so a retitle must not silently re-embed the document and dangle every stored citation.
- **Withdrawal is deletion.** A document whose ticket is gone, or whose kind no longer says it belongs, is *removed* from the corpus rather than merely left unrefreshed. A stale file would stay searchable, and confidently wrong, forever.
- **Rebuilds are incremental and honest about it.** An unchanged document is not rewritten; an unchanged corpus is not re-embedded. This is load-bearing rather than tidy: the index keys incremental work on the file's own stamp, so rewriting every byte-identical file each build would re-embed the entire corpus, at cost, while telling the ranker every document had just changed.
- **The map is generated, always.** Clustered from the same vectors the reader searches, described in the corpus's own vocabulary, and validated by *the reader's own search* — a map whose doors were checked by a different query path would promise routes that do not exist for the agent that follows them. A territory with no validated way in is named rather than passed over. The map is kept out of the corpus it describes, or every rebuild would cluster the previous build's map and the knowledge base would slowly fill with descriptions of its own descriptions.
- **The declaration is the thing in force.** Description, weight and the membership predicate all come from the declaration. Editing it changes what the build produces; a build never overwrites it.
- **One embedding model on both sides.** The vectors the index is built from and the vectors a query is compared against come from the same model, so comparability holds by construction rather than by argument — the failure mode of two models is not an error but plausible-looking nonsense.

**Out of scope**

- **What a conversation does with the knowledge base** — the session's knowledge surface, its priming, and its behaviour when nothing is built — on either host, the operator's own origin or a deployed one reading the packed module. That extends the assistant's own story.
- **Curating the corpus.** Which documents to drop and which to generate is an editorial pass to be made when there is retrieval data to judge by. The answer to a large corpus remains passage search and a map, not a hand-picked subset.
- **Generating corpus members from live sources of truth.** This pipeline exports documents a human wrote and a human classified; a second producer that renders reference documents nobody maintains is a different capability sharing one directory.
- **Tenant knowledge bases, and the ticket store on D1.** The system knowledge base needs neither: it is not inside anyone's store, it takes the scope parameters and does not vary by them. A tenant's own knowledge base can never be packed into a build at all — it is written continuously and differs per tenant — so nothing about the packing above is a decision that has to hold twice.

## Technical Context

- **The corpus is derived, and the declaration is authored.** The built tree is not in version control — a fresh checkout has a declaration and nothing built. That is the point of it being a release artefact: it is reproduced by running the build, never edited in place. The packed module is derived twice over, and is not in version control for the same reason plus one more: it is hundreds of kilobytes of generated content that would be re-diffed on every rebuild, and a checked-in copy of a generator's output is a second definition site the repository's own scan fails on.
- **The packing belongs to the application build, not to the knowledge-base build.** The intent's first acceptance list put the emission on `1c kb build`; the same ticket's later revision moved it to `1c assets`, which is what shipped — a sibling of the other generated re-exports, written by the same pass, reading whatever the knowledge-base build last left behind. This is why the knowledge-base build's own report is unchanged and the packing has criteria of its own rather than a clause inside the pipeline's.
- **The vectors travel base64.** A JavaScript module cannot hold raw bytes, and a UTF-8 round trip would silently replace every invalid sequence — corrupting an index into one that still loads.
- **The knowledge base's name, its source and its corpus type are declared once, in a module that names no filesystem.** Both halves need the same three values and the query-side half cannot import anything that reaches a disk, so they cannot live where the rest of the build's knowledge-base code lives. The failure this prevents is silent by nature: a corpus indexed under one type and searched under another does not error, it returns nothing, and looks exactly like a knowledge base with nothing in it.
- **The application build became asynchronous when the knowledge base joined it**, and its bootstrap now waits for it. Before, the report was handed an unfinished result and the command reported success while writing nothing. That repair is outside this story's declared scope — it belongs to the build that owns the command — but it is what makes the report's figures mean anything, so it is recorded here rather than given a criterion of its own.
- **`landscape: authored` on disk is not a claim a human wrote the map.** It is the shipped-knowledge-base contract: a fixed artefact that ships, read and never refreshed on a cadence — exactly true of one the build wrote. The build flips to `derived` for its own duration. What makes the result authored is *where it is written*.
- **Divergence from the intent's letter, not its substance.** The intent named the declaration `knowledge_bases.yaml`; what shipped is JSON, so the library needs no parser injected. Same file, same role, same content.
- **Why the kind and not a field of our own.** The sub-classification on `doc` tickets already carries `architecture`, `security_policy` and the rest, so "what kind of document is this" is answered where it is already asked; the value set is closed and defined upstream, so a value arrives already validated. It also stays clear of the `kind` field the knowledge component owns for its own awareness reports.
- **One place the "name it, never count it" rule is not followed.** When *no* document carries the membership kind, the build is refused with a message that names the kind and reports how many documents carry another one as a count rather than a list. That is the one case where the list is the whole corpus and the operator's problem is the marker, not any particular document — but it is a deliberate exception to the rule the export otherwise holds to, and worth knowing before someone "fixes" one of the two.
- **Only the export step is this repository's.** Index, chunking, ranking, clustering and access-point validation compose the knowledge library's own exported functions, in the same order its own build script calls them, because that script is absent from the packed artifact. Reported upstream; when it is packed, this shrinks to a call. The packing composes the same library's readers and its own vector encoder rather than restating either.
- **The document store ignores frontmatter timestamps.** It takes both stamps from the file entry, so the exported timestamps are provenance for a human reader and the *file's* stamp is what the incremental build reads. This is why "an unchanged document is not rewritten" is a correctness property rather than an optimisation — and why the packed module has to carry those file stamps forward rather than let a bundled reader default them.
- **Structured fields are dropped rather than coerced.** The corpus format reads one level of fields, so a mapping value has no representation; rendering it as text would put a placeholder in the corpus that is not the value, does not fail, and is indistinguishable from data.
- **The describing model needs no credentials**; the embedding model does, and there is deliberately no local stand-in for it — a stand-in would make laptop vectors incomparable with production ones, which is precisely the failure the single-model rule exists to prevent.
- Related: the assistant's per-site conversation capability consumes this artefact — on the operator's own origin and, through the packed module, on a deployed host; the control surface's generated manual is the *other* half of what the assistant is primed with.

## Reconciliation Decisions

**2026-09-10 — reconciling the corpus-selection behaviour (BUNDLE-26 / REQ-164).**

- **Asking what is built is no longer a pure-filesystem question.** The intent asks for a count that *matches the tickets carrying the marker*; a files-on-disk count cannot show that on its own, so the report asks both sides and prints them next to each other. The cost is that the report now reaches the ticket store, and can therefore fail to reach it — which is why the third form of the corpus line exists. Formalised as an acceptance criterion rather than left as an implementation detail, because the three shapes the line takes (agreement, disagreement with a repair, unknown) are the whole value of the change.
- **Checking the returned envelope is formalised alongside asking for everything.** The intent's own implementation record calls the check beyond its stated scope; it is kept and given a criterion because asking for every document is a promise made by something else, and the failure when that promise is not kept is silent by nature. A criterion that only asserted the request would leave the class of failure reachable from a stale toolchain.
- **Unknown rather than zero is intent, not defensive coding.** An unreadable store is the only swallowed failure in the pipeline, and it is swallowed only for the report — the export and the build both still fail loudly on it. Stated as a criterion so that a later "simplification" to `0` has something to fail against.
- **The retired boolean is superseded, not deprecated.** Nothing accepts both markers; there is one membership rule rather than two. The prior criterion asserting a genuine-boolean opt-in is restated rather than kept alongside the new one.

**2026-09-10 — reconciling the packed knowledge base (BUNDLE-26 / REQ-158, the artefact half).**

- **The deferred question is answered, so the deferral is removed rather than restated.** This story declared "corpus residency for a deployed worker … is not forced yet". It is forced now, and by this pipeline's own outputs: the packing is a fourth artefact derived from the three above, not a second knowledge base. The scope bullet is therefore deleted rather than softened, and what a *conversation* then does with the packed module stays with the assistant's story, where the session's knowledge surface and priming already live.
- **Unconditional emission is a criterion, not an implementation detail.** The intent states it outright in its own answer to "generated, not committed": the module is written always, carrying an explicit nothing when no knowledge base has been built. It is given a criterion because the failure it prevents is not a behavioural one — an import that cannot resolve is a build that does not compile, which no runtime test would ever reach.
- **Carrying each document's own stamp is reconciliation's own decision.** The intent is silent on stamps. The implementation carries them because the bundled reader defaults every document to the epoch while the build's own reader takes each file's modification time, so a stamp-free packing would hand the runtime a corpus dated 1970 against an index built against one dated today — no error, two halves disagreeing about recency, and recency is the ranker's input. Formalised now (2026-09-10) rather than left as a comment, because nothing about the artefact looks wrong when it is missing.
- **The loud report is the operator-facing half of graceful degradation.** The intent asks only that an absent knowledge base degrade rather than fail; the implementation adds a line that shouts. Kept and given a criterion, because silence is precisely how a knowledge-less assistant ships unnoticed — the shout and the degradation answer different failures and neither substitutes for the other.
- **Where the emission lives was settled inside the intent, not against it.** The ticket's acceptance list says the knowledge-base build emits the modules; its later revision says the asset build writes them, always. The later passage governs, the code agrees with it, and the earlier line is read as superseded — so no code-issue is raised and the pipeline's own report keeps describing only what the pipeline produces.

## Dependencies

None. The build runs with no session, and its corpus-only form runs with no model and no credentials at all.
