## Story

**As an** operator who writes and maintains this product's design documentation, **I want** to build the builder assistant's domain knowledge out of those documents — as a repeatable release artefact, with each document deciding for itself whether it is in, and in a shape a runtime with no filesystem can carry — **so that** the assistant answers from what we actually wrote rather than from a second copy that drifted, and nothing reaches a client-facing agent until somebody has said it should.

## Description

The assistant already knows what it can *do*: the control surface generates its manual. It does not know what the system *is* — how storage works, what the L1 substrate is for, what a behavior module may and may not contain, why a colour is a palette reference. That knowledge exists, written down, reviewed and versioned in the ticket store as `doc` documents. This story is the pipeline that turns it into something an assistant can search.

Three artefacts, built in one order, by one command:

| Step | What it produces | Why it is not optional |
|---|---|---|
| **export** | the corpus — the documents themselves, as files | the retrieval identity is the filename, so this is what a citation resolves to |
| **index** | a vector index over whole documents, and one over passages | a whole design document is far too coarse a unit to hand back as an answer |
| **map** | a generated awareness map: territories, described, with validated ways in | what a cold agent is primed with instead of the documents |

A build that produced only the document index would leave the knowledge base technically present and practically useless, so the whole pipeline is one command and the order is fixed.

And then a fourth thing, produced by the asset build rather than by that command, because it is the same knowledge base packed to travel: **the whole of it as an importable module** — both indexes and the corpus text, as values. A knowledge base that only exists as a directory of files is a knowledge base only a machine with a disk can read, and the runtime that most needs it has none.

Every failure this story's export guards against has one shape: **the corpus quietly ends up smaller than it should be.** No error, no warning — an index that builds, works, and is missing documents, with the symptom surfacing much later and several artefacts downstream as *"the assistant doesn't seem to know about that"*. Membership, the query-time predicate and the ticket listing are each specified below against that failure rather than against convenience. The packed half has the same shape of failure and two more instances of it: a corpus dated differently from its own index, and a corpus indexed under one name and searched under another. Neither errors; both return an assistant that knows less than it should.

**In scope**

- **Building it.** One command runs the whole pipeline and reports what it produced. A second form does the corpus alone — no model, no credentials — and still leaves a coherent tree, because it writes the declaration too. A third reports what is currently built. An unrecognised form is refused with usage and a failing exit.
- **Membership is a kind, per document, on the document.** A document is in the knowledge base when its ticket carries the knowledge-base *kind* — a single-valued marker in the document's own classification, not a flag beside it. A kind rather than a boolean because a boolean invites *"this architecture document is **also** a system document"*, and that sentence is the category error the classification exists to prevent: an architecture document is written for someone deciding how to build the product, a knowledge-base document for an AI advising a client. Single-valued means that exclusivity holds by shape rather than by discipline. **Inclusion and not exclusion, deliberately**: an exclusion list answers "what did we throw out", which nobody asks; inclusion answers "what does the assistant know", which is the question that matters, and one a reviewer can settle by reading a single document's frontmatter. It also **fails safe**: a document written tomorrow carries some other kind, or none, until somebody says otherwise. The opposite default would put every new document in front of a client-facing agent the moment it was saved.
- **One membership rule, not two.** The boolean opt-in this pipeline used before is *retired*, not deprecated: a document still carrying it is not a member. Honouring both would put a document in front of a client-facing assistant on a marker nobody maintains any more, and would mean two answers to "is this document in".
- **The shipped corpus is unrestricted.** Once the export has written the corpus, the *directory is the boundary*: everything in it matched by construction when it was written. Re-applying the export's own selection as a query-time predicate is a build-time filter re-run as if it were a membership rule — it can only ever subtract, and the only thing it can subtract is a file whose frontmatter does not look the way the predicate expects, which then disappears from the knowledge base with no error. So the shipped knowledge base declares an empty corpus predicate, and a markdown file placed in the corpus directory is resolved whatever its frontmatter says.
- **The listing the export reads is exhaustive.** The export asks the ticket store for *every* matching document rather than a page of them, and checks the answer it gets back: a listing that arrives truncated anyway is refused by name and the build fails, because a quietly shorter corpus is the exact failure the export exists to prevent. Reading the first page and calling it the corpus is silent by nature — no error, no warning, just documents that stop being carried past the page boundary.
- **Named exclusions.** Every document the export leaves out is reported **by name**, and the report names the marker they lack. A bare count tells an operator that something is missing without telling them what, which is the version of the message that generates a support question — and a document silently absent from the corpus is indistinguishable from one that was never written, with the symptom appearing far from the cause.
- **A short corpus is visible, not inferred.** Asking what is built reports the corpus against the number of documents the ticket store says should be in it, so a truncated export is one line an operator reads rather than something they later deduce from an assistant's silence: 37 documents looks exactly as healthy as 38 unless something says what the number was supposed to be. When the store cannot be read at all, that side is reported as *unknown* — never as zero, which is a real and alarming answer that would send an operator to rebuild a corpus that was never broken.
- **Identity that survives a retitle.** A document is addressed by its human id, never by its title. The address is what a search hit cites and what the incremental build keys on, so a retitle must not silently re-embed the document and dangle every stored citation.
- **Withdrawal is deletion.** A document whose ticket is gone, or whose kind has changed, is *removed* from the corpus rather than merely left unrefreshed. A stale file would stay searchable, and confidently wrong, forever.
- **Rebuilds are incremental and honest about it.** An unchanged document is not rewritten; an unchanged corpus is not re-embedded. This is load-bearing rather than tidy: the index keys incremental work on the file's own stamp, so rewriting every byte-identical file each build would re-embed the entire corpus, at cost, while telling the ranker every document had just changed.
- **The map is generated, always.** Clustered from the same vectors the reader searches, described in the corpus's own vocabulary, and validated by *the reader's own search* — a map whose doors were checked by a different query path would promise routes that do not exist for the agent that follows them. A territory with no validated way in is named rather than passed over. The map is kept out of the corpus it describes, or every rebuild would cluster the previous build's map and the knowledge base would slowly fill with descriptions of its own descriptions.
- **The declaration is the thing in force.** Prompt, weight and the corpus predicate all come from the declaration, and the shipped knowledge base's predicate is deliberately empty. Editing the declaration changes what the build produces; a build never overwrites it — which is why the scaffold a fresh checkout gets and the declaration committed to this repository have to say the same thing, since nothing would report it if they drifted.
- **One embedding model on both sides.** The vectors the index is built from and the vectors a query is compared against come from the same model, so comparability holds by construction rather than by argument — the failure mode of two models is not an error but plausible-looking nonsense.
- **The built knowledge base is also a value.** The corpus and both indexes are emitted as an importable module, so a runtime with no filesystem holds the same knowledge base the disk does. Two things make it the same one rather than a lossy copy: the vector payload travels without a text round trip that would silently corrupt it into something that still loads, and **every document carries its own last-changed time** rather than one default applied to the whole corpus — that stamp is the ranker's own input, so a uniformly stamped corpus is a differently dated corpus from the index it was built against, disagreeing silently.
- **The module is written whether or not there is anything to put in it.** The generated tree is not in version control, so a module written only when a knowledge base existed would leave a static import unresolvable on any checkout that had never built one — turning a missing capability into a build that does not compile. An absent knowledge base is carried explicitly instead, and degrades to an assistant with no knowledge tools, never to a failure.
- **A knowledge base that did not get built is loud.** Degrading gracefully and saying nothing are different things. The build that would ship an assistant with no knowledge says so in its report, names what that costs and names the command that fixes it, at the moment an operator could still act — rather than in a log line nobody reads, with the symptom arriving weeks later in front of a client.
- **One declaration of what this knowledge base is.** Its name, the source its corpus resolves against and the document type its corpus selects are declared once and read by both the half that builds the corpus and the half that searches it. A corpus indexed under one type and searched under another returns nothing, which is indistinguishable from a corpus that was never built — so the two halves are made incapable of disagreeing rather than expected not to.

**Out of scope**

- **What a conversation does with the knowledge base** — the session's knowledge surface, its priming, and its behaviour when nothing is built. That extends the assistant's own story.
- **Curating the corpus.** Which documents to drop and which to generate is an editorial pass to be made when there is retrieval data to judge by. The answer to a large corpus remains passage search and a map, not a hand-picked subset.
- **Tenant knowledge bases, and the ticket store on D1.** The system knowledge base needs neither: it is not inside anyone's store, it takes the scope parameters and does not vary by them. The packing decision is about *this* knowledge base only and must not be generalised: a tenant's corpus is written continuously and differs per tenant, so it can never travel in a release artefact.
- **Documents that nobody authors.** Reference documents generated from a source of truth rather than exported from a ticket are a second corpus producer with its own story; this story owns the exported half and the pipeline that runs around it.

## Technical Context

- **The corpus is derived, and the declaration is authored.** The built tree is not in version control — a fresh checkout has a declaration and nothing built. That is the point of it being a release artefact: it is reproduced by running the build, never edited in place. The importable module is derived in the same sense and for a second reason as well: it is large, and a checked-in copy would be re-diffed in full on every rebuild.
- **`landscape: authored` on disk is not a claim a human wrote the map.** It is the shipped-knowledge-base contract: a fixed artefact that ships, read and never refreshed on a cadence — exactly true of one the build wrote. The build flips to `derived` for its own duration. What makes the result authored is *where it is written*.
- **Divergence from the intent's letter, not its substance.** The intent named the declaration `knowledge_bases.yaml`; what shipped is JSON, so the library needs no parser injected. Same file, same role, same content. Likewise the intent's acceptance says the *knowledge-base build* emits the bundle-importable modules; what shipped puts the reading of the built tree into values beside that build and the *writing* of the module in the asset build, which is where every other generated module the Worker imports is written. Same artefact, same guarantees, written by the pass that already owns that directory.
- **The membership marker is the document's `doc_kind`, not a field of this pipeline's own.** The sub-classification on `doc` tickets already exists and already carries the other document kinds, so "what kind of document is this" is answered where it is already asked; and it stays clear of the `kind` field the knowledge library owns for its own awareness reports. The marker lives on the ticket rather than as an id list in the declaration because it is a fact about the document and has to move with it — an id list drifts silently when a document is renamed or retired.
- **Asking what is built is no longer pure filesystem.** Reporting the corpus against what it *should* hold means asking the ticket store as well as the directory, so the status form shells out. This is the one place the exhaustive listing's failure is swallowed rather than raised: status is the command an operator runs to find out what state things are in, so it must survive a store it cannot reach and still report the half it can see. Export and build both still want that failure and get it.
- **One place the "name it, never count it" rule is not followed.** When *no* document carries the membership kind, the build is refused with a message that names the mechanism and reports how many documents were skipped as a count rather than a list. That is the one case where the list is the whole corpus and the operator's problem is the marker, not any particular document — but it is a deliberate exception to the rule the export otherwise holds to, and worth knowing before someone "fixes" one of the two.
- **Only the export step is this repository's.** Index, chunking, ranking, clustering and access-point validation compose the knowledge library's own exported functions, in the same order its own build script calls them, because that script is absent from the packed artifact. Reported upstream; when it is packed, this shrinks to a call. The same holds of the packed half: the corpus walk, the file list an index is made of and the byte encoder are all upstream's, so an index that grows another sidecar travels without anything here being told about it.
- **The size of the packed module tracks passage count, not text volume.** Measured rather than projected: the compressed module is around 2.75× the markdown it was built from, and roughly four fifths of that is vectors, which do not compress. The documents themselves are nearly free. Packing is the right call at this corpus size and buys a query path with no network on it; if the margin ever tightens, the passage index is what moves out through the same seam.
- **The document store ignores frontmatter timestamps.** It takes both stamps from the file entry, so the exported timestamps are provenance for a human reader and the *file's* stamp is what the incremental build reads. This is why "an unchanged document is not rewritten" is a correctness property rather than an optimisation, and it is the same stamp the packed module carries per document.
- **Structured fields are dropped rather than coerced.** The corpus format reads one level of fields, so a mapping value has no representation; rendering it as text would put a placeholder in the corpus that is not the value, does not fail, and is indistinguishable from data.
- **The describing model needs no credentials**; the embedding model does, and there is deliberately no local stand-in for it — a stand-in would make laptop vectors incomparable with production ones, which is precisely the failure the single-model rule exists to prevent.
- Related: the assistant's per-site conversation capability consumes this artefact; the control surface's generated manual is the *other* half of what the assistant is primed with.

## Reconciliation Decisions

*Recorded 2026-09-03, reconciling BUNDLE-23 / REQ-164 against `tools/generate/src/cli/kb.ts` and `tools/generate/src/cli/index.ts`.*

- **The three status renderings are binding, not incidental.** REQ-164's stated acceptance asks only that the status form "reports a document count that matches the number of tickets carrying the marker". The implementation distinguishes three cases and renders each differently — agreement, disagreement (warned, with the remedy named), and an unreadable store (reported as unknown). The intent is silent on the disagreement and unreadable cases as *separate* outcomes. Decision: formalise all three as acceptance, because the whole value of putting the two numbers on one line is that a *disagreement* is what an operator sees, and collapsing "cannot check" into either of the other two re-creates exactly the silent-shortfall failure the intent exists to close.
- **The retired boolean's non-membership is acceptance, not an implementation note.** The intent's "what landed" half states it, and the two previously-existing suites that pinned the boolean rule were updated to assert the opposite. Decision: state it as a criterion in its own right rather than as an absence, so a re-introduction of dual membership fails a test rather than passing unnoticed.
- **The scaffolded declaration and the committed declaration are both asserted.** The build never overwrites an existing declaration, so the two can drift apart with no error and nothing downstream would report it. Decision: the criterion covers both, not the shipped file alone.

*Recorded 2026-09-03, reconciling BUNDLE-23 / REQ-158 against `tools/generate/src/cli/kb.ts` (`kbBundle`), `tools/generate/src/cli/kb-model.ts`, `tools/generate/src/cli/assets.ts` and `tools/generate/bin/1c.mjs`.*

- **Per-document stamps in the packed module are acceptance.** REQ-158's acceptance asks only that the build "emits bundle-importable modules for the index and the documents"; it is silent on what a packed document carries besides its text. The implementation carries each document's own last-changed time because the default is a single fixed stamp for the whole corpus, which would hand the ranker a corpus dated differently from the index built against it — no error, no warning, just worse answers. Decision: formalise the per-document stamp as a criterion. It is the same silent-shortfall failure shape the rest of this story is specified against, and a default stamp would satisfy the intent's sentence exactly while being wrong.
- **One declaration of the knowledge base's name, source and corpus type is acceptance, not tidiness.** The intent's Q4 answer names the constant and says the knowledge base is "parsed, not paraphrased", but is silent on the two halves keeping their own copies of the three values. They cannot share the module that builds a corpus — it reaches a filesystem, and the searching half is held by an import-graph assertion to reaching none — so the values were extracted to a module carrying nothing else. Decision: state the shared declaration as a criterion, because the drift it prevents produces an empty result set and not an error, and an empty result set is exactly what an unbuilt knowledge base produces.
- **The asset command's report describing work that actually happened is folded into the build-report criterion rather than raised separately.** The command that writes the generated artefacts became asynchronous when the knowledge base joined it, and its caller was not waiting — so it printed a report of unnamed artefacts and exited successfully while writing nothing. The intent is silent on this; it is a defect the intent's own change exposed, inside the intent's declared footprint. Decision: rather than a criterion of its own, sharpen the existing "reports what it produced" criterion to say that a report describes work that has finished, so a successful exit over an empty report fails a test.
- **Where the module is written is a divergence recorded, not a contradiction.** The intent says `1c kb build` emits the modules; the code puts the emission in the asset build. The artefact, its contents and every guarantee about it are the intent's; only the pass that writes it differs, and it is the pass that owns the generated directory. Recorded in Technical Context; the criteria are written against the artefact rather than against which command produced it.

## Dependencies

None. The build runs with no session, and its corpus-only form runs with no model and no credentials at all.
