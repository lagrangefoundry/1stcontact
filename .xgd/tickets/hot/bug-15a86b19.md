## Symptom

`tools/repro-console/bin/boot.mjs` ends its non-`keepAlive` path with

```js
if (!keepAlive) {
  await server.close()
  process.exit(process.exitCode ?? 0)
}
```

`process.exit()` does not flush pending asynchronous writes to stdout. stdout is
asynchronous when it is a **pipe**, so everything past the OS pipe buffer
(65536 bytes on macOS) is discarded — with no error and exit code 0. When
stdout is a **file** it is synchronous and nothing is lost, which is what makes
this invisible to anyone who redirects.

`repro-rail` is the tool on that path (`bin/repro-rail.mjs` boots with
`keepAlive: false`), and `--json` prints its entire report through it:

```js
// tools/repro-console/src/rail.ts:801
console.log(args.json ? JSON.stringify(report, null, 2) : formatRailReport(report))
```

So any consumer that spawns `repro-rail --json` with `stdio: 'pipe'` — or any
human typing `repro-rail --json | jq …` — receives a prefix of the report once
it crosses 64 KiB, and the prefix is valid-looking JSON right up to the cut.

## Why this is a separate ticket from BUG-101

This is the same defect in a second launcher. BUG-101 fixed
`tools/generate/bin/1c.mjs`, where a 71 KB `page get … --json` document made the
truncation observable today; it deliberately left this one alone rather than
change it blind. Two things were not established there and are what this ticket
has to establish:

1. **Whether the rail's report crosses the threshold.** BUG-101 recorded it as
   "under 64 KiB today", which was an inference from the report's shape, not a
   measurement. It grows with the number of sites on the rail, so the question
   is not only "does it today" but "what does it take".
2. **Whether the rail terminates without the forced exit.** BUG-101's fix
   accepts a hang in place of a truncation because a hang is loud, and it could
   afford that trade because every `1c` command was measured exiting on its own.
   The rail spawns `1c`, `pnpm` and `vitest` children and could not be measured
   in the session that found this, so the same trade cannot simply be assumed
   here.

The two packages are also deliberately not sharing a bootstrap — `boot.mjs`'s
own header explains why reaching into `tools/generate` for one is the import
direction EPIC-12 §8.6 forbids. So this is a second fix by design, not a missed
call site.

## Root cause

Same as BUG-101: an explicit `process.exit()` with output still queued.

## What was measured

Both open questions were answered by measurement rather than inference, and the
answers are what chose the fix.

**(1) The report already crosses the threshold, and it does not need more
references to do it.** The size is dominated by the tests phase, which prints
one line per test file that is failing and was not on the recorded bar — so it
is bounded by the size of the *suite*, not by the number of sites on the rail.
Driven through the real `recordRail`/`runRail` against this repo's own list of
test files:

| failing test files | `JSON.stringify(report, null, 2)` bytes |
|---|---|
| 400 | 55,808 |
| 450 | 62,988 |
| 485 | 68,082 |
| 554 (the whole suite today) | **78,203** |

The crossover is around 466 files, and the suite has 554. The ordinary scenario
this rail exists for — a bar recorded green, then an engine change that breaks
the suite — therefore produces a report that the old launcher truncated.

The references phase is the slower axis and was measured separately: roughly
2.2 KB per reference when every one of its 18 metrics regresses (3 references =
6,904 bytes; 20 = 44,425; 40 = 88,565), so ~30 references would cross it on
that axis alone. A clean run of the references phase is ~275 bytes.

**(2) The rail terminates on its own.** With the forced exit removed and a real
`repro-rail record --only typecheck` run through the launcher — which spawns
`pnpm -r build` and `pnpm -r typecheck` as real children — the only live handle
after `await server.close()` resolves is a `ProcessWrap` belonging to an
already-closed child, and node ended the process in the same millisecond `main`
returned. `spawnCommand` resolves on the child's `close` event, which fires
after the process has exited and both its stdio streams have ended, so no child
handle outlives the run.

So the natural-exit variant is safe here, and the explicit-drain variant with
its retained `process.exit` is not needed.

## Fix

Same shape as BUG-101: set `process.exitCode` and let the process end once the
streams drain. `rail.ts`'s `main` already assigns `process.exitCode` and calls
`process.exit` nowhere, so the launcher is getting out of the way of a verdict
that is already set rather than dropping one.

Both exits in `boot.mjs` are converted, not just the success one. The catch arm
ended with `process.exit(1)` after printing the reason to stderr, which is
asynchronous when piped for the same reason stdout is; it now sets
`process.exitCode = 1`, closes the server and returns.

The `keepAlive: true` path (the console's own server) is untouched — it never
reaches the exit at all, and its server must stay open.

The trade is the one BUG-101 named and is recorded in the code: a forced exit
ends the process whatever is still open and this one does not, so a tool that
ever leaves a live handle after `server.close()` will hang here instead of
exiting fast. A hang names itself and is diagnosable from
`process.getActiveResourcesInfo()`; the behaviour it replaces was a truncated
report that claimed to have succeeded.

## Test plan

`tests/test_UAT_FC_BUG-105_rail_piped_stdout_not_truncated.test.ts` makes two
separate claims, because the fix rests on two facts and only one of them is
about the launcher.

**Claim 1 — the launcher.** Driven as a real subprocess, because the truncation
is a property of how a process ends relative to its own pending writes and does
not exist in-process. A document past one pipe buffer arrives byte-identical
through a pipe and through a file descriptor, still parses, the process ends on
its own (no signal, non-null status), and the exit status the entry module set
is still what the caller sees — asserted at 0, 1 **and 2**, because the rail
exits 2 for "nothing regressed but the run covered less than the whole rail" and
a change that collapsed the status to a boolean would silently turn a partial
pass into a pass. The failed-boot arm is asserted too: its message still reaches
stderr and its status is still 1. A floor assertion holds the document above
65536 bytes so the file cannot pass vacuously, and a source assertion holds
`boot.mjs` free of any executable `process.exit(` — with the check that
`repro-rail.mjs` really is still on the `keepAlive: false` path, since a rail
that had quietly moved to the other one would make every claim above true and
irrelevant.

**The fixture, and why the real rail is not it.** `boot` takes the entry module
as an argument, so `tests/fixtures/bug105/boot-fixture.mjs` boots the real
launcher — real Vite server, real `ssrLoadModule`, real exit — and points it at
`tests/fixtures/bug105/large-stdout-entry.ts`, which prints a document of the
size the test asks for. Producing that document from a real rail run would mean
a whole-suite vitest pass, two `pnpm -r` builds, a browser and reference bundles
that are gitignored and therefore absent from a fresh checkout: minutes of wall
clock, none of it the behaviour under test, and all of it skipped on exactly the
machines most likely to regress it. The fixture prints a padded JSON array
rather than one long string, so a truncated copy is a plausible-looking prefix
as the rail's own report is — a test that could only fail on unparseable garbage
would not be testing this bug.

**Claim 2 — the rail's report really can be that big**, so claim 1 is about this
tool and not a hypothetical one. A bar is recorded with the suite green and then
re-run with every one of this repo's real test files failing, both halves
through the real `recordRail`/`runRail` and a real baseline file written and read
back; the resulting `JSON.stringify(report, null, 2)` is asserted past 65536
bytes. Only the command seam is substituted — the same injected `CommandRunner`
the rail's production runner plugs into — because a whole-suite vitest run is
the one thing a test cannot have.

The whole file runs in under two seconds and needs no browser, no network and no
stored reference bundle.

Verified before the fix: the same fixture through the pre-fix launcher returns
exactly 65536 bytes; through the fixed one it returns the whole 70,076.
