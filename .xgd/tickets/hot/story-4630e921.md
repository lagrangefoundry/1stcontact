## Story
**As a** business owner working the Contacts tab, **I want** each contact to carry an append-only history of the things that happened to them (when they came in, each time we invited them, when they signed up, and later every message sent, delivered, bounced or received), **so that** I can see where a contact came from and how they reached where they are now. A rewritten field would lose that history.

## Description
REQ-195 adds an event spine. An event says *this happened, to this contact, at this time*. It is written once and never rewritten. Anything that changes is state and lives elsewhere. Provenance is the earliest event, so there is no `source` column. A contact with two entry facts keeps both.

**In scope**
- An append-only per-contact event record. Each event has a dotted, open-ended kind, separate *occurred* and *recorded* times, an optional reference to a detail record, and a detail bag.
- Rewrites are refused by the database itself. A correction is a new event that supersedes the old one.
- Each event belongs to the contact's own business. Writes and reads cannot cross the business barrier.
- Emitters for acts that exist today: a contact is created by an invite or by seeding a platform operator; each invite press; accepting the terms (sign-up, carrying the terms version).
- A scoped write path that later `email.*` kinds will use. The kinds are proven through that path with a message reference, but nothing sends mail yet.
- A History section in the Contacts detail pane.

**Out of scope**
- Retention/erasure policy for the log. DELETE stays reachable, and erasing a contact cascades to the contact's events.
- The mail sender (REQ-196) and the `email` ticket type (REQ-198).
- Deriving the pipeline stage from events. REQ-188 keeps stage as a stored value.
- `list.joined` and `consultation.booked` emitters. These capabilities do not exist yet.

## Technical Context
- The schema lives in REQ-190's single baseline migration. The table is `contact_events` with an opaque `evt_` key, not a `(contact_id, kind, occurred_at)` composite, so two identical presses in the same millisecond are both representable. It has no `status` column. An index on the timeline and an index on kind over time ("what bounced this week").
- The `contact_events_are_immutable` BEFORE UPDATE trigger enforces immutability. There is no DELETE trigger, so `ON DELETE CASCADE` from the contact still works (DOC-37 erasure).
- `business_id` is derived from the contact row on insert and never supplied by the caller. If a caller names a business and the contact is not in it, nothing is written and the response is the same "no such contact" refusal an unknown id gets, so it cannot be used as an existence oracle.
- The history goes out on the existing contact-detail payload, not a new endpoint. The timeline is capped at 100 events, newest first by occurred time with write order breaking ties. Provenance is a separate earliest-event query, so the cap cannot distort it.
- The kind vocabulary and on-screen labels are shared between browser and server. An unknown kind renders as its dotted string.
- Architecture policy #4 (D1 is the primary store) and #26 (attach account/site ids to customer records, maintain audit events) apply.
- Related stories: STORY-163 (Contacts read, story-0034d937) and STORY-146 (identity/invite, story-7b1025b8) cover present state. This story adds how a contact got there. REQ-198's delivery events (plan item 7) will write through this story's write path.
- Evidence: `tests/test_UAT_FC_REQ-195_contact_events.workers.test.ts`, `tests/test_UAT_FC_REQ-195_contact_history.test.ts`.

## Reconciliation Decisions
- **DELETE is allowed and UPDATE is refused** (decided at reconciliation, 2026-11-04). The original Acceptance section says an event is "never updated or deleted". The ticket's own later section, "What was built, 2026-09-06", narrows this explicitly: rewriting is forbidden, and DELETE stays reachable so that contact erasure cascades. That later section is the operator's refined intent, not a contradiction, so the AC asserts refusal of rewrites and erasure reaching the events. Formalized as AC-2258 (rewrite refused) and AC-2260 (erasure cascades). REQ-195's FC suites have no UAT for AC-2260 yet, so UAT coverage must add one.
- **Emitters beyond email** (decided at reconciliation, 2026-11-04). The original body said "no event emission beyond email". The build section records three emitters for acts that exist today (contact.created, contact.invited, member.signed_up), because otherwise provenance cannot be answered. These are formalized as AC-2265, AC-2266 and AC-2267, and a fresh invite emits two events.
- **History section presentation details** (decided at reconciliation, 2026-11-04). Intent delegates timeline appearance to REQ-189 and is silent on the details. The landed behaviour is formalized: the section appears even when empty and reads "Nothing recorded yet."; an Origin line comes from the earliest event; the recorded time is shown only when it differs from the occurred time; the section offers no controls. Formalized as AC-2270 through AC-2274.
- **Malformed detail bag** (decided at reconciliation, 2026-11-04). Intent is silent here. An event whose detail cannot be decoded is still listed, with an empty detail, rather than breaking the timeline. This is noted for context only. It is internal resilience, not an end-user AC.
