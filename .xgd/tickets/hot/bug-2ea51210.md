## Symptom

`DelegationRuntime`'s `account` hook — `mark`, `changes`, and REQ-188's `claims` and `settle` — is called synchronously. `_mark` returns `hook.mark(ctx)`, `_account` uses `hook.changes(ctx, from, to)` as a value, `_settle` uses `settle(ctx, check, from, to)` as a value. None is awaited.

A host whose record is asynchronous cannot use any of them. 1stcontact's record of a site comes from a store backed by D1 and R2, where every read is async. A hook returning a promise puts a promise on the result, which serialises to `{}` — worse than no field.

## Consequence

- 1stcontact supplies the BUG-71 account by **subclassing** `DelegationToolbox` and bracketing `delegate()` itself (`tools/generate/src/cli/ai/account-core.ts`, `accountingDelegationToolbox`), because the hook can't be used.
- REQ-188's host-settled checks are **unusable** by that host at all. `settle` needs the framework's own bracket (`from`/`to` come from `mark`), and a subclass cannot supply the framework's bracket. So every check still goes to the worker and is charged to the worker's budget — the exact cost REQ-188 was filed to remove. Found from 1stcontact EPIC-20.

## Required behaviour

1. `mark`, `changes` and `settle` are awaited. A synchronous hook passes through `await` unchanged, so no existing host changes behaviour.
2. `claims` may be awaited too; it is called before the brief, so an await costs nothing the worker sees.
3. A hook that rejects is treated exactly as one that throws today: the field is lost, never the delegation.
4. The cross-language conformance corpus for `reconcile` is untouched — this changes when hook values arrive, not what is computed from them.

## Test plan

UAT beside the BUG-71/REQ-188 tests: an async `mark`/`changes`/`settle` hook produces the same `account` and the same settled verdicts as its synchronous twin; a rejecting hook costs the field only.
