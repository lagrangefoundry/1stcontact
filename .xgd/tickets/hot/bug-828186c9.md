## Symptom (Ariel's AR Welding run, 2026-10-21 ~17:33 UTC)

On the turn started by the client's 17:32:41 message ("Here are some
testimonials" + DOC-1 attachment), when the consultant went to work:
1. The composer's ▶ Send turned into a red ■ Stop — although no talker was open.
2. No status widget appeared under the progress banner (BUG-244 placement): no
   "The consultant is …", no elapsed time, no Stop building. The consultant's
   working notes appeared only as italic lines in the chat. On the previous few
   turns the widget did appear at the top.

## What the session log shows (junction, seq ≥ 1250)

turn_start (user) → `get_library_item` → **13 text deltas** (the consultant
answered first, per BUG-240's answer-first rule) → `pin_notes` → `set_stage` ×2 →
`set_ask` → `progress` → `Delegate` (builder) → further `progress` frames and
heartbeats. **No talker round** in this turn.

The dev snapshot (deployed 2026-10-21 08:51) contains LF BUG-89's fix
(`stopOffered` = `talking` only in talk mode) and BUG-244's `statusContainer`.
So in talk mode the composer can offer Stop only while a talker reply
generates, and progress frames should draw the widget in the plan panel.

## Hypotheses to confirm (in order)

1. **Talk mode was off in the browser for this conversation.** `chat.js` sets
   `turnModes: { talk: true }` only when the session payload says the
   conversation has a talker. Without talk mode, BUG-89's old rule applies
   (Stop until the widget is shown). Check every path that (re)mounts the chat —
   reattach to a live turn, the view switch `show_client` made at 17:31:36, a
   business/page change — for the payload losing `talker`.
2. **The widget was drawn into a detached container.** This turn wrote to the
   plan (`pin_notes`, `set_stage` ×2, `set_ask`) before its first `progress`;
   if the plan panel's redraw replaces the element passed as `statusContainer`,
   the widget is shown into a node no longer in the page — and with talk mode
   off, Stop stays because the widget never became visible. The container must
   survive plan redraws (or be re-attached).
3. **A round that answers first and then goes to work** is handled differently
   from one that goes to work at once (the previous turns). Check that progress
   frames after text deltas in the same round still reach the widget.

## Required behaviour

- With a talker configured, the composer never shows Stop unless a talker reply
  is generating — whatever path mounted the chat and however the round began.
- Whenever the consultant is working (any `progress` frame), the status widget is
  visible under the progress banner with its note, elapsed time and Stop
  building — including after plan-panel redraws in the same turn and after a
  reload/reattach mid-build.

## Test plan
- jsdom: talker session; a round that streams text, writes to the plan (forcing a
  panel redraw), then emits `progress` → widget visible inside the plan panel,
  composer shows Send.
- jsdom: reattach to a live worker turn → talk mode on, widget visible, Send shown.
- The view switch from `show_client` does not drop talk mode.


## Update from the operator (2026-10-21, same turn)

- Typing while Stop shows still reaches a talker: the **server side** of talk mode works (the host routes the mid-round message to a talker).
- The status widget is gone entirely and **progress is rendered as chat text**.

That narrows it to hypothesis 1 (with 3 as the likely trigger): the browser is reading this turn's stream through a path that neither enables talk mode nor unwraps `progress` frames into the widget — progress arrives as text, the widget is never shown (`isShown()` false), and with talk mode off the composer falls back to Stop-until-the-widget-shows. Hypothesis 2 (detached container) alone would not put progress into the chat. Look first at how the client consumes a round that **began as an ordinary reply** (answer-first) and then emitted `progress`, and at any reattach/remount path (`tailSession`, the 17:31:36 `show_client` view switch), for a branch that skips the `progress` unwrapping and the talk-mode `turnModes`.


- Later in the same turn: the composer's red ■ is shown **permanently** — the greyed-out (idle) Send state never returns between messages. The operator is reloading to see whether a fresh mount restores talk mode and the widget.


- After a reload the composer and the status widget behaved normally again (operator, 2026-10-21). So the fault is in the live chat's state for the turn that started as an answer-first reply, not in the server or the session payload at load.
