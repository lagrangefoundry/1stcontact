## Story
**As a** client working with the consultant on my site, **I want** the assistant to be able to look at a picture of my draft, the page I am editing, a published revision, a captured reference, any web page, or a picture in the store (one it generated, one I uploaded, a drawing it made) — and actually see it, including a state of my draft that a visitor only reaches by clicking or typing — **so that** its judgements about how the site and its pictures look rest on what is there rather than on guesswork or a description.

## Description
Before REQ-157 the assistant's whole tool surface was site-editing operations; nothing it could call returned an image. This story gives it a **second, read-only declared surface** ("Looking and judging", group `SeeSite`) composed beside the site-editing surface rather than merged into it, and the part of it that lets the assistant *see*:

- **One picture vocabulary.** Every operation names a picture the same way: a `kind` of `reference` (captured bundle), `draft`, `edit`, `revision` (published, frozen), `url` or `image` (a stored picture, REQ-218), plus the fields that kind needs, a viewport (`mobile` / `tablet` / `desktop`, default `desktop`) for the five kinds that are a page, for `draft` only `after` (REQ-216), and for `image` only `image` and `original` (REQ-218). The offered tool schema shows the model that exact shape.
- **`screenshot`** returns a short text line naming what was shot and at what size, and the picture itself as an image content block the model receives inside the same tool loop — on both hosts, with the call still validated, gated and audited by the Toolbox (REQ-206).
- **Driving the draft before the shot (REQ-216).** A `draft` picture may carry `after`: an ordered list of short phrases in exactly two forms — `click "Sign in"` and `fill "Email" with "someone@example.com"` — carried out on the live draft page before the shutter opens, so a modal, a carousel's later slide, a disclosure or a form's success state can be looked at. Controls are named as a person names them and matched against the page's own accessible names; no selector can be named. Every step that cannot be done — no such control, several, not visible yet, a click that changed nothing, a field that did not take the value, a page that never settled — is an `INTERACTION_FAILED` refusal naming what failed, and **no picture is returned**. The other kinds refuse `after`, each for its own stated reason, before a browser is leased.
- **A picture says which channel it is of (REQ-216).** An `edit` picture carries a caption, on the same text block that names the picture, saying the channel ships no behaviour and that a `draft` picture shows what a visitor gets; `compare` reports the same caveat when either side came from the edit channel.
- **A stored picture is a sixth kind (REQ-218).** An `image` picture names a picture in either store by any name it goes under: a site asset's filename, its `/assets/…` handle, or the bare stem a drawing was written under; a Library item's record id, its Library title, or its upload filename. One rule decides across both stores (exact spelling first, then case- and surrounding-whitespace-insensitive), and fonts are not pictures. A name meaning several pictures is refused listing each one's exact name; a name meaning none is refused pointing at the handle returned when the picture was made, its Library name, and `list_assets`. There is no Library listing operation. A stored PNG comes back as stored; anything else is put in front of the browser and comes back as a PNG of itself, so the reduction, `compare` and the reported size all work for a photograph. The browser is opened on a fixed, constant-length shell page and the picture's bytes are handed to it directly in bounded pieces (the browser fetches nothing, and nothing about the picture's size reaches the address it is navigated to), so an ordinary multi-megabyte camera JPEG is photographed (BUG-80). A format the browser will not decode is refused naming its stored type rather than returned blank. A drawing (SVG) carries a caption that it was photographed outside the site's own page in the browser's default face and that `measure_drawing` reads its geometry. `original: true` is accepted and the label says "as originally stored"; until an edit recipe exists it is the same picture. `viewport` does not apply. A stored picture cannot be driven.
- **A stored picture that cannot be shown says so in a sentence, never in a payload (BUG-80).** Any browser failure while a stored picture is being put in front of the browser comes back as a short refusal naming the picture and the browser's own diagnosis, with any `data:` address and any long base64 run removed and the whole held under a fixed character cap — so no failure on this path can hand the model a tool result large enough to end the conversation. A stored picture above an absurd size ceiling (far above any real photograph) is refused by size before a browser is leased. The stored media type is cleaned to a plain media-type token before it is written into the page.
- **Bounded pictures.** Images are reduced (by averaging, not sampling) to a 1024px longest edge and refused over a byte ceiling; the operator's live activity stream carries the text but not the image bytes.
- **A published revision is pictured as it was** — rendered from the frozen snapshot with that revision's own asset bytes.
- **Bound to one site**, read-only, granted to the consultant.
- **Mounted on the builder's Worker for the request's business (REQ-206).** References are stored in, and finished captures adopted from, that business's own private bucket; pictures of our own channels come from the `/preview/*` renderer at the deployment's own origin. The Worker's stored pictures are the site's assets and the business's Library (REQ-218). No HTTP route is added — the surface is reachable only inside an admitted, business-scoped turn.
- **Browser spend is budgeted (REQ-206).** On the Worker a session may make forty live-page browser acquisitions; reading something already captured or rendered spends nothing; the forty-first is refused as one readable refusal while every other tool keeps working.
- **Absent, not broken**, where the deployment has no browser: the session opens and edits with no looking operations. A Worker with no private bucket opens no chat at all, because the transcript store needs it (REQ-160). The looking surface's own private-bucket check is defence in depth (see Reconciliation Decisions). The local `1c` host answers `image` for the site's own assets only, because it holds no Library (REQ-218); a deployment wired with no image store at all refuses every `image` picture as `ENVIRONMENT`.

**In scope:** surface composition and grant, Worker mounting per business, picture vocabulary and resolution of all six kinds, driving a `draft` picture with `after` and its refusals (REQ-216), the edit-channel caption on pictures and comparisons (REQ-216), the stored-image kind: naming across both stores, ambiguity and not-found refusals, PNG pass-through and browser rasterisation, the drawing caption, `original`, the per-host image store, and the `.gif`/`.avif` content types (REQ-218), delivery of a stored picture's bytes to the browser without a URL-length ceiling, the bounded refusal on any browser failure while rasterising it, the sanity size ceiling and media-type sanitising (BUG-80), `screenshot`, image bounding and content-block recovery through the Toolbox, the Worker's browser budget, SSE stripping, read-only guarantee, both hosts.
**Out of scope (sibling stories in this bundle):** `compare` / `check_fidelity` verdicts (plan item 5, story-47fb84e6) — this story covers only that a driven `draft` is read in the same driven state by `check_fidelity`'s value gates, that `compare` carries the edit caveat, and that `check_fidelity`'s value gates refuse an `image` picture; that `compare` accepts an `image` on either side is story-47fb84e6's; `capture_site`, `list_references`, `describe_reference` operation semantics and the egress guard (plan item 6) — this story covers only where their captures are stored and adopted on the Worker. Also out of scope: driving the edit channel or carrying page state across a channel switch (REQ-215); a third interaction verb or any selector-based naming (REQ-216 "Deliberately not in scope"); a Library listing operation (`list_images`, retracted in REQ-218); edit recipes and the renderer that makes `original` differ (REQ-219). Named by REQ-157 itself: redacting the capped base64 from the durable session transcript (upstream follow-up), attaching ingestion descriptions to assets, prompting a backdrop-or-subject question. Named by BUG-80 itself: a general cap on every tool result's text regardless of operation (belongs in `lagrange-framework`'s Toolbox runtime, another repository); a resize/"smaller copy" verb (deliberately not added); moving a Library picture onto the site (REQ-227); repairing the poisoned session's `backend_ref` (data repair, no code).

Names are whitespace-collapsed and case-folded; an exact match wins, otherwise a substring match. Visible controls are considered first; only when none matches are hidden ones checked, to say "not visible".

- **Stored-picture delivery and the failure bound (BUG-80, commit 3f1480ce).** All in `tools/generate/src/cli/capture/screenshot.ts` `rasterizeImage`:
  - Before: a `data:text/html;base64,…` wrapper document carried the picture's base64 inside a document that was itself base64'd (≈ (4/3)² the picture's size) and was passed to `driver.navigate` with no `try`. Chromium refuses URLs over 2 MiB (`net::ERR_ABORTED`), so any non-PNG over ≈1.1 MB could not be photographed, and Playwright's `"<code> at <url>"` message put the whole URL (22.6 MB in `chat-d73a11e1`) into the tool result, ending the conversation.
  - Now: `driver.navigate(shellUrl())` opens a fixed `SHELL_DOCUMENT` (`<img id="stored">` plus the `MAX_RASTER_EDGE` stylesheet), a few hundred bytes and independent of the picture. The base64 is pushed through `driver.query(chunkScript(…))` in `INJECT_CHUNK_CHARS = 512 KiB` pieces into `window.__pic`, then `decodeScript(mediaType)` joins them, sets `src = 'data:<safeMediaType>;base64,…'`, clears the buffer and awaits `img.decode()`.
  - `navigate`, every chunk `query` and the decode `query` sit in one `try`; anything thrown is rethrown as `ImageNotRenderableError("'<name>' could not be put in front of the browser: <safeDriverMessage(err)>. There is no picture to show you; say so and work from what the Library says about it instead.")`. `safeDriverMessage` replaces `data:` URLs with `data:…`, any base64-alphabet run of ≥120 chars with `…`, collapses whitespace, and truncates to `MAX_DRIVER_ERROR_CHARS = 400` with a trailing `…`.
  - `MAX_STORED_PICTURE_BYTES = 64 MiB` is checked before `factory()`, so the refusal (`'<name>' is <N> MB, which is past the <M> MB most this can put in front of a browser …`) leases no browser and spends no budget.
  - `safeMediaType` accepts only a `type/subtype` token (`[A-Za-z0-9!#$&^_.+-]`); anything else becomes `application/octet-stream`, which the browser will not decode, giving the existing named decode refusal.
  - The decode-failure wording is unchanged from REQ-218.
- **The untrusted-content frame is kept on the picture path (REQ-157; fixes BUG-316).**
  - `host-core.ts` (shared by the Worker host and the `1c` CLI) registers every tool as `box.run`. The Toolbox renders each result as text and wraps every `provenance: untrusted` result (every operation on this surface) in `<<<untrusted>>>` … `<<</untrusted>>>`.
  - `contentBlocksFrom` (`fidelity-core.ts`) recovers a picture's blocks from that text so that the model is shown the image, and `host-core.ts` hands them to the model as `contentBlocksFrom(payload) ?? payload`. This is the REQ-206 "picture was being described, not shown" fix, applied once in the shared host core so both hosts get it.
  - The text around the recovered array is carried onto the blocks: the text before the array prefixes the first text block (or becomes a new leading text block when the first block is an image), and the text after it suffixes the last text block (or becomes a new trailing text block). The image itself lies strictly inside the frame (AC-2067). Unframed payloads come back unchanged; refusals come back as `null` and stay text.
  - History: the frame was dropped by the batch-0 code_frozen grant report-be7d1be4 (13aa65737c); an ungranted fixer edit (0a0f97f216) restoring it was reverted (review report-84f2f9bc F1); review report-b5be9c7c F1 directed restoring it under a new rung-1 code_frozen grant (REQ-157, Grant and safety) scoped to `tools/generate/src/cli/ai/fidelity-core.ts` only. That grant landed as report-d58b23f8 (trust-boundary audit fields computed, conformance pass), and the AC-2067 UATs now pass against it.

## Reconciliation Decisions
- **Picture defaults** (decided at reconciliation, 2026-10-27): REQ-157 names each kind's required fields but not defaults; the declaration defaults `viewport` to `desktop` and `page` to `/`. Formalized in the resolution AC because the model is told these defaults and relies on them.
- **No slug anywhere** (decided at reconciliation, 2026-10-27): the original table names draft/edit/revision "by slug + page"; REQ-157's own "Behaviour the build settled" supersedes that — the surface is bound to one site at construction and no picture names a site. Formalized as the binding AC; this follows the later intent passage, not a code deviation.
- **Byte ceiling value** (decided at reconciliation, 2026-10-27): intent says "a declared byte ceiling" without a number; code uses 3 MiB after reduction and names both size and ceiling in the refusal. Formalized at that value since the refusal text tells the model what to do instead.
- **SSE elision form** (decided at reconciliation, 2026-10-27): intent says image data is stripped while the text survives; code replaces the image data with a marker naming its byte count and media type. Formalized: text block intact, no base64 in the streamed event.
