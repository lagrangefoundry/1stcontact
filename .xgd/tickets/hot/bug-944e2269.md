## Symptom

Open the builder, select a site, look at the Site tab's chat panel.

- The composer shows the **STOP** button, with no turn having been invoked.
- Typing a message and pressing Enter renders the user's bubble and then
  nothing happens — no reply, no tool activity, no error.

The message is not merely slow — it never goes at all. Reloading lands in the
same state. See "Two things implementation established" below.

## Root cause

`storedTranscript` in `tools/generate/src/cli/ai/host-core.ts` computes the
`live` flag — "a turn is open at this cursor, so the panel should reattach" —
as:

    deps.lib.closedPrefix(records).length !== records.length

`closedPrefix` returns a **number** (the count of leading records that leave no
turn open), not an array. `.length` on a number is `undefined`, and
`undefined !== records.length` is true for every non-empty record stream. So
**`live` is true for every session, always**, whether or not a turn is running.

The library is loaded untyped (`AiLibrary`), so the type system had nothing to
say about it. The flag was introduced by BUG-46 and its UATs only ever exercise
the case where a turn genuinely *is* open — where the wrong answer happens to be
the right one — so the defect shipped green.

What the operator then sees follows mechanically from that one value:

- `chat.js`'s `setSession` reads `live === true` and calls `chat.resume(...)`,
  which puts the composer into its streaming state — hence the STOP button on a
  panel nobody has spoken to.
- `mountChat`'s submit handler is `streaming ? queue(md) : send(md)`, so the
  typed message is **queued behind the phantom turn** rather than sent. The
  bubble is the queue rendering, not a request.
- `/api/ai/reattach` tails a quiet junction, which yields nothing and returns
  only when `watch`'s own `timeoutMs` (10 minutes) elapses. The composer is
  gated for that whole window.

## Fix

Delete the second read and take `live` from the value `manager.transcript()`
already returns.

Upstream computes exactly this predicate itself
(`manager.js`: `live: closedPrefix(records) < records.length`) and documents it
for precisely this failure — "a reload landing *between* turns would gate its
composer for ten minutes". `storedTranscript` was re-deriving, from a second
read of the same log, a fact the call it had just made had already answered —
and got it wrong. Consuming the library's answer removes the divergence rather
than repairing one side of it, and removes `logFor`/`closedPrefix` from this
module's surface entirely.

## Two things implementation established that the scoping above did not

**The message is dropped, not delayed.** `queue` renders the text as a pending
user turn and hands it to the host's `onQueue` callback; the widget does not
drain it itself. `chat.js` supplies no `onQueue` — the builder has no
session-level queue to issue one to — so `mountChat`'s no-op default takes it.
The text is accepted and then goes nowhere, permanently. Waiting out the
ten-minute tail would not have recovered it. The ten minutes is how long the
composer stays gated, not how long the message waits, and that is why the
symptom reads as silence rather than as slowness.

**A brand-new site was never affected**, which is what makes the report hard to
place. A site nobody has talked to has no junction and no archive entry, so
`storedTranscript` returns null and `live` takes its `?? false` default — the
broken derivation is never reached. The operator therefore meets this on the
SECOND page load and every one after it, on any conversation holding a single
turn, which is why it presents as "the builder is like this" rather than as
something a particular action caused.

Neither changes the fix. Both are asserted, because both are the difference
between a description of this bug that predicts what an operator sees and one
that does not.

## Test plan

Two suites, split the way BUG-46's are: the origin's answer, and what the panel
does with it.

`tests/test_UAT_FC_BUG-64_quiet_session_is_not_live.workers.test.ts` — the
workerd project, against the real session manager, junction and D1 store with
only the Anthropic client doubled.

- A session whose only turn has completed reports `live: false` from
  `POST /api/ai/session`, with its history intact — so the assertion is about the
  flag and not about an empty log.
- A session read *during* a paced turn still reports `live: true`, and hands back
  the cursor that makes the flag actionable. A fix that is "always false" repairs
  this ticket and silently undoes BUG-46; both constants are excluded.
- One session, watched across a whole turn, reports false → true → false. Only a
  value that CHANGES is an answer rather than a constant.
- A freshly opened session reports `live: false`. This one passes on the unfixed
  code and is pinned as the boundary that explains the report — see above.

`tests/test_UAT_FC_BUG-64_panel_is_not_gated_between_turns.test.ts` — jsdom,
mounted against the actually-installed `webui-chat`, since the queue-versus-send
decision is the component's and a mocked panel would assert nothing about it.

- A panel handed a settled conversation is not wearing `is-streaming` — the class
  that hides Send and reveals the live controls, i.e. the STOP button as reported.
- A message typed into that panel reaches `streamPrompt` and is answered. The
  bubble was never evidence of a request, so what distinguishes send from queue is
  whether the transport was asked.
- A genuinely live turn still gates the composer, and what is typed is queued and
  then dropped — asserted so the gate is not "fixed" along with the flag, and so
  the dropped-message finding is written down where it happens.

BUG-46's own suites (both halves), BUG-38's, REQ-122's and the assistant-pane
reconciliation suite all still pass unchanged.
