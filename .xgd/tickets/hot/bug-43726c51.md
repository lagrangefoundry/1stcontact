## Symptom

Dev, 2026-11-05. Opening the builder for a site that has a draft (built and revised many times) consistently lands on the **Input** pane, not **View**. It isn't "where the operator last left it": it happens every time, whichever pane was last used.

## What should happen (already specified)

REQ-442 (`apps/control-app/src/builder/app.js`, `storyFirst`): "ONCE THERE IS A DRAFT, THE PREVIEW OPENS IN VIEW, whatever mode the client last left it in". Only a link followed before the first view is read (`#show=…`, REQ-626's `?show=` in the URL) may decide otherwise. REQ-408's "before the first draft, open in Input" applies only while `drafted` is false.

## What we know

- **The data says "drafted".** `drafted` is `Boolean(fields.milestones?.first_pass_at)` (`tools/generate/src/cli/ai/plan-core.ts`), and this site's plan has `first_pass_at: 2026-11-03T22:45:03Z`. So `storyFirst` should choose View on the first view it reads.
- **So something else moves the pane to Input on load, or runs before `storyFirst` and is then treated as the client's own choice.** Candidates to check, in order:
  1. an `openInput(...)` call on load: a `#show=…` link in the replayed chat being followed, the help panel ("How you can help") or open asks/questions;
  2. `pendingView` being set from the page URL without a `show` the operator gave;
  3. `storyFirst` deciding before `currentSite` is set, so the once-per-site decision is skipped, then an Input default stands;
  4. the panel's remembered mode being applied after `storyFirst`'s choice.
- Not yet reproduced in a test.

## Fix

- When a site with a draft is opened with no `show` in its URL, the builder lands on **View**, every time, regardless of the last-used pane, open questions or the chat's last links. A `show` the client or an email link gave still wins.
- Before the first draft, Input still opens first (REQ-408), unchanged.
- Find the overriding path and remove it. Don't add a second "open in View" rule.

## Test plan

`test_UAT_FC_<ID>_*` (builder app, jsdom):
- A site whose plan has `first_pass_at`, last left on Input, with open questions, and a chat whose last consultant message contains a `#show=questions` link: on load the pane is View.
- The same with `?show=questions` in the page URL: the pane is Input (questions).
- A site with no `first_pass_at`: the pane is Input.

## Cause found (2026-11-05, second session)

The pane is being moved by REQ-408's "before the first draft, open in Input" rule, working as written, on wrong data:

- The operator's builder opens business `1st Contact`, site `site_62d3…` (from `localStorage`: `site:panel:site`). There is **no remembered `mode` key** in storage, which is exactly what `storyFirst`'s `setMode(INPUT_MODE, { remember: false })` leaves. It also explains why no `POST /api/plan/seen` was ever sent: that call is skipped for `chosen: false`. The brief View the operator saw on reload is the panel's default before the plan loads.
- That site's plan (`plan-1b8d65f8`, last updated 2026-10-02, phase `intake`) has **no `milestones` at all**, so `panelView` returns `drafted: false`, even though the site is at version 60 with a page. The site was built before milestones were first stamped (3b3a4e5e2d, 2026-10-03), and nothing ever backfilled `first_pass_at`.
- My earlier investigation looked at a different site, which does have `first_pass_at`.
- The local dev store has 10 plans with no `first_pass_at`. Five of them belong to sites edited past their starter (versions 60, 37, 426, 38, 9), and those five all open on Input in the same way.

So the bug is in the `drafted` signal, not in the pane logic: a site that has a draft to look at can still report `drafted: false`.


## Fix (agreed with the operator, 2026-11-05) — supersedes "Fix" above

The operator's direction: don't signal this on the "first draft" milestone, which can change arbitrarily. Look at the draft site: if there is anything there to look at, show it. That's all.

- **`drafted` in the plan view (`GET /api/plan` and every plan write that answers with the view) means "the draft holds something to look at".** It is false only while the site still holds nothing but the untouched starter page, the grey "Your site will appear here as it's created." placeholder. This is the existing `nothingBuilt` check (BUG-215), the same one that refuses a publish. It is no longer read from `milestones.first_pass_at`. The milestone stays as a record for its other readers (the critic, the consultant cadence), but it no longer decides what the builder opens on.
- So a site that was built before milestones existed, or edited without one being stamped, opens on **View**. A brand-new site that still holds only the starter page opens on **Input**, as before (REQ-408). When the first real section lands, `drafted` turns true and REQ-444 moves the pane to View.
- The builder's pane logic (`storyFirst`, `draftLanded`) is unchanged. It was right; its input was wrong.

## What landed

- `tools/generate/src/cli/ai/plan-core.ts`: `panelView(fields, drafted = false)` no longer reads `drafted` from `milestones.first_pass_at`. It is an input, because it is a fact about the draft, not the plan.
- `apps/control-app/src/router.ts` (`panelWithMaterial`, behind `GET /api/plan` and every plan write that answers with the view): `drafted = !nothingBuilt(store, site)`.
- **Superseded explicitly:** REQ-408's `test_UAT_FC_REQ-408_a_new_site_has_not_been_drafted_and_the_first_builder_session_drafts_it`, which pinned `drafted` to the builder session's milestone, is removed. Its replacement is the BUG-354 UATs above: a site that holds only the starter page is not drafted, and a built site is drafted whatever its milestones say. REQ-408's wire test now seeds the grey starter page that provisioning really writes.
- **Known cost:** a plan read now also reads the site's pages, once per request. This is the same read a publish makes.
