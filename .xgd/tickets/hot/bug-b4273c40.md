## What the consultant reported, verbatim

> Understood — links, not captures. And that's the bug: **`capture_site` reported success both times, then every screenshot of the result came back as a black rectangle reading "refused by egress policy."** So the capture stored bytes it can't render, and the failure surfaced only after it had spent two of my forty page-loads. Worth filing — it burns budget to produce something unviewable.

Three sites asked for as style comps — `stripe.com`, `pentagram.com`, `press.stripe.com`. Every one came back unusable. The consultant spent four turns working around it, correctly concluded *"that's a wall, not a hiccup"*, and delivered the comps as a list of URLs it could not verify.

## Root cause — the guard counts third-party origins and calls them redirects

`egressGuard` (`tools/generate/src/cli/capture/egress-guard.ts:228`):

```ts
// Documents, not subresources: a page with forty images is not forty
// redirects, and counting them as such would refuse ordinary sites.
const documents = new Set<string>()
...
allow(url: string): boolean {
  if (tripped) return false
  ...
  documents.add(new URL(url).origin)
  if (documents.size > maxRedirects) {
    tripped = true
    ...
```

The comment states the intended rule. **The code does not implement it.** `allow()` is called on *every* request — `playwright-driver.ts:104` routes `**/*` through it, `cf-driver.ts:232` calls it from the single `request` listener with interception armed — and there is no document/subresource distinction anywhere in the function. The set named `documents` therefore accumulates the origin of every font host, image CDN, analytics beacon and embed on the page.

`MAX_REDIRECTS = 5`. **Any real website uses more than five origins.** Its own host, a CDN, `fonts.googleapis.com`, `fonts.gstatic.com`, an image CDN, a tag manager — that is six before anything unusual happens. Every site the consultant asked for tripped it, and any site a client names as a comp will too.

Then it gets worse: once `tripped` is set, `allow()` returns `false` for **everything, permanently** — first line of the method, no reset. One `capture_site` performs several navigation passes (noted in [[BUG-67]]). Pass one trips the cap partway through; every pass after it has its **main document** refused and fulfilled with `403 refused by egress policy` (`playwright-driver.ts:108`, `cf-driver.ts:237`), which the browser renders as the page. That is the black rectangle, and it is why the *screenshots* were unviewable rather than merely incomplete.

The refusal even names the wrong thing: *"more than 5 distinct origins were followed; treating this as a redirect loop."* A third-party font host is not a redirect. The cap is a redirect cap in name, an origin cap in behaviour, and an SSRF control in neither — `classifyUrl` is what actually blocks link-local space, and it is untouched by this.

## The second defect — a refused capture reports as a successful one

`capture_site` (`fidelity-core.ts:425-440`) returns `bundle`, `url`, `pages`, `assets`, `reference: adopted` and a `refusals` list. The list is reported always, and the comment defending that is right: *"a capture that quietly skipped a third of a page's images is the exact input that makes a later fidelity verdict wrong."*

But nothing computes a **verdict**. A capture whose own document was refused has the identical result shape to one that worked, plus a list the caller must interpret. So the consultant read success, adopted the bundle, screenshotted it, and only then discovered there was nothing there. The budget was spent before the truth arrived — which is the whole of the complaint, and it is separable from the origin-cap bug: even with the cap fixed, a genuinely refused capture should not look like a good one.

## Fix

1. **Count what the comment says.** Distinguish the navigation document from its subresources and cap only the former — the driver knows which is which (`route.request().resourceType()`, `req.resourceType()`), so this is available at the seam where the guard already runs. A page's forty images stop being forty redirects.
2. **Cap redirects as redirects.** If the intent is loop detection, count hops on a single navigation chain, not distinct origins seen over a capture's lifetime.
3. **Stop `tripped` from poisoning the rest of the capture.** A cap reached on one pass currently refuses the main document of every later pass, which converts a partial capture into a black rectangle. Either scope the trip to the pass that caused it, or abort the capture outright and say so — both are honest; silently returning refusal pages as content is not.
4. **Give the result a verdict.** When the captured document itself was refused, `capture_site` must fail rather than adopt a bundle: the declared `REFUSED` code already exists on the surface for the typed-URL case (`fidelity-core.ts:443`) and is the right answer here too. A capture that stored refusal text is not a capture.
5. **Charge for what was delivered.** A capture that produced nothing viewable should not consume a page-load allowance. See the separate discussion on capture budget — but at minimum, a refused capture must not be billed as a successful one.

None of this weakens the SSRF control. `classifyUrl` — scheme, credentials, private address space — is what stops `169.254.169.254`, it runs on every request before any of the above, and nothing here touches it.

## Test plan

- A page loading subresources from ten distinct third-party origins captures successfully; the origin count is no longer what refuses it.
- A navigation chain exceeding the redirect cap is refused, and the refusal names a redirect loop because that is what it is.
- A cap tripped during one navigation pass does not refuse the main document of a later pass in the same capture.
- A capture whose own document was refused raises `REFUSED` and adopts no bundle, rather than returning a success shape with a populated `refusals` list.
- `classifyUrl` still refuses link-local, loopback, `.internal`/`.local`, non-http schemes and embedded credentials, on the typed URL and on every subresource — unchanged, asserted alongside the above so a relaxation here can never quietly relax that.
