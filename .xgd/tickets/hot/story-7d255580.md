## Story
**As an** operator of a business on the platform, **I want** the invite, sign-in and lapse emails to be copy my business owns and can edit without a deploy, rendered so that a message with a missing link is refused rather than sent, sent from a named address chosen per template, and delivered with both the authored HTML and a plain-text part derived from it through a provider only when the deployment holds a credential, **so that** the people I invite actually receive a working way in that does not look like phishing — and no test or development machine can ever mail a real person.

## Description
Covers three cooperating parts landed by REQ-196, REQ-197 and REQ-205:

**Sending (REQ-196, REQ-205).** One send operation takes `to`, `from`, `subject`, `body` and returns the provider's message id. A deployment holding the Resend credential sends through Resend; anything without it (the test suite, `wrangler dev`) gets a local adapter that records the message, delivers nothing, and returns a `local_`-prefixed id. The credential is the only switch. Both adapters refuse the same malformed messages through one shared check. That check also derives the message's plain-text part from its HTML body: an anchor becomes its words followed by its address (just once when the words already are the address), block elements become line breaks, the contents of `<style>`/`<script>`/`<head>`/`<title>` are dropped, entities are decoded, and whitespace collapses. A body from which no text can be derived is refused. The provider receives the authored HTML and the derived text: one body written, two parts sent. A send failure is reported to the caller, never swallowed. The credential is a secret pushed by a deploy hook, never committed, and is redacted from anything the router shows. `MAIL.md` is the operator's SPF/DKIM/DMARC runbook and records the per-template address table.

**Sending address (REQ-205).** A message is sent from the template's own `from` when the template names one, and otherwise from the deployment's `MAIL_FROM`. `MAIL_FROM` is `1st Contact <no-reply@1stcontact.io>`, in RFC 5322 display-name form, and if it is missing the send is refused. The seeded invite names `1st Contact <invite@1stcontact.io>`; signin and lapsed name no address and use the fallback. The address is not token-substituted and is passed to the provider unchanged. It is resolved once per send, so the delivered message and the outgoing record carry the same value. The invite form displays the resolved address and refuses an edit; the invite route takes the address from the draft the server resolved and ignores any `from` on the request.

**Templates (REQ-197).** A `template` ticket type in the business's own ticket store (`template_key` ∈ invite|signin|lapsed, `subject`, optional `placeholders`, optional `from`, required non-empty body). The newest template for a key is the one in force; a business that has none is given a business-neutral default, once. Rendering substitutes `{{token}}`s in subject and body and refuses — naming template and token — when a declared token is absent from the body, a declared token has no/empty value, or any token is left unsubstituted.

**In scope:** the port, both adapters, the derived text part and its refusal, configuration and secret handling, the per-template sending address and its fallback, the template type, lookup + seeding, rendering and its refusals, the three seed templates.
**Out of scope:** the record of what was sent and the delivery/bounce webhook (REQ-198, plan item 7), beyond the record carrying the same address as the send; any template editing UI; rate limiting; an authored (rather than derived) text part; `List-Unsubscribe`; an operator-editable sender; changing provider; per-recipient personalisation beyond token substitution; our own tenant's invite copy and the operator work REQ-205 lists (mailbox routing for `invite@`, Postmaster Tools, the DMARC policy change).

## Reconciliation Decisions
- **Token declaration is tolerant of `{{name}}` and `name` spellings** (decided at reconciliation, 2026-11-04): intent is silent on how `placeholders` entries are written; the code accepts both because hand-authored tickets use both. Formalized in the render-substitution AC.
- **Subject tokens are substituted but the declaration is checked against the body only** (decided at reconciliation, 2026-11-04): stated in REQ-197's implementation decisions; formalized in the render-substitution and declared-token ACs.
- **Seed templates each declare exactly `{{cta_url}}`, and the signin and lapsed seeds carry the same button + pasteable-URL fallback as invite** (decided at reconciliation, 2026-11-04): REQ-197 requires the three-part structure only of `invite`; the code applies it to all three. Formalized in the seed-template AC.
- **Archiving every template for a key re-seeds the default on next lookup** (decided at reconciliation, 2026-11-04): REQ-197 states this as the accepted consequence; formalized in the lookup/seeding AC.
- **The deploy hook warns and exits 0 (rather than aborting) when the mail key exists nowhere** (decided at reconciliation, 2026-11-04): REQ-196's landed notes make this deliberate while nothing sends; formalized in the deploy-secret AC.
- **Body format: HTML plus a derived text part — the HTML-only send is superseded by REQ-205** (2026-11-07). REQ-197's "the body is HTML, and it is one part" was a decision about *authoring*. REQ-205 keeps one authored body and adds a text part derived from it, explicitly replacing `mail.ts`'s HTML-only send. The earlier code-issue resolution (override report-132efb58, commit c967412886: `html` only, no `text`) is therefore no longer the target. AC-2281 now asserts both parts. The "no text part" assertion was retired by intent, not by drift.
- **The deployment-wide From is no longer the only address** (2026-11-07): REQ-205 makes the address per-template, with `MAIL_FROM` as the fallback, and gives `MAIL_FROM` a display name. AC-2279 now pins `1st Contact <no-reply@1stcontact.io>` as the fallback.
- **A blank template `from` means the fallback** (decided at reconciliation, 2026-11-07): intent says an absent `from` means `MAIL_FROM` and says nothing about an empty or whitespace-only one. The code trims the value and treats empty as absent, which is the only reading that cannot produce an empty sender. Formalized in the sending-address AC.
- **Entity decoding is a small named table plus numeric references, and an unknown named entity is left as written** (decided at reconciliation, 2026-11-07): this is stated in REQ-205's implementation notes. It is not asserted on its own; the observable contract is the href invariant plus text that reads the way the page reads.
- **The seed's `from` naming 1st Contact does not breach seed neutrality** (2026-11-07): REQ-205 says the neutrality decision "stands" for the *copy*; the address is a separate field naming the deployment's only sending domain. AC-2286's no-"1st Contact" check applies to subject and body, not to the address.
