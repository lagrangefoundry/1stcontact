## Symptom

On Ariel's Arc Welding (tenant `biz_1dbc40bad7f023955b8120f053bfd245`), three builder sessions ran and have chat and tool transcripts but appear in no consultant turn's `attributed` list in `turn_spend`: `worker-builder-10-t8nyvl` (built the sign-style logo banner), `worker-builder-18-8ke3mj` and `worker-builder-19-dwnuq3`. Two owner messages, at 18:29:05Z and 19:14:18Z on 2026-10-21, also have no turn row of their own. So the metered $52 for the site is low by an unknown amount, and per-site cost analysis undercounts exactly the turns that went wrong.

Separately, the meter keeps only per-turn totals. The framework already hands the host one usage record per model request (`requests` on the terminal `done` meta), but `spend-core.ts` keeps only `requests.length`, so the per-request counters are thrown away. The Ariel review therefore could not say why delegation turns wrote ~982k tokens to the cache against ~155k of hand-offs, where ~4.7k uncached tokens per consultant request came from, or when the cache expired. Each of those took transcript reconstruction, or stayed unanswered.

## Root cause

Missing rows: **the dev isolate died mid-turn, and a turn was metered only from its `finally`.** Read off the site's own local store (the `SessionJunction` DO log, `turn_log` and `turn_spend`):

- The 18:29:05 turn (`turn_cc6be6d1…`) delegated `worker-builder-10-t8nyvl`, which ran 18:30:06–18:34:02. The junction's `turn_end` for that turn came at 18:35:31, `aborted`, with **no** `attributed`. `turn_log` never closed it and `turn_spend` has no row. The builder counter then restarts at `worker-builder-1` at 18:35, so the isolate was replaced in between. The attribution the delegation surface buffers in RAM for the caller's `turn_end` went with it.
- The 19:14:18 turn (`turn_c4503ad9…`) and the 19:38:53 turn have a `turn_start` and no `turn_end` at all. Builders 18 and 19 ran under the 19:14 turn.

So nothing the host or the framework keeps in memory survives an isolate restart, and the only writer was the turn's `finally`. The earlier guess, a consultant turn aborted in-process while its builders run, is not the cause: an in-process abort waits for the builder and does attribute it. Reproduced, though, it showed a second loss. The aborted turn's own requests were metered as nothing (`requests: 0`, cost NULL), because no terminal meta arrived.

Missing per-request detail: the host never stored it. Some of the wanted fields (timing, part sizes, prefix fingerprints, trigger) aren't in the framework's request records yet. That's lagrange-framework REQ-218.

## Fix

1. Every builder run is attributed to some turn row, and every turn writes a row, whatever its outcome. A turn row is never dropped because the turn ended abnormally.
2. One row per model request, for the consultant and builders alike, in a new D1 table beside `turn_spend` (keyed by turn id and request index, with session, role and tenant), holding:
   - input, cache-read, cache-write (5-minute and 1-hour where split) and output tokens, and that request's cost;
   - once framework REQ-218 lands, and stored whenever the record carries them: send time, part sizes (system, tools, history, uncached tail), part fingerprints, and the trigger (tool name and result size). A field the record doesn't carry is stored as null, never zero.
   Builder requests are stored under the builder's own session and turn, linked to the consultant turn that delegated them, so attribution doesn't depend on that turn's row being written.
3. The spend report (`spend-report-core.ts`) can list a turn's requests, and flags the requests whose cache reads fell from the previous request (a cache break), naming the part whose fingerprint changed when known.

## What changed

- **`request_spend` (migration `0030`)**: one row per model request, keyed `(turn_id, request_index)`, with tenant, session, role, backend, model and `delegated_by`; the five counters, the 5m/1h write split (NULL where unsplit) and cost; and REQ-218's `sent_at`, part sizes (`system/tools/history/tail_chars`), fingerprints (`system/tools/history_fingerprint`) and `trigger` (JSON), each NULL where the record does not carry it. Read defensively from the record's `at`, `parts`, `fingerprints` and `trigger` keys.
- **Requests are written live, as each completes.** `guardTurn` (every backend's wrapper) takes a `requests` sink, asked once per guarded turn and fed each new usage record with its index in the turn.
  - Consultant turns: `siteTurn` registers its turn per site, and the first guarded call on the site's backend after that claims it. Talker rounds run on the same backend but later, so they never claim it.
  - Builders: each guarded call is one builder turn, with an id minted for it. Its rows are written under the builder's session, with `delegated_by` set to the consultant turn in flight on that site.
- **The close writes the requests again** from the turn's own request records, in the same D1 batch as the turn row. They are `INSERT OR IGNORE`, so a request written live stands and one missed live is filled in. Turn and request rows come from the same records, so they always sum to each other. This covers the settings, coordinator and talker turns too.
- **A turn row exists from the moment the turn begins.** `open` writes it with `outcome = 'open'`, zero counters and a NULL cost. The close replaces it, but only while it is still open. A turn that accounted for nothing deletes it, so "no row for a turn that measured nothing" still holds. A turn whose isolate dies keeps the open row.
- **A turn that ends without its terminal meta** (stopped, walked away from) is metered from the requests it was seen to make, not as unobserved.
- **Delegated spend includes builders no list names.** `tenantDelegatedSpend` and `tenantTurnCosts` add, per delegating turn, builder sessions that have request rows with `delegated_by` set to it but are missing from its `attributed` list. Those builders are priced from their own rows' `(backend, model)`.
- **The port is now `TurnMeter`** (`open` / `requests` / `close`), replacing `RecordTurnSpend`. The D1 implementation is `d1TurnMeter`, replacing `d1TurnSpend`. `HostDeps.recordTurnSpend` becomes `turnMeter`.
- **Report**: `spend-report-core.ts`'s `requestLines(rows)` lists requests per turn in index order. It flags any request whose cache read fell from the previous request in the same turn, with `{previousRead, read, changed, gapMs}`. `changed` names the cached parts whose fingerprint differs, or is `null` where fingerprints are absent. `spend.ts`'s `tenantTurnRequests(env, tenant, turnId, {delegated})` reads a turn's rows, optionally with its builders'.

## Design decisions

- **Builders get request rows, not `turn_spend` rows.** `turn_spend` stays the tenant's own turns. REQ-293's report, and BUG-145's "the two figures stay two", count it that way. A builder's "turn row" remains its entry in its caller's `attributed` list, and its request rows sum to that entry.
- **The live consultant path is keyed by site and claimed once per turn**, the same per-`managerKey` pattern `signals` uses. The framework passes no turn id to the backend.
- **Not covered**: the critic backend's requests (REQ-427 hostLook) are charged to the message's ceiling but still belong to no turn row. That is unchanged and out of this ticket's scope.

  - a turn's request rows sum to its row, one per request, for every row of the session (consultant and talker). The builder's rows sit under its own session, linked by `delegated_by`, and sum to its `attributed` entry. `tenantTurnRequests` lists the turn's requests followed by its builder's.
