## What happened
A delegated builder session wrote 8 changes to the draft (change count 67→75): two new sections on page `home`, text edits, a fill/border change, and site title/SEO meta. The session then ended `aborted` (see the companion bug about silent builder results). A later small builder pass (75→77) completed normally.

The draft holds all of these changes. `describe_page` and a `draft` screenshot taken by the consultant both show them. However, the **client's preview window did not show them**. The tester reports the preview never updated.

Several unrelated dev sessions crashed at the same moment, so the preview may simply have lost its update channel at that point. Even so, the preview should not stay stale silently.

## Expected
The client's preview reflects the draft's current change count, whichever session wrote the change. If the preview misses notifications (worker abort, dropped socket), it should resync on reconnect or poll the change count. It could also show a visible "preview out of date — refresh" state, rather than presenting a stale page as current.

## Investigate
- Are preview refresh notifications sent per writing session, and lost when that session aborts before it flushes or commits a notification?
- Does the preview resubscribe and compare change counts after a connection drop?
- Did the later successful pass (75→77) refresh the preview? If not, the stale state is sticky, not just a missed event.

## Reproduce
Delegate a builder write, kill or abort the worker after its writes but before it reports, then check whether the client preview shows the new change count.


## Root cause
The builder's preview frame reloaded only on `site_changed` events, which the host emits inside the **consultant's own chat stream** after tool activity (`host-core.ts` `siteTurn`). Nothing else told the preview the draft moved, so:
- a write made while that stream was no longer being read (worker aborted, isolate died, socket dropped, tab reconnected) never reached the frame, and
- nothing compared the frame against the draft's change count afterwards, so the stale page was shown as current until a later turn happened to emit another `site_changed` on a live stream, or the operator reloaded by hand.

## What changed
The preview now has its own subscription to the draft, independent of any chat session, on the precedent of the Library (`/api/material/changes`, REQ-201) and Contacts (`/api/people/changes`, REQ-233) feeds:

- **`GET /api/sites/changes?site=<key>`** — an SSE change feed over the site's draft change counter (`SiteStore.counter`, the same number `site_changed` carries as `at`; every structured write moves it, whichever session made it). Scoped like every other site read: a missing `site` is a 400, a site this business does not hold is a 404. First frame is `{kind:"ready", at}` carrying the count the connection opened at (also its `id:`). Afterwards, whenever the count moves past the last value sent, one `{kind:"draft", at}` frame with `id: <at>` (several writes inside one poll collapse into one frame). `Last-Event-ID` wins over `?since`, and the first poll runs immediately, so a browser `EventSource` reconnecting after a drop is told about the gap at once. Polls every 2 s (`DRAFT_CHANGE_POLL_MS`, same cadence as the other feeds), heartbeats when idle, tears down when the client leaves.
- **Builder preview responses state their change count** — `/preview/<site>/draft|edit/…` responses carry `Server-Timing: draft-at;desc="<n>"`, the count read just before rendering. The page bytes are untouched (preview bytes must stay identical to build bytes, REQ-119); `Server-Timing` is the one header a same-origin frame can read about itself, through its navigation entry.
- **Builder client** — the app subscribes to the feed for the site in view (re-aimed on site/business switch, closed on unmount; no-op where `EventSource` is unavailable). Every signal — a feed frame or the in-stream `site_changed` — goes through one test: reload the frame only if it is behind the reported count. So any writer's change (a delegated builder, an aborted session, another tab) reaches the preview within one poll, a dropped connection catches up on reconnect, and one write reported both in the chat stream and on the feed reloads the frame once — the operator's own saves (which reload at once) are not reloaded again a moment later. If the frame cannot state a count (mid-load), a reported write still reloads it, but the feed's opening `ready` frame does not.

## Design decisions
- No "preview out of date — refresh" banner: once the preview resyncs on its own, a banner has nothing left to say.
- A `<meta>` stamp in the page was tried first and rejected: it broke the REQ-119 byte-equality between preview and build output.
- The in-stream `site_changed` reload (BUG-43) is kept for immediacy; it now shares the "is the frame behind" guard with the feed.

## Test plan
- `tests/test_UAT_FC_BUG-192_draft_changes.workers.test.ts` (workerd, real D1): the feed opens with `ready` at the current count; a write made through a builder write route (no chat stream) produces a `draft` frame at the new count; a reconnect with `Last-Event-ID` behind the draft is told at once with one collapsed frame (and `Last-Event-ID` beats `?since`); missing site → 400, foreign site → 404; poll cadence is 2000 ms; draft and edit preview responses carry `Server-Timing: draft-at;desc="<count>"` and the page body does not.
- `tests/test_UAT_FC_BUG-192_preview_follows_the_draft.test.ts` (jsdom, real builder app): the builder follows the feed for the site in view and closes it on unmount; a feed frame beyond the frame's count reloads it; a `ready` frame after a reconnect that finds the frame behind reloads it; a count the frame already shows does not; a write reported in the chat stream and then on the feed reloads once.
- Regression: BUG-43, REQ-119, REQ-201, REQ-233, REQ-312 suites pass.
