## What happened
A delegated builder session wrote 8 changes to the draft (change count 67→75): two new sections on page `home`, text edits, a fill/border change, and site title/SEO meta. The session then ended `aborted` (see the companion bug about silent builder results). A later small builder pass (75→77) completed normally.

The draft holds all of these changes. `describe_page` and a `draft` screenshot taken by the consultant both show them. However, the **client's preview window did not show them**. The tester reports the preview never updated.

Several unrelated dev sessions crashed at the same moment, so the preview may simply have lost its update channel at that point. Even so, the preview should not stay stale silently.

## Expected
The client's preview reflects the draft's current change count, whichever session wrote the change. If the preview misses notifications (worker abort, dropped socket), it should resync on reconnect or poll the change count. It could also show a visible "preview out of date — refresh" state, rather than presenting a stale page as current.

## Investigate
- Are preview refresh notifications sent per writing session, and lost when that session aborts before it flushes or commits a notification?
- Does the preview resubscribe and compare change counts after a connection drop?
- Did the later successful pass (75→77) refresh the preview? If not, the stale state is sticky, not just a missed event.

## Reproduce
Delegate a builder write, kill or abort the worker after its writes but before it reports, then check whether the client preview shows the new change count.


## Root cause
The builder's preview frame reloads only on `site_changed` events, which the host emits inside the **consultant's own chat stream** after tool activity (`host-core.ts` `siteTurn`). Nothing else ever tells the preview the draft moved. So:
- a write made while that stream is no longer being read (worker aborted, isolate died, socket dropped, tab reconnected) never reaches the frame, and
- nothing compares the frame against the draft's change count afterwards, so the stale page is shown as current until a later turn happens to emit another `site_changed` on a live stream, or the operator reloads by hand.

## Fix
Give the preview its own subscription to the draft, independent of any chat session, on the precedent the Library (`/api/material/changes`, REQ-201) and Contacts (`/api/people/changes`, REQ-233) feeds already set:

- **`GET /api/site/changes?site=<key>&since=<n>`** — an SSE change feed over the site's draft change counter (`SiteStore.counter`, the same number `site_changed` carries as `at`). Scoped like every other site read. First frame is `ready` carrying the counter the connection opened at; afterwards, whenever the counter moves past the last value sent, one `{kind:"draft", at}` frame with `id: <at>`. `Last-Event-ID` wins over `since`, so a browser `EventSource` that reconnects after a drop resumes from the last count it saw, and the first poll after reconnect reports any change made in the gap. Polls the store every 2 s (same cadence as the other feeds), heartbeats when idle, tears down when the client leaves.
- **Builder client** — the preview panel subscribes to that feed for the selected site (re-subscribing on site switch, closing on unmount). Whenever a frame reports a change count beyond the one the frame last loaded, it reloads the frame. So any writer's change — a delegated builder, an aborted session, another tab — reaches the preview within one poll, and a dropped connection catches up on reconnect.
- The in-stream `site_changed` reload (BUG-43) stays as-is for immediacy. Both paths go through the same "reload if the frame is behind this count" guard, so one write reloads the frame once, not twice.

No "preview out of date" banner: once the preview resyncs on its own, a banner has nothing left to say.

## Test plan
`test_UAT_FC_BUG-192_*`:
- route: the feed opens with a `ready` frame at the current counter; a write to the draft from outside any chat stream produces a `draft` frame with the new count; `Last-Event-ID` behind the current count gets a frame for the gap immediately; a missing `site` is a 400.
- client: a feed frame with a higher count reloads the preview frame; a frame (or `site_changed`) at a count the frame already shows does not reload again.
