## Priming: checked, and it is not stuffing (2026-09-08)

Traced end to end. **No document body is ever placed in a session's context.**
The KMS handles it exactly as designed:

`priming.json` declares five entries in order — `consultant-role` (authored),
`product-system` (authored), `km-landscape` (**provider**), `purpose`
(authored), `km-mechanism` (**provider**) — then a cache boundary.

The two providers come from the shared component
(`@lagrangefoundry/ai-knowledge/src/priming.js`): `km.landscape` renders the
awareness map (what territories exist), `km.mechanism` renders how to search
them. Its own header states the contract — *"Neither carries a document body,
which is the point: a session is told where to look and how to look, and pulls
what it needs. Nothing is stuffed into context."* Both re-read on every call, so
a document published mid-session is reachable.

Budget: `MAX_PRIMING_CHARS = 60_000`, currently priming at roughly 16,000 —
4,851 static plus about 11,000 of projected tool manual. The landscape is the
only part that grows with the corpus, and it has room.

### The real defect, which is smaller and different

The authored `purpose` entry hardcodes three document ids: *"the consultation
playbook (DOC-33) … personas, modes and registers (DOC-35) … the differentiation
audit (DOC-31)."*

That is a hand-maintained id list doing the awareness map's job, and it is the
exact drift `kb.ts` rejects id lists for elsewhere — *"an id list drifts silently
when a document is renamed or retired."* It also creates a two-tier corpus:
three documents are named in priming, every other member is discoverable only
through the map.

It is currently load-bearing for a bad reason — `kb/system/awareness.md` is
stale (dated 2026-08-31, four documents, no mention of the REF projections), so
the map it compensates for is not doing its job. Once the map is rebuilt the
compensation is unnecessary.

**The obligation it states is still right and still belongs in priming** —
*"your method is written down and you are expected to read it before you start"*
is a behavioural instruction, not a discovery mechanism, and the map cannot
carry it. The fix is to state the obligation without pinning ids.

Note that [[DOC-31]] is now demoted, so the entry already names a document that
is no longer in the corpus.

## The four incumbents, against the standard

Standard applied: *a system-KB document is written for the AI, is canonical, and
is kept accurate and current.*

**Kept — [[DOC-33]] and [[DOC-35]].** Both are addressed to the AI, both are the
canonical statement of their subject, and both are things we would maintain.
Nothing in the new six replaces either.

**Demoted to `architecture` — [[DOC-31]] and [[DOC-17]].** Both fail the
standard by construction rather than by quality:

- [[DOC-31]] is a dated market research report. Its final section is
  recommendations addressed to us, and a competitor snapshot is not a document
  anyone will keep current.
- [[DOC-17]] is a working log — *"append here as you build"*, dated session
  entries, internal ticket references. A log is the raw material canon is
  distilled from; it is never itself canonical.

Their usable findings are carried by [[DOC-48]], which also gained a curated
reference set (§12) so the named exemplar sites survive the demotion.

**Corpus is now eight authored documents plus three projections.**

## Purpose

Decide the composition of the **system knowledge base** — the corpus the builder
chat AI searches when advising a client. Specifically: which existing `doc`
tickets should carry `doc_kind: system_kb`, which contain relevant material but
are written for the wrong reader, and which system-KB documents need authoring
from scratch.

Driven by [[DOC-39]] §3.5 / §10, which deliberately deferred "which system-KB
documents get written" as an authoring exercise to run once the machinery was in
place. The machinery is in place.

## Findings — the KB is connected

- Membership is `fields.doc_kind == 'system_kb'` on a `doc` ticket
  (`tools/generate/src/cli/kb.ts`, `MEMBER_KIND`). Single-valued and exclusive
  with `architecture` by design ([[DOC-39]] §3.1).
- `1c kb build` exports members to `kb/system/*.md`, indexes them, and writes
  `awareness.md`. `1c assets` inlines the result into
  `apps/control-app/src/generated/kb.js`, which ships in the Worker bundle.
- The builder session searches **both** KBs — `SESSION_KBS = [PROJECT_KB,
  SYSTEM_KB]` (`apps/control-app/src/session-knowledge.ts`).
- Current corpus: four authored documents (DOC-17, DOC-31, DOC-33, DOC-35) plus
  three generated projections (REF-l1, REF-surface, REF-behaviors).

**Defect found:** `kb/system/awareness.md` is stale — dated 2026-08-31, describes
"4 documents in 2 territories", and does not mention the REF projections at all,
though all seven are in the index manifest. The awareness map is what primes the
AI on *what kinds of knowledge exist*, so the assistant is currently unaware that
the tool manual, the L1 vocabulary and the behavior catalogue are searchable.

## Requirements the corpus must cover

1. What 1st Contact is, what it sells, and where the front office stops.
2. The differentiation: no templates, not four minutes, consultation-led.
3. How to run the consultation (covered — DOC-33).
4. How to build a page in L1 — craft, not vocabulary.
5. How to wield the tool surface — practice, not the manual.
6. Product behaviour a client will ask about: drafts, publishing, addresses,
   what they can edit themselves.
7. **What actually exists today vs. the aspirational product** — a living
   beta-reality document, so the AI does not promise unbuilt capabilities.
