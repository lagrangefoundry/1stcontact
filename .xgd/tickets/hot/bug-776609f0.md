## Symptom

The builder will not show the 1st Contact site. Instead:

> Module not found in catalog: 'account-chrome' v1. Known modules: contact-form@4, carousel@3, account-portal@1, account-chrome@2.

## Diagnosis

The operator's live 1st Contact draft lives in D1 (`site_pages`, site
`site_62d3d0097bbc7b6e86bdcdb3728389a3`, page `home.json`). Its
`account-chrome` instance (`id: "signin"`) is pinned to **version 1**:

```
config: { account, businesses, signIn, portal, signInLabel, emailLabel,
          submitLabel, sentMessage, portalLabel, businessesLabel, dismissLabel }
slots:  [ signedOut, signedIn, businesses, dialog ]
```

`0b5a32d465` (BUG-76) took `account-chrome`'s contract to **version 2** and
**removed v1 from the catalog entirely**. `getModuleMeta`/`getModule` resolve
on `"<id>@<version>"`, so a pinned v1 instance no longer resolves and the whole
page fails to load — one orphaned instance takes the entire site down.

v2 is a genuinely breaking change against what is stored:

- `sent` and `error` are new **required** slots (the stored instance has neither);
- `config.sentMessage` is gone — its words moved into the `sent` slot;
- `config.account` was never a declared key (v2 config validation is strict at
  the write boundary, so it would now be refused on the next edit);
- `labelMode` is new, defaulting to `visible`.

**Scope of the damage, audited across both stores:** exactly one orphan. Every
other stored instance in D1 (`contact-form@4` × 6) and in `storage/sites/`
(`contact-form@4` × 4, `account-chrome@2` × 1) resolves. 1st Contact has no
published revisions, so only the draft row is affected.

**Why the fixture did not catch it.** `0b5a32d465` updated
`storage/sites/1stcontact/draft/pages/home.json` — the file-backed fixture
(module `id: "chrome"`) — to v2. That is a *different copy* from the operator's
D1 draft (module `id: "signin"`), authored separately and never migrated. The
fixture being green is what made the orphan invisible.

## The systemic gap

A breaking module version bump silently orphans every already-stored instance
pinned to the previous version. There is no migration facility, no compatibility
window, and nothing that fails at bump time — the only signal is the site going
dark at load. `latestModuleVersion`'s own doc comment says "existing instances
still pin their own version", which is only true if the catalog keeps resolving
those pins, and it does not.

DOC-25 says `version` is "bumped on a breaking contract change" and says nothing
about what happens to instances already carrying the old number. That policy is
undecided and this bug is the first time it has cost anything.

## Fix

(to be agreed — see below)

1. **Repair the orphan.** Rewrite the stored instance as a valid v2: add authored
   `sent` and `error` cards matching the dialog's own paint (paper fill, accent
   border, radius 16, max 380px), carry the existing `sentMessage` wording into
   the `sent` card, drop `sentMessage` and `account` from config.
2. **Close the class** (scope to be decided): a guard that a version bump cannot
   land while a stored instance still pins the old version, and/or a declared
   per-version migration applied by an upgrade pass over a `SiteStore`.
