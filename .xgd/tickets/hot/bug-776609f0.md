## Symptom

The builder will not show the 1st Contact site. Instead:

> Module not found in catalog: 'account-chrome' v1. Known modules: contact-form@4, carousel@3, account-portal@1, account-chrome@2.

## Diagnosis

The operator's live 1st Contact draft lives in D1 (`site_pages`, site
`site_62d3d0097bbc7b6e86bdcdb3728389a3`, page `home.json`). Its
`account-chrome` instance (`id: "signin"`) is pinned to **version 1**:

```
config: { account, businesses, signIn, portal, signInLabel, emailLabel,
          submitLabel, sentMessage, portalLabel, businessesLabel, dismissLabel }
slots:  [ signedOut, signedIn, businesses, dialog ]
```

`0b5a32d465` (BUG-76) took `account-chrome`'s contract to **version 2** and
**removed v1 from the catalog entirely**. `getModuleMeta`/`getModule` resolve
on `"<id>@<version>"`, so a pinned v1 instance no longer resolves and the whole
page fails to load — one orphaned instance takes the entire site down.

v2 is a genuinely breaking change against what is stored:

- `sent` and `error` are new **required** slots (the stored instance has neither);
- `config.sentMessage` is gone — its words moved into the `sent` slot;
- `config.account` was never a declared key (v2 config validation is strict at
  the write boundary, so it would now be refused on the next edit);
- `labelMode` is new, defaulting to `visible`.

**Scope of the damage, audited across both stores:** exactly one orphan. Every
other stored instance in D1 (`contact-form@4` × 6) and in `storage/sites/`
(`contact-form@4` × 4, `account-chrome@2` × 1) resolves. 1st Contact has no
published revisions, so only the draft row is affected.

**Why the fixture did not catch it.** `0b5a32d465` updated
`storage/sites/1stcontact/draft/pages/home.json` — the file-backed fixture
(module `id: "chrome"`) — to v2. That is a *different copy* from the operator's
D1 draft (module `id: "signin"`), authored separately and never migrated. The
fixture being green is what made the orphan invisible.

## Why only this site broke

Three independent facts had to line up, and they did only here.

1. **1st Contact is the only site that carries an `account-chrome` instance at
   all.** The module is gated on `config.capabilities.accounts`, declared per
   site and never derived. Across all seven sites in D1, exactly one declares
   it — `site_62d3d0097bbc7b6e86bdcdb3728389a3`, `capabilities: {accounts: true}`.
   Every other site is a brochure site whose only module is `contact-form`, which
   this commit did not touch. So the blast radius of an `account-chrome` bump is
   "every site with accounts", and today that set has one member.

2. **`contact-form` has never been exposed to this failure mode, so it never
   demonstrated the hazard.** Its last version bump (3 → 4) landed in
   `3d35dec430` on 2026-07-25. The earliest site in D1 was created
   2026-09-06 — six weeks later. Every stored `contact-form` instance was
   therefore *born* at v4; there has never been a stored instance carrying an
   old `contact-form` pin. The bump that would have taught us this lesson
   happened before there was any data to break.

3. **The one copy that got migrated was the one visible in the repo.**
   `0b5a32d465` updated `storage/sites/1stcontact/draft/pages/home.json` to v2
   (+68 lines, adding the `sent`/`error` slots). That is the file-backed fixture,
   module `id: "chrome"`. The operator's draft is a different copy in a different
   store, module `id: "signin"`, and nothing in a repo-level edit can see it. The
   stored draft was last written 2026-09-11T02:14Z; the bump landed ~21 hours
   later and never reached it.

The third point is the one that generalises: **a migration performed by editing
files in the repo can only ever reach the fixtures.** As long as that is how a
version bump migrates data, the live stores are guaranteed to be missed, and the
only reason the damage was one site this time is fact 1.

## The systemic gap

A breaking module version bump silently orphans every already-stored instance
pinned to the previous version. There is no migration facility, no compatibility
window, and nothing that fails at bump time — the only signal is the site going
dark at load. `latestModuleVersion`'s own doc comment says "existing instances
still pin their own version", which is only true if the catalog keeps resolving
those pins, and it does not.

DOC-25 says `version` is "bumped on a breaking contract change" and says nothing
about what happens to instances already carrying the old number. That policy is
undecided and this bug is the first time it has cost anything.

## Fix

### Part 1 — repair the orphan (done)

The stored instance is rewritten as a valid v2: `version` 1 → 2, `sentMessage`
and the never-declared `account` key removed, and `sent` + `error` cards added.
The cards are built from **the instance's own `dialog` slot** — this site paints
on palette refs (`paper`/`ink`/`accent`) at radius 16, and an L2-preset-shaped
card would have arrived with hardcoded `#ffffff` at radius 8. The author's
`sentMessage` wording carries into the `sent` card verbatim; `error` reads
"That didn't send. Please check your connection and try again."

The original row is kept as a test fixture: it is the only surviving example of
a real orphaned instance, and Part 2's migration must reproduce the repair from
it exactly.

### Part 2 — a declared migration per bump, applied over the port

**A migration cannot be derived from the data, and the design must not pretend
otherwise.** For v1 → v2: dropping `account` and defaulting `labelMode` are
mechanical, carrying `sentMessage`'s words is mechanical, but the *card that
holds them* does not exist in v1, and the `error` slot has no source data at all
— v1 hardcoded that string in the component. Only the author making the breaking
change knows what the old shape meant. So the automation is not inference; it is
giving the migration a declared home, applying it everywhere, and refusing a bump
that has not got one.

**2a. Declare it beside the contract.** `BehaviorMeta` gains an optional
`migrations`, keyed by the version each produces:

```ts
migrations?: Record<number, (prev: BehaviorInstance) => BehaviorInstance>
```

`account-chrome` carries `{ 2: … }`. Keyed by the version produced rather than
consumed so the key matches the `version` the instance ends up holding.

**2b. Upgrade one instance.** `upgradeInstance(type, version, instance)` walks
`version + 1 … latestModuleVersion(type)`, applying each declared migration in
turn — so an instance two bumps behind crosses both — then validates the result
against the target contract with the existing `validateBehaviorConfig` /
`validateBehaviorSlots`. **A migration whose output does not validate is an
error, not a warning:** writing an instance that fails its own new contract
would replace a loud catalog miss with a quiet one.

**2c. Upgrade a whole site, over the port.** `upgradeSiteModules(store, slug,
opts)` reads every page through `SiteStore`, upgrades every stale instance, and
reports what it would change. It is **read-only unless asked**: `write: true`
writes the upgraded pages back as one `SiteWrite`. A facility that silently
rewrites live site data on first run is not one to ship. Being port-to-port, the
same function serves the filesystem store and D1 — which is the whole gap, since
the store that actually broke was D1 and the copy that got migrated was the
fixture.

**2d. Reach both stores.** `1c module upgrade <slug>` drives the local
filesystem store; `--origin` posts to `POST /api/modules/upgrade` on the control
app so the **Worker** performs the D1 write through the bindings it serves from
— the same reasoning `/api/import` already follows, and for the same reason
(Node holds no D1 binding, and a second writer would be a second definition of
what a site is made of). Dry-run by default on both paths; `--write` applies.

**2e. The guard that makes a bump fail at bump time.** A test asserting that for
every module in the catalog, every version from 1 to the current one has a
complete migration path to the current one. It needs no stored data, so it runs
in CI on every commit: bump `account-chrome` to 3 without declaring
`migrations[3]` and the build goes red *in the commit that does the bumping*,
instead of a site going dark days later. This is the piece that converts the
failure mode from "discovered by an operator" to "discovered by the author".

**2e-i. Declaring a version extinct.** Landing 2e's guard immediately showed
it demands more than `account-chrome`'s missing step: `contact-form` is at v4
and `carousel` at v3, and neither has a migration for any of its historical
bumps. Writing those would mean inventing transformations of contracts that no
longer exist, for data that is in no store — untestable code whose only effect
is to turn the guard green. But *omitting* them silently is precisely how
`account-chrome` shipped its bump with no migration, so absence cannot be the
way to say it either.

So `BehaviorMeta` gains `migrationsFrom` — the oldest version a module still
migrates from, defaulting to 1. Below it, versions are **declared extinct**: a
number in the meta that a reviewer sees, carrying the audit it rests on in its
comment. `contact-form` declares 4 and `carousel` 3, on the evidence gathered
diagnosing this bug: the last `contact-form` bump was 2026-07-25, the earliest
site in the cloud store was created 2026-09-06, and an audit of both stores
found ten `contact-form` instances, all v4, and no `carousel` instance at all.

A floor is a **claim about the world**, not an exemption, and an instance found
below it disproves the claim. `upgradeInstance` therefore refuses such an
instance with its own message — naming the floor and saying to lower it — rather
than reporting a generic missing migration, because the remedy is different:
somebody has to write the steps *and* correct the declaration that said none
were needed.

**2f. The audit, as a command.** `upgradeSiteModules` in its default read-only
mode already answers "which stored instances do not resolve" — the audit run by
hand when diagnosing this bug. It must run against a **real** store, because the
repo fixtures being green is exactly what hid this defect.

### Explicitly rejected

- **Upgrading silently on read.** The stored data stays stale forever, the defect
  becomes permanent and invisible, and every read pays the cost.
- **Keeping old versions resolvable in the catalog.** It means keeping v1's
  component, client and stylesheet alive indefinitely; BUG-76 deleted that
  behaviour deliberately, and resurrecting it would be dishonest about what the
  site renders.

### Known limit

The guard forces a migration to *exist*; it cannot judge whether the migration is
*correct*. That stays a per-bump UAT, written by the author who already
understands the change — which is what `test_UAT_FC_BUG-85_account_chrome_v1_to_v2`
is.

## Test plan

UATs, all named `test_UAT_FC_BUG-85_*`:

- **`migration_path_guard`** — every catalog module has a complete migration path
  from its declared floor to its current version; a module with a gap fails, and
  a module still at v1 is not asked for a migration into v1. Covers 2e.
- **`upgrade_instance`** — `upgradeInstance` chains multiple migrations, is a
  no-op for an instance already current, refuses a pin no migration reaches and
  a pin below a declared-extinct floor (each with its own remedy in the
  message), refuses a pin ahead of the catalog rather than downgrading it,
  drops undeclared config keys and slots **after** the migrations have had
  their chance to read them and names every one dropped, carries page-level
  fields the contract says nothing about, and **throws when a migration
  produces an instance that fails the target contract**. Covers 2b and 2e-i.
- **`account_chrome_v1_to_v2`** — run against the real orphan captured from D1,
  the migration retires `sentMessage`, drops the undeclared `account` in the
  open, authors `sent` and `error`, cuts both cards from the instance's own
  dialog rather than the L2 preset, never overwrites a card an author has since
  drawn, and produces something the v2 contract accepts. Covers 2a and the
  known limit.
- **`upgrade_site_modules`** — over an in-memory `SiteStore`: the default run
  writes nothing and reports every stale instance; `write: true` writes upgraded
  pages back as a single `SiteWrite`; a site with nothing stale reports nothing
  and writes nothing. Covers 2c and 2f.
- **`upgrade_route`** — `POST /api/modules/upgrade` reports without writing by
  default, writes when asked, and is a no-op on a second run. Runs **inside
  workerd against real D1**, because a facility proved only against the
  in-memory store would repeat this bug's own mistake at one remove: green
  everywhere except where the data lives. Covers 2d.
