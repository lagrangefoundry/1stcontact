#### Claude
The whole of `bin/deploy` runs under a node wrapper (`env-file.mjs`). That's my lead suspect, so I'm reading that next.

The sandbox won't let me open a pseudo-terminal ("out of pty devices"), so I can't reproduce this live. Switching to reading what each child does to the terminal.

Wrangler only hides and shows the cursor (`?25l`/`?25h`), and its prompts switch raw mode off again when they close. Next: how wrangler runs Docker for the container build and push.

I couldn't confirm a root cause, and I think the ticket's lead theory is probably wrong. The likeliest explanation is that a process is still holding the terminal when you start typing, not that a terminal mode was left switched on.

**Why I couldn't confirm it:** I tried to run `bin/deploy --dry-run --env production` under a pseudo-terminal, but the sandbox refuses to open one ("out of pty devices"). So everything below comes from reading the code, not from a run.

**Ruled out:**
- **The node wrapper.** `bin/deploy` immediately re-runs itself through `tools/generate/bin/env-file.mjs`. That uses `spawnSync('bash', …, { stdio: 'inherit' })`, so it waits for the script and then exits. It doesn't keep the terminal.
- **Wrangler.** Its prompts switch raw mode on and off again when they close. The only other terminal codes it writes are hide/show cursor. It has no extended-keyboard, bracketed-paste or keypad codes.
- **Docker and buildx.** Wrangler runs both as children. Their binaries only hide and show the cursor.
- **The dev services.** `1c dev refresh` starts them with `detached: true, stdio: ['ignore', log, log]` (`tools/generate/src/cli/dev.ts:618`). The ticket was right about this.
- **Leftover `stty` settings.** Node restores the terminal's settings when it exits, and a bare `stty` change from a child doesn't usually survive to a zsh prompt.
- **Extended keyboard modes.** You're in Apple Terminal (from `$TERM_PROGRAM`). It doesn't support the keyboard protocols that make Ctrl-combinations come out as escape codes, and zsh accepts both forms of arrow key.

**The theory that fits better:** one of `bin/deploy`'s children is still running in the foreground after the last output. If nothing is editing the line, the terminal just echoes what you type: arrows show as `^[[A` and backspace misbehaves. Ctrl-C kills that process and the shell comes back working. That is exactly "Ctrl-C once puts it right", with no mode involved.

The candidates are whatever runs last:
- for the cloud deploy, `1c images prune` or a wrangler process that's slow to exit;
- for dev, `1c dev refresh`, if something keeps node alive after it starts the services.

A related possibility: Wrangler runs `docker push` with the terminal on stdin and in its own session (`runDockerCmd`, `stdio: 'inherit'`). If a process like that outlived the deploy, it would steal keystrokes from the shell.

**This changes the planned fix.** The backstop in the ticket (save the settings with `stty -g`, restore them in the EXIT trap) wouldn't help in either case. It restores `stty` settings, and neither of these causes leaves any. Nor would a UAT based on raw mode prove the bug is fixed.

**Two quick checks from you would settle it:**
1. When it's broken, has your shell prompt come back, or is the cursor just sitting after the deploy's last line? And is that with `--env dev`, `--env production`, or both?
2. While it's broken, from a second terminal tab run:
   ```
   ps -o pid,pgid,tpgid,stat,command -t ttysNNN
   ```
   Use the broken tab's device, which `tty` prints in that tab before you deploy. Anything besides `-zsh` whose `pgid` equals `tpgid` is the process holding the terminal. Optionally, run `stty -g > /tmp/a` before the deploy and `stty -g | diff - /tmp/a` afterwards to rule the settings in or out.

Once we know which process it is, the fix is probably small: give that child `</dev/null`, or make it exit cleanly. The ticket's Fix and Test plan would then change to match. I haven't changed the ticket or any code yet.

#### Claude
The prompt does come back, so my lingering-foreground theory is wrong. But `^[[A` printed in caret notation at a zsh prompt is a strong clue. That's the terminal driver echoing raw input. zle switches echo off while it edits, so something must have switched the terminal back to normal mode after zsh drew its prompt. Something detached that exits later would do that, and the shell resets its mode when you press Ctrl-C, which fits. I'm looking for that late process.

I still can't tell which process it is from the code. The prune step only runs `docker` with stdin closed, and wrangler waits for every Docker child it starts. The process that resets the terminal is already dead by the time you see the broken prompt. So it has to be caught in the first few seconds after `bin/deploy` returns.

**What the symptom tells us:**
- The broken setting isn't a mode left switched on: it's the terminal put back to normal (echo on) while zsh is reading your line.
- That happens after `bin/deploy` has returned and zsh has drawn its prompt.
- It comes from a process that outlives `bin/deploy` with the terminal still attached. Most likely that's a node process exiting a moment later, because node puts the terminal back to its startup settings when it exits.

**This changes the fix.** The ticket's backstop (save the settings with `stty -g` and restore them in the EXIT trap) can't work, because the trap runs before the change happens. Neither would the planned UAT built on raw mode. The real fix is to find the survivor and make it exit before `bin/deploy` does, or start it without the terminal attached (`</dev/null`).

**To catch it**, please run this in one line, exactly as written:

```
T=$(basename $(tty)); bin/deploy --env production; (for i in {1..16}; do echo "--- $(date +%T.%N 2>/dev/null || date +%T)"; ps -o pid,ppid,pgid,stat,etime,command -t $T; sleep 0.25; done > /tmp/bug391-ps.txt 2>&1 &)
```

It records every process attached to this tab, every quarter-second for about 4 seconds after the deploy returns. Then press ↑ to confirm the terminal broke, and paste `/tmp/bug391-ps.txt`. Any line besides `-zsh`, `ps` and the loop's own shell is the culprit. Its `ppid` tells us who started it.

If you'd rather not do a full production deploy just for this, try `bin/deploy --dry-run --env production` first. If the terminal breaks there too, that would point at wrangler's bundling rather than the container build, push or prune.

I haven't changed the ticket or any code. Once we know the process, I'll rewrite the ticket's Likely causes, Fix and Test plan to match and propose the change.
