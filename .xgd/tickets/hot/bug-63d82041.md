## Symptom

During Charlie's Plumbing 2, the consultant put an ask on the plan panel asking for photos to use on the site. Three things went wrong:

1. **Only one file could be uploaded.** The ask asked for images, plural, but the picker takes a single file.
2. **The photos landed as background material, so the consultant couldn't use them.** Its `place_on_site` refused them.
3. **Neither the client nor the consultant could see how to turn them into site material.**

## Root cause

1. `plan-panel.js` ~L159 creates `<input type="file">` without `multiple` and uploads `file.files[0]` only.
2. `plan-panel.js` ~L108 uploads every ask attachment with a **hard-coded `role: 'reference'`**. `material.ts` ~L183 derives `republishable: role !== 'reference'`, and `place_on_site` refuses anything not republishable (`NotRepublishableError`, ~L845). So every file uploaded through the panel can never be placed, whatever the ask was for.
3. **The client:** a control exists but is buried. REQ-213 made "What it is for" editable in the Library item's detail pane (`library.js` RIGHTS_FIELDS, gated by `roleIsTheirs`; `reviseRole` in `material.ts` ~L2255 flips `republishable`). It's a select inside the rights record, and nothing on the panel or in the chat leads to it. **The consultant:** the library surface offers only `list_library`, `get_library_item` and `place_on_site`. There is no operation to change an item's role.

## Fix

1. **An ask says what its uploads are for.** When the consultant writes an upload ask, it sets the ask's intended role: `site` (photos for the site, logo) or `reference` (price lists, flyers, background reading). The panel uploads with that role instead of a constant. When the consultant doesn't set it, it defaults to `reference`, so nothing lands on the site's side unasked.
2. **Several files per ask.** An upload ask accepts several files when the ask allows it, which is the default for site-role image asks. All of them are recorded against the ask, and the change notice the consultant gets names how many arrived.
3. **The client can move an upload to the site in one obvious step.** A reference-role upload shows a "Use on the site" action where the client sees it: on the panel ask's answered row and on the Library row or detail. It changes the role through the existing `reviseRole` path, which keeps REQ-213's rule that only `uploaded` items qualify.
4. **The consultant can change an upload's role**, on the client's say-so. The library surface gets an operation to set an upload's role between `site` and `reference`, applying the same `reviseRole` gate: `uploaded` origin only, never captures or fetched material. Its description says a role reflects what the client wants the file used for, so the consultant changes it when the client asks, or confirms with the client first, and never decides on their behalf. The consultant tells the client in chat that it did.

## Added 2026-10-03: deleting material

**The client already has delete.** REQ-281 landed "Delete this from your Library" in the Library item's detail pane (`library.js` ~L150 and ~L931, `DELETE /api/material`). It archives the item, and a picture already placed stays on the site, because placement copied the bytes. Like "What it is for", it's only reachable by opening the item, so it's covered by fix 3's discoverability rule: wherever the client sees an upload (the answered ask on the panel, and the Library row), the actions on it are visible, and delete is one of them.

**The consultant gets delete too.** It's a library-surface operation over the same archive path the client's control uses (`DELETE /api/material`'s implementation, not a second mechanism), with these rules:
- **Only on the client's instruction, in this conversation.** The consultant never deletes material on its own judgement, for example to tidy duplicates. It may suggest deleting, and the client decides.
- **The result says what happened:** removed from the Library, and if the item was placed, that the page still shows it, since the site keeps its own copy. To take it off the page as well, the consultant edits the page.
- **The same scope as the client's control:** whatever REQ-281 lets the client delete, and nothing else.

Additional UATs:
- The consultant's delete operation archives an item, and the item disappears from `list_library`.
- Deleting a placed item leaves the page's asset in place, and the result says so.


## Added 2026-10-03: delete must look like a dangerous action

**Today it looks like a link.** `.builder-library__delete` (`builder.css` ~L1769) strips the button styling (`border: 0; background: none`), sets it at 0.85em, and underlines it in `--shell-danger` red. It reads as a hyperlink, not as an action that removes something.

**Wanted (operator):** a clear, dangerous-looking button.
- A real button with a **trash-can icon** and the word **Delete**, in the shell's danger colour (`--shell-danger`). It's filled or strongly outlined, with a hover and focus state, at normal control size, not caption size.
- **One style for delete everywhere it appears:** the Library detail pane, the Library row action, and the answered ask on the plan panel.
- The confirmation dialog's **Delete** button uses the same danger style, so the dangerous step looks dangerous at both points.
- The icon is decorative, so the button's accessible name stays "Delete this from your Library" (the existing `DELETE_LABEL`).

UAT: the delete control renders as a button carrying the danger class and a trash icon, not as a link-styled control, in each place it appears.



## As implemented (2026-10-03)

**Plan model (`plan-core.ts`, `plan-surface.json`).** An ask carries `upload_role` (`site` | `reference`, absent = `reference`) and `multiple` (absent = true only for a `site` ask). `set_ask` accepts both, and its description tells the consultant to set `upload_role: site` when asking for files to put on the site. `panelView` resolves both defaults for every upload-taking ask, so the panel reads them and never re-derives the rule. `answer_material` holds one uid (a string, as before) or several (a list). The plan reminder and the client-change notice name the count: "2 documents (uid, uid)".

**Panel (`plan-panel.js`).** The file picker is `multiple` when the ask is. Every picked file is uploaded with the ask's role and the open site (so a `site` upload is placed as it lands), and the ask is then answered once, citing all of them. An answered upload ask lists its files. Each file shows **Use on the site** (only for a reference upload, `origin: uploaded`, the same rule `reviseRole` enforces) and **Delete**. A file deleted since shows "Deleted from your Library". `GET /api/plan` and `POST /api/plan/ask` now return `materials`: the Library rows the answers cite, from `listMaterial`. `POST /api/plan/ask` checks that every cited uid is this business's.

**Library (`library.js`).** Each row has the same two actions, and pressing one doesn't open the row. The detail pane keeps its delete at the foot, now using the shared control.

**Shared control (`material-actions.js`, new).** The delete button, Use on the site, the delete confirmation dialog, and its sentences now live in one module that the pane, the row and the panel all mount. Delete is a real button with a trash-can SVG and the word "Delete" in `--shell-danger`, strongly outlined, filling on hover, at control size. Its accessible name stays "Delete this from your Library". The dialog's confirm button wears the same `builder-danger` class, filled.

**Consultant (`library-core.ts`, `library-surface.json` v4, `library.ts`).** A new `KeepLibrary` group is granted with the surface:
- `set_upload_role {item, role}` calls `reviseRole`. It is refused as `NOT_AN_UPLOAD` for fetched or captured material and as `ALREADY_ON_SITE` when narrowing a placed file. It does not place: placing stays `place_on_site`. Its description says the role is the client's decision, to be changed on their say-so, and that the consultant tells the client it did.
- `delete_library_item {item}` calls `archiveMaterial`, the same function behind `DELETE /api/material`, including the index forget seam. It returns `still_on_site` and a `note` saying a placed picture stays on its page and that edit-the-page is how to take it down. Its description says: only on the client's instruction in this conversation, never on its own judgement.
