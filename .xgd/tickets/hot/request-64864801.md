## What this builds

Move rendering from "already on disk" to **request-time inside `control-app`** — the
draft preview and edit channels rendered on demand via the Astro Cloudflare adapter,
replacing T1's static serving.

Phase 1 ticket **T5** of [[DOC-28]] §12. Design: [[DOC-8]] §4.1.

## Why last

This changes **where** the render runs, not **what** it produces. Everything above is
built and proven against a real rendered page first, so if the runtime move surfaces
problems they are isolated to this ticket rather than tangled with the editor's own
correctness.

## Contingency — read before starting

**This ticket presumes an answer to [[DOC-8]] §13 Q3**: does v1 of the builder run
against the file-backed store locally first, or move to D1? If v1 stays local, **T5 is
deferred, not dropped** — phase 1 is functionally complete at T4. Confirm the answer
before scheduling.

## Scope

- **Request-time render** of the draft preview and edit channels inside `control-app`,
  reading the draft definition.
- **One render implementation, not two.** The seam where the L1/module render path is
  shared between the build-time renderer and the adapter is the substance of this
  ticket ([[DOC-8]] §13 Q2). Two renderers would reintroduce exactly the drift the
  server-side-only decision exists to prevent.
- The heavy Node/Vite/Container-API compilation stays at **build time**; the Worker
  only ever runs the compiled result.
- **Publishing is unchanged** — published sites still render at build time and are
  served by `public-site`. This ticket touches the draft and edit channels only.
- Swap the iframe's source; **the display panel and toolbar must not change**
  ([[DOC-8]] §3.2 — a mode change swaps the source, it does not rebuild the pane).

## Non-goals

- **No change to published rendering or to `publish` semantics.**
- **No storage migration.** Moving the canonical store to D1 is [[DOC-12]] §7's phase 2
  and is its own work, even though this ticket is what makes it pressing.
- **No new editor capability.** If this ticket changes what the user can do, its scope
  has leaked.

## Acceptance criteria

1. The draft preview and edit channels are served by `control-app` at request time; no
   pre-rendered artifact on disk is required.
2. The rendered output is **identical** to what the build-time renderer produces for
   the same definition — verified by comparison, not by inspection.
3. There is **one** render implementation shared by the build-time path and the
   request-time path; adding an L1 axis requires changing it in exactly one place.
4. Published rendering and `publish` are unchanged, and `public-site` still serves the
   published channel from the build-time render.
5. The display panel, toolbar and mode switching are untouched — only the iframe's
   source URL changes.
6. Editing still works end-to-end (T3, T4) against request-time renders.
