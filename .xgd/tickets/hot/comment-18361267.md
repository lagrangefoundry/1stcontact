#### Claude
I've read the substrate. Here's what I found, and my position.

## The specific thing you asked for already exists

`account-chrome` ([[REQ-200]], `packages/framework/src/modules/account-chrome/`) is a shipped behaviour module that is *exactly* your flow: a `signIn` control opens a `dialog` slot holding an `email` input and a `submit`; on submit it POSTs the address and replaces the panel with `sentMessage` — defaulting to *"Check your email for a sign-in link."* It never reads the response, deliberately, so a known and an unknown address are indistinguishable ([[REQ-134]]).

So putting a sign-in modal on 1st Contact is a **site-definition** job — instantiate `account-chrome`, fill its four slots with L1 (there's an L2 preset at `l2/account-chrome.ts` to start from) — not an L1 extension. Worth separating that from this ticket.

## But the general question is real, and the code says so

`account-chrome/styles.css` ships this, and justifies it in a comment:

```css
.account-chrome[data-account-chrome-enhanced] .account-chrome__dialog {
  position: fixed; inset: 0; z-index: 2147483000;
  display: flex; align-items: center; justify-content: center;
  background: rgba(0, 0, 0, 0.5);
}
```

> *"Covering the page and centring on it is behavioural — a modal that did not would not be one — and no L1 axis can express `position: fixed`."*

DOC-25 §10.2 says a conforming behavior ships **zero CSS beyond §10.3 invariants**. A 50%-black backdrop no site can vary is not an obligation-pinned invariant, it's taste. That comment is an honest admission of a **substrate gap**, not a principled carve-out — and it's the strongest in-repo evidence that overlay presentation belongs in L1.

## Decomposing a modal

Applying DOC-25 §10.3's own line — *L1 owns everything the reference can legitimately vary; the module owns what an obligation pins*:

| part | today | belongs to |
|---|---|---|
| panel look (fill, radius, padding, width, type) | L1 already | **L1** — nothing needed |
| overlay presentation (fixed, cover, centre, backdrop, entry motion) | module CSS, unvariable | **L1** — this is the gap |
| open/close + what triggers it | module `client.js` + `data-*` | **split** — L1 says *what opens what*, renderer owns *how* |
| dialog obligations (`role`, focus trap, Escape, return-focus, scroll lock, inert background) | **mostly absent** | **renderer**, not the author |
| step transition ("swap for the message") | module, hardcoded per module | **module** — it's a server round-trip |

That fourth row is worth flagging on its own: today's dialog has `aria-expanded` on the opener and `.focus()` on the field, and that's all. No `role="dialog"`, no Escape, no focus trap, no return-focus, no scroll lock. It's a disclosure styled as an overlay. That's a defect in REQ-200 regardless of what we decide here — and it's the argument *against* letting every future modal be hand-rolled per module.

## My recommendation

**Two small L1 additions, both roles rather than node kinds** — following the `link`/`reveal` precedent exactly:

1. **`overlay` on a node** — "this subtree presents above the page rather than in flow." Carries only what a reference can legitimately vary (backdrop paint via existing surface axes, panel placement via existing geometry). The renderer emits `<dialog>` and owns everything the dialog contract obliges.
2. **`action` alongside `link`** — a *closed* verb set, initially `{ opens: <id> }` / `{ closes: <id> }`. Not an event system: an enumeration of what one node may do to another's disclosure state. Mutually exclusive with `link`, enforced by `.strict()` the way `control` already can't carry `link`.

The precedent for putting obligations in L1 rather than a module is already there: `l1LinkSchema` pins `rel="noopener noreferrer"` whenever `newTab` is set — *"there is deliberately no way to ask for `_blank` without its `rel`"* — and `href` goes through `isSafeUrl`. `l1FocusRingSchema` exists because DOC-24 holds focus above taste. The renderer being the sole sink is how L1 already carries non-negotiables.

The `reveal` doc comment argues this case for us almost verbatim: motion became an L1 *adjective* rather than a module partly because *"putting it in a module would make animated content unfoldable by construction — `fold` maps captured node axes onto L1 node axes and never authors a module."* **A captured reference site with a modal has the same problem.** If modal-ness only exists as a module, reproduction can never fold one.

**What stays in a module:** anything with a server round-trip or a policy obligation. The sign-in flow's "one message whatever the server answers" is REQ-134 policy and can never be an L1 axis. What changes for `account-chrome` is that its `dialog` slot's overlay presentation comes from L1, and it deletes the stylesheet block above.

**What I'd explicitly not build:** a general L1 state machine for multi-step flows. Every step transition anyone has actually needed is "swap when the behaviour says so", and the behaviour is always the thing that knows the submit succeeded. Both `contact-form` and `account-chrome` already reinvent this ad-hoc (`data-account-chrome='signed-out'` + module CSS hiding the other states). The cheaper, better-motivated move is to generalise *that*: module-declared named states, framework-owned visibility switching, one rule the framework emits instead of each module writing its own.

## Open questions I'd want your answer on

1. **Is `opens`/`closes` enough, or does `action` need to be extensible from day one?** A closed two-verb set is easy to validate and hard to abuse; but the next ask (a tab strip, an accordion, a "show more") is the same shape and would want in.
2. **Does the trigger need to reach across a module boundary?** Your case is trigger-in-header, panel-at-page-level. `action.opens: <id>` targets a node id, so it does — but that means an L1 node can reference a node inside a module's slot subtree, which nothing currently validates.
3. **Non-JS baseline.** `account-chrome` renders the form *open* and script folds it away, so script only ever subtracts. Should an L1 `overlay` inherit that discipline (render in flow, become an overlay on enhancement), or is a `<dialog>` that simply isn't reachable without JS acceptable?
4. **Is a modal a `<dialog>` or a positioned box?** `<dialog>` gets the platform's focus trap, Escape and inertness free, but constrains what the backdrop can be. Hand-rolling gets full paint control and owes all of it.

## What L1 gained

**`dialog`** — a node-level role on `box` / `container`. Carries only what a reference can legitimately vary: `backdrop` (colour + opacity), `placement` (center/top/bottom), `dismissOnEscape`, `dismissOnBackdrop`, `ariaLabel`. The panel's look is its ordinary surface and sizing axes. Both dismissals default **on**, so a trap has to be asked for.

**`action`** — a node-level role on `box` / `container` / `text`. A closed set of two verbs, `opens` / `closes`, naming a panel's `id`. Not an event system: a document can change which of its own declared panels is open, and there is no third thing it can say. Mutually exclusive with `link`.

Four structural rules in `validate.ts`: a panel must declare an `id`; an action names exactly one verb; what it names must exist **and carry `dialog`**; no node carries both `link` and `action`.

## What the renderer owns

Action nodes **retag** to `<button type="button">` — REQ-106's discipline, so the class, paint axes and focus ring stay put. A panel is **wrapped** in a covering shell (the one place a wrap is the faithful shape: the panel keeps focus and every axis, and covering the page is a statement the panel's own element can't make).

One vetted script, emitted only when a document carries a modal and byte-identical across sites — I assert that in a UAT by rendering two different modals and comparing the scripts. It owns focus-in, focus-return, the Tab trap, Escape, the scrim click, and the scroll lock.

**Every overlay rule is gated on a marker only that script sets.** No script → the panel is an ordinary in-flow, open part of the page. Script only ever subtracts, which is `account-chrome`'s discipline generalised. The edit render ships none of it.

One thing that doesn't compose, so the emitter declines it: **`reveal` on a panel is not emitted**. A closed panel never intersects, so the entrance could never fire and REQ-100's pre-state rule would leave it at `opacity: 0` inside a modal that opens onto nothing.

## Two things I left out, deliberately

- **No multi-step vocabulary.** "Swap the form for the message" is always driven by something that knows the submit succeeded — a module. `account-chrome`'s "one message whatever the server answers" is REQ-134 policy and shouldn't be an L1 axis.

## Can the AI implement your original ask?

**The shape, yes. The sign-in semantics, no — and that part was already true before this change.**

I probed it: a behaviour module mounts cleanly *inside* an L1 dialog. This validates and renders correctly:

```
text  "Sign in"      action: { opens: 'signin' }
container #signin    dialog: { backdrop: …, ariaLabel: 'Sign in' }
  └ slot             behavior: contact-form
  └ text "Close"     action: { closes: 'signin' }
```

The module's markup lands inside the panel, inside the shell. So all four beats of your ask are reachable: link top-right → modal opens → real field + Continue that submits → `contact-form`'s success message replaces the panel's contents in place.

What the AI **cannot** do is author a bare text field. `control` nodes only paint elements a *module* declared — there is no free-standing `<input>` in L1. So the field always comes from a mounted component, which means today it's `contact-form` (lead capture), not a sign-in.

For a genuine sign-in — magic link, "if you are already a member", the rule that a known and unknown address must be indistinguishable — that's `account-chrome`/REQ-134, and it works today. But it **cannot be re-housed in an L1 dialog**: its Sign In trigger is a module `control`, and `control` deliberately cannot carry `action`. So account-chrome keeps painting its own overlay, exactly as I flagged in the ticket's out-of-scope section.

## Is it documented?

Partially, and the gap is the important bit.

- `REF-l1` — every field, every shape, all four rules, projected from the declarations. ✓
- `DOC-48 §14` — when a modal is right and when it isn't. ✓

Also missing: that sign-in specifically is `account-chrome`'s job, not L1's — so an AI reading DOC-48 §14's "signing in is the canonical case" could reasonably try to build one out of L1 and hit the `control` wall.

That's a real gap in §7 of this ticket's own scope. It's a document change, so no branch needed — shall I close it now? It's about three paragraphs in DOC-48 §14: what can go inside a modal, and the one flow that is a module's rather than L1's.
