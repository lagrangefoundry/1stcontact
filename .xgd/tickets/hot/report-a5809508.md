All three tickets in this batch now have passing tests. I only changed tests and one shared test helper; no production code was touched. The AC-1400 cause is unconfirmed, though: the test was already passing here before my change, so I never reproduced its failure.

**AC-2227 (import guard)** — new file `tests/reconciliation-import-guard.workers.test.ts`, 3/3 passing. It runs inside workerd against the real D1 and R2, through the Worker's own `/api/import` and the real `pushSite`:
- After one builder change, an import gets a 409 that names the slug, a change count of 1, and a separate `force` field.
- The stored definition and every page are byte-identical after the refusal.
- `force` values of `false`, `'true'` and `1` are still refused; only `force: true` lands, and the stored page then matches the payload.
- A fresh slug lands, and so does a slug that has only ever been imported to.
- An ordinary push sends no `force` key at all; asking for force sends `force: true`.

**AC-2228 (`1c reset`)** — new file `tests/reconciliation-1c-reset-command.test.ts`, 7/7 passing. The command finds the repo root from where its own source file sits, so running it in-process would have deleted this worktree's real `.wrangler`. Instead, the tests copy the CLI source into a temp repo (dependencies linked) and run the real `tools/generate/bin/1c.mjs` there. They check exit codes, printed output and what is left on disk:
- The preview shows the control-app directory's path, file count and size, deletes nothing, and exits 0.
- `--yes` removes only the control-app store; `--include-public` removes the public-site store too.
- `storage/` is untouched under every flag.
- A listening port is refused with nothing deleted; `0`, `-5` and `eighty` are rejected as usage errors.
- A missing store is reported as already empty and exits 0.
- Running from a subdirectory gives identical output.

The suite takes about 18 seconds because each case starts the real binary.

**AC-1400** — `test_UAT_AC1400_…` passes on its own and alongside the two other suites that use the same helpers, both before and after my change. Following the planner's guidance, I hardened `tests/support/local-d1.ts` without changing its signatures:
- wrangler's stdout and stderr now go into the thrown error instead of being discarded, so a setup failure names its cause.
- The `wrangler d1 … --local` subprocesses are serialised across vitest workers with a lock directory under `.wrangler/`; a lock older than two minutes is treated as stale and removed.
- A run that fails with "database is locked" is retried up to five times.

**Environment limits you should know about:**
- In the combined run, AC965 and `test_UAT_FC_REQ-115_control_app_fronts_the_builder_same_origin` time out. wrangler tries to reach `api.cloudflare.com`, which this sandbox blocks. They failed the same way before my helper change, and the planner's quality report shows them passing in the real run. AC964 and AC975 in that run pass.
- eslint isn't installed in the repo and couldn't be fetched (registry blocked by the sandbox), so lint did not run.
- `tsc` with the base config reports only missing workers types (`cloudflare:test`, `Fetcher`, `D1Database`). The existing workers tests and `local-d1.ts` already show these same errors, so they aren't new.

I didn't edit any tickets: both ACs match what the code does. Nothing is committed; I've left the changes in the working tree for the outer workflow.
