## Story

**As a** business owner working on my site in the builder,
**I want** to hand the platform a file by dropping it into the conversation or onto my Library and
answering the one question it asks — *is this for the site, or just for you to read?* —
**so that** what I meant by giving it to you is what actually happens to it: the photograph I meant
to publish is on my site the moment I let go of it, and the document I marked private can never
appear there.

## Description

Before this there was no way to put a byte into the system from the browser at all. The image
picker chooses among assets a site already holds; it is a field editor, not a way in. This is the
way in, and it is the same interaction from both moments it is wanted: the conversational one (the
assistant asks *"do you have a logo?"* and the answer is to drop one into the chat) and the
deliberate one (material that is not part of the current conversation, dropped onto the Library).

**The one question is about the file's role, not its type.** The kind of thing a file is can be
read off the bytes ([[CAP-108]]); what it is *for* cannot be read off anything. The case that
decides it: a JPEG may be a hero photograph destined for the site, or a screenshot of a competitor
the assistant should look at and must never publish — identical bytes, identical type, opposite
rights. So the client is asked the one thing only they know, and never asked the legal question
([[DOC-38]] §10.1 refuses *"do you own this?"* because clients frequently do not know the answer).

**In scope**

- One question surface serving both entry points, raised by dragging a file onto either, offering
  exactly two answers with the copy that makes each one's consequence plain — including that
  reading material stays off the site.
- Every answer reachable without dragging, because drag is a gesture some people cannot perform and
  some devices do not offer.
- **Nothing created without an answer.** A file that lands on the surface but on neither answer
  creates nothing; the question stays up and says what is missing. Both possible defaults are
  silently wrong — one publishes what the client marked private, the other withholds the photograph
  they meant to publish.
- **The answer narrows the rights, never widens them.** An answer outside the two offered is
  refused rather than coerced; a file arriving with no answer keeps the rights its provenance
  already decided, so entry points that predate the question behave exactly as they did.
- **"Put it on the site" means the bytes are on the site.** A file offered for the site while a
  site is open is placed in that site's asset library immediately, through the existing
  republishability gate ([[CAP-108]] AC-1547) — which the reading answer is now mechanically
  incapable of passing. Placement copies the bytes across the private/public boundary rather than
  pointing across it, picks a free name rather than overwriting an asset already live on the site,
  and reports a placement failure alongside a kept file rather than as an upload that did not
  arrive.
- **A conversation-route drop is the client's own turn in the transcript**, reporting what actually
  happened including the parts that went wrong. A Library-route drop is not, because it puts no
  line in a conversation it was not part of.

**Out of scope**

- The ingestion pipeline itself — storing the bytes, classifying, describing, indexing — which is
  [[CAP-108]]'s ([[STORY-132]], [[STORY-133]]). This story owns the surface and the role question;
  ingestion owns what happens to the bytes after the answer.
- The Library's read surface — the list, the detail pane, the description correction — which is
  [[STORY-134]].
- Retrieving material on the client's behalf, and capture; both create the same records and appear
  in the same list, but neither is uploaded here.
- Registering a placed file in the site's asset *registry*, which remains the asset picker's own
  business. Placement puts the bytes in the site's asset library and no more.

## Technical Context

- The role question is a field on the material record, declared beside the rights block it narrows
  ([[CAP-106]], plan item 11) rather than as a parallel mechanism, because it is not derivable
  from republishability: a capture of the client's own previous site is republishable *and* plainly
  reference material.
- Placement stands on [[CAP-108]]'s existing refusal ([[AC-1547]]) — this story is that refusal's
  first real caller. The refusal itself remains [[CAP-108]]'s criterion; what this story asserts is
  that the reading answer produces material the refusal must reject.
- Placement depends on bytes being readable back through the record that owns them, which is
  [[CAP-106]]'s corrected blob addressing (plan item 12). Before that correction the success path
  of placement had never run.
- The surface follows the workspace's single site selector rather than owning one: the toolbar is
  the one place a site is chosen, and a second control that could disagree with it is worse than no
  control ([[CAP-85]]).

### Scope boundary recorded, not an omission

REQ-161 states that "either route fires the delta on the next turn ([[DOC-39]] §6.4), which is what
tells the AI the material arrived." No delta channel exists: the intent's own dialogue records that
DOC-39 §6.4 is design-only, and the reconciliation plan assigns the delta and session priming to
REQ-160. The arrival guarantee that *is* provable here is [[CAP-108]]'s — the material is offered to
search once and is findable the moment the request returns ([[AC-1540]]). No acceptance criterion is
written for the delta, because nothing in this bundle implements one. This is a scope boundary, not
a contradiction between intent and code.

## Reconciliation Decisions

- **A drag carrying anything other than files never raises the question** (decided at
  reconciliation, 2026-09-03): REQ-161 is silent on what a drag has to be carrying. The landed code
  raises the surface only for a file drag, so dragging selected text or a page element across the
  builder does not interrupt the client with a question about a file they are not offering.
  Formalized as [[AC-1576]] because the alternative — a question raised by every drag — is a
  visible defect that no other criterion would catch.

- **Dismissing the question creates nothing and leaves nothing behind** (decided at reconciliation,
  2026-09-03): REQ-161 resolves the ambiguous drop as *"prompt, never default"* but does not say
  how a client who changed their mind gets out. The landed code closes on Cancel or Escape without
  creating anything. Formalized as [[AC-1577]] because a surface that keeps asking must have an
  answer that is "neither" — otherwise "keep asking" is a trap rather than a prompt.

- **Every file in one drop becomes its own record and its own report** (decided at reconciliation,
  2026-09-03): REQ-161 speaks throughout of *a* file. The landed code accepts a multi-file drop or
  selection and takes each file through the whole path in turn, so three files produce three
  records and, on the conversation route, three reports in the order they were given. Formalized as
  [[AC-1578]] because the client's expectation on dropping a folder's worth of photographs is
  exactly this, and nothing else in the matrix asserts it.

- **After either route the new material is in the Library without a reload** (decided at
  reconciliation, 2026-09-03): REQ-161 says a Library-route drop puts no line in the conversation
  but does not say what it *does* show. The landed code re-reads the list from the origin after
  every upload, from either entry point. Formalized as [[AC-1587]] because otherwise the deliberate
  path has no
  visible consequence at all — the file would be stored and the screen unchanged — and because the
  list is re-read rather than patched from what the upload returned, so what the client sees is
  what was actually recorded.
