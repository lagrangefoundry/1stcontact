# probes/values-diff: the oracle's measured-height ladder ignores `segments`, and 22 of 59 `arrangement` comparisons are skipped without being counted

Filed by the reproduction console, **iteration 9** of `repro-gigabytealchemy-ai`
against `storage/references/gigabytealchemy.ai/index`. Two independent defects in
the **instrument**, both of which distort what this round's `gate.json` says
about the reproduction. Listed with the one that changes a verdict first.

Companion to the round's gap ticket
(`recovery-padding-track-drops-its-segments`). **Issue 1 below must be fixed
before that ticket's numbers can be read**, because it inflates the very
overhangs that ticket is measured by.

---

## Issue 1 — `measuredAt` lerps the oracle's height ladder through a `snap` window, so the probe models content the renderer never paints

**`defect_class: instrument-asymmetric`** — inside one evaluation the surface's
height is resolved by a segment-aware cascade (`evalScalarTrack`, `evalGeometry`)
and the content's height by a segment-blind one (`measuredAt`), so the overhang
the probe reports between two ladder widths is partly its own arithmetic.

### The code

`tools/generate/src/l1/probes.ts:412-424`:

```ts
function measuredAt(track: Array<{ at: number; height: number }>, width: number): number | undefined {
  if (!track.length) return undefined
  if (width <= track[0].at) return track[0].height
  for (let i = 0; i < track.length - 1; i++) {
    const a = track[i]
    const b = track[i + 1]
    if (width >= a.at && width < b.at) {
      const t = b.at === a.at ? 0 : (width - a.at) / (b.at - a.at)
      return lerp(a.height, b.height, t)
    }
  }
  return track[track.length - 1].height
}
```

There is no `segments` in that signature and no `snap` branch in that loop. Its
own doc comment, three lines above, claims otherwise:

> *"Resolve a measured track at `width`, with **the renderer's own cascade**: hold
> the first measurement below the ladder, interpolate within a segment, hold the
> last above it. **The same rule {@link evalGeometry} applies to position**,
> applied to the height that travels with it"*

It is not the same rule. The other two resolvers in the same file both branch:

| resolver | line | honours `segments` |
|---|---|---|
| `evalGeometry` | `probes.ts:287` — `const seg = geo.segments?.[i] ?? 'interpolate'` … `if (seg === 'snap')` | **yes** |
| `evalScalarTrack` | `probes.ts:346` — `const seg = track.segments?.[i] ?? 'interpolate'` … `if (seg === 'snap') return a.value` | **yes** |
| `measuredAt` | `probes.ts:412` | **no — unconditional `lerp`** |

`measuredAt` is reached from `takeMeasured` (`probes.ts:427`), whose result is
what `box.height` becomes for every text leaf at `contentScale === 1`
(`probes.ts:875-889`: `grown = measured * 1`, `box.height = grown ?? natural`).

### The consequence, measured

`repro-gigabytealchemy-ai`'s L1 marks the 375→768 window `snap` on every one of
its 69 geometry tracks, and the renderer honours it — the served
`home.html` pins `.l1-64 { width: 233.46px }` as a literal in
`@media (min-width: 375px)` and only adds `white-space: nowrap` from 768. So at
506px and 637px a browser lays those runs out exactly as it does at 375px.

The probe does not. From `1c l1-gate --ref storage/references/gigabytealchemy.ai/index --json`
(run this round, current tree), the `escape` finding boxes at
`0.1.0.0.3.0.2.1`:

- at **506px**: `{"x":85.55,"y":3957.583,"width":233.46,"height":40}`
- at **637px**: `{"x":85.55,"y":3861.667,"width":233.46,"height":32}`

Same run. Same box width, to the hundredth. **Two different heights, and neither
is a whole number of its own 24px lines.** Both are `measuredAt`'s lerp of the
oracle, exactly — from `multistate.json`, `'Practical tools for modern software
development'` is `elements[38]` and measures `h=72 @320`, `h=48 @375`,
`h=24 @768` (3 lines, 2 lines, then 1 line once `nowrap` starts):

- `lerp(48, 24, (506−375)/393) = 48 − 24·0.33333 = ` **40.00** ✓ matches
- `lerp(48, 24, (637−375)/393) = 48 − 24·0.66667 = ` **32.00** ✓ matches

The browser paints 48 at both, because the window snaps. Across the seven wrapped
runs inside `card-5` the under-measurement is not marginal:

|---|---|---|---|---|---|---|
| `Designed for developers building AI-enhanced workflows` | 48 | 24 | 40.00 | 32.00 | 8.00 | 16.00 |
| `Open source and community-driven` | 48 | 24 | 40.00 | 32.00 | 8.00 | 16.00 |

| **total** | | | | | **96.00px** | **192.00px** |

Every `probe h@637` in that column is confirmed against the live finding boxes:
`XGD` 53.333333, `Coming soon` 34.666667, the three bullet texts 32 — the probe's
own output, to six decimal places.

Against that under-measured content, `card-5`'s own evaluated box is
`height: 500` at 506px and `height: 412` at 637px. **That is the whole
`structural-failure` verdict**: `gate.json` reports 20 `escape` findings, all
against `card-5`, at 506px and 637px only, up to *"96px below its bottom edge"* —
overhangs computed against a content column the evaluator has shortened by up to
192px. The magnitudes are not trustworthy and neither is the finding count.

**A further tell that this is the ruler and not the page:** the eight other
off-sample widths — 338, 357, 853, 939, 1109, 1195, 1333, 1387 — are all clean. 338
and 357 sit inside the 320→375 window, which is `interpolate`; every off-sample
width inside the one `snap` window fails. A defect in the reproduction would not
care which segment kind it was sampled in.

### Which stored reference exhibits it

`storage/references/gigabytealchemy.ai/index`. **One bundle** — but the defect is
in the resolver, not the page: any document with a `snap` segment and a run whose
measured height differs across it hits it, and `holdAcrossReflowWindows`
(`fold.ts:1684`) exists precisely because real pages reflow, so the population is
"every reproduction with a reflow window".

### Proposed change

Give `measuredAt` the node's `segments` and add the `snap` branch the two
neighbouring resolvers already have:

```ts
function measuredAt(track, width, segments?: L1Segment[]): number | undefined {
  …
  if (width >= a.at && width < b.at) {
    if ((segments?.[i] ?? 'interpolate') === 'snap') return a.height
    …
  }
}
```

The caller has it: `takeMeasured(ctx, node, width)` is called from the `case
'text'` arm where `node` is in scope, so `geometryOf(node)?.segments` is one
expression away. Index alignment holds because the measured track's keyframes are
built per captured width from the same ladder (`probes.ts:390-400`) — **assert it
rather than assume it**, since the measured track skips a width the oracle did
not measure the run at, and a mis-indexed segment array would be worse than none.
Then fix the doc comment so it describes what the function does.

**Expect the delta and finding counts to MOVE, and expect `escape` counts to
fall.** That is the instrument becoming right, not the page changing: nothing
about the reproduction is different.

## Issue 2 — `arrangement` is skipped on 22 of 59 pairs, and the skip reaches no tally

**`defect_class: instrument-blind`** — a `CRITICAL`-tier axis was compared on 37
of 59 pairs and the other 22 were neither compared nor counted, so `gate.json`
reports `unmeasuredAxes: []` and a headline of "0 axes" over 22 measurements that
did not happen.

### The code

`tools/generate/src/cli/capture/values-diff.ts:2708`:

```ts
if (exp.arrangement && act.arrangement && exp.arrangement !== act.arrangement) {
```

A falsy value on **either** side takes the whole comparison out, silently. There
is no `push` to `unmeasuredAxes`, no `notComparableAxes` row, and nothing on the
`suppressed` counter (`values-diff.json` this round: `"suppressed": 0`).

### Why it fires, and how often

`arrangement` is assigned at capture by sorting a side's **own** element list
top-to-bottom and relating each element to the one before it
(`extract.ts:1817-1824`, `assignArrangement`), and `relate`
(`extract.ts:1806-1814`) returns `null` for a pair that is neither a `row` nor a
`stack`. The two sides do not sort the same list — this round
`values-diff.json` says `"elementCounts": {"expected": 59, "actual": 65}`, the six
extra reproduction entries being band containers whose `text` is the
concatenation of their descendants' copy (e.g.
`'Gigabyte AlchemyIntentional SoftwareTools for clarity, prese…'`). So the two
sides' predecessors differ and the two `arrangement` values are not the same
measurement. `values-diff.ts:2691-2707` already documents this asymmetry in as
many words; what it does not do is count the consequence.

Paired the 59 expected elements against the actual manifest by text (all 59
pair), from
`iteration-9/diff/{expected,actual}-manifest.json`:

| | pairs |
|---|---|
| both sides non-null, agree | 37 |
| both sides non-null, differ | **0** |
| reference `null`, reproduction non-null → **skipped in silence** | **22** |
| reference non-null, reproduction `null` | 0 |

The 22 include the page's first element and every run that opens a band —
`'Gigabyte Alchemy'` (ref `null`, ours `row`), `'Intentional Software'` (`null` /
`stack`), `'A Different Approach'`, `'Our Mission'`, `'What We're Building'`,
`'The Alchemy'`, `'Get in touch'`, `'© Gigabyte Alchemy 2025'`, `'LinkedIn'`,
`'GitHub'`, and the three `'✓'` bullets — 37% of the run population, on the axis
whose tier table (`values-diff.ts:1207`) reads `arrangement: 'CRITICAL'`.

Meanwhile `gate.json` reports `"unmeasuredAxes": []` and the round's headline
unmeasured count is **1** (one probe). Per [[REQ-277]] an unmeasured axis is not
a clean one; these 22 are invisible in both `deltas` and the unmeasured set.

### Which stored reference exhibits it

`storage/references/gigabytealchemy.ai/index`. The mechanism is the
element-count asymmetry every reproduction has (the reproduction emits band
containers; the reference does not), so it is not bundle-specific — but the
**count** quoted above is from this bundle only.

### Proposed change

Emit a `notComparableAxes` row when the guard drops a pair, aggregated per side
rather than per element — the shape `unreadableTransformAxes`
(`values-diff.ts:3694-3709`) and BUG-153's `bandPaintActual` already use, and for
the same stated reason: *"an exclusion nobody can see is indistinguishable from a
measurement nobody made"*. One row, with the count and the reason (*"the
reference read no arrangement for N of M pairs because the two sides sort
different element lists"*), so the gate's unmeasured tally stops reading zero.
The second guard in the same block — `ownGeometryAgrees` — deserves the same
treatment; it happened not to fire on this page (0 pairs differed) and will.

  `elementCounts: {'expected': 59, 'actual': 65}`, `unmeasuredAxes: []`,
  `notComparableAxes axes: ['contentAnchor']`.

  `notComparableAxes` (or `unmeasuredAxes`) carrying that count and its reason,
  so the gate's unmeasured headline counts 22 skipped run comparisons instead of
  reporting `0 axes`.
