## Symptom

The platform operator opens another customer's business from the Console tab's **Open** control (REQ-367 — "entering" a business, e.g. faelanwesthead / faelan.com). They then leave it — the banner's way back, or the business switcher, or a reload at `/` — and go to their own business. The Site tab keeps showing the entered customer's site (faelan.com) even though every other surface has moved to the operator's own business.

## Root cause

The operator's way back lands on their first own business (1st Contact itself), whose only page is the `/account` portal — and `/api/sites` deliberately lists only kind `site`, so that business has **no sites**. `selectBusiness` therefore calls `panel.setSite(null)`, and the display panel's `show()` computes an empty URL for a null site and `navigate()` wrote it into the iframe as `src=""`. Browsers do not unload an iframe for an empty `src`, so the frame went on showing the document it already held — the entered customer's site. A reload reproduces it too: `restore()` reopens the remembered (entered) site first, then the switch to the site-less business writes `src=""` over it.

## Fix

`packages`-free, one spot: `apps/control-app/src/builder/panel.js` `navigate()`. When the pane has nothing to show (empty URL), the frame is pointed at `about:blank`, so it genuinely unloads. The panel's own bookkeeping (`rec.src`, `getSrc()`, the `src` event) still reads `''` for "nothing shown", so no consumer changes.

User-visible behaviour: after switching to a business with no sites, the Site tab's preview is blank — never a previously shown (possibly another customer's) site.

## Test plan

`tests/test_UAT_FC_BUG-207_leaving_an_entered_business_clears_the_preview.test.ts` (jsdom, real `mountBuilder` + real display panel, asserting on the shown frame's `src` attribute — what the browser actually loads):

- **the way back to a site-less business blanks the preview** — enter a business that has a site, take the banner's way back to the operator's own business with no sites: the shown frame is `about:blank`, not the entered site, while `panel.getSrc()` still reads `''`.

- **switching to a site-less business blanks the preview** — the switcher route: own business with a site, then the site-less one: frame is `about:blank`.

Both fail without the fix (frame left at `src=""`). Regression scope run green: REQ-367 chrome suite, BUG-79, REQ-391, BUG-131, REQ-248, REQ-378, builder workspace chrome (48 tests).

## Reopened 2026-10-17: the empty-src fix did not cover the reported case

Operator report: the bug is **not specific to impersonation**. Selecting "Charlie's plumbing - 3" after visiting 1st Contact left **1st Contact's site** in the preview, with Charlie's plumbing selected everywhere else. A browser refresh showed the correct page. Both businesses have sites, so the `src=""` path above is not the cause of this report (that fix stays: it is still correct for a business with no sites).

### Root cause (switch between two businesses that both have sites)

A site switch points the shown frame at the new site's URL. Before that navigation commits, the frame still holds the old document. `selectBusiness` → `showSite` → `followDraft(newSite)` opens the draft feed for the new site ([[BUG-192]]), and its opening `ready` frame runs `catchUp`. Two things then go wrong:

1. `shownAt()` reads the `draft-at` count from the frame's *current* navigation entry, which is still the **old site's document**. It compares the old site's count to the new site's count, and when the old one is lower it decides the frame is behind.
2. `panel.reloadDocument()` calls `contentWindow.location.reload()` on that same old window. A reload from the old document cancels the pending navigation to the new site and reloads the old site. The panel's bookkeeping (`rec.src`) already says the new site, so nothing ever re-points the frame. The old site stays on screen until a full page refresh.

This explains every part of the report: it needs only a switch, a refresh fixes it, and it depends on which site's change count is higher (so it is intermittent across pairs).

### Fix

`apps/control-app/src/builder/panel.js` only:
- `reloadDocument()` does not reload a frame that has not finished loading what it was last pointed at. A frame mid-navigation has no current document worth reloading in place, so it is re-pointed at its own `src` instead (`navigate(current, current.src)`). It never reloads the document being left.
- The panel exposes `loading` (the shown frame has not yet loaded what it was last pointed at). The builder's `shownAt()` (`app.js`) treats a loading frame as "cannot say which count it holds" (`null`), so the old document's count is never read as the new site's. A `ready` frame then does not reload (as for any unknown frame), and a reported write re-points the loading frame at its own URL.

User-visible behaviour: after switching business or site, the preview shows the newly selected site, never the previously shown one, without a browser refresh.

### Test plan (addition)

`tests/test_UAT_FC_BUG-207_switching_between_sites_shows_the_new_site.test.ts` (jsdom, real `mountBuilder` + real panel, draft feed injected as in BUG-192):
- **a feed `ready` arriving mid-switch does not reload the old site**: switch from a business whose site is shown to another business with a site. While the frame is still loading, the new site's feed reports a higher count than the old document states. Expected: the old window's `location.reload` is not called, and the shown frame points at the new site.
- **a write reported mid-switch re-points the frame at the new site**: the same setup with a `draft` frame. Expected: the frame is re-navigated to the new site's URL, never reloaded in place.

Regression scope: BUG-192 panel suite plus the existing BUG-207/REQ-367/BUG-79/REQ-391 builder suites.
