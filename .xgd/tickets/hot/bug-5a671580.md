## Source

The consultant's report from production, PLATFORM_ISSUE-12, raised while updating a site's three purchase pages to the current `checkout` component (version 1). The client was told the two buttons "aren't picking up the site's lettering".

## Problems

1. **The checkout's own controls can't be styled as buttons.** The `retry` control (checkout mode) and the `request-cancel` control (status mode) were placed in the module's `page` slot inside a box with `component: button.secondary`, each control with `role: caption`. `describe_page` flags both as broken: "unstyled: font, size". A control won't accept a `component`, and typing font and size axes on it is off-system. Two builder rounds couldn't clear it, so on the live page the buttons may draw in the browser's default form-control lettering.
2. **A component colour reported as hand-written.** On the same status page, a 'Back to the shop' text with `component: button.secondary` and colour `{ref: text}` is flagged inconsistent ("#2a2224 written by hand — it is the palette's 'text'"). The flag stays when the colour axis is removed, so it comes from the component's own resolved colour, not from anything the page wrote.
3. **The cancelled page's back link takes no height.** On a page in `cancelled` mode, the slot section holding the `back` field "takes no height" at every width in the draft render, so the way back to the shop may not show.

## Expected behaviour

1. **A control inside a component box takes that component's type** (family, size, weight, letter spacing) and its role's settings, by inheritance, or a control accepts `component` itself. `describe_page` and the layout check then report no "unstyled" finding, and the rendered control's computed font matches the site's button style.
2. **A colour that comes from a design component** is never reported as written by hand.
3. **The `cancelled` page's back field draws** with the size of its content at every width, in the draft and the published render, so visitors always see the way back to the shop.

## Test plan

UATs `test_UAT_FC_BUG-<n>_*`, through the real renderer and `describe_page`:
- a checkout-mode page with `box{component: button.secondary} > control{retry, role: caption}`: no "unstyled" attention, and in a real browser the control's computed font family and size equal the site's `button.secondary` text;
- the same for `request-cancel` in status mode;
- a text with `component: button.secondary` and no colour axis gets no "written by hand" finding;
- a `cancelled`-mode page renders its back field with a non-zero height at 375, 768 and 1280px.

## Root causes (found 2026-11-09)

1. **Two causes for the controls.**
   - `describe_page`'s style audit resolved the site design over the page's own tree only, never over a component's slots, so a control there was read with no face even when its role (`caption`) gave it one. That produced "unstyled: font, size".
   - Separately, a control takes no type from its containers (BUG-373: a field in a heading slot is not set as a heading). A `button.*` box's lettering therefore never reached the control inside it, and with no role of its own the control was drawn in `body`.
2. **The audit's "written by hand" read the design-resolved tree.** A design colour role written as the palette's own hex (here `text`: #2a2224) is copied onto a `button.secondary` text when the component is resolved, and the audit took that copy for a literal the page wrote.
3. **The back link was drawn. The finding was about the element beside it.** Where a page is one section, the layout check descends into the checkout's own elements. The order-cancelled page's empty status message (`role=status`, `aria-live`, filled only by the page's script) became a "section" next to Back to the shop, 0px tall at every width. The `collapsed` rule also reported height before it checked `display: none`, so anything a page hides on purpose was reported the same way.

## What changed

1. **A control inside a component box takes the component's type** (`packages/site-schema/src/l1/design.ts`, `applyComponents`). A `control` that names no `role` of its own, inside a group drawn as a design component that has a `role`, takes that role (family, size, weight, line height, letter spacing), just as a text run inside does. The component's text colour already reached controls. **A role the control names itself still wins**, as a run's own role does. This keeps the ordinary precedence and BUG-373's rule that a control's *slot* type does not reach it: only the component frame's role does. So the report's exact tree (`role: caption` on the control) still draws in caption type. To get the button lettering, drop the control's role.
2. **The style audit reads as drawn and judges what was written** (`tools/generate/src/cli/style-audit.ts`). `auditPage(page, palette, design)` resolves the design itself, over the page's tree and every component's slots, for the face, size, ink and contrast checks. The palette check ("written by hand") walks the page *as stored*, under the same keys, so a colour a component or role resolves to is never reported. A literal the page does write is still named. Both callers pass the design: `describe_page` (`toolbox-core.ts`) and the builder evaluation (`eval-builder.ts`).
3. **The layout check's `collapsed` rule** (`tools/generate/src/cli/ai/layout-check.ts`) skips a part that is `hidden` or `display: none`, and an empty live region (`aria-live`, or `role` status, alert or log) waiting for its script. Real sections that take no height are still reported.

## Superseded expectation

`test_UAT_FC_REQ-349_unstyled_inputs_are_broken_beside_a_styled_button` expected "font" among a bare contact-form input's gaps. The test site's starter design has a `body` face, which that input is drawn in once its slot is resolved, so "font" was the same false report as problem 1. The test now expects padding and placeholder (still `broken`) and no "font". `test_UAT_FC_REQ-349_a_control_matches_a_page_that_names_no_face` was red on clean working for this same reason and is now green.
