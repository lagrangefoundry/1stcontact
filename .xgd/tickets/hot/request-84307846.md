## Purpose

The first slice of [[EPIC-31]]: **an inventory module for any business that sells physical goods.**
- A business can bring its existing product catalogue in from another shop platform, starting with WooCommerce.
- The owner can see and edit every item in a new **Shop** tab.
- The owner can go on building the site while checkout is built and tested behind it.

**Timing:** [[GOAL-55]]'s first customer needs this by **Friday 2026-11-06**.

**This is a product, not a migration for one shop** (operator, 2026-11-02). Nothing specific to any customer's shop may appear in the code, tests, fixtures or this ticket: names, URLs, category names, counts, or quirks. Every difference between shops is **data the owner enters or chooses at runtime**. Where this ticket gives an example, it is illustrative.

This ticket takes **no money and has no public-site output**. Orders, checkout and Stripe come in later children of EPIC-31 and [[EPIC-9]]. The model must leave room for them without building them.

## What the user sees

1. **A Shop tab** in the business tab strip, business-scoped like the others (`apps/control-app/src/builder/config.js`: `SITE_TAB`, `SETTINGS_TAB`), using the existing list-detail split (`fill: true`). In this ticket it holds **Inventory**. Orders, a second top-level view, comes later.
2. **The Inventory list.** One row per inventory item, showing:
   - the first photo, name and price
   - **availability** as an integer
   - collection and categories
   - a **Sold** badge when availability is 0, and a **Live** or **Not live** badge

   The list can be filtered by collection, category and live state, and searched by name. With hundreds of items it must stay usable, through paging or virtualised rows. Clicking a row opens the item detail.
3. **The item detail page.** The owner can edit:
   - **photos**: add, remove, reorder; the first is the main photo
   - **name**
   - **summary**: one or two lines of plain text, used by grid cards, the SEO meta description and link previews. It may be empty.
   - **description**: paragraphs and line breaks, used by the product page
   - **price**: a single field in the business's currency, entered as written (`19.99`) and stored as an integer in minor units, with no floating point. Malformed values (`19.999`, `abc`, a negative amount) are refused.
   - **availability**: an integer ≥ 0
   - **collection**: at most one, from the business's own list of collections, which the owner can add to
   - **categories**: any number, from the business's own list of categories, which the owner can add to
   - **attributes**: a list of name/value pairs (for example `Material: silver`), editable as simple rows
   - **live** and **made to order** (each on or off)

   **Edits are private until Save.** Save validates and persists. Invalid input (negative availability, a bad price, an empty name) is refused with a message, not stored. "Made to order" is stored now and used by checkout later.

   **Live or not live, and Save publishes** (operator, 2026-11-02; see [[EPIC-31]]):
   - A not-live item exists here but appears nowhere on the site. **New items start not live.**
   - A live item has no draft copy. Once the catalog module ([[REQ-633]]) exists, Saving a live item puts the change on the site straight away, independently of the site's Publish.
   - **This ticket stores the live flag and the Save. The rebuild belongs to REQ-633.**
   - Sold (availability 0) is separate from live: a live sold item stays on the site as portfolio.
4. **New item and delete item** from the list.
5. **The import**, described below.

## The import

**Source.** "Import from WooCommerce" takes a shop URL. It reads the shop's public **Store API** (`/wp-json/wc/store/v1/products`, paged), which **needs no key**. Every fetch goes through `guardedFetch`. The import is written so another platform can be added as another source behind the same mapping step and report.

**Step 1: scan and map.** Before creating anything, the import scans the source and shows the owner what it found:
- **every source category**, with its parent and its product count
- **every attribute name**, with the number of products carrying it

For each source category, the owner chooses **a collection, a category, or nothing**, and names the target herself. Several source categories may map to one target. For each attribute name, the owner chooses **keep or drop**.
- **The default proposal:** a top-level category that has child categories is proposed as a collection, any other category as a category, and every attribute is kept. The owner can change any of these.
- **The mapping is saved per business**, and a re-run starts from it.

**Step 2: import.** Runs as a **background job** that survives Worker time limits (a Queue or the existing durable-job pattern, resumable), with visible progress. Each product becomes one item:
- **name**
- **description** from the source's long description. **summary** from the source's short description, reduced to plain text. If the source has no short description, the summary stays empty; it is never generated. If the long description is empty, the short one fills the description too. Both are reduced to the structured text the site schema allows: paragraphs and line breaks, with links as plain text and no raw HTML kept ([[DOC-5]] security policy).
- **price**: the Store API's `prices.price` is a string of minor units, with `currency_code` and `currency_minor_unit`. It is parsed as an integer, with no floating point, into one price row (that currency, all markets). A product whose `currency_minor_unit` disagrees with the currency's ISO decimal count is reported as failed, never guessed.
- **availability**:
  - out of stock → 0
  - in stock with a stock limit (`add_to_cart.maximum`) → that limit
  - **in stock with stock not tracked** (no real limit) → 1, reported as "stock not tracked". Made to order is never set automatically, because it changes when payment is taken.
- **collection and categories, through the mapping.**
  - A source category mapped to a collection sets only the collection; it does not also become a category.
  - Target categories with the same name merge (trimmed, ignoring case).
  - If a product maps to more than one collection, **the first in the owner's collection list wins**, and the product is listed in the report.
- **attributes**: the kept ones, as name/value pairs
- **photos**: all of them, brought into the business's Library through the existing site-import pipeline (`ingestFromSite` in `apps/control-app/src/site-import.ts` / `material.ts`), with provenance kept. **Only each product's main photo is described by AI during the import.** The others are stored undescribed and described lazily: when first opened, or by a background sweep. Product photos are public site material, so they may go to the AI provider (DOC-5 rule 26).
- **source**: the platform, and the source product id as the import key. **Re-running updates by source id and never duplicates.** The SKU is kept when the source has one, but a shop may have none, so it is never relied on.

**Live on arrival** (operator, 2026-11-02). Imported items arrive **live**, because they are already public on the owner's current shop. The exception is an item showing a general sign that it is not a real product:
- a **price of 0**
- **stock not tracked**
- **no photo**

These arrive **not live**, with the reason in the report, for the owner to review. **The import never recognises a product by its name.** Sold products are imported too: they become the portfolio.

**The report.** At the end the import shows:
- counts: created, updated, failed (with reasons)
- items imported not live, and why
- items whose collection was decided by precedence
- items with stock not tracked
- **summaries that are identical, or share the same opening, across many products**, which suggests shop boilerplate the owner may want to clean up. The import never strips text by rule.

## Model

The data lives in D1, in a new migration in `db/migrations/`, keyed by business. **Inventory records are separate from site publication** ([[EPIC-31]]): they are not part of the site definition's revisions, and the site follows each item's Save. Fields:
- id and business
- name, summary and description
- **prices** as a list, one row per (currency, market), each with `amount` as an integer in minor units and an ISO 4217 `currency` ([[EPIC-31]] "Prices"). Each item has one row for now: the business's currency, all markets. **There is no single price column, so adding currencies later needs no migration.**
- availability (integer)
- collection (one or none) and categories (many), each a reference to the business's own list, which has its own order
- attributes (ordered name/value pairs)
- live and made to order
- photo references (ordered Library material ids)
- source: platform and source id (and SKU when present), or `manual`
- the saved import mapping, per business and source
- created and updated timestamps
- **slug**: unique per business, set from the name the first time the item is saved live, and never changed afterwards, so published URLs stay stable

**The contract with [[REQ-633]]** (2026-11-02):
- **This ticket owns the inventory table and lands its migration as the first commit**, so REQ-633 can build on it. REQ-633 never creates its own.
- This ticket provides **`liveItems(business)`**, which returns the live items with all their fields.
- After every Save, and every change to live, availability or deletion, it calls **`catalogItemChanged(business, itemId)`**. REQ-633 provides this function; until REQ-633 lands, it is a no-op.

**There are no order, invoice or payment tables yet.** They come in a later child.

Name the UATs `test_UAT_FC_<this ticket>_*`. They exercise the real Worker endpoints, with the Store API served by a local fixture.

**The fixture is a synthetic shop with made-up names.** It is never a copy of a customer's data. It must include:

- a parent category with child categories
- a product in two categories that are both mapped to collections
- two source categories with the same name
- a sold product
- a product with stock not tracked
- a product priced 0
- a product with no photo
- a product with several photos
- a product with no short description
- an attribute present on most products
- a `<script>` and a link inside a description

The UATs:
- **Scan and map.** The scan lists the source categories with parent and count, and the attribute names. The default proposal makes the parent category a collection. An owner's mapping (rename, merge two sources into one target, drop an attribute) is saved, and a re-run reuses it.
- **Import.** Items are created with the mapped collection and categories, the kept attributes, the summary and description, the correct price and availability, and the photos in the Library with only the main photo described.
  - The two-collection product takes the first collection in the owner's order.
  - Same-name categories merge.
- **Live on arrival.** Ordinary products arrive live. The price-0, stock-not-tracked and no-photo products arrive not live, each with its reason in the report. Stock not tracked gives availability 1 and made to order off.
- **Re-run.** Re-running updates in place by source id and creates no duplicates.
- **Prices.** A Store API price of `1999` in a two-decimal currency is stored as 1999 and shown as `19.99` with its currency. Entering `19.99` stores 1999, and `19.999` is refused. No value passes through floating point.
- **Edit.** Editing through the API persists. Invalid input (negative availability, a bad price, an empty name) is refused. A new item starts not live. Saving persists the live flag, and an unsaved edit is not persisted.
- **Safety.** Imported text contains no raw HTML: the `<script>` is inert and the link is plain text.
- **Report.** The report lists the not-live items with reasons, the precedence cases, the stock-not-tracked item, and summaries repeated across products.
- **List.** The Inventory list returns items filtered by collection, category and live state, with the Sold and Live flags.
- **Browser.** The Shop tab shows the mapping step, the list and the item detail, and an edit is saved.


## Implementation (2026-11-02, free-coded on `free-REQ-631`)

**Decisions taken in-session** (each is behaviour the UATs pin):
- **The business's currency** is a per-business shop setting. The first import sets it where it is empty; the owner can set it in the Shop tab's bar. A Save with a price needs it. A product priced in a different currency from the shop's is reported as failed.
- **Collections and categories follow the category tree.** A product in a child category is also in that category's ancestors, so a parent mapped to a collection gives its children's products that collection. The mapping is applied to the product's categories and all their ancestors.
- **The mapping must be saved before an import starts.** Starting refuses otherwise. The collections the mapping names are created when the run starts, in mapping order, after any the business already has, so the business's collection list is the precedence order. Collections can be re-ordered through the API (`POST /api/shop/collections {order}`).
- **A re-run updates in place by source id.** The source's fields (name, summary, description, price, availability, collection, categories, attributes, photos) are refreshed. **Live, made to order and the slug stay the owner's** once the item exists. Photos already imported are kept by source address and never fetched again. The "imported not live" list reports only items created by this run.
- **Stock not tracked** is detected from the Store API's own "no limit" purchase quantity (its 9999 default), which is a platform constant and not anything shop-specific.
- **Repeated summaries:** the report lists a summary text, or a first sentence, shared by at least max(3, 5% of the imported items).
- **Lazy description:** photos after the main one are stored with `describe_later` and described the first time the Library opens them (`GET /api/material/item`), once only. **The background sweep is not built.**
- **The background job** is the `ShopImport` Cloudflare Workflow (binding `SHOP_IMPORT`, declared in every environment). It runs one durable step per page of 10 products, then a finish step. A page is safe to re-run: items are found by source id and photos by source address, and each photo is recorded on its item as it lands. Without the binding (the suites, the CLI) the same steps run in the isolate. One run per business at a time; a run that has not advanced for 30 minutes may be replaced.
- **Items are scoped to their business.** Another business's item id reads as not found.
- **The Shop tab sits immediately before Settings**, which stays the last product tab, with Debug after it. This supersedes REQ-353's five-tab count and REQ-239's fixed Settings index; both UATs now count the sixth tab.
- **Shop route errors** pass through the router's scrubber.

**API** (all business-scoped):
- items: `GET /api/shop/items` (`collection`, `category`, `live`, `q`, `offset`, `limit` ≤100), `POST /api/shop/items`, `GET|PUT|DELETE /api/shop/item?id=`
- lists and currency: `GET /api/shop/taxonomy`, `POST /api/shop/collections`, `POST /api/shop/categories`, `POST /api/shop/settings`
- import: `POST /api/shop/import/scan`, `POST /api/shop/import/mapping`, `POST /api/shop/import`, `GET /api/shop/import[?id=]`
