## Root cause (to confirm)

1. **Memory grows with the conversation, not just with the work in flight.** A turn that only took a screenshot hit 128 MB, so the isolate is near the limit before a turn does anything. The likely cause is state proportional to the session's size: the junction log read whole (`log.readFrom(0)` on every read, see the BUG-101/"stop polling" finding), the transcript and tool transcript loaded and re-serialised, per-site manager state held in module-level maps (`managers`, per-site maps) across requests. Ariel's session is long and the failures got more frequent as the day went on. BUG-320's `max_concurrent: 1` bounds builders per turn, but not this. And because one isolate serves several businesses, one large session kills other businesses' turns (21:51:16). Per Cloudflare's docs, Durable Objects of one class share their isolate's memory too (BUG-320, "Not done"), so moving work into a DO alone doesn't fix this.
2. **The lost-turn cue isn't marked hidden.** Other host cues are kept off the client's screen (`storedTranscript`, the `*-cue` convention); `lostContinuationCue()` isn't.
3. **A cue's dead turn is treated as the client's unsent message.** BUG-121's "interrupted, not recorded" path restores the turn's prompt into the composer without checking that the prompt was the client's own words.
4. **The lost-turn repaint doesn't preserve scroll.** The rejoin / notice repaint moves the reader off the bottom.

## Fix

1. **Bound per-request memory by measurement.**
   - Add a memory reading to each turn's log (where the runtime exposes one; otherwise measure offline by replaying Ariel's session through the host with a heap profile) and find what grows with session length.
   - Read the junction log incrementally (from a cursor) instead of whole, and don't hold whole transcripts in memory across requests. Cap or evict module-level per-site state that outlives its request.
   - Target: a turn on Ariel's full session (and on a session three times its size) runs a Delegate with headroom under 128 MB.
   - One business's session can't push another business's request over the limit. If isolation needs a platform change (e.g. a separate Worker for long turns), record the finding and the choice here.
2. **The lost-turn cue is hidden from the client,** like every other host cue: not in the client's transcript or panel; only "Picking up where I left off." shows.
3. **A host cue is never restored to the client's box.** When a cue's turn dies, the composer is left as the client had it, and the notice is BUG-294's ("The work stopped…" with Carry on), since BUG-312 allows only one automatic carry-on.
4. **A lost-turn repaint keeps the reader's scroll:** pinned at the bottom stays at the bottom; scrolled up stays put.
5. **Deploy BUG-320 promptly** (operator decision); it removes the parallel-builder share of the memory.

## Findings (BUG-324 session, measured 2026-10-31)

**Symptoms 2, 3 and part of 4 have one cause, in `interruptedTurn` (host-core).** It decides whether a dead turn's prompt was recorded by comparing the pending record with the last *visible* user turn. The transcript hides every `*-cue` turn, the carry-on cue included (`storedTranscript` → `isHostCue`, which was already right). So when the carry-on turn died, its pending record — the cue — never matched. It was reported `recorded: false`, and the panel's BUG-121 path painted it as the client's own message, stamped with the pending record's time (the "visible user turn at 21:47:08"), and put it in the composer. Root cause 2 above ("the cue isn't marked hidden") was this, not a missing hide.

**Scroll (symptom 4).** A lost-turn chase that re-reads a finished turn repaints by remounting the panel. Replayed bubbles paint their text a frame after the panel last pinned itself, and the component's ResizeObserver watches only the list's own box, not its content height, so a reader at the bottom was left a few turns short of it. Every notice appended afterwards pins to the bottom, so a reader scrolled up was pulled down.

**Memory: the framework's junction record cache never evicts, and every turn logs the whole priming again.**
- **Correction to the question that led to Decision 2:** screenshots are *not* in the log. The 27.6 MB junction measured first (21.3 MB of base64 screenshots) dates from 2026-10-18. BUG-229 (2026-10-19) has stored screenshots as placeholders since then, and that junction's own later screenshots carry 0 bytes of image.
- **What does grow, on post-BUG-229 dev junctions:** a 19.1 MB junction (9,869 records, 106 turns) is **14.6 MB `context` records**: one per turn, about 134 KB each, written by the framework (`manager.js`, `log.append(CONTEXT, {priming, reminder, volatile})`). `priming` averages 117 KB and is identical in 100 of 106 turns. A 13.6 MB junction shows the same pattern (10.1 MB context). The junction grows about **180 KB per turn**, three quarters of it repeated priming.
- **What holds it in memory:** lagrange-framework BUG-102 (`60da8ec8a3`, 2026-10-29) added `RECORD_CACHES` in `session_log.js`, a module-level `Map` of every parsed, deep-frozen record of every junction the isolate has read, evicted only by `seed()`/`delete()`. The 19.1 MB junction retains **35.6 MB** of heap once cached; a fresh isolate's first read also holds the bytes and the decoded string while it parses. Several sessions, or one long one, in an isolate approach 128 MB before a turn does anything, and the cache spans every business served by that isolate.
- **Production:** the build live now (redeployed 2026-10-31 22:40Z, downloaded from the Cloudflare API) contains `RECORD_CACHES`. The 01:07Z build's own content can't be downloaded, but it was built 27 h after BUG-102 landed from the same shared store, so it almost certainly had it too.

(a), keeping image pixels out of the log, is already true via BUG-229, so BUG-105 asks instead for the real lever: write `priming` into a `CONTEXT` record only when it changes (estimated growth about 180 → 65 KB per turn; context 14.6 → about 2.4 MB on the measured junction). (b), shrinking screenshots, was implemented and then reverted before commit: screenshots aren't logged, so it would cost the model image quality and buy no memory.
3. **Growth per turn, recorded:** about 180 KB per turn now, and about 65 KB per turn once BUG-105's context dedupe lands, measured on the 106-turn dev junction rather than a synthetic one.
4. **The memory UATs (`turn_memory_bounded_on_long_session`, `junction_read_incremental`) belong with BUG-105,** where the cache and the context writer live. Cursor-based junction reads already landed upstream in BUG-101 (`b535719ae4`). No memory code lands in this ticket.

## What changed (this ticket's code)

- **A host cue is never handed back as the client's words** (`tools/generate/src/cli/ai/host-core.ts`, `interruptedTurn`). A pending prompt that is a host cue (stage guides stripped) reports no `interrupted` turn. The session still reports `failed.stopped`, and because the dead turn was itself the carry-on (`isLostCarryOn`), `carry` is false. So the panel shows BUG-294's "The work stopped…" notice with Carry on, never the cue as the client's message and never "back in the box". The composer is left as the client had it. A dead turn whose prompt was the client's own words is still handed back exactly as BUG-121 does.
- **A lost-turn repaint keeps the reader's scroll** (`apps/control-app/src/builder/chat.js`, `keepingScroll`). Around the chase's repaint of a finished turn and the stopped notice after a rejoined stream ends `lost`, the panel reads whether the reader was at the bottom (within webui-chat's 40 px) and their offset. It restores them right after the repaint and again two animation frames later, once the replayed text has painted: at the bottom stays at the bottom, scrolled up stays at the same offset. A site switch in between drops the restore.
