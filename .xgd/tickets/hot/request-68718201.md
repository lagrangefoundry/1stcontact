## What changes

**The assistant can make a picture.** Today it can look at what the client uploads, talk
about it, and place it on a site — but if the client has no photograph of their shopfront
and no budget for one, the conversation stops. A consultant that can say *"here is a hero
image in the mood we just described, tell me if it is close"* turns an absent asset from a
blocker into a draft.

This adopts lagrange-framework's `create_image` plugin ([[REQ-141]]) over
`components/imagegen`, and configures it for this product.

## This is the first non-Anthropic credential in the product, and that is the real change

Anthropic does not generate images. `components/imagegen` is built over two vendors —
OpenAI's `gpt-image-1` and Google's — so giving the assistant this capability means this
deployment holds an image-generation key for a vendor that is not the one taking the
conversation's turns. Nothing in this repository reaches a second vendor today:
`aiConfigured` asks one question about one key, and every path behind it assumes the
answer covers everything.

**It is an image credential, not a chat backend, and the distinction is load-bearing.**
The session still runs on `ClaudeAPIBackend`; what changes is that one *tool* reaches
OpenAI's images API underneath. Running a session's own turns on a ChatGPT chat backend is
a different change with different consequences — it is what would make tool availability
vary by backend — and it is deliberately not in scope here.

- **The model never learns which vendor drew the image.** The provider is a construction
  option in the framework plugin, not a parameter, and no error sentence or line of the
  manual names one. A deployment can move from OpenAI to Google without the assistant
  noticing.
- **A deployment with no image key has no image tool.** The plugin declares the credential
  it needs and drops out of the surface and the manual when nothing supplies it — the
  absence machinery [[REQ-139]] ships. The session still opens and every other tool keeps
  working, which is the same shape a missing describer already has.
- **`aiConfigured` should not start speaking for two vendors.** Its question is *"can this
  deployment reach a model at all"*, and the answer still turns on the Anthropic key.
  Image generation being absent is an ordinary state, not a deployment fault, so it must
  not make the whole product report itself unconfigured.

## Where a generated image lands

The framework plugin creates a ticket of a configured type, titles it from the prompt,
writes the prompt and what came back into the body, and attaches the bytes. That is
already this product's shape: material is a ticket with one attachment and a
retrieval-shaped body.

**The body being the prompt is a genuine fit, not a coincidence.** [[DOC-38]] §6 needs
every piece of material to carry a written description so the knowledge base indexes
bodies uniformly and never learns that images exist. A generation prompt is a description
of the picture written in the words someone would search by — it is what the vision
describer works to produce, arriving for free because somebody typed it. A generated image
is therefore findable the moment it exists, with no describing call and no cost.

**A generated image must be legible as generated.** A client's library filling quietly
with synthetic pictures presented as their own photography is the failure that matters
here — someone months later choosing an image for a printed brochure needs to be able to
tell. The record says what made it, in a field a predicate can select on, and the Library
shows it where it shows the other things it knows about a file.

**The open decision is the ticket type, and it should be settled before this is built.**
`create_image` takes the type as configuration because the type pack is the deployment's
(DOC-8 §13.1), and `material` is the obvious answer. But `writeMaterial` also sets
`kind`, `description_status`, `description_model`, `content_type` and `filename`, and the
plugin knows about none of them — a `material` written by the plugin would be missing the
fields the Library's rows and the re-describe predicate both read. Two candidates:

- **Write `material` and fill the gap on this side**, so a generated image is
  indistinguishable from an uploaded one everywhere downstream and needs no second code
  path. Costs a normalising step wherever the plugin's write lands.
- **Write a distinct type and promote it**, so the plugin owns its own record and this
  product converts it. Keeps the plugin's write untouched at the cost of a second shape in
  the Library.

The first is preferred unless the normalising step turns out to need the plugin's write to
change, which would make it the framework's problem rather than this one's.

## How it behaves

- **The assistant generates an image when the client has none and the conversation needs
  one** — a hero, a background, a placeholder standing in for photography the client will
  shoot later. It is expected to say what it made and why, and to treat the result as a
  draft the client judges.
- **It does not generate what the client already has.** A client who uploaded twelve
  photographs of their bakery is asking for those to be used, and an assistant that
  invents a thirteenth has misread the room.
- **Generation is bounded per session.** It costs real money per call, so a configuration
  caps how many images one session may make, and exhausting the cap refuses that operation
  in words the model can act on while every other tool keeps working. A generation counts
  when it is attempted rather than when it succeeds — a call that failed partway may still
  have been billed.
- **A refusal from the provider is an error the model can act on.** The framework
  component classifies refusals into named categories with their own prose, so a model
  told the prompt was declined can rewrite it rather than retry it unchanged.
- **A shape the provider cannot make is named as a shape**, separately from every other
  missing capability, because the aspect ratio is the one thing the model can fix by
  itself.
- **Nothing is placed on a site by generating it.** `promoteToSiteAsset` remains the only
  way an image reaches a site, unchanged and still a separate, deliberate step.

## Adoption, not authoring

The surface, the executor, the refusal taxonomy and the cost model all live in
lagrange-framework. This repository installs the plugin, names the provider, supplies the
credential and the ticket type, writes the grant, and adds the Worker re-export shim. **No
tool surface is authored here.** If this ends up needing TypeScript beyond wiring and the
ticket-type normalisation above, that is a finding about the plugin worth reporting
upstream rather than working around locally.

## What this does not do

- **It does not run a session on a ChatGPT backend.** One tool reaches a second vendor
  underneath; the conversation is unaffected.
- **It does not add image editing, reference images or seeds.** The framework surface
  declares capabilities per provider and hides what the configured one lacks; widening
  what this deployment asks for is a later decision.
- **It does not change how uploaded material is described.** The vision path and its four
  branches are untouched.
- **It does not give the assistant a way to write arbitrary tickets.** The plugin holds
  its own scoped store handle and the only record it can cause is one holding a picture it
  was allowed to make.

## Depends on

- lagrange-framework [[REQ-141]] (`ai_imagegen`, `free_coded`) and [[REQ-139]] (the plugin
  layer, `ready_to_reconcile`).
- The shared component store carrying a post-REQ-139 `@lagrangefoundry/ai` plus
  `ai-imagegen` and `imagegen`; the installed `ai` predates the plugin layer today.
- A Worker re-export shim in `assets.ts`, as every framework component here needs.
- An image-generation credential for the chosen vendor, held as a secret and never written
  into configuration.
