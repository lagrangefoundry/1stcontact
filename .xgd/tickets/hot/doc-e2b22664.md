# Build and Deployment

How to build this system, run it locally, and deploy it — with the credentials
each step needs and why it needs them.

Two supported environments: **local Cloudflare simulation** and **Cloudflare**.
A third, raw Node hosting, is discontinued — see §1.

Everything here is derived from `bin/build`, `bin/deploy`, `bin/publish`,
`bin/smoke`, the two `wrangler.toml` files and the deploy hooks. Where this
document and those disagree, they are right and this is stale.

---

## 0. One-time setup

Needed once per machine, before either environment works.

```bash
# 1. Toolchain
node --version            # 20+
pnpm install

# 2. Shared component store — delivered out of band, NOT via pnpm
cd ../lagrange-framework && bin/install --lang js --component all

# 3. Cloudflare CLI auth
npx wrangler login

# 4. Local dev secrets (personal, never in the repo)
mkdir -p ~/Documents/secrets
printf 'ANTHROPIC_API_KEY=sk-ant-...\n' > ~/Documents/secrets/1c.dev.env
chmod 600 ~/Documents/secrets/1c.dev.env
```

**`pnpm install`** — workspace dependencies. It cannot supply step 2, which is
the whole reason step 2 exists as a separate command.

**`bin/install --component all`** — the shared webui components live in a store
outside this repo and are never vendored into it, so `pnpm install` cannot fetch
them and the lockfile cannot notice them missing. A missing BROWSER component
does not fail the build by default: it yields an import map that loads, renders
chrome, and dies at the first `import` in the operator's browser. `1c preflight`
exists to catch that, and fails with exit code 6 naming what is absent.

**`wrangler login`** — an OAuth session for your Cloudflare account. Sufficient
for everything in §2 and §3 except `1c kb build`, which needs API-token
credentials instead (§4).

**`~/Documents/secrets/1c.dev.env`** — holds `ANTHROPIC_API_KEY` and nothing
else. It sits outside the repo because the repo is not where a personal API
credential belongs. The path is overridable with `ONECONTACT_SECRETS`.

## 1. Raw servers — discontinued

**Do not use `1c serve`.** It is a `node:http` static file server over rendered
output. Nothing deploys through it and it presents a second, divergent way to
view a site next to the real one. [[REQ-177]] removes it.

Serve a site through a Worker instead: `pnpm dev` locally, `bin/deploy` in the
cloud. Both use the routes, store and runtime that production uses.

### What is *not* being discontinued, and why

Three things resemble raw servers and are not. They bind an ephemeral loopback
port inside a test or a CLI run and close it again:

| Thing | What it is | Used by |
|---|---|---|
| `startServe` | capture fixture | `1c shot`, `1c aligned-crops`, the conformance harness |
| `startBuilder` | the control-app router's test transport | 42 test files |
| the file-backed store | the local authoring and reproduction tier | `1c new`/`render`/`publish`, `bin/publish` |

The screenshot loop is the load-bearing one: `1c shot` renders to disk, serves
that directory on loopback and drives a browser at it. The bytes under test are
static render output, not Worker behaviour, so moving it to workerd would cost
speed and buy no fidelity — and [[REQ-157]] depends on it.

## 2. Local Cloudflare simulation

`wrangler dev` runs the Workers in **workerd**, the same runtime Cloudflare runs,
with D1 and R2 simulated on disk under `apps/*/.wrangler/state/`. This is the
development loop.

```bash
bin/build                       # preflight, assets, typecheck, bundle
pnpm dev                        # both Workers: public :8787, control :8788
bin/publish                     # seed the local store with your local sites
# open http://localhost:8788/builder
```

Run `bin/build` again whenever `1c assets` inputs change; `pnpm dev` alone is
enough for ordinary source edits.

### Per command

**`bin/build`** — produces every deployable artifact, in four stages that must
run in this order:

1. `1c preflight` — verifies the shared component store and declared packages
   *before* anything is emitted. Exit 6 means the environment is wrong.
2. `1c assets` — copies the builder client and each installed webui component
   into `apps/control-app/dist-assets/`, type-strips the framework bridges, and
   derives the import map. **Before the typecheck**, because the Worker's own
   source imports two of these and neither is committed — a fresh checkout
   cannot typecheck until this has run. It also inlines the system knowledge
   base into `src/generated/kb.js` (§4).
3. `pnpm -r build` — each workspace package's typecheck.
4. Per-app bundle — `wrangler deploy --dry-run --outdir dist`, through the very
   invocation that deploys, minus the upload. The bundle is evidence, not input:
   `wrangler deploy` rebuilds from source and does not consume `dist/`.

**`pnpm dev`** — starts both Workers concurrently. The control app's script is
the one to read:

```
wrangler dev --port 8788 --env-file .dev.vars \
             --env-file ${ONECONTACT_SECRETS:-$HOME/Documents/secrets/1c.dev.env}
```

`--env-file` **replaces** the default `.dev.vars` lookup rather than adding to
it, which is why `.dev.vars` is named explicitly on the left. Later files win, so
the secrets file supplies `ANTHROPIC_API_KEY` and `.dev.vars` supplies the rest.
Drop the left flag and Cloudflare Access switches itself back on; drop the right
one and the chat panel reports the assistant is not switched on.

`.dev.vars` is committed and holds no secrets. It blanks `ACCESS_TEAM_DOMAIN`
and `ACCESS_AUD` so that `ACCESS_DEV_OPEN=1` takes effect and the local builder
is reachable on loopback without an Access challenge. It cannot reach
production: `wrangler deploy --env production` reads `[env.production.vars]`,
and `.dev.vars` is a dev-server-only mechanism.

**`bin/publish`** — copies a local site's draft (definition plus assets) from
`storage/sites/` into the store the Worker serves from. Without it the local
builder has nothing to open. It posts to the Worker's own import route rather
than writing D1 directly, because Node has no D1 or R2 binding — so an import
lands by exactly the path an edit lands by, and the same command works against
`wrangler dev` and production. Defaults to `http://localhost:8788`; reaching
production requires `--production` to be typed (§3).

### Credentials

| Credential | Where | Why |
|---|---|---|
| `wrangler login` session | your keychain | workerd needs no account, but wrangler checks auth at startup |
| `ANTHROPIC_API_KEY` | `~/Documents/secrets/1c.dev.env` | the assistant's turns; absent, the builder opens and shows history but cannot take a turn |

No Cloudflare Access credential is needed locally — that is what `ACCESS_DEV_OPEN`
is for.

### Gotcha: `1c builder` is not `pnpm dev:control` ([[BUG-50]])

Both start `wrangler dev` on the control app, but `1c builder` spawns it with
no `--env-file` flags. Wrangler then falls back to its default `.dev.vars`
lookup, so Access is off (correct) and **`ANTHROPIC_API_KEY` is never loaded** —
the builder comes up and the assistant cannot take a turn. Use `pnpm dev` unless
you specifically want the store flags `1c builder` adds. The key's absence is not
only a chat problem: `defaultDescriber` returns `undefined`, so uploaded images
are stored and never looked at, and the material body says so in a way that is
indistinguishable from the feature being broken. **[[BUG-50]] removes this
divergence, and deletes this subsection when it lands.** `1c builder --remote`
points at the **deployed** D1 and R2, which means editing production data from a
laptop.

## 3. Cloudflare

```bash
export ANTHROPIC_API_KEY='...'        # only when setting or rotating it
bin/build                             # same artifacts as local
bin/deploy --dry-run                  # rehearse: hooks run, nothing uploads
bin/deploy                            # migrate, push secrets, upload both Workers
bin/smoke --slug <slug> --draft <sha> # prove the origin serves
bin/publish --production <slug>       # optional: copy a local site up
```

### Per command

**`bin/build`** — as §2. Deploy does not build for you; `wrangler deploy`
rebuilds from source, but `1c assets` output is not committed, so a machine that
has not run `bin/build` deploys a Worker whose imports do not resolve.

**`bin/deploy --dry-run`** — the same code path as the real deploy, with
`--dry-run` appended to the same composed command line. Hooks still run and are
told to change nothing, so a rehearsal tells you whether the deploy *would*
stop: it reaches Cloudflare to list migrations and read secret names, and
therefore catches a missing binding, a wrong database name or an expired token
without uploading anything.

**`bin/deploy`** — for each app in `apps/*/`, discovered from the tree rather
than a list: run the migrate hooks, run the secrets hooks, then
`wrangler deploy --env production`. A hook that exits non-zero aborts that app
before anything is uploaded — a migration that fails must stop the code that
assumes it ran.

Two hooks exist today, both gated to `control-app`:

- `migrate/10-d1-site-store` — `wrangler d1 migrations apply 1stcontact --remote`.
  `--remote` is the deployed database, not the local miniflare one. On a dry run
  it *lists* instead of applying.
- `secrets/10-anthropic-api-key` — pushes `ANTHROPIC_API_KEY` into
  `wrangler secret`. The logic matters: **in your environment → push** (supplying
  a value means you mean to rotate it); **else already in the store → leave it
  alone**; **else → fail before anything uploads.** So you only export the key
  when setting or rotating it. A later deploy reads the name back off the Worker
  and skips. Only a positive read satisfies the guard — a `secret list` that
  fails for any reason counts as absent, because the failure mode being guarded
  against is a confident skip based on an answer nobody got.

**`bin/smoke`** — asserts a deployed origin actually serves. Bare, it checks the
apex and an unknown slug; with `--slug` and `--draft` it runs the full suite.
Plain JavaScript with no dependency or transform, so it runs on whatever Node is
present straight after a deploy.

**`bin/publish --production <slug>`** — the §2 command aimed at
`https://app.1stcontact.io`. There is no "push everywhere" and no default that
reaches production; `--production` has to be typed.

### Credentials

| Credential | Form | Needed for | Notes |
|---|---|---|---|
| `wrangler login` session | OAuth, keychain | `wrangler deploy`, `d1 migrations apply`, `secret put` | or `CLOUDFLARE_API_TOKEN` in CI |
| `ANTHROPIC_API_KEY` | env var at deploy time | the secrets hook | only when setting or rotating; stored in `wrangler secret` thereafter |
| `CF_ACCESS_CLIENT_ID` + `CF_ACCESS_CLIENT_SECRET` | service token **pair** | `bin/publish --production` | Access fronts `app.1stcontact.io`. Provision with `bin/access-token` |

`CLOUDFLARE_API_TOKEN` is an API credential for `api.cloudflare.com` and is
**refused** by `bin/publish` exactly like no credential at all — Access needs the
service-token pair it exchanges at the edge for a JWT. See
`apps/control-app/ACCESS.md`.

### What is deployed, and the configuration rule that governs it

| Worker | Route | Bindings |
|---|---|---|
| `1stcontact-public-site` | `1stcontact.io` (custom domain), `*.1stcontact.io/*` | `SITES` (R2), `DB` (D1) |
| `1stcontact-control-app` | `app.1stcontact.io/*` | `ASSETS`, `DB` (D1), `SITES` + `BLOBS` (R2), `BROWSER`, `AI` |

`app` is a reserved slug, so the control app's more specific route wins over
public-site's wildcard.

**A named environment inherits neither `vars` nor bindings.** Every binding is
declared at the top level *and* repeated under `[env.production]`. Omitting a
repeat is not a graceful degradation — the deployed Worker sees the binding as
absent and every call throws on `undefined`. UATs pin the two sides together.
`observability` and `workers_dev` *are* inheritable and are repeated anyway, so
that nothing depends on remembering which keys inherit.

Two settings are security controls rather than preferences:

- `workers_dev = false` on the control app. Access attaches to a *hostname*, so a
  `workers.dev` hostname would serve the builder to anyone who guessed it while
  the policy on `app.1stcontact.io` looked perfectly correct.
- `run_worker_first = true` on the assets binding. By default assets answer
  before the Worker; the Access gate lives in `fetch`, and bytes that never
  enter `fetch` are never gated.

`ACCESS_DEV_OPEN` is declared **only** at the top level, deliberately. It cannot
reach production because named environments inherit no vars, and a UAT fails the
build if anyone restates it under `[env.production.vars]`.

## 4. The system knowledge base

Not part of `bin/build`, and easy to forget — with consequences, see [[BUG-48]].

```bash
export CLOUDFLARE_ACCOUNT_ID='...'
export CLOUDFLARE_API_TOKEN='...'     # Workers AI read
1c kb build                           # export, index, chunk, map
bin/build                             # re-inline into src/generated/kb.js
```

**`1c kb build`** writes `kb/system/` — every opted-in doc ticket plus the
generated `REF-*` reference — then indexes it, chunks it and generates the
awareness map. It needs `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` for
the embedding model over REST. The map's paragraphs come from the Claude Code
CLI when no `ANTHROPIC_API_KEY` is set.

**`1c kb export`** writes the corpus only — no embedding, no credentials, **and
no index**. That asymmetry is the trap: a document exported but not built is
carried in the bundle and is invisible to search. `1c assets` reads `docs` as a
directory listing and the index as a build artifact, and does not currently check
that they agree. Until [[BUG-48]] lands, **run `1c kb build`, not `1c kb export`,
whenever a KB document changes**, and re-run `bin/build` afterwards so the result
is re-inlined.

The same embedding model is used on both sides — `@cf/baai/bge-small-en-v1.5`
over REST at build time, the `AI` binding in-datacentre at query time. Vectors
from two different models are not comparable and the failure mode is not an
error but plausible-looking nonsense.

## 5. Order of operations, end to end

```
one-time:   pnpm install → bin/install → wrangler login → secrets file
local:      bin/build → pnpm dev → bin/publish
knowledge:  1c kb build → bin/build
cloud:      bin/build → bin/deploy --dry-run → bin/deploy → bin/smoke
```

The invariants worth remembering: **`1c assets` before any typecheck**, because
the Worker imports its output and it is not committed; **migrations before
upload**, because code that assumes a column must not ship ahead of it; and
**`kb build`, not `kb export`**, because only one of them produces an index.
