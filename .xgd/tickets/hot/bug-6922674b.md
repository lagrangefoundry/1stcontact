## Symptom

First build on dev after the 2026-10-24 deploy (snapshot `b1e175c76f`, deployed 23:52Z), site "First-Draft-Test Dina's Diner" (tenant `biz_a403927e506760c2e798c89a263443ff`, session `site-site_3f5eb611595bd06502f628de6eabf698`):

- 00:16:19 the consultant called `Delegate` (home page first draft).
- The builder `worker-builder-1-wry01u` worked continuously: 19 model requests between 00:16:19 and 00:21:07, 4–60 s apart, each a tool round (describe_site, use_font, set_page_style, add_palette_color, set_l1, decompose_page, get_l1, describe_page…).
- 00:21:23 the consultant's turn was ended by the BUG-249 progress deadline:
  `stop_request {reason: "stalled"}` then `turn_end {status: "aborted", abandoned: true, reason: "stalled", stall: {silentMs: 304352, awaiting: "tool Delegate", last: "tool_issue"}}`.
- The builder was cut off before it reported. The client got no first draft, and the turn shows as aborted.

`stall_seconds` is 300 (`turn-clock.json`). Builder runs routinely last longer than 5 minutes (median 23 requests), so as things stand **any delegation over 5 minutes ends the consultant's turn**, however active the builder is. This blocks every real build.

## Root cause (to confirm)

BUG-249 (`5ad2bf9cad`, at `ready_to_reconcile`) made the deadline count a delegated worker's activity. `witnessed()` (`host-core.ts` ~4957) wraps the manager's `junctions` so that every progress append on any session the manager opens stamps `witness.at`. `stallWatch()` (~5025) passes `progressedAt: () => witness.at`, and `progress-core.ts:279` takes the later of the turn's own progress and that. The logic is right, but here the builder's activity never reached the witness: the consultant saw 304 s of silence while its builder was making requests. This is the first long builder run on a snapshot that includes BUG-249, so it hadn't been exercised in a real deployment before.

Candidates for the fix session to check:
- the consultant's turn and the delegation runtime are on **different `SessionManager` instances**, each with its own witness. The runtime gets `manager: () => manager`; check it's the instance whose witness `stallWatch` reads;
- on the Workers host, a worker session's junction isn't opened through the wrapped `junctions.open` (durable junctions, the memory fallback, a cached log, or appends through a method other than `append`);
- the worker's records are all filtered out by `isProgress`.

## Fix

The progress deadline counts every delegated worker's activity as the waiting turn's progress, on the Workers host as well as the Node host. A consultant waiting on a builder that is making requests or tool calls is never ended as stalled. A genuinely silent builder (no request, tool call or delta for `stall_seconds`) still ends the turn as BUG-249 intends.

A model request is progress even when it produces no junction record. The builder's guard (`guardTurn`) or meter (`charge`) runs on every request and is a reliable place to stamp the witness if junction appends prove unreliable.

## Test plan

- UAT (workers pool, same host path as production: durable junctions, real delegation runtime): a `Delegate` whose scripted builder makes requests every 60 s for longer than `stall_seconds` (shortened via `setStallDeadline`) completes, and the consultant's turn ends `complete`, not `aborted`/`stalled`.
- UAT: a `Delegate` whose scripted builder goes silent for longer than `stall_seconds` still ends the consultant's turn `stalled`, naming `tool Delegate`.
- Regression: the existing BUG-249 UATs still pass.


## Ruled out by reading (EPIC-20, 2026-10-25)

Each of these looks correct in the code. The fault needs a reproduction to find:
- **Same manager.** `build()` constructs one `SessionManager` with `junctions: witnessed(deps.junctions, witness)` and `progressWitness.set(manager, witness)` (`host-core.ts` ~3563–3583). The delegation runtime holds `() => manager` for that same instance, and builder sessions open through it (`delegation_toolbox.js` `_openWorker` → `manager.createSession`).
- **The append path.** The manager opens each session's log once through `this.junctions.open` and caches it (`manager.js` `logFor`, ~935). Every record goes through `log.append(kind, fields)`, which is the method `witnessed()` wraps. The Workers adapter's `open` (`apps/control-app/src/junctions.ts` ~527) returns a `SessionLog` whose `append` is that method.
- **Progress kinds.** `isProgress` excludes only `heartbeat`, `turn_claim`, `stop_request`, `enqueue`, `interpose`, `subject` and host-sourced `progress`. A builder's `turn_start` / `tool_issue` / `tool` / `delta` all count.
- **The comparison.** `progress-core.ts:279` takes the later of the turn's own progress and `progressedAt()`.

Still open, to check first by reproduction:
- whether `deps.junctions` is actually set on the request path that runs the consultant turn. With no junctions, there's no wrapper, and `witness.at` stays at the manager's creation time;
- whether the manager the stall watch reads (`stallWatch(manager, …)`, ~6230) is the instance from `build()` for this request, or one cached from an earlier request in the isolate;
- whether the builder's appends happen at all during its run on this host. The dev store holds no junction for `worker-builder-1-wry01u`; only the site and business junctions exist.
