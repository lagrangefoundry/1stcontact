# Fix Plan — Iteration 6

## Hypothesis
`tests/test_reconciliation_builder_page_carry.test.ts` still drives the pre-BUG-79 single-frame model: it patches `contentWindow`/`contentDocument` on whichever frame `app.panel.frame` returned at mount (the View frame) and delivers every document to `frame()`, but since BUG-79 `panel.frame` is a getter for the SHOWN frame and each mode owns its own frame, so after the switch to Edit the workspace reads the unpatched Edit frame's blank jsdom window and the carry, the open panel and the selector all observe nothing.

## Analysis
Failures (quality report report-a661f56a, commit ba111c27):
- AC2496 at line 295: `expected [] to deeply equal [640]`. The Edit document's recorded `scrollTo` list is empty.
- AC2497 at line 318: `expected [] to deeply equal ['signin-panel']`. The panel is not open in the Edit document.
- AC2499 at line 390: `expected true to be false`. The selector is hidden because it read a document with no panels.
- The three orphaned-AC entries (AC-2496/2497/2499) exist only because those three UATs fail. They clear when the UATs pass.

Root cause, from the reference state (`git show reconcile-src-BUG-79:apps/control-app/src/builder/panel.js`):
- Lines 538-543: a frame is created for every document mode at registration.
- Lines 491-500: `prime()` loads the idle channel once the visible frame has loaded.
- Lines 517-525: `show()` reveals a frame that already holds the right URL WITHOUT navigating, and announces it through `emit('document', …)` rather than a `load`.
- Lines 561-565: `setMode` invalidates nothing.
- Lines 604-610: `get frame()` returns `current?.el`, the shown frame.

The page-carry harness (lines 184-205 and 226-261 of the test) pins the fake window onto one frame at mount and dispatches `load` on `frame()`. After `modeButton('edit').click()`, `frame()` is a different iframe whose `contentWindow` is jsdom's own blank window. So:
- `scrollTo` is recorded on an object nobody reads.
- `openPanels(edit)` reads a document the workspace never touched.
- The selector reads a page with no panels.

The test's "post-save reload" step (`arrive` again on `frame()`) also no longer models a write. Since BUG-248 a write loads into a frame behind the shown one and swaps it in (panel.js lines 43-45 and the refresh/swap paths around lines 377-416 and 688-745).

The ACs are already correct for BUG-79. AC-2496's body says "A switch navigates neither channel ([[BUG-79]]) … applies that to the document revealed". AC-2497 and AC-2499 describe carried state and a no-reload pick, and nothing in them needs one frame. Only the test harness is stale.

The sibling file `tests/test_reconciliation_builder_flip_in_place.test.ts` (AC2517-AC2522, all passing) already has the frame-per-mode harness the builder should reuse:
- It patches every `.builder-panel__pane` frame (lines 144-153).
- It addresses `viewFrame()`/`editFrame()` (lines 161-163).
- It has an `arrive` that targets a specific frame (from line 190).

This is a test-only rewrite in reconcile mode. No production change is needed, and none is permitted.

Prior history: the earlier fix_plan and batch_fix_assessment reports for story-e674c60a (report-103eb41e, report-555646dd and the rest, dated before this BUG-79 run) cover different ACs (AC960/964/967/975/1400). They are not this failure set. This hypothesis has not been tried before. The builder has reported no `blocked_by`, so there is nothing to rule on.
