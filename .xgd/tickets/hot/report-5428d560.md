this deletion removes, and the baseline does not carry it.** Main appended the

`git show 5c012c3758:db/migrations/0001_baseline.sql | grep ticket_changes`
returns nothing — the baseline predates the addition. After this pick, a fresh
database gets no change-log tables.

Nothing in the tree reads them today: a repo-wide grep (excluding
`node_modules`, `.git`, `.xgd`) finds `ticket_changes` **only** in the deleted
migration. But the ticketing component is not vendored into this checkout (only
`tests/support/ticketing-installed.ts` is tracked), and
`tests/test_UAT_FC_REQ-162_ticket_store_bindings.test.ts:133` asserts that
**every** statement in the installed component's `SCHEMA_STATEMENTS` appears
verbatim in the migration. If the component that added these two tables also
publishes their DDL, REQ-162 fails on the baseline as soon as the workers suite
runs. That is the check to run first.

Resolving it is authoring, not resolution, and it needs a decision this session
may not take: the change log has to re-enter as a **second** migration — which
`test_UAT_FC_REQ-190_the_migrations_directory_is_one_baseline` forbids by
name — or be folded into the baseline, which requires relaxing REQ-190's
`PRIMARY KEY` census to admit `ticket_change_floor`. Either way it is a
deliberate amendment to REQ-190, and it belongs to whoever reviews this bundle.
