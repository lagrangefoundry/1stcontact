`gate.json` cannot distinguish "the value gates measured everything and found
nothing" from "the value gates measured nothing". On a `pass` run it reports the
second as the first, and adds `nextStep: "Nothing outstanding from this gate."`
while the same report carries a coverage finding.

Found while diagnosing loop-1 iteration 1 of `repro-gigabytealchemy-ai`
(the gap ticket is REQ-269).

## Evidence

`storage/tmp/repro-console/repro-gigabytealchemy-ai/iteration-1/diff/gate.json`,
in full on the relevant fields:

```json
{
  "pass": true,
  "verdict": "pass",
  "diagnosis": "The perceptual eye and the structural gate agree the reproduction is faithful. No cross-gate disagreement to explain.",
  "nextStep": "Nothing outstanding from this gate.",
  "values": { "deltas": 0, "matched": 59, "unmatched": 0 },
  "coverage": {
    "mirroredImages": 1, "referencedImages": 0,
    "unreferencedImages": ["assets/AlchemistLabWithTech.png"],
    "sections": 8, "pageHeightPx": 4428, "pxPerSection": 554,
    "findings": [ { "kind": "unreferenced-image", "detail": "1 of 1 mirrored image asset(s) are referenced by no element in the reference manifest — …" } ]
  }
}
```

The `values-diff.json` those three numbers were taken from carries two facts the
report has nowhere to put:

```json
"sectionsNotComparable": "the reproduction segments into ONE body-spanning band (4376px, covering its whole page), so the reference's 8 sections have no bands to compare against — section-level values (overlay, contentAnchor, textAlign) are UNMEASURED here, not clean",
"sectionPairing": [],
"unpairedActual": [ 7 objects ]
```

So on this run:

1. **`deltas: 0` includes eight reference sections whose `overlay`,
   `contentAnchorRatio` and `textAlign` were never compared.** `gate.json` says
   the reproduction is faithful; `values-diff.json` says those values are
   UNMEASURED. A reader of `gate.json` alone cannot know.
2. **`unmatched: 0` counts only unpaired *expected* objects.** Seven unpaired
   *actual* objects are dropped, so a reproduction that renders objects the
   reference does not have still reads as a complete match.
3. **`nextStep: "Nothing outstanding from this gate."` is emitted while
   `coverage.findings` is non-empty.** The coverage finding is in the same JSON,
   two keys below the line that says there is nothing outstanding.

## Cause

`GateReport.values` is typed as
`Pick<ValuesDiffReport, 'deltas' | 'matched' | 'unmatched'>`
(`tools/generate/src/cli/gate-core.ts:158`) and assembled at `:349` as
`{ deltas, matched: input.values.matched, unmatched: input.values.unmatched }`.
`sectionsNotComparable` and `unpairedActual` are structurally excluded.

For (3): `reconcileGates` (`gate-core.ts:283`) is a ladder. Rung 2
(`} else if (!perceptualBreach) {`, `:301`) returns `pass` and sets `nextStep`
from the delta count alone (`:306–309`); the coverage rung is below it at
`:310`, so on a passing run a computed coverage finding is reported in the JSON
and contradicted by the operator-facing line. The rung order itself is correct
and documented — this is only about what the pass rung says.

## Proposed fix

- Carry `sectionsNotComparable` (or a boolean plus the reason) and
  `unpairedActual.length` into `GateReport.values`, and print them in the human
  gate output. "0 deltas over 59 matched objects, with section values not
  comparable" is a different sentence from "0 deltas".
- On the pass rung, when `coverage.findings.length > 0`, say so in `nextStep`
  instead of "Nothing outstanding from this gate."

**Wrong result (now):** the gate line reads

## Decisions taken in implementation

These are behaviours the fix has that the proposal above does not spell out. They
are recorded here so the matrix has language for them.

- **The pass rung names everything outstanding, not only the coverage finding.**
  "Nothing outstanding from this gate." is a claim, and on the run this ticket
  came from it was false three ways over — a coverage finding, seven unpaired
  repro objects, and eight sections whose values were never measured. Naming only
  the first would leave the same sentence lying about the other two. So on a
  `pass` the step enumerates, in this order: outstanding values-diff deltas,
  unpaired repro objects, the not-comparable reason, and each coverage finding.
  With none of them it still reads "Nothing outstanding from this gate."
- **The verdict ladder is unchanged.** No rung is reordered and no run changes
  verdict because of this fix. A run that passed still passes; it just says what
  it did and did not measure.
- **`unpairedActual` is a required input, `sectionsNotComparable` is optional.**
  The cause was a structural exclusion, so the reconciliation input asks for the
  unpaired objects rather than letting a caller omit them — countable only
  (`readonly unknown[]`), following the precedent `perceptual.regions` already
  sets in the same interface. `sectionsNotComparable` is optional because it is
  optional on `ValuesDiffReport`: absent means the sections WERE comparable.
- **The human gate output carries both.** The `values-diff` line reports the
  unpaired-repro count alongside matched/unmatched, and a not-comparable run
  prints the reason as its own warning row under it — so an operator reading the
  terminal sees it without opening `values-diff.json`.
- **`check_fidelity` hands the same block to the model.** `fidelity-surface.json`
  returns `reconcileGates`' `values` verbatim, so its description of that key is
  updated to name the two new facts and `surface_version` is bumped.
