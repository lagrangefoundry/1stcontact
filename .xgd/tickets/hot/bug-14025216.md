## Residual class

`coverage-check-misses-section-background-images`

## References exhibiting it

`storage/references/gigabytealchemy.ai/index` — the only bundle I have evidence from this round. It is, however, the bundle `gate-core.ts` itself cites as its calibration anchor (`gate-core.ts:60-62`), and the defect is structural rather than site-specific: it will reproduce on any reference whose imagery is painted as CSS `background-image` rather than as `<img>`.

## Evidence

```json

    "detail": "1 of 1 mirrored image asset(s) are referenced by no element in the reference manifest — the capture kept the bytes but never attributed them to the page."
```

**The capture did attribute it.** `capture.json:295-303`, the hero section:

```json

  "kind": "image",
  "color": "#ffffff",
  "image": "assets/AlchemistLabWithTech.png",
  "overlay": { "color": "#030717", "opacity": 0.3 }

```

**The manifest carries it too.** `multistate.json:4141-4158`, section `index: 1`:

```json
{ "index": 1, "overlay": { "color": "#030717", "opacity": 0.3 },
  "contentAnchorRatio": 0.62, "box": { "x": 0, "y": 0, "width": 320, "height": 800 },
  "backgroundImageUrl": "https://gigabytealchemy.ai/images/AlchemistLabWithTech.png" }
```

That URL is character-identical to the asset entry at `capture.json:4458-4462` (`"src": "https://gigabytealchemy.ai/images/AlchemistLabWithTech.png"`, `"localPath": "assets/AlchemistLabWithTech.png"`).

**The reproduction renders it.** `page.json` (this iteration's L1) contains `backgroundImageUrl":"/assets/AlchemistLabWithTech.png"`. Nothing was dropped.

**The search key does not exist in the manifest at all.** The string `"src"` occurs **zero times** in `multistate.json` — this page has no `<img>` elements whatsoever, so the `referenced` set is empty and `referencedImages` is `0` by construction.

**Value deltas are irrelevant to this finding** — `values-diff.json` reports `matched: 59`, `unmatched: 0`, and only 2 deltas (`gap` 142px→149px HIGH; `§0 contentAnchor` `bottom (0.66)`→`center (0.50)` LOW). Neither concerns the image.

## Hypothesis

`referenceCoverage()` in `tools/generate/src/cli/gate-core.ts:234-237`:

```ts
const referenced = new Set(
  manifest.elements.map((el) => el.src).filter((src): src is string => typeof src === 'string' && src.length > 0),
)
const unreferencedImages = images.filter((a) => !referenced.has(a.src)).map((a) => a.localPath)
```

The set is built from `ValueElement.src` alone. Background imagery is deliberately recorded elsewhere, and two comments in the engine say so explicitly:

- `values-diff.ts:246-250` (BUG-13, on `SectionValues.backgroundImageUrl`): "The page's hero + section imagery is painted as `background-image` on the band, not as `<img>` elements, **so it never reaches the element manifest**; carrying it here lets the fold emit a section-background `box`."
- `extract.ts:1336-1340` (BUG-27): a painted background box "carries the image handle as `backgroundImageUrl` rather than `src`, because it paints a SURFACE behind content, not replaced content in flow."
- `types.ts:443-446` types `backgroundImageUrl` as "Distinct from {@link src}".

So the coverage check reads the one field that structurally cannot hold a background image, and `referenceCoverage` is blind to exactly the imagery the fold is most careful about.

**Why this matters beyond a noisy line.** `reconcileGates` (`gate-core.ts:310`) tests `coverage.findings.length` **before** the `deltas > 0` branch at line 323:

```ts
} else if (coverage.findings.length) {
  verdict = 'capture-incomplete'
```

So on any run that breaches the perceptual floor, a single false `unreferenced-image` finding overrides `reproduction-wrong` and returns `capture-incomplete`, telling the operator "This is a CAPTURE defect, not a reproduction defect" and that the values-diff deltas "are not yet evidence" — against a reference that is in fact complete. Per the loop-1 console brief, `capture-incomplete` also means the round files nothing and stops. This round escaped only because mean 0.69 / 0.31% is under the 8 / 25 floor, so `!perceptualBreach` returned `pass` at line 301 first.

This was observed once before and never fixed: `request-7ff1bacd` (REQ-88 close-out, line 809) records "`unreferenced-image` on `AlchemistLabWithTech.png` is a false positive" as a reporting artifact. It was prose in a completed ticket, not a tracked defect.

## Proposed change

In `referenceCoverage()` (`tools/generate/src/cli/gate-core.ts`), widen the `referenced` set to every way the manifest can hold an image handle:

1. `manifest.sections[].backgroundImageUrl` — `SectionValues.backgroundImageUrl`, `values-diff.ts:255`.
2. `manifest.elements[].backgroundImageUrl` — `ValueElement.backgroundImageUrl`, `values-diff.ts:206`, which is how BUG-27 records nested backdrop boxes below the band root.
3. keep `manifest.elements[].src` for genuine media elements.

Compare by asset basename rather than by exact URL string, reusing the existing `assetBasename()` helper (`values-diff.ts:2356-2357`, which already normalises this way when diffing background URLs). Exact-string matching happens to work on this bundle, but the reproduction side stores `/assets/AlchemistLabWithTech.png` while the reference side stores the absolute origin URL, so any future comparison across the two forms would resurrect the false positive.

Regression test: gating `storage/references/gigabytealchemy.ai/index` must yield `referencedImages: 1`, `unreferencedImages: []`, `findings: []`. A second case should keep a genuinely orphaned asset reported, so the proxy is widened rather than disabled.

Consider also whether `unreferenced-image` should escalate to `capture-incomplete` on its own at all, given how expensive a false one is: a mirrored-but-unused asset (a preloaded sprite, a `srcset` variant) is common and is not by itself evidence that the capture stopped short. Ranking `section-density` above it, or requiring both proxies, would make the verdict harder to hijack. That is a judgement for the implementer, not part of the defect.

## Implementation decisions (2026-09-17)

### The fix

`referenceCoverage()` builds its `referenced` set from **every** field in the
reference manifest that can carry an image handle, not from `ValueElement.src`
alone:

1. `manifest.elements[].src` — genuine media elements (unchanged).
2. `manifest.elements[].backgroundImageUrl` — BUG-27's nested backdrop boxes.
3. `manifest.sections[].backgroundImageUrl` — BUG-13's section-band imagery,
   which is the field that holds the hero on any page whose imagery is painted
   as CSS `background-image`.

Membership is tested by **mirrored-asset basename**, reusing the exported
`assetBasename()` helper from `values-diff.ts` rather than adding a second
normaliser. That is the same identity `localizeAssets` mirrors by and the same
one the values-diff already uses when comparing background URLs, so the check
now asks the question the rest of the engine asks: *is the same asset painted
here?* Exact-string matching happens to work on this bundle (both sides record
the absolute origin URL), but `flattenCapture` records the **local** path
(`assets/…`) where `flattenSignals` records the **absolute** URL, so a
single-width projection would have resurrected the false positive.

An asset whose handle has no basename (a bare `data:` handle, an empty tail) is
left out of the referenced set rather than matching everything.

### The proxy is widened, not disabled

A genuinely orphaned mirrored asset — bytes the capture kept and no field in the
manifest names — is still reported as `unreferenced-image`, and still escalates
the verdict under a breaching perceptual eye. UAT coverage pins both directions.

### Judgement on the verdict ladder (the ticket's open question)

`reconcileGates`'s ordering is left **unchanged**: `coverage.findings.length`
still outranks `deltas > 0`, and `unreferenced-image` still escalates on its
own.

Three reasons. The hijack the ticket describes was caused by the finding being
*false*, not by the ordering being wrong — a truthful "the capture mirrored
bytes it attributed to nothing" under a page-scale perceptual breach is real
evidence that the value gates are blind, which is exactly what rung 3 is for.
Demoting it would invalidate REQ-94's own acceptance criterion
(`test_UAT_FC_REQ-94_capture_incomplete_when_reference_is_impoverished` pins a
bundle with three unattributed images and no section-density finding reading
`capture-incomplete`), and superseding a matrix entry is an intent-level
decision, not an implementer's. And requiring both proxies would make a capture
that dropped the page's imagery but segmented it correctly read as
`reproduction-wrong`, sending a round to chase value deltas against a reference
that is missing the page.

If the ordering does turn out to need loosening, the trigger is a *second*
observed false `unreferenced-image` from a different cause — and that is a new
intent, with its own supersession of REQ-94's AC.

### Behaviour this ticket adds

- Coverage counts a mirrored asset as referenced when **any** manifest field
  names it: an element `src`, an element `backgroundImageUrl`, or a section
  `backgroundImageUrl`.
- Matching is by mirrored-asset basename, so the reference-side absolute origin
  URL and the site-local `/assets/…` mirror of the same bytes are the same
  asset.
- A mirrored asset no manifest field names is still reported as
  `unreferenced-image`, and still drives `capture-incomplete` when the
  perceptual floor is breached.
- A page whose imagery is entirely CSS `background-image` — no `<img>` anywhere,
  so `manifest.elements[].src` is empty by construction — reads
  `referencedImages` equal to its mirrored image count, `unreferencedImages: []`
  and `findings: []`, and a breaching perceptual run over it reconciles to
  `reproduction-wrong` rather than being hijacked to `capture-incomplete`.
