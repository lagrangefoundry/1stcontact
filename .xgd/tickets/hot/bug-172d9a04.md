## What happened
A client uploaded a PNG image (role `site`). `list_library` shows `described.status: "failed"`, `by: null`. `place_on_site` then returns this description text:

> The 'material_image_describer' backend refused this content: image content requires a backend with the vision capability. The 'material_image_describer' backend declares no vision capability — check backendCapabilities("material_image_describer").vision before sending image content, or use a backend that can see.

Captures from `capture_site` also show `described.status: "failed"`. Text documents (markdown) were described fine.

## Expected
Uploaded images get a description, which the docs say alt text should be written from.

## Impact
Every image needs a `screenshot` (expensive, and it stays in context) before it can be placed or given alt text. Builders working from the Library description get nothing to go on.

## Likely fix
Point `material_image_describer` at a vision-capable backend, or check the capability before routing image content to it.



## Diagnosis (EPIC-19, 2026-10-17)

The cause is in this repo. `describerSession` (`apps/control-app/src/ai.ts:285`) registers its backend with `lib.registerBackend(name, () => backend)` and **no capabilities argument**. Upstream `registerBackend` (`backend.js:329`) then records `NO_CAPABILITIES` for that name, and `SessionManager` admits a turn's content against `backendCapabilities(backendName)` (`manager.js:1063`), not against the adapter instance, which does declare `vision: true`. So every image is refused at the manager's gate, while text passes because it carries no image block. The chat host's own registrations are unaffected.

**Fix:** pass the adapter's capabilities as the third argument for both describers (`lib.ClaudeAPIBackend.capabilities`). Re-describe material already left at `failed`.

**Test:** an image upload, with the Anthropic client faked, ends `described.status: described` and the faked client received an image block.



## Confirmation (BUG-214 session, 2026-10-17)

- Diagnosis confirmed against the shared store: `registerBackend(name, factory, caps = null)` records `NO_CAPABILITIES` for a new name, and `SessionManager.promptStream` admits content via `backendContent(backendName, content, backendCapabilities(backendName))`. `ClaudeAPIBackend.capabilities` declares `vision: true`, but the registry never sees it. The only `registerBackend` call in this repo is `describerSession` in `apps/control-app/src/ai.ts`.
- This is upstream drift, not a bug in REQ-207 as written. The registry-level gate landed in lagrange-framework around 2026-10-04 (`b19ea3c5a1`), after REQ-207 (`597939256b`, 2026-09-08). The shared store is unpinned, so the change reached this repo silently.
- The existing evidence already catches it: all 8 of `tests/test_UAT_FC_REQ-207_image_describer_session.test.ts` fail now with this exact BackendError. The REQ-173 text describer UATs (5/5) pass.
- `capture_site` goes through the same `describeImage` (describe.ts:512), which is why captures also end `failed`.
- No re-describe pass exists yet. It is anticipated in comments (describe.ts, material.ts) but not implemented, so repairing existing `failed` rows is new scope.



## Decision (2026-10-17)

Scope is the code fix only. Images already at `failed` are redescribed by hand by the operator (there are few of them). This ticket adds no re-describe pass.

## Fix

`describerSession` (`apps/control-app/src/ai.ts`) registers its backend with `lib.ClaudeAPIBackend.capabilities` as the third argument. That covers the text describer and the image describer, so the session manager admits image blocks.

## Test plan

- The 8 existing REQ-207 image describer UATs (`tests/test_UAT_FC_REQ-207_image_describer_session.test.ts`) are the regression evidence. They fail before the fix and pass after it.
- New `test_UAT_FC_BUG-214_*`: with only the Anthropic client faked, an uploaded image runs through the real describer, ends `described`, and the fake received an image block.
- REQ-173 text describer UATs stay green.
