## What happened
A client uploaded a PNG image (role `site`). `list_library` shows `described.status: "failed"`, `by: null`. `place_on_site` then returns this description text:

> The 'material_image_describer' backend refused this content: image content requires a backend with the vision capability. The 'material_image_describer' backend declares no vision capability — check backendCapabilities("material_image_describer").vision before sending image content, or use a backend that can see.

Captures from `capture_site` also show `described.status: "failed"`. Text documents (markdown) were described fine.

## Expected
Uploaded images get a description, which the docs say alt text should be written from.

## Impact
Every image needs a `screenshot` (expensive, and it stays in context) before it can be placed or given alt text. Builders working from the Library description get nothing to go on.

## Likely fix
Point `material_image_describer` at a vision-capable backend, or check the capability before routing image content to it.



## Diagnosis (EPIC-19, 2026-10-17)

The cause is in this repo. `describerSession` (`apps/control-app/src/ai.ts:285`) registers its backend with `lib.registerBackend(name, () => backend)` and **no capabilities argument**. Upstream `registerBackend` (`backend.js:329`) then records `NO_CAPABILITIES` for that name, and `SessionManager` admits a turn's content against `backendCapabilities(backendName)` (`manager.js:1063`), not against the adapter instance, which does declare `vision: true`. So every image is refused at the manager's gate, while text passes because it carries no image block. The chat host's own registrations are unaffected.

**Fix:** pass the adapter's capabilities as the third argument for both describers (`lib.ClaudeAPIBackend.capabilities`). Re-describe material already left at `failed`.

**Test:** an image upload, with the Anthropic client faked, ends `described.status: described` and the faked client received an image block.
