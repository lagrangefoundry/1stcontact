## What this builds

The **edit render** — a third render channel producing the page the editor works on:
deliberately non-functional, showing everything at once, segmented, and stamped with
addresses that map a clicked element back to the definition that produced it.

Renderer-side only; no UI, and testable entirely on rendered output. Phase 1 ticket
**T2** of [[DOC-28]] §12. Design: [[DOC-28]] §5, §6.

## Why a render and not an overlay

The alternative — a client-side overlay hit-testing the normal page — was rejected.
The renderer is already walking the L1 tree, so it knows which node it is emitting
and can stamp the address as it goes; a client would have to rebuild that mapping
and keep it valid. Making edit mode a render also makes "the page does not work"
honest (we simply do not emit the link targets, the form action, or the behaviour
scripts) rather than a working page smothered in JavaScript.

## Scope

### 1. The channel

A third channel alongside published and draft preview ([[DOC-8]] §4.1): the **same
L1 document and the same renderer**, rendered differently. It is never published,
never content-addressed, and never enters `history.json` ([[DOC-12]] §11).

### 2. The page deliberately does not work

- **Links have no target** — clicking a link edits its copy, it does not navigate.
- **Forms have no action**; behaviour scripts are not emitted — nothing submits or
  fetches.
- **No motion** — the motion script is not emitted.

### 3. Content renders in its settled state — load-bearing

Emitting content in its *initial* state is the trap: pages that fade text in on
scroll would render that copy **invisible** and its segment unclickable, which is
worse than leaving the animation on. The edit render emits the **final, settled**
state.

Generalised: **the edit render shows all content simultaneously**, because nothing
is interactive to reveal it. Worked example — a carousel's slides are all in the DOM
(a scroll track, not `display:none`), so their copy is reachable, but with behaviour
off they sit scrolled out of view; the edit render lets the track **stack** so every
slide is visible at once.

### 4. Derived segmentation

Segments are **derived from the tree, not declared** in the definition — no schema
change, no author burden, nothing for the AI to forget ([[DOC-28]] §6.2):

| L1 node | Segment kind |
|---|---|
| `text` | copy segment |
| `image` | image segment |
| `box`/`container` carrying paint (background, fill, border…) | container segment |
| behavior-module instance | module segment |

Regions with nothing editable are **not outlined**, so the outlines themselves tell
the user what is available. Measured expectation on `storage/sites/xgd/draft`: ~62
copy, ~10 container, 1 module slot; nesting 2–5 deep.

### 5. Addresses

- **Behavior-module instances** already carry `data-fc-module` / `data-fc-type`
  (landed, CHAT-9 M1). Unchanged.
- **L1 nodes** get a **render-scoped structural path** — the renderer's own walk of
  child indices — stamped in the edit render **only**. Content inside a module slot
  is addressed the same way, rooted at the instance rather than the document.

The address is **render-scoped, not persistent**: it need only stay valid for the
lifetime of the document the client is displaying, because every edit re-renders and
regenerates it. So a structural path is safe here despite the usual objection that
reordering breaks it — reordering produces a new render.

**L1's existing `id` must not be reused for this.** REQ-106 gave it a different job
(real DOM `id`, so `href="#how"` resolves and `for`↔`id` wires up); it is optional
and sparse — 34 of 128 elements on `xgd/home` — and user-visible in URLs.

### 6. Outlines

Drawn **by the renderer**, which knows each segment's box, rather than hit-tested and
computed by the client. Faint by default; the hover treatment (brighter outline, small
movement) is the client's to add in T3.

## Non-goals

- **No UI, no modals, no click handling** — T3.
- **No change to the published or draft-preview channels.** Handles and outlines
  exist only in the edit render; published bytes are untouched.
- **No preserved animation.** Rejected for phase 1: untriggered reveals hide
  segments, motion competes with the outline signal, and a segment mid-transition has
  no stable box to outline.
- **No structural editing affordances** — no drag handles, no insert points.
  Structure stays with the AI ([[DOC-28]] §7.3).

## Acceptance criteria

1. The edit channel renders the same document as the draft preview, with links
   carrying no navigable target, no form action, and no behaviour or motion scripts
   emitted.
2. A page whose copy is revealed by a scroll-triggered animation renders that copy
   **visible** in the edit render.
3. A carousel's slides are all simultaneously visible in the edit render.
4. Every `text` and `image` node, every painted `box`/`container`, and every module
   instance carries a segment address; a node with nothing editable carries none and
   is not outlined.
5. An address resolves to exactly one node in the definition, and resolving every
   stamped address on a page yields the nodes it was derived from.
6. Reordering sibling nodes and re-rendering yields addresses that still resolve
   correctly — the client resolves only against the render it is displaying.
7. Copy inside a behavior module's slot is addressable, rooted at the instance.
8. The published and draft-preview renders of the same page are **byte-identical
   before and after this ticket** — no handle, outline or attribute leaks.
9. L1's `id` is unchanged in meaning and emission; nothing in this ticket writes or
   depends on it.
