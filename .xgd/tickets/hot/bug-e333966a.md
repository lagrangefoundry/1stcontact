**Doing:** viewing draft pages that use the `catalog` component (grid mode) after the BUG-337 fix landed.

**Expected:** each card's image element (`bind: {field: "photo", link: true}`, template `src` a placed site asset) shows the product's photo, as it did before the deploy.

**Actual:** every card shows a broken image: the browser paints the alt text (the product name, so the binding to the record resolves) in link blue, with no picture. It happens on both pages using the component (a full collection grid with pageSize 24 and a home 'latest' grid with limit 8), at desktop and phone widths, in `draft` screenshots. Non-catalog images on the same pages (placed assets in plain image elements) render fine.

**Likely:** the photo URL the catalog resolves for each record no longer points at a served file. This may be a side effect of the change to the origin resolver for BUG-337 (the site's library is about 1,600 items, and the product photos are library items imported from the client's site).

**Repro:** screenshot `draft` of any page with a catalog grid on a site whose catalogue photos are library imports. Look at the card images.



---

## Diagnosis (2026-11-04)

Not BUG-337's change: the BUG-335 batching fix only touched price/category hydration. The broken pictures come from **BUG-333**, which moved catalog photos to `shop-photos/<slug>/<n>` on the site. That path is answered by:
- public-site, for the published site (via the control app's AssetGate), and
- the router's `/preview/<site>/<draft|edit>/shop-photos/…` route, for the operator's browser.

It is **not** answered by the browser the builder drives for `screenshot`, comparison captures, and tester feedback shots. That browser never reaches the router: `previewOriginResolver` (`tools/generate/src/cli/preview.ts`) answers every request to our own host in-process, from the `PreviewRenderer` (pages, `assets/…`) and the font mirror (`_fonts/…`), and returns 404 for anything else. So each card's `<img src="shop-photos/<slug>/0">` 404s and the browser paints the alt text. Placed site assets live under `assets/`, so they still render. Before BUG-337/335 was fixed the render failed outright, which hid this.

## Fix (as landed)

- The in-process preview answers `shop-photos/<slug>/<n>` on the draft, edit and revision channels with the Library material behind that live item's `n`th photo. Only a live item of the current business is served; a slug, index or not-live item with no photo behind it is a 404.
- **One place answers it: `PreviewRenderer`.** It takes an optional shop-photo reader next to its catalog reader. Everything that reads a preview goes through it: the router's `/preview` route (`servePreview`) and the origin the screenshot browser is handed (`previewOriginResolver`). So the builder's `screenshot`, comparison captures and tester-feedback shots all get the photo with no extra wiring. The router's separate BUG-333 special case for this path is deleted. The reader is built where the store learns its business (`openSiteStore`, beside the catalog's inventory source), from `shopPhotoMaterial` + `materialFile`. The CLI host passes none, so the path is an ordinary miss there.
- `openSiteStore` is exported so the UAT can drive the store the consultant host actually opens. It is exported for the same reason as `sessionFidelity`.
- Side effect: the route's old `cache-control: no-store` on photo responses is gone. Photos are now served like every other preview byte (no cache header).

## Test plan

UAT `test_UAT_FC_BUG-338_*` (control-app workers suite): a business with a live Shop item with one Library photo, and a draft page with a catalog grid. Drive the fidelity surface's origin resolver (the one the screenshot browser is handed) for the page's photo URL:
- it returns 200 with the photo's bytes and content type;
- an unknown slug and an out-of-range index return 404;
- an item of another business is not served.
Regression scope: the BUG-333 / REQ-633 catalog suites and the shot/preview suites.
