## What was reported

Submitting the whitepapers form showed *"This site cannot take messages at the moment."* with
this in the logs:

    D1_ERROR: table asset_grants has no column named form_handle: SQLITE_ERROR

## Why this is not a defect

Two environment facts, neither of them a fault in the product.

**The local database was behind the code.** [[BUG-93]]'s fix ships migration
`0009_asset_grant_form_handle.sql`, which renames `asset_grants.instance_id` to `form_handle`.
The development database was at `0008`, so the new code wrote a column the schema did not
have. Applying the migration fixed it.

**It then appeared a second time, forty-five minutes after being fixed.** `wrangler d1
migrations apply --local` writes the SQLite file directly, while miniflare's D1 Durable Object
holds its own open handle on that file — so a running `wrangler dev` kept serving the old
schema after the rename. Restarting it fixed that.

The operator-facing message was correct throughout. `lead.ts` reports and never renders, so a
visitor gets the frozen acknowledgement and the diagnosis goes to the log — working as
designed.

## What it did produce

The real finding is that nothing tells a developer their database is behind their code.
Production is guarded by `bin/deploy.d/migrate/10-d1-site-store`, which aborts the deploy
rather than let a Worker meet traffic assuming a column that does not exist. Development has
no equivalent, and this mismatch was met three separate times on [[EPIC-10]] before it was
recognised.

That is [[REQ-253]] — *a development server refuses to run against a database that is behind
its code* — which also covers the stale-handle half, since a server already running must be
restarted after migrations are applied.

Closing as an environment issue. Superseded by [[REQ-253]].
