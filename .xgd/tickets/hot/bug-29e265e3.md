## Symptom

Several controls in the builder chrome read as unstyled — browser-default size, noticeably larger than everything around them, and inconsistent with each other:

- the top bar's **Theme** and **About** buttons

- on the **Users** tab: the filter row (search box, state select) and **Invite**

- the **Provision a business** button in the person detail pane

- the buttons inside the dialogs those two controls open — **Invite**, **Provision** and their **Close** partners

## Root cause

Two distinct defects producing the same appearance.

**1. **`font: inherit`** with nothing to inherit.** `.shell-actions button` (shell.css), `.builder-people__search`, `.builder-people__states`, `.builder-people__invite`, `.builder-people__fulfil` and `.builder-modal__btn` all set `font: inherit`. Nothing in the chain declares a `font-size` — `.shell` sets only `font-family` — so every one of them resolves to the browser default 16px, while the rest of the app runs at 12–13px (the People table takes 13px from `--fields-font-size`, per REQ-189). They are styled; they are just styled at a size that belongs to no one.

**2. **`builder-modal__button`** is a dead class.** The canonical dialog-button class is `builder-modal__btn`. Five call sites spell it `builder-modal__button`, which matches no rule anywhere, so those five buttons render fully browser-default — the genuinely unstyled case. This is the same defect REQ-189 fixed for the tab's own classes; its dialog test only swept classes prefixed `builder-people`, so the `builder-modal__*` typo passed straight through it.

The three controls also disagree with each other on padding: `3px 6px` for the search and select, `3px 10px` for Invite, `4px 12px` for Provision a business — so the filter row's controls do not share a height.

## Fix

**One control type size, declared once.** A `--builder-control-font-size` token (13px, the app's existing control size) is applied to the shell action buttons, the People filter's three controls, and the dialog buttons. The shell component lives in the out-of-repo shared store and is not editable from here, so the top-bar rule is an override in `builder.css`, which chrome.ts already loads after the component stylesheets.

**One height for the filter row.** The search, the state select and Invite take a single shared padding so the row reads as one control group rather than three.

**The five dead class names are corrected** to `builder-modal__btn`, and the two affirmative actions (Invite, Provision) additionally take `builder-modal__btn--primary`, matching how every other dialog in the app distinguishes its confirming button (`editor.js`, `palette-popup.js`).

Deliberately unchanged: the dialog buttons keep their larger `8px 18px` padding — a dialog footer is not a filter row — and Invite keeps its accent fill. Only the type size is unified there.

## Test plan

`tests/test_UAT_FC_BUG-53_control_type_is_consistent.test.ts`, mounted against the real installed webui components on the REQ-189 pattern:

1. Every `builder-*` class the Users tab and both its dialogs emit is matched by a rule in `builder.css` — the sweep widened past `builder-people` so the `builder-modal__button` class of defect cannot recur.

2. The shell's own action buttons, the filter row's controls and the dialog buttons all resolve to the same declared control size, read from the token rather than restated as a literal.

3. That size is smaller than the browser default the controls used to take.

4. The filter row's three controls share one padding.

5. Each dialog's affirmative button carries the app's primary-button class.


## Follow-up: the fix was overridden by the rules it was meant to repair

Verified in the browser after the first commit: **Theme and About took the new size; every control on the Users tab did not.**

`font: inherit` is a **shorthand** — it resets `font-size` along with family, weight and the rest. The token rule was written near the top of `builder.css`, but each control's own rule (`.builder-people__search, .builder-people__states`, `.builder-people__invite`, `.builder-people__fulfil`, `.builder-modal__btn`) sits **later in the same file** at equal specificity — one class each. Later wins, so the shorthand reset the size straight back to the browser default. The rule parsed, matched its elements, and reached none of them.

Theme and About escaped for the one reason that also explains the split: `.shell-actions button`'s competing `font: inherit` lives in the **shell component's stylesheet**, which `chrome.ts` emits *before* `builder.css`. For that selector ours is the later declaration; for the other five it is the earlier one. Same rule, same token, opposite outcome, decided entirely by which file each declaration sat in.

**Fix.** The size is declared **immediately after each `font: inherit`**, in the rule that does the clobbering, so the result no longer depends on source order or on any rule added later. `--builder-control-font-size` remains the single definition site — the four component rules reference the token, they do not restate 13px. `.shell-actions button` keeps its own rule at the token declaration, where order is the mechanism rather than the hazard.

**Why the first test suite passed while the defect was on screen.** It asserted that a rule naming all six controls **existed**. It did exist. Existence and effect are different claims, and only the second one is the bug.

## Test plan (follow-up)

6. For each of the six controls, the **last** `font` or `font-size` declaration that applies to it — walking every rule in the sheet in source order — is the control token, not a `font` shorthand. This fails against the previously committed CSS for the five Users-tab controls and passes for `.shell-actions button`, reproducing the reported split exactly.
