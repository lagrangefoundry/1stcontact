## Symptom

A visitor submits a form. They are told it worked. Nothing was written, and the
running system says nothing about it — no row, no event, no log line. The
operator has no way to find out, and no way to know there is anything to find.

Observed 2026-09-12 while testing the 1st Contact beta form. The capture itself
worked (`1c-beta-test-1@westhead.me`, `20:47:00.057Z`), but establishing that
took a direct query against the D1 file, because a submission that had NOT
landed would have looked exactly the same from outside.

## Root cause

`captureLead` (`apps/control-app/src/lead.ts:435`) returns every outcome as
data. Two of them write nothing:

- `{ accepted: false, reason: 'unknown_site' }` — the site key names no row in
  `sites` (`lead.ts:437`).
- `{ accepted: false, reason: 'no_email' }` — no submitted field resolves to an
  address, so there is nobody to add (`lead.ts:452`).

A third writes the contact but not the thing the visitor was promised:
`assetSkipped` of `already_sent`, `suppressed` or `no_address` (`lead.ts:486`)
means the form offered a download and none left the building.

`LeadRefusal` is already documented as *"Why a submission wrote nothing.
Reaches a log; never a visitor"* (`lead.ts:95`). It never reached a log. The
sole caller in `public-site` awaits the promise and discards the result
(`apps/public-site/src/lead.ts:462`), so all three outcomes are computed
correctly and then dropped.

The contrast is the tell: when `captureLead` *throws*, the same caller catches
it, writes `lead_capture_failed` and returns 503 (`public-site/src/lead.ts:468`).
The thrown path is handled. Only the returned-refusal path vanishes.

## Fix

Record the outcome where it is decided, inside `captureLead`, rather than at the
caller.

This follows the precedent set by `denyAdmission`
(`apps/control-app/src/identity.ts:918`), which was itself filed from a silent
refusal that locked an operator out of their own deployment "with nothing in
the running system saying why". Its rule: *deciding and recording are the same
statement, so a reason cannot be computed without being reported.*

It also matters here because **`captureLead` has two callers** — `public-site`
over the service binding, and the builder preview in-process
(`apps/control-app/src/router.ts:3216`). A log at the `public-site` call site
would leave the preview path silent, which is the exact failure mode the
`identity.ts` comment warns about. There is one implementation, so recording
inside it covers both by construction.

Uses the structured-log idiom the codebase already uses in ~14 places —
`console.warn(JSON.stringify({ event, … }))`, stated as the house rule at
`identity.ts:931` — so these lines can be queried out of the Worker invocation
logs rather than grepped out of prose. No logging helper, no new module, no
dependency: a logging abstraction is EPIC-1's job in lagrange-framework, and
inventing one here would create something that epic has to adopt or delete.

### What is logged

- **A submission that wrote nothing** is logged with its reason, the site key
  it named, and the form instance handle it carried. When `no_email`, it also
  carries the NAMES of the fields that were submitted — not their values — so
  an operator can see that a form sent `your_email` and that nothing in it
  parsed as an address, without the diagnostic itself becoming a store of
  whatever a stranger typed into a text box.

- **An asset the form promised and did not send** is logged with which of
  `already_sent` / `suppressed` / `no_address` applied, the business, and the
  contact it concerned.

- **`not_offered` is not logged.** It is set on every submission to a form that
  never promised an asset, which is most of them. Logging it would bury the
  three skips that mean something under a line per ordinary submission, and a
  log nobody can read is the state this ticket is fixing.

- **A submission that lands cleanly logs nothing.** Quiet is the signal that
  everything worked.

### What does not change

- **The visitor still sees one frozen acknowledgement.** The reason is for the
  operator and never for the person who submitted; a response that varied by
  outcome would be an oracle for which site keys exist and who is already a
  contact. `identity.ts:926` states this: the visitor is told one thing
  precisely because they are unauthenticated, and the operator reading the
  Worker's log is not the visitor.
- **The honeypot and rate-limiter paths stay silent** (`public-site/src/lead.ts:405`,
  `:426`). Those acknowledge without writing BY DESIGN — a caller who could
  tell the difference would hold a probe for how much they had already spent —
  and they fire on volume, so logging them would be the same flood
  `not_offered` would be.
- **No change to what is written, sent, or answered.** This ticket adds a
  record of decisions that were already being made.

## Test plan

`tests/test_UAT_FC_BUG-87_lead_outcome_logged.workers.test.ts`, driving
`worker.fetch` — `public-site`'s real handler — inside workerd against real D1
and R2 bindings, with the REAL `captureLead` behind the service binding. Reuses
the REQ-223 harness (`seedFormSite`, `applySchema`) rather than standing up a
second fixture.

Happy-path coverage:

1. A submission naming a site key that is in no `sites` row is acknowledged,
   writes no contact, and leaves one structured log line carrying
   `unknown_site` and the site key.
2. A submission carrying no address is acknowledged, writes no contact, and
   leaves one line carrying `no_email` and the submitted field NAMES, with no
   submitted value anywhere in it.
3. A form that promises an asset, submitted twice, leaves a line for the second
   carrying `already_sent` and the contact it concerned.
4. An ordinary accepted submission to a form with no asset leaves NO line —
   proving `not_offered` is not noise and that quiet means success.

Regression scope: `tests/test_UAT_FC_REQ-223_lead_endpoint.workers.test.ts`
(the endpoint's own suite, which asserts the frozen acknowledgement and the
no-oracle property this must not disturb).

## Why free-coded

Small and behaviour-preserving — it adds a record of decisions the code already
makes, touching one function and no interface.
