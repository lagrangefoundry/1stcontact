# Site data model

Design session on how *all* content around a site is organised and reached by the
AI — not just the site itself.

## Outcome

- **DOC-38** — *Content Model, Rights & the Project Corpus* (this repo).
- **`lagrange-framework` REQ-104** — *Ticket attachments: a BlobStore port, with
  typed attachment records*. Named in prose, not as a wikilink: this repo's own
  REQ-104 is an unrelated L1 ticket.

## Decisions

1. **Exposure is derived from rights, never set independently.** "Is it publicly
   viewable" conflates a fact about someone else's server with a permission on
   ours.
2. **Ownership yields two independent bits that invert.** A client's own previous
   site is republishable but not exportable; a third-party reference is the
   reverse. Both stored explicitly; neither derived from the other.
3. **Everything is a ticket; the body is the material's text shadow.** Extracted
   text for a PDF, a written description for an image. The modality axis then
   disappears at the corpus layer — the KB indexes bodies and never learns media
   exists.
4. **Two knowledge bases, not six** — `system` and `project`. A KB is a *view*,
   not a folder: membership overlaps (`row.kbs` is a list), corpora are
   predicates over fields, and re-indexing is already incremental by `since`
   cursor. The six candidates were ticket types and fields wearing KB costume.
5. **The site enters the corpus through a source adapter, not as page tickets** —
   avoiding write amplification per keystroke-settle and a parallel copy of the
   definition that could drift from, or be written back into, the L1 control
   surface.
6. **Quarantine sits at the write path, not the read path.** The AI is supposed
   to look at references; what must not happen is verbatim third-party copy
   reaching a published site.
7. **Attachment blobs are content-addressed within a tenant prefix.** Global
   content addressing would be an existence oracle across the tenant barrier and
   would contradict DOC-37 erasure.

## Findings worth keeping

- **Ranked search takes `Math.max` over a document's KB weights**, so a second KB
  can only ever *raise* rank. Any future down-weighting needs disjoint corpora —
  a constraint on how a split is done, not a knob found afterwards.
- **The JS ticketing component has no attachment op today** (`create / update /
  get / query / comment / comments / backlinks`). The original conception
  supported attachments; the shipped component does not. Hence REQ-104.

## Open

- Where the rights bits get set — ask at capture/upload, or infer from the
  client's declared domain and ask only on mismatch.
- Whether `reference` earns its own type or is `material` with `kind: capture`.
- Whether site copy pollutes co-ranking (answered with measurement, per DOC-10
  §6.3's precedent).
