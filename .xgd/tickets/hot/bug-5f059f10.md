## Symptom

Dev, 2026-11-04, a site whose shop has dozens of live products shown in a `catalog` grid. Each time the consultant's turn reaches "checking the pages" (taking screenshots of the draft), the dev worker dies:

> I've got the clip and it's still ready. Now I'm checking the pages, then I'll hand over the fixes. This will take a few minutes.
> *That reply stopped before the turn finished, and the conversation could not be re-read (POST /api/ai/session → 503). Reload the builder to see where the turn got to.*

A reload then gives `Error: Network connection lost` (miniflare `entry.worker.js`), and afterwards the worker answers 500/503 to everything until `dev-worker` is restarted. **It has happened three times in a row.** Each time, `bin/dev up` or `restart` was followed by Carry on and then the crash, with the operator seeing **under 5 minutes** from start to crash.

## What the logs show (`storage/tmp/dev/dev-worker.log`)

The same signature every time:

```
<--- Last few GCs --->
[87418:0x78e2d4000] 79535 ms: Mark-Compact (reduce) 1398.6 (1440.0) -> 1398.6 (1440.0) MB … last resort; GC in old space requested
*** Received signal #6: Abort trap: 6
V8 fatal error; location = Reached heap limit; message = : allocation failed: JavaScript heap out of memory
POST …/api/ai/session 503 Service Unavailable
```

- **The process that dies is the workerd runtime, not wrangler's Node.** `*** Received signal #6` and `V8 fatal error; location = …` are workerd's (KJ) crash format; Node prints `FATAL ERROR: … JavaScript heap out of memory`. So it is **the worker's own JavaScript heap** reaching about 1.4 GB of *old space*: live JS objects or strings, not ArrayBuffers or wasm memory. Dev doesn't enforce production's 128 MB isolate limit, so dev only dies at V8's ceiling. In production the same work would be killed far sooner as `exceededMemory`.
- Raising Node's heap (`NODE_OPTIONS=--max-old-space-size=…`) has no effect, as confirmed on the third crash, since workerd isn't Node.
- In the latest crash, the heap reached about 1.4 GB **about 80 s** after the runtime started. During that time the worker served only a handful of requests (`GET /`, `/api/domain`). So the memory is allocated inside the resumed turn, not by request traffic. (The `ms` in the GC lines is the dying process's uptime. An earlier crash's 2,203,094 ms belonged to a runtime that wasn't the one the operator had just started, so it doesn't measure time-to-crash.)
- The site's junction (DO) store is under 1 MB, so the turn's stored log isn't the source.
- All three crashes came at "checking the pages". The site has >100 live shop items (see BUG-335), shown as photos in the `catalog` grid on Home and Preloved.

## First fix: in-process photo fulfilment (a real cost, not this crash)

*This section was written first, as "Cause (confirmed)". The cost it describes is real and its fix stands, but the crash below shows it wasn't what killed the dev runtime. See "Cause (confirmed by reproduction)" further down.*

The heap goes to **in-process fulfilment of the catalog's product photos** in the browser the builder drives for "checking the pages" (screenshots and the layout check, `cf-driver.ts` behind `shot.ts`). Every request that browser makes to our own preview host is answered from the worker: the worker reads the bytes and hands them over with `req.respond`, which `@cloudflare/puppeteer` sends as a base64 string inside a CDP `Fetch.fulfillRequest` message. Two things multiplied that:

1. **The library's encoder costs about 28× the body in JS heap.** `HTTPRequest.getResponse` pushes one string per byte into an array, then joins and `btoa`s it. Measured in V8: a 3 MB photo uses 85 MB of transient heap, and a 24 MB photo can't be encoded in a 96 MB heap at all. Run under that cap, the library's encoder aborts the process with the same `JavaScript heap out of memory` as the dev crash.
2. **Nothing bounded how many were in flight.** A browser asks for every picture on a page at once, and each fulfilment's base64 copy stays reachable until the browser acknowledges it. The screenshot shoots several widths in parallel, so with a 100-card grid the worker had **302 fulfilments in flight at once**. With this site's 336 live products (photos p90 about 2.7 MB, largest about 22 MB), that is over a GB of live strings. The dev log fits this: just before the latest crash the worker took about 4 s to answer each of the iframes' own `shop-photos` requests, because it was busy encoding.

Ruled out: the draft and junction store are small (12 KB of page JSON), and the assembled-draft memo (BUG-37) is not involved.

## What changed

- **Bounded in-flight fulfilments** (`tools/generate/src/cli/capture/cf-driver.ts`). An isolate-wide gate, `FULFILMENT_LIMIT = 6`, covers each in-process fulfilment from reading the body until the browser takes it. At most 6 encoded bodies exist at any moment, however many products a page shows and however many widths or drivers are running. It is isolate-wide rather than per driver because widths run in parallel and they share the heap.
- **A chunked encoder** (`fulfilmentBody` in `cf-driver.ts`). It encodes base64 in fixed 24 KB chunks (a multiple of 3 bytes) and costs about 2.7× the body. A string body is encoded as its UTF-8 bytes, as before. `cf-driver.ts` still names no browser library. `apps/control-app/src/shot.ts` (the one file that imports `@cloudflare/puppeteer`, per REQ-154) installs it as `HTTPRequest.getResponse` when the module loads, so every `respond` goes through it.
- Each photo still reaches the picture with its own bytes. Only how many are held at once changed.

## Design decisions

- **Patch the library's static rather than fork or `pnpm patch` it.** The request class's private CDP client can't be reached, so the encoder can't be bypassed from outside. A runtime replacement in the one composition root keeps the change in one file. A UAT pins that the replacement is installed and that the library's real `CdpHTTPRequest.respond` sends the right bytes through it, so a library upgrade that renames the static fails a test instead of silently bringing the bug back.
- **6, not 1.** Reading a photo from storage is the slow part, and a few reads in parallel keep a 100-photo page well inside the 30 s navigation timeout. Six of even a large photo is a few tens of MB.

## Not done / open

- **Production check (Fix step 3) has not been done.** The logs from prod's `ConsultantTurn` `exceededMemory` (2026-11-03) weren't examined. The same path runs in production, and there it would hit the 128 MB isolate limit far sooner, so it is a likely contributor. That is still unconfirmed.
- **Off-heap residue, unchanged.** The driver's response cache (`cached`, which feeds `responses()` for captures) still keeps every fulfilled body as an ArrayBuffer until the driver closes. That memory is outside the V8 heap, so it isn't this crash. It does count toward production's 128 MB isolate memory, about 100 × photo size per page per width. It would be its own ticket if the production check implicates it.

The fake browser asks for everything at once and takes a few ms to acknowledge each fulfilment. The test asserts that every photo is served with its own bytes, that the peak number in flight is between 2 and `FULFILMENT_LIMIT`, and that it returns to 0. ## Cause (confirmed by reproduction): the builder case recorder reads the whole Library once per item, all at once

On dev, every delegation is recorded as a replayable case (REQ-452; `RECORD_BUILDER_CASES = "1"` on dev, REQ-454). The case is written when the builder's opening capture is taken (`draftAccount.mark` → `caseRecorder.opened`), which is exactly the moment each crash happened. The case includes `libraryCatalogue`: every Library item's listing, description and **own text**.

- **Each item's text was a full scan of the business's comments.** `LibraryDeps.text` → `materialText` is a ticket-store predicate query. The ticket-store component (`@lagrangefoundry/ticketing`, `read_slice.js` `query`) answers any predicate by materialising **every ticket of the hoisted type** in JS and filtering after. For `type="comment"`, that includes every chat transcript.
- **All items were read at once** (`Promise.all` over the whole Library).
- **This site's numbers:** the shop import (BUG-335) put **1,617 materials** in the Library, and the business has 11 comments holding **642 KB** of bodies. So one builder start held up to 1,617 copies of the comment corpus at once, over 1 GB of strings.
- **Reproduced:** this business's real ticket rows, loaded into the workers test pool and run through `libraryCatalogue(chatLibrary(…))`, kill workerd in 11 s with the dev signature, byte for byte (`Mark-Compact (reduce) 1399.2 -> 1399.2 MB … last resort`, `Received signal #6`, `JavaScript heap out of memory`). With the fix, the same data completes in **421 ms**, and the recorded catalogue is the same size (2.86 MB). The reproduction used customer data, so it stayed a scratch file and isn't committed. The committed UAT uses synthetic data.
- This is why only dev crashed (production records a client's cases only on opt-in), why it began after the shop import, and why the page-check fix didn't help.

## What changed (second fix)

- **One scan for every item's text.** `LibraryDeps` gains `texts(): Promise<Map<string, string>>`: every item's own text by name, with items that have none absent. It is for a reader that wants the whole Library; no model operation calls it. The worker's `chatLibrary` answers it with a new `materialTexts` (`apps/control-app/src/material.ts`), one query for every `material_text` comment, keeping the first per subject as `materialText`'s `limit: 1` did. The replay's `caseLibrary` answers it from the case.
- **`libraryCatalogue` reads the texts once and the rest bounded.** It calls `texts()` once, alongside `list`/`deleted`. The per-item `read`s that remain (one ticket `get` each) run at most `CATALOGUE_CONCURRENCY = 8` at a time, however large the Library is. Item order and the recorded shape are unchanged; a failed `texts()` records every item's text as `null`, as a failed per-item `text` did.
- `LibraryDeps.text(name)` (the model's `KnowledgeGet`-style read of one item) is unchanged.

## Not done / open (second fix)

- **The ticket store's predicate scan is still O(corpus) per query.** That's the component's design, and it lives in a sibling repo. Any other caller that issues per-item predicate queries over a large tenant will hit the same cost. A fix there (pushing simple equality terms into SQL) would be its own ticket in that repo.
- **The builder's start-up** (priming, rounds) after the case was not separately profiled. Only the case write ran before the crash in every recorded instance.
