## Symptom

The assistant created a page with `path: "papers/download"`. The write was
accepted. Every subsequent render of the site then failed with:

```
page slug 'papers/download' is nested: rendered pages must sit flat at the
snapshot root, because emitted asset URLs are relative to it (REQ-109)
```

This is not one broken page — `renderSiteFiles` throws on the first nested slug
it meets, so **no** page renders. Draft preview, published render and publish all
fail together. The user's site is dark until someone repairs the definition by
hand.

## Root cause

Three things line up:

1. **Nothing validates the slug's shape.** `pageSchema.slug`
   (`packages/site-schema/src/schema.ts:601`) is `z.string()` carrying only the
   REQ-153 locale-shape refusal. A slug containing `/` validates cleanly and is
   written to the store.

2. **The flatness invariant is enforced at render time only.**
   `tools/generate/src/render/render.ts:335` throws — correctly, and for a real
   reason (REQ-109: emitted asset URLs are document-relative, which is only
   correct while every page sits flat at the snapshot root). But by then the bad
   value is already durable, and the failure is site-wide rather than scoped to
   the page that caused it. The guard is in the right place for correctness and
   the wrong place for the author.

3. **The tool surface invites it.** `add_page`'s `path` parameter is documented
   in `tools/generate/src/cli/ai/l1-surface.json` as *"Its address in the site.
   Defaults to the page id."* Nothing there says a page is one segment at the
   top level, so `papers/download` reads as a reasonable address to write.

This is a long-standing gap, not a regression from a recent change: the render
guard has been the only check since REQ-109.

The same gap exists on `pageSchema.id`, which is unconstrained and becomes the
store key `<id>.json` — a nested id writes a nested page file.

## Fix

Move the refusal to the moment of the write, where the author can act on it, and
keep the render guard as a backstop.

1. **Refuse a non-flat page slug in the schema.** A new shape predicate and
   message beside `isLocaleShapedSlug` in `packages/site-schema/src/locale.ts`'s
   sibling position, wired into `pageSchema.slug`. Because every authoring path
   (`editPageAdd`, `editPageUpdate`, the AI toolbox, the store loader) funnels
   through `validateSite`, one rule covers all of them — the same reasoning
   REQ-153 used. The error is raised at `/pages/N/slug` so an AI author can
   self-correct, and the message names a concrete alternative
   (`papers-download`) rather than saying "pick something else".

2. **Refuse the same shape on `pageSchema.id`**, for the same reason: it is
   concatenated into the store key.

3. **Refuse a non-home page slugged `index`.** `renderSiteFiles` writes
   `index.html` as an alias for the home page *after* the page loop, so a
   second page slugged `index` is silently overwritten and serves the home
   page's bytes at its own address. Same class of failure — a value accepted on
   write that cannot be served correctly — and cheap to close while we are here.
   Site-level refine, beside the duplicate-slug check.

4. **Stop the surface inviting it.** `add_page` / `update_page`'s `path`
   description says a page sits flat at the top level of the site: one segment,
   no slashes.

5. **Keep the render-time throw.** Defence in depth; the existing
   `test_UAT_FC_REQ-109_nested_page_fails_loud` UAT stays green.

### The allowed shape

Mirrors `SITE_KEY_PATTERN` in `apps/public-site/src/routes.ts` and its stated
reasoning — boring filename characters, because the value is concatenated into
an R2 key and becomes a file at the snapshot root:

```
/^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$/
```

This refuses the hazard (`/`, `\`, `\0`, `.`, `..`, empty, whitespace,
percent-encoding bait) without refusing shapes an existing site may already be
using (`about_us`, `Products`). Existing slugs in `storage/sites/` — `home`,
`contact`, `whitepapers` — are unaffected.

### Repair path for a site already in this state

`update_page` with a corrected `path`: the edit path reads pages raw from the
store rather than through the validator, so a site holding a bad slug can still
be repaired rather than being bricked by the new rule.

## Test plan

UATs under `tests/test_UAT_FC_BUG-92_*`, asserted on `validateSite` and on the
real authoring entry points (`editPageAdd` / `editPageUpdate`), not hand-built
fixtures:

- A nested slug (`papers/download`, and the backslash form) is refused at
  `/pages/N/slug`, with a message naming the flat alternative.
- `add_page --path papers/download` fails with `SCHEMA_INVALID` and writes
  nothing — the store still holds the pages it held before.
- The traversal and empty shapes (`.`, `..`, ``) are refused.
- A nested page **id** is refused.
- A non-home page slugged `index` is refused.
- Ordinary slugs (`home`, `contact`, `whitepapers`, `about_us`, `papers-download`)
  still validate — guard against an over-eager rule.
- A site already holding a nested slug can be repaired with `update_page --path`.
- The existing REQ-109 render guard still fires (regression scope).

Regression scope: `tests/req109-relocatable-output.test.ts`,
`tests/test_UAT_FC_REQ-153_locale_slug_reservation.test.ts`,
`tests/test_UAT_FC_REQ-247_email_page.test.ts`, and the page-composition surface
