## Symptom

The assistant created a page with `path: "papers/download"`. The write was
accepted. Every subsequent render of the site then failed with:

```
page slug 'papers/download' is nested: rendered pages must sit flat at the
snapshot root, because emitted asset URLs are relative to it (REQ-109)
```

This is not one broken page — `renderSiteFiles` throws on the first nested slug
it meets, so **no** page renders. Draft preview, published render and publish all
fail together. The user's site is dark until someone repairs the definition by
hand.

## Root cause

Three things line up:

1. **Nothing validates the slug's shape.** `pageSchema.slug`
   (`packages/site-schema/src/schema.ts`) is `z.string()` carrying only the
   REQ-153 locale-shape refusal. A slug containing `/` validates cleanly and is
   written to the store.

2. **The flatness invariant is enforced at render time only.**
   `tools/generate/src/render/render.ts` throws — correctly, and for a real
   reason (REQ-109: emitted asset URLs are document-relative, which is only
   correct while every page sits flat at the snapshot root). But by then the bad
   value is already durable, and the failure is site-wide rather than scoped to
   the page that caused it. The guard is in the right place for correctness and
   the wrong place for the author.

3. **The tool surface invites it.** `add_page`'s `path` parameter was documented
   in `tools/generate/src/cli/ai/l1-surface.json` as *"Its address in the site.
   Defaults to the page id."* Nothing there said a page is one segment at the
   top level, so `papers/download` reads as a reasonable address to write.

This is a long-standing gap, not a regression from a recent change: the render
guard has been the only check since REQ-109.

The same gap exists on `pageSchema.id`, which is unconstrained and becomes the
store key `<id>.json` — a nested id writes a nested page file.

## Fix

The invariant was never wrong; its position was. A rule enforced after the value
is durable can only report a site that is already broken. The refusal moves to
the moment of the write, where the author can still act on it, and the render
guard stays as a backstop.

`packages/site-schema/src/page-name.ts` is the new home of the rule, exported
from the package index and wired into `pageSchema`.

1. **A page slug must be one addressable segment.** Refused in the schema, so
   every authoring path (`editPageAdd`, `editPageUpdate`, the AI toolbox's
   `add_page`/`update_page`, the store loader) is covered by one rule — the same
   reasoning REQ-153 used for the locale reservation. The issue is raised at
   `/pages/N/slug` so an AI author can self-correct (DOC-8 §6), and the message
   ends in a slug that would work (`papers/download` → `papers-download`) rather
   than in a description of one — the difference between a refusal recovered
   from in one turn and one recovered from in three.

2. **A page id is held to the same rule**, at `/pages/N/id`, because it is the
   key the page is stored under.

3. **`index` is refused as a slug.** `renderSiteFiles` writes `index.html` from
   the home page *after* the page loop, so a page slugged `index` is rendered and
   then silently overwritten — its address serves the home page's bytes, with
   nothing raised anywhere. Refused for every page rather than for every page but
   the home one: deciding which page is home is the renderer's rule, and
   restating it in the schema would be a second copy free to drift. Nothing is
   lost, because the home page is already served at `/`.

4. **A `.html` tail is refused as a slug**, which is the same collision from the
   other side. A page slugged `about.html` renders to `about.html.html`, so the
   address its author would write — `/about.html` — resolves to whatever
   `about.html` is: the page slugged `about`, if there is one. Two addresses, one
   page, no error.

5. **Refused, not sanitised** — and that is the deliberate difference from an
   asset name (`sanitizeAssetName`, REQ-246), which is total because refusing a
   customer's file over its filename is not a thing this product should do. A
   page name is an address chosen deliberately, published, and permanent once a
   revision ships. Quietly filing `papers/download` under `papers-download` would
   put the page at an address its author does not know, and the nav link they
   write next would 404.

6. **One issue per slug, not one per rule.** The refusals are ordered by how
   fundamental they are and the first that fires is the only one reported.
   Telling an author that `de/luxe` is both malformed and locale-shaped invites
   them to fix the wrong half.

7. **The surface stops inviting it.** `add_page`/`update_page`'s `path` says a
   page sits flat at the top level — one segment, no slashes, with
   `papers-download` named against `papers/download` — and the shared `page_id`
   type says "one word: no spaces and no slashes". `surface_version` 10 → 11.

8. **The render-time throw stays.** Defence in depth; the existing
   `test_UAT_FC_REQ-109_nested_page_fails_loud` UAT stays green.

### The allowed shape

```
/^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$/
```

RFC 3986's unreserved set less `~` — deliberately the same set
`sanitizeAssetName`/`isUnsafeAssetName` (REQ-246) admit and the same one
`SITE_KEY_PATTERN` (`apps/public-site/src/routes.ts`) admits, because all three
answer the same question: what survives being a URL path segment, an R2 key and a
filename with no encoding anywhere? Three statements rather than one shared
constant is deliberate — the Worker's copy cannot import the schema package, and
each site carries the reasoning for its own rule.

Requiring the first character to be alphanumeric is what makes `.`, `..` and
`.hidden` unreachable without naming them: a traversal is just a name that starts
with a dot, so refusing the shape refuses the family. The 64-character ceiling
matches `SITE_KEY_PATTERN`'s.

The set is lenient enough not to refuse shapes a live site may already hold
(`about_us`, `Products`, `v1.2`). Every slug in `storage/sites/` — `home`,
`contact`, `whitepapers` — is unaffected, as is every slug REQ-153's allowed list
names.

### No store-level floor, and why

Assets have one (`assertWritablePageNames`'s counterpart,
`assertWritableAssetNames`) because an asset name arrives from a client. A page
name does not: every path that *mints* one goes through `editPageAdd`, and every
other page write reuses a name the store already holds (`import-site` copies
between stores; publish copies draft → revision). A floor across four adapters
would be guarding a path that cannot produce a new name.

### Repair path for a site already in this state

A definition written before this rule now fails to **load**, loudly, naming the
field — already better than the render throw it replaces. The edit path reads
pages raw from the store rather than through the validator, so the repair is an
ordinary `update_page` with a corrected `path`, and the site renders again.

### Fixtures corrected

Five test fixtures built a home page with `slug: ''`, using the empty string as
"this page has no path segment". That was never true — the scaffolder writes
`slug: 'home'` and `index.html` is the home page's alias — and an empty slug
renders to `.html` at the snapshot root, so it is refused by rule 1. The fixtures
now carry the scaffolder's own value, which makes them more faithful rather than
less: `req107-authored-l1-envelope`, `test_UAT_FC_BUG-76_slot_error_localisation`,
`reconciliation-colour-palette-overlay`, `reconciliation-colour-shade-axis`,
`reconciliation-l1-authoring-envelope`.

## Test plan

`tests/test_UAT_FC_BUG-92_page_name_shape.test.ts` — asserted on `validateSite`
(the contract every writer funnels through) and on the real authoring entry
points `editPageAdd`/`editPageUpdate` (what the toolbox's `add_page`/`update_page`
call), never on a hand-built approximation:

- Every non-segment shape is refused at `/pages/0/slug`: `papers/download`, the
  backslash form, leading and trailing separators, `..`, `.`, `../escape`,
  `.hidden`, the empty string, a space, `?`, `#`, `%`.
- The message says why and names the flat slug to write instead.
- `de/luxe` produces exactly one issue, not one per rule.
- `index` is refused, and says it is the home page's address.
- An `.html` tail is refused.
- The rule is not over-eager: `home`, `contact`, `whitepapers`,
  `papers-download`, `about_us`, `Products`, `v1.2`, `a`, `2026-review`, and
  REQ-153's `design` / `de-luxe` / `zh-Hans` all still validate.
- A nested page **id** is refused at `/pages/0/id`.
- `add_page --path papers/download` fails with `SCHEMA_INVALID` at
  `/pages/1/slug`, the message carries `papers-download`, and the store still
  holds exactly the pages it held before.
- **The symptom, asserted directly**: after the refused add, the draft still
  loads and `renderSiteFiles` still produces `home.html` and `index.html`. The
  claim is not that the call failed but that the site did not go dark.
- The same page at `papers-download` is created normally.
- `update_page` refuses the same value, proving the rule sits behind both writers
  rather than in one of them.
- A site whose store already holds `papers/download` fails to load with the field
  named, is repaired with `update_page --path papers-download`, and renders
  `papers-download.html` afterwards.
- Every site in `storage/sites/` still validates, in its draft and in every
  published revision — a frozen revision could not be edited out of a rule that
  broke it.
