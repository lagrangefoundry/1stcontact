# The round's authentication depends on the terminal that launched the server

## What the operator experienced

The operator tried to run a diagnosis round on the console at 127.0.0.1:8710
repeatedly, and every attempt came back saying the API key was invalid. Since
the console is supposed to run the round through the Claude Code CLI on the
operator's own subscription — `claude -p`, no API key anywhere — the reasonable
reading was that the console had stopped using the CLI and was calling the API
directly behind their back.

It had not. The console did spawn `claude -p`. The CLI then authenticated with
an API key it found in its environment, and that key was dead.

## Evidence

`storage/tmp/repro-console/repro-gigabytealchemy-ai/iteration-8/ai/transcript.txt`:

```
— session started (claude-opus-5[1m])
— api_retry            (×10)
Failed to authenticate. API Error: 401 API key is invalid.
— round finished · $0.00 · 3m 02s · 1 turn · 0→0 tok
```

The first line is `formatStreamEvent`'s rendering of the CLI's own `system`/`init`
event, so the CLI started and named its model before anything failed. The zero
cost and `0→0 tok` are the 401: the round never reached the model.

## The mechanism

`tools/repro-console/src/ai.ts`, in `attempt()`:

```ts
const child = spawn(command, args, { cwd: opts.cwd, stdio: ['pipe', 'pipe', 'pipe'] })
```

No `env` is passed, so the child inherits the console server's `process.env`
verbatim — and the Claude Code CLI prefers `ANTHROPIC_API_KEY` over the
subscription login it is signed in with. This repo already states that
precedence as a known rule, in `bin/kb-release`:

> Needs CLOUDFLARE_API_TOKEN for the Workers AI embedder. The map's paragraphs
> are written by the Claude Code CLI **when no ANTHROPIC_API_KEY is set**, so it
> needs no credential of its own.

So which credential a round runs on is decided by the shell the operator
happened to start `bin/repro-console` from. `bin/deploy` requires
`ANTHROPIC_API_KEY` to be exported — `bin/deploy.d/secrets/10-anthropic-api-key`
asks for exactly that, and `~/.zshrc` carries an `export-anthropic-key` alias to
do it — so a terminal used for a deploy and then for the console is an ordinary
sequence, not a mistake. Whether the round then works depends on whether that
exported key is still good.

Two things confirm the environment and not the invocation is at fault:

- The same invocation shape, `--setting-sources ''` included, run from an
  environment with no `ANTHROPIC_API_KEY`, authenticates and returns normally.
- The key on disk at the path the alias reads is live (HTTP 200 on
  `/v1/models`), so the value in the failing server's environment is some other,
  older one — a stale export that outlived the file it came from.

## Why this is not just an operator error

`claudeCommand` is a pure function of the environment, and its doc comment says
why: *"so the tool policy is assertable without spawning anything — which is the
only way a test can prove that the process the console starts cannot write
code."* The tool policy got that treatment. The credential did not. The one
property the console most wants to be true of every round — that it runs on the
operator's Claude Code subscription — is currently a property of the launching
shell, which no test can reach and no page can show.

The cost is per attempt, not once: the CLI retries ten times before giving up,
so each attempt burns about three minutes of wall clock. The operator spent
several of those.

`AI_COMMAND_ENV` and `AI_MODEL_ENV` are read from the same environment and are
deliberate operator overrides, so this is a targeted removal, not a clean slate.

## Behaviour wanted

1. **A round authenticates as the operator's Claude Code CLI does, regardless of
   the environment the console server was started in.** The credential variables
   that would redirect the CLI away from its own login — an Anthropic API key, a
   bearer auth token, a base-URL override, and the Bedrock/Vertex provider
   switches — are removed from the child's environment at the spawn.
2. **The operator's own knobs survive.** `REPRO_CONSOLE_AI` and
   `REPRO_CONSOLE_AI_MODEL` are read from that same environment and still take
   effect; so does everything else the CLI needs to run, which is why this
   removes named variables rather than passing a minimal environment.
3. **The guarantee is assertable without spawning a process**, the way the tool
   policy already is: the environment a round would be given is computable and
   testable on its own.

## Acceptance

- Given a server environment carrying `ANTHROPIC_API_KEY`, the environment the
  console hands `claude -p` does not contain it, and the same holds for
  `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, `CLAUDE_CODE_USE_BEDROCK` and
  `CLAUDE_CODE_USE_VERTEX`.
- `REPRO_CONSOLE_AI` and `REPRO_CONSOLE_AI_MODEL` set in the server environment
  still reach the child and still select the executable and the model.
- The child environment is otherwise the server's, so a round still finds `node`,
  `git`, `xgd` and `1c` on `PATH` and still resolves the operator's home.
- The sanitisation is asserted from a pure function, with no process spawned.
- The `claudeCommand` argv, the permission mode, both tool lists and the resume
  behaviour are unchanged.
