## What happens

A valid access-sim token is ignored by the control app. Signing in at
`http://127.0.0.1:8799/login` and picking a person leaves the builder anonymous, on
both the watch builder (8788) and the deployed dev environment (8789).

Reproduced with curl, so it is not a browser or cookie-jar artefact:

```
$ TOK=$(curl -s 'http://127.0.0.1:8799/mint?email=martin@westhead.me')   # 626 chars
$ curl -H "Cookie: CF_Authorization=$TOK" http://127.0.0.1:8788/api/businesses
{"person":null,"businesses":[{"id":"biz_51a6746495c8057e886ff98d4208e6b9",
 "name":"biz_51a6746495c8057e886ff98d4208e6b9","selectable":true,"lapse":null}],
 "ownsPlatformBusiness":false}
```

Identical on 8789. `person: null`, one business shown by its raw id, and
`ownsPlatformBusiness: false` for an email that **is** in `PLATFORM_ADMINS`.

## Why — the token is not ignored by accident

`.dev.vars` blanks `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD`; `wrangler.toml` sets
`ACCESS_DEV_OPEN = "1"`. So `isUnconfiguredLocalDev` is true, and on that branch
`index.ts:440` skips **both** the Access gate and `admit`. `scope.ts` states the
consequence outright: *"On that path there is no token, no verified email and no
admissible set, so there is nothing for a fallback to choose FROM."*

**Dev-open mode and "signed in as a person" are mutually exclusive, and that is
correct.** Dev-open is an anonymous caller with full access to `TENANT_ID`. Nothing
here is wrong with `index.ts` or `scope.ts`.

What is wrong is that the documented way to leave dev-open mode does not work.
`bin/access-sim` tells the operator:

    point the Worker at it:  ./bin/access-sim --print-env > .dev.vars.local

`--print-env` emits `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD` and `SERVICE_TOKEN_IDENTITIES`
pointed at the simulator. Un-blanking that pair is exactly what makes
`isUnconfiguredLocalDev` false and switches the Access path on. The simulator's JWKS
endpoint is up and answering, so its half of the exchange is healthy.

## Two faults, either one sufficient

**1. `apps/control-app/.dev.vars.local` is 0 bytes**, dated 2026-09-06. The values were
never written, or were truncated. On this machine, today.

**2. It would not be read even if it were populated — and this is the one that
matters.** `devEnvLayering` (`tools/generate/src/cli/dev-env.ts`) composes exactly two
`--env-file` flags: `.dev.vars` and the secrets file. Its own comment records why that
is decisive:

> `--env-file` REPLACES the default `.dev.vars` lookup rather than adding to it
> (wrangler's `getVarsForDev` guards that read with `if (!envFiles?.length)`)

So `.dev.vars.local` sits outside the layering for **both** `1c builder` and
`1c dev serve`. Before [[BUG-50]] made the builder's argv explicit, wrangler's own
`.dev.vars*` lookup would have found it; after, nothing does.

**This is a documentation/implementation split, which is why it presents as a mystery
rather than as an error.** `bin/access-sim` still prints instructions for a file no
launcher reads, and a file that is read but empty and a file that is not read at all
produce the identical symptom. The operator follows the printed instruction, sees no
change, and has nothing to look at.

## The third trap on the same path

`1c dev serve`'s banner (`snapshotSummary`, `dev-snapshot.ts:185`) prints
**`http://localhost:8789`**. `CF_Authorization` is host-scoped to `127.0.0.1`, and
`bin/access-sim` is explicit that this is load-bearing:

> Cookies are scoped by HOST and ignore the PORT, so a cookie set on 127.0.0.1:8799
> is sent to the builder on 127.0.0.1:8788. It is NOT sent to `localhost:8788` — a
> different cookie host — which is why the redirect below names the same host the
> operator will browse.

access-sim took care to name the host the operator will browse; the new environment's
banner then names the other one. Once faults 1 and 2 are fixed, an operator who opens
the URL `dev serve` printed is logged out again, for a third and different reason.
`builder.ts:482` prints `localhost` too, so this is a pre-existing wart that REQ-318
inherited rather than invented — but it is now on the path the operator is being moved
onto, and it should be `127.0.0.1` in both.

## What is NOT broken

Worth stating, because each was checked and excluded:

- The store is intact. access-sim's `/login` lists 19 seeded people, read live from D1.
- Both servers serve the builder shell and answer 200 on both hosts and both ports.
- `1c workerd` reports one version; the two workerds sharing `.wrangler/state` are not
  implicated.
- The simulator's JWKS endpoint answers with a well-formed RSA key.
- `ACCESS_DEV_OPEN` is behaving exactly as designed; this is not a security hole.

## The workaround, which needs no fix

The secrets file IS in the layering and is loaded **last**, and `devEnvLayering` records
that last wins: *"Wrangler parses these with `override: true`, so the last file wins."*
So appending the simulator's values there beats `.dev.vars`'s blanks today:

    ./bin/access-sim --print-env >> ~/Documents/secrets/1c.dev.env

then restart the servers. Neither value is a credential — `wrangler.toml` says so
explicitly, the team domain is public and the AUD is an identifier — so the secrets file
is an odd home but a harmless one. **No redeploy is needed for 8789**: env-files are read
at server start and are not baked into the snapshot, so the freeze does not cover them.

That this workaround exists is itself part of the finding: the mechanism is sound and
only the wiring of one file is missing.

## Acceptance

- With `.dev.vars.local` populated by `./bin/access-sim --print-env` and the servers
  restarted, a token minted at `127.0.0.1:8799/mint` resolves a person: `/api/businesses`
  returns a non-null `person`, and `ownsPlatformBusiness` is true for an email in
  `PLATFORM_ADMINS`.
- The same holds on **both** 8788 and 8789 — one layering, both launchers.
- `.dev.vars.local` is loaded AFTER `.dev.vars`, asserted on the composed argv rather
  than observed in a running server, so the override direction cannot silently invert.
- An absent `.dev.vars.local` is not an error and not silent: it warns in the shape
  `devEnvLayering` already uses, naming the resolved path and what will not work —
  "access-sim cannot sign anyone in; the Worker is in dev-open mode".
- A 0-byte or Access-var-less `.dev.vars.local` is reported as distinct from an absent
  one, because those were indistinguishable here and cost the diagnosis.
- `1c dev serve`'s banner and `1c builder`'s printed URL both say `127.0.0.1`, and a UAT
  pins it to access-sim's cookie host rather than to a literal.
- `bin/access-sim`'s printed instructions name a file the launchers actually read.

## Boundaries

- **No change to `isUnconfiguredLocalDev`, the dev-open branch, or `admit`.** They are
  correct; REQ-147's two-independent-mistakes standard stays exactly as written.
- **No change to what `--print-env` emits.** The three keys are right; only where they
  are written and whether anything reads them is in scope.
- **`.dev.vars.local` stays gitignored and per-clone.** This ticket wires it in, it does
  not commit anyone's copy.


## The secrets-file workaround is hazardous, and that argues for this fix

The workaround offered while this ticket sat unbuilt — append `--print-env` to the
secrets file, which **is** in `devEnvLayering` and **is** read last — failed on the
operator's machine, and not for a reason either fault above predicts.

`~/Documents/secrets/1c.dev.env` ended without a trailing newline, so `>>` fused two
settings into one line:

    CLOUDFLARE_ACCOUNT_ID=<hex>ACCESS_TEAM_DOMAIN="http://127.0.0.1:8799"

Net: `ACCESS_TEAM_DOMAIN` undefined, `ACCESS_AUD` and `SERVICE_TOKEN_IDENTITIES` defined,
`CLOUDFLARE_ACCOUNT_ID`'s value corrupted. That state is worse than dev-open:
`isUnconfiguredLocalDev` needs BOTH Access vars empty, so a populated `ACCESS_AUD` alone
switches the gate on, and `guardAccess` then refuses **every** request 503 for an empty
`ACCESS_TEAM_DOMAIN`.

Relevant to this ticket in two ways:

- **It is an argument for the fix, not for a better workaround.** The recipe this ticket
  restores writes `.dev.vars.local` with a truncating `>`, which cannot fuse lines. The
  append hazard exists only because the file the recipe names is not read.
- **The three keys are not credentials** (`wrangler.toml` says so: the team domain is
  public and the AUD is an identifier), so the secrets file was always the wrong home for
  them on grounds of meaning as well as safety. Whatever this fix does, it should leave
  no path where an operator is advised to put Access configuration in the secrets file.

One more thing the fix should not have to discover: an env-file change only takes effect
on a process started after it, and `bin/dev up` deliberately leaves an answering port
alone without writing a pidfile, so `bin/dev down` cannot stop it. On this machine that
left the 8788 builder running with the pre-change environment and hid the corruption
entirely — its `/api/businesses` still answered in dev-open shape. `bin/dev reap`
(`ours && !managed`) is what reaches such a process. Recorded on [[EPIC-16]] §N8; the
supervisor half belongs to [[REQ-322]], not here.


**Correction on the restart half:** the paragraph above attributes it to `up` leaving an
answering port alone, and hands the supervisor question to [[REQ-322]]. Measured since,
that was wrong: `up` DID start this builder and recorded the `bin/1c` wrapper's pid
rather than the `workerd` grandchild's, so `down` signals a process that is not serving
and `1c ps` reports the service as unowned. That is [[BUG-147]], not REQ-322, and it is
why this ticket's workaround could not be tested — the builder kept the pre-change
environment across a `down && up`.


## What was built

`.dev.vars.local` is now the third `--env-file` in `devEnvLayering`, so both
launchers load it. Everything below is either that, or a consequence of it that had
to be decided rather than inherited.

**It lives beside `.dev.vars`, in the config directory** —
`apps/control-app/.dev.vars.local`, not the repository root the old recipe named.
`--env-file` resolves a relative argument against the config directory, so a
sibling needs no `../../`; and one location is the point, because this machine had
a populated copy at the root and an empty one in the app directory, which is the
ambiguity that cost the diagnosis. `devVarsLocalPath()` is the only place that
path is built, and the printed recipes are checked against it.

**It loads LAST, after the secrets file.** The acceptance only requires "after
`.dev.vars`", but the ordering against the secrets file is a real choice: the
retired workaround appended the same vars there, so putting the local file last is
what makes the supported recipe beat a leftover workaround instead of losing to it.
That is also the `.env` / `.env.local` convention.

**Half a configured Access pair is now reported too.** `isUnconfiguredLocalDev`
needs BOTH vars empty, so one alone switches the real gate on and `guardAccess`
refuses every request 503 — the exact state the newline-less `>>` produced above,
and a state strictly worse than dev-open. It is asked of the composed result rather
than of any one file, because no single file is wrong in it. A UAT drives the real
Worker to confirm the 503 the warning claims.

**`bin/seed` printed the same recipe** and is corrected with `bin/access-sim`; both
now name the layered path and point at `./bin/1c builder` rather than a hand-rolled
`wrangler dev` with three `--env-file` flags, because the reason for launching by
hand was precisely the missing slot. A UAT holds every `--print-env >` redirect in
`bin/` against `devVarsLocalPath()`, and asserts no script advises `--print-env`
into the secrets file — the second half of "leave no path where an operator is
advised to put Access configuration there".

**The cookie host is one constant.** `DEV_HOST` / `devUrl(port)` in `dev-env.ts`,
used by `1c dev serve`'s banner, `1c builder`'s printed URL and `startBuilder`'s
handle URL (`builder.ts`, the pre-existing wart), so the three cannot drift apart.
The UAT pins `DEV_HOST` to the issuer `bin/access-sim --print-env` publishes rather
than to a literal, which is the property that matters: the two processes agreeing.

**`readDevEnv` is now a merge of what the layering already parsed**, rather than a
second pass over the same files, because the layering has to read them anyway to
tell an empty file from an incomplete one.

## What the UATs prove, and where they stop

`tests/test_UAT_FC_BUG-146_dev_vars_local.test.ts` runs the real simulator, asks it
for the real `--print-env`, writes it where the recipe says, composes the real argv
for **both** launchers, derives the vars the way wrangler derives them, and hands
those to the product's own gate. Both directions are asserted in one leg: with the
file, an anonymous request is refused 401 and a minted token is admitted; without
it, the same anonymous request is waved through by dev-open. Nine of eleven legs
fail with the third `--env-file` removed.

They stop at the gate. The ticket's boundary is that `isUnconfiguredLocalDev`, the
dev-open branch and `admit` are unchanged and correct, so the new fact is the
layering REACHING the gate — the admitted path with a real database, a real grant
and a resolved person is already proved in
`test_UAT_FC_REQ-167_identity.workers.test.ts`, which has bindings for it. This node
suite has none, so it proves the join rather than approximating the far side.

The fixtures pin `$HOME` to a temporary directory. Without that they read the
operator's own secrets file — which on this machine holds the retired workaround,
so every assertion about a blanked or half pair would measure the workaround rather
than the fix, and would pass or fail according to whose laptop ran it.
