## Symptom

Session `chat-d73a11e1` ("Lagrange Foundry — initial website build", 2026-09-09
22:52–23:30). Two distinct failures, both visible to the operator:

**1. Reference capture "failed" on a site that was up.** The AI tried three
hostnames it had invented and reported all of them dead:

| Attempt | URL | Result |
|---|---|---|
| 23:01:20 | `https://www.gigabytealchemy.com` | `Navigation timeout of 30000 ms exceeded` (~90s: 3×30s) |
| 23:01:34 | `https://www.1stcontact.io` | `net::ERR_NAME_NOT_RESOLVED` |
| 23:18:47 | `https://www.gigabytealchemy.ai` | `net::ERR_NAME_NOT_RESOLVED` |
| 23:20:29 | `https://gigabytealchemy.ai/` | **succeeded** — 7 pages, 5 assets |

It then told the operator *"Gigabyte Alchemy isn't reachable — the site may
already be down"* and *"Both reference sites are offline"*. Neither statement was
true. It only tried the bare apex after the operator pasted the exact URL and
said *"are you sure you can't reach it...if so that's a bug"*.

**2. Twelve consecutive silent failures writing the page.** From 23:21:55 to
23:30:11 the AI issued `set_l1` twelve times, ~45s apart. Every call arrived at
the toolbox with **empty input** and was refused identically:

```
Input:  {}
Result: Error: set_l1 requires parameter 'page' (A page's id — short, lowercase, …)
```

Audit records confirm `"params":{}`, `"policy":{"decision":"refuse","rule":"schema"},
"durationMs":0`. The turn ended on the 600s timeout with the AI saying
*"Apologies for that — something went wrong on my end."* No page was ever built.
~9m42s of the operator's time, zero output.

Preceding calls in the same turn (`set_page_style`, `update_page`,
`add_palette_color`) all carried their arguments correctly — only the large one
lost them.

## Root cause

### Defect A — `max_tokens: 4096`, and truncation is invisible

`lagrange-framework/components/ai/js/src/backends/claude_api.js:192` hardcodes
`max_tokens: 4096` on every request. The model is `claude-sonnet-4-6`
(`claude_api.js:39`), which supports 64k output tokens — so ~94% of the available
budget is unused.

A whole-page L1 tree for a five-section site does not fit in 4096 tokens. The
model spends ~45s emitting the `node` argument, hits the cap mid-JSON, and the
tool call is truncated. Then:

- `AnthropicAccumulator` (`backends/api_tools.js:727–763`) initialises
  `block.input = {}` at `content_block_start` and only replaces it at
  `content_block_stop`, where `JSON.parse(partialJson)` either succeeds, or on
  failure yields `{ raw: partialJson }`. A stream cut short leaves `input` as the
  initial `{}`.
- **Nothing anywhere in the package inspects `stop_reason`** — `grep -rn
  stop_reason components/ai/js/src` returns zero hits. `max_tokens` is therefore
  indistinguishable from a normal `end_turn`.
- The toolbox validator (`toolbox/params.js:100`) reports the *downstream*
  symptom: `requires parameter 'page'`. That message is false about what
  happened — the model did send `page` — so it gives the model nothing to act on.
- The model retries the identical call. `MAX_TOOL_ITERATIONS = 50`
  (`api_tools.js:35`), so nothing stops the loop; the 600s turn timeout ends it.

The failure is structural, not incidental: the documented path for "build a page"
is `describe_page → get_l1 → set_l1` at the root (`l1-surface.json` sequences),
`set_l1` replaces a whole subtree, and there is no insert/append operation and no
documented size ceiling. So the only way to build a page from scratch is a single
call that is guaranteed to exceed 4096 tokens for anything non-trivial.

### Defect B — capture retries a deterministic DNS failure and never tries the apex

`tools/generate/src/cli/capture/pipeline.ts:236–250` retries `captureOnce`
unconditionally three times with no error classification, and does no hostname
normalisation:

- `ERR_NAME_NOT_RESOLVED` cannot change between identical attempts — three tries
  is pure latency.
- A guessed `www.` prefix that does not resolve is never retried against the
  apex (or vice versa), even though that is the single most common cause of a
  "this site is down" false negative.
- The error text surfaces the raw Chromium code and offers no hint that the
  hostname, not the site, may be at fault — which is why the AI concluded the
  site was down and told the operator so.

## Fix

**Defect A** (in `lagrange-framework`, `components/ai/js/src`):

1. Raise `max_tokens` from 4096 to a value that matches the model's real output
   ceiling, and make it configurable per backend rather than hardcoded.
2. Read `stop_reason` off the stream. When a turn stops at `max_tokens`, do not
   present a truncated tool call as a schema violation — fail it with an error
   that names what actually happened ("the arguments were cut off at the output
   limit; send a smaller subtree") so the model can adapt instead of repeating.
3. Treat a `tool_use` block whose accumulated JSON does not parse as a
   truncation, not as `{}` / `{raw:…}` — the current fallbacks both produce
   misleading downstream errors.

**Defect B** (this repo, `tools/generate/src/cli/capture/pipeline.ts`):

4. Classify capture errors: retry transient failures (timeouts, resets), fail
   fast on deterministic ones (`ERR_NAME_NOT_RESOLVED`).
5. On a DNS failure, retry once against the alternate host form — strip a `www.`
   prefix, or add one if absent — and report which form succeeded.
6. Make the failure message say what a caller can do about it, rather than
   passing the Chromium code through.

**Craft note (no code):** the AI reported a platform/product failure
("the site may already be down") on the evidence of its own guessed hostname.
DOC-48 §9 already says a refusal is evidence about your syntax, not about the
platform. This is the second recorded instance of that failure mode
(the first: DOC-17 §G, reporting shipped capabilities as missing) and belongs in
the design-lessons log.

## Scope

The primary defect is in the shared `@lagrangefoundry/ai` package, which lives in
the `lagrange-framework` repo — outside this repo's ticket store. Fixing it needs
a ticket there. Defect B is local to this repo.

## Test plan

Once a fix is authorised:

- `test_UAT_FC_BUG-67_*` in this repo: capture pipeline given a driver that
  throws `ERR_NAME_NOT_RESOLVED` on `www.<host>` and succeeds on `<host>` —
  assert one navigation per host form (not three) and a successful capture;
  assert a transient timeout still retries.
- Framework-side UAT: an accumulator fed a stream that stops at `max_tokens`
  mid-`input_json_delta` must surface a truncation error naming the output
  limit, not an empty-input schema refusal.
