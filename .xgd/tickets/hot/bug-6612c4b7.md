## Symptom

Switching the builder to **Edit** mode on `app.1stcontact.io` returns
Cloudflare **Error 1102 — Worker exceeded resource limits**. Reported as 100%
reproducible: every switch to Edit produces it. View mode is unaffected.

## What Edit mode actually requests

Edit is not a separate route. `apps/control-app/src/builder/app.js:82-90`
registers two panel modes over the same preview URL builder:

| mode | `src` |
|---|---|
| View | `/preview/<slug>/draft/` |
| Edit | `/preview/<slug>/edit/` |

So the failing request is `/preview/<slug>/edit/`, handled at
`apps/control-app/src/router.ts:567` and served by
`PreviewRenderer.file(slug, 'edit', rel)`.

**This matters for reproduction.** An earlier investigation probed `/edit/...`
and reported 200 with ~51KB. `/edit/...` matches no route: it falls through to
`env.ASSETS.fetch(request)` (`router.ts:582`) and returns a build artifact. That
pass therefore never exercised the edit render, and its "cannot reproduce" is
not evidence.

## Leading hypothesis — the preview render cache never hits in the Worker

`PreviewRenderer` memoises a whole `RenderedSite` per `slug\0channel`
(`tools/generate/src/cli/preview.ts:85,147-161`). The router holds those
renderers in

```ts
// apps/control-app/src/router.ts:78
const PREVIEWS = new WeakMap<TenantSiteStore, PreviewRenderer>()
```

keyed on the **store handle**. But `storeFor` constructs a fresh handle per
request, deliberately and correctly — the tenant check must not be memoised
across requests, or a handle would outlive a deactivation
(`apps/control-app/src/store.ts`).

The two are incompatible. A new store object per request means a new WeakMap key
per request, so:

- the renderer cache is dead in the Worker — **every** preview request renders
  the entire site from the definition, and
- each request allocates its own `PreviewRenderer` holding a complete
  `RenderedSite` (every page's HTML plus CSS as strings), live until GC.

Workers memory is per-**isolate** and shared across concurrent requests, so N
concurrent previews hold N whole site renders simultaneously. That shape matches
the observed kill better than a CPU ceiling does: the recorded victim burned
**94ms CPU** with **zero subrequests** and died roughly seven seconds after a
12-request burst — a request that is not CPU-bound, dying while the isolate is
crowded.

Why Edit and not View: the edit channel renders with `{ edit: true }`
(`preview.ts:157`), which additionally stamps segment addresses through the
document. It is the larger of the two renders, on the same dead cache.

## The `deps.store` complication

`RouterDeps.store` is a factory, not a store. The Node transport already works
around the same problem in `tools/generate/src/cli/builder.ts` by memoising the
handle per workspace, with a comment naming this exact hazard:

> the router caches a `PreviewRenderer` against the store OBJECT, so handing
> back a new one per request would rebuild the render cache on every fetch.

So the Node transport gets caching and the Worker does not, and the divergence
is invisible because both satisfy the same interface. Whatever fix is chosen
should close that gap rather than add a second workaround.

## Candidate fixes — for design, not yet chosen

1. **Re-key the renderer cache off something stable.** `<tenantId>\0<slug>` is
   the natural key and is available at the router. Removes the WeakMap's
   dependence on object identity entirely. Cache invalidation is already handled
   inside `PreviewRenderer` by the draft `stamp`, so a longer-lived renderer does
   not serve stale bytes.
2. **Bound what a render holds.** Even with a working cache, one
   `RenderedSite` per site per channel is retained per isolate. Worth measuring
   before assuming (1) is sufficient.
3. **Stream or paginate the edit render.** Only if (1) and (2) prove
   insufficient; much larger change.

Not decided here. (1) is the cheapest thing that would falsify the hypothesis.

## Prerequisite — there is no telemetry to confirm any of this

`apps/control-app/wrangler.toml` declares **no `[observability]` block**, so the
account retains no invocation logs, only aggregate analytics. That is why the
earlier attempt could establish *that* a request was killed but not *which URL*
killed it.

**Do this first.** Add `[observability]` (and repeat it under
`[env.production]`, which inherits nothing — the file already documents that
trap at lines 51 and 75), redeploy, reproduce once, and read the actual failing
request. Every claim above is inference from source plus aggregate counters
until that lands.

## Reproduction

```bash
# needs a Cloudflare Access service token — see apps/control-app/ACCESS.md,
# provision with bin/access-token
curl -sS -o /dev/null -w '%{http_code}\n' \
  -H "CF-Access-Client-Id: $CF_ACCESS_CLIENT_ID" \
  -H "CF-Access-Client-Secret: $CF_ACCESS_CLIENT_SECRET" \
  https://app.1stcontact.io/preview/xgd/edit/
```

Compare against `/preview/xgd/draft/`, which is reported working.
