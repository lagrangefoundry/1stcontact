## Symptom

The spend meter under-reports every turn that writes to the prompt cache. `prices.json` prices `cache_write` at 1.25× the input rate (Opus 5.5 $5/M, Haiku 4.5 $1.25/M). That is the **5-minute** cache rate. Every request this product sends asks for the **1-hour** cache: the framework's `DEFAULT_CACHE_TTL` is `'1h'` (`@lagrangefoundry/ai` `api_tools.js`), and no backend here overrides it. The API bills 1-hour cache writes at **2×** the input rate (Opus 5.5 $8/M, Haiku 4.5 $2/M).

So every cache write is priced at 62.5% of what it costs. On Bob's Salon 3 (2026-10-20/21) the meter says $42.46; re-priced at the 1-hour rate it is about $49.60:

| | metered writes | at 1-hour rate |
|---|---|---|
| Consultant (Opus 5.5) | $5.35 | $8.56 |
| Builders (Haiku 4.5) | $6.53 | $10.45 |

Every figure EPIC-20 has drawn from `turn_spend` since REQ-292 carries the same error. The meter is the instrument the epic's decisions rest on, so this outranks the cost work it measures.

## Fix

**A cache write is priced at the rate of the lifetime it was written with.**

- `prices.json` carries both write rates per (backend, model): `cache_write_5m` (1.25× input) and `cache_write_1h` (2× input), replacing the single `cache_write`. Its `about` text explains why there are two.
- Until the usage record says which lifetime each written token had (lagrange-framework REQ filed alongside this ticket, see below), a turn's writes are priced at the rate of the lifetime **its backend requested**. Today that is 1 hour for every backend. The meter reads that from the same place the backend does, not from a constant in the pricing code.
- When the usage record carries the split (`cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens`, as the API reports it), each part is priced at its own rate. Rows already written keep their stored `cost_micros`; this ticket does not re-settle history.
- The same pricing applies to delegated spend (`attributed` entries priced by their own backend and model), which is where the console's delegated figures come from.

Out of scope: changing which lifetime any backend requests (that is the builder caching REQ under EPIC-20).

## Upstream

The per-lifetime split needs lagrange-framework to keep `usage.cache_creation`'s two counters in its usage record. Filed there as part of the cache-lifetime REQ. This ticket ships without it: the requested-lifetime rate is exact for every turn today, because every backend requests one lifetime for everything.

## Test plan

- `test_UAT_FC_<ID>_*`: a turn on a backend requesting the 1-hour cache, with known counters, settles `cost_micros` with writes at 2× input; one requesting the 5-minute cache settles at 1.25×.
- A delegated entry on `claude_builder` is priced at Haiku's 1-hour write rate.
- A usage record carrying the 5m/1h split prices each part at its own rate.
- Existing REQ-292 / REQ-293 / REQ-297 / BUG-145 pricing UATs updated where they pin the old single rate; say which in the commit.
