`bin/smoke` reports **1 failed, 2 passed, 7 skipped** against production. Seven of ten
checks did not run, and six of them skip for one reason: no `--site-key` was given. A
check that only runs when an operator remembers a flag is a check that will not run.

This is the assertion surface for "did the deploy actually serve anything", so the
skips are worse than ordinary test debt: the one moment it exists for is the moment
nobody is in a position to supply the argument it wants.

## Why the current design skips, and where the reasoning stops short

The script's header is right about what it refuses to depend on:

> The published-channel checks need a site key and cannot discover one — a key is 128
> random bits and this script takes no dependency that could ask D1 for it.

True of D1, and the no-dependency rule is worth keeping — `bin/smoke` runs straight
after a deploy on whatever Node is there, and a bundler or a package in that path is a
new way for the diagnostic to be unavailable when it is needed.

**But four of the six checks do not need a key.** `APEX_SITE_KEY` names a published
site served at the root of the host, so when an apex is configured the apex *is* the
published channel, and these assertions have a target already:

| Check | Needs a key? |
|---|---|
| `published_index_serves_html` | No — `GET /` and its content type |
| `published_cache_policy` | No — `cache-control` on `/` |
| `published_miss_is_404` | No — a missing asset and a missing directory under `/` |
| `published_assets_resolve` | No — crawl from `/`, which is the whole point of the check |
| `published_root_redirects` | **Yes** — it asserts the `/site/<key>` → `/site/<key>/` grammar |
| `unpublished_site_indistinguishable` | **Yes** — it needs a key that exists and has published nothing |

So the honest split is four checks that should run unconditionally whenever the apex
serves, and two that genuinely require an argument.

The implementer should confirm one thing first: that the apex path and the
`/site/<key>/` path serve through the same code with the same headers in
`apps/public-site/src/index.ts`. If they diverge, asserting the cache policy at `/` is
a different assertion from asserting it at `/site/<key>/` and the ticket's premise
needs revisiting rather than working around.

## The other skips

`control_app_workers_dev_closed` skips without `--workers-dev-origin`. The script
already derives `--control-origin` for the known apex rather than making the operator
retype it — [[BUG-57]] records that making them retype it is what left the [[REQ-147]]
gate unchecked by default. The same argument applies here, and this check guards a real
exposure: `apps/public-site/wrangler.toml` still declares `workers_dev = true`.

The account's workers.dev subdomain is not in the repository, so this one may not be
derivable. If it is not, say so **in the output** — "not derivable, pass
`--workers-dev-origin`" is a different report from a silent skip, and the config's
`workers_dev = false` declaration can be pinned by a static check meanwhile.

`unpublished_site_indistinguishable` has a second, softer version of the same problem:
even when it runs it can return *"the site has a live revision; nothing to compare"* and
report a pass having asserted nothing. A check that passes without asserting is
indistinguishable from one that holds.

## What this asks for

1. **The four apex-reachable checks run whenever an apex is configured**, with no flag.
2. **`--site-key` remains** for the two that need one, and those two report clearly that
   they were not asked to run rather than appearing as ordinary skips beside checks
   that could have run and did not.
3. **No new dependency.** If the apex key has to be read from
   `apps/public-site/wrangler.toml`, a line match is enough — no TOML parser, no
   package. Reading a file in the repo it ships in is not the dependency the header
   argues against; asking D1 is.
4. **A skip must say what would make it run**, and the summary line must distinguish
   "not applicable to this deployment" from "nobody supplied an argument". The present
   output gives the same word to both.
5. **A check that asserts nothing must not report `pass`.** Give
   `unpublished_site_indistinguishable`'s no-op branch its own outcome.

## Explicitly not in scope

`apex_resolves` failing today is not a defect: the deployment has published nothing and
`APEX_SITE_KEY` is empty, so a 404 is the correct answer and smoke is right to fail on
it. Nothing here should make that failure quieter.

## Done looks like

`bin/smoke`, run with no arguments against a deployment that has published its apex,
exercises the asset crawl, the content types, the cache policy and the 404-on-miss —
none of which have ever run against this product — and every remaining skip names the
argument that would turn it into a check.

## What was built

### The four root-only checks address the apex, with no flag

`published_index_serves_html`, `published_cache_policy`, `published_miss_is_404` and
`published_assets_resolve` now address a **published channel root** that is `/` unless
a key names somewhere else. Confirmed first, as the ticket asked: `route()` in
`apps/public-site/src/index.ts` handles `case 'apex':` and `case 'asset':` in **one
branch** into one `serve()`, so the apex and `/site/<key>/` are the same assertion
rather than two similar ones. The premise holds.

**What counts as a published apex**: `GET /` answering `200` with a `text/html`
content type. The content type is part of the question rather than pedantry — an
origin can answer 200 at `/` with something that is not a site (a health endpoint, a
staging origin's plain-text greeting), and pointing four assertions at it would report
four failures about a deployment that never claimed to publish an apex. A false alarm
is worse than a skip; that is already this script's rule for `--control-origin`.

The consequence is deliberate and is not a hole: an apex serving `200 text/plain`
**skips** rather than failing, because that is indistinguishable from an origin with
no published apex. An apex serving HTML with the *wrong* type — a Worker that stopped
setting the charset — is a genuine breakage and does fail.

**`--site-key` wins when both are available.** An operator who names a site wants that
site smoked; a run that quietly asserted against the apex instead would be answering a
question nobody asked. Every one of the four names the root it read in its detail line,
so a pass says what it proved.

### `skip` and `n/a` are different words with different meanings

- **`skip`** — nobody supplied an argument, and the detail names the argument.
- **`n/a`** — this deployment has nothing for the check to assert against; no argument
  fixes it. It is also what a check reports **instead of a pass when it compared
  nothing**.

They are counted apart in the summary (`… N passed, M skipped, K not applicable to
this deployment.`), and the `n/a` clause is absent rather than reading `, 0 …` when
none apply. A run in which no check either passed or failed adds a line saying so in
as many words.

`unpublished_site_indistinguishable`'s "the site has a live revision" branch is the
`n/a` case the ticket names, and its detail says what key would let it assert.

### What each remaining skip says

- The two key-needing checks state what only a key has — the `/site/<key>/` grammar,
  and a key that exists and has published nothing — so they read differently from
  checks that could have run against this deployment and did not.
- The four root-only checks, when there is no root, name **both** halves: `--site-key`
  would run them, and so would publishing the apex. Against the default apex the
  reason also reads `APEX_SITE_KEY` out of `apps/public-site/wrangler.toml` and reports
  that it is empty — a line match via `node:fs`, best-effort and swallowed on any
  error, decorating a check that has already decided its outcome rather than deciding
  it. No TOML parser, no package, no question to D1.
- `control_app_workers_dev_closed` says it **cannot be derived** and why (the hostname
  embeds the account's workers.dev subdomain, which is nowhere in this repository), and
  points at the `workers_dev = false` declaration in `apps/control-app/wrangler.toml`
  that `test_UAT_FC_REQ-147_control_app_answers_on_no_workers_dev_hostname` already
  pins statically — while saying that only a request proves the door is shut.

### A technical consequence: the cache policy has two legal answers

`serve()` rewrites a page carrying account chrome per visitor and marks that response
`private, no-store` with `vary: cookie`. Which policy applies is a property of the
**page**, so it is the same question at `/` and at `/site/<key>/` — but the apex is
this product's own front door and therefore the page most likely to carry chrome. A
check that knew only `public, max-age=60` would report a **failing** cache policy for a
correctly-served apex, which is exactly the false alarm moving the check to `/` must
not create.

`published_cache_policy` therefore asserts the policy the Worker defines for the
response it got: the session policy when the response varies on cookie, the shared one
otherwise. `vary: cookie` is asserted rather than merely consulted — session bytes in a
shared cache without it is the leak the private policy exists to prevent. `SESSION_CACHE`
is restated in the script beside `PUBLISHED_CACHE` and **both** are pinned against
`apps/public-site/src/index.ts` by a UAT, the arrangement the existing constant already
had.

### No new dependency, asserted rather than promised

A UAT extracts every `import … from '…'` specifier in `smoke.mjs` and requires each to
be a `node:` builtin or a relative path. `bin/smoke` runs straight after a deploy on
whatever Node is there, and a package in that path is a new way for the diagnostic to
be unavailable at the one moment it is needed.

### Existing acceptance this supersedes

Requirement 5 changes an outcome three reconciled UATs pinned, in
`tests/reconciliation-platform-build-deploy-smoke.test.ts`. The assertions were updated
in place and remain true of the new behaviour:

- **AC-1336** asserted every check passes with nothing skipped against a published
  fixture. `unpublished_site_indistinguishable` cannot pass there — it needs a key that
  has published nothing while the channel checks need the same key to serve, which is
  why `unpublishedOrigin()` has always existed beside `correctOrigin()`. It now reports
  `n/a`; AC-1340 is where it passes.
- **AC-1337** listed `pass` and `skip` as the outcomes a non-broken check may report;
  `na` is a third.
- **AC-1340** asserted the live-revision branch is a `pass`. It is `n/a`, which is
  requirement 5 stated directly.

`apex_resolves` is untouched: it still fails on a 404 at `/`, and nothing here makes
that quieter.

## Test plan

New — `tests/test_UAT_FC_BUG-136_smoke_runs_without_arguments.test.ts`:

- the four root-only checks run and pass with **no arguments** against a published
  apex, and the requests they made were against `/`;
- each of the four **fails** against an apex broken in the way it owns (a lost charset,
  an immutable cache policy, a directory listing on a miss, a mistyped font reached
  from inside the stylesheet);
- `--site-key` is the target when given, and the crawl walks the keyed root;
- the two key-needing checks skip, naming what only a key has;
- a check that compared nothing reports `n/a`, never `pass`, and passes when given a
  key that has published nothing;
- the summary counts skips and n/a apart, and omits the n/a clause when there are none;
- an apex that is not a published site index skips and names both what would run it;
- against the default apex the reason reads `APEX_SITE_KEY` out of the config, and
  `apex_resolves` still fails;
- the workers.dev skip says it cannot be derived, and the `workers_dev = false`
  declaration it points at is true of the file;
- a session-dependent apex is a pass and not a cache-policy failure, the same policy
  without `vary: cookie` is a failure, and both constants match the Worker;
- the script imports only `node:` builtins and its own repo.
