`bin/smoke` reports **1 failed, 2 passed, 7 skipped** against production. Seven of ten
checks did not run, and six of them skip for one reason: no `--site-key` was given. A
check that only runs when an operator remembers a flag is a check that will not run.

This is the assertion surface for "did the deploy actually serve anything", so the
skips are worse than ordinary test debt: the one moment it exists for is the moment
nobody is in a position to supply the argument it wants.

## Why the current design skips, and where the reasoning stops short

The script's header is right about what it refuses to depend on:

> The published-channel checks need a site key and cannot discover one — a key is 128
> random bits and this script takes no dependency that could ask D1 for it.

True of D1, and the no-dependency rule is worth keeping — `bin/smoke` runs straight
after a deploy on whatever Node is there, and a bundler or a package in that path is a
new way for the diagnostic to be unavailable when it is needed.

**But four of the six checks do not need a key.** `APEX_SITE_KEY` names a published
site served at the root of the host, so when an apex is configured the apex *is* the
published channel, and these assertions have a target already:

| Check | Needs a key? |
|---|---|
| `published_index_serves_html` | No — `GET /` and its content type |
| `published_cache_policy` | No — `cache-control` on `/` |
| `published_miss_is_404` | No — a missing asset and a missing directory under `/` |
| `published_assets_resolve` | No — crawl from `/`, which is the whole point of the check |
| `published_root_redirects` | **Yes** — it asserts the `/site/<key>` → `/site/<key>/` grammar |
| `unpublished_site_indistinguishable` | **Yes** — it needs a key that exists and has published nothing |

So the honest split is four checks that should run unconditionally whenever the apex
serves, and two that genuinely require an argument.

The implementer should confirm one thing first: that the apex path and the
`/site/<key>/` path serve through the same code with the same headers in
`apps/public-site/src/index.ts`. If they diverge, asserting the cache policy at `/` is
a different assertion from asserting it at `/site/<key>/` and the ticket's premise
needs revisiting rather than working around.

## The other skips

`control_app_workers_dev_closed` skips without `--workers-dev-origin`. The script
already derives `--control-origin` for the known apex rather than making the operator
retype it — [[BUG-57]] records that making them retype it is what left the [[REQ-147]]
gate unchecked by default. The same argument applies here, and this check guards a real
exposure: `apps/public-site/wrangler.toml` still declares `workers_dev = true`.

The account's workers.dev subdomain is not in the repository, so this one may not be
derivable. If it is not, say so **in the output** — "not derivable, pass
`--workers-dev-origin`" is a different report from a silent skip, and the config's
`workers_dev = false` declaration can be pinned by a static check meanwhile.

`unpublished_site_indistinguishable` has a second, softer version of the same problem:
even when it runs it can return *"the site has a live revision; nothing to compare"* and
report a pass having asserted nothing. A check that passes without asserting is
indistinguishable from one that holds.

## What this asks for

1. **The four apex-reachable checks run whenever an apex is configured**, with no flag.
2. **`--site-key` remains** for the two that need one, and those two report clearly that
   they were not asked to run rather than appearing as ordinary skips beside checks
   that could have run and did not.
3. **No new dependency.** If the apex key has to be read from
   `apps/public-site/wrangler.toml`, a line match is enough — no TOML parser, no
   package. Reading a file in the repo it ships in is not the dependency the header
   argues against; asking D1 is.
4. **A skip must say what would make it run**, and the summary line must distinguish
   "not applicable to this deployment" from "nobody supplied an argument". The present
   output gives the same word to both.
5. **A check that asserts nothing must not report `pass`.** Give
   `unpublished_site_indistinguishable`'s no-op branch its own outcome.

## Explicitly not in scope

`apex_resolves` failing today is not a defect: the deployment has published nothing and
`APEX_SITE_KEY` is empty, so a 404 is the correct answer and smoke is right to fail on
it. Nothing here should make that failure quieter.

## Done looks like

`bin/smoke`, run with no arguments against a deployment that has published its apex,
exercises the asset crawl, the content types, the cache policy and the 404-on-miss —
none of which have ever run against this product — and every remaining skip names the
argument that would turn it into a check.
