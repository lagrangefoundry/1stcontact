## Symptom

On Bob's salon 2 (`site-site_c78b12e50dde030a34e9becfabb6815d`, chat `chat-63f4762a`, business `biz_1fa3e4ce…`), every consultant turn since 22:07 UTC 2026-10-18 ends with:

> Unexpected token 'g', "guWid6rN1D"... is not valid JSON

It is the turn's own failure, recorded server-side in `turn_log.detail` (turns `turn_20f7c1da…` 22:07, `turn_da343e3c…` 22:27, `turn_7f3fc6fe…` 22:53, all `outcome: error`). The browser's Network tab shows nothing failing, because the error arrives inside the chat request's own stream.

## Worse: the conversation stopped being saved earlier

The session's archive comments stopped updating at **20:50:09 UTC**: the chat transcript (`comment-2ecd6062`, 45 KB) and the tool transcript (`comment-b3b6c00a`, 640 KB). Turns at 21:04 and 21:16 UTC are recorded `complete` in `turn_spend`, but neither reached the archive. So the end-of-turn save has been failing since about 20:50, silently for two turns and then loudly. Everything said since then may exist only in the session's Durable Object junction. **Do not clear the dev junction state** while investigating.

## What is established

- **Not a code change.** The dev server runs the snapshot deployed at 09:57 (`apps/control-app/.dev-snapshot`), unchanged since. Something in the stored data changed between ~20:50 and 21:04 UTC.
- **The bad value is computed, not stored.** `guWid6rN1D` appears nowhere in the local D1, Durable Object or R2 storage, as text or as its base64-decoded bytes (`82 e5 a2 77 aa cd`). Something is passing a non-JSON string (likely base64 or a service response) to `JSON.parse` / `res.json()`.
- **Sizes are below the archive ceiling** (REQ-309/REQ-176), so this is not the earlier `SQLITE_TOOBIG` failure.

## Root cause (investigation, 2026-10-19)

**A junction write over the DO's ~2 MB value ceiling dropped one record from the middle of the Durable Object's stream. From then on, the isolate's mirror and the DO counted bytes differently, and the archive watermark was written in the mirror's byte offsets.**

1. **20:38:20.489Z (20:36 turn):** `screenshot {detail:"low", of: image material-6e3cbe73}` returned the full 1024×1024 PNG as base64 (2,460,461 bytes). Its junction record (seq 3648, **2,460,779 bytes**) was refused by `SessionJunction.append`: `dev.log` shows `write did not land — Error: string or blob too big: SQLITE_TOOBIG` at `junction-do.ts:194`.
2. **The write-behind chain kept going** (`junctions.ts` `queue`: "one failed write must not poison the chain"). Every later record landed, so the DO holds seq 1–5237 **minus 3648**. That is a hole, not the tail gap the comment assumes, and `behind()` cannot repair a hole.
3. **20:50:09 fold:** the syncer read the isolate's mirror, which still held seq 3648. The archive folded correctly (the archived tool transcript has `toolu_01Fv9LF8CBJprmQxbcvVhMJV`, which the DO lacks). But `setWatermark` wrote the mirror's offset, 19,592,232 + 2,460,779 = **22,053,011**, and that value was queued to the DO.
4. **Next `prepare`:** the mirror was longer than the DO and the DO was not a prefix of it, so `adopt` replaced the mirror with the DO's stream and kept the DO's `meta`. The watermark now pointed 2.46 MB past the real archived boundary (19,592,232, the end of the 20:50 `turn_end`).
5. **21:04 and 21:16, silent:** the junction was still shorter than 22,053,011, so `readSpans` returned `[]` (`size <= cursor`). The end-of-turn sync was a successful no-op. Nothing threw and nothing was saved.
6. **22:07 onward, loud:** that turn's 1.43 MB screenshot record (seq 4588, starting at byte 21,901,477) pushed the stream past 22,053,011. `readSpans(22053011)` then started 151,534 bytes inside it, so `JSON.parse` received `guWid6rN1D…`: base64 that is computed rather than stored, matching the ticket's observation. Every sync since then throws. The 00:12:50Z turn on the new snapshot fails in 130 ms because a fresh isolate syncs at turn start.

**Evidence:** DO `2113f608…sqlite` holds 5,236 contiguous chunks, `size` 26,252,597, epoch 0, `meta {"cursor":22053011}`, with no seq 3648. The needle `guWid6rN1D` is at byte offset exactly 22,053,011 of the reconstructed stream. Every line of the stream parses.

**Recoverable:** every record since 20:50 is in the DO junction. Resetting the junction watermark to 19,592,232 makes the next sync fold 21:04 onward. The only thing lost is the DO's copy of seq 3648, and the archive already holds that (capped to 5,800 bytes).



## Cause located (EPIC-19, 2026-10-18 17:20 PDT)

**The junction's drain cursor points into the middle of a record.** Bob's salon 2's junction Durable Object (`1stcontact-control-app-dev-SessionJunction/2113f6080beb…sqlite`, `__miniflare_do_name` = `site-site_c78b12e50dde030a34e9becfabb6815d`), read offline from a copy:

- `state.size` = 26,252,597 bytes in 5,236 chunks; **every record line is valid JSON**.
- `state.meta` = `{"cursor":22053011}`, the archive-drain watermark.
- Byte 22,053,011 is **not** a chunk start, and lies **151,535 bytes into one record** (an image carried as base64). The bytes there are `guWid6rN1D0qFYNbmhdBPpzSWGWkntZ0DwnjAZ9L…`, the fragment in the error.
- That record starts at byte **21,901,477**, the preceding newline.
- The offset matches neither the UTF-16 nor the character count of a record boundary, so it is not a unit mismatch between byte and string lengths.

So the drain reads from a cursor that is not a record boundary and parses half an image as a record. Everything after it (about 4.2 MB, since about 20:50 UTC) is undrained, which is why the archive stopped updating.

**Questions for the fix:**
1. How did a non-boundary cursor get written? Candidates: a cursor computed from the isolate mirror's length after the mirror diverged from the object (a write-behind append that landed partially, or a record redacted or aged in the mirror but not in the object — e.g. REQ-168 image ageing shortening a record), or a cursor advanced by a record's length measured differently from its stored bytes.
2. Why the read path trusts it. `junction-do.ts` `read` falls back to `cursor 0` when `from` isn't a chunk start, but something downstream still parses from the stored cursor; find which reader slices by its own cursor instead of the returned `at`.

**Recovery for this session:** the records from byte 21,901,477 are intact, so folding from that boundary recovers everything since 20:50 UTC (at worst re-folding one record, which the archive's de-duplication should absorb). Do this with the dev server stopped, through code or a script, not by hand-editing the sqlite file.

**Guard regardless of cause:** a drain cursor that isn't at a record boundary is detected and snapped back to the previous newline, with a warning naming the session, never parsed.



## Answer to question 3 (operator via EPIC-19, 2026-10-18)

## Change of scope (operator, 2026-10-18): images by reference, now

*"No, let's just fix this now please."* The "later ticket" above is withdrawn; it is part of this one.

**Image bytes are not stored in the junction's durable copy.** On write, our junction adapter (`junctions.ts` / `junction-do.ts`) replaces each image block's base64 data with a reference (a content hash, plus media type and size), and stores the bytes once in R2 under that hash. On `prepare`, it resolves the references back into the isolate's mirror, so the framework still reads complete records synchronously and nothing upstream changes. Identical screenshots share one object.

Constraints:
- Byte positions are computed on what the Durable Object actually stores, so the mirror and the object can never disagree about offsets again. The watermark is always a record boundary in the stored stream.
- A reference whose bytes can't be fetched resolves to the framework's existing image placeholder (`[image: …]`), never an error, so a missing object can't take a turn down.
- The archive is unchanged (it already trims large tool results).
- Records stay small, so the split-large-appends fix becomes a safety net, not the normal path. Keep it.

Together with "low detail is genuinely low", these are the fix. Test plan additions: a turn whose screenshot is over 2 MB stores a record of a few hundred bytes in the Durable Object and the image in R2; a fresh isolate's `prepare` rehydrates it, and the model is sent the real image; a reference to a missing object becomes the placeholder.



## Correction to the change of scope (operator, 2026-10-18): no new storage

*"All the images should already be getting stored in the library — there should be no need for new storage or new references."* The R2-by-content-hash design above is withdrawn. Instead, in the junction's durable copy:

- **A Library image** (a `screenshot` of an `IMAGE-n`, a picture placed in the chat, anything the image block's REQ-168 `label` names) is stored as its **Library reference**: the material's label/uid plus media type. On `prepare` the adapter resolves it from the Library, through the same path the Library and `screenshot` already read, back into the mirror, so the framework still reads complete records. Where the Library item is gone, it becomes the framework's `[image: …]` placeholder.
- **A screenshot of a draft page** is not a Library item; it's a render of the page at that moment. It is **not stored anywhere**: its durable copy is the placeholder (e.g. `[image: screenshot of home at 1280px]`). That costs nothing the model still uses: REQ-168 already ages images out after two turns, and a rebuilt conversation already starts from placeholders. Within the live isolate the mirror keeps the real bytes, so the turn that took it, and the next two, still see it.
- Byte positions and the watermark are computed on what the Durable Object stores, as above.

Test plan, replacing the R2 cases: a turn with a screenshot of a Library image over 2 MB stores a record of a few hundred bytes naming that Library item; a fresh isolate's `prepare` resolves it and the model is sent the real image. A draft-page screenshot is stored as its placeholder only. A reference to a deleted Library item becomes the placeholder.



## Pre-coding check (BUG-229 session, 2026-10-19), three points to confirm

1. **Offsets need translating in the adapter.** Upstream SessionLog takes every offset from the bytes the mirror returns (session_log.js readSpans). If the mirror keeps real image bytes and the Durable Object stores references or placeholders, they are two coordinate systems. Plan: junctions.ts keeps a per-record map from mirror offsets to stored offsets. writeMeta translates the mirror cursor to the stored cursor before it reaches the object, adopt translates it back after rehydrating, and since() is asked in stored offsets. The object's watermark is then always a record boundary of its own stream. Upstream is unchanged.
2. **"Snap back to the previous newline" loses data here.** The poisoned watermark is 2.46 MB too far, not slightly mid-record. The previous newline (21,901,477) would skip 19,592,232–21,901,477, permanently losing the 21:04 and 21:16 turns and the start of 22:07. The correct point is 19,592,232. Proposed guard: a watermark that is not a stored record boundary, or is past the end, snaps to the end of the record carrying the highest seq the archive already holds. If that can't be established, nothing is folded, and the failure is logged and shown to the client. Recovery then happens through this code on the next prepare, with no sqlite edit.
3. **Low detail.** fidelity-core.ts screenshot: the of.kind==='image' branch ignores detail entirely (it returns the whole image, capped at a 1024 edge, PNG passed through). Draft tiles at low are 768-wide PNGs of 200–670 KB each. The repo has a PNG codec only, no JPEG encoder. "Genuinely low" needs one: either the jpeg-js package (pure JS, runs in workerd; the operator runs the install), or a small baseline encoder in-repo.



## Answers to the pre-coding check (operator via EPIC-19, 2026-10-18)

**1. No offset translation map.** Make the two copies identical instead: replace image data with the Library reference (or, for a draft-page screenshot, the placeholder) **at append time, before the record reaches either the isolate mirror or the Durable Object.** Mirror and object then hold the same bytes and the same offsets by construction, and `SessionLog`'s arithmetic is right with nothing upstream changed. A map between two offset spaces is the class of bookkeeping that caused this bug. Before coding, confirm that nothing live reads an image back from the junction (the warm backend keeps the turn's images in its own message state; a rebuild already seeds from redacted records; tool records aren't rendered as images in the chat). If something does, resolve the reference at that read, not via a map.

**2. Agreed: snap to the end of the last record the archive holds** (19,592,232 here), not the previous newline, which would lose the 21:04 and 21:16 turns. If that point can't be found, fold nothing, log it, and show BUG-121's notice. Recovery happens through this code on the next `prepare`; no SQLite edit.

**3. Neither (a) nor (b): use the existing image renderer.** Low detail is a recipe through the same renderer the Library editor uses (REQ-219, `IMAGES` binding): longest edge 768 px, output JPEG at about quality 75, for Library images and draft tiles alike. One image pipeline, no new dependency. Only if that binding can't output JPEG in local dev, fall back to adding `jpeg-js` (the operator runs the install).
