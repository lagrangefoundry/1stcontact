## Symptom

On Bob's salon 2 (`site-site_c78b12e50dde030a34e9becfabb6815d`, chat `chat-63f4762a`, business `biz_1fa3e4ce…`), every consultant turn since 22:07 UTC 2026-10-18 ends with:

> Unexpected token 'g', "guWid6rN1D"... is not valid JSON

It is the turn's own failure, recorded server-side in `turn_log.detail` (turns `turn_20f7c1da…` 22:07, `turn_da343e3c…` 22:27, `turn_7f3fc6fe…` 22:53, all `outcome: error`). The browser's Network tab shows nothing failing, because the error arrives inside the chat request's own stream.

## Worse: the conversation stopped being saved earlier

The session's archive comments stopped updating at **20:50:09 UTC**: the chat transcript (`comment-2ecd6062`, 45 KB) and the tool transcript (`comment-b3b6c00a`, 640 KB). Turns at 21:04 and 21:16 UTC are recorded `complete` in `turn_spend`, but neither reached the archive. So the end-of-turn save has been failing since about 20:50, silently for two turns and then loudly. Everything said since then may exist only in the session's Durable Object junction. **Do not clear the dev junction state** while investigating.

## What is established

- **Not a code change.** The dev server runs the snapshot deployed at 09:57 (`apps/control-app/.dev-snapshot`), unchanged since. Something in the stored data changed between ~20:50 and 21:04 UTC.
- **The bad value is computed, not stored.** `guWid6rN1D` appears nowhere in the local D1, Durable Object or R2 storage, as text or as its base64-decoded bytes (`82 e5 a2 77 aa cd`). Something is passing a non-JSON string (likely base64 or a service response) to `JSON.parse` / `res.json()`.
- **Sizes are below the archive ceiling** (REQ-309/REQ-176), so this is not the earlier `SQLITE_TOOBIG` failure.

## What to find

1. The path that runs at turn end and throws: archive fold (`TicketSessionArchive.apply`, segmented artifacts), the junction drain from the Durable Object (`junction-do.ts` `read` returns raw bytes over RPC), spend recording, plan/cadence hooks, corpus re-index, or the delegation account. The first turn to fail silently (21:04) is the one to reproduce from: what it wrote that earlier turns did not.
2. Why the save could fail silently for two turns before the turn itself started failing.

## Fix

- The cause, whatever it is.
- **Recover what is unsaved:** fold the junction's records since 20:50 into the archive, so the conversation since then is not lost.
- An end-of-turn save failure is never silent: it is logged with the artifact, and the client is told the reply may not have been saved (BUG-121's wording).

## Test plan

UAT reproducing the trigger through the real host (only the model scripted): the turn completes and its exchange is in the archive. Plus: a forced archive failure is logged and surfaced, never silent.
