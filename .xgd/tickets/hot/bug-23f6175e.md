## What the consultant reported, verbatim

> **And one more for the bug list — a nasty one for you specifically.** The state summary I'm handed at the start of each turn says the draft is at **change 113**. It's actually at **117**. My own last four writes aren't in it. Same with my engagement record: it shows twelve decisions, I've written thirteen. So the context I'm given lags my own work by a turn.
>
> That matters more than it sounds. It's precisely the mechanism that's supposed to tell me *"your client edited something, go look before you write."* If it can be a turn behind, then in a session where you and I are both editing, I could overwrite your work while reading a summary that says you haven't touched anything. `list_changes` is accurate — I checked against it — but the summary that arrives unprompted isn't, and that's the one designed to catch this.

It had already been bitten by the weaker version of this earlier in the same session, when the operator asked *"I made a change did you check, if you cannot that is a bug"* and the consultant could not tell whether the edit had landed and not been recorded, or never landed at all.

## Why this is the one that must not be wrong

[[REQ-285]] built the digest precisely because the session was confabulating state — asking for changes since revision 120 when the true count was 76. The ticket's own promise is in the module header:

> IT IS DERIVED, NEVER STORED. Every field here is read back out of the store on the turn it is delivered — **which is the whole of what makes it authoritative.**

A digest that is a turn behind is not a weaker version of that promise. It is the same failure the digest was built to remove, now arriving with the system's authority behind it instead of the model's imagination — and therefore harder to catch, because there is nothing to distrust.

The stated purpose makes it sharper still. This is the mechanism that says *"your client edited something, go and look before you write."* One turn of lag in a two-editor session is exactly a lost write, and the consultant named that consequence itself.

## Verified defect — the cache key does not move for every write

`siteDigestSource` (`digest-core.ts:242`) caches on the store's version:

```ts
const version = await opts.store.version(slug)
if (cached && cached.version === version) return cached.digest
```

defended as:

> THE DERIVATION IS CACHED AGAINST `SiteStore.version`, NOT AGAINST TIME. The version is bumped by every write, so **a cache keyed on it cannot be stale by construction**.

That claim is false as written. In `d1r2-store.ts` there are two counters and two separate writes:

- applying a change (`:697`) — `UPDATE sites SET version = version + 1, updated_at = ?`
- recording a change (`:753`) — `UPDATE sites SET counter = ? WHERE id = ?`

The second **does not touch `version`.** So any write that moves the change counter without applying a draft change leaves the cache key unmoved and the digest serving a stale copy — including the change count it reports, which is read from `counter`. The cache cannot be stale by construction only if every counter movement also moves the key, and it does not.

This is a real defect on its own terms, independent of whether it fully explains 113 → 117.

## Not yet settled, and the experiment that settles it

The engagement ledger lagged by exactly one as well — *"it shows twelve decisions, I've written thirteen"* — and the ledger is in the ticket store, not the site store, so it does not share this cache key. Two unrelated stores lagging by exactly one turn suggests a second mechanism: providers read from a snapshot taken before the previous turn's writes were drained, rather than at assembly time.

So this ticket has one verified cause and one open one, and the fix must not stop at the first. The decisive experiment is cheap: in one session, write N times, then at the next turn compare the digest's change count, `sites.counter`, `sites.version` and `list_changes` — and separately compare the ledger digest against the ledger's own record. Whichever pairs disagree names the mechanism.

## Fix

1. **Key the digest cache on something that moves whenever anything it reports moves** — or drop the cache. It is defended as costing "one `version` read" on a quiet turn, which is a small saving against a wrong number on a busy one, and the `SiteStore` is the right place to decide what a version means rather than the digest.
2. **Settle the ledger half** by the experiment above and fix whatever it names; a digest that is authoritative about the site and stale about the engagement record is still a digest nobody can trust.
3. **Make the promise testable rather than asserted.** The header claims authority in prose. It should be a test: after any sequence of writes, the next turn's digest equals what a fresh derivation would produce. That assertion is what stops this reopening the next time a counter is added.
4. **Say what the digest is as of.** Even correct, a digest is a snapshot; a stamp the consultant can compare against `list_changes` turns a silent disagreement into a visible one. `list_changes` was accurate throughout this session and is what the consultant used to catch the lag — it should not have needed to.

## Test plan

- A write that moves the change counter without applying a draft change invalidates the digest; the next turn reports the new count.
- After N writes in one turn, the next turn's digest equals a fresh derivation — asserted generically over the write paths, not against one of them.
- The engagement-record digest reflects a decision written in the previous turn.
- A digest carries a stamp that identifies the state it was derived from, and that stamp agrees with `list_changes`.


## Both halves, settled

The decisive experiment named above was run as a test rather than as a live
session, which is what makes it repeatable. It splits the report cleanly in two.

**The site half is a real defect, and worse than the counter case alone.** The
digest reports four things that move independently: the page shapes, the journal
counter (and with it the page last worked on), the live revision, and how much is
unpublished. Only the first is behind `SiteStore.version`. So two ordinary events
moved what the digest says while leaving its cache key still:

- **a journal record with no draft change under it** — `appendChange` moves
  `counter` and nothing else, which is how the builder, an AI turn and every
  structured-edit command end;
- **a publish** — `writeRevision` + `setDraftBase` change what the public can see
  and touch the draft not at all, so the digest went on saying *"nothing has been
  published yet"*, or quoting a superseded pending count, indefinitely.

Both are reproduced as failing tests against the old code and pass against the
new one.

**The engagement-record half is not a second mechanism, and there is none.** The
ledger is read through `ledger.read()` on the turn it is delivered, and the
framework assembles both the reminder and the volatile seed at the START of
`promptStream` — before generation, after everything the previous turn wrote. A
test that records a decision through the real `record_decision` tool on turn one
and reads the next turn's assembled tail finds it there. What the consultant
actually compared was the record it was handed when the turn began against a
write it made during that same turn. Which is the real remaining problem, and is
fix 4 below rather than fix 2: the entry never said what it was as of, so a
snapshot doing its job and a snapshot that is wrong read identically.

## What was implemented

**1. The cache is gone, not re-keyed.** A composite key over
version-and-counter-and-base-revision would be correct today and silently wrong
the next time a counter is added — which is precisely how this arose. The entry's
own header promised *"derived, never stored … which is the whole of what makes it
authoritative"*, and the cache was a caveat on that sentence with exceptions the
header did not list. So `siteDigestSource` derives on every turn. The one store
read that is not part of the derivation is the existence check: `version` answers
`null` for a site the store does not hold, and an absent site is not an empty one.

The saving that was given up is a handful of store reads on a turn that changed
nothing, paid immediately before a model call costing seconds and cents. That was
never the budget in question.

**2. The digest says what it is as of, and the stamp is the counter.** No second
field: a stamp that could disagree with the count the entry already quotes would
be one more thing to distrust. What changed is the prose — the entry now says the
snapshot was taken when the turn began, that it does not move as the session
works, and that `list_changes since {at}` is exactly what has happened after it.
That turns the silent disagreement the consultant caught by hand into one the
entry invites. The engagement record's decision count is dated the same way and
for the same reason.

## Test plan — as implemented

`tests/test_UAT_FC_BUG-128_the_digest_cannot_lag.test.ts`

- A journal record alone is in the next turn's digest.
- A publish alone is in the next turn's digest — the live revision and the
  pending count, which no earlier test covered.
- Generic over the write paths: after a draft change, a journal record or a
  publish, the next turn's digest equals what a fresh derivation would produce.
  Asserted over a list of write paths rather than against one of them, because a
  test written against the first would have passed throughout the defect.
- The change the digest names is the one `list_changes` reports.
- The entry tells the session the number is as the turn began, asserted on what
  the model was actually sent through the real host.
- A decision recorded on the previous turn — through the real `record_decision`
  tool, the real ledger surface and the real per-turn assembly — is in this
  turn's record.
