# Execution architecture: where work runs

**Status:** decided 2026-11-04 under [[EPIC-32]]. It amends [[DOC-1]] items 2, 7 and 8 and
adds items 31–35, and it extends [[DOC-5]] §"Cloudflare Platform Components".

## 1. Why this exists

From late October to early November, consultant and builder turns kept stopping on
prod and in dev. About ten point fixes each removed one cause, and another took its
place every time: BUG-288, BUG-312, REQ-483, BUG-320, BUG-324, REQ-624, REQ-627,
BUG-332, BUG-340, BUG-341, and the framework's log-tail and record-cache fixes. The
causes differed, but one thing was common to all of them: **a long-running,
memory-heavy agent process was running inside a runtime built for short requests.**

What we measured on 2026-11-04:
- **A typical turn** runs 15–30 min of wall time with 140–170 s of CPU, holding the
  conversation, the site, the catalog and the tool state in memory the whole time.
- **The Worker isolate it runs in** has 128 MB, shared with every other request and
  Durable Object that isolate is hosting, and at most 5 min of CPU per invocation.
- **Workflows add durability, not capacity.** Every step runs in a Worker isolate
  under the same limits, and the steps of one instance can share an invocation:
  one prod turn's 9 rounds and 5 builder passes ran as **one** invocation.
- **Every new feature raises the memory floor** (the catalog, the Library, video),
  so each fix only buys time until the next feature.

## 2. Workload classes and where each runs

| Class | Shape | Examples | Runs on |
|---|---|---|---|
| **Edge request** | ms–s, small memory, stateless | API, sign-in, forms, the portal, Stripe webhooks, published pages, the junction stream | **Workers** |
| **Coordination** | per-key serialisation and state | the session junction (turn log), site locks | **Durable Objects** |
| **Orchestration** | durable sequence, retries, checkpoints; does no heavy work itself | consultant job rounds, shop and material import, comp capture, scheduled checks | **Workflows / Cron / Queues** |
| **Agent and batch compute** | minutes–hours, hundreds of MB to GBs, CPU-bound bursts | consultant and builder rounds, page capture and screenshots, catalog-wide rebuilds, video and image processing | **Containers** |
| **Published site** | static bytes | rendered pages, assets, photo renditions | **R2 + Workers static serving + edge cache** |

**The placement rule:** if a unit of work can grow with the size of a business
(pages, products, Library items, the length of a conversation), or runs longer than
a request, it is **compute** and belongs in a container, orchestrated by a Workflow.
A Worker or DO only does work whose size is bounded by a constant.

## 3. The container design

- **Images:** one Docker/OCI image (`linux/amd64`) holding the host in Node. That is
  the code the `1c` CLI already runs in-process. Built and pushed by `wrangler
  deploy`.
- **Addressing:** one container instance per **job**, reached through a Durable
  Object keyed by the job id. It is started on demand and sleeps as soon as the job
  ends. No instance is kept per site between messages.
- **Size:** standard-1 (4 GiB, ½ vCPU) to start. The size is configuration, not code.
- **The container is disposable compute and never holds state.** The junction (DO),
  D1 and R2 remain the only record. On restart, a container rebuilds everything it
  needs from them. Its disk is ephemeral and is never read back.
- **Orchestration stays in Workflows.** A round step asks the job's container to run
  the round and awaits the result. The step spends seconds of CPU and unbounded wall
  time, which suits Workflows. A container that dies fails the step, the Workflow
  retries it, and the round resumes from the junction, exactly as today.
- **Shutdown:** on SIGTERM (a deploy or host move; up to 15 min grace) the container
  finishes its current tool call, writes a checkpoint record, and exits. The retried
  step resumes from it.
- **Credentials:** the container gets only the secrets the host needs (model keys,
  a scoped token to the Worker's internal API). It reaches D1, R2 and the junction
  **through the control-app Worker over an internal entrypoint**, never with account
  credentials.

## 4. Liveness is reported, never inferred

Only the runner (the Workflow step or the container) declares a job's state. The
follow stream (`POST /api/ai/prompt`) and the panel **read** that state. They never
conclude from a gap in the records that a job has died. Silence that lasts past a
deadline is shown as "no news from the job for N min", with the job still running,
until the runner itself records an ending. This fixes the false "lost" verdict of
2026-11-04: the stream declared a working job dead 5 min into a 29-min turn.

## 5. The published site never depends on compute

A live site's pages, assets and **photos** are static bytes in R2, served by
`public-site` and the edge cache. No request from a visitor may reach the agent
path or depend on the control-app being healthy. The two dynamic exceptions are
narrow Worker endpoints: lead capture and checkout.
- **Today's exception, to be removed:** shop photos are fetched live from
  control-app on every request, as full-size originals with a 60 s cache.
- **What replaces it:** they become publish-time renditions like every other image.

## 6. Development parity

`bin/dev` runs the same container image locally through `wrangler dev`'s container
support (Docker required). Dev no longer emulates agent compute inside workerd: the
1.4 GB workerd heap crashes of 2026-11-04 cannot recur there, and a memory problem
shows up in dev exactly as it would in prod. [[DOC-41]] records the Docker
prerequisite.

## 7. Bounded-by-construction rules for code that stays on Workers

- No per-item store query inside a loop over a business's items. The ticket store's
  `query` scans a whole type, so one scan must be shared across all the items.
- No `Promise.all` over an unbounded list. Fan out with a fixed concurrency.
- No whole-log reads per poll. Readers tail from a cursor.

## 8. Cost

On 2026-11-04 a 29-min, 166 s-CPU prod turn cost:
- **As a Workflow:** about $0.003 of compute.
- **On standard-1:** about $0.02.
- **Model spend for the same turn:** at least $6.35.

So compute cost is not a deciding factor. The one design that would make it one is
keeping a container awake per site, which §3 forbids.

## 9. Migration (see [[EPIC-32]] for tickets)

1. **Stabilise in place first,** while the cutover is built: report liveness
   truthfully, deploy the BUG-341 scan fix, and bound the store queries.
2. **One cutover, not a phase-in.** All agent compute (consultant and builder rounds,
   page capture and screenshots) moves to per-job containers in one change, and the
   in-isolate agent path is deleted in the same change. There is no switch and no
   period with two paths. Revisions follow from end-to-end runs on dev and prod.
3. **Catalog rebuilds become container jobs, and shop photos become static
   renditions** (§5).
