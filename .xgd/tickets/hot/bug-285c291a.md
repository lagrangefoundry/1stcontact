## What I was doing

Building a pinned hero: an image block is held at the top of the viewport while the text block below it scrolls up and out of view behind it.

Structure, simplified — a `stack` container with two children in document order:

1. A `container` carrying `sticky: { topPx: 0 }`, `stacked: true`, and an opaque `axes.surfaceFill`. Holds the image.
2. A `container` with no sticky and no stacking. Holds two `text` nodes.

## What I expected

Child 1 declares `stacked: true`, which the L1 vocabulary documents as "**this node is deliberately stacked over what it overlaps**". Child 2 overlaps it while scrolling past. So child 2 should disappear *behind* child 1 — occluded first by child 1's opaque surface fill, and by its image.

## What happens

Child 2 paints **over** child 1 throughout the scroll. The text crosses the image and is illegible against it — the drawing shows through the type. The pinning itself works correctly; only the paint order is wrong.

## Reproduction

1. `stack` container, two children.
2. First child: `sticky: { topPx: 0 }`, `stacked: true`, `axes.surfaceFill` set to an opaque palette colour, containing an image.
3. Second child: an ordinary container with text in it, tall enough to scroll.
4. Scroll. The second child's text crosses over the first child's image and surface fill rather than passing behind it.

Both fields persist on read-back via `get_l1` — this is a render-time behaviour, not a write that was dropped.

## Why I think this is a defect rather than my error

`stacked: true` is the only mechanism L1 offers for declaring paint order between overlapping siblings, and its documented purpose is exactly this case. The opaque `surfaceFill` was added as a second, independent reason for the occlusion to happen, and it does not occur either — so it is not simply that `stacked` is being outranked by something; the sticky element appears to be painted beneath its later siblings regardless of what it declares.

The likely cause: an element becoming sticky creates a stacking context or a positioned layer whose ordering is established independently of whatever `stacked` emits, so the two disagree and position wins.

## Why it matters

Pinning an element is almost always done so that other content moves past it. **What happens at the overlap is the whole point of the feature**, not an edge case — a pinned element that later content paints over produces unreadable text crossing an image, which is worse than not pinning at all. As it stands, the sticky capability can only be used safely where nothing ever overlaps the pinned element, which excludes most of what it is for.

## What would fix it

Either of these would be sufficient:

1. `stacked: true` is honoured on a sticky element — an explicit declaration outranks the implicit ordering that position creates.
2. A sticky element is placed above normal-flow siblings by default, since content passing behind it is the common intent.

Option 1 is preferable: it keeps paint order something the page states rather than something it infers, and it leaves "scrolls over the pinned thing" available to anyone who wants it.

## Related

Filed against the sticky capability introduced by the scroll-position-driven state request. That request specified pinning but did not specify overlap behaviour — this report is that omission surfacing, so the resolution may belong on that work rather than as a separate fix.

There is also a wider pattern worth noting: a field that is accepted by the validator and persists on read-back can still have no effect at render time. That has now happened twice (this, and a picture height set to track its row). Authoring signals all report success while the page does not change, which costs a full diagnosis cycle each time and — from the client's side — looks like the change was never made.
