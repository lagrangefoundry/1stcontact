## What I was doing

Building a pinned hero: an image block is held at the top of the viewport while the text block below it scrolls up and out of view behind it.

Structure, simplified — a `stack` container with two children in document order:

1. A `container` carrying `sticky: { topPx: 0 }`, `stacked: true`, and an opaque `axes.surfaceFill`. Holds the image.
2. A `container` with no sticky and no stacking. Holds two `text` nodes.

## What I expected

Child 1 declares `stacked: true`, which the L1 vocabulary documents as "**this node is deliberately stacked over what it overlaps**". Child 2 overlaps it while scrolling past. So child 2 should disappear *behind* child 1 — occluded first by child 1's opaque surface fill, and by its image.

## What happens

Child 2 paints **over** child 1 throughout the scroll. The text crosses the image and is illegible against it — the drawing shows through the type. The pinning itself works correctly; only the paint order is wrong.

## Reproduction

1. `stack` container, two children.
2. First child: `sticky: { topPx: 0 }`, `stacked: true`, `axes.surfaceFill` set to an opaque palette colour, containing an image.
3. Second child: an ordinary container with text in it, tall enough to scroll.
4. Scroll. The second child's text crosses over the first child's image and surface fill rather than passing behind it.

Both fields persist on read-back via `get_l1` — this is a render-time behaviour, not a write that was dropped.

## Why I think this is a defect rather than my error

`stacked: true` is the only mechanism L1 offers for declaring paint order between overlapping siblings, and its documented purpose is exactly this case. The opaque `surfaceFill` was added as a second, independent reason for the occlusion to happen, and it does not occur either — so it is not simply that `stacked` is being outranked by something; the sticky element appears to be painted beneath its later siblings regardless of what it declares.

The likely cause: an element becoming sticky creates a stacking context or a positioned layer whose ordering is established independently of whatever `stacked` emits, so the two disagree and position wins.

## Why it matters

Pinning an element is almost always done so that other content moves past it. **What happens at the overlap is the whole point of the feature**, not an edge case — a pinned element that later content paints over produces unreadable text crossing an image, which is worse than not pinning at all. As it stands, the sticky capability can only be used safely where nothing ever overlaps the pinned element, which excludes most of what it is for.

## What would fix it

Either of these would be sufficient:

1. `stacked: true` is honoured on a sticky element — an explicit declaration outranks the implicit ordering that position creates.
2. A sticky element is placed above normal-flow siblings by default, since content passing behind it is the common intent.

Option 1 is preferable: it keeps paint order something the page states rather than something it infers, and it leaves "scrolls over the pinned thing" available to anyone who wants it.

## Related

Filed against the sticky capability introduced by the scroll-position-driven state request. That request specified pinning but did not specify overlap behaviour — this report is that omission surfacing, so the resolution may belong on that work rather than as a separate fix.

There is also a wider pattern worth noting: a field that is accepted by the validator and persists on read-back can still have no effect at render time. That has now happened twice (this, and a picture height set to track its row). Authoring signals all report success while the page does not change, which costs a full diagnosis cycle each time and — from the client's side — looks like the change was never made.

## Diagnosis

The pin already has a paint-order field, and it is not `stacked`. REQ-328 added
`sticky.lift` for exactly this composition: it compiles to `z-index: 1` inside the
pin's own declaration list, which is what puts a held node above the siblings that
travel past it. The report's "that request specified pinning but did not specify
overlap behaviour" is out of date — the omission was closed; what was not closed is
that the author has to find `lift` to benefit from it.

`stacked: true` is a different field with a confusable name. Its job is to tell the
envelope evaluator that an overlap is the design rather than a defect, so the gate
stops reporting it. It is documented as **not a paint axis** and the renderer emits
nothing for it — which is why every authoring signal reported success and the page
did not change.

So the two halves of the report are both real:

- The composition is achievable today (`sticky: { topPx: 0, lift: true }`).
- The field the author reached for was accepted, persisted, and inert.

The second half is the defect. `stacked` says, in its own prose, that the node
carrying it "is the composition" — the figure of the overlap rather than its ground.
On a node in ordinary flow that claim needs no `z-index`, because document order
already paints a later sibling over an earlier one and a fold authors `stacked` on
captured reproductions whose paint must not move. On a **pinned** node it is the one
place where document order gives the opposite of what the declaration says: the page
moves past a node that does not, so the sibling that arrives later covers the figure.

## Fix

Take the report's preferred option, bounded to the case where the two declarations
actually meet.

**`stacked: true` on a node that also carries `sticky` lifts it**, emitting the same
single `z-index: 1` that `sticky.lift` emits, in the same declaration list. The two
spellings converge on one declaration:

- One `z-index`, never two, when a node carries both `stacked` and `sticky.lift`.
- Confined to the pin's declaration list, so a `fromPx`-gated pin lifts only inside
  its width band — below the gate the node is in ordinary flow and its paint is
  untouched, exactly as a gated `lift` behaves.
- Emitted in every render channel the pin is emitted in, including the edit render,
  because where a box sits and what level it holds at is structure, not motion.

**`stacked` alone still emits nothing.** The lift is keyed on the pair. This is what
keeps the change from moving a pixel on any existing page: the fold authors `stacked`
on reproductions of references whose overlaps it measured, and it never authors
`sticky`, so no folded document can reach the new branch. A `stacked` headline over a
hero photograph paints exactly as it did.

**`sticky.lift` is unchanged and is not deprecated.** It remains the direct spelling,
and it is the one a pin that is not part of a declared overlap should use.

## Vocabulary

The confusion was the report's own diagnosis of the cost ("a field that is accepted by
the validator and persists on read-back can still have no effect at render time"), and
half of it is the prose. The schema doc comments are the authoring reference — they are
lifted into the projected L1 reference — so they are corrected with the behaviour:

- `stacked`'s "NOT A PAINT AXIS" paragraph now states the pinned exception and names
  `sticky.lift`, so an author who arrives at `stacked` first is pointed at the field
  they wanted rather than left believing they have already declared it.
- `sticky.lift`'s field doc records that `stacked` on the same node is accepted as the
  same declaration, so the pair is documented from both ends and neither reads as the
  sole spelling.
- The `sticky` schema header's "it is `lift`'s" is widened to name both.

## Test plan

`tests/test_UAT_FC_BUG-154_sticky_stacked_paint_order.test.ts`, alongside
`test_UAT_FC_REQ-328_sticky_paint_order.test.ts`, whose harness (base-rule and
media-block declaration readers) it reuses:

1. The reported composition renders with the pin above its siblings — a `stack`
   container whose first child carries `sticky`, `stacked` and an opaque
   `axes.surfaceFill`, and whose second child is a plain container of text. The pin
   emits `z-index: 1`; the surface fill is still painted; the text container is
   untouched.
2. `stacked` without `sticky` emits no `z-index` anywhere — the folded-reproduction
   guarantee, asserted as byte-identity against the same document with `stacked`
   removed.
3. `stacked` and `sticky.lift` on one node emit exactly one `z-index`.
4. A `fromPx`-gated pin carrying `stacked` lifts only inside its band: nothing in the
   base rule, both declarations in the `min-width` block.
5. The envelope is unchanged — `stacked` stays `true`-or-absent, a pinned `stacked`
   node is still refused against an absolute geometry track and still refused on an
   email page.
