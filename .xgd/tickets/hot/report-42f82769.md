# Fix Plan — Iteration 11 (re-plan after validation refusal)

## Hypothesis
AC-2487 fails on two gaps in `tools/generate/src/cli/picture.ts`. First, `PictureEnvironmentError(NO_IMAGE_STORE)` (picture.ts:502) reaches the Toolbox without the surface's `ENVIRONMENT` code. Second, `storedImage`'s not-found refusal (picture.ts:472-478) uses one Library-pointing sentence on every host, so the `1c` CLI, which holds only the site namespace (`mergeImageLibraries({ site })`, ai/host.ts:252), never says it holds no Library.

## Analysis
- **Why this is a re-plan.** The first iteration-11 plan (REPORT-11612) was refused by `validate_fix_plan` with this reason: "batch 0: the `code_frozen` override was refused: rule 'code_frozen' was rejected by a review for this batch".
  - The denial is REPORT-6909 (report-07babd4a, `override_misjudged`, bundle-5607a08d).
  - It judged a different grant wrong: REPORT-6790, from an earlier bundle. That grant ported REQ-157 image-block and Worker-composition behaviour into host-core.ts, fidelity-core.ts, ai.ts, router.ts and shot.ts, for AC2031/AC2034/AC2025.
  - Its finding was a trust-boundary one: marking on the screenshot path was preserved only by an ungranted fidelity-core.ts edit.
  - The denial is keyed by batch index 0, and batch indices are reused by every iteration and every bundle.
- **How this plan differs from the denied batch.**
  - **Different work.** The AC-2487 work is a different test, a different AC (REQ-218, not REQ-157), different files, and has no trust-boundary component.
  - **Narrower files.** The previous iteration-11 plan listed fidelity-core.ts. This plan removes it, so the grant names only picture.ts and image-library.ts and touches nothing the denial was about.
  - **Placed at index 1.** This follows the precedent of REPORT-11603 (iteration 9), which made the same distinction for interact.ts at batch 1. That grant was accepted and passed conformance (REPORT-11607).
  - **Stated openly** so that a later review can overturn it if index reuse is not the intended reading.
- **Where the code comes from.** The reference already has the convention for coded refusals from this surface: fidelity-core.ts:563 and :690 throw `new Error(\`REFUSED: ${message}\`)`, and the Toolbox renders that as `Error: <op> failed (REFUSED). …`.
  - fidelity-surface.json:126-128 declares `ENVIRONMENT` for "no image store to hold the pictures", and lists it for `screenshot` and `compare`.
  - picture.ts:214-221 says `PictureEnvironmentError` means exactly that refusal.
  - So the ENVIRONMENT code can be attached in picture.ts itself, through the same declared-code convention. No surface implementation file needs to change.
- **What fails** (REPORT-11611, 41 of 42 pass):
  1. Line 617: the no-store refusal lacks `(ENVIRONMENT)`, although its sentence is present.
  2. Lines 636–638: the CLI's not-found refusal lacks "no Library" and "only the site's own assets", and still says "the name it appears under in the Library".
  - Everything else in the test passes.
- **Hypothesis history.** This is the same root cause as the refused plan. It was never run by a builder, so it has not been retried. No earlier batch touched AC-2487.
- **Isolation.** The failure is a deterministic assertion on text, with no contamination signal.
