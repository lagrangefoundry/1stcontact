## Story
**As a** client asking the consultant to reproduce or learn from an existing website, **I want** the assistant to be able to capture that site itself, see what it recorded, and keep it as material it can recall later, **so that** it can work from a faithful reference without me running tools, find that reference again by what the site *is*, and never fetch something inside my system it should not reach.

## Description
REQ-157 gives the assistant a read-only "looking and judging" surface (STORY-157). This story is the part of that surface that **brings a reference in**:

- **`capture_site(url)`**: the assistant names a public http/https address. A real browser loads it, records it at each viewport width, reads its values (including the page's own `<title>`) and mirrors its images. The result is a named reference, which every later picture of kind `reference` takes.
- **The capture becomes client material (REQ-166).** On a host that has a ticket store, `capture_site` does not stop at the reference store. After the bundle is complete it adopts it as **one `reference` material ticket**, so the capture is searchable corpus material in the same way an uploaded file is (REQ-163):
  - **One attachment record per bundle member**, each tagged with the member name it holds (`capture.json`, `screenshot.full.png`, `assets/hero.jpg`, …). That lets any single member be read without reading the others.
  - **Title**: the captured page's own `<title>`, trimmed. If it is blank or absent, the host is used instead.
  - **Body**: a description of the site written at capture time from the capture record plus the screenshot. The first line is always a markdown link to the captured address. The palette, type and section count measured from the capture record are always present. Prose about what the business appears to be is added when a describer is available and a screenshot exists. When it is not, the body says so instead of failing.
  - **Rights come from provenance; nobody is asked the legal question.** A capture of the client's declared domain, or a subdomain of it, is recorded `republishable` and not `exportable`. A capture of any other domain is the reverse. The two bits are set independently.
  - **One ticket per bundle, identified by bundle name and not by URL.** Recapturing a bundle updates the same ticket in place. The title and body are rewritten, including a description the client corrected. Members whose bytes are unchanged (same content hash) are left alone, with no new blob and no new record. A changed member gets a new record and its superseded record is detached (sent to the trash, which is reversible). A member the bundle no longer holds is detached.
  - **The answer always says what happened.** `capture_site`'s result carries a `reference` object stating whether a reference ticket was written, which one, whether it was newly created, and why not when it wasn't. A host with no ticket store (the `1c` CLI) captures exactly as before and says no reference was written. An adoption that fails (describer unreachable, corpus down) is reported with its reason. The capture itself does not fail, and the bundle stays complete in the reference store.
- **`list_references`**: what has been captured, with each capture's address and time taken from its capture record.
- **`describe_reference(name)`**: what one capture holds, i.e. the widths it recorded, its sections, images mirrored against images referenced, and the coverage findings that say whether it looks complete. The assistant reads this before trusting any comparison against the capture. An unknown name is an error naming the bundle and saying it has no capture record.
- **The egress guard.** `capture_site` is the first operation that fetches an address *a model chose*, which makes it a server-side request forgery surface ([[DOC-2]]). The rule refuses non-http(s) schemes, URLs carrying credentials, and private, loopback, link-local, unique-local, CGNAT and multicast address space. That includes the cloud metadata endpoint written as a bare IPv4 address or as IPv4-mapped IPv6, plus `localhost` and `.local` / `.localhost` / `.internal` / `.home.arpa` names. The rule is applied to the typed address up front (so a bad address leases no metered browser) and then to the requests the page makes. On the Worker (Browser Rendering), that is every request, including each redirect hop and every subresource. On Node (Playwright), it is every request `page.route` sees: the navigation and its subresources, but not redirect hops (see Known gaps). On the Worker the guard also trips a redirect cap (more than 5 distinct origins) and a byte cap (32 MiB), after which every later request is refused at the seam.
- **Refusals are named and journalled.** A refusal of the typed address reaches the model under the surface's declared `REFUSED` error with a reason. Address-space refusals name the address, scheme refusals name the scheme, and credential refusals never echo the URL. The model is told not to retry or re-spell. The Toolbox audit record for the call carries the URL. Requests refused mid-capture, including cap trips, are reported to the model in the result's `refusals`, never dropped silently. They are not carried in the audit record, though: that record holds only the typed URL and a successful outcome (see Known gaps 7).
- **What comes back is a stranger's content.** All three operations return `untrusted` provenance, and `capture_site` tells the model that captured words are material to report on, never instructions.

**In scope:** the three operations, the egress rule at both driver seams, the Worker-side caps, pre-flight, REFUSED and audit, untrusted-content marking, and (REQ-166) adoption of a completed capture as a multi-member `reference` material ticket with provenance-derived rights, idempotent recapture and an always-present adoption report.
**Out of scope:** surface composition, grant, the picture vocabulary and `screenshot` (STORY-157, plan item 4); `compare` / `check_fidelity` (plan item 5); the operator-typed `1c capture` command (STORY-124/147), which installs no guard and keeps its existing network behaviour; how the Library list and detail pane present a capture (screenshot preview, member count, screenshot download, description links), which is STORY-144; retention, the internal-corpus export and the quarantine write gate ([[DOC-38]] §11–12); the asset-library promotion gate on `republishable` ([[DOC-38]] §5).
**Explicit non-goal:** DNS rebinding is not defended. The guard sees host names and literal addresses, not what a name resolves to, and nothing inside workerd can resolve a name to check it.

## Technical Context
- Part of CAP-92 (Site Control Surface: Declared, Granted, Validated & Audited). The operations are declared in the fidelity surface declaration (group `SeeSite`, every operation `effect: read`). The audit record is the Toolbox's own, as for the L1 surface.
- Builds on STORY-124/147 (capture mechanics and reference bundle storage) and STORY-142 (guarded retrieval for material fetch, which is a separate path). This story pins SSRF enforcement at the **browser drivers' request seams**, which material fetch does not cover.
- Refactor carried with REQ-157, with no behaviour change: the capture pipeline is inject-or-fail (it no longer defaults its driver seams to Playwright), and the Node defaults live in the Node-only capture barrel, so `1c capture` and real-browser tests call what they always did. STORY-147's ACs are unchanged.
- Caps as declared: 5 redirect origins, 32 MiB total response bytes (`MAX_CAPTURE_MS` = 60 s is declared but not applied). A request refused at the seam is answered 403, so the page fails that resource and carries on rather than stalling.
- **REQ-166 adoption.** The ticket store reaches `capture_site` as an optional adoption dependency on the fidelity surface's deps: present on a host that can write tickets, absent on the `1c` CLI (no D1; [[REQ-155]] removed `node:fs` from the capture import graph). This follows the same conditional-composition rule the surface itself is registered under. Adoption runs only after the bundle is whole. Its order is ticket first, then member records. A crash can therefore leave a reference with fewer members (repaired by recapturing) or an orphan blob (swept), but never a record naming absent bytes. The reference ticket carries `kind: capture`, `origin: captured`, `role: reference`, `source_url`, `bundle`, `rights`, `republishable`, `exportable` and description status/model, and **no** `filename` field. The Capture record gained an optional `title` read during the capture pass, so re-extraction (which reads `capture.json` first) and the ticket agree on what the site is called. Adoption awaits the corpus index refresh when one is wired, so the capture is findable as soon as the call returns.
- Evidence: `tests/test_reconciliation_capture_site_egress.test.ts` (AC2044–AC2053), the AC6 UATs in `tests/test_UAT_FC_REQ-157_fidelity_surface.test.ts`, and (REQ-166) `tests/test_UAT_FC_REQ-166_capture_site_adopts.workers.test.ts` and `tests/test_UAT_FC_REQ-166_capture_to_ticket.workers.test.ts`.

## Known gaps (aligned to code, see fix_plan iteration 6)
The ACs describe the code as landed, except where marked as a REQ-166 code-issue below. Each of the following contradicts intent. Gaps 1–5 and 7 are tracked by the follow-up fix ticket **BUG-315 (bug-84072362)**, "capture_site: refusals narrower than REQ-157 AC6":
1. **The redirect cap counts every origin, not redirect hops.** The guard adds the origin of *every* allowed request, subresources included, and trips once more than 5 distinct origins have been seen, even though its own comment says "documents, not subresources". An ordinary page that loads a web-font host, a CDN and analytics trips the cap, and every later request is refused. (Out-of-window BUG-127 changes this.)
2. **The byte cap is not enforced on Node.** Only the Browser Rendering driver records response bytes against the guard. The Playwright driver never does, so Node captures are unbounded in size. (Out-of-window BUG-172 later removes the byte cap entirely.)
3. **The time cap is never applied.** `MAX_CAPTURE_MS` (60 s) is declared ("passed to the session lease"), but nothing passes it anywhere.
4. **A tripped capture is not refused.** Intent says a capture over the size cap or caught in a redirect loop "is refused". `capture_site` never checks `guard.tripped`; it returns a successful named reference with the trip listed in `refusals`.
5. **Node redirect hops are not checked (SSRF).** Playwright does not invoke `page.route` for redirect hops, so on the Node host a public URL that redirects into private or link-local space is followed without being checked. This sits beside the DNS-rebinding non-goal as a known limitation.
6. **Not-found paths are unreachable.** `readCapture` throws `Bundle '<name>' has no capture.json.` before `describe_reference` can map a missing name to `NOT_FOUND`, and before `list_references` can report a record-less bundle with null url/time. So `list_references` fails outright if any bundle lacks a capture record.
7. **Mid-capture refusals are not journalled with their URL.** The Toolbox audit record for a `capture_site` call carries `params.url` (the typed address) and an outcome. `capture_site`'s `returns` declares no `summary` projection, so a capture that completes with seam refusals is recorded as `outcome.ok: true` with `outcome.summary: null`. The refused request URLs reach the model in `refusals` but never reach the journal. Only typed-address refusals are journalled as refusals. (BUG-315, bug-84072362)

**REQ-166 code-issues (for `fix_uat_coverage`; the ACs carry the intent, not the code):**

8. **The deployed Worker never adopts a capture.** REQ-166 says *"The Worker supplies it in `shot.ts`"* and *"`capture_site` yields both a bundle and a `reference` ticket, and says which"*. `shot.ts`'s `fidelityDeps` accepts the adoption dependency, but `router.ts` calls `fidelityDeps(...)` without it, and nothing else in the app binds `adoptCapture`. So on the deployed host every capture answers `reference: {adopted: false, why: 'this deployment keeps no corpus…'}` and no reference ticket is written. The adoption AC is written to intent and is expected to fail against the production composition until `router.ts` binds adoption over the request's ticket store.
9. **The client's declared domain never reaches adoption.** The rights rule takes a declared client domain, but no caller supplies one (the adoption dependency takes only a bundle name). In production every capture is therefore recorded third-party (not republishable, exportable), including the client's own old site. That contradicts REQ-166's rights table (3a: their own domain is republishable, not exportable).
10. **The domain-mismatch question is not asked.** REQ-166 acceptance: *"a domain mismatch prompts the one factual question rather than assuming"* ("is this your site?"). No code path asks it. Rights are decided from the URL alone. This is recorded here and not given an AC under this plan item. It is a client-facing prompt that the capture_site operation cannot express on its own, and it needs its own intent-driven follow-up.

## Reconciliation Decisions
- **Refused subresources do not fail the capture** (decided at reconciliation, 2026-10-27): intent is silent on what happens when one subresource of an otherwise public page is refused. The code answers it 403, lets the page finish, and reports every refusal in the result even on success, because a capture that silently skipped imagery makes every later verdict wrong. Formalized as the "every request is checked" AC.
- **Pre-flight before leasing a browser** (decided at reconciliation, 2026-10-27): intent puts the control at the driver seam and does not mention a pre-flight. The code also checks the typed address first, so an obviously bad address costs no metered browser and no retries, and the caller is told "refused" rather than "capture failed". Formalized as the typed-address AC.
- **Credentials in a URL are refused, not stripped, and not echoed** (decided at reconciliation, 2026-10-27): intent does not mention credentials. The code refuses, because whoever wrote them meant them to be sent, and sending them to a host the model chose must not happen quietly. The refusal text does not repeat the URL. Formalized within the typed-address AC.
- **The concrete cap values** (5, 32 MiB) (decided at reconciliation, 2026-10-27): intent says "cap" without numbers. The values as declared in the code are formalized.
- **list/describe report shapes** (decided at reconciliation, 2026-10-27): intent says only "what has been captured, and what is in it". The fields the code returns are formalized, because the image counts and findings are what `check_fidelity` and the surface's own workflow note depend on.
- **ACs aligned to code** (fix_plan iteration 6, 2026-10-27): code_frozen was not lifted. AC2045–AC2050 were rewritten to the behaviour as landed, and the divergences were moved to Known gaps above.
- **Intent–code conflict: refusals are narrower than REQ-157 AC6** (recorded at reconciliation review report-9ddac478, G1, 2026-10-30). REQ-157 (request-3f8737f2) AC6 says `capture_site` "is refused for private address space, over-large responses and redirect loops; each refusal is journalled with the URL". Its design says this holds on both hosts. The code as landed diverges, and this story's ACs describe the code, not the intent:
  - **Over-large response:** the guard trips (`response-cap`) on the Worker, but `capture_site` never checks `guard.tripped`, so a bundle is still returned with the trip only listed in `refusals` (AC-2050).
  - **Redirect loop:** the cap counts distinct origins (subresources included), not redirect hops, and when it trips the capture still succeeds and returns a reference (AC-2049).
  - **Node host:** there is no byte cap, no loop detection and no redirect-hop guard. Playwright's `page.route` does not see redirect hops, and the Playwright driver never records bytes (AC-2048, AC-2050).
  - **Time cap:** `MAX_CAPTURE_MS` (60 s) is declared but never applied.
  - **Journalling:** only typed-address refusals reach the audit record as refusals. Seam refusals and cap trips are reported to the model but not journalled with their URL (AC-2051).

  Code was frozen for this reconciliation, so the conflict is not resolved here. The AC titles were rewritten so that none promises refusal or both-host behaviour the code does not deliver. The fix is tracked as **BUG-315 (bug-84072362)**. When it lands, AC-2048–AC-2051 should be restored to the refusal wording.
- **REQ-166 dedup: unchanged recapture writes neither blob nor record** (decided at reconciliation, BUNDLE-34, 2026-10-31): REQ-166's earlier line *"recapturing an unchanged site creates new records but no new blobs"* is explicitly superseded by its own "Corrections" section, because attachments are no longer content-addressed. The AC uses the corrected wording: a member is matched by content hash, an unchanged one writes nothing, and a changed one replaces its record and detaches the superseded one.
- **REQ-166 identity is the bundle name, not the URL** (decided at reconciliation, BUNDLE-34, 2026-10-31): the intent's corrections section overrides its own "one `reference` per URL". The AC keys recapture on the bundle name.
- **Members that vanish on recapture are detached** (decided at reconciliation, BUNDLE-34, 2026-10-31): intent covers changed members but is silent on a member the new capture no longer holds. The code detaches it, so the attachment set mirrors the current bundle and no stale member stays live. Formalized in the recapture AC.
- **A subdomain of the declared domain counts as the client's own** (decided at reconciliation, BUNDLE-34, 2026-10-31): intent says "matches the client's declared domain" without defining a match. The code treats the declared domain and its subdomains (with a leading `www.` ignored) as the client's own, and does not use a bare suffix match, so `notexample.com` does not match `example.com`. Otherwise `www.example.com` would mark the client's own copy unpublishable on their own site. Formalized in the rights AC.
- **The adoption report's shape** (decided at reconciliation, BUNDLE-34, 2026-10-31): intent says the answer "says whether a `reference` ticket was written". The code answers `reference: {adopted, uid, created, why}` on every call, with `why` null on success and a reason otherwise. These fields are formalized in AC-2044.
