# Behavior Modules — Contract & Catalog

**Status:** Founded by **REQ-85** (framework pivot Phase D), alongside [[DOC-23]]
(L1 substrate) and [[DOC-24]] (framework purpose). Specifies what a **behavior
module** is after the pivot, its typed contract, how it renders, and how it is
validated — with `carousel` and `contact-form` as worked examples. Supersedes the
"module = layout unit" model of [[DOC-14]].

## 1. What a behavior module is

Since the pivot, **layout is owned by the L1 substrate** ([[DOC-23]]) and a
*module* no longer means a unit of layout. A **behavior module** is a **vetted
behavioural building block** — a carousel, a lead-capture form; later payments,
auth, email-capture, scroll-animation. It is defined by four things:

1. **A vetted behavioural core** — framework code (the AI *configures* it, never
   writes it inline): the scroll-snap mechanics, the form submission + anti-spam
   surface, the client behaviour that ships as JS.
2. **Typed `config`** — behavioural / integration parameters (how many slides
   show, an endpoint URL, a field schema). **Never aesthetics.**
3. **Named L1 presentation `slots`** — the behavior declares slots; the instance
   fills each with an **L1 subtree**. Appearance is 100% L1, inside the validated
   L1 security envelope. The module *wraps* L1; it never paints it.
4. **Conformance obligations** — the universal ACs the behavior must satisfy
   ([[DOC-20]]) plus **isolation**.

This is the division that makes the product a strict superset of template builders
([[DOC-24]]): **behaviour is fixed, vetted, tested code; appearance is flexible L1
the AI authors freely.** A behavior is the structured escape valve to arbitrary
behaviour that never leaves the model.

## 2. The contract (`BehaviorMeta`)

Each module exports a `behaviorMeta` satisfying `BehaviorMeta`
(`packages/framework/src/modules/behavior.ts`):

```ts
interface BehaviorMeta {
  id: string
  version: number                 // bumped on a breaking contract change
  kind: 'behavior'
  config: Record<string, BehaviorConfigSpec>   // behavioural params only
  slots:  Record<string, BehaviorSlotSpec>     // named L1 presentation slots
  conformance: {
    obligations: ('safety'|'security'|'x-browser'|'responsive'|'isolation')[]
    except?: Record<string, string>              // AC id → reason
  }
}
```

- **`BehaviorConfigSpec`** — `type` ∈ `boolean | integer | enum | string | url |
  list`, `required`, plus bounds (`min`/`max`, `minItems`/`maxItems`, `values`,
  `itemSchema` for lists of objects, `default`). Config is **data-only** — it can
  never carry raw CSS/HTML.
- **`BehaviorSlotSpec`** — `required`, `repeated?` (a repeated slot takes an
  array of subtrees, one per item — carousel slides), `minItems`/`maxItems`.

It deliberately replaces the pre-pivot `ModuleMeta` (variants + aesthetic dials +
styled `contentSchema`): those axes moved to L1.

## 3. The instance

A behavior instance carries `config` + `slots` (Option A — the behavior
*wraps* L1; see REQ-85):

```jsonc
{ "id": "gallery", "type": "carousel", "version": 2,
  "config": { "view": "peek", "controls": "dots" },
  "slots":  { "slide": [ <L1 subtree>, <L1 subtree>, … ] } }
```

`slots` values are L1 nodes (a single subtree, or an array for a repeated slot),
validated by the L1 envelope. `moduleInstanceSchema` carries `config` + `slots`;
the pre-pivot `variant`/`dials`/`content` fields remain optional only for the
capture→dials reproduction engine (its re-basing onto L1 is separate work).

## 4. How a behavior renders

- **Presentation** — the core mounts each slot's L1 subtree via `renderL1Fragment`
  (`l1/render.ts`), which renders an array of subtrees under one class namespace
  (`<instanceId>-<slot>-l1-N`) so multiple slots and multiple instances on a page
  never collide. The per-instance CSS (geometry/colour vary by slide) is emitted
  inline in the module output; the static chrome CSS lives in the `.astro`
  `<style>` and is folded into `theme.css` by `getModuleCss()`.
- **Client behaviour** — a behavior ships **fixed, vetted, tested client code**.
  `tools/generate` renders SSR HTML through Astro's container API, which does not
  bundle island scripts; so each behavior authors a self-contained, defensive
  **`client.js`** (plain browser JS, no imports), `getModuleClientJs()` folds them,
  and the pipeline writes one **`capabilities.js`** asset the page references as a
  single `<script type="module">`. No dev-path island scripts. The `.astro` marks
  behavioural state with `data-*` attributes the `client.js` reads.

## 5. Validation

`packages/framework/src/modules/behavior.ts` exports:

- `validateBehaviorConfig(meta, config)` — types + bounds + enum + required.
- `validateBehaviorSlots(meta, slots)` — required slots present; repeated slot
  counts within bounds; single-vs-list shape; **every subtree parses as a valid L1
  node** (the security line — slot content can never smuggle raw markup past the
  L1 envelope).
- `validateBehaviorInstance(meta, {config, slots})` — both together.

## 6. Conformance obligations

Every behavior declares the universal ACs ([[DOC-20]]) **plus isolation**:

- **safety / security / x-browser / responsive** — the four universal envelope ACs,
  run through the shared harness against **config/slot** fixtures.
- **isolation** (REQ-85) — a behavior given schema-valid but *degenerate*
  config/slots must **degrade inertly**: render without throwing and keep the page
  structurally intact. A render that throws (`isolation.render-throws`) or emits no
  band (`isolation.empty-render`) is a violation. Render-level — needs no browser,
  so it always runs. Isolation fixtures are hostile-but-*safe* (wrong-typed config,
  a null slide, a missing optional slot) — **not** security payloads, since a
  behavior that *fails loud* on an unsafe URL is correct there.

## 7. Worked example — `carousel`

- **core** — a pure CSS `scroll-snap` track (swipeable with no JS), per-view slide
  sizing, a decorative dots row, and autoplay/loop via `carousel/client.js`.
- **config** — `view` (`single|peek|multi`), `controls` (`none|dots`), `autoplay`
  (bool), `loop` (bool). All behavioural.
- **slots** — `slide` (repeated, 1..20) — each slide's entire look is an L1 subtree.
- **isolation** — malformed slides are dropped, not rendered; `client.js` guards
  every element access and try/catches, degrading to the no-JS scroll baseline.

## 8. Worked example — `contact-form`

- **core** — a functional, a11y-labelled `<form>` from `config.fields`, the honeypot
  + Turnstile anti-spam surface, the no-JS `method=post` baseline, and the JSON-fetch
  progressive enhancement (`contact-form/client.js`).
- **config** — `action` (url), `fields` (list of `{name,label,type,required}`),
  `successMessage`. Field `label`s stay in the core — a programmatic label is an
  accessibility obligation (the responsive/a11y dimension), not styling.
- **slots** — `intro` (optional decorative heading/subhead), `submit` (optional L1
  look for the submit button; absent → a plain functional button).

## 10. Amendment (REQ-96) — the two composition directions

**Amends §1.3, §2, §7 and §8.** Founded by [[request-3a064234]] (REQ-96), on
evidence from [[request-7ff1bacd]] (REQ-88)'s gigabytealchemy.ai reproduction.

### 10.1 What §1.3 got wrong

§1.3 states the rule correctly — *appearance is 100% L1; the module wraps L1, it
never paints it* — but assumes a single composition direction: **the module wraps
L1**. A slot is a container the module renders *around* an L1 subtree.

That holds when the behavioural element is itself a **container**. A carousel's
`<li class="carousel__slide">` genuinely can hold a slide's entire L1 look.

It is structurally impossible for a **leaf**. `<input>` is a void element;
`<textarea>`'s content is its value. There is nowhere to put an L1 subtree. So
for form controls the rule is not merely unmet — it is **unreachable**, the
module has no choice but to paint, and **no validator can detect the violation**,
because §2's contract has no vocabulary for "this element's look belongs to L1".

The `submit` slot is the tell: it works only because `<button>` happens to be a
container, and REQ-88 still had to add a `.contact-form__submit--l1` modifier to
stop the module painting over the L1 chip bound into it. That modifier is the gap
made visible.

Both shipped modules violate §1.3 and §2 today. `carousel`'s is the more
instructive, because it is in the doc's own worked example:

```css
.carousel.view-peek .carousel__slide { flex-basis: 85% }   /* → 60% at ≥768px */
```

`config.view` is an **aesthetic dial wearing behavioural clothes**. §2 says config
is data-only, *"never aesthetics"* — and `view` resolves to a flex-basis.

### 10.2 The rule, restated

A behavior composes with L1 in **two** directions, chosen per element by whether
that element can hold children:

| element | direction | mechanism |
|---|---|---|
| **container** (carousel slide, form wrapper) | module wraps L1 | `slots` — unchanged, §1.3 stands |
| **leaf control** (`<input>`, `<textarea>`, a button's face) | **L1 wraps module** | **`control` node** — new |

An L1 node carrying `control: '<name>'` emits the element the module declared
under that name, with **L1's class, geometry and paint axes**. The module
supplies only that element's **attribute bundle**.

| | owns |
|---|---|
| **L1** | class, geometry, every paint axis — for the behaviour's own controls, not merely decoration around them |
| **module** | which elements must exist; their `type` / `name` / `required` / `for`↔`id` wiring; the endpoint; the client behaviour |

A conforming behavior therefore ships **zero CSS** beyond §10.3's invariants. Not
less — none. Layout-agnostic *by construction* rather than by discipline, which
is the only version a contract can enforce.

### 10.3 Invariant elements — the carve-out

**Not every element is L1's to style.** The honeypot must be invisible; the
Turnstile mount must sit where the widget expects it; a visually-hidden label
must stay out of flow.

Those are **obligations, not taste**. A designer must not be able to reveal the
honeypot. So a behavior keeps a small, declared set of **invariant elements**
whose presentation is fixed by the obligation rather than by the author, and
whose CSS therefore stays in the module.

The line is not *"L1 owns everything"*. It is:

> **L1 owns everything the reference can legitimately vary; the module owns what
> an obligation pins.**

Invariant elements are **declared**, not incidental — anything not on that list
paints from L1 or does not paint at all.

*Second consumer:* invariant elements are also invisible to the eye but very
visible to the value gate. On GA they put **15 repro-only objects** into
`values-diff` (hidden labels, honeypot inputs, Turnstile divs), sliding the
control pairing so every field mispaired against its neighbour and all 26
reported deltas became unreadable. A gate must exclude module-invariant elements.
See [[request-16253634]] (REQ-94).

### 10.4 Security is unchanged — and must stay construction-time

L1 contributes **class + geometry + paint, and only those**. The module still
authors `action` through `assertSafeUrl`, the `name` / `type` / `required`, and
the label↔input pairing.

This is load-bearing. The framework's value is the safety envelope ([[DOC-24]]);
if inverting the composition direction degraded a guarantee from *"true by
construction"* to *"hopefully validated"*, the amendment would be a net loss. It
does not: the module authors every security-relevant attribute exactly as before,
and `validateBehaviorSlots`'s rule (§5) extends unchanged to `control` nodes —
they parse as L1 or they are rejected.

### 10.5 The default look moves to L2

Deleting a module's stylesheet means a behavior authored **without** a capture has
no look at all, so every site would pay authoring cost for what used to be
drop-in.

The stylesheet is therefore **relocated, not deleted** — to an **L2 preset**, the
optional library of vetted L1 designs [[DOC-24]] already anticipates. The default
look becomes a *starting point* instead of a *ceiling*.

This is precisely the move the pivot already made for layout modules
([[DOC-14]] → [[DOC-23]]): capability that used to be locked inside a module
becomes L1 anyone can vary, and the vetted arrangement survives as a preset.

### 10.6 Evidence

GA reproduces to a passing cross-gate (perceptual mean 2.61/255, l1-gate maxΔ
0.9px, 0 fold residuals). The only visible defect left is the form, and the
perceptual diff is emphatic: the top five regions are all form, the two buttons
worst (mean 120 and 145), the rest of the page near zero.

| | reference | ours | closes via |
|---|---|---|---|
| field surface | transparent, dark 1px border | white fill, `#e5e7eb` border | L1 paint axes |
| field height | 50px (textarea 146) | 44px (textarea 116) | L1 geometry |
| Subscribe | inline, right of its field | stacked below | *ceases to be a concept* — each control carries its own geometry |

The third row is the one that matters for the contract: **"inline vs stacked" is
not a dial the module should have, at any granularity.** Arrangement is an
emergent property of where L1 puts each control.

§7 and §8's slot lists are superseded accordingly; both worked examples are
re-specified when REQ-96 lands.

## 11. Cross-reference (CHAT-26) — locale, money and time obligations

**Does not amend §1–§10.** [[DOC-34]] adds obligations that bind behavior modules
**not yet authored**, recorded before the code exists because they are free now
and expensive to retrofit:

- **payments** — the charged amount is `config` as `{amount_minor, currency}`;
  the displayed amount **derives** from it, never independently authored copy, so
  shown price and charged price are equal by construction. Formatting is
  `Intl.NumberFormat`, never hand-rolled. The module declares its VAT-display
  obligation per site `country`.
- **calendar** — never emits a hand-formatted date/time string; always
  `Intl.DateTimeFormat` with the page locale. Stores **instants in UTC plus an
  IANA zone id**, never a wall-clock string or a fixed offset (offsets break
  across DST, and the EU and US transition on different dates).

Both sit inside §2's *config is data-only, never aesthetics* line rather than
straining it: a formatted price or date is **data resolved from locale**, not a
presentation choice. Their appearance remains 100% L1.

**Update (REQ-152): the seam both are obliged to use now exists**, at
`packages/framework/src/intl.ts` — `formatMoney(amountMinor, currency, locale)`
and `formatDateTime(instant, timeZone, locale, opts)`. Neither module has to
invent its own answer, and neither should grow its own: a module that formats
money or a date reads `props.locale` (REQ-151) and calls these. Two details the
seam settles so a module cannot get them wrong — **minor units are not always
two** (JPY 0, KWD 3, so there is no `/100` anywhere), and a **zone-less
wall-clock string is refused**, not reinterpreted as the build host's zone.

`formatDateTime` deliberately has no clock-reading overload. That is [[DOC-34]]
§8.4's render-determinism rule made structural: a behavior module renders
byte-identically twice, and content that depends on *now* is emitted as a mount
point plus data for the client to resolve — never baked into an immutable
published revision.

See [[DOC-34]] §6–§8, §8.4.
