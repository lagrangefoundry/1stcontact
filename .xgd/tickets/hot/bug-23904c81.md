## Symptom (operator, production, 2026-11-07)

A WooCommerce import into a production business stalled and still shows "running" in the Shop tab.

- **Products: done.** 367 products were imported across 37 pages, with no errors.
- **Photos: stopped.** 42 of 1,943 were stored; 1,901 are still `pending`. Nothing has moved since 00:39:31 UTC.
- **The `ShopImport` Workflow instance is reported `Completed`** by Cloudflare, yet the `shop_imports` row is still `status = 'running'`, `phase = 'photos'`.
- **A new import is refused** ("An import is already running") until the row is 30 minutes stale (`STALE_RUN_MS`). Even then a rerun would stop at the same point.
- **Not seen on dev:** local miniflare doesn't enforce the limit below.

## Root cause (production Workers Logs and the instance's step list)

1. **The whole run shares one Worker invocation's API-request budget.** `runShopImport` runs every step (`items 0…36`, `photos n`, and the `describe n` chain beside them) in the same invocation, because the waits between steps (`DESCRIBE_WAIT_MS`, 3 s) are too short for the instance to hibernate. D1, R2 and other binding calls add up across the items phase and every photo's store and index update. During `photos 1` the invocation hit Cloudflare's cap: `Too many API requests by single Worker invocation`. The step's retries ran in the same invocation and failed at once (`❌ Error`, 0 s each).
2. **The fail path needs the exhausted budget.** The `fail` step (`failImport`, one D1 write) hit the same cap and failed. The run then returned, so the instance is `Completed` while the row stays `running` for good. The describe chain also stopped (`shop_import_describe_stopped`, same error).
3. **Concurrent photo stores corrupt the business's Library index.** Each stored photo runs `indexAfterWrite` → an index refresh. Photos are stored several at a time (`inLanes`), and each refresh is a read-modify-write of four separate R2 objects (`embeddings.bin`, `metadata.json`, `manifest`, `model_info.json`, written one after another by `saveIndex` in `@lagrangefoundry/knowledge`'s `index_store.js`). Interleaved refreshes left a mismatched pair. The production index for the affected business now holds 86 metadata rows and 33,792 floats, which is not a whole number of rows; the declared dimension is 384. Logged warnings during the run: "the index is corrupt", "index row width is 2304 / 416 / 390 but model_info.json declares 384", and R2 `10058` ("Reduce your concurrent request rate for the same object").
4. **A corrupt index never heals.** `loadIndex` throws on a mismatched index. Every later refresh loads it first and fails (BUG-119's warning, "the next successful pass picks it up", is never true), so nothing stored after this is findable by Library search until the index is rebuilt.

## Fix

### 1. The photo phase doesn't run inside one Worker invocation
- Per Architecture Policy 31 (catalogue-wide media processing belongs in a job container, one on-demand instance per job, addressed through a DO and orchestrated by a Workflow step), **the photo phase (download, store, describe) runs in the job container** (EPIC-32's rig), with the Workflow step sequencing it and D1 holding progress. The container reaches platform data only through the control app's internal entrypoint (Policy 32).
- An import of any size completes: thousands of photos, with no per-invocation request cap reached. Progress (`stored`/`pending` counts) keeps moving and is visible as today.
- A killed container or a failed step is a retried Workflow step that resumes from the `pending` rows. Nothing already stored is downloaded again.
- The items phase stays bounded per step. If it is close to the cap at a few hundred products, it moves with the photos; check this against the cap and record the decision in "What landed".

### 2. A failed import is always recorded as failed
- When a run can't continue, the import ends as `failed` with the error shown in the Shop tab, never `running` with nothing moving. That holds even when the run that failed can no longer make calls.
- **A run whose Workflow instance has ended with its row still `running` is reconciled to `failed`** the next time the import's status is read. Comparing the instance's state with the row is enough; nobody waits the 30 minutes.
- Starting a new import after a failed one works at once, and re-imports without duplicates (BUG-333's rule).

### 3. A business's Library index can't be corrupted by concurrent writes, and a corrupt one is rebuilt
- **Index refreshes for one business are serialized:** one at a time, through the business's coordinator (Policy 7) or an equivalent single-writer rule. Many photos stored at once leave a consistent index containing all of them.
- **A refresh that finds a corrupt index rebuilds it** from the stored materials, instead of failing every refresh after it. This is logged once as `kb_index_rebuilt`, with the business id and the reason.
- If the atomic-save or single-writer part has to change `@lagrangefoundry/knowledge` itself, that change is a ticket in that package's repository (cross-repo rule), and this ticket covers the 1stcontact side.

### 4. Repair the affected production business
- After deploy, the stuck import is reconciled to `failed` by fix 2, and the business's Library index is rebuilt by fix 3, checked as a whole number of rows at dimension 384.
- Re-running the same import then finishes all photos without duplicates. Record the counts here.

## Test plan
UATs named `test_UAT_FC_BUG-380_*`. Stripe isn't involved; WooCommerce is mocked at its HTTP boundary, and the per-invocation request cap is simulated by a counting binding wrapper that throws Cloudflare's exact error past N calls.
- An import with far more photos than one invocation's cap completes, and every photo is stored.
- With the cap reached mid-photos, the import ends `failed` with the error and doesn't stay `running`. A new import can start at once and resumes without duplicate items.
- A row whose Workflow instance has ended while the row is still `running` reads as `failed` on the next status read.
- Twenty photos stored concurrently leave a Library index whose float count is rows × dimension, containing all twenty.
- A refresh over a corrupted index rebuilds it and logs `kb_index_rebuilt` once; the next refresh succeeds.

## Definition of done
After deploy to production: the stuck import shows failed, the affected business's index loads cleanly, and a rerun of its import stores all ~1,943 photos, with no `Too many API requests` in Workers Logs. Record the results here.
