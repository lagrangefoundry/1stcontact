## Story
**As an** owner (or operator) of a business in the builder, **I want** a Contacts tab listing everyone my business knows, and for any one of them a single view of who they are, which businesses they run and which grants they hold, **so that** I can see my business's population, and spot lapsed customers or stray grants, without querying the database.

## Description
The builder gains a third tab, labelled **Contacts**, beside the Site and Library tabs. It shows the people of **whichever business the caller is currently scoped to**. From the 1st Contact business these are our customers. From a customer's business they are that customer's customers. The tab works the same way for every business and is never named for, or limited to, the platform's privileged half (REQ-170 2026-09-04 revision; BUG-56).

In scope:
- **List**: every person row in the scoped business. That includes uninvited contacts, because the list shares the CRM's population. Each row has two separate cells, the display name (or *No name yet*) and the address, ordered oldest first. The list heading reads **Contacts**.
- **Business switch**: the list is cleared and then re-read for the new business. It is never re-filtered in place.
- **Isolation**: someone in another business can't be read. Asking for them gives the same "not found" answer as asking for an id that doesn't exist.
- **Detail pane**: it opens immediately for the selected person and then fills with:
  - **Who they are**: the person's record.
  - **Businesses**: one table keyed by business. It joins the businesses this person runs (operator relation) with the grants concerning them (entitled relation). It has column headings, and empty cells say why they are empty in words.
- **Presentation**: the list, the detail sections, and the dialogs this tab opens all use the builder's field type scale and spacing (webui-fields). No style keys on what a state is called.

Out of scope, and owned by sibling stories in this bundle:
- Editing the record, withdrawing grants, the suspend/status control, and the provisioning dialog's behaviour (plan item 4).
- The invite (plan item 2).
- Pipeline and access axes, badges and facets (plan item 5).
- Editing `display_name` (REQ-183 §5).

## Technical Context
- Read surface over D1 identity tables (`users`, `memberships`, `entitlements`, `tenants`). Scope is resolved by the business-scope capability (story-7102ffe3, CAP-114), and everything is read through the tenant-scoped handle.
- The routes are deliberately not under an `admin` prefix (REQ-170 "What was implemented"). Per DOC-40 §2.1 rule 1, a people list must not branch on which business it is.
- The tab id stays `people` while the visible label is `Contacts` (BUG-56). The id namespaces the persisted split position and selection.
- A grant carries its business's name through a left join to `tenants`. A grant whose tenant row is gone still appears and shows the business id instead (REQ-189 "What the implementation had to add").
- Grants stay a list and are never collapsed into one current value (DOC-40 §5). Several grants on one business sit under a single business/role cell.
- REQ-186's repair: the detail pane must render content. Before the repair it was blank for every person, with no visible error.
- Related: CAP-85 (Builder Workspace) supplies the tab shell; CAP-114 owns the identity model these rows come from.

## Reconciliation Decisions
- **List ordering** (decided at reconciliation, 2026-11-01): the intent doesn't specify an order. The code orders by creation time, oldest first, so that rows don't move when someone signs in. Formalized in the list AC because a stable order is what an operator relies on.
- **Grant-only businesses sort last** (decided at reconciliation, 2026-11-01): REQ-189's implementation notes record this as a consequence rather than a requirement. Operated businesses keep their membership-grant order and grant-only rows come after them. Formalized in the joined-table AC.
- **Empty Businesses section** (decided at reconciliation, 2026-11-01): the intent doesn't say what to show for someone who runs nothing and holds nothing. The code shows a sentence saying so, *None — they run no business, and hold no grant.*, and no empty table. Formalized because REQ-189's rule that "every empty cell says why" applies just as much to an empty section.
- **Dangling grant shows the business id** (decided at reconciliation, 2026-11-01): REQ-189 requires the grant to name its business. When the tenant row is gone there is no name to show. The code falls back to the id, which is the only remaining handle, so the row is never dropped or left blank. Formalized in the grant-names AC.
- **Status marker only for the exception** (decided at reconciliation, 2026-11-01): the intent doesn't cover this. The list adds a status marker only for a person who is not `active`. Left out of this story's ACs because the status control belongs to plan item 4.
- **Exception markers are condition hooks, not value hooks** (decided at reconciliation, 2026-11-01): REQ-188/189 say no rule may name a state label or a value of either axis. The code has two exception classes, `__suspended` and `__revoked`.
  - `__suspended` is drawn for any account status that is not `active`, and prints the actual status as a word.
  - `__revoked` (shown as "withdrawn") is drawn whenever a membership has a revocation time.
  Each is selected by a condition ("cannot sign in", "membership withdrawn") rather than by one stored value, and neither belongs to the pipeline or access axes the rule was written for. Decided compliant. The no-value-hook AC therefore covers the stage, access and grant-status cells.
- **Type scale is 13px for primary text, not for every element** (decided at reconciliation, 2026-11-01): REQ-189 says to match webui-fields' type scale. The code puts primary text (row name, table, empty and hint text) at 13px, and gives secondary text (the address, pills) a smaller muted size, which follows webui-fields' label/value hierarchy. The styling AC is written to those specific metrics.
- No contradictions between intent and code were found for this item. The earlier "Users" and "People" labels were superseded by BUG-56, and the code matches BUG-56.
