## Story

**As a** small-business client working in the builder,
**I want** one place that shows me everything I have given the platform — the document or
picture itself, shown rather than named, what the platform understands it to be, and what it
says may be done with it — and lets me correct that understanding,
**so that** I can see what my assistant is working from, find a particular thing again, read it
without leaving the workspace, and fix a description that is wrong so the assistant stops
answering from it.

## Description

A Library of the client's own material, beside the site they are working on.

**One business's material, whole.** The list is everything the open business holds — material
placed on its site and material placed on none, both roles, every kind. Under one site per
business (CHAT-36) the business is the scope: a client's other businesses are not shown, because
an assistant carrying one business's material into another's is a contamination worse than a
blank sheet, and the remedy for a cold start is to hand over the background documents you want
carried. Filters narrow by what the material is *for* (its role), by what kind of file it is, and
by a search over its title and filename. There is no "used on this site" filter: with one site
there is nothing for it to separate that the role filter and the warning do not already say.
Choosing a different business in the header selector — which is what switching site now means —
replaces the list with that business's material; the rows on screen are dropped before the new
list is asked for, so no row from the previous business survives the switch, even when that
request fails. The Library itself never asks which site is open.

**Badge the exception, not the rule.** Placement is read from one fact: the list of sites the
material has actually been placed on, recorded when a promotion onto the site landed (STORY-143).
A placed site asset is the normal case and carries no badge — marking it would spend the row's
emphasis on nearly every site-role row to say nothing about the few that matter. The one state
that is marked is a site asset whose placement is empty: the client asked for it to go on their
site and the bytes never got there. That row carries a warning in its own right — the words
*Not on the site*, a decorative glyph, the full sentence on hover, in the danger colour rather
than the accent — perceivable without colour. Background information is never marked: it is
never placed by construction, so its empty placement is a category, not a failure. The record's
**Placed on** row reads the same list and so always agrees with the warning; it is named for what
it holds — where the bytes went — rather than *Used on*, because a draft asset is in use by no
one until the client publishes, and it stays a list because the store allows more than one site.

**A row is one line, and its type is a shape.** Each row opens with an icon for the material's
kind instead of a kind pill: document, image and font each have their own, and capture — plus
any kind the filing vocabulary adds later — falls back to one shared icon, so no row is ever
iconless (an empty leading cell reads as a rendering fault, not as a kind). The pill was the only
place the row said its type in words, so the icon is announced to a screen reader as the kind:
the fact moved to the icon, it did not leave the row. The icon is followed by the title, then the
role pill on the same line — and, only on an unplaced site asset, the warning beside it. The title is the row's elastic part — set at
the same 13px as the workspace list component's own rows, taking the remaining space and
truncating with an ellipsis — while the icon and pills keep their width and never wrap, because a
half-rendered pill reads as a bug. The role pill names the role by the same words the hand-over
overlay uses (*Site asset*, *Background information*; STORY-145). Kind is still a filter and
still part of the detail record.

**The detail shows the thing, not its path.** Selecting a row shows the file itself, beside the
record of what the platform holds: filename, kind, role, where it came from, its rights, whether
it may appear on the site, every site it is placed on, and the address it was fetched from. That
record is **read-only**: rights are inferred from provenance precisely so the client is never
put in front of a legal question, and a control they could set by hand would be that question
with a checkbox on it.

**What "shown" means is decided by the content type, not by the kind.** A picture is rendered;
a markdown document is rendered as markdown; any other text, plus JSON and XML, is shown as
itself with its own line breaks kept; a PDF is given the browser's own viewer. The filing
vocabulary calls a markdown note, a plain-text export and a brand PDF all *document* — three
files that have to be shown three different ways — so the resolved content type travels on the
row beside the filename, and material that predates that field resolves its type from its own
name rather than becoming a fourth state the pane has to handle. What nothing can render — a
font, an unrecognised binary — is offered exactly as it was before: a download link and nothing
else. **The download link survives every case**, because being able to read a file on screen is
not the same as having it.

**A capture is a picture and a description, not a directory.** Most material is one file. A
captured reference is not: it is a whole site we captured, held as many files, and it reaches
the Library as a *capture*-kind row with no change to how the list is queried or filtered. The
client's model of it is *a picture of that site and what you thought of it*, so its detail shows
the capture's full-page screenshot as the preview — fetched as one named file of the capture,
never by pulling the rest — and offers no reader window, even though the capture also holds
machine-readable files a reader could draw. The single-file *File* field is dropped, because a
capture has no one filename to show; in its place the pane says plainly how many files the
capture holds (*"99 files captured"*), because a list of 99 members would be honest and useless.
The download link survives here too, and it fetches the screenshot under the screenshot's own
name rather than whichever member happens to come back first. Ordinary single-file material
keeps its *File* field and its plain, member-less download, exactly as before.

**The reader is bounded, and expands.** The window sits above the metadata, is capped at the
height the picture already uses, and scrolls, so a fifty-page brand book does not push the
rights record and the description off the bottom of a pane whose job is to show them together.
An expand control opens the same content at modal size in the workspace's existing dialog, so a
long document can be read without the list and the metadata competing for it — and browsing to
another row takes the expanded window with it rather than leaving it hanging over the file that
replaced it.

**Rendered markdown is scrubbed, and plain text is left alone.** Markdown becomes HTML, and
these bytes are not necessarily the client's own, so both the reader and the description are
rendered through the one render-then-sanitize path the workspace already uses for the
assistant's own words rather than a second one beside it. A plain-text file put through a
markdown parser would lose its own line breaks and gain headings its author did not write, so it
is shown as itself; an uploaded HTML document is shown as its source rather than run; and an SVG
stays a picture, because showing a client their own logo as angle brackets would be a regression
dressed as a feature.

**The description is the one editable thing.** The description is what the platform understands
a piece of material to be, and it is what search answers from. It is written as markdown, and it
is shown as rendered markdown rather than as its source — while clicking it still opens an
editor over the source, and a committed correction is repainted rendered. The client frequently
knows better than the description we generated, so they may rewrite it — and the correction
**re-indexes**, so it reaches retrieval rather than only the screen, and records the client as
its author, so a later re-description pass cannot overwrite their words. An empty description is
refused: the description is the only thing that makes a file findable.

**A link in a description opens away from the builder.** A capture's description opens with a
link to the site it describes, so the client can always get from our prose about a site back to
the site. The Library is a tab inside a single-page builder, so a link that navigated in place
would take the whole workspace — and any unsaved edit — with it. Every link in a rendered
description therefore opens in a new browsing context that cannot reach back into the builder,
and keeps doing so after every repaint, so a committed, reverted or cancelled correction does not
leave its links bare.

**A surface that renders markdown waits for the renderer.** The rendering engines arrive
asynchronously, and until they do, rendering degrades to escaped source — right when they are
absent, wrong when they are merely late. Both the reader and the description therefore repaint
once the engines have settled, including into an expanded window that is already open, so a pane
opened on a cold load upgrades itself instead of staying as source.

**In scope**: the Library tab and its filters; how a row presents a material (its type icon,
its one-line layout, its role pill, and the not-on-the-site warning on the exception); the detail pane, its reader, its expand-to-modal
window and its read-only rights record; how the detail presents a multi-file capture (its
screenshot preview, its file count, its screenshot download); description links that open away
from the builder; the warning and the *Placed on* row as readers of the recorded placement;
replacing the list when the business changes;
correcting a description; and the read/write surface the tab is written against — listing the
account's material (with what the bytes are, and where they are placed, on each row), reading
one piece in full (with, for a capture, the names of the files it holds), serving its bytes or
one named file of a capture, and writing a corrected description.

**Out of scope**: putting a file into the platform from the browser (the drop-to-upload
overlay), the ingestion pipeline that stores, classifies and describes a file — including the
content-type repair whose result this row carries — promotion of material into a site's asset
library and the writing of the placement record (STORY-143), the capture pipeline and the
adoption of a capture into a reference record — its members, its description and the link that
opens it, its title (STORY-159) — and the site asset picker, which chooses a value for a field
and is not replaced by this tab. The assistant pane's own wait on the same rendering engines is
not restated here.

## Technical Context

- Depends on material ingestion (STORY-140): this tab is a read view over what ingestion
  creates, and is cheap after it and impossible before it. The content type the row carries is
  the value ingestion resolved — this story reads and caches it, it does not resolve it.
- Placement travels on each listed row as `placed_on`, a list of site slugs (absent or malformed
  reads as the empty list, so a row has no third "unknown" state). It replaced `site_slug`, the
  site open at upload, which the then badge, record row and filter had all misread as placement
  (BUG-47). Under one site per business (REQ-181) the list holds zero or one slug, so "placed on
  this site" collapses to "placed at all"; the Library reads only whether it is empty. This story only reads it; STORY-143 writes it. Material that carried only
  the retired field is shown as placed nowhere — BUG-47 deliberately does no backfill.
- The description fields it writes — the description's outcome and the describer that produced
  it — are the declared vocabulary owned by STORY-128; this story writes them, it does not
  declare them.
- Re-indexing on correction reaches the client's own knowledge base (STORY-138/STORY-139); this
  story asserts that the correction is what retrieval answers with afterwards, not how the index
  is maintained.
- Serving a material's bytes is a route on the builder origin rather than a public URL: the
  public site Worker has no binding on the private material store, deliberately, and giving it
  one to save a hop would be the disclosure that boundary exists to prevent. The PDF reader is
  the same route read once by the browser's own viewer — there is no second transport.
- A capture is a `reference` record holding one attachment per bundle member, each naming its
  member (REQ-166, DOC-38 §9); STORY-159 writes it. This story reads it. The member names travel
  on the single-item read (an empty list for ordinary material, never absent) and not on the
  listed row, because listing them would cost one attachment listing per row to draw a column
  nobody looks at. The file route takes an optional member name; absent, it serves an ordinary
  material's one file exactly as before, so every earlier caller is unaffected. Naming the
  member is the same member-addressed read REQ-166's re-extraction criterion requires — one
  route serves both needs.
- The screenshot member's name (`screenshot.full.png`) is known to the pane up front rather than
  discovered from the member list, because the preview is built before the detail's own read
  lands. The file count, by contrast, waits for that read.
- The modal the expand control opens is the workspace's existing dialog shell, so Escape, the
  backdrop and the close button are the shell's behaviour and not this story's.
- The workspace chrome that hosts a tab, and the origin-wide caching behaviour its routes
  inherit, belong to STORY-99 (CAP-85). This story adds the second tab and its routes; it does
  not restate the chrome's own criteria. The tab-counting criteria those routes and panels
  falsified (AC-959, AC-976, AC-1064) are restated under their own plan item, not here.
- Row presentation (REQ-176) is the Library's own: the row content cell is built by the
  Library, and the 13px title and one-line layout are set in the builder's stylesheet. The
  workspace's shared list-detail component, which other hosts use, is not changed. Layout is
  verified through the stylesheet contract that produces it, because the test DOM computes no
  layout.
- The role pill's words are not this story's: they are the hand-over areas' labels, read from
  the one definition STORY-145 owns (AC-2021), so a relabel there reaches the pill and the role
  filter without an edit here.
- **The placement wording (REQ-181).** The pill *On this site*, its accent and the filter *Used
  on this site* are gone, superseding REQ-176's open question about renaming them; the record row
  is *Placed on*; the warning reads *Not on the site*. A *Live on the site* indicator remains out
  of scope: promotion writes to the draft, so a truthful "live" statement is a read against
  published state and belongs to its own ticket.
- **The business switch is driven by the host (REQ-179/REQ-181).** The header's business
  selection clears the Library and then re-reads the new business's material; the Library offers
  a clear and a refresh and has no site-change hook. A site change within a business is nothing
  to it. The prior premise — that a client's second site should inherit the first's material
  (DOC-38 §7.7 / DOC-10 §4.1) — is reversed by CHAT-36; that DOC change belongs to CHAT-36's
  write-up, not to this story.

## Reconciliation Decisions

- **A free-text filter over title and filename** (decided at reconciliation, 2026-09-10): the
  intent names filters by role, by kind, and by "used on this site", and is silent on a search
  box. The landed Library carries one, conjunctive with the other three. Formalized, because a
  list of tens to low hundreds of rows is browsed by name before it is browsed by category, and
  a filter the client can type into is the observable behaviour of the surface as built.
  Formalized as AC-1716.

- **Only the requesting account's material is listed** (decided at reconciliation, 2026-09-10):
  the intent states the list is tenant-*wide* and is silent on the other half — that it is
  tenant-*bound*. Formalized, because this is the first surface that shows a client their own
  files and is therefore the surface that would leak another client's if the binding were not
  real. Formalized as AC-1722.

- **A record whose bytes are gone says so** (decided at reconciliation, 2026-09-10): the intent
  is silent on a material whose stored file cannot be read. The landed pane replaces the preview
  with a plain statement rather than leaving a broken-image glyph. Formalized, because the
  ordering the pipeline uses makes this state unconstructible in normal operation — so if it is
  ever reached, saying so is the only useful behaviour. Formalized as AC-1717 (and the
  no-file-attached case as AC-1723).

- **A uid that names nothing this surface reaches is answered as not-found on the write as well
  as the reads** (decided at reconciliation, 2026-09-10): the intent states the 404-not-403 rule
  for "all four read/write routes" but motivates it only as an existence oracle. Formalized to
  include that the named record is left unchanged, because the write route is the one where the
  refusal also protects a record of another kind from being rewritten through a surface built
  for material. Formalized as AC-1724.

- **A reader that is still loading says so** (decided at reconciliation, 2026-09-14): REQ-172
  names the two ends of the reader's life — the bytes arriving, and the bytes being gone — and
  is silent on the interval between them. The landed window states that it is reading rather
  than showing an empty box. Formalized as part of the reader criterion, because a bounded
  window that is simply blank is indistinguishable from a document with nothing in it, and the
  pane's whole claim is that a client can tell what they are looking at.

- **The expanded window closes when the detail it belongs to is replaced** (decided at
  reconciliation, 2026-09-14): REQ-172 states that the reader is destroyed with the detail and
  gives the reason, but states it as an implementation consequence rather than as something a
  client observes. Formalized as client-observable, because the observable failure — an expanded
  document hanging over the row that replaced it — is the one that would be reported as a bug.

- **The "Used on" row lists every placed site, and an unplaced material shows it empty**
  (decided at reconciliation, 2026-10-25, BUNDLE-32): BUG-47 requires that the row agree with
  the badge and the filter and that a two-site material be badged on both, and is silent on how
  a plural placement is written in one record row. The landed row joins the sites with commas
  and shows nothing for a material placed nowhere. Formalized in the placement criterion,
  because a row naming only one of two sites would disagree with the badge on the other.

- **A row with no recorded kind is announced as a file** (decided at reconciliation,
  2026-10-25, BUNDLE-32): REQ-176 requires every row to carry an icon, including kinds the map
  does not name, and that the icon carry the kind to a screen reader — and is silent on a row
  whose kind is missing altogether. The landed row shows the fallback icon and labels it
  *file*. Formalized in the type-icon criterion (AC-2019), because an image with an empty
  accessible name is announced as nothing, which is the same silent deletion the labelled icon
  exists to prevent.

- **Links in every description open away, not only a capture's** (decided at reconciliation,
  2026-10-31, BUNDLE-34): REQ-166 asks that following the link at the head of a capture's
  description not navigate the builder away, and is silent on links in other material's
  descriptions. The landed pane treats every link in every rendered description the same.
  Formalized for all material, because the harm REQ-166 names — the builder navigated away and
  editor state discarded — is the same whoever wrote the link, and a correction the client types
  may contain one.

- **The opened link cannot reach back into the builder** (decided at reconciliation,
  2026-10-31, BUNDLE-34): REQ-166 states only that the link opens in a new context. The landed
  anchors also sever the opener and send no referrer. Formalized, because these addresses come
  from a page captured off the public web, and an opened page able to script the builder through
  its opener would be a hole in the very surface built to keep the builder in place.

- **The capture shows no reader window** (decided at reconciliation, 2026-10-31, BUNDLE-34):
  REQ-166 says a capture's preview is its screenshot and is silent on whether the reader REQ-172
  added also applies. A capture's resolved content type can name a machine-readable member the
  reader would draw as text; the landed pane shows only the screenshot. Formalized, because the
  client opened the row to see the site, and a JSON dump beside the picture would be the
  "directory" REQ-166 says a capture is not.

- **The file count is said in words, and says nothing until it is known** (decided at
  reconciliation, 2026-10-31, BUNDLE-34): REQ-166 gives the wording *"99 files captured"* and is
  silent on one member, none, or the interval before the detail loads. The landed line reads
  *"1 file captured"* in the singular and is empty while the detail is loading or when no member
  names are known. Formalized, because an interim or zero count would be a false statement about
  what the platform holds.

- **A capture whose screenshot cannot be fetched says so** (decided at reconciliation,
  2026-10-31, BUNDLE-34): REQ-166 is silent on a capture holding no screenshot. The file route
  refuses the request with a statement naming the member it does not hold, and the pane shows the
  same "no longer in storage" statement it shows for any material whose bytes are gone.
  Formalized in the screenshot-preview criterion and in AC-1723.
