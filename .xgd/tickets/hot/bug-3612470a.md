## What happened
After a builder pass, `get_palette` held 6 named colours, all with `count: 0`, and `get_text_styles` held 5 styles, all with 0 uses. Every element on page `home` carries literal hex in `axes.color` / `axes.surfaceFill` and inline `fontSizePx` / `fontWeight`. On the pass before that, the palette was completely empty and every colour was literal.

`describe_page` reported `attention: { broken: 0, inconsistent: 0, worth_a_look: 4 }` both times. The 4 were the form inputs, flagged `unstyled: placeholder`.

## Expected
The `describe_page` description says it flags "a colour pasted in by hand [that] matches nothing else on a page that uses its palette" as `inconsistent`. A page that has a palette and references none of it should show up in the attention counts, at least once a palette exists. Also, browser-default form controls are described as a typical `broken`/`inconsistent` case ("a form field nobody styled paints in the browser's own typeface"), yet unstyled inputs here were rated only `worth_a_look`.

## Why it matters
The consultant and the builders both gate on `broken = 0 / inconsistent = 0`. That gate passed on a page with no palette or text-style references at all, so the problem only surfaced through a separate `get_palette` call.

## Reproduce
1. Create palette entries.
2. Write elements with literal hex colours that match those palette values.
3. Run `describe_page` and read `attention`.

## Root cause
`checkPaletteDiscipline` in `tools/generate/src/cli/style-audit.ts` is proportional only: it flags literals only when the page's palette references outnumber (or equal) its literals. A page with zero references is never flagged, even when its literals are exactly the palette's own colours written out by hand.

## Fix (behaviour)
- **A literal colour that IS a palette colour is `inconsistent`, whatever the page's proportion of references.** If an element's own colour value (any colour axis, including a text run's colours) equals a palette entry's value — compared as colours, so `#ABC`, `#aabbcc` and `#aabbccff` are the same — the element is flagged `inconsistent` with a phrase naming the colour and the palette entry it should reference (e.g. `#1f2937 written by hand — it is the palette's 'ink'; reference it`). This is decidable and never intentional: the palette entry exists, and the literal will silently stop following it when the palette changes.
- The existing proportional rule (a literal that matches no palette entry, on a page that mostly references its palette, is `inconsistent`) is unchanged. A literal that matches no palette entry on a page that does not use its palette is still not flagged — nothing decidable says it is wrong.
- A site with no palette is still never nagged.
- The `describe_page` description names the new case alongside the existing one.

## Decisions on the rest of the report
- **Form inputs rated `worth_a_look`: no tier change.** The inputs in the report named a face, a size, padding and an ink colour; only `placeholderColor` was missing. The "nobody styled" case in the description (browser face, no padding) is already `broken` and stays so. A missing placeholder colour on an inked field is a real but minor gap — `worth_a_look` is correct.
- **Text styles written inline: out of scope here.** A text style is a bundle of type axes; a run carrying some of the same values is not decidably "the style written by hand" the way an equal hex is the palette entry, so no equality rule is added.

## Test plan
`tests/test_UAT_FC_BUG-183_palette_literals.test.ts`, driving `describe_page` through `l1Operations` over a memory site (same harness as the REQ-349 UATs):
- A page with a palette and zero references whose elements carry the palette's values as literals (different hex spellings) → each such element `inconsistent`, the phrase names the palette entry, `attention.inconsistent` counts them.
- A literal matching no palette entry on that same zero-reference page → not flagged.
- Regression scope: `tests/test_UAT_FC_REQ-349_style_audit.test.ts`.
