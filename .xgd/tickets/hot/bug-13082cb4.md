## Symptom

In the builder's copy editor (the modal opened by clicking a copy segment), the
`gigabytealchemy/home` title **"Gigabyte Alchemy" renders as nothing** — the box
is empty. Every other run on the page previews correctly.

Reproduce: `1c render gigabytealchemy --edit`, open the builder's Site tab in Edit
mode, click the hero wordmark. The modal opens, the segment resolves, Save works —
but the words are not visible while editing them.

## Root cause

The run is painted with a `gradientFill` (`storage/sites/gigabytealchemy/draft/pages/home.json`,
the `text` node at index `0.15`). `render.ts` compiles that the standard way — the
glyphs are painted by the element's OWN background, clipped to the text:

```
background-image: linear-gradient(90deg, #f5e6a3 0%, …, #ff6b35 100%);
-webkit-background-clip: text; background-clip: text;
-webkit-text-fill-color: transparent; color: transparent;
```

The modal's preview (`apps/control-app/src/builder/page-style.js`, REQ-121) reads
presentation off the live element and reproduces it in the dialog. Two reads
between them lose the glyph paint entirely:

- `readTypography` copies `getComputedStyle(el).color` into `--preview-color`,
  which `builder.css` feeds to `--fields-fg`. For this run that value is
  `rgba(0, 0, 0, 0)` — so the modal is faithfully reproducing a transparent
  foreground.
- `readBackground`/`paintedBehind` deliberately start ONE PAST the element
  (`stack.slice(self + 1)`), because the question it asks is "what is *behind*
  this copy". Correct for a backdrop; it means the element's own background —
  which here is not a backdrop at all but the glyph fill — never crosses.

So the preview reproduces both halves of the technique separately and the half
that makes it visible is dropped. Nothing is wrong with the render or the bridge.

This is the only `gradientFill` run in `storage/` today, which is why it has gone
unnoticed; the defect is general to the axis, not to this page.

## Fix

Teach the preview that a text run's glyph paint can live in its own background.
`readTypography` (or a sibling read alongside it) detects `background-clip: text`
on the element itself and, when present, carries the element's own
`background-image` plus the clip and fill-colour across as preview variables;
`builder.css` applies them with defaults so a run WITHOUT a glyph gradient is
completely unaffected (`var(--preview-text-clip, border-box)` etc. — an absent
value never produces a declaration, matching the module's existing discipline).

Backstop, so this class of defect can never again produce invisible copy: when
the resolved foreground paints nothing and no glyph fill was found, fall back to
the chrome's own foreground rather than writing a transparent `--preview-color`.

Size in the preview is already clamped to 14–32px (`clampPreviewSize`), and a
`linear-gradient` with proportional stops re-resolves against the smaller box, so
the preview shows the same sweep at dialog scale — the same trade already made
for every other background layer.

## Test plan

UAT `test_UAT_FC_BUG-34_*` against `readPageStyle` / `readTypography`, driving a
jsdom document that carries the render's real declarations:

- a run with `background-clip: text` + a gradient previews with the glyph fill
  reproduced and a non-transparent visible result
- a plain run is byte-for-byte unaffected (no new variables emitted)
- a run whose `color` computes transparent with no glyph fill falls back to a
  visible foreground rather than emitting a transparent one

Regression scope: `tests/req121-copy-modal-elegance.test.ts` plus the builder
suites.
