# values-diff: ten of 64 deltas on www.hearingzone510.com compare a stacking level, a no-op clip and a text node that the two sides do not have in common

## Item 1 — `zIndex` compares a raw level across different stacking structures · `instrument-asymmetric`
Six HIGH deltas `zIndex` on "(generic)" expected `z:13` actual `z:0` (3050.93 each). The six are
expected-manifest elements 19, 39, 44, 56, 73, 92 — Zyro's `.block-background{z-index:13;…}`
(mirrored `assets/_..Bf-H_B6P.css`), one per section, each the ground of its own section's stacking
context. The fold deliberately writes no level on a backdrop (`fold.ts` ~4053-4064: "A BACKDROP'S LAYER
IS THE FOLD'S DECISION, NOT THE CAPTURE'S … The level a backdrop paints at is already stated, by where
the fold puts it"). So the reproduction is right by its own contract and the comparator reports HIGH
because it compares absolute numbers rather than order among the elements that overlap. *Defended:* the
two sides express paint order by different procedures (z-index vs document order), so the delta is the
instrument's own. And it misses the one ordering defect that matters on this page (REQ-370 issue 1: the
hero photo above its 45% scrim), which it reports only as `z:2` vs `z:0` on the scrim.
**Proposed:** compare relative paint order of overlapping pairs (above/below), not raw `zIndex`.
**See:** `python3 -c "import json;print([d['expected'] for d in json.load(open('values-diff.json'))['deltas'] if d['property']=='zIndex'])"`
in the diff dir → **now** `['z:13'×6, 'z:2']`; **fixed:** only the scrim-vs-photo inversion remains.

## Item 2 — `clip-path: inset(0px)` reads as a mask · `instrument-blind`
Three MEDIUM deltas `mask` expected `present` actual `none` (2040 each) on expected elements 19, 39,
44, whose `maskEdge` is `inset(0px)` — a clip to the element's own box, which removes nothing. The

**Proposed:** normalise `inset(0…)` (all four zero, no round) to no mask on both sides.
**See:** `grep -c '"mask"' values-diff.json`-style count of `property=="mask"` → **now 3**, **fixed 0**.

## Item 3 — a bare text node beside a styled span is recorded with its parent's box · `instrument-asymmetric`
HIGH `renderedTextBox` on "F": expected `667×157`, actual `11×22`. raw.html:
`<p dir="auto" class="body-large">F<span style="color: rgb(0, 30, 66);">or over 20 years…</span></p>`.

## Fix

**Item 1 — paint order compared as the relative order of overlapping pairs, resolved through the stacking chain.**
Comparing the pairwise order on the raw `zIndex` integer would still be wrong on this page. On the reference, the section
ground `.block-background` (z 13) and the copy inside `.block-layout` (z 14 → `.layout-element` z 1) sit in sibling
stacking contexts. So "13 > 1" would read the ground as painting *over* the copy that is plainly visible on top of it.
- **Extractor (both sides, one procedure):** a new `paintStack` on every run and field. It is the chain, outermost
  first, of the boxes that carry the element through paint order: a box `z-index` applies to (positioned, or a
  flex/grid item) that declares an integer level, or any box that establishes a stacking context (level 0). Each
  entry is `{ id: <document path>, z: <level> }`. The element closes the chain at level 0 when it is not itself such
  a box. The existing `zIndex` field is unchanged; the fold still reads it.
- **Comparator:** the per-element `z:13 vs z:0` comparison is **replaced**. This supersedes BUG-179 item 4's
  "compared as a clamped rank" and REQ-48 item 2's per-element level compare. For every two paired elements whose
  boxes overlap on **both** sides (intersection ≥ 1% of the smaller box), each side answers "which paints above?"
  from its own data:
  1. Find the first chain entry where the two differ and compare levels there.
  2. On equal levels, compare document order: an ancestor comes before anything inside it.
  3. If one chain is a prefix of the other, the descendant paints above.
  4. If the chains are identical (two runs of one element), the pair has no order.

  A pair is reported only when both sides order it strictly and the orders disagree. The delta is filed as one
  `zIndex` delta on the element the reference paints above: expected `above "<partner>"`, actual
  `below "<partner>"`, with ` (+N more)` when there are several partners. Magnitude is the inversion count; the tier
  stays HIGH, kind `zOrder`. A level that differs on an element with no overlapping neighbour is no longer a delta.
  The arrangement pass and this pass accumulate into the same object card.
- **Flat fallback, declared:** a side without `paintStack` (a bundle older than schema 16) is ordered on one flat
  level, `zIndex` then manifest order. `unmeasuredAxes` then gets `{axis: 'paintStack', scope: 'element', side}`.
- **Calibration:** the `wrong z-order` seeded defect injects a real inversion (`z:-1`, the image dropped below the
  copy it overlaps) instead of `z:99`, which no longer reorders anything.
- **Schema:** `CAPTURE_SCHEMA` goes 15 → 16, and both new axes are named for stale bundles.

**Item 2 — a no-op clip is not a mask: delivered by REQ-371, not by this ticket.** REQ-371 (commit `79cd898a1f`,
`paintsMaskEdge` in `mask-geometry.ts`, with UATs in `test_UAT_FC_REQ-371_reveal_root_margin_pill_height`) landed
the same normalisation while this ticket was in flight. This ticket's own version was dropped at merge, so the rule
has one implementation. Nothing in BUG-187's commits touches the mask axis.

**Item 3 — a text node is measured by its own range when its element also holds other runs.** The extractor's
`ownRun` test was "this element holds exactly one run". For `<p>F<span>or over…</span></p>`, the `<p>` holds one
run ("F") and the span's run is nested inside it, so "F" took the paragraph's box and glyph extent. `ownRun` now also
requires that no other emitted run is nested under the element. "F" is then measured with `textNodeBox`, over its own
range (≈ 11×22), for both `renderedTextBox` and `box`, the same way the reproduction measures its own span. This is
one procedure on both sides (schema 16 axis, with no presence probe).
