## Item 1 — `zIndex` compares a raw level across different stacking structures · `instrument-asymmetric`
Six HIGH deltas `zIndex` on "(generic)" expected `z:13` actual `z:0` (3050.93 each). The six are
expected-manifest elements 19, 39, 44, 56, 73, 92 — Zyro's `.block-background{z-index:13;…}`
(mirrored `assets/_..Bf-H_B6P.css`), one per section, each the ground of its own section's stacking
context. The fold deliberately writes no level on a backdrop (`fold.ts` ~4053-4064: "A BACKDROP'S LAYER
IS THE FOLD'S DECISION, NOT THE CAPTURE'S … The level a backdrop paints at is already stated, by where
the fold puts it"). So the reproduction is right by its own contract and the comparator reports HIGH
because it compares absolute numbers rather than order among the elements that overlap. *Defended:* the
two sides express paint order by different procedures (z-index vs document order), so the delta is the
instrument's own. And it misses the one ordering defect that matters on this page (REQ-370 issue 1: the
hero photo above its 45% scrim), which it reports only as `z:2` vs `z:0` on the scrim.
**Proposed:** compare relative paint order of overlapping pairs (above/below), not raw `zIndex`.
**See:** `python3 -c "import json;print([d['expected'] for d in json.load(open('values-diff.json'))['deltas'] if d['property']=='zIndex'])"`
in the diff dir → **now** `['z:13'×6, 'z:2']`; **fixed:** only the scrim-vs-photo inversion remains.

## Item 2 — `clip-path: inset(0px)` reads as a mask · `instrument-blind`

**See:** `grep -c '"mask"' values-diff.json`-style count of `property=="mask"` → **now 3**, **fixed 0**.

## Fix (scope agreed for free-coding)

**Item 1 — paint order compared as relative order of overlapping pairs, resolved through the stacking-context chain.**
Comparing the pairwise order on the raw `zIndex` integer would still be wrong on this page. On the reference, the section
ground `.block-background` (z 13) and the text inside `.block-layout` (z 14 → `.layout-element` z 1) sit in sibling
stacking contexts. So "13 > 1" would read the ground as painting *over* the text that is plainly visible on top of it.
The capture therefore records how each element stacks:
- **Extractor (both sides, one procedure):** a new `paintStack` on every run and field. It is the chain, outermost
  first, of the boxes that carry the element through paint order: a box `z-index` applies to (positioned, or a
  flex/grid item) that declares an integer level, or that establishes a stacking context. Each entry is
  `{ id: <document path>, z: <level> }`. The leaf is appended at level 0 when it is not itself such a box. The
  existing `zIndex` field is unchanged.
- **Comparator:** the per-element `z:13 vs z:0` comparison is **replaced** (this supersedes BUG-179 item 4's
  "compared as a clamped rank" and REQ-48 item 2's per-element level compare). For every two paired elements whose
  boxes overlap on **both** sides, each side answers "which paints above?" from its own data:
  1. Find the first entry where the two chains differ and compare the levels there.
  2. On equal levels, compare document order (path).
  3. If one chain is a prefix of the other, the descendant paints above.

  A side that lacks `paintStack` (a bundle older than schema 16) falls back to one flat level: `zIndex`, then manifest
  order. That fallback is stated in `unmeasuredAxes`, not passed over silently. A pair is reported only when both
  sides give a strict order and the orders disagree. Each inverted pair is one `zIndex` delta, filed on the element
  that should be above (expected `above "<other>"`, actual `below "<other>"`). An element's inversions aggregate into
  one delta (`+N more`), with magnitude = the inversion count. A level that differs on an element with no overlapping
  neighbour is no longer a delta.
- **Calibration:** the `wrong z-order` seeded defect now injects a real inversion (the image dropped below the text
  it overlaps) instead of `z:99`, which no longer changes any order.
- **Schema:** `CAPTURE_SCHEMA` goes 15 → 16, with `paintStack` named as a stale-bundle axis.

**Item 2 — a no-op clip is not a mask.** `inset(0)` / `inset(0px …)` with all four offsets zero, and no round or a
zero round, clips an element to its own box and removes nothing. Both sides normalise it to no mask before the `mask`
comparison and before the layer-resolution `maskEdge` axis. This is comparator-only, so it takes effect on existing
bundles without re-capture.

**Item 3 — a text node is measured by its own range when its element also holds other runs.** The extractor's
`ownRun` test was "this element holds exactly one run". For `<p>F<span>or over…</span></p>`, the `<p>` holds one
run ("F") and the span's run is nested inside it, so "F" took the paragraph's box and glyph extent. `ownRun` now also
requires that no other emitted run is nested under the element. "F" is then measured over its own text node
(≈ 11×22), the same way the reproduction measures its own span. This applies on both sides because it is one
procedure (schema 16 axis, with no presence probe).
