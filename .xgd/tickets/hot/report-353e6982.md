## One deviation from a suggested edit, with evidence

Finding 1's suggestion offered an optional companion: "if AC-687's path list is
extended alongside, assert its reported path is `/root/axes/textTransform`". **I
tried that and reverted it**, because it silently guts AC-687's actual criterion.

Measured, by driving `validateL1` directly on the three docs:

- enum alone → 1 error, `/root/axes/textTransform`, "Invalid option: expected one of
  …" ✅
- AC-687's original 3-violation doc → **3** errors (`/widths/1`,
  `/root/children/0/axes/fontSizePx`, `/root/children/1/src`) ✅
- the same doc **plus** an enum-violating third child → **1** error, the enum one
  only. The other three vanish.

The reason: the range / ladder / URL-allowlist checks are post-parse refinements that
only run once the base schema parse succeeds. A schema-level (enum) violation
short-circuits them, so a mixed document collapses to a single error. Adding the enum
child to AC-687 therefore turned `errors.length >= 3` into `>= 1` — the criterion
"returns the **full list** of per-field errors" would have been left asserting the
opposite of itself. The enum path assertion lives in AC-686 instead (mutation 1),
where it costs nothing.

**Forwarded as an observation, not raised as a finding or fixed:** whether the
envelope *should* report schema-level and refinement-level violations in one pass is
a question about AC-687's intent, not something this level's findings asked for, and
I did not touch `packages/site-schema` to change it. If the assessor judges that
AC-687's "full list" is meant to span both classes, that is a `code-issue` for a
future cycle with this measurement as its evidence chain.
