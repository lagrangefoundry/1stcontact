Parent: [[EPIC-19]].

## What is wrong

Opening a site in the builder shows an empty chat pane, though the site was
built in a long conversation. The conversation is intact in the store; the
builder is looking for it under an address it no longer has.

## Why — and what is already correct

A session is keyed on the site's ADDRESS: `sessionIdFor(site)` returns
`site-${site}`, and `TicketSessionArchive` finds-or-creates the `chat` ticket
homing that session by `fields.session_id`. When the address changes the lookup
misses, and because "no ticket with this session_id" is indistinguishable from
"a site that has never been talked about", a fresh empty session is created
silently. No error, no trace in the UI.

**The key model is already right, and this ticket does not change it.**
[[REQ-190]] made `tools/generate/src/store/ids.ts` the one minter of opaque keys:
128 bits from a CSPRNG, `<prefix>_<32 hex>`, explicitly NOT a digest of the row's
data — that module states the reason, which is that `sha256(email)` is
data-as-key wearing a disguise and still changes when the address does. Every
`sites` row is `site_<32hex>`; every `tenants` row is `biz_<32hex>` bar one
legacy UAT fixture (`biz_uatwestheadme`, with its matching `acct_uatwestheadme`).

**The code is already right too.** The four `sessionIdFor` call sites all receive
a site id, and a session opened today is keyed
`site-site_<32hex>` — the opaque key. The consultant, the ledger and the
settings session (`business-biz_<32hex>`) all agree.

So this is not a design defect to fix. It is the RESIDUE of a migration that has
already happened: when site addressing moved from name-slugs to opaque ids, the
chat tickets keyed on the old addresses were not re-keyed, and they were left
behind.

## What has to happen

### 1. Verify the key model has no stragglers

Assert what is believed above rather than trusting it: every `sites.id` and every
`tenants.id` is opaque (`isOpaqueId`), no session id is derived from a name, and
the legacy `biz_uatwestheadme` fixture is either migrated or deliberately
exempted with the reason written down. A UAT pins it so a future name-keyed path
cannot land unnoticed.

### 2. Re-home the orphaned conversations

Three distinct cases, and they do not take the same repair.

**(a) The orphan has the content, the current session is empty.** Re-key the
orphan and retire the empty one. Re-keying rather than copying, because the
orphan ticket carries more than its transcript: its title, its AI-maintained
summary body ([[REQ-171]]), its `tool_transcript` comment and its `created_at`.
The repair is `fields.session_id` on the ticket, plus `id` and `backend` in the
`xgd-session` header inside the `chat_transcript` comment; `chat_ticket_uid` is
already correct because the ticket itself is not moving. The empty ticket must be
retired in the same step or it goes on winning the find-by-session_id lookup.

`backend_ref` in the header must be CLEARED as part of the repair. It names a
backend segment that no longer exists, and a stale one is what makes a restored
chat fail on its next turn rather than on its first read.

Affected (local dev):

| site | keep (has content) | orphan address | retire (empty) |
|---|---|---|---|
| Lagrange Foundry `site_936dd7c92e5e14df694dd9a80433aa4f` | `chat-d73a11e1` — 26,815 transcript / 224,813 tools / 3,404 summary | `site-unnamed` | `chat-50932534`, `chat-b98f4eec` |
| 1st Contact `site_62d3d0097bbc7b6e86bdcdb3728389a3` | `chat-5c9fd79b` — 106,129 / 589,882 / 3,666 | `site-1stcontact` | `chat-15df6ccb` |

**(b) Both the orphan and the current session have content.** XGD
(`site_bca807fc7cdd0bf418b15e255f8c45c6`) has a live session `chat-9d2dcca0`
(22,635 / 323,855 / 2,092) at the correct address AND an orphan `chat-d53aa031`
(10,041 / 153,901 / 933) at `site-xgd`. These cannot be merged mechanically —
the orphan is earlier history, not a duplicate. This case needs an operator
decision per site, not a rule. Do not re-key it silently, and do not delete it:
the default is to leave the orphan in place and make it REACHABLE (see 4).

**(c) Nothing to recover.** Gigabyte Alchemy
(`site_d669b155d61270d8210471d9771dd645`) has an orphan `chat-05efe82b` at
`site-gigabytealchemy` and a current `chat-39609382`, both empty. Felix Test has
only an empty `site-unnamed` session and no current-address session at all.
Retire the empties; there is no conversation to restore.

**A name-keyed address is not tenant-unique, and the data shows it.** Three
tenants each hold a `site-unnamed` session, and `site-xgd` exists in TWO — the
real one in the XGD tenant and an empty `chat-bff48a7f` in the 1st Contact
tenant. The store is `forTenant`-bound so these never actually collided, but the
stray row is what a mutable, human-meaningful key produces and is worth recording
as evidence rather than quietly deleting.

### 3. Fix production

Everything above is the LOCAL dev store. Production has not been surveyed and
cannot be from a sandbox. The repair ships as something the operator can run
against prod: survey first — every chat ticket whose `session_id` does not match
an existing site or business key, with its transcript size and its tenant — then
apply, per site, with the (a)/(b)/(c) classification made explicit in the output
rather than inferred. A dry-run that prints the plan and changes nothing is the
default; applying is a second, explicit invocation.

### 4. Make the failure legible instead of silent

The repair is one-off; the silence is not. A session ticket whose `session_id`
names no live site is currently invisible — it is not an error, it is nothing at
all. At minimum an orphan should be discoverable: the operator should be able to
ask a site which conversations have ever been homed on it, including ones keyed
on an address it no longer answers to. That is also what makes case (b) tractable
without a data decision.

## Out of scope

Changing how session ids are derived. The address is already an immutable
opaque key, and re-deriving it from something else would be a second migration
with the same failure mode. If a stronger guarantee is wanted later — the site
row carrying its chat ticket uid, so the lookup never goes through a derived
string at all — that is its own ticket, and `TicketSessionArchive` already
supports addressing a session by ticket (`_chatUids`).
