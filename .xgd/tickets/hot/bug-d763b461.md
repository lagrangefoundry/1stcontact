# The beta form's action is root-relative, so it never reaches the preview's lead endpoint

## Symptom

On the 1st Contact homepage, submitting "Apply to join the early beta" shows the
inline error **"Something went wrong (404). Please try again."**

That message is `contact-form/client.js`'s non-2xx branch with
`response.status === 404` — so unlike [[BUG-78]], the `fetch` now *completes*. A
server answered. It answered 404.

## Where this was observed

**The builder's draft preview, not production.** Verified 2026-09-11:

- `GET https://1stcontact.io/` → `404` — nothing is published there; the
  production `sites` table is still empty, exactly as [[BUG-78]] recorded.
- `POST https://1stcontact.io/api/lead` → `405` — `leadTarget` returns null
  because production has no `APEX_SITE_KEY`, so the request meets the ordinary
  method refusal.

Neither of those is a 404, and `handleLead` cannot produce one — its whole
answer set is 200/400/403/413/415/503. So the 404 did not come from
`public-site`. It came from `control-app`.

## Diagnosis

The form's configured action is root-relative:

    site_62d3d0097bbc7b6e86bdcdb3728389a3 / home.json
    modules[beta-form].config.action = "/api/lead"

`component.ts` emits that value verbatim (`assertSafeUrl(action)` — no
rewriting), and a **root-relative** action resolves against the serving *origin*,
discarding the document's directory entirely.

In the preview the document is served at
`/b/<businessId>/preview/1stcontact/draft/`, so the submit goes to
`https://app.1stcontact.io/api/lead`. `control-app` has no such route — the
preview lead endpoint [[BUG-78]] added is at
`/preview/<slug>/draft/api/lead` (`router.ts:3178`) — so the request falls
through the whole route table to `env.ASSETS.fetch(request)` (`router.ts:3218`),
which answers 404 for a path that names no build artifact.

**[[BUG-78]] set this value, and its own decision text says what it should have
been.** That ticket promised "one `action` value is correct in both places
without the renderer knowing which channel it is in" — and the route it built
delivers exactly that, but only for a **document-relative** action. The value
written was the root-relative one. Its "Two findings" section already names the
correct form: *"the correct value for a non-apex site is `/site/<key>/api/lead`,
or a document-relative `api/lead`, which resolves correctly for both."*

## Why `api/lead` (no leading slash) is right everywhere

A document-relative action resolves against the request URL's directory, which
is precisely the channel root in every surface that serves a form:

| Surface | Document URL | `api/lead` resolves to | Correct? |
| --- | --- | --- | --- |
| builder preview | `/b/<biz>/preview/<slug>/draft/` | `/b/<biz>/preview/<slug>/draft/api/lead` | yes — the route `router.ts:3178` answers |
| published apex | `/` or `/whitepapers` | `/api/lead` | yes — `leadTarget` resolves the apex |
| published non-apex | `/site/<key>/` or `/site/<key>/whitepapers` | `/site/<key>/api/lead` | yes — and the site key is the *right* one |

The last row is not incidental. `routes.ts` deliberately refuses to make a
trailing-slash path eligible for the HTML fallback (`htmlFallbackFor`) so that a
page's directory is always the channel root — the same property that makes
document-relative `theme.css` references land (REQ-109). The form's action gets
that for free by being relative, and gets it wrong by being absolute.

## This is not only our homepage

Every real form in the store carries the same root-relative value:

| Site | Page | `action` | Consequence |
| --- | --- | --- | --- |
| `1stcontact` (apex) | `home` | `/api/lead` | 404 in the preview; would work once published |
| `xgd` (non-apex) | `home` | `/api/lead` | 404 in the preview; **and once published, its leads land in the apex tenant's contact list** |
| `xgd` (non-apex) | `whitepapers` | `/api/lead` | same |

The second column of consequences is [[BUG-78]]'s finding 2 — the cross-tenant
lead leak — and it has the same root cause as this 404. `leadTarget` reads the
site key out of the path, so a root-relative `/api/lead` from a site served under
`/site/<key>/` names the *apex*, not that site. Fixing the action to `api/lead`
closes both.

## Fix — options, for the operator to choose

**A. Data only.** Rewrite the three `action` values from `/api/lead` to
`api/lead`, the way [[BUG-78]] applied its edit (page row rewritten,
`sites.version` bumped). No repo code changes, no reconciliation. Closes this 404
and the cross-tenant leak. Does nothing to stop the next form being configured
the same way.

**B. Data plus a guard.** A above, plus something in the repo that makes the
wrong value impossible to ship silently — the candidates being a `contact-form`
config validation that refuses a root-relative path beginning `/api/lead`, or a
UAT that renders each shipped site and asserts the emitted action resolves to a
route that exists.

**C. Make the endpoint not a dial at all.** `action` is `{ type: 'url',
required: true }` free text, and the product's own lead endpoint is not a URL an
operator should be typing. A sentinel (`action: "lead"`) or a separate
`destination` discriminator would let the renderer emit the right relative target
itself, while keeping free-text `action` for the case [[DOC-47]] describes — a
client whose enquiries must go to a mailbox they already have. Schema change;
larger than a bug fix.
