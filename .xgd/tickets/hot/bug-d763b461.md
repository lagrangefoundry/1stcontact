# The beta form's action is root-relative, so it never reaches the preview's lead endpoint

## Symptom

On the 1st Contact homepage, submitting "Apply to join the early beta" shows the
inline error **"Something went wrong (404). Please try again."**

That message is `contact-form/client.js`'s non-2xx branch with
`response.status === 404` — so unlike [[BUG-78]], the `fetch` now *completes*. A
server answered. It answered 404.

## Where this was observed

**The builder's draft preview, not production.** Verified 2026-09-11:

- `GET https://1stcontact.io/` → `404` — nothing is published there; the
  production `sites` table is still empty, exactly as [[BUG-78]] recorded.
- `POST https://1stcontact.io/api/lead` → `405` — `leadTarget` returns null
  because production has no `APEX_SITE_KEY`, so the request meets the ordinary
  method refusal.

Neither of those is a 404, and `handleLead` cannot produce one — its whole
answer set is 200/400/403/413/415/503. So the 404 did not come from
`public-site`. It came from `control-app`.

## Diagnosis

The form's configured action is root-relative:

    site_62d3d0097bbc7b6e86bdcdb3728389a3 / home.json
    modules[beta-form].config.action = "/api/lead"

`component.ts` emits that value verbatim (`assertSafeUrl(action)` — no
rewriting), and a **root-relative** action resolves against the serving *origin*,
discarding the document's directory entirely.

In the preview the document is served at
`/b/<businessId>/preview/1stcontact/draft/`, so the submit goes to
`https://app.1stcontact.io/api/lead`. `control-app` has no such route — the
preview lead endpoint [[BUG-78]] added is at
`/preview/<slug>/draft/api/lead` (`router.ts:3178`) — so the request falls
through the whole route table to `env.ASSETS.fetch(request)` (`router.ts:3218`),
which answers 404 for a path that names no build artifact.

**[[BUG-78]] set this value, and its own decision text says what it should have
been.** That ticket promised "one `action` value is correct in both places
without the renderer knowing which channel it is in" — and the route it built
delivers exactly that, but only for a **document-relative** action. The value
written was the root-relative one. Its "Two findings" section already names the
correct form: *"the correct value for a non-apex site is `/site/<key>/api/lead`,
or a document-relative `api/lead`, which resolves correctly for both."*

## Why `api/lead` (no leading slash) is right everywhere

A document-relative action resolves against the request URL's directory, which
is precisely the channel root in every surface that serves a form:

| Surface | Document URL | `api/lead` resolves to | Correct? |
| --- | --- | --- | --- |
| builder preview | `/b/<biz>/preview/<slug>/draft/` | `/b/<biz>/preview/<slug>/draft/api/lead` | yes — the route `router.ts:3178` answers |
| published apex | `/` or `/whitepapers` | `/api/lead` | yes — `leadTarget` resolves the apex |
| published non-apex | `/site/<key>/` or `/site/<key>/whitepapers` | `/site/<key>/api/lead` | yes — and the site key is the *right* one |

The last row is not incidental. `routes.ts` deliberately refuses to make a
trailing-slash path eligible for the HTML fallback (`htmlFallbackFor`) so that a
page's directory is always the channel root — the same property that makes
document-relative `theme.css` references land (REQ-109). The form's action gets
that for free by being relative, and gets it wrong by being absolute.

## This is not only our homepage

Every real form in the store carries the same root-relative value:

| Site | Page | `action` | Consequence |
| --- | --- | --- | --- |
| `1stcontact` (apex) | `home` | `/api/lead` | 404 in the preview; would work once published |
| `xgd` (non-apex) | `home` | `/api/lead` | 404 in the preview; **and once published, its leads land in the apex tenant's contact list** |
| `xgd` (non-apex) | `whitepapers` | `/api/lead` | same |

The second column of consequences is [[BUG-78]]'s finding 2 — the cross-tenant
lead leak — and it has the same root cause as this 404. `leadTarget` reads the
site key out of the path, so a root-relative `/api/lead` from a site served under
`/site/<key>/` names the *apex*, not that site. Fixing the action to `api/lead`
closes both.

## Fix — options, for the operator to choose

**A. Data only.** Rewrite the three `action` values from `/api/lead` to
`api/lead`, the way [[BUG-78]] applied its edit (page row rewritten,
`sites.version` bumped). No repo code changes, no reconciliation. Closes this 404
and the cross-tenant leak. Does nothing to stop the next form being configured
the same way.

**B. Data plus a guard.** A above, plus something in the repo that makes the
wrong value impossible to ship silently — the candidates being a `contact-form`
config validation that refuses a root-relative path beginning `/api/lead`, or a
UAT that renders each shipped site and asserts the emitted action resolves to a
route that exists.

**C. Make the endpoint not a dial at all.** `action` is `{ type: 'url',
required: true }` free text, and the product's own lead endpoint is not a URL an
operator should be typing. A sentinel (`action: "lead"`) or a separate
`destination` discriminator would let the renderer emit the right relative target
itself, while keeping free-text `action` for the case [[DOC-47]] describes — a
client whose enquiries must go to a mailbox they already have. Schema change;
larger than a bug fix.

## Re-diagnosed 2026-09-11 — this is three defects, and only one of them is data

The operator's objection to the framing above is correct and the "Fix — options"
section is superseded. "Get the value right in the store" is not a fix, because
nothing in the product can author that value correctly and one part of the
product actively instructs the author to get it wrong.

### Defect 1 — the renderer skips relativisation for exactly one URL sink

`l1/render.ts` has `relativizeUrl` (line 157), which turns a root-relative
`/x` into a document-relative `./x`. It exists for [[REQ-109]] — a published
snapshot must be relocatable under any prefix — and it carries [[BUG-30]]'s two
RFC-3986 edge cases (empty first segment, colon in first segment) that make the
transformation safe rather than merely shorter.

**Every URL the renderer emits goes through it except the form's action.**

| Sink | Line | Relativised? |
| --- | --- | --- |
| link `href` | `render.ts:2624` | yes |
| image `src` | `render.ts:2852` | yes |
| CSS `url()` | `render.ts:201` | yes |
| image `srcset` | `render.ts:1716` | yes |
| **`contact-form` action** | `contact-form/component.ts:110` | **no** — `assertSafeUrl(action)` and nothing else |

So the action is the one reference in a rendered page that does not survive
being served under a channel prefix. That is the whole of the 404: the preview
serves the document at `/b/<biz>/preview/<slug>/draft/`, every asset on the page
resolves correctly because it was relativised, and the form alone posts to the
origin root.

This is a **code** defect in the renderer, not a data defect. Fixing it makes
`/api/lead` correct in all three channels, and closes [[BUG-78]]'s finding 2 —
the non-apex cross-tenant lead leak — by the same mechanism, because
`./api/lead` under `/site/<key>/` names that site rather than the apex.

### Defect 2 — the endpoint is a required free-text URL with no default

`meta.ts:32` — `action: { type: 'url', required: true }`. The generated
reference the builder AI reads (`kb/system/REF-behaviors.md:27`) renders that as,
in its entirety:

    - `action` — url; required

There is no default, no mention that the product has a lead endpoint, no mention
that the value must be relative, and nothing that could tell an author the
correct answer. The submit target of the product's own lead-capture form is a
fact about serving topology, and it is being asked of whoever is authoring the
page's content.

### Defect 3 — the shipped knowledge base tells the author to point the form away

This is the one that explains the data. [[DOC-47]] (`doc-708a06c6`, still
carrying the line at its own line 117, so this is the source and not a stale
build) is current system knowledge the production AI reads:

> *"A contact form on a published site posts to an address you configure. The
> published site is read-only — it serves pages and does not receive anything —
> so there is no 1st Contact inbox behind the form yet... you must settle where
> it goes with the client... that's an address you already have."*

[[REQ-223]] built that inbox. `public-site` receives `POST /api/lead`, writes a
contact into the site's own tenant, and delivers the promised asset. DOC-47 was
never updated, so the instruction to route enquiries to a third party is still
live.

**The store reads exactly as that instruction predicts:**

| Value in the store | Where it came from |
| --- | --- |
| `https://app.1stcontact.io/beta-apply` | AI-authored; route never existed ([[BUG-78]]) |
| `https://api.gigabytefoundry.ai/contact` | AI-authored; an external address, as DOC-47 directs |
| `https://example.com/enquiry` | AI-authored placeholder |
| `/api/lead` | only ever typed by a human — [[BUG-78]]'s manual edit, and the `xgd` seed |

A form pointed at a third-party URL also silently loses everything REQ-223
built: no contact record, no asset delivery, no server-side honeypot check, and
no Turnstile verification (the secret is ours). It looks like the product's lead
capture and is not.

### What the fix has to be

Defect 1 is a genuine bug and is fixed on its own terms: send the action through
`relativizeUrl` like every other sink. That alone stops the 404 and the
cross-tenant leak.

Defects 2 and 3 are the model the operator is objecting to, and the answer is
that **the lead endpoint needs no parameter at all.** Document-relative
`api/lead` is correct for every site in every channel without anything being
configured per-site, because page slugs are a single flat segment, so a
document's directory is always its channel root — the same invariant
`routes.ts` already protects with `htmlFallbackFor`'s trailing-slash refusal, and
the same one REQ-109 relies on for `theme.css`.

So `action` should stop being a required free-text URL that authorship has to
supply, and DOC-47 should stop describing an inbox that now exists as missing.

## Decided 2026-09-11 — the module provisions its own endpoint, and `action` is deleted

The operator settled both open questions:

> *"The module should be self-contained, it should be automatically provisioned
> by the system with the correct URLs etc. The AI has freedom to style and
> arrange it with any look but it should not need to set up its functionality."*

> *"This is an email capture module, it is to capture emails into your site, this
> is not a general web form module."*

**The third-party escape hatch is not kept.** It was raised on [[DOC-47]]'s
authority, but DOC-47 describes posting to "an address you already have" as a
workaround for an inbox that did not exist. [[REQ-223]] built the inbox, so the
capability is vestigial — and a lead-capture module that can be pointed at
another server is a form that looks like this product's capture and silently
isn't: no contact record, no asset delivery, no server-side honeypot, no
Turnstile.

### What changes

**1. `action` is removed from `contact-form`'s config contract.** It stops being
a setting an author supplies, so `REF-behaviors.md` stops offering it and the
builder AI cannot set it, correctly or incorrectly. Styling and arrangement are
untouched: the `form` slot, every `control` node and the L1 subtree are exactly
as they were. Only the functionality stops being authorable.

**2. The component emits the endpoint itself, document-relative.** The value is
`./api/lead` — `./` rather than a bare segment for [[BUG-30]]'s reason, which
`relativizeUrl` already records: an explicit path segment cannot be re-read as a
scheme and resolves against the document's DIRECTORY rather than the document.

That one constant is correct on every surface, with nothing configured per site,
because a page slug is a single flat segment so a document's directory is always
its channel root:

| Surface | Document URL | resolves to |
| --- | --- | --- |
| builder preview | `/b/<biz>/preview/<slug>/draft/…` | `/b/<biz>/preview/<slug>/draft/api/lead` |
| published apex | `/` or `/whitepapers` | `/api/lead` |
| published non-apex | `/site/<key>/` or `/site/<key>/whitepapers` | `/site/<key>/api/lead` |

Row 1 is the 404 this ticket was raised for. Row 3 is [[BUG-78]]'s finding 2 —
the cross-tenant lead leak — closed by the same constant, because the site key
in the path is now the site the visitor is actually on.

**3. The endpoint path is defined once, in the framework module.** `LEAD_PATH`
lives in `apps/public-site/src/lead.ts` today while the module that must agree
with it lives in `packages/framework`. The constant moves down to the module and
`public-site` imports it, in the direction that already exists — `lead.ts`
already imports `fields.ts` from this module. Two definitions of the endpoint
would be a server and a form that agree until they do not.

**4. The edit channel is unchanged.** [[REQ-116]] renders no `action` and no
`method` and ships no client script, and that survives: the endpoint is emitted
only on the functional channels.

**5. Removing a config key is a breaking contract change, so the version is
bumped and a migration is declared.** This is a technical consequence of 1
rather than something requested, and [[BUG-85]] settles how it is done: the
catalog holds one meta per id, so an instance pinned to a version the catalog no
longer carries fails to resolve and takes the whole page down — which is what
the `account-chrome` 1 → 2 bump did to 1st Contact's own site. So:

- `contact-form` goes to **v5**, and `migrations: { 5: … }` is declared beside
  the bump, dropping `action` from a v4 instance's config.
- `migrationsFrom` stays 4 — the claim that nothing is stored below v4 is
  unaffected.
- Stored instances are carried forward with `1c module upgrade --write`, the
  command [[BUG-85]] built for exactly this, rather than by hand-edited SQL.
  A migration performed by editing repo files can only ever reach the fixtures.

**6. [[DOC-47]] is corrected.** It currently tells the builder AI that "the
published site is read-only… there is no 1st Contact inbox behind the form yet"
and to settle enquiries on an address the client already has. That instruction
is why the store holds `https://api.gigabytefoundry.ai/contact` and
`https://app.1stcontact.io/beta-apply`. It is replaced with what is now true: a
form on a published site captures into that site's own contact list, and the
author configures no destination because there is none to configure.

### Test plan

UATs under `test_UAT_FC_BUG-86_*`:

1. The rendered form's `action` is the module's own endpoint, on a page whose
   instance config supplies none.
2. `action` is no longer a declared config key — an instance supplying one is
   refused by the behavior validator, naming the key.
3. The emitted action is document-relative: it begins `./` and carries no
   leading `/`, so it cannot resolve against the origin root.
4. Resolved against a real document URL for each of the three surfaces in the
   table above, it yields that surface's real endpoint — including
   `/site/<key>/api/lead` for a non-apex site, which is the leak proof.
5. The edit channel still emits neither `action` nor `method`.
6. The v4 → v5 migration drops `action`, and its result validates against the v5
   contract.
7. The framework's endpoint constant and the path `public-site` routes on are
   the same value, so the form and the server cannot disagree.
