## Symptom

Dina's Diner 4 on dev, 2026-10-26 UTC. The operator replied "yes I love it" at 00:57. The consultant
started the home-page fixes ("about 10 minutes") and sent "still working" every minute until 01:05:31.
The last junction heartbeat was at 01:05:47; the turn never recorded an end. The builder kept showing
no working indicator and no notice. Later the panel said: "Replies in this conversation keep stopping
before they finish, and the conversation could not be re-read. Reload the builder to see where the
turn got to."

## Cause

1. **The dev server restarts often, and every restart kills in-flight turns.** `storage/tmp/dev/dev.log`
   shows 7 restarts between 23:50 and 01:45 (about 00:08, 00:28, 00:58, 01:02, 01:05, 01:24, 01:45), and
   276 across the log. Nearly all look like:
   `⎔ Starting remote preview… ⎔ Detected changes, restarted server. Preview token expired, fetching a new one`.
   The control app's Workers AI binding (`env.AI`, the knowledge-base embedder) always runs
   remotely. When wrangler's preview token for it expires, wrangler fetches a new one and reloads
   the local server (192 token-expiry lines in the log).
2. **A config edit restarts it too.** `bin/dev` serves a frozen snapshot (`.dev-snapshot/`), but
   wrangler still watches the checkout's `apps/control-app/wrangler.toml`. BUG-288's merge edited it at
   01:05:45, the same second the turn died.
3. **The panel doesn't tell the client the turn died.** After each restart the panel reattached
   (`/api/ai/reattach` 200), but the conversation store still showed a turn under way: the junction
   had no turn end and the ledger row was open, and the dev snapshot predates BUG-288's silence rule.
   So the panel rejoined a stream that would never finish. It chased it `RECOVERY_CHASES` (3) times
   (`apps/control-app/src/builder/chat.js`), then gave up with "reload the builder", which won't
   help: the turn is gone.

## Fix

1. **A credential refresh doesn't restart the dev server.** The remote AI binding's preview token
   refresh must not reload the local server under live requests. Options: declare the binding
   `remote: true` explicitly as wrangler's warning suggests (if that stops the reload), call Workers
   AI over its REST API in dev, or leave the binding out of dev unless the knowledge base is being
   tested. Acceptance: an hour-long turn survives in dev.
2. **A checkout edit doesn't restart it either.** `bin/deploy --env dev` snapshots the config
   (`wrangler.toml` and the vars it reads) along with the code, and `bin/dev` points wrangler at the
   snapshot's copy. Editing or merging the checkout's config changes nothing until the next deploy,
   the same as code.
3. **A dead turn is reported as dead.** When the panel reattaches or chases a stopped reply, the
   origin judges the conversation's last turn by BUG-288's silence rule, not by whether the junction
   recorded an end. A turn silent past the window is reported as stopped, and its ledger row and
   junction are closed so it's not "live" any more. The panel then says, in the conversation, that
   the work stopped before it finished, what the consultant was doing (its last progress line), and
   offers to carry on. It doesn't chase again or tell the client to reload.

## What changed (implementation)

**Fix 1: the token refresh was not what restarted the server.** In wrangler 4.111 the "Preview token
expired, fetching a new one / Detected changes, restarted server" lines come from the remote-binding
*proxy session* re-uploading itself. The local runtime's `onPreviewTokenExpired` is a no-op; only a
config or bundle change reloads the local server ("⎔ Reloading local server…"). The dev log agrees: 193
token-expiry lines but only 9 local reloads. The 00:57 turn survived the 00:58 and 01:02 refreshes and
died at the 01:05:44 reload that BUG-288's `wrangler.toml` edit triggered. So Fix 2 is the actual cure.
The AI binding is now declared `remote = true` in `[ai]`, `[env.production.ai]` and `[env.dev.ai]`. That
is what it already was, it silences wrangler's warning, and the config comment records where those log
lines come from. `wrangler deploy` ignores it.

**Fix 2: the config is frozen with the code.** `bin/deploy --env dev`'s local ship step copies
`wrangler.toml` into `.dev-snapshot/` and records `"config": "wrangler.toml"` in `snapshot.json`.
`devServeArgs` passes `--config .dev-snapshot/wrangler.toml`. Wrangler watches that copy, which only the
next deploy rewrites, so editing or merging the checkout's config changes nothing that is served. The
entry, `--assets` and `--persist-to` stay cwd-relative (wrangler reads them that way). The `--env-file`
layering is now passed as absolute paths, because wrangler resolves a relative env file against the
config's directory, which is now the snapshot. A snapshot manifest without `config` (deployed before this
change) reads as no snapshot, so `bin/dev` asks for one `bin/deploy --env dev` instead of serving it
against the checkout's config.

**Fix 3: a dead turn is reported as dead.** The sign of life is the producer's junction claim. It beats
every 5 s while the turn lives, and the framework's `resolveClaim` (30 s lease) is its one liveness test.
A turn that is open on the junction (`turn_start`, no `turn_end`) with no live claim has nobody driving
it. host-core's `closeLostTurn` re-reads the junction from the Durable Object first, so a stale mirror
can't kill a live turn. It then closes such a turn the way the stall deadline does (`turn_end` aborted,
`lost: true`) and returns the consultant's last model-sourced progress line.
- `/api/ai/session` (site and settings conversations) runs it before the fold. So `live` is false, the
  ledger row is closed `lost` (`restarted` if its silence began at a deploy, BUG-288's rule) via
  `closeLostSessionTurn`, and `failed` carries `stopped: true` and `progress`. Without
  `TURN_DIAGNOSTICS` there is still no turn id or cause.
- `/api/ai/reattach`: the tail runs the same check every 10 s (`LOST_CHECK_MS`). When the followed turn
  is found dead, it closes it, closes the ledger row, and ends with one `done` frame,
  `meta: {status: 'lost', progress}`. Before, it waited out `watch`'s 10-minute backstop.
- A turn whose claim beat recently is left alone however long it has run: open, not closed, the panel
  rejoins.
- Panel (`chat.js`): `failed.stopped` from a reopen, or a rejoined stream ending `lost`, paints "The work
  stopped before it finished. Where it had got to: "<progress line>". Press Carry on to pick it up from
  there." This comes with a **Carry on** button that sends "Please carry on from where you stopped." as
  the client's message. There is no further chase and no "reload" text. (If the client's own words
  reached no transcript, the existing BUG-121 path that puts them back in the box still runs instead.)

## Design decisions

- Junction claim rather than the ledger's `alive_at` as the death signal: `alive_at` is stamped once a
  minute against a 5-minute window, so it can't tell the chase within seconds. The claim can, and it is
  already the rule the framework uses to let another producer take a dead session. The ledger is then
  made to agree.
- The rejoined stream ends with a terminal `lost` frame instead of stopping without one, so the panel
  never re-enters the chase loop. That loop is what produced "Replies in this conversation keep
  stopping… Reload the builder".
- Carry on is a client message, not a new host cue, so it reuses the ordinary prompt path.
- An old snapshot without `config` is refused rather than served against the checkout's config. Supporting
  both would be two code paths, and the old one is this bug.
