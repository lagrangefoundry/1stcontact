Parent: [[EPIC-12]] §8. **Follows [[REQ-256]]**, which put the AI into the
console's loop. This ticket is what the FIRST LIVE ROUND taught us — it ran on
`gigabytealchemy.ai` on 2026-09-16 and its evidence is at
`storage/tmp/repro-console/repro-gigabytealchemy-ai/iteration-1/ai/`.

## What the first round showed

The round worked. It read the evidence, named a real defect in the engine's own
gate, proved it from the captured files rather than from the screenshot, traced
the consequence through `reconcileGates`, and handed back a complete gap ticket
with a 6,346-character body.

**The console then threw it away** and reported `the round produced no outcome
block.` Everything in this ticket follows from reading that transcript.

## Goal

Make a loop-1 round cheap enough to run many times and capable of keeping what
it finds. Three things are in the way: the console cannot read a good round's
answer, every round starts from zero knowledge, and a round can only report the
one thing that fits the one shape it is allowed to return.

## Behavior

### 1. The outcome block survives a ticket body that contains fenced code

`parseOutcome` (`tools/repro-console/src/ai.ts`) extracts the round's answer
with a lazy fenced-block regex:

```
finalText.matchAll(/```(?:json)?\s*\n([\s\S]*?)```/g)
```

A gap ticket that carries its evidence quotes `gate.json` and `capture.json` in
fenced code blocks, exactly as [[REQ-256]]'s own brief §6.3 demands. Those
fences are literal characters inside the JSON `body` string, so the lazy match
stops at the first one and the outcome block is truncated — in the observed
round, at 1,130 of 7,500 characters. It then fails to parse and the round is
reported as having produced no answer.

**The better the ticket, the more certainly this fires.** It is not an edge
case; it is the common case for any round that honours the brief.

The parse must not depend on fence discipline. A string-aware balanced-brace
scan for the last JSON object carrying a `status` recovers the observed round's
answer whole, ticket body intact, and was verified against the real transcript
before this ticket was written.

### 2. A round may file what it finds, not only the one gap it was sent for

[[REQ-256]]'s round returns exactly one outcome: one gap class against the
reproduction engine. The first round found more than that and said so —
"Regions 1-5 and 9 ... are candidate classes for a later round; I am filing the
one that is provable end-to-end." Those candidates were discarded with the
prose that described them.

It also found something that is not a reproduction-engine gap at all but a
defect in `1c` proper — the gate mis-routing its own verdict — and had no shape
in which to report it except by folding it into the gap ticket.

A round must be able to hand back **defects it found in `1c` along the way**,
separately from its gap diagnosis, and the console must file them the same way
it files the gap ticket: it runs `xgd`, the round does not, and they land at
`status: draft` and never at any `ready_*` status. Behaviour 3 of [[REQ-256]] —
the round writes no code and runs no command — is unchanged and remains
structural.

Open: whether a round may hand back more than one gap class per round, or
whether one-per-round is a deliberate throttle worth keeping. The first round's
deferred candidates are the evidence either way.

### 3. Rounds are primed, and carry what they learned forward

**Priming.** The standing brief (`tools/repro-console/brief/DIAGNOSE-THE-GAP.md`)
teaches method — transcribe don't reconstruct, the reading order, the verdicts,
how to name a residual class. It teaches no vocabulary and gives no map. It
references [[DOC-19]] and [[DOC-17]] only.

The first round found its way by grepping, competently, and spent tool calls
rediscovering that `backgroundImageUrl` is deliberately distinct from `src` —
which is stated plainly in the engine's own comments and will be rediscovered
by every future round that has the same question. Twenty tool calls, ten of
them `Read`, on a round whose answer turned on one documented distinction.

A round must be primed with:

- **The L1 documentation that already exists** — [[DOC-23]] (the typed element
  tree), [[DOC-27]] (L1 reproduction vocabulary), [[DOC-30]] (the control
  surface API). None of these are referenced by the brief today.
- **Documentation of the reproduction engine itself, which does not yet
  exist** — what each part of `tools/generate/src/` owns, where the boundary
  between capture, fold, probe and gate falls, and which field carries what.
  There is no doc ticket covering this; the closest are [[DOC-7]] and
  [[DOC-9]], and neither describes the pipeline.
- **Guidelines for spotting an engine gap** — the diagnostic patterns that have
  actually produced good tickets, as distinct from the brief's reading order.
  The first round's reasoning is the first worked example.

The engine documentation is a writing job, not a coding job, and may deserve
its own `doc` ticket rather than riding inside this one.

**Resume.** Every round today is a fresh `claude -p` with no `--resume` and no
`--session-id`. Each one re-reads the brief and re-derives its bearings, and a
second iteration on the same site knows nothing of what the first diagnosed.

Rounds must be able to carry context forward across iterations of the same
reproduction. The design question this has to answer: resume is valuable
because the round already knows the site, and dangerous because it anchors the
round on last round's hypothesis when the evidence underneath it has changed,
and because context grows without bound across a long iteration chain. State
the scope the implementation chose — per site, per iteration chain, reset on
what — and why.

### 4. The transcript shows the round once

`formatStreamEvent` prints the `result` event's text, and the same text has
already been printed as the assistant's final message. Every round's diagnosis
therefore appears **twice** in `transcript.txt` and twice in the pane the
operator reads — 22KB for the observed round, half of it a duplicate. The
`system` event line also printed four times, and printed no model, because the
field it reads was not populated.

### 5. A round's answer is recoverable without re-running the round

The observed round's work was not lost — it is in `transcript.txt` — but the
only way to get a ticket out of it was to re-run the round and pay for it
again. A round that produced a final message the console could not parse must
be recoverable from the artifacts already on disk.

The failure text must also point at those artifacts. `the round produced no
outcome block.` gives the operator nothing to act on and does not mention that
the round's entire diagnosis is sitting next to the message.

### 6. Every round records its model and what it cost

Nothing in `tools/repro-console/src/` records cost, tokens or the model used —
verified by search. `REPRO_CONSOLE_AI_MODEL` is optional, so with it unset a
round runs on whatever the CLI happens to default to, and the console does not
record which that was.

This loop is meant to run many times and its per-round cost is the thing that
decides how many. The `result` stream event carries usage and cost and the
console currently discards both. Record the model and the round's cost beside
the outcome, so "is this affordable to run often" is answerable from the
artifacts rather than from impression.

### 7. Evidence is pre-digested where that is cheaper than reading it

A round has no `Bash`, deliberately, so it cannot query a 4,000-line
`multistate.json` — it reads and greps. That is the correct trade for
[[REQ-256]]'s behaviour 3 and this ticket does not reopen it.

The cheaper half of the same problem is the console's: where a round
predictably needs a derived fact, the console can compute it while it is
already writing the evidence directory, and the round reads one line instead of
a file. Any such digest is an addition to the evidence on disk, never a
replacement for it — the brief's one rule is that claims come from the captured
files, and a round must still be able to reach them.

### 8. The tool policy is asserted, not enumerated from memory

`AI_DISALLOWED_TOOLS` names every tool that can act, and its own comment
records that the list "can go stale as the CLI grows tools." A round gaining
resume and a wider filing surface makes that staleness matter more. The
session's reported tool list arrives in the transcript's first event; check it
against what the policy intended rather than trusting the enumeration.

## Requirements

1. `parseOutcome` parses an outcome block whose `ticket.body` or `evidence`
   contains fenced code blocks, including ```` ```json ```` fences.
2. The observed round's transcript at
   `storage/tmp/repro-console/repro-gigabytealchemy-ai/iteration-1/ai/transcript.txt`
   is a fixture: parsing it yields `status: filed`, residual class
   `coverage-check-misses-section-background-images`, and a ticket body of
   non-zero length containing its fenced evidence intact.
3. A round can hand back `1c` defects separately from its gap diagnosis, and
   the console files them at `status: draft`.
4. The round still has no tool that can write a file, run a command, reach the
   network or spawn an agent. [[REQ-256]] behaviours 3 and 4 hold unchanged.
5. The brief references the existing L1 documentation and the new engine
   documentation, and both are reachable by a round whose only tools are
   `Read`, `Glob` and `Grep`.
6. Engine documentation describing `tools/generate/src/` exists and is
   referenced by the brief.
7. Rounds on the same reproduction can resume a prior round's session. The
   chosen scope and reset rule are stated in the code that implements them.
8. A round's diagnosis appears once in `transcript.txt`, and the session line
   names the model.
9. The console can produce a ticket from a completed round's artifacts without
   spawning a new round.
10. A failed round's reason names the artifact that holds what it said.
11. The model and the round's cost are recorded beside the outcome.

## Acceptance

- The `gigabytealchemy.ai` round that motivated this ticket parses, and the gap
  it found is filed rather than discarded.
- A second iteration on the same site demonstrably knows what the first one
  diagnosed.
- A round that finds a `1c` defect outside its gap diagnosis files it.
- Per-round cost is readable from the round's own artifacts.

## Out of scope

- The AI writing code. [[REQ-256]] §"In v1 the AI does not write code" stands;
  this ticket widens what a round may REPORT, never what it may DO.
- The gap the first round actually found. That is its own ticket, and filing it
  is this ticket's acceptance criterion rather than its content.
