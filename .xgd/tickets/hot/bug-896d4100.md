## Symptom

On production (2026-11-08), the container starts working on a consultant reply only 4.6–7.7 s after the client's message arrives, before any session rebuild or model call. BUG-385's timing lines, together with the platform's own events for `turn_c0fea102…` (a Carry on, 20:48 UTC) and `turn_389342a6…` (20:28 UTC), split that time as follows:

- **The request handler takes 0.4–1.5 s to create the Workflow.** `POST /api/ai/prompt` arrives, and the Workflow instance is created (its `event.timestamp`) 0.4 s later in one case and 1.5 s later in the other. The slow one also logged 30 `transcript: malformed turn order` warnings while re-reading a transcript of about 160 entries.
- **The Workflow takes 1.7–4.7 s to reach its first step** (`job_step_queued since=job_created`, 3 samples). `runConsultantTurn` calls `step.do('round 0', …)` straight away, so none of our code runs in that gap.
- **About 1.1 s more passes before the job's Durable Object calls `start()`.** The step begins, and `start()` comes about 1.1 s later (inferred from `job_container_intercept` at +1.28–1.43 s and `intercept_ms` 190–270). The Durable Object is new for every job, and it writes the step clock, an alarm and the token first.
- **Then the container takes 1.2–1.4 s** until it answers its health check.

Cloudflare's serverless products don't normally take seconds to start, so the likely cause is ours. **The main suspect is cold isolates loading our bundle.** The control app deploys as a **13 MB unminified `worker.js` (226,239 lines)**. The client's requests reach isolates that are already loaded. The Workflow and each new Durable Object may get a fresh isolate, possibly in another data centre, which has to load and evaluate all 13 MB first. The alternatives are Cloudflare's own Workflow scheduling, or placement far from the client. Workers Logs records neither the data centre nor whether an isolate was fresh for these events, so the current logs can't tell these apart.

## Fix — LOGGING ONLY

This ticket adds the logging needed to split a reply's start-up time, and changes no behaviour. The operator deploys it, sends a few messages, and the fix is decided from what the logs show.

Every line is one JSON object carrying the job id where one exists. No line logs a token, a header, a key, a query string, message text or a request body.

1. **`isolate_cold`, logged on the first invocation an isolate serves.** A module-level marker records when the module was evaluated. The first invocation logs:
   - `isolate_cold: true`;
   - which entrypoint it was (`fetch`, the `ConsultantTurn` Workflow, `AgentContainer`, `PlatformApi`);
   - `isolate_age_ms`, from when the module was evaluated until this invocation began;
   - `module_eval_ms`, the time the module's top level took to evaluate, where it can be measured.
   Later invocations log nothing for this.
2. **The data centre each runs in.** The request handler logs its `request.cf.colo`. The Workflow and the Durable Object have no request, so each looks its data centre up once per isolate, from `https://<own host>/cdn-cgi/trace` or an equivalent that needs no credentials. The result is cached at module level and added to their timing lines. The lookup happens once per isolate, never per step, and a failed lookup logs `colo: null` and costs nothing more.
3. **`turn_start_timing`, from the request handler** that starts a job (the prompt, and Carry on), with:
   - `handler_ms`, from the request arriving until `create()` is called, with the main sub-steps before it timed separately (including the transcript read and its checks);
   - `create_ms`, how long `create()` itself took;
   - the colo.
4. **`job_run_entered`, from the Workflow's `run()`** on entry, with `since_created_ms` (from the instance's `event.timestamp`). It is logged once per entry of `run()`, so a replay after a retry shows up as well. The gap from `run()` entry to the first step, which `job_step_queued` already measures from creation, is then attributable.
5. **`job_container_wake`, from the Durable Object's `runStep`**, with:
   - `rpc_ms`, how long the Workflow's call took to arrive, using a call timestamp the Workflow passes in the request;
   - `storage_ms`, the time spent on the storage writes before `start()`;
   - `isolate_cold` and the colo.
6. **`container_boot`, from the container.** Its server logs once at listen time, with `boot_ms` from process start until the server listens. The timing of a round step, carried back on the step's compute, includes `rebuild_ms` (the session rebuilt from the junction, D1 and R2) and `first_token_ms` (the step's start until the model's first token).
7. **`turn_first_output`.** When the first text of the reply is written to the junction, a line logs `since_request_ms`, from the client's message arriving (passed with the job).

## Why free-coded

Response time matters for every consultant reply. These lines decide which fix is worth doing (bundle size, isolate warmth, placement, or a container started in parallel), so we don't guess.

## What landed (logging only, no behaviour change)

All lines are one JSON object on the console (Workers Logs / container stdout). None holds a token, header, key, query string, message text or request body.

- **`isolate_cold`** (`src/startup-timing.ts`, imported FIRST by `worker.ts`, which calls `moduleEvaluated()` at its end): logged once per isolate, on its first invocation, with `entrypoint` (`fetch` from `index.ts`, `ConsultantTurn` from `runConsultantTurn`, `AgentContainer` from `JobContainer.runStep`/`alarm`/`verify`, `PlatformApi` from its `fetch`), `job` where there is one, `isolate_age_ms` and `module_eval_ms`. workerd does not advance its clock during synchronous code, so on production `module_eval_ms` will read about 0 and `isolate_cold: true` itself is the signal; in the node suites it is `null`.
- **Data centre**: the request handler uses `request.cf.colo`. The Workflow and the Durable Object look it up once per isolate from `<origin>/cdn-cgi/trace` (2 s timeout), cached at module level, a failure cached as `null`. The lookup is never awaited by the work: the line is written once the colo is known (`logWithColo`).
- **`turn_start_timing`** (prompt route, so Carry on too), logged when `create()` returns: `job`, `handler_ms` (request arrival in `fetch` → `create()` called), `steps` (ms per sub-step: `body_read`, `spend_cap_checked`, `client_words_recorded`, `host_built`, `ledger_opened`, `person_read`, then inside host-core's `answered()` via a new optional `TurnRunner.mark`: `session_resolved`, `gone_job_checked`, `lost_turn_closed`, `message_opened`, `session_loaded` (the transcript read and its checks), `job_recorded`), `create_ms`, `colo`.
- **`job_run_entered`** (start of `runConsultantTurn`, so every entry of `run()`, replays included): `job`, `since_created_ms`, `isolate_cold`, `colo`.
- **`job_container_wake`** (`JobContainer`, just before `start()`): `job`, `kind`, `rpc_ms` (from a `calledAt` the Workflow now puts on the step request), `storage_ms` (step-clock write + token read/write), `warm`, `isolate_cold`, `colo`.
- **`container_boot`** (container server, at listen): `job`, `boot_ms` (process start → listening). A round's `rebuild_ms` (step start → session rebuilt, just before the model round) and `first_token_ms` (step start → first text event) are measured by `runJobStep` (new optional `StepTiming` argument), returned on the step's compute as `rebuildMs`/`firstTokenMs`, and logged on the existing `job_container_step_timing` line. They are not written to the ledger.
- **`turn_first_output`** (`executeStep`, once per job per process — a job's container is per job): `job`, `step`, `since_request_ms`, from a `requestedAt` the request handler passes with the job (`ConsultantTurnParams.requestedAt` → the round request).

Bundle check (no deploy, `wrangler deploy --dry-run --env production`): 13,101,440 bytes / 226,329 lines unminified; 8,635,805 bytes / 16,717 lines with `--minify` (−34%).
