# 1st Contact Builder UI — Architecture Principles

> **Rewritten 2026-07-30 (CHAT-9).** This document previously committed to an
> **in-browser renderer**, an **AI-only** edit path with click-to-edit "permanently
> out of scope", and an **Astro + React + shadcn** chrome. All three are withdrawn —
> see §12 for the ledger. The pipeline, the validation contract and the state model
> survive intact. The *page editor* itself — the direct-manipulation surface, its
> exposure rule, its edit bridge and its modals — is specified in its own document,
> [[DOC-28]]; this document covers the app around it.

## 1. Purpose & Scope

The builder is the surface where a site is edited: an AI proposes structured
site-definition edits from chat, **and** the user manipulates the live preview
directly. This document captures the durable architectural principles for that
surface — where it runs, how the preview is produced, what the edit pipeline is,
and how edits are validated.

It is paired with:

- [[DOC-4]] — product vision
- [[DOC-5]] — platform architecture (Cloudflare / D1 / R2 / Workers)
- [[DOC-7]] — framework architecture principles (renderer, structured-edit discipline)
- [[DOC-12]] — site storage, versioning & rendering model (draft / revisions / publish)
- [[DOC-23]] — the L1 layout substrate (what layout edits actually edit)
- [[DOC-25]] — behavior modules (what behaviour edits actually configure)
- [[DOC-28]] — **the page editor** (the direct-manipulation Design view, in detail)

**This document commits to:**

- The builder is a **feature of the `control-app` Worker**, not a separate app (§2).
- Preview is **server-rendered HTML in a same-origin iframe** — never a client-side
  renderer (§4).
- **Two producers, one edit vocabulary**: the AI and direct manipulation both emit
  the same validated structured diffs (§5).
- A canonical pipeline: **intent → structured diff → validate → state → re-render → refresh**.
- The AI's tool surface is **L1 tree edits + behavior-module `config`/`slots` edits** (§6).
- Enforcement of the four-layer mechanical validation gate defined in [[DOC-7]] §6.5 (§7).
- Vanilla ES-module chrome consumed from `xgd-framework`, **never forked here** (§9).

**This document deliberately does not commit to:**

- The page editor's own interaction design, modals, or edit-hook contract — [[DOC-28]].
- Specific AI tool-call schemas (defined per REQ).
- Chat UI components, message rendering, attachment shapes (REQ-scope).
- Auth flow specifics ([[DOC-5]] magic-link model).
- Portal / dashboard / CRM surfaces beyond the builder.

## 2. Product topology — one app, two Workers

`apps/` holds **Cloudflare deploy units**, not products. There are two because
there are two genuinely different runtimes on two route patterns:

| Worker | Route | What it is |
|---|---|---|
| `control-app` | `app.1stcontact.io/*` | **The 1C application** — dashboard, builder, authenticated API. The builder is a *feature inside it*. |
| `public-site` | `1stcontact.io/*`, `*.1stcontact.io/*` | The **multi-tenant site server**: every published site by host/slug, plus public form/API endpoints. |

The consequences worth stating, because they have been misread before:

- **There is one 1C application.** The builder is not a separate app, does not get
  its own directory tree, and does not get its own server. It grows inside
  `control-app`.
- **Sites are data, not apps.** Customer sites *and* the 1C marketing site are
  definitions + rendered output served by the one `public-site` Worker; the 1C
  marketing site is simply the apex tenant. It is built and edited **with the
  builder** — the product dogfoods itself.
- **There is no long-running Node server.** Cloudflare runs Workers (V8 isolates).
  `nodejs_compat` is set on both Workers, but there is no persistent filesystem and
  no arbitrary Node process. Any design that assumes one is wrong for this target.

## 3. Layout

### 3.1 Two-panel composition (the destination)

```
┌────────────┬─┬──────────────────────┐
│  Preview   │S│                      │
│  (iframe   │p│   Chat Panel         │
│   + toolbar│l│                      │
│   above)   │i│                      │
│            │t│                      │
└────────────┴─┴──────────────────────┘
```

Preview with its toolbar on one side, chat on the other, draggable splitter
between. The chat panel collapses to a rail with a restore chevron, mirroring the
proven XGD dashboard pattern. Panel widths and collapsed state persist in
namespaced local storage.

**Rationale:** builder work alternates between wanting all the screen for the
conversation and all of it for the result. Persistent collapse + drag-resize
covers both with one mechanism — no separate "preview-only" or "chat-only" view to
maintain.

### 3.2 v1 is the preview alone

The first build is **one Design tab: toolbar + iframe + edit mode** — no chat
panel, no split. Chat is a known-shaped addition (the `webui-split` /
`webui-chat` components already exist and nest), so deferring it costs nothing and
lets the genuinely new capability — direct manipulation over a server render —
be proven first. An **Asset** tab is the second tab; the two may collapse onto one
screen later, since the asset picker is reachable as a modal from the image editor
([[DOC-28]] §8).

## 4. Preview Rendering

### 4.1 Server-side, always — the split by channel

Rendering is server-side ([[DOC-7]] §2.4, [[DOC-12]] principle 6). It happens in
two places, by channel, and the split is the normal Jamstack-plus-SSR shape:

| Channel | When it renders | Where | Serves |
|---|---|---|---|
| **Published site** | at publish (build time) | full Node env (build step / CI), our existing `tools/generate` renderer | static output via `public-site` |
| **Draft preview** | on request | `control-app`, via the Astro Cloudflare adapter reading the draft definition | the builder's iframe, and the "open in new tab" URL |

The heavy Node/Vite/Container-API compilation always happens at **build time** in a
real Node environment; the Worker only ever runs the compiled result. Rendering
Astro on Cloudflare is a supported, standard path in both modes — there is no
research fork here, only plumbing. What is *not* portable is our current
`1c`/`tools/generate` entry point specifically, because it assumes a filesystem and
a Vite CLI bootstrap; it gets wired to the build step for publish, and its
component render path gets wired to the adapter for preview.

### 4.2 Same-origin iframe

The preview lives in a same-origin `<iframe>`; the builder reaches it through
`iframe.contentDocument` directly — no `postMessage` protocol.

Rationale (note that the *reasons* changed even though the mechanism did not):

- **CSS isolation** — site CSS does not leak into builder chrome and vice versa.
  The iframe inherits exactly the framework's own reset and token system, identical
  to a published page.
- **Direct DOM access is now load-bearing, not incidental.** The edit overlay
  hit-tests and outlines elements *inside* the preview document ([[DOC-28]] §5).
  Cross-origin isolation would make the editor impossible; same-origin is safe here
  because preview content is operator-controlled, not arbitrary user content.

### 4.3 Iframe and "open in new tab" show the same bytes

The toolbar's "open in new tab" points at **the same draft render URL the iframe
loads**. Because both are the same server-rendered artifact, iframe-vs-tab
divergence reduces to viewport width — which is exactly what §4.4 is for. (This was
a real worry under the withdrawn in-browser-render design, which would have
*created* a second renderer and therefore a genuine divergence source. Server
rendering removes it.)

### 4.4 Viewport switching

| Preset | Width | Use |
|---|---|---|
| `mobile` | 375px | verify mobile-first rendering ([[DOC-7]] §4.2) |
| `tablet` | 768px | mid-breakpoint check |
| `desktop` | 100% of the preview pane | default |

## 5. The Edit Pipeline — two producers, one vocabulary

### 5.1 The cycle

```
intent
  ├── chat message → AI → one or more structured tool calls
  └── direct manipulation → editor modal → the same structured edit
        → validated against the site definition + framework catalog
             ├─ invalid: rejected. AI receives a machine-readable error and
             │            retries in-turn; the editor surfaces it and reverts.
             └─ valid:   applied to draft state
        → re-render the draft  → iframe refresh
```

### 5.2 Direct manipulation is a second *producer*, not a second *path*

The load-bearing invariant is unchanged from the original doc: **site definitions
are structured data only, never raw code, CSS or HTML** ([[DOC-7]] §6.2,
[[DOC-2]]). Click-to-edit was originally banned because it was assumed to breach
that. It does not — provided the editor emits **the same validated structured
diffs the AI emits**, through **the same validator**. A copy editor that sets a
content field, a colour picker that sets a token, and an image editor that sets an
`asset-ref` plus structured crop/scale/scrim params are all structured edits. The
chat AI and the editor modals are **peers**.

The rule that carries the invariant: **no editor may produce anything the AI's
tool surface could not have produced.** If a proposed editor control cannot be
expressed as a structured edit, it does not ship as a control — it goes to the AI.

### 5.3 State is the single source of truth

The site definition is canonical; everything else derives.

- Chat history is metadata, not state.
- The preview is a pure function of `(siteDefinition, framework)` — see
  [[DOC-12]] §6.
- Save / publish persist state; they never compute it.
- Undo / redo operate on state diffs.

### 5.4 Edits are diffs, not full replacements

Both producers emit **diffs** — never the whole definition. Cheap payloads, natural
undo/redo history, and a basis for conflict detection if two actors ever edit one
site.

### 5.5 Progressive application

The AI may emit several tool calls in one turn. The builder applies them in order,
re-validates after each, and re-renders — so the user watches the site build during
a single turn, which is [[DOC-4]]'s core promise.

## 6. AI Tool Surface

Since the pivot ([[DOC-24]]) the allowed-edits surface is two things:

- **Author L1 directly** for all layout and appearance — the typed [[DOC-23]]
  substrate, under the safety envelope. This is where taste lives; there are no
  aesthetic dials.
- **Configure behavior modules** ([[DOC-25]]) for behaviour: set an instance's
  typed `config` (behavioural params only — never aesthetic) and fill its named
  `slots` with **L1 subtrees**. The AI *configures* a module; it never writes its
  code.

Both are structured and both are validated (`validateL1`,
`validateBehaviorInstance`); neither can express raw CSS/HTML ([[DOC-2]]).

**The forbidden list is enforced by absence.** [[DOC-7]] §6.3's forbidden actions
translate to *the absence of a corresponding tool*: no tool writes framework or
module source, none sets arbitrary CSS or HTML, none introduces a module type or
version outside the catalog, none bypasses a schema. Even a hallucinated call
cannot land, because §7 validates before applying.

**Failures self-correct in-turn.** Validation returns machine-readable errors
(tool, path, expected, got); the AI emits corrected calls within the same turn.

## 7. Validation Contract

| Layer | Where | What | On failure |
|---|---|---|---|
| 1. Edit intent | builder client | every AI tool call **and every editor-modal edit** validated before applying | reject; structured error to the AI / surfaced + reverted in the editor |
| 2. Builder state | builder client | the state store refuses invalid definitions | toast; revert |
| 3. Save | `control-app` | server-side re-validation before persisting | 4xx; client surfaces |
| 4. Publish / build | `tools/generate` | pre-render validation | block publish; operator notified |

All four layers consume the **same** validator exported by
`packages/site-schema` — one validator, one set of rules, every layer. Drift
between layers is the only way invalid data could ship, which is why it is shared
rather than duplicated. Layer 1 covering *both* producers is what lets §5.2 hold.

## 8. State & Persistence

Storage is governed by [[DOC-12]], which is authoritative; the builder only
consumes it.

- **Working state** — in memory in the builder client, plus the draft definition
  itself, which is *already* the mutable working copy ([[DOC-12]] §3). There is no
  separate builder-side draft concept.
- **Saved state** — today the draft is file-backed under
  `storage/sites/<slug>/draft/`; it moves to D1 (+ R2 for asset bytes) in
  [[DOC-12]] §7's phase 2, which is triggered precisely by a *server-side builder*
  needing to read and write it. The builder is that trigger.
- **Publish** — the toolbar's Publish is a thin call over existing machinery:
  snapshot `draft/` into the next immutable revision, diff, append to `history.json`,
  render. Forward-only; live = latest. Rollback is `checkout <old>` + `publish`,
  not a distinct command.
- **Revision history** — owned by the save/publish endpoint, not the builder. The
  builder hands over a validated definition; the endpoint owns snapshot mechanics.
- **Undo / redo** — per session, over the in-memory diff log. Cross-session undo
  means loading a prior revision; not v1.

## 9. Chrome Technology

The builder's chrome is **vanilla ES modules** on the `@gendevlabs/webui-*`
components from `xgd-framework` — `webui-shell` (tab bar, theming, namespaced
storage), `webui-split` (the draggable, collapsible, nestable two-pane),
`webui-chat` + `webui-markdown`. Zero dependencies, no build step. The XGD
dashboard already proves this exact stack for this exact kind of tool.

React is reserved for a specific editor that genuinely needs it (e.g. a full
rich-text engine), mounted as an island *inside a modal* — not as the chrome.

**One source of truth: the shell is never edited in this repo.** If the shell needs
changing, it changes in `xgd-framework` and flows here. Two consumption routes
satisfy that, and the choice is open (§13):

- **Publish the components as versioned packages** (they are currently
  `private: true`, `0.0.0`, no registry config) → depend on
  `@gendevlabs/webui-shell@^x` like any dependency. The proper destination; needs
  publishing set up upstream.
- **Git submodule**, pinned by commit, read-only here — structurally enforces
  "don't change it in this project". The clean interim.

**Copying the components into this repo is rejected.** It creates exactly the
divergence the rule exists to prevent. (An earlier CHAT-9 plan to vendor
`webui-shell` into `packages/builder-ui/vendor/` is withdrawn.)

## 10. Mobile

**The builder is desktop-first; the sites it builds are mobile-first.** The
preview + chat surface needs real estate a phone cannot give. A future mobile
builder might collapse to "chat with swipe-to-preview"; that is v2+.

Every site rendered in the preview and shipped by the build is mobile-first
responsive ([[DOC-7]] §4.2); §4.4's viewport switcher is how that is verified from
a desktop browser.

## 11. Out of Scope (v1)

| Item | Status |
|---|---|
| Mobile builder | v2+ |
| Multi-user concurrent editing of one site | v2+ |
| Cross-session undo / redo | v2+ |
| Chat panel in the builder | deferred — v1 is the preview + editor alone (§3.2) |
| Drag-to-reorder in the preview | v1 out; structured edit only |
| Field-level (sub-block) edit hotspots | v1 out; block granularity first ([[DOC-28]] §6) |
| Diff visualization ("what changed this turn") | likely v1.5 |
| Voice input | out |
| **Raw JSON / raw CSS editing mode** | **permanently out of scope** |

The last row is the load-bearing one and is unchanged. A "drop to raw" escape hatch
would invalidate every guarantee about structured edits, validation, tool-surface
enforcement and catalog evolution. Note the distinction from §5.2: *direct
manipulation* is in scope because it produces structured edits; *raw editing* is
out because it does not.

## 12. Withdrawn Commitments (ledger)

Recorded explicitly so a reader does not re-derive them from an older copy.

| Withdrawn | Was | Now | Why |
|---|---|---|---|
| **In-browser rendering** (old §3.1) | the preview invokes `packages/framework` as a JS module in the browser; "preview cannot drift from production because it is the same code" | server-rendered HTML in an iframe (§4) | modules are Astro components — build-time by nature. Running them in-browser needs either a second React reimplementation of the whole catalog (two catalogs = exactly the drift being avoided) or an Astro-in-browser hack. [[DOC-7]] §2.4 and [[DOC-12]] principle 6 withdrew it; this doc had not caught up. It also forced the framework to stay browser-ESM-pure — a constraint [[DOC-12]] §10 explicitly lifted. |
| **"Click-to-edit inline in the preview — permanently out of scope; AI-mediated only"** (old §9) | direct manipulation forbidden as a breach of the structured-edit guarantee | the product's primary editing surface (§5.2, [[DOC-28]]) | the ban confused *raw editing* with *direct manipulation*. Only the former breaches the invariant. Editing copy and images on the page was always the intent; doing it in a separate asset-manager tab is simply a worse framing of it. |
| **"Direct token / dial / variant pickers — AI-mediated only"** (old §9) | no non-AI controls | friendly parameters are exposed (a colour picker, never a token name); anything sophisticated still goes to the AI ([[DOC-28]] §3) | same reasoning; the exposure rule, not the producer, is what protects the user from the implementation. |
| **Astro + React islands + Tailwind + shadcn chrome** (old §9.2) | the builder is a React app | vanilla ES modules on the `webui-*` components (§9) | what we are consuming from `xgd-framework` is zero-dep vanilla ESM, and the XGD dashboard proves the stack. Adopting React around it would add a build step to import no-build components. |
| **A separate Node server / separate app for the editor** | briefly proposed in CHAT-9 | the builder is a feature of `control-app` (§2) | there is one 1C application, and Cloudflare does not host long-running Node processes. |
| **Vendoring `webui-shell` into this repo** | briefly proposed in CHAT-9 | publish or submodule (§9) | copying forks the shell and guarantees divergence. |

## 13. Open Questions

1. **How we consume `webui-*`** — publish versioned packages upstream, or git
   submodule as the interim (§9). Blocks the first builder REQ.
2. **Draft preview SSR wiring** — the exact seam where the module/L1 render path is
   shared between the build-time renderer and the Cloudflare adapter, so there is
   one render implementation and not two (§4.1).
3. **When phase-2 storage lands** — the builder is [[DOC-12]] §7's stated trigger
   for moving the canonical store to D1. Does v1 of the builder run against the
   file-backed store locally first, or wait for D1?
4. **Autosave cadence vs explicit save** — write frequency, debouncing, and what
   happens if one site is open in two tabs.
5. **Streaming AI responses** — narrate as it arrives, or re-render once per turn?
6. **Tool-call batching** — re-render per call (true progressive) or coalesce per
   animation frame?
7. **AI intent layer** — direct structured tools vs. a higher-level interpreter
   turning "make the hero darker" into the right edits. v1 is direct tools.
8. **Diff visualization** — sidebar, preview highlight, both, or neither.
