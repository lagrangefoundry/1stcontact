## Symptom

In production, pressing *Click here to start* in the builder showed "That didn't start — please try again." Pressing it again did the same.

## Root cause (confirmed from production log_records / user_acceptances)

- The 2026-10-31 01:07 UTC production deploy published new legal-document versions (REQ-488): Terms doc-2634e408, Privacy doc-58a6b2c9, Beta Terms doc-324deda9. Publishing any new version means every existing account owes a fresh acceptance on its next request.
- The operator's builder tab was already open. From then on `guardTerms` (`apps/control-app/src/terms.ts`) refused every non-navigation request with **403** and `TERMS_REQUIRED_MESSAGE`. It serves the acceptance page only to a navigation. log_records show it: 15:32 UTC `POST /api/ai/opening` 403 ×2, each followed by `POST /api/ai/session` 403 (actor null); 17:49 every `/api/*` from another business tab 403.
- The start button's catch (`paintStart` in `apps/control-app/src/builder/chat.js`) cannot tell a terms refusal from any other failure. It re-reads the session (also 403) and shows the generic `CHAT_START_FAILED`. Retrying can never succeed.
- After a reload, the navigation got the acceptance page. 18:04:16 the documents were accepted, and 18:04:34 `POST /api/ai/opening` returned 200.

The same thing happens to every existing user who has a tab open across a legal publication, on every builder surface, not only the start button.

## Fix (proposed — awaiting operator confirmation)

When any builder API call is refused because legal documents are owed, the builder reloads the page, so the person lands on the acceptance page instead of seeing a generic error. The refusal needs to be recognisable by the client, e.g. a header or JSON marker on guardTerms' 403, checked in the shared `send()` of `builder/api.js`.

## Test plan

A UAT `test_UAT_FC_BUG-317_*`: an admitted session that owes documents presses *Click here to start* / makes a builder API call → the page navigates (reloads) rather than painting CHAT_START_FAILED.

## Operator assessment (2026-10-31)

The operator sees this as an upgrade issue: after a page reload, things worked as expected. Nothing is broken for the account now. The proposed fix is not authorised; it only matters if a tab left open across a future legal publication is worth handling.

## Resolution: won't fix (2026-10-31)

Closed as won't fix by the operator. The failure was a one-off upgrade effect: the 2026-10-31 deploy published new legal documents while a builder tab was open. That tab's requests were refused (403) until a reload took the user to the acceptance page. After the reload and acceptance, *Click here to start* worked as expected. The proposed client-side reload on a terms refusal was not implemented, and no code was changed.
