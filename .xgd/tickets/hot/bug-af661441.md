## Symptom

The XGD site holds a correctly formed email page — `whitepapers-email`, `kind: 'email'`,
subject *"Your two XGD papers"*, declared placeholder `cta_url`, with real copy in it. The
page control lists it. Selecting it shows nothing: there is no way to look at the message, and
therefore no way to style it or check it before it goes to a stranger.

The operator's report is exactly this: *"It is creating an email, but the builder cannot
navigate to it."*

## Root cause

[[REQ-247]] added the rule that an email page is never served, and enforced it at render:

    function servedPages(site: Site): Page[] {
      return site.pages.filter((page) => page.kind !== 'email')
    }

with the reasoning that this is *"the one place a published revision's bytes are decided,
rather than in the router — a route that refused a path would be a rule somebody could relax,
while a file that was never written is a page there is no way to ask for."*

That reasoning is right for a published revision and wrong for the builder, because
`preview.ts` is deliberately **not a second renderer** — *"Everything here reads
`renderSiteFiles`"* — so the draft preview goes through `servedPages` too and no bytes are
produced for an email page in the one place somebody is supposed to edit it.

**The ticket caused this, not the implementation.** [[REQ-247]] §2 states flatly *"It is never
served"* and then qualifies it as *"not routable in a published revision"*. AC-1 requires the
page be *"opened through the page control and edited like a page, and styled with L1"*. Those
cannot both hold under the broad reading, and the implementation reasonably took the broad
one.

## Fix

Draw the distinction the ticket failed to draw: **publish** writes no file for an email page;
the **draft preview** renders one, through the email render target that already exists.

*Not publicly addressable* is not the same as *not renderable in the builder*. The property
worth keeping is that no published revision carries the bytes and no path reaches them — and
that is unaffected by a preview that renders from the draft on demand for an authenticated
operator inside their own builder.

The email render target is already built and tested; what changes is which pages the preview
asks it for.

### Where the distinction is drawn

The render grows one option that says *emit the site's messages too*. **The builder's preview
is the only caller that sets it** — publish and `1c render` pass nothing, so a published
revision still carries no file for a message, which is the same "a file that was never
written" property [[REQ-247]] chose and not a route that declines to serve. `servedPages` is
left saying exactly what it said, and stops being the only answer to *which pages does this
render emit*.

It is set for **every channel the builder's preview serves**, `rev-<id>` included. A frozen
revision is not the public surface — it is what the public surface was — and an operator
asking what a message said in revision 3 is asking the same question as one asking what it
says now.

### What the operator sees

A message is rendered by the **email target**, byte-for-byte as the sender (`lead.ts`) will
render it: tables, styles inlined on every element, palette references resolved to literal
colour, real font fallback stacks. It carries none of the web target's head — no theme
stylesheet, no client bundle, no edit stylesheet — because a mail client loads none of them,
and emitting them would make the preview differ from the send in the direction that flatters
it.

**A message has one rendering, and the View/Edit toggle does not change it.** The toggle
chooses between a page as a reader meets it and the same page with its behaviour off and its
regions addressable; neither half of that distinction exists for something a mail client will
paint. So the two channels return the same bytes, and the toggle can never put the bug back on
one side of itself.

The consequence, stated so it is not mistaken for an oversight: **click-to-edit does not
operate on a message.** The edit channel's segment stamping belongs to the web emitter, and
the email emitter does not stamp. Copy is changed through the assistant's `set_l1`, which is
how [[REQ-247]] AC-2 already has it; what was missing and is restored here is the ability to
*look*. Stamping the email target for direct manipulation is separate work and is not in this
ticket.

An email page holding no L1 document is skipped rather than emitted empty — the same answer
the sender already gives it. `add_page` always seeds copy, so this is only reachable for a
definition written by hand or pushed from elsewhere.

### What comes free

Screenshots. `shot.ts` shoots through the same `PreviewRenderer`, so a message becomes
something the assistant can look at as well as read — which is the surface the design work on
a message actually needs.

## Test plan

`tests/test_UAT_FC_BUG-94_email_preview.test.ts`, driven through real entry points: the
message is made and edited through the consultant's own toolbox, fetched over HTTP from the
real builder transport at the URL the real page control composes, from a listing taken from
the real `/api/pages`; the published half goes through `1c publish` and is read off the bytes
it actually wrote.

- An email page is rendered by the draft preview, and the bytes are **exactly** the email
  target's — asserted as an equality against `renderL1Email` over the stored document and the
  stored palette, not as a spot check for a table.
- It is not the web target's: no linked stylesheet, no class selectors, no script — asserted
  against markers taken from a served page in the same site rather than written into the test.
- A palette reference reaches the preview as a literal colour, in neither the stored `ref`
  form nor the `var(--…)` a browser would be handed.
- The page control lists the email page, and the URL it composes for that row serves the
  message — the whole chain, since the listing had the row all along.
- The same is true in the edit channel, which returns the same bytes.
- **The published half is unchanged, asserted directly**: a published revision's HTML file
  list is compared exhaustively and holds no file for the message under its own name or any
  other, and no published artifact carries the message's copy anywhere. (There is no sitemap
  artifact in this project for one to be absent from; this is the stronger property that claim
  stood for.)
- A site with an email page still publishes, and every published artifact — pages and
  `theme.css` alike — is byte-identical to what the same site without the message publishes.
- Editing an email page's copy and re-requesting shows the change rather than the words the
  operator just replaced.
- The declared-placeholder rule still holds at this surface: copy that would drop `{{cta_url}}`
  is refused, and the preview goes on showing the copy that was kept.
