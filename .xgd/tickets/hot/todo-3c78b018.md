**Operator task — not code.** [[REQ-196]] cannot be tested end to end until this is
done, and [[REQ-197]], [[REQ-198]], [[REQ-199]] and [[REQ-200]] all sit behind it. It is
the only item in the onboarding set with *waiting* in it.

## 1. Account and domain

1. Create a Resend account.
2. Add **`1stcontact.io`** as a sending domain.
3. Resend returns a set of DNS records. Add them in Cloudflare DNS for the zone.
4. Click verify. Propagation is usually minutes on Cloudflare, but allow for hours.

**Until the domain verifies, Resend will only send to your own account address.**
So do this before writing any code that expects to mail somebody else.

## 2. The DNS records, and the one that bites

You will be adding three kinds:

- **SPF** — a TXT record naming who may send as the domain
- **DKIM** — a public key, whose private half signs each message
- **DMARC** — what a recipient does when the other two fail, and where to report

**If `1stcontact.io` already has an SPF record, MERGE into it. Do not add a
second.** Two SPF TXT records on one domain is a hard failure — not a warning, not
a fallback — and it fails *all* mail from the domain, including anything you send
today. This is the single most common way this setup goes wrong. Check for an
existing `v=spf1` TXT record first.

**Start DMARC at `p=none`,** with a `rua=` reporting address. `p=reject` on day one
will bin your own mail the moment alignment is slightly off, and you will be
debugging it from the outside with no reports. Tighten to `quarantine` and then
`reject` once reports show clean alignment.

## 3. Decide the sending subdomain

Sending from the apex is fine for transactional mail and is the simplest thing.

Worth deciding now anyway: if 1st Contact ever sends **marketing** mail, it should
not share sender reputation with sign-in links. The usual shape is a dedicated
subdomain for bulk, leaving transactional on the apex. Cheap to decide now, awkward
to separate after volume has accumulated on one name.

## 4. The API key

- Create a key scoped to **sending only**, not full account access.
- Install it as a Worker secret, not a var: `wrangler secret put RESEND_API_KEY`
- **Do this per environment.** Production and preview have separate secret stores,
  and a missing key in preview looks exactly like a broken adapter.
- It must not appear in `wrangler.toml` or any committed file ([[REQ-196]]).

## 5. The webhook

[[REQ-198]] needs delivery and bounce events.

- Add a webhook endpoint in Resend pointing at the control-app's bounce route.
- Subscribe to delivered, bounced and complained events.
- Capture the **signing secret** and install it as a second Worker secret. The
  endpoint is public and unauthenticated, and the signature is the only thing
  standing between it and anybody who can POST.

## 6. Inbound mail — a decision, not a step

`no-reply@1stcontact.io` needs no mailbox to send.

But consider whether the domain should accept mail at all. A domain that rejects
everything inbound scores slightly worse with some filters, and more practically,
somebody *will* reply to a sign-in email. Cloudflare Email Routing can catch-all to
your real address for nothing, which is probably the right answer.

## 7. Prove it before trusting it

Send a test message to **both a Gmail address and an Outlook/Hotmail address** —
they fail differently and passing one tells you little about the other.

In each, open the raw headers and confirm all three:

```
spf=pass   dkim=pass   dmarc=pass
```

A message that arrives in the inbox with `dmarc=fail` is a message that will start
going to spam later, without anything changing.

## Watch the free tier

3,000 messages/month and **100/day**. A single beta invite blast plus retries can
reach the daily cap, and the failure arrives as rejected sends partway through a
batch — which [[REQ-198]] will record as `failed` rather than lose, but which still
means half your invitees were not written to.

## Done when

- `1stcontact.io` verifies in Resend
- exactly one SPF record exists on the zone
- DMARC is published at `p=none` with a reporting address
- `RESEND_API_KEY` and the webhook signing secret are Worker secrets in both
  production and preview
- a test message to Gmail and to Outlook both show `spf=pass dkim=pass dmarc=pass`
- the webhook endpoint receives a delivery event
- a decision is recorded on inbound mail and on whether marketing will later need
  its own subdomain

## Done, 2026-09-07 — §1, §2 and §6, with two defects found on the way

Resend is live and has sent real mail. What follows is what was actually found in
DNS, because two of these were wrong in ways nothing reported.

### §2 — the SPF record was not an SPF record

The apex TXT read:

```
"Value: v=spf1 include:amazonses.com ~all"
```

The dashboard's field label had been pasted in with the value. Per RFC 7208 a TXT
record that does not *begin* with `v=spf1` is not an SPF record at all, so the apex
published no policy — it published a string that looked like one. Sends still
authenticated, because SPF is evaluated against the return-path (`send.1stcontact.io`,
which was correct) and DMARC aligned on DKIM. Nothing anywhere reported a problem.

Fixed. **When pasting a record value, paste only the value.**

### §2 — two SPF records, and the warning above needs a qualifier

This ticket says "if `1stcontact.io` already has an SPF record, MERGE into it, do not
add a second". That is right and it is about **one name**. There are legitimately two
SPF records on this domain, on different names:

- `1stcontact.io` — `v=spf1 include:amazonses.com include:_spf.mx.cloudflare.net ~all`
- `send.1stcontact.io` — `v=spf1 include:amazonses.com ~all`

**The `send.` one is load-bearing** — it is the return-path domain, so it is the record
real sends are judged against. Cloudflare's Email Routing setup lists both as
"conflicting" because it compares values rather than names, and resolving that prompt
deleted it. SPF silently became *none* on every send; DMARC kept passing on the DKIM leg,
so nothing looked wrong. Restored.

Same name → merge. Different names → leave both alone.

### §6 — decided and done: the domain accepts mail

Cloudflare Email Routing is enabled, forwarding to a real mailbox. It stopped being
optional when [[REQ-205]] made the invite send from `invite@1stcontact.io`: a repliable
address that bounces is worse than `no-reply@`.

It also turned out to be a prerequisite for §4's DMARC work. DMARC Management publishes
`rua=mailto:dmarc@1stcontact.io`, and with no MX records on the domain those reports
could not be delivered — the policy was collecting nothing while appearing configured.

### Where §4 now stands

DMARC is published at `p=none` with a reachable `rua`, so reports have somewhere to land
and the evidence for `p=quarantine` can start accumulating. That move is still open, and
still gated on reports showing clean alignment.
