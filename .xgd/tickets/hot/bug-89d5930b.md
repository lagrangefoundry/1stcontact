## Why this exists

Downstream half of **`lagrange-framework` BUG-58**. Upstream is being fixed in
`webui-chat` so that a per-turn stream which ends without a terminal `done` is
treated as a turn whose fate is UNKNOWN rather than a turn that produced nothing:
the assistant bubble is kept and marked interrupted, no resend control is offered
(the resend is what duplicated the operator's prompt), the composer is released,
and the host is told via a new `opts.onTurnLost({markdown, error})`.

That stops the builder duplicating a prompt. **It does not repaint the reply**,
because the widget has no origin to ask. Asking is this side's job, and nothing
here does it yet.

## The gap

`apps/control-app/src/builder/chat.js` rejoins a live turn in exactly one place:
`setSession`, at MOUNT, using `live` + `cursor` from `POST /api/ai/session`
(BUG-46). A page that *loads* mid-turn reattaches and paints the tail.

**A panel already mounted, whose live stream dies, never reattaches.** There is
no mid-life recovery at all. The reply carries on being produced and drained —
`streamTurn`'s `ctx.waitUntil` sees to that — and the operator sits in front of a
panel that has stopped showing it. Their only recovery is a page reload, which is
how they came to lose a long prompt (see BUG-122).

The transport cannot currently tell the two endings apart either:
`readEventStream` (`builder/api.js:652`) yields frames until the response body
ends and says so deliberately — *"a chat turn that stops is a turn that
stopped."* That reading is what BUG-58 disproves.

## What this ticket should do

1. **Notice the loss.** Wire `onTurnLost` when mounting the panel in `chat.js`.
   Optionally tighten `readEventStream`/`postEventStream` so an unterminated
   chat stream is distinguishable from a finished one at the transport seam
   rather than only at the widget.

2. **Ask the origin what happened.** Re-read the conversation
   (`POST /api/ai/session`, which already answers `turns` + `cursor` + `live`).

3. **Recover according to the answer.**
   - `live` → `streamChatReattach(sessionId, cursor)` and hand that stream to
     `resume()`, which adopts the lost bubble so the reply is ONE message
     rather than two.
   - not `live` → the turn is over; repaint the pane from the fresh transcript
     rather than inventing a text-offset partition the junction cursor cannot
     express (the cursor is a junction offset, not a byte offset into the reply).

4. **Bound it.** A few attempts with backoff. When recovery genuinely fails, say
   so in the conversation — the operator is owed the reason, not a silent stall.

## What was built

### The recovery, in `builder/chat.js`

`createChatPanel` now passes `onTurnLost` to `mountChat`. A turn reported lost
starts a **chase**:

1. **Pause, then ask.** The first wait is deliberately not zero. The commonest
   reason a stream stops is that the origin's turn ended badly and the record of
   that ending is written in a `finally` still running when the client notices
   the silence — asking immediately reads the conversation one moment before the
   answer lands. The ladder is `[400, 1500, 4000]` ms; the later rungs are for a
   different failure, an origin that is genuinely unreachable.
2. **Re-read**, through a new `options.reopen` seam (below).
3. **`live` → rejoin.** `streamChatReattach(sessionId, cursor)` through
   `watchForWrites`, handed to `resume()` seeded with **the panel's own painted
   partial**, not the transcript's: `resume` continues the bubble on screen, and
   the origin's fold stops at exactly the cursor the tail resumes FROM, so
   seeding from the transcript would repaint text the tail will not resend. The
   widget adopts the lost bubble, so the reply is one message and the lost
   notice is removed.
4. **not `live` → repaint.** `paint(session)` redraws the whole conversation
   from the transcript the origin just answered with.
5. **Give up out loud.** When every attempt fails, a note in the conversation
   carrying the origin's own error text.

### `paint` split out of `setSession`

`setSession` was one function doing two jobs: deciding *which* conversation is on
screen, and drawing it. The second half is now `paint(session)`, called by both
`setSession` and the chase's repaint — so the rejoin, the unsent rescue
([[BUG-122]]) and the interrupted notice ([[BUG-121]]) are stated once rather
than in two painting paths free to disagree.

A repaint is a **remount**, which is this file's existing answer to "repaint"
everywhere else: `mountChat` renders each message as it is appended and offers no
way to empty itself. It costs the operator nothing they typed — the composer
persists its draft under the panel id on every keystroke, and the id is the
conversation's, unchanged.

### `options.reopen` — the host's half of the seam

`() => Promise<session>`, answering the same shape `setSession` takes. It is a
**top-level option and not part of `transport`**, on the split REQ-127 already
draws in `app.js`: *"opening a session is this module's, because only this module
knows a site; running a turn is the pane's."* The pane holds a session id, and
`/api/ai/session` does not take one — it takes a site, or the business scope.

`app.js` wires both panels: the site chat to `openSession(currentSite)`, the
settings chat to `openSettings()` ([[REQ-239]] — it names nothing, because the
business is already in the request's path prefix).

**A host that passes none keeps every behaviour it had.** It simply cannot find
out, and the panel says so in the conversation rather than stalling silently —
which is the half of this that is an improvement with no seam wired at all.

### Two bounds, because they bound two things

- `RECOVERY_BACKOFF_MS = [400, 1500, 4000]` — how hard ONE chase tries to reach
  an origin that is not answering.
- `RECOVERY_CHASES = 3` — how many times a chase that DID reach the origin,
  rejoined, and then lost the rejoined stream too may go round again. The ladder
  cannot see that ping-pong; each leg looks like a fresh first failure.

The budget is spent per conversation and **refilled by a prompt**: an exhausted
budget describes a connection that was failing a minute ago, and the operator
pressing Send is them asking for it to be tried again. It is also reset by
`setSession`.

### Two guards on every await

A chase captures `sessionKey` and refuses to paint anything if, by the time an
answer arrives, either:

- the pane has been handed a **different conversation** — the generation-token
  guard `setSession` and `app.js` are already built around; or
- the panel **is streaming again**. BUG-58 releases the composer on a lost turn,
  so the operator can simply send the next prompt while the chase is still
  asking. A repaint would destroy the bubble of a turn running right now, and a
  rejoin would be `resume` silently declining behind it.

### `options.wait` — a test seam

The ladder is measured in seconds because it stands in front of a person
watching a reply that stopped. A suite spending it per assertion is a suite
nobody runs, so the pause is injectable. Real time is the default.

### The transport seam was NOT tightened

Point 1 offered this as optional and it is declined, with the stale comment in
`readEventStream` corrected in place rather than acted on. `webui-chat` already
knows what a terminal frame is and reports the difference; `chat.js` is the only
layer with an origin to ask. Teaching the parse to re-derive the same predicate
would be a second definition of "a turn ended" for the two to drift apart on —
which is the failure [[BUG-64]] is named for, arrived at from the other side.
`postEventStream`'s non-OK path already yields a synthetic `done`, so an HTTP
refusal correctly ends the turn rather than losing it.

## The constraint, decided

`streamTurn`'s comment states that an abandoned SSE *aborts* the turn: *"ENQUEUEING
ONTO A STREAM THE CLIENT MAY HAVE ABANDONED THROWS, and that throw is load-bearing
on the happy path — it is how an aborted SSE stops the turn."* Whether a turn
should survive its watcher leaving was left to this ticket.

**DECIDED: it should not. Abort-on-abandon stays, unchanged.**

- The junction is RAM (`ai.ts`), so an isolate evicted mid-turn loses the turn
  anyway. Making a turn outlive its reader would buy a guarantee the storage
  cannot keep — it needs a Durable Object, which is [[EPIC-19]]'s, not this
  ticket's.
- A turn that survives every reader is a turn with no one to stop it. The
  session-level Stop is the deliberate ending; a closed tab is not, and treating
  it as "keep going" means unbounded model spend answering nobody.

So *"walking away is lossy"* stays true, deliberately. What this ticket removes
is the other half — *"reload is lossy"* — by making the reload unnecessary: the
pane now performs, by itself and without destroying the composer, the re-read the
operator was reloading the page to get.

The consequence is visible and is the behaviour the UATs pin: a chase very often
finds `live: false`, because the socket dying is itself what aborted the turn.
That is not a degraded outcome. The fresh transcript carries the partial reply as
the junction recorded it, and the origin's own `interrupted` notice ([[BUG-121]])
is painted with it — *"That turn was interrupted — the reply above is not all of
it. Ask again to pick it up."* A successful chase therefore adds **no narration of
its own**: either the reply is now whole, or the transcript already says the true
thing better than a second sentence from here would. The panel speaks only when
it has genuinely failed, which is the one outcome the operator cannot see for
themselves.

## Supersedes

**[[BUG-46]]'s `a_failed_rejoin_costs_the_tail_and_nothing_else`.** That test
asserted the pane says NOTHING when a rejoin fails, on the grounds that the
rejoin is a request the operator did not make. BUG-123 reverses it: a rejoin that
fails is a turn whose fate is now unknown, the reply in front of the operator has
stopped either way, and silence is precisely what left reloading as their only
move. The test is renamed
`test_UAT_FC_BUG-46_a_failed_rejoin_leaves_the_turn_and_the_pane_intact` and now
asserts the notice alongside the invariants BUG-46 actually cared about — no
unhandled rejection, the pane still mounts, the turn is untouched.

## Test plan

`tests/test_UAT_FC_BUG-123_a_lost_stream_is_rejoined.test.ts`, mounted against
the **actually-installed** `webui-chat` like [[BUG-46]]'s and REQ-122's suites —
what is under test is specifically what the real widget does when a stream stops,
and a mocked panel would assert nothing about it. Transport and `reopen` are
injected; both are HTTP, jsdom cannot serve it, and the workers suites drive the
real routes.

1. `a_dropped_stream_asks_the_origin_what_happened` — a stream that stops without
   `done` produces exactly one `reopen` call.
2. `a_turn_still_live_is_rejoined_into_one_message` — reattach is asked at the
   cursor the origin JUST handed out (not one remembered from mount); the reply
   is one message; the lost notice is gone.
3. `a_turn_that_ended_is_repainted_from_the_transcript` — `live: false` repaints
   the conversation whole, including the half of the reply the panel never saw.
4. `the_origin_is_retried_before_the_pane_gives_up` — two refusals then an
   answer; three attempts, and the recovery still lands.
5. `a_recovery_that_fails_is_said_out_loud` — the note carries the origin's own
   words, and the partial reply is still on screen.
6. `a_host_with_no_reopen_is_unchanged_but_not_silent` — mounts and runs exactly
   as before, and explains the stall.
7. `a_recovery_for_a_conversation_left_behind_is_dropped` — a re-read still in
   flight when the operator switches site paints nothing.

**The suite skips on a STALE install, not only an absent one.** `WEBUI_INSTALLED`
is presence-only and says so; a `webui-chat` predating BUG-58 is present and
simply ignores `onTurnLost`, which would fail every assertion for a reason that
is not a defect here. The gate is a capability probe at module scope — it mounts
the installed panel and loses a turn — because `it.skipIf` is evaluated at
collection, before any hook runs.

Regression scope: the full `node` vitest project. 3914 passed / 3 failed, against
a `xgd-working` baseline of 3909 passed / 8 failed — every failure pre-existing
and confirmed on the baseline (`bug32-webui-scope-rebrand`, `BUG-50` env-file
port nondeterminism, `BUG-67` backend settings, plus load-sensitive flakes).

## Dependency

Needs the `webui-chat` change from `lagrange-framework` BUG-58 to be installed
here (`bin/install --lang js --component all` upstream). The dependency is
implicit — nothing in this repo's `package.json` records it — so a `WEBUI_INSTALLED`
skip is the expected failure mode on a machine that has not installed it.

**It is not installed on this machine.** The shared store still holds a
pre-BUG-58 copy, so the new suite skips here until that command is run. The
implementation was verified against the upstream source by staging it into the
store's resolution path; the staging was removed afterwards.
