## Criterion
In a builder session for a business, a successful `create_image` result carries a `display` sentence. It tells the model to show the picture by including one line in its reply exactly as written. That line is an ordinary markdown image, `![<name>](/b/<businessId>/api/material/file?uid=<uid>)`:
- `<uid>` is the material ticket the generation just created;
- the path names the current business explicitly (`/b/<businessId>/…`), so a replayed transcript never resolves against a different business;
- the alt text is the generated file's name without its extension and without square brackets. It is not a description of the picture.

Fetching that URL in the same business's session returns the generated picture's bytes. The session offers the image tool, and the image tool's own manual (the image surface's declaration, assembled with the business's material address as the router assembles it) describes the `display` field. The same surface assembled without a material address does not, so the mention comes from the factory and not from boilerplate. The check is on the image surface alone, because the l1 surface (version 9) also mentions `display` for `write_image`.

Clicking the picture to open it in an editor is not claimed here. That belongs to REQ-220.

## Verification
Through the Worker's route table, over real D1 and R2, with only the model and the image provider's HTTP endpoint doubled: generate a picture in a session for a known business. Assert that the result's `display` contains exactly one markdown image line, that its URL starts with `/b/<businessId>/api/material/file?uid=` followed by the new material's uid, and that its alt text is the file name without its extension. Split the URL's business prefix the way the production router does, fetch it, and assert that the generated bytes come back. Assert that the session offered the image tool. Assert that the image surface's own manual, with the material-URL factory, contains `display`, and that without it the manual does not.
