## Cluster 8 Resolution

**Boundary**: Local serving: both CAP-82 (Site Delivery) and CAP-85 (Builder Workspace) own a host that serves rendered site bytes on the operator's machine
**Stories resolved**: 3

### Verdict

All three stories confirm in place. No reassignment, no merge, no ticket changes.

The survey saw one capability ("a local host serving rendered site bytes") where
there are two hosts with different jobs. Both exist in code and neither is a
generalisation of the other:

| Host | Entry point | Serves | Owner |
|------|-------------|--------|-------|
| Local preview server | `startServe()` — `tools/generate/src/cli/serve.ts:37` | exactly one site, one rendered channel, as static files | CAP-82 |
| Workspace origin | `startBuilder()` — `tools/generate/src/cli/builder.ts` | the chrome document, the installed webui components, the builder's own browser source, *any* site's channel, plus list/publish/edit operations | CAP-85 |

`builder.ts` imports `resolveStaticFile` and `sendFile` from `serve.ts`. That is
the coupling the survey detected — and it is **shared implementation, not shared
ownership**. The helper's own comment states the reason: the builder serves
several static trees and every one needs identical confinement, so there is one
implementation and a traversal guard cannot be present on one tree and missing
on another. Two capabilities may observe the same function at two different
entry points under two different contracts; that is reuse, not an overlap.

### The boundary rule

- **CAP-82 owns what bytes a URL names for a site's rendered output** — the
  addressing and resolution contract, and specifically the requirement that it
  *agrees* between the local preview server and the deployed site.
- **CAP-85 owns the operator's workspace surface and the origin that hosts it** —
  which trees that origin serves, that they are all confined and non-cacheable,
  and the chrome, display panel and toolbar around them. It displays channels
  other capabilities produce and never produces one.

Applied to the local host: CAP-82 owns the *resolution rule* the preview server
applies; CAP-85 owns the *workspace origin* that happens to reuse it.

### Boundary observation (recorded, not acted on)

Because the workspace origin calls the shared `resolveStaticFile`, it inherits
the extensionless-to-`.html` mapping. No AC on STORY-99 claims that behaviour,
and STORY-96's AC-915 is scoped to the local preview server ("In local
preview"). So the mapping is *unclaimed* at the workspace origin.

That is a **coverage gap, not an overlap** — it changes no story's capability
assignment, which is why no action was taken here. It is noted because it is
the same shape as the divergence STORY-99 already flags rather than absorbs
(the `no-store` directive was added to the shared send path and reached the
standalone preview server, whose own intent never asked for it). If the matrix
later wants that behaviour pinned at the workspace origin, the natural home is
an added AC on STORY-96 — the story that owns the resolution rule — extending
its agreement from two environments to three. Creating stories is out of scope
for overlap resolution.
