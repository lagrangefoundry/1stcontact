# `1c kb build` cannot finish: `search` is called with `source`, upstream wants `indexes`

## The failure

```
$ ./bin/1c kb build
knowledge base 'system' reads from source 'shipped', which this host has no index for (available: none)
```

`tools/generate/src/cli/kb.ts:928` calls `lib.search(query, { source: indexSource,
… , sources: binding.sources })`. Upstream `@lagrangefoundry/knowledge` takes
**`indexes`** — a map from *source name* to `IndexSource` — and `scopedIndexes`
resolves each KB through `indexFor(kb, indexes)`
(`knowledge/src/search.js:127`). With no `indexes` key the map is empty, so
`available: none`.

`indexFor` refuses rather than degrading, deliberately:

> *"That is a deployment error and it fails here, loudly, rather than
> contributing no rows to the ranking — which is indistinguishable, from the
> caller's side, from 'this knowledge base is empty'."*

The refusal is right. The caller is wrong.

## What changed

Upstream REQ-112 made it **one index per source** rather than one index per host.
A KB's `source` now names both the store its corpus resolves against and the
artifact its vectors live in, so a singular `source:` no longer says enough. This
repository still passes the pre-REQ-112 shape.

The shared components arrive out of band — `bin/install` writes them into a store
this repository cannot update from a lockfile — so nothing in a `pnpm install`
would have caught the skew, and nothing in CI notices, because nothing runs the
suite when the shared store is rewritten.

**Only the read seam moved.** `buildIndex` and `buildChunkIndex` still take a
positional `source` (`doc_index.js:125`, `chunk_index.js:95`) and REQ-112 did not
touch them, so the four build-side calls in this repository are correct as they
stand. What changed is `search`, `searchChunks` and `KnowledgeRuntime.open`.

## Where

`1c kb build` is where this was noticed, not where it lives. **Every read path in
the repository is on the pre-REQ-112 shape** — seven call sites across four
files:

| File | Line | Call | What it needs |
| --- | --- | --- | --- |
| `tools/generate/src/cli/kb.ts` | `928` | `lib.search` (the awareness map's own reader) | `indexes` keyed by `shipped` |
| `tools/generate/src/cli/kb.ts` | `1073-4` | `KnowledgeRuntime.open` | `indexes` / `chunkIndexes` |
| `apps/control-app/src/system-knowledge.ts` | `147-8` | `KnowledgeRuntime.open` | `indexes` / `chunkIndexes` |
| `apps/control-app/src/session-knowledge.ts` | `315-6` | `KnowledgeRuntime.open` (project KB) | `indexes` / `chunkIndexes` |
| `apps/control-app/src/session-knowledge.ts` | `198` | `search` (the co-ranked override) | `indexes: runtime.indexes` |
| `apps/control-app/src/session-knowledge.ts` | `227` | `searchChunks` (the co-ranked override) | `indexes: runtime.chunkIndexes` |
| `apps/control-app/src/knowledge.ts` | `339` | `ProjectKnowledge.search` | `indexes` keyed by `project` |

`session-knowledge.ts:128` constructs a `KnowledgeRuntime` with `source: null`
directly. That one is harmless — the constructor ignores the key and `indexes`
already defaults to null — but it is stale vocabulary, and the comment above it
explains a deliberate `source: null` that no longer names anything.

The `KnowledgeRuntime.open` sites are the ones that hide. `open({indexes = null,
...rest})` sweeps `source` and `chunkSource` into `rest` and stores them nowhere;
the runtime is frozen with `indexes`/`chunkIndexes`, so `runtime.source` at line
`198` is `undefined` and there is no error at the seam that dropped it.

**So the assistant's own knowledge search is broken in the running app, not only
in the build.** `CoRankedKnowledge` overrides the upstream toolbox's `search` and
`chunk_search` with the old shape, so both hosts — the Worker and the Node CLI —
lost the same capability.

`binding.sources` is a map of **corpus stores** and is a different seam — it
stays. So do the `source:` keys in the KB declarations (`kb.ts:529`, `kb.ts:588`,
`kb/knowledge_bases.json`), which name a store rather than an artifact.

## The second failure, which is silent

`KnowledgeRuntime.open` **seeds the document snapshot from `indexes`**
(`ai-knowledge/src/toolbox.js:191`, `229`). With `indexes` unset the snapshot is
empty, so the `document` scope axis places no uid and every document read is
refused as `not_in_corpus` — "the corpus does not contain this", which is not an
error and does not look like a break.

Repairing `search` alone would leave reads politely empty, so the two move
together: a fix is only a fix if a hit can then be *read*.

One asymmetry the fix has to respect. `storeFor` falls back to the base store for
a KB that names no source; `indexFor` deliberately has none — *"an unnamed index
is not 'the project's index', it is an artifact nobody built"*. The project KB
declares no `source` in `kb/knowledge_bases.json`, so it resolves to
`DEFAULT_SOURCE` — `project` — and its index must be keyed under that name
explicitly rather than passed unnamed.

## Why it went unnoticed, and what it has been costing

`kb build` runs four stages and dies at the last one:

```
corpus → index → chunks → awareness map
                            ↑ here
```

So the first three succeed and `1c kb status` reports `index: built, chunks:
built, map: built` afterwards — the map being the *previous* one. The command
exits non-zero and leaves a plausible-looking state behind, which is why it reads
as a transient rather than a break.

The window is **four days, not months**: REQ-112 landed upstream on 2026-09-01
and this repository's call sites date from 2026-08-31 to 2026-09-02. The severity
is in the blast radius rather than the duration — the whole read half of two
knowledge bases, on both hosts, plus every document read.

Inside that window: `1c assets` inlines the awareness map and reports `awareness
primed not indexed`, so every bundle built since carries a degraded map. It also
explains the index skew that blocked `1c assets` outright ([[CHAT-23]],
2026-09-05): [[REQ-165]] added the projected `REF-*` documents to the corpus and
no build could complete afterwards to index them. And it is the likeliest
mechanism behind [[DOC-17]] §G (2026-09-02), where the assistant reported a
shipped capability as missing — an empty document snapshot answers exactly that
way.

## The coverage exists and is red

The last thing to say about this is that the suite already catches it. A full
`npm test` at the branch point fails **30 tests**, and the ones bottoming out in
`KnowledgeConfigError` span seven files — the system KB's own suites, the project
KB's, ingestion, the material surface and the projected reference:

```
tests/test_UAT_FC_REQ-123_system_kb.test.ts       tests/test_UAT_FC_REQ-161_material_surface.workers.test.ts
tests/test_UAT_FC_REQ-123_session_knowledge.test.ts   tests/test_UAT_FC_REQ-163_ingestion.workers.test.ts
tests/test_UAT_FC_REQ-159_project_kb.workers.test.ts  tests/test_UAT_FC_REQ-165_projected_reference.test.ts
tests/reconciliation-system-knowledge-base.test.ts
```

So the gap is not a missing assertion — it is that **nothing runs the suite when
`bin/install` rewrites the shared store**, and that store's contents are
invisible to the lockfile. The answer is a trigger, not another test.

The call sites are not all in `src/`, either: the suites above reach the seam
directly, so a signature change strands the tests in the same way it strands the
code. Those move with it.

## What this ticket does NOT fix

A second, independent skew came to light while fixing this one, and it is
deliberately left alone rather than folded in.

**The priming seam.** `@lagrangefoundry/ai-knowledge` made `KnowledgeDocs.documents()`
a coroutine (its own note cites DOC-22 §N: *"`documents()` is now a coroutine
that re-reads per call"*), while the installed `@lagrangefoundry/ai` still
iterates it synchronously in `assemblePrimingPrompt`. The two installed
components contradict **each other**, so no call site in this repository can
reconcile them — every session dies at priming with *"role.source.documents is
not a function or its return value is not iterable"*.

It is worse than stale: framework HEAD has moved past both, deleting
`ai_knowledge/js/src/docs.js` outright (*"KM priming providers replace
KnowledgeDocs"*, 2026-09-03) and rebuilding `ai` priming around an entry model
with no "documents" in it at all. Upstream is self-consistent; the installed
store is a mix of two moments.

That accounts for the 15 tests still failing after this fix, plus the stale tool
list (upstream added `KnowledgeChanges`). It is a migration, not a keyword
change, and it wants its own ticket.

## Acceptance

- `./bin/1c kb build` completes, all four stages
- `search` and `searchChunks` are called with `indexes` keyed by source name, and
  `KnowledgeRuntime.open` with `indexes`/`chunkIndexes`; `sources` continues to
  carry corpus stores, and the build-side `buildIndex`/`buildChunkIndex` calls are
  left alone
- the system KB's index is keyed `shipped` and the project KB's `project`, the
  name each KB's own declaration resolves to
- the assistant can search **and read** a document again — a hit that comes back
  from either knowledge base can be fetched, rather than refused `not_in_corpus`
  off an empty document snapshot
- the co-ranked surface searches both knowledge bases on both hosts: the Worker
  through `session-knowledge.ts`, the Node CLI through `openKnowledgeRuntime`
- every test that failed on `KnowledgeConfigError` passes — seven files, across
  both knowledge bases and both hosts
- `1c assets` reports the awareness map as indexed, not primed
- something notices when the repository and the shared store disagree about this
  seam. `bin/install` lives in `lagrange-framework` and cannot be reached from
  here, so the check belongs where this repository can run it: beside the
  existing shared-store preflight, which already asks whether each component is
  PRESENT and has never asked whether it is COMPATIBLE. One seam, checked
  positively, reported on its own line — a green result must not read as though
  it covered seams it never tested, since reading a narrow pass as a broad
  assurance is how this ran for days in the first place
