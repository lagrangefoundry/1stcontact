Found by loop 1, iteration **5** of `repro-gigabytealchemy-ai` against
`storage/references/gigabytealchemy.ai/index`.

**Residual class:** `declined-per-section-measurement-is-counted-nowhere`

**`defect_class: instrument-blind`** — the run explicitly declared it could not make a
measurement, wrote the refusal into `values-diff.json`, and the headline the round is
told to drive down counted it as **zero**. The score is not wrong; for that measurement
it is empty. Secondary `harness`, because half the fix is in the console's tally rather
than in `1c`.

```
REPO=/Users/martin/lagrangefoundry/1stcontact
ITER=$REPO/storage/tmp/repro-console/repro-gigabytealchemy-ai/iteration-5
```

## What happened

This iteration's headline, from `$ITER/ai/prompt.md` and `$ITER/ai/evidence-digest.md`:

> **unmeasured 1** — 0 axes, 1 band, 0 populations, 0 probes.

The run declined **two** measurements, not one. The second is in
`$ITER/diff/values-diff.json`, on the hero band's pairing row:

```json
{ "label": "§1", "box": {"x":0,"y":0,"width":1280,"height":800},
  "actualLabel": "§0", "overlap": 1,
  "anchorComparable": false,
  "anchorReason": "§0 sits inside this band, so the reference measured its anchor over a
   DOM-descendant population that EXCLUDES those runs while the reproduction's geometric
   band includes them — the two anchors are not the same measurement and are not compared" }
```

That refusal is REQ-270's landed fix working exactly as designed
(`tools/generate/src/cli/capture/values-diff.ts:2938-2950`): rather than compare
`0.53` against `0.39` over two different populations, it declines. The defect is that
**nothing downstream can see that it declined.**

## Why nothing sees it

**1. `gate.json` does not carry it.** `reconcileGates` builds the `values` block at
`tools/generate/src/cli/gate-core.ts:800-810` from `deltas`, `matched`, `unmatched`,
`unpairedActual`, `worstTier`, `unpairedSections`, `unpairedActualSections`,
`unmeasuredAxes` and the optional `sectionsNotComparable`. `sectionPairing` is never
read — the only mention of it in the whole file is a comment (line 677). Confirm:

```
grep -n "sectionPairing\|anchorComparable" $REPO/tools/generate/src/cli/gate-core.ts \
  $REPO/tools/generate/src/cli/gate.ts $REPO/tools/repro-console/src/*.ts
```

returns exactly one line, and it is that comment.

**2. The console's tally has no part for it.** `unmeasuredOf`
(`tools/repro-console/src/unmeasured.ts:115-158`) is four counts:

| part | source | this run |
|---|---|---|
| axes | `values.unmeasuredAxes` | 0 |
| bands | `values.unpairedSections` + `values.unpairedActualSections` | 1 |
| populations | `values.unmatched` + `values.unpairedActual` | 0 |
| probes | `values.sectionsNotComparable` (one global string) | 0 |

The `probes` row is documented at `unmeasured.ts:108` as *"a measurement the run declared
it could not make at all"* — which is precisely what `anchorComparable: false` is. But
`probes` is computed at line 131 as `typeof values.sectionsNotComparable === 'string' ? 1 : 0`,
and that global string is set in one place only (`values-diff.ts:2851-2857`): the
flat-L1 degenerate case, where the reproduction segments into a single body-spanning
band. A **per-section** refusal on an otherwise healthy pairing sets nothing.

So a declined measurement falls between all four parts, and
`headlineOf`/`breakdownOf` print `unmeasured 1 — 0 axes, 1 band, 0 populations, 0 probes`
with no `≥` and no `silent` entry, because every part the report carries was counted.
The module's own doc comment says *"A report that does not carry one of the four parts has
a total that can only be higher than it reads"* (`unmeasured.ts:162-168`) — that is exactly
this situation, and the guard does not fire, because the report does not carry the fact at
all rather than carrying it as `null`.

## Reproduce

```
python3 -c "
import json
g=json.load(open('$ITER/diff/gate.json'))
v=json.load(open('$ITER/diff/values-diff.json'))
print('gate says unmeasured parts:', g['values']['unmeasuredAxes'],
      g['values']['unpairedSections'], g['values']['unpairedActualSections'],
      g['values']['unmatched'], g['values']['unpairedActual'],
      g['values'].get('sectionsNotComparable'))
print('declined anchors in values-diff:',
      [p['label'] for p in v['sectionPairing'] if p.get('anchorComparable') is False])
"
```

**Wrong (what it prints now):**

```
gate says unmeasured parts: [] 1 0 0 0 None
declined anchors in values-diff: ['§1']
```

— one band counted, one declination not, headline `unmeasured 1`.

**Right:** `unmeasured 2` on this run, broken down as `0 axes, 1 band, 0 populations,
1 probe (§1 contentAnchor — <reason>)`. Concretely:

1. `gate-core.ts` carries the per-section declinations into the `values` block — the
   cheapest shape is `notComparableAxes: [{ scope: '§1', axis: 'contentAnchor', reason }]`,
   which matches the `{scope, axis}` shape `unmeasured.ts:88-92` already knows how to
   name; and
2. `unmeasured.ts` counts them under `probes` beside the global string, so the round's
   headline moves when the comparator stops declining.

## Why it matters beyond the arithmetic

The round is instructed that `unmeasured` "is the number to drive down". A refusal that
costs nothing in that number is a refusal no round will ever be paid to fix — and this
particular one hides the hero/header content anchor, the one section value on this page an
eye would actually check (§0 is unpaired, §1 is declined: **2 of the reference's 8 bands
have a `contentAnchorRatio` compared nowhere**, out of a headline that says 1).

Cross-reference: [[BUG-111]] closed the sibling hole (an unpaired reference section was
reported nowhere the gate reads) and its fix is visible here — `unpairedSections: 1` is in
`gate.json` and is counted. This is the same hole one row over, for a section that DID
pair.
