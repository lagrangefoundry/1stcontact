# A browser reload during an assistant turn destroys that turn

## Observed

An operator was working in the builder chat. The assistant said it had made
changes to the site; the preview did not refresh, so the operator reloaded the
page. The whole turn — their message and the reply they had just watched arrive —
was gone from the conversation. The assistant's **tool calls had already
committed**: the site edits were in the store. Only the transcript was lost.

That asymmetry is the tell. Side effects durable, conversation not.

## Root cause

Three facts compose. The third is ours.

**1. The archive lags by a whole open turn, deliberately.**
`ArchiveSyncer._sync` cuts at `closedPrefix(records)`: it archives only up to a
boundary where no turn is open. Folding half a turn splits one reply into two
stored turns and destroys the whitespace at the seam (lagrange-framework BUG-19
D1). This is correct and is not changing.

**2. In the Worker the junction is RAM, scoped to one isolate.**
`workerHost()` passes `lib.memoryJunctions()` (`apps/control-app/src/ai.ts:191`),
held in the module-level `CHAT` singleton (`apps/control-app/src/router.ts:116`).
So between `turn_start` and `turn_end`, the turn exists in exactly two places:
the browser's DOM and one isolate's heap.

**3. Our page-load handler reads the archive, never the junction.**
`openSession()` calls `storedTurns()`, which is
`await manager.archive.load(sessionId)`
(`tools/generate/src/cli/ai/host-core.ts:501-511`). We never tail the junction —
`SessionManager.watch()` has no HTTP caller anywhere in this repo. Only
`/api/ai/session` and `/api/ai/prompt` exist (`router.ts:905, 921`).

So **the entire duration of every turn is a window in which a reload loses the
turn**, even on a healthy isolate. That is (3) alone.

The permanence comes from the drain. `promptStream`'s `finally` appends
`turn_end` and `await`s `sync()` *before* yielding `done`, so a turn that reaches
`done` is durable. This one had not. The reload aborted the SSE →
`controller.enqueue` threw on the cancelled stream (`router.ts:1135`) → the
generator's `.return()` ran the `finally` → `turn_end` + `sync`. But that drain is
a multi-round-trip D1 sequence (`query` all chat tickets → `comments` → `get` →
CAS `update`), started *after* the client had gone, with nothing holding the
request open. `router.ts:1112` says so in as many words: **"`ctx.waitUntil` is not
reachable from here."**

## We were also told something false, and it is worth knowing which part

`ai.ts:187-190` reads: *"an eviction mid-turn loses the turn in flight, because
`ArchiveSyncer` drains continuously and everything before it is already durable."*

That restates lagrange-framework DOC-21 §15.4, which restated §1.5 — *"long-term
storage is updated continuously as we go, exactly as the browser is"*. **§1.5
stopped being true when BUG-19 added `closedPrefix`**, and §15.4's safety argument
for a memory junction was resting on it. Our exposure was never "a partial turn";
it was always a whole one.

DOC-21 §1.5, §11 and §15.4 have now been corrected upstream, and
lagrange-framework BUG-38 adds the call that was missing. Fixing our comment is
part of this ticket — leaving it restating a retracted claim is how the next
person re-derives the same wrong risk model.

## The fix

### 1. Render from the junction (`host-core.ts`) — the actual bug

Replace `storedTurns`'s archive read with the upstream call added for this:

```ts
const { session, cursor } = await manager.transcript(sessionId)
```

`transcript()` folds the junction and returns the cursor it consumed; where there
is no junction it seeds one from the archive, so §11's "one source with no splice"
holds. It touches no backend, which preserves the property `openSession` already
depends on: a deployment with no API key still shows the conversation and says why
it is frozen. Keep reading the transcript *before* `attach` for that reason.

`ChatSession` should carry the `cursor` out to the client so (3) can use it.

Note the existing `catch { return [] }` in `storedTurns`: a site with no
conversation yet is normal, but that swallow is also what let this bug read as an
empty conversation rather than a failure. Narrow it to the "no chat ticket for
session" case.

### 2. Let the drain outlive the client (`router.ts`)

`streamTurn` needs the `ExecutionContext`. Thread `ctx` from the fetch handler
into it and `ctx.waitUntil()` the stream's completion, so an aborted SSE does not
take the `turn_end` + `sync` with it. The audit flush in the same `finally` gets
the same protection for free, and the comment at `router.ts:1112` should be
updated rather than left saying `waitUntil` is unreachable.

This is the smallest change that stops the reported loss, and it is worth doing
first and separately: it makes a *completed* turn safe even under a reload race.

### 3. A reattach route over `watch()`

With (1) and (2), a reload during a turn shows the transcript up to the fold —
correct, but the operator still loses the live tail and sees the turn frozen
mid-sentence until it lands. Add a route that takes `{sessionId, cursor}` and
streams `manager.watch(sessionId, {cursor})` as the same `data:` frames the panel
already parses, so a reloaded panel rejoins the turn in progress. This is DOC-21
§11 as designed, and the pane's existing SSE reader can consume it unchanged.

### 4. Consider a Durable Object junction (separate ticket if taken)

(1)-(3) make the failure survivable, not impossible: with a memory junction, an
isolate evicted mid-turn still loses that turn. DOC-21 §15.4 names a Durable
Object as the route back — single writer per session, synchronous SQLite, and it
fits the existing `Junctions` port with no library change. Out of scope here; note
the residual risk when closing this.

## How to prove it is fixed

The regression is only visible on reload, so a UAT must actually reload:

1. **Reload mid-turn keeps the turn.** Drive a turn to a known delta (pace the
   backend, as the framework's `test_UAT_FC_BUG-38_*` do), call `/api/ai/session`
   again, and assert the response carries the partial assistant turn. Today it
   comes back without it.
2. **A cancelled SSE still archives.** Abort the prompt request mid-stream, then
   read the `chat_transcript` comment and assert the turn is there with
   `status: aborted`. This is the `waitUntil` half and fails today.
3. **Reattach resumes.** After (1), tail from the returned cursor and assert the
   concatenation of painted + tailed text is the whole reply, exactly once.
4. **A frozen panel still renders.** No `ANTHROPIC_API_KEY`: `openSession` returns
   `ready: false` *and* the full transcript.

Test (2) is the one that would have caught the reported incident; (1) is the one
that catches the wider window it exposed.

## What was implemented, and the behaviour that came with it

(1), (2) and (3) all landed. (4) did not, and is still out of scope. Everything
below that is not already stated above is behaviour this ticket now claims,
written down because a UAT asserts it.

### The cursor is required, not defaulted

`/api/ai/reattach` takes `{sessionId, cursor}` and **refuses a request without a
cursor** with a 400, rather than treating a missing one as `0`. Defaulting it
would replay the whole conversation into a panel that has already painted it —
duplication that looks like the feature working. A negative cursor is refused the
same way. `cursor` travels on `ChatSession` and nowhere else, because it is only
meaningful paired with the transcript it was folded from: a cursor obtained
separately describes a different fold, and the seam between them is the
gap-or-repeat the pairing exists to remove.

### A turn's outcome rides the `done` frame

"Assert the turn is there with `status: aborted`" cannot be read from the
archived transcript, and that is not a defect: the session file format carries
dialogue, not outcomes. The status lives on the junction's `turn_end` record. The
reattach route projects `turn_end` onto `done` and carries the status in
`meta.status`, so an abandoned turn is observably `aborted` rather than `complete`
— through the same route a client already uses.

### The record→event projection belongs to the host

`watch()` yields junction records in the producer's vocabulary (`delta`, `tool`,
`card`, `turn_end`); the panel reads the library's stream vocabulary (`text`,
`tool_activity`, `card`, `done`). The mapping lives in `host-core.ts`, not
`router.ts`, because the router is a transport and decides nothing about a
conversation. A reattached tail is therefore indistinguishable from a live turn
to the client, which is what lets the pane's existing reader consume it
unchanged. Tool activity is scrubbed of image bytes on the way through, exactly
as a live turn's is (REQ-157) — a replayed `screenshot` carries the identical
base64.

### `ExecutionContext` is threaded, and optional

`route()` and the fetch handler both take it optionally. The Node transport in
`builder.ts` has no execution context at all, and a Worker response that needs no
drain needs no extension — absent, everything behaves exactly as it did before.
The reattach route deliberately does **not** register anything: tailing writes
nothing durable, so a client that walks away leaves nothing to finish.

### The client transport, and what is NOT wired

`api.js` gains `streamChatReattach(sessionId, cursor)`, beside
`streamChatPrompt`; the shared SSE frame parse is extracted so the two routes
read the origin's framing in one place rather than two.

**The panel is not wired to call it, and cannot be from this repo.** `chat.js`
would need to render a resumed stream into the live assistant bubble, and
`@lagrangefoundry/webui-chat`'s surface has no affordance for that: every
streaming path goes through `send(text)`, which appends a user message and calls
`sendPrompt`. Driving the component from a stream it did not initiate needs a new
upstream capability. So a reloaded panel currently paints the turn up to the fold
(which is (1), and is the reported bug fixed) but does not yet resume painting;
the route and the transport are in place and tested for when that affordance
exists. This is the one part of (3) that is deferred, and it is deferred for a
reason outside this repo rather than for scope.

## Two findings worth recording

**A frozen panel reports `ready: true` in the Worker.** The proof obligation
above says `openSession` returns `ready: false` without an API key. It does on
the Node host, where the key is read from `process.env` while the manager is
built. It does **not** in workerd: the backend factory is lazy, so nothing
between `openSession` and `attach` tries to build one and the failure surfaces on
the first turn instead. This predates BUG-46 and is untouched by it — REQ-146's
own `a_missing_key_costs_a_turn_and_not_the_conversation` covers the same
scenario and asserts the same subset, silently, for the same reason. The UAT here
asserts the part this ticket is responsible for: the full transcript comes back
from a keyless cold isolate, proving the junction seed reaches the archive and no
backend. Whether the Worker should detect a missing key at open time is a
separate question and a separate ticket.

**A test that passes against the bug is worse than no test.** The `waitUntil`
proof cannot be written as "the transcript ended up archived": nothing tears an
isolate down under vitest, so an unregistered drain simply carries on and
finishes, and that assertion holds either way. It was written that way first and
passed against the unfixed code. It now asserts both halves — that the route
handed the runtime a promise (false before this ticket, where `waitUntil` was
called zero times), and that awaiting only what was registered is sufficient for
durability.

## Residual risk on closing

(1)–(3) make the failure survivable, not impossible. The junction is still
`memoryJunctions()` — RAM scoped to one isolate — so an isolate evicted mid-turn
still loses that turn. DOC-21 §15.4 names a Durable Object as the route back:
single writer per session, synchronous SQLite, and it fits the existing
`Junctions` port with no library change. Not taken here; no ticket filed for it
yet.


## The deferred panel wiring now has a ticket

**lagrange-framework REQ-114** — *webui-chat: a panel cannot render a turn it did
not start — §11's tail has no destination*.

That is the blocker named above, stated where it can be fixed. `mountChat` welds
three things together in `send(text)`: append a user bubble, open an assistant
bubble, call `sendPrompt(text)`. A reattaching client wants only the third, and
the rest of the surface offers no alternative — `appendMessage` renders a
complete message with no update path, and the render loop is private. So the
host half of (3) is built and tested here with nowhere to deliver it.

REQ-114 asks for `chat.resume(events, {markdown})`: attach a host-supplied
stream to a new assistant message, seeded with what the transcript already
painted, consuming the same `text` / `tool_activity` / `card` / `done`
vocabulary — ideally through `send`'s own loop factored out, since a live turn
and a resumed turn rendering differently is the defect that substitution would
introduce.

**A non-streaming fallback exists here and needs no framework change**, and is
worth stating because it changes what "deferred" costs. On load, when a turn is
live: paint the user message, skip the partial assistant turn, tail
`/api/ai/reattach`, buffer it, and `appendMessage('assistant', painted + tailed)`
when `done` arrives. The operator sees the complete reply land with no second
reload; what is lost is watching it stream, and only for a turn they reloaded
into. It needs one thing this ticket did not add: `/api/ai/session` does not
report whether a turn is live. That flag was left out as speculative while
nothing consumed it, and is cheap to derive — `closedPrefix(records).length !==
records.length` over the junction the fold has already read.

Not taken here either way; the choice between waiting for REQ-114 and shipping
the fallback is the operator's.
