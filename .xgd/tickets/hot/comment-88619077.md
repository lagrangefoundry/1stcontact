## What "registered" means

There are two separate records, in two different places:

1. **The bytes** — the file itself, at `draft/assets/<filename>` in the site's R2 bucket.
2. **The registry entry** — one item in `site.json`'s `assets` array: `{ id, src, alt }`. A name, which file it points at, and the alt text.

"Registered" means the second one exists. It's the site's own inventory of its pictures. The two are written independently, which is how you end up with bytes present and no entry — which is your file.

## What registers something today

Exactly two functions write into that array:

- `editAssetAdd` — `tools/generate/src/cli/edit.ts:1984`. This is what `1c asset add` runs, and what the assistant's `add_asset` tool calls.
- `editImageWrite` — `edit.ts:2082`. The assistant's `write_image` drawing tool.

Both do it the same way: build the new entry, append it to `site.json`'s array, and write the updated `site.json` *and* the bytes in a single `store.write` call.

Every other path that puts bytes into `draft/assets/` omits `siteJson` from that call, so no entry is ever created. There are two such paths: the capture mirror, and your chat upload — `apps/control-app/src/material.ts:563`:

```ts
await sites.write(args.slug, { assets: [{ name, bytes }] })
```

No `siteJson`. That single line is why your image is unregistered.

## What I'm proposing

Replace that line with a call to `editAssetAdd` — the function whose entire job is to create the registry entry. That is the registration. Concretely: keep the existing safety checks that already run before it (the republishable gate, and picking a non-colliding filename), then hand the name and bytes to `editAssetAdd` instead of writing them past it.

The knock-on benefit is that promotion inherits everything else that function does and currently skips: schema validation of the resulting `site.json`, and a change-journal record — so the assistant is *told* an asset arrived, rather than having to notice.

## On naming and describing

You're correct that your uploads are named and described. That naming lives on the **material ticket**, in the private ticket store — the confidential side. The site's registry entry is a different record in a different bucket, with its own `alt` field, and promotion currently carries none of the ticket's metadata across.

So `editAssetAdd` as it stands would register your file with `alt: ''` — hardcoded, at `edit.ts:1983`. The second part of fix 1 is to give that function an optional `alt` and pass the material ticket's title, so the description you already have lands on the site instead of being left behind.

That's the whole of fix 1: **create the registry entry, and populate its alt from what we already know.** Fixes 2–4 are about the assistant's *beliefs* — they don't register anything, and none of them would have helped if the entry were missing.
