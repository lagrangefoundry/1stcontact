Diagnosis is clear. Writing the ticket first.

I traced it. The assistant's explanation was, sentence for sentence, something we told it — and all three claims are now false.

**1. The declared absence still says uploads are impossible.** `tools/generate/src/cli/ai/l1-surface.json` carries an `absences` entry, *"Uploading a picture, or any file"*:

> …you cannot take a file from a conversation and put it in the site… Offer the user the images already in the site's list, and tell them **adding a file is done outside the chat**.

That was true before REQ-161. It isn't now — the overlay's first drop area *is* "put it on the site", and `router.ts::placeOnSite` promotes the bytes into the site's asset library in the same request. The reply you got, including sending you to the asset manager, is this paragraph read back. It's a projected reference, so no prompt tuning will beat it while it says this.

**2. Promotion writes bytes but never registers.** `material.ts::promoteToSiteAsset` calls `sites.write(slug, { assets: [{name, bytes}] })` directly and never touches `site.json`'s `assets` array. So `editAssetList` reports it `registered: false` and renders it `(unregistered)` — the exact word the assistant used. It also drops the alt text: ingestion described the image (DOC-38 §6) and promotion discards that description.

**3. `get_asset` contradicts `list_assets`.** `editAssetGet` reads only the registry, so an asset `list_assets` just listed raises `NOT_FOUND`. The manual agrees with the wrong side: `asset_id` is *"The registered name…"*, `get_asset` is *"one registered image or font"*.

An assistant that lists, probes, and reads the manual can only conclude unregistered means unusable. It doesn't: nothing requires registration to reference an asset — every capture-folded page references `/assets/<name>` against an empty registry, and no validator checks it. Then, having decided it was blocked, it drew a substitute and didn't say so; `write_image` warns it's "not a way to make a photograph" but doesn't forbid standing in for a file you supplied.

BUG-45 is written up with that diagnosis and this fix:

1. `promoteToSiteAsset` goes through `editAssetAdd` — registered, journalled, validated by the same path every other asset takes — carrying the material ticket's AI-written title as `alt`.
2. Rewrite the stale absence: the assistant still can't put a file in itself, but the client can from the chat, so ask for the drop rather than routing them to the builder.
3. `get_asset` answers for anything `list_assets` showed; drop "registered" from the surface language where it implies a permission it isn't.
4. `write_image` says plainly it is never a stand-in for a file the client supplied.
