# Styled Text Content Model & Markup

## 1. Purpose

Define the **single canonical model** for styled text that is shared by both
directions of the reproduction loop:

- **Represent** — how a site document authors text (the storage schema the
  renderer consumes). See [[DOC-12]].
- **Read** — how the capture projects an original page's text back into the same
  shape. See [[DOC-13]].

The two sides use the **same schema and the same textual notation**, so
transcription is "paste the captured value" and the values-diff pairs run-for-run.
This doc is the shared contract; DOC-12 and DOC-13 reference it rather than each
defining their own text model.

## 2. The problem it replaces

The prior model represented a text block as a single markdown `body` string plus
one `bodyStyle`. That cannot express a block whose runs differ — an italic tagline
at 18px above a 16px paragraph, a "More to come" line at 14px after it, an inline
emphasis at a different weight/colour. Real sites style *within* a block
constantly. The capture already reads per-run computed styles, so the loss was on
the represent side: the document could not hold what the capture could see.

## 3. Canonical model — a block-document tree with inline-run leaves

Text content is a **block `baseline` style plus an ordered list of blocks**. This
is a *tree*, not a flat run list, because structure is a tree: paragraphs,
headings, lists, blockquotes, code and tables are block nodes; their **inline
leaves** are runs, and a run overrides only what differs from the baseline —
mirroring CSS inheritance, which is exactly what the browser does.

```jsonc
body: {
  baseline: { fontFamily: "ui-sans-serif", fontSizePx: 16, lineHeightPx: 26, color: "#314158" },
  blocks: [
    { kind: "paragraph", runs: [
      { text: "Your private space to think out loud", emphasis: "italic", fontSizePx: 18 }, // overrides only the delta
      { text: "A voice-first app that helps you access clarity…" }                          // inherits baseline
    ]},
    { kind: "list", ordered: true, items: [        // an item is a *block* container
      { blocks: [{ kind: "paragraph", runs: [{ text: "Pick a starting point." }] }] },
      { blocks: [{ kind: "paragraph", runs: [{ text: "Drop in your words and pictures." }] }] }
    ]}
  ]
}
```

- **Block** — a node of the document tree. The kinds:
  - `paragraph` — inline `runs`.
  - `heading` — a `level` 1–6 plus inline `runs`.
  - `list` — one kind for bullet **and** ordered (an `ordered` dial); each
    **item is a block container** (`blocks[]`), so an item can nest a sub-list or
    span multiple paragraphs. Ordered lists carry `start` only when they begin at
    an ordinal other than 1; item ordinals are positional (`start + index`).
  - `blockquote` — a **container** of child `blocks` (nested / multi-paragraph
    quotes), not a paragraph-level flag.
  - `code` — raw verbatim `text` + optional `language`; its text is *not*
    inline-parsed.
  - `table` — a 2-D grid of cells (`rows[row][col]`), each cell a container of
    child `blocks`.
- **Run** — an inline leaf: `text`, optional inline markers (`emphasis`, link
  `href`), and any subset of the `TextRun` override fields (`fontSizePx`,
  `fontWeight`, `color`, `lineHeightPx`, `letterSpacingPx`, `paddingLeftPx`, …).
  Structure is **not** a run concern — it lives on the enclosing block.
- **Baseline + sparse overrides** keeps common cases terse: most runs carry only
  their text; only the exceptional run states an override. A plain field is the
  degenerate document `{ blocks: [{ kind: "paragraph", runs: [{ text }] }] }`.
- The model applies to **every text-bearing module**, not just `text-block`.

### 3.1 Why a tree (not markers on a flat run list)

The flat `{ baseline, runs[] }` shape is an *inline* model — superb at per-run
style fidelity, its motivating case, but it cannot cleanly hold **structure**.
Lists nest; a table is 2-D; a code block owns raw text + a language. A flat run
list with `paragraphBreak`/`blockquote` markers is a tree serialized badly.
Structure therefore lives at the block level; the runs model is unchanged, it is
just the leaf.

### 3.2 Why this shape — the WYSIWYG editor

Users edit a text block in a **semantic WYSIWYG editor** (ProseMirror/TipTap- or
Lexical-shaped) and never see the notation. The editors that give that UX store
a **block-tree-with-marks** document internally — markdown is only their
import/export side-channel, and markdown cannot even hold per-run font-size/colour
(§2). So the storage model mirrors a block tree, and the editor renders semantics
*loosely* (bold as bold, a list as a list, gold-ish as gold — not pixel-accurate)
while the framework renderer produces the exact pixels. Two projections of one
model.

## 4. Authoring / serialization surface — markdown + attribute-spans

The canonical *runtime* form is the block tree. The canonical *authoring and
serialization* surface is a text string: **CommonMark markdown extended with a
generic attribute-span**.

- **Block structure:** blank lines separate sibling blocks; `#…###### ` prefixes
  a heading; `- ` / `N. ` line prefixes a bullet / ordered list item (the first
  ordinal is the list's `start`); `> ` prefixes a blockquote (whose stripped
  content is itself block content — nesting and multi-paragraph quotes fall out);
  a ```` ``` ```` fence is a code block (optional language after the opening
  fence, text verbatim); and a nesting `::: table` / `::: row` / `::: cell` …
  `:::` structural-fence family carries a table. Because lists, blockquotes and
  cells all hold *blocks*, the parse/serialize is **recursive descent**; an
  item's second block or nested list is indented under its marker.
- **Attribute-span (the general inline form):** `[text]{fontSizePx=18
  color=#314158 letterSpacingPx=2}` compiles to one run with exactly those
  overrides. The attribute keys **are** the `TextRun` field names — so any value
  the capture can read has a notation; nothing is inexpressible.
- **Markdown is shorthand for specific attribute-spans:** `*x*` ≡
  `[x]{emphasis=italic}`, `[x](url)` ≡ a run with `href`. Markdown covers the
  common cases ergonomically; `[…]{…}` covers everything else.
- **Block-level escape hatch:** a fenced form (`::: {lineHeightPx=20 …}` … `:::`)
  supplies the document `baseline`, so block-level styling has the same
  completeness as inline.

### 4.1 Escaping (required for round-trip)

Delimiters are escaped with **CommonMark backslash-escaping** — no bespoke rule:

- `\[ \] \{ \}` (and `*`, `` ` ``, `\`, `>`) are literals; only **unescaped**
  `[…]{…}` is a span.
- A paragraph whose text merely *starts* like a block marker (`- `, `N. `, `> `,
  `# `, or a fence's `:`) is escaped (`\- `, `N\. `, `\> `, `\# `, `\:`) so it
  stays a paragraph. (`>` and `` ` `` are escaped everywhere, so a leading code
  fence or blockquote marker is covered by the general delimiter escape.)
- Attribute **values are quotable** — `key="value with spaces or a } inside"` —
  for values containing whitespace or delimiters.
- The **capture serializer must escape** any literal delimiter in a run's text so
  what it emits re-parses to the identical document.

## 5. The correctness invariant

The notation is correct iff it round-trips losslessly:

> **`parse(serialize(x)) === x`** for any block document — paragraphs, headings,
> code, tables, rich blockquotes, bullet + ordered lists (nested / multi-block
> items), text laden with `[ ] { } *` and dense per-run overrides — up to
> normalization. Normalization merges adjacent same-format runs within a block
> **and adjacent same-type sibling lists** (both are indistinguishable in the
> notation — a blank line between items is the same list, not a boundary).
> Formally `parse(serialize(x))` deep-equals `normalizeStyledText(x)`.

This is the property that makes "consistent way of representing everything" true,
and it is the lead acceptance test.

## 6. Read / represent symmetry

- **Read:** capture projects the original DOM → block tree (group by block, list
  items from `<li>`, dominant computed style → baseline, per-run deltas →
  overrides) → serializes to the markup string.
- **Represent:** the author edits in the WYSIWYG editor (or pastes the string);
  it compiles to the same tree; the renderer emits each run as baseline+override
  inline styles under the block's structure.
- **Diff:** compares runs to runs, paired by block + order + text.

One notation, round-trippable, transcription = paste.

## 8. Status / still deferred

The block model is deliberately extensible — new block *kinds* slot in beside the
existing ones without touching the run leaf.

**Landed (model + notation, under the §5 round-trip invariant):** the block tree
plus `paragraph` / `list` ([[REQ-54]]); `heading`, `code`, rich/nested
`blockquote` (which replaced REQ-54's paragraph-level `blockquote` flag), `table`,
and nested / multi-block list items ([[REQ-57]]).

Still deferred:

- **Schema / render / capture / diff for the block model.** REQ-54/57 cover the
  runtime model and the string notation only — `text-markup.ts` is a pure unit
  not yet wired into any stage. Carrying the block tree through content-schema
  validation, the renderer, the capture projection (§6) and the values-diff is a
  follow-up, once those stages exist.
- Component-owned typography that today has no per-run hook (badges, checklist
  items) — tracked separately; this model gives them a home once hooks exist.
- Structured run fields (`gradient`, `position`) are runtime-only and outside the
  string surface (the attribute-span is scalar `key=value`); stages carrying them
  do so as JSON, not markup.
