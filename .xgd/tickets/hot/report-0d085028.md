## The shape of this conflict

Both sides are the SAME refactor applied to different columns of `users`, and
they collide everywhere that shape is written down. HEAD carries `ee85dd30`
(REQ-191, "a person's email addresses are a table"); the incoming commit is
`0d170e40` (REQ-193, "user_names table, resolver, tab"), which removes
`users.display_name` in favour of `user_names`.

So every resolution is INTEGRATE BOTH: the address joins from `user_emails`
(REQ-191, already on HEAD) and the name joins from `user_names` (REQ-193,
arriving). Nothing was decided by picking a side wholesale.

## Incoming changes preserved

Every REQ-193 change in the conflicting hunks is present in the resolved tree:
the `./names` imports, `Person.name`/`Person.formerNames`,
`UserRecord extends JoinedName`, `CURRENT_NAME_COLUMNS` in `USER_COLUMNS`,
`USER_SOURCE` on all five reads, `formerNamesIn`/`formerNamesOf`,
`nameFromJoin` gating the invite's name write, `writeName` on both invite
paths, `PersonPatch.name`/`nameReason`, the `Their name` pane and rename
button, the `user_names` migration comment, and both tests' `currentNameOf`
assertions.

No hunk was dropped under the BUG-1301 precedence exception. What was dropped
in each case is the *other* side of the same column's history — incoming's
`u.email AS email`, `users.email` INSERT, `u.email = ?` lookup, `sets`/`binds`
UPDATE and "the address is still a column" comment — all of which are REQ-191
statements that HEAD's already-integrated `ee85dd30` supersedes. That is
REQ-191 winning over a stale REQ-191, not main winning over incoming.

## One thing this resolution could not fix, and it is not in this commit

`tests/support/contact.ts` — HEAD's REQ-191 fixture — still writes
`INSERT INTO users (id, tenant_id, status, display_name, …)`. This commit
removes that column, so `seedContact` will fail at runtime for every suite
that calls it. The file is NOT in `0d170e40`'s diff, so it is out of this
step's staging scope and was left untouched. It needs `display_name` dropped
from that INSERT and the name written through `writeName`, the same shape
`addContact` now uses.
