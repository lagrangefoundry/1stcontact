# Fix Plan — Iteration 4

## Hypothesis
`tests/reconciliation-identity-invite-provision-admission.workers.test.ts` was never moved onto the person model of REQ-191, REQ-193 and REQ-194. Its local helpers (`anOperator`, line 150; `addContact`, line 159; `rowsFor`, line 181) and 20 `provisionBusiness({accountUserId, email})` call sites fail during setup. The 20 orphan ACs are the ACs of those same 22 failing UATs.

## Analysis
This is a resubmission of the iteration-4 plan (REPORT-10862). Plan validation failed after it was filed. The diagnosis is unchanged and was re-checked against the working tree. This version also covers all 42 listed failures. The 20 orphan-AC entries are now explicitly in the batch's `tests` rather than being explained away in prose.

**Everything is in one file.** All 22 failing UATs are in `tests/reconciliation-identity-invite-provision-admission.workers.test.ts`. Each of the 20 orphan ACs (AC-2075, AC-1748, AC-2169, AC-2170, AC-2172, AC-2173, AC-2174, AC-2176, AC-2115, AC-1742, AC-1743, AC-2077, AC-2076, AC-2112, AC-2113, AC-2114, AC-2116, AC-1752, AC-1751, AC-1753) has exactly one test token in that file, and it is one of the failing UATs. They clear when those UATs pass. They are not a matrix-linkage defect.

**The failure output is incomplete.** The JUnit XML is missing. The 7 error messages that survived are all `Error: A business needs an account to belong to.` from `provisionBusiness`. The workers pool cannot bind a port in the planner sandbox (`listen EPERM`), so the planner could not run the tests.

**Stale shapes confirmed in the working tree:**
1. `provisionBusiness` calls pass `accountUserId` and `email`: lines 433, 529, 569, 617, 646, 660, 663, 799, 800, 875, 889, 911, 912, plus about seven more further down the file. The current `BusinessSpec` takes `accountId` (an `accounts.id`) and no email. The person's account is `users.account_id`, as in `tests/support/invite-account.ts`.
2. `addContact` (line 163) does `INSERT INTO users (… email …)`. That column no longer exists, and the insert omits the now-required `account_id`. The registered fixture `seedContact` (`tests/support/contact.ts`) already handles this.
3. `rowsFor` (line 182) runs `SELECT * FROM users WHERE … email = ?`. Addresses now live in `user_emails` (REQ-191).
4. AC2171 (lines 374 and 380) asserts `row.display_name`. Names now live in the names module (REQ-193).
5. `anOperator` (line 152) reads `findAccount(...)` as if it returned a person. Since REQ-194 it returns an `AccountRow`, so `.platform_operator` is undefined and `acceptTerms` receives an account id. This is what breaks AC2170, AC1744, AC2172, AC2173 and AC2174.
6. AC2170's `shape()` must also exclude `account_id`. The `grant()` helper's `accountId` must be an `accounts.id`.

**This hypothesis is new, not a repeat.** Iterations 1–3 fixed different drift: the `accountId` → `businessId` rename and the removed `provisionInvite`. This iteration targets the REQ-191/193/194 person model.

**Isolation.** These are deterministic setup errors, with no contamination pattern.

**Dependency tests.** `test_UAT_AC1741_` through `test_UAT_AC1760_` (excluding the failing ones) are in the same file and pass today. They must stay green after the helper rewrite. `test_UAT_AC2175_` is in `tests/reconciliation-identity-invite-control.test.ts` and serves as a check on the shared fixtures.

## Spec Changes Made
None. AC-2115 ("optionally an account as subject") and AC-2176 ("reaches only that business and its account") still read correctly under REQ-194. If the builder finds an AC that names a person where REQ-194 says account, it should correct the AC in place with a note citing REQ-194.

- `the invite is a transition, not a creation test_UAT_AC2169_inviting_a_known_contact_promotes_that_row_and_reports_created` — infra-reuse-gap — the local `addContact` reinvents `tests/support/contact.ts#seedContact`. Delete it rather than patch it.

## Batches
One batch. All 22 failing UATs, the 20 orphan-AC entries and the passing dependency tests in the same file share three helpers (`anOperator`, `addContact`, `rowsFor`). Splitting would put the helper rewrite into more than one batch. No production files are in the edit path.
