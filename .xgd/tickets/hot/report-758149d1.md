## BUG-1301 precedence — three forced resolutions

These hunks were dropped because their entire target was removed by a
legitimate, documented upstream refactor already integrated into HEAD. Taking
the incoming text would not compile, or worse, would silently yield an empty
KB.

1. **`system-knowledge.ts`, `KnowledgeDocs` import.** Incoming imports
   `KnowledgeDocs` from `./generated/ai-knowledge`. That export no longer
   exists: `generated/ai-knowledge.d.ts` lists exactly
   `LANDSCAPE_PROVIDER`, `MECHANISM_PROVIDER`, `KnowledgeRuntime`,
   `KnowledgeToolbox`, `knowledgeInstanceConfig`, `registerKmProviders`, and
   in the upstream package `@lagrangefoundry/ai-knowledge` the name survives
   only inside a comment in `src/priming.js:30`, which documents the removal:
   the `KnowledgeDocs.open()`/`documents()` split "existed only to" serve a
   synchronous snapshot assembled once, which by construction cannot reflect a
   document published after the session opened. That is a reasoned upstream
   decision with a stated defect behind it, not LLM churn.

2. **`system-knowledge.ts`, `KnowledgeRuntime.open` option names.** Incoming
   passes `source:` / `chunkSource:`. Upstream reads `indexes` / `chunkIndexes`
   (`@lagrangefoundry/ai-knowledge/src/toolbox.js:308,336,344,520`);
   `chunkSource` appears nowhere in the package. Because the generated `.d.ts`
   types these as `any`, this would NOT have been caught by a typecheck — the
   options would be silently ignored and the KB would open and return nothing.
   That is precisely the failure mode incoming's own commit message warns
   about ("it returns nothing and looks like an empty KB"). HEAD's
   `indexes: { [SHIPPED_SOURCE]: ... }` is the only side that works.

3. **`system-knowledge.ts` / `ai.ts`, `knowledgePriming`'s purpose argument.**
   Incoming calls `knowledgePriming(runtime, CARETAKER_PURPOSE)`. Upstream
   replaced the assembled document with the `LANDSCAPE_PROVIDER` /
   `MECHANISM_PROVIDER` pair, and `host-core.ts` now owns where the role's
   purpose sits in the entry list, so HEAD's `knowledgePriming(runtime)` takes
   one argument. The purpose is still rendered — it moved from a call argument
   to `host-core.ts`'s entry list (`host-core.ts:559`,
   `new lib.Entry({ name: 'caretaker-purpose', text: CARETAKER_PURPOSE })`),
   so no priming content is lost.

Resolving `ai.ts` to HEAD also drops incoming's
`import { CARETAKER_PURPOSE } from '.../host-core'`, which auto-merged into a
region HEAD did not touch. Under HEAD's one-argument `knowledgePriming` that
import has no remaining consumer in the file; leaving it would be an unused
import. HEAD's `ai.ts` is exactly incoming's file with that import absent and
the two call sites evolved, so `--ours` is the complete resolution rather than
a partial one.
