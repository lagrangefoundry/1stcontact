## What the client asked for

> "Lets talk about the image creating experience — right now it is pretty poor.
>
> Today —
> - ask AI to create an image
> - image created
> - I have to go to the library to look at it
> - No tools available to edit (crop, colorize etc)
> - AI says it can't 'see' it :-(
>
> I think a created image needs to appear in the chat — it can be small —
> clicking on it would open a modal with the image in our (limited) editing tool
> suite. The image, of course, appears in the library too. The modal should
> include the item name that it appears under in the library — user should be
> able to edit that."

## The principle

**A picture you made is one you can see, name, change without losing what it
was, and publish at a sane size.**

Every child of this epic is one clause of that sentence. Nothing here is about
making *better* pictures — the generator is fine. It is about the fact that a
picture, once made, falls out of the conversation that made it.

## What is actually wrong today, verified

**The assistant is telling the truth when it says it cannot see the image, and
that is by design upstream.** `components/ai_imagegen/js/src/imagegen_surface.json`
tells the model in its own overview: *"A generated image is not returned to you
as a picture. It is stored, and you are told the id of the ticket holding it …
the picture itself never enters this conversation."*

**And the blindness is wider than generated images.** `screenshot`'s `picture`
type (`tools/generate/src/cli/ai/fidelity-surface.json`) offers five kinds —
`reference`, `draft`, `edit`, `revision`, `url`. None of them addresses a stored
image. So the assistant cannot look at *any* picture in the Library: not one it
generated, not one the client uploaded, not an SVG it drew itself with
`write_image`. An upload's one-time text description at ingest is the model's
only access to it, ever.

**The chat has no image channel, but the pieces are there.** A turn is
`{role, markdown}` and the sanitizer is stock DOMPurify, which already permits
`<img>` — so a markdown image in a turn would render today if anything emitted
one. Nothing does.

**The Library already has most of the modal.** `library.js` renders the image,
carries an editable fields block, and `mountReader` already opens documents in a
modal host (REQ-172). A picture modal is that pattern extended.

**No image editing exists anywhere** — not in the UI, not as a tool. There is a
pure-JS PNG codec (`tools/generate/src/cli/png.ts`) but it is PNG-only and lives
on the CLI/fidelity path, not the Worker's material path.

**Publish renders in the Worker.** `POST /api/publish` (REQ-149) freezes the
draft and writes rendered bytes to R2; `public-site` only serves what is there.
So "build time" is workerd — no node, no `sharp`, no CI step. That constraint
shapes every rendering decision below.

## The decisions taken, and why

**1. The image reaches the chat as markdown in the assistant's own turn, and the
tool authors the line.** A tool result is not a chat bubble — only an assistant
text turn is in the transcript, and the transcript is what replays on reload. So
the tool composes the exact markdown line and the surface prose instructs the
model to paste it verbatim. The tool authors the string; the model places it.
This is what makes the picture survive a page reload, which the framework's card
mechanism would not: cards are ephemeral and the replayed transcript would drop
them.

The failure mode is a model that does not paste the line. It is visible, it is
cheap — the picture is still in the Library — and the surface's `absences`
section exists for exactly this kind of instruction. Host-injecting a trailer
would close it and was rejected as not worth the cost.

**2. Any image a turn produces appears this way**, not only generated ones. An
SVG the assistant draws with `write_image` is exactly as invisible today, and a
rule is easier to hold than a list.

**3. The assistant looks at a picture only when it asks.** An image in context
costs real tokens *and stays in every subsequent turn* — `fidelity-core.ts`
already carries that warning about screenshots. So the capability is a sixth
`picture` kind rather than an automatic return, the model looks deliberately,
and `compare` gains the ability to measure a stored image against a captured
reference for free.

**4. An edit is a recipe over a retained original, never new bytes over old.**
The original is kept forever; an ordered list of parameterised operations sits on
the record; any state is the original plus a prefix of that list.

This is what delivers *"I cropped it, and later decided it needed to be a little
wider."* That is not undo — it is **editing the crop operation's parameters**.
Because the operations are parameterised rather than baked, every past state
stays reachable by editing or removing an operation, in any order, months later.

**So the recipe is persisted and the undo/redo stack is editor session state
only.** The recipe is a better history than a history log, because its entries
are individually revisable rather than merely reversible.

**Coordinates are normalised**, as fractions rather than pixels. A pixel crop
silently moves the moment a resize is inserted before it.

**The operation vocabulary is closed and shared by the UI and the tool** — one
list, one implementation, or they drift within a month. v1: `crop`, `rotate`,
`resize`, `adjust{brightness,contrast,saturation}`. **`flip` is deliberately out
of v1** — the platform renderer cannot do it, and keeping it would mean a second
renderer for one operation.

**5. Editing is an assistant capability as well as a client one.** DOC-48
already instructs the assistant to *"crop an interesting strip and set the text
beneath it"* — advice it currently cannot act on. `edit_image` composes with the
sixth `picture` kind: look, crop, look again.

**6. One renderer, used in three places: the Cloudflare Images binding.** Its
transform pipeline maps almost one-to-one onto the operation vocabulary, so a
recipe is a transform chain rather than a canvas program. It renders the
editor's true preview, the model's view of a picture, and the published output.

The client's browser does the *interaction* only — dragging a crop box over a
CSS overlay — then commits the recipe and re-fetches the real bytes. That is how
editors behave anyway, and it is what stops a client cropping one thing and
publishing another: preview and artifact come from the same code.

Browser Rendering (`[browser]`, REQ-154) was the alternative — already bound,
already paid for — and was rejected: heavier per publish, and it cannot decode
HEIC.

**7. HEIC converts at the door, and the HEIC bytes are discarded.** Chrome
decodes no HEIC, so neither the client's canvas nor Browser Rendering can read
an iPhone upload; conversion must happen server-side on the upload path, and
synchronously, or the Library shows a broken image until it completes. This is
the strongest single argument for the Images binding — without it, "convert on
upload" needs a wasm libheif in the Worker.

Discarding the HEIC is a deliberate exception to *never lose the original*: we
can do nothing with those bytes, and the client has the file on their phone by
definition.

**8. Delivery sizes are built at publish, and the client is never asked about
them.** Two axes that must not be conflated: *editorial versions* are what the
picture is (the recipe, visible and the client's business); *delivery renditions*
are the same picture at several widths (a consequence of publishing, invisible).
Conflating them is how a Library ends up holding five copies of everything.

Under JAMStack this is clean, because a published revision is already a frozen
byte snapshot: the ladder is generated at publish into that revision's own R2
prefix, immutable and versioned with it. **The draft gets no ladder** — it is not
the public site — which halves the work.

**`render.ts:2459` is the single place an `<img>` is emitted**, so it gains
`srcset`/`sizes` from the ladder manifest and **`assetRefSchema` never changes**.
The site document stays innocent of delivery.

**Renditions are content-addressed** on the original, the recipe and the width.
Publishes are frequent and image edits are rare, so an unchanged picture costs
zero transforms on republish. The material store already content-addresses blobs
(`t/<tenant>/blob/<sha256>`), so this is the established pattern.

**`resize` still earns its place in the editorial vocabulary** — a logo that is
400px because that is what it is — and the surface prose must state plainly that
delivery sizes are handled automatically, or the model will start hand-optimising
bandwidth against the ladder.

**9. The modal shows the Library name and it is editable.** A generated image is
titled from its prompt, so it arrives under a name no one chose. The name in the
modal is the name in the Library — one field, one meaning, both places.

## What was considered and rejected

- **The framework's chat card mechanism** (`webui-chat`'s card registry) — richer
  payload and a structured click target, but cards do not survive transcript
  replay, and making them do so is upstream work to reach a worse place than
  markdown reaches for free.
- **Editing bytes in place** — a picture already placed on a page would change
  silently under the draft, and the describer's text would be wrong for a crop.
- **A separate derived material per edit** — keeps materials immutable, clutters
  the Library, and still loses the ability to widen a crop.
- **Browser-only rendering, with the browser uploading flattened bytes** — an AI
  edit would not reach the published site until a human opened the builder. An
  assistant capability that silently requires a human's browser is not one.
- **`srcset` in `assetRefSchema`** — delivery is not a property of the document.

## Corrections and one new decision, 2026-09-10

All six children were investigated before any code was written. Five facts this
epic asserted are wrong, one question it left open is now settled, and four
remain with the operator. The wrong sentences above are left in place and
corrected here rather than rewritten, so the record of what was believed at
scoping time survives.

### The new decision: the recipe is applied at promotion, not at publish

The epic never said where a material's recipe meets the site asset it was
promoted to, and it turns out nothing joins them: `promoteToSiteAsset` copies
bytes across the bucket boundary and `site_assets` carries no back-pointer.

**Settled in [[REQ-219]]: the material records the asset name it was promoted to,
and a recipe change re-promotes.** Renditions then content-address on the
promoted asset's own bytes plus width and format — a recipe change is new bytes,
so a new hash, so a new rendition, correct by construction. This is why
[[REQ-222]] needs nothing from [[REQ-219]] but the binding declaration.

**And SVG drawings are out of scope for editing.** A drawing is a site asset with
no material record, so a recipe has nowhere to live — and needs none: `write_image`
can redraw, cropping a vector means changing its viewBox, and the platform cannot
transform SVG. Drawings stay in scope for being seen ([[REQ-217]]) and looked at
([[REQ-218]]).

### Five corrections

**Content addressing was withdrawn, not established.** The claim above that *"the
material store already content-addresses blobs (`t/<tenant>/blob/<sha256>`)"* is
stale — upstream REQ-108 withdrew it and keys are `t/<tenant>/<attachmentUid>`.
Renditions would be *introducing* content addressing. The design survives; the
"we already do this" argument for it does not.

**`flip` is out of v1 for simplicity, not capability.** The platform's
`ImageTransform` carries `flip`. The decision stands — the stated reason was
wrong and would have misled reconciliation.

**HEIC input may be Enterprise-only.** Decision 7 rests on the Images binding
decoding HEIC, and Cloudflare's limits page lists that as an Enterprise feature.
This is with the operator. It does not disturb decision 6 — the transform chain
fitting the recipe, and per-publish cost, are why the binding was chosen — but it
does remove the HEIC argument from decision 6's reasoning.

**`assetRefSchema` is the wrong schema to name**, twice above. The `<img>` sink
reads `l1ImageSchema.src`. The intent — no schema change, delivery is a property
of the publish — is right and holds.

**Publish applies sizing, not the recipe.** Follows from the new decision above.

### Open with the operator

- **Is the account Enterprise for Images?** Gates [[REQ-221]] entirely.
- **Description staleness after a crop.** `description_status`'s values are all
  reasons a description could not be *produced*; none means *produced but no
  longer true*. Making a stale description a query is a schema decision, not a
  free one.
- **Background images.** `srcset` cannot reach `axes.backgroundImageUrl`, which is
  what the only real photograph in the repo is referenced as. [[REQ-222]] as
  scoped saves nothing on it.
- **Format negotiation and publish latency.** Serving WebP/AVIF from a static
  publish means `<picture>`, which changes the sink's shape; and a first publish
  of a photo-heavy site is N×M transforms inside a synchronous route.

One defect found in passing and deliberately not folded in: a Library-route
upload failure is completely silent (`receiveFiles` surfaces the error only when
`source === 'chat'`). Independent of this epic, wants its own ticket.

## Operator decisions, 2026-09-10 (second pass)

**HEIC conversion is dropped.** There is no visible route to Cloudflare's
Enterprise tier or its price, and the epic will not wait behind a procurement
question. [[REQ-221]] is rescoped to what needs no plan change: detect HEIC by
magic number, **refuse honestly** with the *Settings → Camera → Formats → Most
Compatible* advice, and give the picker the `accept` attribute it never had. That
replaces two wrong outcomes — a false *"That file is no longer in storage."*, or
silently filing a photograph as a document — with one true one. The conversion
design is recorded in that ticket for a follow-on if the binding ever becomes
available.

This also drops [[REQ-221]]'s dependency on [[REQ-219]]: a refusal needs no
renderer. It can ship first, and on its own.

**Background images are in scope, for delivery and reachability.** The only
raster site asset in the repo is referenced as `axes.backgroundImageUrl`, which
`srcset` cannot reach — so [[REQ-222]] as originally scoped would have saved
nothing on the one real photograph we have. It now covers background images with
the same ladder, emitted as per-width `background-image` rules rather than
`image-set()`, since L1 already emits per-width rules.

**Reachability is the other half of that decision.** A background image must be
reachable by every capability in this epic — looked at ([[REQ-218]]), edited
([[REQ-219]]), renamed ([[REQ-220]]) — and since it is an ordinary site asset,
mostly that already follows. The risk being guarded against is a predicate
written against pictures placed as `<img>` that silently skips backgrounds, which
nobody would notice because backgrounds are exactly the pictures nobody clicks
on.

**The upstream tickets are answered.** lagrange-framework REQ-149 composes its
declaration at construction, so a deployment's manual describes only what that
deployment can supply, and the seam carries a host-composed **sentence** on the
`host_detail` precedent rather than a bare handle. REQ-150 is closed-loop v1,
reuses REQ-149's mechanism for capability-driven absence, owns the repair of the
OpenAI edit transport, and waits behind REQ-149 and REQ-141/142's reconciliation.

## Still open

Two questions on [[REQ-222]], and one defect waiting on a decision.

- **Does the publish emit `<picture>`?** A static publish cannot vary on
  `Accept`, so serving WebP or AVIF means typed `<source>` elements, which
  changes the shape of what the sink emits rather than just its attributes.
- **Is a slow first publish acceptable?** `POST /api/publish` is synchronous
  behind a toolbar button, and a photo-heavy site's first publish is every
  picture times every rung. Republishes are near-free once the derived cache
  exists; the first one is not.
- **The silent Library-drop failure** (`receiveFiles` surfaces an upload error
  only when `source === 'chat'`) now blocks [[REQ-221]]'s value: the honest
  refusal is delivered through exactly that silent path. Needs its own ticket.



## Operator decisions, 2026-09-11 (third pass) — "Still open" above is now closed

All three items under **Still open** are decided. That section is superseded by
this one and is kept only as the record of what was asked.

**The publish emits `<picture>` with typed `<source>` elements — yes.** A static
publish cannot vary on `Accept`, so format negotiation can only live in the shape
of what the renderer emits, and that shape is expensive to retrofit and cheap to
adopt now. **Two formats in v1: the source's own, plus WebP.** AVIF is excluded on
the same reasoning that excluded `flip` — it is the expensive half of a decision
whose cheap half carries most of the value. WebP is roughly a quarter to a third
smaller than JPEG at equivalent quality and universally supported; AVIF's further
saving is modest while its encode cost is several times higher, and encode cost is
exactly what the latency budget below is rationed by. Once the sink emits
`<picture>`, adding AVIF later is one more entry in a list — which is the whole
reason to take the shape now and the format later.

A format conversion is **delivery, not a recipe operation**. `convert` must stay
out of the editorial vocabulary, for the same reason [[REQ-222]] already warns that
the surface prose must say delivery widths are automatic: otherwise the assistant
starts hand-picking codecs against the ladder.

**A slow first publish is acceptable in minutes, with the client told what is
happening. Hours would need a different UX.** That is a budget, and the honest
finding is that the ladder as it stands does not obviously fit inside it once
formats double the work — **not because any transform is slow, but because
`ladder.ts` renders every rendition sequentially**, making wall-clock the sum of
every transform on the site. A 30-picture site at six rungs and two formats is on
the order of 300–500 transforms plus as many R2 writes.

So three things land in [[REQ-222]], and the first is not optional:

1. **Bounded concurrency** instead of one transform at a time. This is the change
   that converts "minutes, perhaps more" into "under a minute, predictably", and it
   is a small edit to code that has already landed.
2. **The publish reports progress.** The operator's budget is explicitly *minutes
   with explanation*, so the explanation is part of the deliverable: a toolbar
   button that goes quiet for a minute reads as a hang, and a client who reloads
   mid-publish has learned not to trust it.
3. **A budget the publish refuses to exceed, informatively** — because the failure
   to design against is not slowness but a publish that dies most of the way
   through with a platform error naming nothing the client did.

A republish stays free: the content-addressed derived cache already means an
unchanged picture costs zero transforms. This is about the *first* publish of a
photo-heavy site, and the first after the ticket lands.

**Two numbers behind this are estimates, not measurements**, and [[REQ-222]] says
so: the per-transform timings, and specifically whether an Images binding transform
counts against the same outbound-subrequest budget an R2 write does. The second
decides whether item 3 is a real guard or a formality. Confirm before fixing the
concurrency ceiling — the same caution the epic already carries about confirming
the transform vocabulary rather than trusting a remembered list.

**These land on [[REQ-222]] rather than a new ticket.** That ticket is
`free_coded` with six commits — a stable resting state, and extending it with
further commits is the ordinary path for work that is one intent. The width ladder
and the format ladder are one intent: they are the same ladder, and splitting them
would give the reconciler two overlapping claims on one surface.

**The silent Library-drop failure still needs a ticket and has not been filed** —
it was raised with the operator and no instruction to file it has come back. It is
not cosmetic: [[REQ-221]]'s honest HEIC refusal is delivered through exactly the
path that swallows upload errors on a Library drop, so until it is fixed that
ticket's whole value is invisible on the surface it matters most on.



## Correction and decision, 2026-09-11 (fourth pass)

### The silent Library-drop failure was already fixed — no ticket filed

The epic carried this as an open defect needing its own ticket, and the operator
authorised filing it. **It should not be filed: [[REQ-221]] already fixed it**, in
`f87c58e2a1`, and the epic's record was stale rather than the code.

`receiveFiles` in `builder/app.js` now collects refusals across the round and ends
with `if (source !== 'chat' && refusals.length) library.refused(...)`, and
`library.js` has the `refused(message)` sink to receive it. The reasoning is in the
comment there, and it is the reasoning this epic wanted: a file the origin refused
used to simply never appear, leaving the client to conclude the product had ignored
them — *"the same experience as dropping a photograph into silence, arrived at
differently."*

**So the block on [[REQ-221]]'s value is gone**: the honest HEIC refusal reaches a
Library drop as well as a chat drop, which is the surface it matters most on.

**The lesson is about the record, not the bug.** This defect was reported as open
twice after the commit that closed it landed. Children merge into the working
branch while the epic is reasoning about them, so a defect the epic is carrying is
worth re-checking against the code before acting on it — filing this would have
produced a ticket whose entire content was already true.

### A publish locks the builder, explains itself, and shows real progress

The operator's call on the latency budget's second item. Recorded in full in
[[REQ-222]]; in summary:

**The builder locks while a publish runs.** Today `publishAction` disables the
Publish button and nothing else, so a client can keep editing through a publish —
and then hold a reasonable, untested belief about whether that edit is live.
[[REQ-173]]'s `blockEverything`/`inert` is the right mechanism and should be
reused, **but not its register**: REQ-173's block means *something is broken*, and a
publish block means *something is working*. Importing the alarm would tell a client
their site is broken at the moment it goes live.

**The message names the cause, and is shown only when true.** *"First-time
publication of images requires resizing, which can take some time — please leave
this tab open."* "First-time" is accurate because the derived cache makes a
republish free — and because it is accurate, a republish with nothing to build must
not show it, or the client learns to ignore the one case that matters.

**The progress bar is determinate, and cheap.** For a wait of minutes a spinner is
what reads as a hang, which is the failure this is meant to prevent. Two facts make
a real bar affordable: the ladder knows the rendition count before the first
transform (assets × rungs × formats, minus cache hits), and SSE is already the
house transport — `router.ts` serves three event-stream routes and `api.js`'s
`postEventStream` is a shared parser that exists precisely so there is only one of
them. Publish progress is a fourth caller, not a new transport.

**The design cost is named rather than discovered**: an SSE response commits `200`
before the first rendition is built, so a mid-publish failure cannot be an HTTP
status. The terminal frame must state success or failure, and a stream that ends
*without* one must be treated as failure — otherwise a dropped connection renders
as a completed publish, which is the worst outcome on offer.

**`1c publish` is unaffected.** Progress is a property of the route, not of the
publish — the same line this epic already drew around the ladder, which
`publishSite` takes as an optional argument and the CLI does not supply.



## Child review, 2026-09-11: the promotion join was decided and never built

A sweep of all six children's bodies and chat transcripts for questions left
unanswered. Most were answerable from this epic's own design conversation and are
now recorded on the children themselves. **One is not a question — it is a hole
across three tickets that no single ticket's tests can see.**

### The hole: *change* and *publish* are joined by nothing

[[REQ-219]] settled the material ↔ site-asset join as **option three**: promotion
records the site asset name it wrote, and a recipe change re-promotes. That
decision is correct and stays. **Neither half was implemented**, and each of the
three tickets that touch it has a reason not to have noticed:

- **`promoteToSiteAsset` does not record the promoted name.** It computes a free
  name — which may *rename* on collision — writes the bytes, and records only
  `placed_on` slugs.
- **`reviseRecipe` does not re-promote.** It writes `fields.edits` and returns.
- **Publish reads no recipe**, which is correct *under this design* — it is meant
  to ladder bytes that promotion already corrected.

So a client crops a photograph in [[REQ-220]]'s editor, sees it cropped in the
Library, publishes, and their site serves the uncropped original. No error is
raised anywhere, because every component is behaving exactly as designed; what is
missing is the seam between them.

**This is the epic's own title.** *"A picture you made is one you can see, name,
change, and publish at a sane size"* — the fourth verb does not currently receive
the third.

**[[REQ-220]] found it during investigation and was told the answers were in the
ticket.** They were, at the design level — [[REQ-219]] had decided it. The design
was never built, so the finding stands: *"editing the recipe in the Library changes
the Library's picture and not the site's."* Recording a decision and shipping it
are different acts, and this epic conflated them.

**It needs a ticket and one has not been filed** — it spans three children and
belongs to none of them, and this session does not create tickets without being
asked.

## Operator principle, 2026-09-11: one catalogue, reachable through the ticket API

> *All site materials MUST have catalogue (ticket) entries and MUST be available
> via the ticket API — that's what it was built for.*

Recorded as an epic-level constraint, not a preference. It arrives from [[BUG-80]]'s
conversation and it changes how three things in this epic should be read.

### It reframes the promotion-join hole — and confirms the fix

The hole recorded above (*"change and publish are joined by nothing"*) was written
as **a decided design that was never built**: [[REQ-219]] chose that promotion
records the site asset name and a recipe change re-promotes, and neither half
exists in the code.

**Under this principle that decision is not merely cheapest — it is the correct
shape**, and the reasoning [[REQ-219]] used to reject the alternative needs
revisiting. It dismissed a `material_uid` column on `site_assets` because *"adding
a column and a cross-bucket read at publish buys a purity nobody consumes."* The
operator has now said that purity is exactly what the ticket store was built to
provide. The conclusion survives — option three still wins — but for a stronger
reason than cost: **the catalogue is the source of truth and the site's assets are
a projection of it.** A material that records where its bytes landed, and
re-promotes when its recipe changes, *is* that projection. A join key between two
peer stores is what the principle rules out; a derived copy that knows its origin
is what it asks for.

So the fix does not change. Its justification does, and it stops being optional.

### It joins up with two tickets filed outside this epic

The same principle produced [[BUG-84]] and [[REQ-228]] from [[BUG-80]]'s session.
Neither is a child of this epic, and this epic does not claim them — but they are
the same problem seen from two other sides, and whoever picks any one of the three
should know about the other two:

| | What it covers |
|---|---|
| **[[BUG-84]]** | `write_image` mints no ticket. 14 SVG drawings are live on sites; 0 have catalogue entries. The *entry* half. |
| **[[REQ-228]]** | The AI cannot read the catalogue as tickets, and cannot promote. The *access* half. |
| **This epic's promotion hole** | A catalogue entry's recipe never reaches its projected copy. The *propagation* half. |

**All three are the same sentence** — the catalogue is the source of truth — failing
at a different point: nothing to project from, no way to read it, nothing carrying
changes forward. Fixing any one alone leaves the promise false.

### It falsifies a premise this epic used twice, and the guidance is corrected

**This epic told [[REQ-217]] not to make its picture clickable, and endorsed
[[REQ-220]]'s exclusion of drawings, on the grounds that *"a drawing has no
material record."*** That is true today and is precisely what [[BUG-84]] calls a
bug. Guidance resting on a defect's current behaviour is guidance with an
expiry date, and both tickets have been corrected.

**The corrected position**: a drawing gets a catalogue entry, so it is an ordinary
picture for everything the catalogue confers — being listed, being looked at, being
**named**. What stays excluded is *cropping*, and for a reason that has nothing to
do with records: [[REQ-219]] refuses SVG because a normalised crop on a
resolution-independent drawing is not expressible, and `info()` returns no
dimensions for one. **So the modal should open for a drawing and offer naming
without the transform tools** — rather than not open at all, which is what the
current predicate does and what this epic wrongly confirmed.

### What could not be verified

The operator points at *"REQ-150 in lf"* as adding `xgd ticket fetch` to retrieve
attachments through the ticket API. **lf REQ-150 is
*"imagegen: edit an existing image"*** (draft, low) and is not about attachments; a
search of lf's and xgd's ticket stores for an attachment-fetch or `ticket fetch`
ticket found nothing. The number is wrong or the ticket is elsewhere. **This is
asked rather than assumed**, and nothing in this epic is blocked on it — the
principle stands on its own, and for pictures the byte paths already exist
(`materialImageLibrary.read` → `readBlob`, and promotion's server-side read).



## What is still open, design-wise — 2026-09-11

A deliberate sweep for questions nobody has answered, as distinct from decisions
taken and not yet built. Ordered by how much damage the wrong answer does.

### 1. Re-promotion must overwrite in place, and the function promotion uses cannot

**The sharpest open question in the epic, and it is a correctness trap rather than
a preference.**

The decided design says a recipe change re-promotes. Promotion today runs through
`freeAssetName` (`material.ts:812`), which on collision appends `-2`, `-3`, and so
on. **So a naive re-promotion mints `logo-2.png` on the first edit and
`logo-3.png` on the second** — while every page that references `logo.png`
continues to serve the *unedited* original. The client crops their logo, the
Library shows it cropped, the site shows it uncached and unchanged, and a new
orphan appears in the bucket on every commit.

**Re-promotion therefore cannot reuse the promotion path**, and that is not a
detail — `freeAssetName` exists for a stated reason: *"promoting a second
`logo.png` would REPLACE the first — silently changing a picture that is live on
the client's site, from a surface whose whole promise is that it only adds."*
Re-promotion needs precisely the behaviour that comment forbids, because it is the
one caller for which replacing is correct.

**So the two doors must be told apart explicitly**: a *new* placement takes a free
name; a *re*-placement of a material that already records its asset name
overwrites that name and mints nothing. Which is another reason the recorded name
is load-bearing — it is what distinguishes the two.

### 2. What a recipe change does to a material placed on more than one site

`placed_on` is a **list**. A logo on two sites whose recipe changes must
re-promote to both, and collision resolution may have given it a different name on
each. Unspecified today, and it follows directly from (1): once re-promotion
addresses a recorded name, the record has to be per-site rather than a single
string.

### 3. The catalogue boundary: a delivery rendition is a picture and is not material

**The operator's rule and [[REQ-222]] collide on a literal reading, and the line
needs stating before either is built further.**

[[BUG-84]] scopes the rule as *"a **picture** that lands in a site's assets gets a
catalogue ticket"*, and excludes fonts and stylesheets as build output. **A
delivery rendition is a picture and is build output.** [[REQ-222]] writes up to six
per photograph into the revision's `out/assets/d/`, and with `<picture>` that
doubles. Read literally, the ladder fills the client's Library with hundreds of
derived files nobody uploaded and nobody can name.

**The boundary that actually works is not "picture" but provenance**: a catalogue
item is something **authored or received** — uploaded, generated, drawn, captured.
Bytes **derived at publish from a catalogue item** are not material and get no
ticket; they are already addressed by content and owned by the revision that built
them. This epic has drawn that exact line once already, for delivery renditions
versus editorial versions, and it is the same line.

Worth saying out loud in BUG-84, or the first person to implement the rule against
a photo-heavy site will either flood the Library or quietly special-case the
ladder and leave no record of why.

### 4. Whether an edit is expected to change the live site before a republish

Re-promotion updates the **draft**. A published revision is a frozen snapshot and
does not change. So a client who crops a picture and does not republish sees the
old one on their live site — correct, and consistent with [[REQ-220]]'s *"what the
client is looking at after a commit is what **will be** published"*. **But nothing
tells them.** Given the operator's decision that a publish now explains itself,
this is the same class of thing and probably wants a sentence in the same place.

### 5. Description staleness after an edit — punted, and the punt may not hold

[[REQ-219]] explicitly decided to leave it and say so: a description describes the
original. The reason to revisit is that **the description is what the knowledge
base indexes**, so a crop that changes what a picture shows leaves the KB
answering from text about a picture that no longer exists. `description_status`
exists to make a re-describe a query rather than a migration. Still a defensible
punt; it should be a re-affirmed one rather than an inherited one.

### 6. Already decided, not yet scheduled

Not open, but unbuilt and easy to lose: [[REQ-218]]'s font-context refinement
(photograph a drawing in the site's draft preview, not a bare document);
[[REQ-220]]'s `materialUidFromUrl` scope defect and its three AC977 probes;
[[REQ-222]]'s `<picture>`, bounded concurrency, progress reporting and budget
guard; and the promotion/propagation hole itself, which still has no ticket.

### 7. Small and genuinely unspecified

What sentence the host supplies for `create_image`'s `host_display.display`. The
seam asks for *"the host's own words about its own surface"*, and nobody has
written those words.



## Operator answers to the open design questions, 2026-09-11

### 1 — Replacement is explicit. Filed as [[REQ-229]]

Re-promotion **replaces bytes at an existing name**, as one operation, rather than
deleting and re-adding. The operator's reasoning is recorded there in full: a
delete-then-add leaves a window in which the site's pages reference an asset that
does not exist, and a publish inside that window renders a snapshot with a hole in
it.

The mechanism that makes it safe is the recorded name doing double duty: **a
material with no recorded asset name is a new placement and takes a free name; one
that already records a name is a re-placement and overwrites it.** `freeAssetName`
is left exactly as it is — its "only ever adds" promise is correct for every door
but this one, and this door is told apart by the record rather than by a flag.

REQ-229 carries the propagation half of the catalogue principle, alongside
[[BUG-84]] (entry) and [[REQ-228]] (access).

### 2 — Multi-site placement is not a live problem. Withdrawn

Correct, and the concern is withdrawn rather than parked: **a business holds one
site in v1**, so a material placed on two sites is not a state the product can
currently reach. `placed_on` being a list is forward-shaped, not evidence of a
gap.

Where it would surface, if v1 ever stops being true: the recorded asset name in
[[REQ-229]] is per-material, and two sites could have resolved the same upload to
different names. That is a note for whoever lifts the one-site assumption, not
work for anyone now.

### 3 — The ladder is catalogued under the picture's own ticket

The operator's model, and it is better than the boundary this epic proposed.
**A ticket catalogues multiple assets, so the ladder for picture X belongs to
ticket X** — optionally as a declared `fields.image_ladder[]` of pointers to the
sized copies, rather than as separate catalogue items.

**This answers the objection cleanly.** The worry was that a literal reading of
*"every picture gets a catalogue ticket"* would fill the client's Library with
hundreds of derived files. Under this model it cannot: the Library shows **one
item per picture**, and the renditions hang off it as what they are — sized copies
of that picture, not pictures in their own right. It also brings them inside the
attachment record, which is what blob garbage collection reads, so a rendition
stops being a bucket object nothing names.

**On re-reading, the collision this epic reported was narrower than stated.**
[[REQ-222]] writes renditions into the *revision's* `out/assets/d/`, and the draft
gets no ladder at all — so renditions do not land in the draft's asset namespace,
which is what [[BUG-84]]'s rule is about. The boundary still wants writing down,
but as a definition rather than as a conflict to resolve.

**One thing the model does not by itself answer, worth settling when it is built:**
a material ticket holds *the current* ladder, while a published revision needs
*its* ladder frozen — REQ-222 copies renditions into the revision prefix
deliberately, so a snapshot stays relocatable under any path prefix ([[REQ-109]]).
Those are different lifetimes, not competing homes: the ticket's `image_ladder[]`
is the catalogue's view of what currently exists, and the revision's copy is the
frozen artifact it published. They should be allowed to coexist rather than one
being made to serve both.

### 4 — Withdrawn

Draft and published differing is the intended semantics, and changes propagating
only on publish is the product's rule everywhere. There was no problem here.

### 5 — The description-staleness punt stands

Re-affirmed rather than inherited: a description describes the original, and the
knowledge base indexing that text is a known and accepted consequence.

## Decision — the ladder needs no catalogue field, and no ticket (2026-09-11, operator asked)

**Question.** Item 3 of the design survey proposed that the delivery ladder for
picture X be catalogued under ticket X, possibly as `fields.image_ladder[]`
holding pointers to the sized copies. Does that need a ticket?

**No, on both halves — and the reason is that the code already does the right
thing for a reason nobody has written down.**

**The "one item per picture, not one per rendition" half is already true by
construction.** `tools/generate/src/publish/ladder.ts::buildImageLadder` returns
`{manifest, derived}`, and `derived` is keyed by path **within the revision's
`out/`** — never `assets/`. Its own comment says why: *"a checkout restores what
the site IS, and a delivery rendition is not part of that."* So renditions never
enter the draft asset namespace that REQ-228's strong-form catalogue is a
complete account of, and the Library cannot fill with derived files. There is no
conflict to resolve, only a definition to state.

**The `fields.image_ladder[]` half is the wrong shape, and would be wrong rather
than merely redundant.** A ladder is not a property of a picture. It is a
property of *(picture, revision)* — REQ-222 freezes each revision's renditions
into that revision's own prefix, immutable and relocatable. A mutable field on
the catalogue ticket has no correct value to hold: it is stale the moment a
second revision is published, and wrong the moment a recipe changes. The
catalogue's honest statement about delivery is *"the revision that published me
holds my sizes"*, which is the manifest, which already exists.

**The blob-GC argument for pulling them into the attachment record does not
apply** — and this corrects the previous turn's reasoning, not its conclusion.
Renditions are not blobs in the material store (`t/<tenant>/blob/<sha256>`);
they are revision bytes under the revision's prefix, owned by that revision and
disposed of with it. They are never orphans, so there is nothing for an
attachment record to rescue.

**The line that matters, stated once.** Catalogued = **authored or received** —
uploaded, generated, drawn, captured. Not catalogued = **derived at publish**
from a catalogue item, content-addressed, owned by the revision that built it.
This epic has drawn that line once already, between editorial versions (the
recipe — the client's business) and delivery renditions (a consequence of
publishing, which the client should never see, never be asked about, and never
be able to get wrong). It is the same line.

**What this leaves.** Nothing to build. The risk was only ever that REQ-228's
"every asset is a catalogue item" would be read literally by a later
implementer and either flood the Library or quietly special-case the ladder
leaving no record of why. REQ-228 has since landed (`free_coded`), and the
separation held — so the line above is recorded here as the reason it held,
rather than as work.
