## The core problem, confirmed

`surfaceFillOf` (`extract.ts:343`) walks the ancestor chain compositing **`backgroundColor` only**. A gradient panel (`bg-gradient-to-br from-slate-100 to-slate-200`) is a `background-image` sitting on a *transparent* `background-color`, so the composite skips right past it and records the band colour (#e8dfd3). And `gradientCss` (`extract.ts:567`) is captured **only** when `background-clip: text` — i.e. text fills, never panels. So a gradient panel is invisible to capture, has no way to be authored, and has no diff axis. A render-only fix would produce a *false match* (both sides read the band), exactly as the ticket warns.

## The three-part change

**1. Capture** (`extract.ts`) — add a `surfaceGradient` sibling to `surfaceFillOf`. Walk the same ancestor chain, but at each node read `backgroundImage` and test for `gradient(` **without** the `clip === 'text'` gate (that gate is what currently restricts gradients to text fills). Return the raw gradient CSS of the first painting ancestor, distinct from the composited solid `surfaceFill`. The existing text-fill `gradientCss` path stays untouched — this is a parallel field for panel backgrounds.

**2. Framework** (`text-style.ts` / `row.ts`) — a `surfaceGradient` treatment on the card/panel. Reuse `TextRunGradient` (`{ angleDeg, stops }`) verbatim, and reuse `resolveColor` per stop so each stop is absolute-or-overlay (`#hex` literal OR `var(--color-role)`) — this satisfies the [[absolute-values-palette-is-overlay]] rule the ticket points at (REQ-58 T11). I'd factor `resolveGradient`'s stop-rendering so the panel path emits `background-image: linear-gradient(...)` **without** the `background-clip: text; color: transparent` tail that the text-fill variant appends. Rendered as the `fc-band` / card `background`.

**3. Diff** (`values-diff.ts`) — a `surfaceGradient` axis mirroring the existing `gradient` axis (`:1785`). Reuse `normalizeGradient` + `gradientsMatch` + `stopsMatch` as-is. Wiring is the known 5-spot pattern: `ValueElement` field, `DeltaProperty` union, `PROPERTY_KIND` → `'gradient'` tier, the raw-run→element projection, and the comparison block.

## One design question before I'd build

The ticket says "distinct from the composited solid `surfaceFill`." Worth deciding now: when a panel has a gradient, does `surfaceFill` still record the composited solid (the gradient's *average*, roughly) **as well as** `surfaceGradient`, or does `surfaceGradient` supersede it? I'd lean toward capturing **both** and having the diff prefer `surfaceGradient` when present (falling back to `surfaceFill` when absent) — that way a gradient-vs-solid mismatch surfaces as a real delta rather than one axis going silent. Sensible?

That's the whole shape: a capture + framework + diff triple, each reusing machinery that already exists for text-fill gradients and for `surfaceFill`. Nothing here is speculative.
